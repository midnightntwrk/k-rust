First-principles project report · 2 September 2026

Where K-in-K2 stands

K-in-K2 is building a trustworthy Rust product around formal language definitions: inspect them as typed data, transform them safely, observe their behavior, search their executions, and use those capabilities for semantic mutation testing and execution-pattern matching. The portable product core works. A narrow native path also works. The remaining work is chiefly about proving that native results are complete, traceable, and safe enough to authorize production decisions.

Executive view

The shortest accurate explanation

The project is past the “paper design” stage. Its backend-neutral contracts and Rust implementations are substantial and tested. It can also compile and execute a deliberately small KRS-authored rule through k-rust and recover a positive state/path witness. What it cannot yet do is turn arbitrary native success, empty search results, or unlinked source metadata into a trustworthy production receipt.

What works now

  • Deterministic portable identities, canonical data, artifact ingress, typed patching, pattern evaluation, receipts, caches, replay, and reporting.
  • Exact-pin KRS → k-rust structured compilation for selected fixtures.
  • Positive bounded state, path, pattern, and pattern-path witnesses.
  • Ordered branch-local committed-rule observations.
  • Fail-closed handling of unknown, bounded, cancelled, unsupported, or unproven outcomes.

What does not work at an accepted production level

  • Full qualification of every KRS form the product intends to use.
  • End-to-end source provenance that survives into k-rust’s native provenance objects.
  • Proof that an empty symbolic result means “nothing exists” rather than “the search stopped.”
  • A checked proof that frontend lowering preserved the required relation.
  • Qualified K-authored discovery/compiler and independent evaluator integration.
  • Hard resource isolation and the sealed issuer that would authorize production receipts.
Bottom line: development is not globally blocked. The project can continue building and testing positive, bounded functionality. Final native acceptance is blocked because the system cannot yet prove provenance, completeness, lowering correctness, isolation, and issuer prerequisites together.
From first principles

What problem is this project trying to solve?

A programming-language definition is more than source text. It contains syntax, types, configuration cells, rewrite rules, claims, conditions, and metadata. K-in-K2 wants to treat that definition as typed, identity-bearing data that a product can inspect and transform without losing meaning or silently guessing.

Product goal 1: execution-pattern matching

Observe semantic events on one execution branch and answer questions such as “did rule A occur before event B?” The product must preserve branch order, bindings, and uncertainty. A truncated search cannot be reported as a definite no-match.

Product goal 2: semantic mutation testing

Generate controlled edits to a language definition, apply each mutation atomically, run a corpus, and report whether behavior changed. Coupled edits must apply as one transaction, and every result must be traceable to the original definition and exact mutation.

The shared foundation

Both goals need stable semantic identities, source provenance, typed patch paths, deterministic serialization, validation, backend execution, honest search completeness, resource isolation, replay, and machine-readable receipts. Most of the backend-neutral form of this foundation has been implemented in Rust. The open work is connecting it to native K execution with evidence strong enough for production decisions.

Important historical distinction: the old K-in-K repository was a partial 2018–2020 experiment that expressed parts of K’s frontend in K itself. K-in-K2 preserves the metaprogramming/product goals, but the active implementation is a modern Rust-based portable core plus a new KRS/k-rust native path. It is not an attempt to revive the retired Java/Haskell/OCaml-era stack.
Architecture

How a definition reaches execution

Think of this as a compiler pipeline surrounded by an evidence and orchestration product. KRS supplies the authoring language and typed compiler stages. k-rust supplies the K frontend and execution/search backend. K-in-K2 supplies portable contracts, validation, product behavior, and rules about what evidence is strong enough to accept.

01 · AUTHOR

KRS Rust source

Typed macros and Rust items describe sorts, terms, cells, rules, and claims.

02 · COLLECT

Descriptors

KRS reparses exact authored regions and collects a deterministic package theory.

03 · CHECK

Semantic IR

Names, sorts, rules, and terms are resolved into checked semantic data.

04 · LOWER

Definition IR

A target-neutral structured definition and source-origin sidecar are produced.

05 · ADAPT

k-rust model

KRS maps Definition IR into k-rust’s native structured frontend representation.

06 · EXECUTE

KORE/backend

k-rust prepares, lowers, compiles, executes, proves, or searches the definition.

07 · DECIDE

K-in-K2 product

Adapters produce typed witnesses, receipts, cache records, replay, and reports.

KRS owns

The Rust authoring language, source collection, Semantic IR, Definition IR, and the structural adapter into k-rust.

k-rust owns

The K frontend/backend engine: preparation, lowering, compilation, execution, proof, search, observations, and primitive provenance storage.

K-in-K2 owns

Portable semantics, mutation contracts, adapters, validation policy, receipts, cache/replay, worker orchestration, reporting, and sealed acceptance.

Why KORE appears in the pipeline
KORE is K’s lower-level Matching Logic representation. Human-friendly language-definition constructs are transformed into KORE declarations and axioms that execution and proof backends consume. Producing parseable KORE proves useful transport, but it does not by itself prove that the transformation preserved all required semantics or provenance.
Evidence model

“It ran” and “we may trust it” are different claims

The codebase deliberately uses a proof ladder. A lower rung is still useful, but it cannot be relabeled as a higher rung merely because a test passed or a JSON receipt has the right shape.

Blockers

What prevents the key milestones?

The blockers are deliberately assigned to the component that can actually resolve them. Some are ordinary local implementation work. Others require new upstream evidence APIs or host-level authority that this repository cannot manufacture.

K-in-K2 / KRS qualification

Incomplete selected-surface qualification

The inventory is closed, but most selected forms do not yet have an exact continuous fixture. Negative structured failures also need runtime proof. Until this closes, KRS is not accepted as the complete authoring surface K-in-K2 intends to use.

Blocks: full NR-07Q and therefore NR-07I.

KRS · KRS-BRIDGE-001

Provenance sidecar is not connected to native carriers

KRS knows where authored nodes came from, and k-rust has native provenance structures. The adapter returns these as separate worlds. It does not prove that a KRS source node became a particular native term, production, generated rule, or final KORE entity.

Blocks: provenance-complete receipts, portable emitting-sentence provenance, and production authority.

k-rust · KRUST-UP-003

No explicit proof of successful search exhaustion

k-rust reports positive witnesses and several stop reasons. But ResultBound has no retained frontier or unvisited-work count, and there is no explicit Exhausted record. Therefore an empty result cannot prove absence.

Blocks: exhaustive no-match, finite not-reached, complete denotation, and symbolic absence claims.

k-rust · KRUST-UP-004

No checked lowering proof and registered checker

A compiler successfully producing KORE or executing a result is operational evidence, not a proof that the lowering relation was correct. The project requires a versioned proof artifact bound to exact source/output/profile identities and an independent checker.

Blocks: checked native validation and final production authority.

K-in-K2 · after NR-07Q

K-owned discovery/compiler/evaluator not qualified

The desired product must use K-produced mutation sites and joined tuples rather than a host-side Cartesian substitute. Its pattern compiler and independent evaluator also need separate conformance subjects and receipts.

Blocks: NR-07I and the compiler/evaluator prerequisites of production issuance.

Host/product environment · NR-04

No delegated hard isolation authority

The design requires one fresh child per attempt with enforced wall time, resident memory, swap, process count, output bytes, and writable-disk quotas. The current agent sandbox cannot supply a delegated cgroup-v2 subtree and quota-backed writable root.

Blocks: trustworthy campaign execution and final native readiness.

K-in-K2 · final integration

Production issuers intentionally remain sealed

Even schema-valid evidence must not create authority until every prerequisite validates together: pins, provenance, lowering, completeness, compiler, evaluator, execution profile, and isolation. Constructors remain unavailable by design.

Blocks: publishing native mutation/materialization or oracle outcomes as authoritative.

Scope control

Compatibility fixes are not authority

The aligned k-rust adds direct complete-cell handling, semantic downcast projections, Rust 1.88 support, and better parser behavior. KRS still retains some compatibility lowerings. These fixes improve feasibility but do not solve provenance, exhaustion, or checked lowering.

Blocks: nothing new by itself; prevents overclaiming what the repin achieved.

Recommended work

The shortest credible path forward

The best local sequence is to finish qualification before building product integration on top of an unstable surface. Upstream and environment work can proceed in parallel because those blockers are independent.

Finish NR-07Q positive rows

Add exact current-pin tranches for the remaining selected forms: declarations, imports, rules/claims, conditions, sequences, sets, attributes, configurations, and backend execution.

Add continuous cell/collection routes

Carry one KRS-authored cell artifact and one heterogeneous List/Map artifact continuously through collection, both IRs, adaptation, preparation, compilation, and KORE reparse/execution.

Run structured failures

Prove undefined labels, dangling variables, unsupported host expressions, initializer drift, and adapter-specific fields stop at the correct stage with typed diagnostics and no output.

Accept full NR-07Q

Audit the complete 36-row inventory. Accept only the declared selected surface; retain every named gap and SidecarOnlyMissingBridge boundary.

Build NR-07I

Integrate K-produced discovery sites/joined tuples, the K-authored pattern compiler, and an independently qualified evaluator as positive-only evidence.

Land upstream evidence APIs

Implement the KRS provenance bridge, explicit k-rust search exhaustion/frontier accounting, and a checked lowering proof/checker.

Implement NR-04 isolation

Provide delegated cgroup-v2 and disk-quota authority, fresh workers, closed stop mapping, durable publication, and replay-before-acceptance.

Unseal NR-07 and audit NR-08

Only after all prerequisite receipts validate, expose the production issuer and run an independent final audit over exact pins and profiles.

Can run in parallel

  • Remaining NR-07Q local tranches.
  • KRS provenance-bridge design and implementation.

  • NR-04 host/product authority planning.

Must remain sequential

  • Full NR-07Q acceptance before NR-07I.
  • NR-07I qualification before final NR-07 issuance.

Glossary

Terms used in this report

K Framework
A system for defining programming-language syntax and semantics as rewrite rules, then executing or proving properties about programs.
KRS
A Rust-based language and compiler for authoring K definitions as typed Rust constructs.
k-rust
The Rust K frontend/backend engine used to prepare, lower, execute, prove, and search definitions.
IR
Intermediate representation: structured compiler data between source code and backend form.
KORE
K’s lower-level Matching Logic representation consumed by execution and proof backends.
Provenance
Evidence that says where a semantic node came from and how generated nodes relate to authored source.
OriginMapping
KRS’s deterministic sidecar mapping from authored/Definition-IR origins to structural native destinations.
Continuous route
One exact artifact passes through every stage in one chain; results from separate tests are not spliced together.
Positive witness
Concrete evidence that something was found: a state, execution path, match, or rule observation.
Exhaustion
Evidence that all reachable work was visited. Required before absence can be concluded.
Fail closed
Missing or uncertain evidence yields unknown/not-proven and publishes no authority-bearing result.
Receipt
A machine-readable record binding an operation and its outputs to exact inputs, identities, versions, and profiles.
Production authority
Permission for validated native evidence to create an accepted artifact or decision rather than only an experimental result.
Sealed issuer
A constructor deliberately inaccessible until all required evidence has validated together.
NR-07Q
The full selected KRS surface qualification milestone.
NR-07I
Positive-only K-owned discovery/compiler/evaluator integration after NR-07Q.
NR-04 / NR-07 / NR-08
Hard isolation; final production authority; and final independent native-readiness audit, respectively.
Exact pin
An immutable Git commit and tool/profile identity used to make evidence reproducible.
