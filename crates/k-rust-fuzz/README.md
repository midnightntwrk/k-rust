# k-rust-fuzz

`k-rust-fuzz` crafts concrete input values for a given program under a given K specification, so that an execution of that program reaches a stated target: a named rule, a pattern, a client observer, or a difference between a baseline and a mutant definition.
It is built to steer values with the specification's state space (its rules, guards, coverage and path conditions), and it never generates programs.
Generating whole programs is out of scope: random or grammar-driven program generation produces nothing a human would write, and the author (a person or an LLM) already writes the program.
Crafting inputs that reach a target is in scope: the author marks the program's input holes beside the unmodified program (typed spans of data, such as an `Int` literal), names the target, and the crate chooses hole values, runs the program with k-rust, and reports.
The report holds either a witness that a concrete re-run confirmed (the hole values, the initial and final configurations, the outcome), or a bounded "no witness found" with the budget, the cases run, the coverage reached and the outcome counts, which is never a proof that no witness exists.

The library builds without k-rust's `cli` and Z3 features; the `z3` feature enables the solver-backed proposer (solve).
The design is in the fz26 programme's `ARCHITECTURE.md`; the rustdoc of each item cites its section.

## Outcome classes

Every case receives exactly one `OutcomeClass` (ARCHITECTURE 5.3).

| Class | Meaning |
|---|---|
| `hit` | a clean leaf reaches the target and confirmation agrees; reported as a property failure for a negated property |
| `miss` | the run ended naturally on every leaf without reaching the target |
| `stuck` | a clean leaf is an abnormal stop (stuck, but not a natural end), and no leaf reaches the target |
| `reached-unfinished` | under `run-to-completion`, the target was reached on a leaf that is clean except for its halt, which is neither a natural end nor an unsupported halt (an abnormal stop, an undefined step, a bound, a timeout or a cancellation); and no leaf is `unsupported` |
| `depth-bound` | a `depth-bound` or `breadth-bound` halt |
| `work-bound` | a `work-bound` halt; deterministic, distinct from timeouts |
| `timeout` | a `timeout` or `cancelled` halt, a cancellation or step deadline that ended the run as an `Err`, or the per-case safety limit |
| `undefined` | a `trivial` halt: an undefined step |
| `unsupported` | `unsupported-hook`, `simplification-error`, `indeterminate`, `vacuous` after depth 0, an `Err` result other than a clock stop or a refused state, a leaf unclean for a reason other than its halt, a target-reaching leaf that is not clean (and not `reached-unfinished`), or, for a rule or pattern target with `run-to-completion` and `data-end`, a reaching natural end that is not data |
| `rejected` | a hole value violates its sort or constraints, does not round-trip through the program's syntax, or the backend refuses the initial state (`vacuous` at depth 0, or an invalid state) |
| `baseline-incomplete` | differential only: the baseline's set of ends is incomplete (ARCHITECTURE 4.3) |

When a result has several leaves, the case takes the first of these that some leaf has:
`hit`, `unsupported`, `reached-unfinished`, `timeout`, `work-bound`, `depth-bound`, `undefined`, `stuck`, `miss`.
`reached-unfinished` applies only when no leaf is `unsupported`.
A leaf that is unclean for a reason other than its halt (an implementation-chosen value, a contradicted claim, remaining constraints, a term that is not ceil-free, a stack stop, an undecided solver answer, and so on) is `unsupported` whether or not it reaches the target, because it may hide a reaching state, so `miss` or `stuck` would be unsound.
`rejected` is decided before execution, and `baseline-incomplete` by the differential judge before the mutant's leaves are looked at; neither is chosen by precedence.
A stuck, truncated, timed-out, undefined or unsupported run is never reported as a pass.

A rule or pattern target with `run-to-completion` asks for a witness that becomes a test: by default (`data-end`, on unless the campaign file says `data-end = false` or the command line `--no-data-end`, `Target::data_end` in the library) its hit also needs the reaching natural end to be data, as every end the differential target compares is (below), so that the test's end can be compared with a mutant's. A reaching natural end that is not data, such as one holding an unevaluated function application, is `unsupported`, and the witness's `clean-leaf-facts` name `end-data`. A negated property is exempt: its counterexample is decided by its match, whatever the end's function applications denote. The command line refuses `data-end` on a differential target.

A pattern (a target's or the `normal-end-pattern`) whose `requires` reads a variable that its configuration does not bind, such as `<k> .K </k> <state> M </state> requires R >Int 0`, is refused by `Campaign::new`, naming the variable. Such a variable is almost always a misspelling (of a variable the configuration names, or of a key), and a leaf's match then leaves a condition over it, which a leaf judgement decides only when it is trivially true or false (`R ==Int R`, `... orBool true`) and otherwise classes `unsupported`. The refusal is a rule of use, not a proof that no leaf matches: it refuses the few such patterns that some leaves would match, which are better written without the variable. `krust krun --pattern` answers such a match with the remaining condition in its result instead.

A pattern target (a negated property included) also reports `totals.pattern-body-matches`: how many end leaves of the cases inside the determinism contract matched the pattern's configuration without its `requires`, whatever the `requires` gave there (true, false or undecided), each leaf on its own as targets are matched; a leaf counts when it is clean apart from the target's own undecided verdict: a leaf unclean for another reason (an implementation-chosen value, a contradicted claim, a state that is not ceil-free) is left out even when its configuration matched, as every verdict of the campaign leaves it out, so a semantics whose every end is unclean also gets 0 and the warning (its `unsupported` reasons say why). When no executed case had one, a warning (`pattern body: …`) says that the pattern may name a cell, key or value no end holds, such as a misspelled key: a negated property then holds vacuously, which its `miss` cases alone cannot tell from one that holds. The configuration's own match only informs: its verdict never makes a leaf `unsupported`.

### Natural ends

`miss` against `stuck`, a run-to-completion hit and a differential end under `run-to-completion` all rest on the natural end: a clean `stuck` leaf on which the program finished (without `run-to-completion`, any clean decided `stuck` leaf is a differential end, a natural end or an abnormal stop alike).
A campaign's `normal-end-pattern` (`CaseOptions::normal_end_pattern`) decides it when given; otherwise the default reads the `<k>` cells:

- `single-k`, for a configuration whose `<k>` cell is not under a multiplicity cell: the leaf matches `<k> .K </k>` with the rest of the configuration free;
- `every-k`, for a configuration whose `<k>` cell lies under a cell of multiplicity `*` or `?` (threads, as in SIMPLE or KOOL): every `<k>` cell of the leaf holds `.K`, and a leaf with no `<k>` cell left (every thread finished and was removed, `<threads> .Bag </threads>`) is a natural end too, provided the initial configuration had a `<k>` cell (otherwise no thread ever ran, and the program may have stopped elsewhere: the leaf's natural end is undecided). A leaf with one thread's computation left is an abnormal stop (a deadlock or a stuck thread).

The report's `normal-end` records which applied to each definition, and when `every-k` decided cases, a warning (`every-k: …`) says so and how to override it.
The default reads only the `<k>` cells, so a semantics that removes a thread on error, or whose finished threads keep a value in `<k>`, needs its own pattern (for example over an error cell).

### Why a case is unsupported

Every `unsupported` and `baseline-incomplete` case has a reason, counted in `totals.unsupported-reasons` and `totals.baseline-incomplete-reasons` (each sums to its class's count).
A case is counted once, under the first of its reasons in the order of `exec::UnjudgedReason`, which runs from facts of the run (an `Err`, a bound, a halt) through facts of a leaf (`not-ceil-free`, `undecided-state`, `implementation-chosen-value`, …) to facts of a judgement (`natural-end-undecided`, `reached-undefined-step`, `reached-end-not-data`, `definition-not-confluent`, `mutant-end-not-data`, …).
A definition whose full critical-pair check reports findings has no data end at all (below), which is known before the first case: a campaign that reads data ends on it runs no case and ends `not-comparable` ([Not comparable at setup](#not-comparable-at-setup)). The reason `definition-not-confluent` keeps its place in the reason order, but no case of a campaign is counted under it any more.
The no-witness statement, and the summary of a report with a witness, list the reasons, largest first, with the largest one's remedy (`UnjudgedReason::remedy`); a remedy only suggests actions that keep verdicts sound (a bound, a pattern, another program or hole range), never a change to the definition's claims, and names options by campaign key and command-line flag; a `not-ceil-free` case also adds a warning naming the partial function whose application a leaf holds.

### Incidental findings

A rule missing from the semantics, or a partiality its author did not intend, is invisible to every target: no mutant of an absent rule exists, a baseline and its mutant get stuck alike, and coverage lists the rules that exist.
So the report keeps the first case of each of the classes `stuck` and `undefined` as information, `incidental.stuck` and `incidental.undefined` (`report::Incidentals`), whatever the target; the key, and each class's entry, is absent when no case had the class.
The classes are the classes of one run (above), under the normal end the report's `normal-end` names: `stuck` is a clean, decided `stuck` leaf that is not a natural end (under `every-k`, some `<k>` cell still holds a computation), `undefined` a clean undefined step (a rule applied whose result is undefined there; its leaf is the configuration before the step, and it is no end), each with no leaf of higher precedence.
The run is the semantics under test's: in a rule, pattern or observer campaign the case's own, so the finding's class is the case's class; in a differential campaign the baseline's run of the case (all paths), classed alone, whatever the pair's class.
A stop or undefined step only the mutant has is never a finding: without `run-to-completion` it is a kill (an added or removed end, below); under `run-to-completion` an abnormal stop is no kill, and the pair's class (the mutant's) reports that the sides disagree.
A case that ends the campaign with a witness gives no finding; its witness shows its runs.
Each finding holds the case's number (counted from 0), its hole values, how many leaves the run has (`leaves`) and which one is the finding (`leaf`), its depth (`steps`; an undefined step is the step after it), the first item of each `<k>` cell that holds one, in order, as K text (`k-heads`: under `every-k` a stuck configuration is stuck in every thread, so each is where a thread stopped, a thread waiting for another included; for an undefined step, the items before the step), the leaf's configuration as KORE, the `krun` line that re-runs that run (on all paths for a differential baseline), and, for a differential baseline's run, `baseline-run: true`, which the summary line also states ("in the baseline's own run on all paths (not the pair's class)").
`krun` reports an undefined step only when every path of its run takes one; when another path of the finding's run does not, the krun line says so in its trailing comment (one comment, after the max-work note when there is one) with the finding's leaf and step, and the summary line says the finding is on one of several paths.
Only findings whose run is inside the determinism contract are kept, so a finding reproduces (in a differential case that run is the baseline's: a clock or stack fact of the mutant's run alone does not suppress it); keeping one changes no class, case or budget, and nothing is re-run or shrunk.
The summary prints one line per finding, worded as information: a K semantics often leaves a program stuck on purpose (an ill-typed program, a division by zero the language leaves without meaning).

## Hole declarations

A hole replaces a span of the unmodified program, addressed by `program`, an optional `line`, `find` (a text that occurs exactly once in the addressed line or program) and `literal` (the hole's literal, which occurs exactly once in `find`), or by `line`, `column` and `literal`.
Instead of a unique `find`, `line` and `column` may place the literal: `column` is the one-based column, counted in characters (a tab is one), of the literal's first character on that line, and `find` is then left out (or is the literal itself). This addresses a literal that also occurs nearby inside other text, such as the `3` of `(i32.const 3)`, whose `i32` holds a 3: give the line and the column of that `3`, with `literal = "3"`.
The text at the span is the hole's anchor value, the first value the explicit proposer tries.
A configuration variable (`$NAME`) can also be a hole, addressed by its name; so can a free variable of a KORE initial pattern, in the library API.
The declaration format of ARCHITECTURE 2.2, with the program `transfer.imp` unchanged:

```toml
[[hole]]
name = "AMOUNT"
sort = "Int"
program = "transfer.imp"
line = 4
find = "amount = 250;"
literal = "250"
range = { min = 0, max = 1000000 }
```

In the library, the same hole is a `HoleDecl` with a `HoleLocation::Span(SpanAddress { .. })` and its `Constraints`.

A span hole can take only the values whose printed text the grammar reads back, at the hole's position, as that value: every case is round-trip-checked, and a value that reads as something else is `rejected`.
For an `Int` hole the difference is the sign. Digits read back wherever the anchor's did, but whether `-` followed by digits reads back as a negative integer depends on the grammar there: a signed literal token (`INT-SYNTAX`) reads it as the value, while a grammar of unsigned literals (`UNSIGNED-INT-SYNTAX`, as in IMP and SIMPLE) reads a unary minus applied to the magnitude, or does not parse it.
So `Campaign::new` probes each `Int` span hole whose range admits a negative value (and whose anchor is not negative) with two admissible negative values of different digit strings, through the same round-trip check at the same position: the one nearest zero (`-1`, or the range's maximum) and the one of greatest magnitude with at most three digits (`-999`, or the range's minimum).
Only when every probe is refused do the hole's effective bounds start at 0.
The probes establish that those values cannot be written there, not that no negative value can: a grammar may spell one negative literal as a terminal of its own (a production `"-1"` beside signed literals) or read a sign before some digit strings only, and two probes of different lengths make such a collision unlikely to narrow a hole, but do not rule it out.
Narrowing is an economy of generation, not a judgement: generators, the dictionary, the climb, the corpus, the solve proposer and shrinking use the effective bounds, while the declared constraints and the round-trip check still judge each case, so an explicit negative value is still run and judged as before.
The report lists every narrowed hole in `identity.effective-constraints`: the declared and effective constraints, a reason code (`negative-not-read-back`), the side whose grammar refused, and each probe with its outcome (`reads-as`, with the term the position held instead as K text, or `does-not-parse`).
A warning says the same in words, with the parser's message for a probe that does not parse, and what to do.
A declared range that holds only negative values is refused at such a hole when every probe is refused, since no probed value of it can be written there.
Configuration-variable and KORE-template holes, holes with `choices`, and other sorts are not narrowed: a binding is parsed whole at its variable's sort, a template's values are never printed, and a choice set is the author's own list.
To give such a language a negative input, write the program with a unary minus before the literal (`- 5`) and keep the hole on the digits; to silence the warning, declare `range = { min = 0 }`.

A hole is data, and `Campaign::new` enforces it (ARCHITECTURE 2.4).
It refuses a hole whose sort is `K`, `KItem`, a cell sort, or a user sort in the closure of the program start sort's productions (a sort in which programs are written, such as `AExp` or `Stmt` in IMP).
It accepts builtin and hooked sorts that have a generator (`Int`, `Bool`, `String`, `Bytes`, `MInt`), collections with declared element sorts, and user sorts outside that closure, such as transactions, events or records declared in semantic modules.
The rule applies to every sort a value of the hole's sort may contain: collection element sorts and the argument sorts of its constructors, transitively, so `List<Stmt>`, `List<K>` and a record holding an `AExp` are refused, and `KResult` and other K-internal sorts count as computation.
When the start sort is `K` or `KItem`, the closure is every non-hooked sort of the syntax module.
User token sorts such as `Id` are refused, because an identifier names a declaration of the program.
`allow_refused_sort` (`allow-refused-sort = true` in a campaign file) overrides a refusal, and the report records the override; the refusal itself says why the sort is refused and, where an override applies, names it.
The values of an admitted token sort are tokens, written `{ token = { sort = "Id", text = "n" } }` in a campaign file (`{"token": {"sort": "Id", "text": "n"}}` in JSON), in `choices` too; a plain string there is refused with that form.

## Differential target

A differential campaign (a mutant beside the definition) looks for an input on which the two definitions' sets of ends differ (ARCHITECTURE 4.3).
A side's ends on an input are its final configurations: each clean, decided `stuck` leaf, whether the program finished there (a natural end) or stopped mid-way (an abnormal stop); in both, no rule applies.
An undefined step (a `trivial` leaf) is no end: its configuration is reached but is not stuck, since a rule applies to it, and it has no successor, so the run's outcome there is undefinedness, which is no configuration (`krun` prints `\bottom`; `docs/compatibility.md`, "Undefined steps in proofs", "Trivial rule results"). A side whose every path takes one has no end at all.
A case kills the mutant by an *added end*, a mutant end that the baseline's complete set lacks, or a *removed end*, a baseline end that the mutant's complete set lacks: a baseline that stops where the mutant's step is undefined (a dropped guard on a division) is one.
Every compared end must be data, on both sides: built from constructors, injections, domain values, well-formed collections, and irreducible applications of overload heads (`k_rust_backend::data_term`).
An overload head is an `anywhere` production whose only equations are overload equations of the shape `g(p1, ..., pn) = inj(h(x1, ..., xn))`, each `pi` the variable `xi` or `inj(xi)` (SIMPLE's `_,_Exps` and `_,_Vals`), and roots no other equation; an application of it that no overload equation lowers (`_,_Exps(x = 1, inj{Bottoms,Exps}(.Bottoms))`) is a normal form, distinct from every other one.
A definition has data only when its full critical-pair check (run once per definition at campaign setup, about 0.03 s on SIMPLE and 0.2 s on WASM) reports nothing: an identification anywhere reaches other terms through every equation that tells them apart, so a definition with an unjoined pair or an overload premise violation has no data at all, and the campaign is [not comparable at setup](#not-comparable-at-setup). WASM's `test.md` is such a definition today (48 pairs the check does not join: 36 of `wasm-data.md`'s `unescape`, 8 of the `getOrDefault` lookups of `list-int.k` and `list-ref.k`, 4 of `sparse-bytes.k`), so its differential ends are not compared.
Each definition reads the ends with its own theory, so every compared end must be data in both definitions, each judged by its own (its own overload families, `anywhere` and function equations, and subsort order): a mutant that adds an overload member, an `anywhere` rule or a subsort below an overload argument is never killed through an end the change makes reducible.
A side that carries an implementation-chosen value or a contradicted claim (`total` or `preserves-definedness`), on a leaf or on its result's lists, is no evidence: the baseline is then `baseline-incomplete`, and a would-be kill of the mutant `unsupported`.
Under `run-to-completion` only natural ends kill.
A case on which the work bound stops the mutant while the baseline reached all its ends is `work-bound`; the no-witness statement counts those cases apart, with the most work the baseline needed in one of them, and says that the mutant may not terminate on that program (a mutant that turns a loop's decrement into an increment), without advising a larger `max-work`, since whether a run terminates cannot be decided. A case on which the bound stops the baseline as well is `baseline-incomplete`, and its advice to raise `max-work` stands.

### Not comparable at setup

When the campaign's judgement reads data ends (a differential target, or a rule or pattern target with `run-to-completion` and `data-end`) and a definition's full check reports findings, no end of that definition is data, so no case could kill (or hit), whatever the budget, bounds or values. `Campaign::new` decides this before any case: every run reports the outcome `not-comparable` with the definitions without data (`sides`) and a statement, runs no case, and the report lists every finding in `definition-findings`, with one warning per such definition (`definition-not-confluent (baseline|mutant): ...`). A negated property, a target without `run-to-completion`, and `data-end = false` read no data end and are unaffected.

Each finding says whether it is **genuine** or **undecided**. A pair is genuine only when the check exhibits a ground input with two normal forms (the `instance`): an instance of the overlap built from normal forms (no map or set keyed twice by one normal form), at which both equations apply by the evaluator's own rule (each matches, its `requires` evaluates to true, and no equation of the same head with a higher `priority`, `owise` the lowest, applies there; one whose condition is undecided counts as applying), and whose two reducts evaluate to different normal forms (k-rust's internal normal form). Evaluation of that input is then not uniquely determined, so the definition read by its normal forms (`M_NF`, as `k_rust_backend::data_term` reads it) is not a model, and k-rust's result for the input depends on the order in which it tries the equations: a defect to fix in the definition. This is not a claim that no model satisfies the definition (KORE keeps, for instance, injections from different source sorts apart by no axiom). The instance is searched among small terms of each variable's sort (integers 0, 1, -1, the Booleans, short strings, nullary constructors, empty and one-element collections, constructor applications over those, injections of a subsort's terms; at most 81 assignments per pair). Every other finding is undecided: *not shown to join*, which may be a limit of the check (a condition its solver-free reader does not decide, a collection its unifier gives up on) as well as a defect; do not rewrite a correct equation because of one. WASM gives 2 genuine pairs (`getOrDefault` at index `-1` in `list-int.k` and `list-ref.k`: on a one-element list the first equation gives the element, the second the default) and 46 undecided ones. Two different terms that would print alike (injections from different sorts) are written with each injection's source sort, `(t : Sort)`. Findings name each equation by its written position (`FILE:LINE:COLUMN`), and show the overlap, the two reducts, the conditions the check left open and the instance as K text. The summary groups findings by equation pair, genuine pairs first, and shows the first 5 pairs per definition; the report lists all of them.

A finding can be **assumed**, a premise the user states (for a pair, assumed joined): `--assume-joined NAME` (repeatable), the campaign file's `[options] assume-joined = [NAME, ...]`, `CaseOptions::assume_joined` in the library, with each `NAME` as the finding's `name` prints it (`FIRST,SECOND@POSITION`; a compiler-generated overload axiom, which has no written position, as `overload:GREATER:LESSER` with the K labels of its overloaded pair, each in `"` when it holds `,`, `:`, `@`, a quote, a backslash or whitespace (`overload:"_,__EXPS":"_,__IDS"`; the KORE names are accepted too); a rule part may also be any trailing part of the written path, the rule's unique id or its label, and a root pair may be named in either order). Every other finding that keeps a definition without data has a name too, so that each can be assumed: an equation at an evaluated hook that is not shown to agree with the hook (a hook pair, of which one name covers every equation of the hook's written meaning, or an equation at a hook with no written meaning) is `hook:EQUATION`, another equation the evaluator does not apply to every subject it describes `equation:EQUATION`, and a precondition row `precondition:EQUATION`, or `precondition:KIND:LABELS` when it names no equation (`precondition:no-least-common-overload:A:B`), each `EQUATION` a rule part as above. Such a finding is then read as resolved: the equation as agreeing with its hook or applied as written, the row as met. The data judgement then reads both definitions as if those pairs joined: when no other finding is left, the definition has data again. Every verdict of the campaign then holds for the definition read that way, not for the definition as written; that no program reaches the pair (WASM's indices are unsigned, so `getOrDefault` at `-1` is unreachable from WASM programs) does not change this, since the judgement reads the definition by its normal forms, and a genuine pair leaves some input with two whatever the inputs that reach it. The assumed pairs are part of the campaign's identity (`identity.options.assume-joined`, sorted), the report keeps their findings marked `assumed` with their verdicts (the summary's counts include them, then say how many are assumed and how many of those are genuine), a warning states the premise, and one more names each assumed pair that is genuine. An unprefixed name applies on each definition where it matches and must match the same equations (by unique id) on both; `baseline:NAME` and `mutant:NAME` apply on one definition. A name that matches no finding, more than one finding of one definition, or different findings on the two definitions is refused, and so is any name on a campaign that reads no data end. The overload data heads still come from the definition's load verdict, which withholds the claims an assumed pair's taint reaches, so an assumption can only leave fewer terms data than a definition in which the pair joins.

### How the sides run

The baseline runs on all paths and the mutant on the campaign's path mode, both as state sets (`result_modality: state-set`), which report the same final configurations as path sets without exploring the paths that converge on them (`docs/compatibility.md`, "Search results").
One mutant path cannot show what the mutant's other paths reach, so in the one-path mode a case whose one mutant path is complete, adds no end and misses some baseline end is decided by a second run of the mutant on all paths, whose work the case counts.
Each side of a witness lists every leaf's configuration with its halt (`final-configurations`, `halts`; every witness kind carries `halts`, and `--replay` compares them); the witness's `clean-leaf-facts` name the conditions its kind of kill rests on.
Re-entering a witness as a test takes the instantiated program and a `krun` line per side: every witness case with a program text carries `program` (the program with each span hole's K text in its span), and a differential witness carries `krun-command` for the baseline (strategy `all`, its directory left as `<definition-dir>`) and `mutant-krun-command` for the mutant (`<mutant-dir>`; strategy `all` for a removed end or the all-paths mode, `any` for an added end in the one-path mode). The summary of a differential witness prints the kind of kill, the program, each side's ends as K text (krs-unparse's pretty form; `krust krun` itself prints KORE; the first four ends of each side and the killing end wherever it lies, marked, with the count of leaves at an undefined step, which are no ends, and whose recorded configuration is the state before the undefined step) and the two `krun` lines.
The all-paths mode can refuse a kill the one-path mode takes: when a chosen value or a contradicted claim lies on another path than the killing one (on a leaf, or on the result's lists after a state-set merge), the all-paths result carries it and the case is `unsupported`, while the one path never met it and its end kills. Both are sound: the one-path kill rests only on its own path, which carries no mark, and the all-paths refusal is conservative, since it judges the result as a whole and a mark anywhere on it could stand for a path that differs in another model; it can only miss a kill.

## Library usage

The caller compiles the definition (`CompiledDefinition::from_artifacts` takes an in-process compilation, with the loaded definition's source table, and reduces it to what `krust kcompile` stores in a compiled directory, so that both give one definition), builds a `CampaignSpec` (the definitions, the program, the holes, the target, the case options, the proposers, the seed), and runs it:

```rust
use k_rust_fuzz::{Budget, Campaign, CampaignError, CampaignSpec, FuzzReport};

fn fuzz(spec: CampaignSpec) -> Result<FuzzReport, CampaignError> {
    let mut campaign = Campaign::new(spec)?;
    Ok(campaign.run(Budget::Cases(10_000), None))
}
```

`Campaign::new` validates the spec: a mutant is given exactly for a differential target, each definition's backend is built on its route, and the holes, their generators and the target are resolved.
It assembles and round-trip-checks the program with its anchor values, and returns a `CampaignError` for every refusal (a `find` or `literal` that does not occur exactly once, overlapping spans, an anchor that does not parse back, a refused hole sort, an unknown, ambiguous or refused target, and so on).

`Campaign::run` runs cases on the calling thread until the budget (`Budget::Cases` or `Budget::Work`) is spent, a witness is confirmed and shrunk, the rejection cap is reached, every assignment of the holes' finite domains has run, or the `CancellationToken` is cancelled.
When every hole takes finitely many values (its `choices`, a `Bool`, or a closed integer range of an `Int` or `MInt` hole, as generated, so a narrowed range counts from 0) and their product is at most 4096, the loop records which assignments have been tried, and no assignment is tried twice: a case's outcome is a function of its assignment, so a proposal that repeats one is not run and is replaced by the next untried assignment in a permutation of the domain drawn from the campaign seed, credited to the same proposer (which observes it as its own case; a climb or corpus proposer thus learns from the replacement, not from the repeat it proposed). Once each assignment has been tried, after exactly as many cases as the domain has assignments when every proposal lies in it, the campaign ends without a witness and its statement says `Domain exhausted` with the number of assignments. A value outside the domain (an explicit assignment outside the choices or the range) is run and not counted. A case outside the determinism contract (a timeout) counts as tried.
The explicit proposer tries the anchors first, then the author's assignments; the other proposers are mixed by a deterministic schedule seeded from the campaign seed.
This build provides blind generation (`ProposerKind::Blind`), the dictionary (`ProposerKind::Dictionary`), the climb (`ProposerKind::Climb`) and the corpus (`ProposerKind::Corpus`), below: guard harvesting, which draws each hole, with probability 1/2, from the literals of the guards and left-hand sides of the target and of the rules at most two rule-graph edges before it, of the equations their guards call, and of the higher-priority rules an `owise` rule competes with, plus or minus 1 to 3 and negated (ARCHITECTURE 8.3; the rustdoc of `proposers::dictionary`). `Campaign::new` refuses a proposer the build does not provide.
The default `ProposerConfig` weighs blind generation alone; a positive `dictionary` weight (in the library, the campaign file's `[proposers] weights` or the bindings' `proposers.weights`) adds the dictionary, and the report then records its parameters (`identity.dictionary`).
It also provides the climb (`ProposerKind::Climb`) for rule and observer targets: targeted hill climbing, which keeps the best-scored `miss` case and proposes typed moves of one or two of its holes (integers by `±2^e` with an exponent that grows after an improvement and shrinks after a rejection, Boolean negation, single edits of strings, byte strings and collections, constructor swaps), preferring the holes whose values the scored guard read, and spends at most half of the cases, and of the work up to its last case's work (ARCHITECTURE 6.4, 8.4; the rustdoc of `proposers::climb` and `score`).
A rule target's case is scored by its rule-graph distance to the target and the branch distance of the guard that stopped it, read from the condition records the backend reports (`collectConditions`), which only a campaign with the climb, the corpus or the solve proposer requests; an observer target's case by the greatest progress (`ObserverVerdict::Progress`) its observer reported.
A positive `climb` weight needs a positive `blind` or `dictionary` weight beside it, and the report then records the climb's parameters (`identity.climb`); pattern and differential targets are refused with the climb.
A campaign whose proposers score its cases (the climb or the solve proposer) reports `totals.best-score`: how many `miss` cases were scored and the best score among them, the earliest case on a tie, with its level (the rule-graph distance; absent when no rule-graph path reaches the target) and guard distance (an exact fraction `N/D`, 0 when the guard holds), which the summary prints, so that a reader sees how near the guided search came; it is `null` when no proposer scores. The best case may be one outside the determinism contract (a `miss` decided with a solver `unknown` on a clocked solver, counted in `totals.outside-determinism`), as the schedule observes those cases too.
It also provides the corpus (`ProposerKind::Corpus`) for every target kind: coverage-guided mutation, which keeps each `miss` case that reached a rule (in coverage `applied` or `matched`) no earlier `miss` case reached, or applied a rule a number of times in a bucket (each count below 16, then 16-31, 32-63, and so on) no earlier `miss` case applied it in (k-rust's applied counts, `collectCounts`, which a campaign asks for only when it weighs the corpus), or, beside the climb or the solve proposer (which score cases), that scored better than every earlier case, and proposes one or two typed mutations of a kept case (the newest three times in four): a collection hole replaces, inserts, deletes or appends one element, keeps a prefix, or crosses over with another kept case, and every new value or element is a harvested literal of its sort (the dictionary's harvest, which here also fills collection elements), a fresh draw, a nudge of the current value (for a record, one field, at any depth, so one field of one transaction in a list), or a splice from another kept case (ARCHITECTURE 8.5; the rustdoc of `proposers::corpus`).
It pays off on sequence-shaped holes, such as a `List` of transactions processed in a loop, whose progress lives in cells that neither the rule graph nor the climb's score sees; it spends at most half of the cases (and of the work, up to its last case's work), needs a positive `blind` or `dictionary` weight beside it, and the report then records its parameters (`identity.corpus`).
Where every step of a loop fires the same rule, the applied counts make a step more progress: a list of keys in a window, consumed by one rule, is followed one key at a time (the tally). The counts cannot tell progress from noise: where another rule's count follows the data too (work after the loop over the input left over, such as a map lookup per remaining item or a rule that drains the rest), a mutation that only lengthens that leftover also reaches a new bucket, is kept, and becomes the newest entry; on the tally with such a rule the corpus still reaches depths main never does, but at a fraction of the seeds (depth 16 at 1 to 4 of 10 held-out seeds instead of 9 or 10). Neither demoting count-only entries nor keeping only new maxima helped there (`research/stall-benchmark.md`, FZ-17 fix round). Where each step's values must also match the state (a balance, a nonce inside a record), one mutation rarely makes a whole valid step and the harvest holds none of the values; there the corpus gains little alone, and the run-time literals below supply the values (`research/stall-benchmark.md` in the fz26 notes, the bank).
The climb and the corpus also draw run-time literals (ARCHITECTURE 8.3; the rustdoc of `proposers::runtime`): for a rule target, their campaigns record the condition entries of the rules whose guards the dictionary's harvest reads (the target, the rules at most two rule-graph edges before it, and the higher-priority rules they compete with), and a case's pool is the comparisons in each such guard's last refuted entry that refuted it (below nodes that refuted it, so not under a disjunction that held or an undefined node), with the two values the run compared, such as a transaction's amount and the running balance in `A ==Int B`; a rule whose records the backend truncated gives none, and the target's comparisons come first (at most 64).
A proposal from a case whose pool is not empty is, with probability 1/4, a change from it instead of a move or a mutation: one occurrence of a compared value in the case's holes, at any depth (one field of one record in a list), takes the value nearest the other operand that passes the comparison (`B` for `==`, `<=` and `>=`, `B - 1` for `<`, `B + 1` for `>` and `=/=`; a `String` equality the other string); drawn by side of a comparison, then occurrence, and the climb proposes each change at most once from the same best case.
The climb changes its best case so; the corpus a kept case, and, with probability 1/2, its own last case when that was a `miss` with a pool, up to two such follow-ups after a mutation, so that a transaction appended with a wrong nonce is repaired though it reached nothing new.
The values belong to the state of the case that compared them, so the dictionary, which builds each case from nothing, does not draw them; a campaign without the climb or the corpus records no conditions and its cases do not change.
The report records the parameters (`identity.climb` and `identity.corpus`: `runtime-probability`, `follow-probability`, `follow-depth`, `max-comparisons`, `runtime-condition-rules`, and the climb's `runtime-guard-radius`).
With the `z3` feature (native builds; the `cli` feature implies it) it also provides the solve proposer (`ProposerKind::Solve`) for rule targets (ARCHITECTURE 8.6; the rustdoc of `proposers::solve`).
Every `miss` case that entered and refuted a guard on the target's keyed chain (the target, its predecessors whose right-hand side keys `<k>`, theirs, up to 8 edges; the cases of a solving campaign record those rules' condition entries) gives a query: the case's values with the `Int` and `Bool` holes whose values that guard read made symbolic (holes of a sort hooked to `Int` under another name stay concrete).
The proposer keeps the unsettled queries (at most 64, one per rule, symbolic holes and other holes' values), ranked by the guard's distance to the target along the chain, then its guard distance; when the score has not improved for 8 cases, it asks the best-ranked one.
It runs the configuration under strategy `all` on fresh backends of its own, on a thread of its own, within 4 times the case's work plus 64 states, and asks `Backend::get_model` for a model of the constraint of a leaf whose path applied the blocked rule (up to 4 leaves), with the holes' declared constraints conjoined.
A model is a candidate case like any other: admissible values, the round-trip check, and confirmation on a fresh backend.
Every query is asked once: whatever it answers (a candidate, no path, no model, an undecided model, a run stopped by a cancellation or the per-case safety limit, which is charged at least 1 work), it is settled and the next pending query is asked at the next draw while the stall lasts. A blocked rule with a given set of symbolic holes is given up for the campaign after 4 settled queries that gave no candidate.
The proposer's solver is clock-free (`BackendOptions::smt_resource_limit`): each decision of its run gets 250,000 Z3 resource units with 2 retries at doubled units, each model query 2,000,000 with 2 retries, and an undecided model query is a deterministic "no candidate", and an undecided decision of the run is handled as the backend handles any undecided answer (an indeterminate step, or both sides kept).
It spends at most a quarter of the cases and of the work; the work of its runs (states visited) and model queries (1 each) counts in its share and in `totals.work` before its candidate runs, so the share, and a work budget, may be exceeded by one run's bound plus one case's work.
A positive `solve` weight needs a positive `blind` or `dictionary` weight beside it; the report then records its parameters (`identity.solve`, with the unit budgets and the Z3 version that counts them) and its runs (`totals.solve`).
A build without the `z3` feature, and the WebAssembly package, refuse a positive `solve` weight.
The guided proposers (the climb, the corpus and the solve proposer) together also spend at most half of the cases and work, so blind sampling and the dictionary keep at least half whatever the weights (`engine::schedule`); the solve proposer's runs and model queries count in that work before its candidate runs.
A candidate hit becomes a witness only after a confirmation on a fresh backend agrees.
A confirmed witness is then shrunk (unless the options turn `shrink` off), within at most 256 candidate runs, each candidate confirmed as the witness was: every hole first tries its least value (the admissible integer nearest 0, or the shortest admissible prefix of a string, byte string or collection), a blindly drawn value then shrinks along its value tree, and passes of bisecting moves towards the least values repeat over every hole while one of them makes progress. So a hole the witness does not need ends at its least value, and a hole that could shrink only after another one did is moved again (TRIAL2's `M = 8, N = 8` ends at `M = 1, N = 0`).
Each move changes one hole: a witness that rests on a relation between holes (a kill that needs `X * 2 == Y + 1000` exactly) keeps it only through values where one hole alone can move, so its shrunk form may be larger than the smallest assignment that keeps the relation, and when no single-hole move keeps the hit the report has no shrunk witness (`X = Y = 1000` stays as it is, though `X = 500, Y = 0` also kills).
Each run starts from fresh proposer state, so a second run reports exactly what a fresh campaign with the same spec and budget reports.
The `FuzzReport` (`to_canonical_json` gives its canonical bytes) is a function of the definitions, program, holes, target, options, budget, seed, the k-rust revision and `ENGINE_VERSION`, and for a solving campaign also of the Z3 version (`identity.solve.z3-version`), whose search counts the solver's resource units: the solver reads no clock, so its answers, `unknown` included, do not depend on the machine's speed or load.
The exceptions are counted, never hidden: cases outside the determinism contract (`totals.outside-determinism`; the cases run on the case options' clocked solver, as in every campaign) and the solver's runs that a stack stop, a cancellation or the per-case safety limit ended (`totals.solve.outside-determinism`).

The Node-API (`k-rust-napi`) and WebAssembly (`k-rust-wasm`) packages run one campaign per call, `runFuzzCampaign`, from the specification's JSON form, and return this report; without a caller identity they record the same k-rust build identity as `krust-fuzz` (below).
Observer targets are library-only, and the WebAssembly package has neither the solve proposer nor a per-case safety limit ([k-rust-napi](../k-rust-napi/README.md#fuzzing-example), [k-rust-wasm](../k-rust-wasm/README.md#fuzzing-example)).

## Command line

The `krust-fuzz` executable runs the same campaign from a compiled directory, a program and a campaign file (ARCHITECTURE 9.4).
It needs k-rust's `cli` feature, which loads compiled directories (and implies Z3), so it is built with this crate's `cli` feature: `cargo build -p k-rust-fuzz --features cli,z3-gh-release`.
`z3-gh-release` links the Z3 release that k-rust's default features download, as `krust` does; with `cli` alone, a build of this package links the Z3 the build environment provides (README, "Install and build").
`krust fuzz ARGS` runs it, as `cargo` runs `cargo-NAME`.
krust looks for an executable `krust-fuzz` beside itself, then on `PATH`, skipping files that are not executable.
It passes the arguments after `fuzz` exactly as given (a leading `--` included) and its own k-rust build identity, and `krust-fuzz` refuses to run (exit status 2, "version skew") when it was built from other k-rust sources.
When no `krust-fuzz` is found or it cannot be started, `krust fuzz` exits with status 2, never with `krust-fuzz`'s "no witness" status 1.
Each release ships `krust-fuzz` in its own archive (package `k-rust-fuzz`, built with `cli` and `z3-gh-release`) for every target `krust` ships for, with a shell installer that puts it in the directory where `krust`'s puts `krust`; the two packages share k-rust's version, so one release tag ships both (README, "Install and build").

```text
krust fuzz --definition imp-kompiled --program transfer.imp --campaign holes.toml \
  --reach-rule IMP.overflow --max-work 100000 --cases 5000 --seed 0x5eed --json
krust fuzz --campaign holes.toml --reach-rule imp.k:47
krust fuzz --replay witness.json
```

A rule target (`--reach-rule RULE`, the file's `rule`) names one rule of the definition's catalog, read by the shape of `RULE`:
`FILE:LINE`, where `LINE` is a decimal number, is a source position, any line from the rule's first to its last, as kink lists uncovered rules (`imp.k:47`). `FILE:FIRST-LAST`, the range the summary prints for a rule written on several lines (`calc.k:28-30`), names the rule that spans `FIRST`, as `FILE:FIRST` does, and is refused before any case unless that rule spans `LAST` too (a range past one rule may name another); the summary's `target rule:` line shows the rule chosen.
`FILE` must name exactly one file of the definition: a whole catalog path names its file; otherwise the paths it is a suffix of after a `/`, or, for an absolute `FILE`, the relative paths it ends with; a leading `./` is dropped, and a `FILE` that names several files is refused, whatever the line, with the files listed.
Exactly 64 hexadecimal digits are a unique id, as the report names rules and the summary's `krun` line prints them; any other text is a label, `IMP.neg` or, when no label is that, `neg`.
Every rule has a source position and a unique id, so a label of either shape is still named by those, and unlabelled rules (most of SIMPLE's, IMP's expression rules) need no labelled copy of the definition.
A reference that names no rule is refused with what can be named instead: the nearest labels and the number of unlabelled rules, the rules written nearest the line, or the files that hold rules; one that names several rules lists them with their unique ids.
The report's `identity.target-rule` names the rule a rule target resolved to, and its `totals.coverage.names` gives every reached id its kind, label and source locations; each location's `reference` is the shortest path suffix that names its file alone, so `reference:line` (or `reference:first-last`) as printed is a valid `RULE`.
The summary names the target rule, then lists the rewrite rules the cases applied, and those whose condition was entered but which never applied, by source position, label and unique id.

A compiled directory is loaded as `krust krun --definition` loads it (`k_rust::native::load_runnable_artifact`, plus the directory's `syntaxDefinition.kore` and `macros.kore`, which printing and reading back data values need), and every backend is built on krun's route, with the compiler's rewrite order.
The program's path as written names it, as `krust krun` names a program: span holes address that name, and the program's locations carry it.
The start sort defaults to the sort of `$PGM`.

The campaign file holds the `[[hole]]` declarations of [Hole declarations](#hole-declarations) and, optionally, everything else; paths in the file are relative to its directory.
Every flag overrides the file: each switch has a negation (`--one-path`, `--no-run-to-completion`, `--no-negated-property`, `--data-end`, `--shrink`), and a target named by flags replaces the file's target kind with its `mode` and `at`.
`--rule-mode` and `mode` are refused unless the target is a rule, `at` unless it is a pattern, and `--mutant` selects the differential target only when no other target is named (a mutant with a rule or pattern target is refused).
A pattern the campaign refuses (it does not parse, or its `requires` reads a variable its configuration does not bind) is named by where it came from (`--pattern`, `--normal-end`, or the key and table of the campaign file), with positions as lines and columns of the pattern's own text; the library's `TargetProblem::Pattern` and `CampaignError::NormalEndPattern` give the same positions.

```toml
definition = "imp-kompiled"   # --definition; `mutant` (--mutant) names a mutant: the differential target
program = "transfer.imp"      # --program; `sort` (--sort) and `config-vars = ["N=1"]` (-c) as krun takes them
seed = "0x5eed"               # --seed; `cases` (--cases) or `work` (--work) is the budget, 1000 cases by default

[target]                      # exactly one of rule, pattern, differential (OD-2)
rule = "IMP.overflow"         # --reach-rule: FILE:LINE, a unique id or a label; `mode` (--rule-mode) is fired, covered or condition-reached
# pattern = '<k> .K </k> ...' # --pattern, in krun's --pattern syntax with `requires`; `at` is final
# run-to-completion = true    # --run-to-completion; negated-property (--negated-property)
# data-end = false            # --no-data-end: accept a run-to-completion hit whose end is not data

[options]                     # paths = "all-paths" (--all-paths), max-depth, max-work, normal-end-pattern,
safety-limit-seconds = 60     # shrink, smt-timeout-ms, smt-retry-limit; no-safety-limit = true (--no-safety-limit)
# assume-joined = ["list-int.k:64:3,list-int.k:71:3@root"]   # --assume-joined NAME (repeatable, added to these)

[[hole]]
name = "AMOUNT"
sort = "Int"
line = 4                      # `program` defaults to the program's name; `$NAME` addresses a binding's text
find = "amount = 250;"        # defaults to `literal`; or `column = 10` places the literal on `line`
literal = "250"
range = { min = 0, max = 1000000 }   # also `length`, `elements = { element = "Int" }`, `choices = [1, 2]`

[[hole]]
name = "TX"
sort = "Tx"
config-var = "TX"             # a configuration variable's whole value
```

`[bounds]` (`int-bits`, `length`, `depth`) and `[proposers]` (`anchors-first`, `weights`, `explicit = [{ AMOUNT = 7 }]`) map onto `GenerationBounds` and `ProposerConfig`.
A value is written as a TOML integer (an `Int`, or the unsigned value of an `MInt{N}` hole), boolean or string, or as a table in the library's JSON form, such as `{ int = "123456789012345678901234567890" }` or `{ list = [{ int = "1" }] }`.

Every case has a wall-clock safety limit of 60 seconds unless `--safety-limit SECONDS` or `--no-safety-limit` says otherwise (D24): `max-work` counts steps, and a step whose ground function evaluation does not terminate would otherwise never end.
The limit bounds each execution of a case, so a differential case (baseline, mutant, and in the one-path mode possibly the mutant's all-paths re-run) can take up to about three times it.
A limit of 0 seconds, which would stop every case, is refused, and so is a campaign file that sets both `safety-limit-seconds` and `no-safety-limit`.
A case the limit stops is `timeout` and outside the determinism contract; the report's options record the limit.
The library sets no limit by default.
The campaign runs on a thread with a 256 MiB stack, which the report records.
The report's k-rust revision is always k-rust's build identity (`k_rust::build_identity`), which `krust-fuzz --version` also prints; no flag or campaign-file key can name another.
The identity is the k-rust version followed by `+src.` and a digest of the sources k-rust is built from: k-rust's build script hashes the non-test Rust sources of `k-rust`, `k-rust-kore`, `k-rust-backend` and `k-rust-regex` and the files they embed (`crates/k-rust/build/source_digest.rs` gives the exact rule); crates.io dependency versions, features and the profile are not part of it.
Builds whose k-rust sources differ, committed or not, have different identities, and `krust` and `krust-fuzz` built from one tree have the same one.
Outside this workspace's layout the build script cannot read those sources, the identity is the version followed by `+unverified`, and the skew check and `--replay` say when they compare such identities.
The identity covers k-rust, not this crate: two `krust-fuzz` builds that differ only in this crate's code record the same revision.

The summary goes to standard output, or the canonical report with `--json`; `--report FILE` writes the report, and `--witness FILE` writes the witness file when a witness is found and removes an existing FILE when none is, so that the file never holds an older run's witness.
Both paths are checked before the campaign runs (and must name different files), and the result is printed before they are written, so a failed write loses no result.
The exit status is 0 when a witness was found and confirmed, 1 when not (including `equivalent`, `rejected-out` and `aborted`), and 2 on an error (including a failed write after the result was printed).

A witness file (`schema: "krust-fuzz-witness"`, `version: 1`) holds the campaign as resolved (absolute paths, every option) and the report; `--replay` refuses a witness whose report is not a `krust-fuzz-report` of the `REPORT_VERSION` this build writes (6), by its schema and version, read before the rest of the file, so an older witness gets that refusal and not an error about the fields its version lacks.
`--replay FILE` loads the recorded definitions and program, rebuilds the specification and checks that its identity is the witness's.
It compares every field of the report's identity except nine: the proposers and the budget, which the replay sets itself, `options.shrink`, the engine version and the dictionary's, the climb's, the corpus's and the solve proposer's parameters (`dictionary`, `climb`, `corpus`, `solve`), which cover only the code that chooses cases, and `effective-constraints`, which only bounds generation; it compares `target-rule` by its id alone, since the rule's name holds the source paths where the definition was compiled.
That includes the k-rust revision, each definition's modules, execution digest, route, rewrite order, frontend, execution-definition and syntax-and-macro digests and initial configuration, the program, overlay and target digests, the options, the bounds and the solver.
The frontend and execution-definition digests are the SHA-256 of each definition's canonical provenance JSON with its source table, which holds every sentence, attribute, term and provenance record and reads back to an equal definition; the syntax-and-macro digest hashes the two KORE files with their layout normalized. In all three, each source is named by its path relative to the directory of the file holding the main module (that file is `<main>`, a file beside it `./expr.k`, one outside it `./../lib/x.k`, a builtin `krust-builtin://…`), not by the absolute path a compiled directory records: the same sources compiled in another directory or checkout, or in process under the bindings' default entry name `definition.k`, give the same identity, and a witness replays there. Each source's contents stay digested, so any change of a source's bytes refuses the replay, a comment-only edit included.
On a mismatch it lists every difference by its path in the report (for example `definitions[0].syntax-definition-digest`) and refuses (exit status 2) unless `--force` is given.
A forced replay prints each mismatch and a `forced: replayed despite N identity mismatches` line; its exit status still says whether the cases reproduced.
It then runs the first and, when there is one, the shrunk witness case as the campaign's only explicit assignment, without shrinking, and a case reproduces when the replay confirms a hit whose witness case (hole values, class, initial and final configurations, halts, reaching leaf and step count) equals the recorded one; the exit status is 0 when every case reproduced and 1 otherwise.
`--definition`, `--mutant` and `--program` relocate the recorded inputs; the identity check still applies, and the replay's revision is always this build's.
