# k-rust-fuzz

`k-rust-fuzz` crafts concrete input values for a given program under a given K specification, so that an execution of that program reaches a stated target: a named rule, a pattern, a client observer, or a difference between a baseline and a mutant definition.
It is built to steer values with the specification's state space (its rules, guards, coverage and path conditions), and it never generates programs.
Generating whole programs is out of scope: random or grammar-driven program generation produces nothing a human would write, and the author (a person or an LLM) already writes the program.
Crafting inputs that reach a target is in scope: the author marks the program's input holes beside the unmodified program (typed spans of data, such as an `Int` literal), names the target, and the crate chooses hole values, runs the program with k-rust, and reports.
The report holds either a witness that a concrete re-run confirmed (the hole values, the initial and final configurations, the outcome), or a bounded "no witness found" with the budget, the cases run, the coverage reached and the outcome counts, which is never a proof that no witness exists.

[docs/fuzzing.md](../../docs/fuzzing.md) is the user guide: how to mark holes, choose a template, kill a mutant, reach a rule or hit a pattern, read the report and replay a witness, with `krust fuzz` and with kink's `kink-flow fuzz`; this README is the reference.

The library builds without k-rust's `cli` and Z3 features; the `z3` feature enables the solver-backed proposer (solve).
The design is in the fz26 programme's `ARCHITECTURE.md`; the rustdoc of each item cites its section.

## Outcome classes

Every case receives exactly one `OutcomeClass` (ARCHITECTURE 5.3).

| Class | Meaning |
|---|---|
| `hit` | a clean leaf reaches the target and confirmation agrees; reported as a property failure for a negated property |
| `miss` | the run ended naturally on every leaf without reaching the target |
| `stuck` | a clean leaf is an abnormal stop (stuck, but not a natural end), and no leaf reaches the target |
| `reached-unfinished` | under `run-to-completion`, the target was reached on a leaf that is clean except for its halt, which is neither a natural end nor an unsupported halt (an abnormal stop, an undefined step, a bound, a timeout or a cancellation); and no leaf is `unsupported` |
| `depth-bound` | a `depth-bound` or `breadth-bound` halt |
| `work-bound` | a `work-bound` halt; deterministic, distinct from timeouts |
| `timeout` | a `timeout` or `cancelled` halt, a cancellation or step deadline that ended the run as an `Err`, or the per-case safety limit |
| `undefined` | a `trivial` halt: an undefined step |
| `unsupported` | `unsupported-hook`, `simplification-error`, `indeterminate`, `vacuous` after depth 0, an `Err` result other than a clock stop or a refused state, a leaf unclean for a reason other than its halt, a target-reaching leaf that is not clean (and not `reached-unfinished`), or, for a rule or pattern target with `run-to-completion` and `data-end`, a reaching natural end that is not data |
| `rejected` | a hole value violates its sort or constraints, does not round-trip through the program's syntax, or the backend refuses the initial state (`vacuous` at depth 0, or an invalid state) |
| `baseline-incomplete` | differential only: the baseline's set of ends is incomplete (ARCHITECTURE 4.3) |

When a result has several leaves, the case takes the first of these that some leaf has:
`hit`, `unsupported`, `reached-unfinished`, `timeout`, `work-bound`, `depth-bound`, `undefined`, `stuck`, `miss`.
`reached-unfinished` applies only when no leaf is `unsupported`.
A leaf that is unclean for a reason other than its halt (an implementation-chosen value, a contradicted claim, remaining constraints, a term not shown to exist (k-rust's `ground_defined`, reason `not-ceil-free`; it reads the definition's declarations, so it counts an application of a hooked `value-production` symbol as existing whether or not its hook ran, and the run-level unsupported-hook check is what refuses a leaf resting on an unevaluated hook), a stack stop, an undecided solver answer, and so on) is `unsupported` whether or not it reaches the target, because it may hide a reaching state, so `miss` or `stuck` would be unsound.
`rejected` is decided before execution, and `baseline-incomplete` by the differential judge before the mutant's leaves are looked at; neither is chosen by precedence.
A stuck, truncated, timed-out, undefined or unsupported run is never reported as a pass.

A rule or pattern target with `run-to-completion` asks for a witness that becomes a test: by default (`data-end`, on unless the campaign file says `data-end = false` or the command line `--no-data-end`, `Target::data_end` in the library) its hit also needs the reaching natural end to be data, as every end the differential target compares is (below), so that the test's end can be compared with a mutant's. A reaching natural end that is not data, such as one holding an unevaluated function application, is `unsupported`, and the witness's `clean-leaf-facts` name `end-data`. A negated property is exempt: its counterexample is decided by its match, whatever the end's function applications denote. The command line refuses `data-end` on a differential target.

A pattern (a target's or the `normal-end-pattern`) whose `requires` reads a variable that its configuration does not bind, such as `<k> .K </k> <state> M </state> requires R >Int 0`, is refused by `Campaign::new`, naming the variable. Such a variable is almost always a misspelling (of a variable the configuration names, or of a key), and a leaf's match then leaves a condition over it, which a leaf judgement decides only when it is trivially true or false (`R ==Int R`, `... orBool true`) and otherwise classes `unsupported`. The refusal is a rule of use, not a proof that no leaf matches: it refuses the few such patterns that some leaves would match, which are better written without the variable. `krust krun --pattern` answers such a match with the remaining condition in its result instead.

A pattern target (a negated property included) also reports `totals.pattern-body-matches`: how many end leaves of the cases inside the determinism contract matched the pattern's configuration without its `requires`, whatever the `requires` gave there (true, false or undecided), each leaf on its own as targets are matched; a leaf counts when it is clean apart from the target's own undecided verdict: a leaf unclean for another reason (an implementation-chosen value, a contradicted claim, a state that is not ceil-free) is left out even when its configuration matched, as every verdict of the campaign leaves it out, so a semantics whose every end is unclean also gets 0 (its `unsupported` reasons say why). When some executed case had an end clean enough to be judged and none matched, a warning (`pattern body: …`) says that the pattern may name a cell, key or value no end holds, such as a misspelled key: a negated property then holds vacuously, which its `miss` cases alone cannot tell from one that holds. `totals.pattern-body-judged` (present exactly when `pattern-body-matches` is) counts the cases inside the determinism contract with such an end, so a 0 among the matches tells a pattern no judged end holds from a campaign that judged none, and the command's `pattern body:` line names both counts. The warning counts only the cases whose ends were judged, and says how many other cases had no end clean enough to judge; when no case had one (every end unclean, or no end reached), it is not given, since nothing was learned about the pattern. The configuration's own match only informs: its verdict never makes a leaf `unsupported`.

### Natural ends

`miss` against `stuck`, a run-to-completion hit and a differential end under `run-to-completion` all rest on the natural end: a clean `stuck` leaf on which the program finished (without `run-to-completion`, any clean decided `stuck` leaf is a differential end, a natural end or an abnormal stop alike).
A campaign's `normal-end-pattern` (`CaseOptions::normal_end_pattern`) decides it when given; otherwise the default reads the `<k>` cells:

- `single-k`, for a configuration whose `<k>` cell is not under a multiplicity cell: the leaf matches `<k> .K </k>` with the rest of the configuration free;
- `every-k`, for a configuration whose `<k>` cell lies under a cell of multiplicity `*` or `?` (threads, as in SIMPLE or KOOL): every `<k>` cell of the leaf holds `.K`, and a leaf with no `<k>` cell left (every thread finished and was removed, `<threads> .Bag </threads>`) is a natural end too, provided the initial configuration had a `<k>` cell (otherwise no thread ever ran, and the program may have stopped elsewhere: the leaf's natural end is undecided). A leaf with one thread's computation left is an abnormal stop (a deadlock or a stuck thread).

The report's `normal-end` records which applied to each definition, and when `every-k` decided cases, a warning (`every-k: …`) says so and how to override it.
The default reads only the `<k>` cells, so a semantics that removes a thread on error, or whose finished threads keep a value in `<k>`, needs its own pattern (for example over an error cell).

### Why a case is unsupported

Every `unsupported` and `baseline-incomplete` case has a reason, counted in `totals.unsupported-reasons` and `totals.baseline-incomplete-reasons` (each sums to its class's count).
A reason whose fact rests on a hook names it: `totals.unsupported-hooks` and `totals.baseline-incomplete-hooks` map each such reason to the hooks its cases named, `{hooks: [{hook, class?}], omitted?, cases}`, sorted by hook and class, at most 8 with `omitted` counting the rest, and `cases` counting the reason's cases that named a hook (a reason may also stand for facts that name none, such as a contradicted claim off the leaves), so the list is a function of the set of hooks and not of the order cases ran in (absent when no reason names one). `implementation-chosen-value` names each hook that read a value the definition leaves open with the value's `class` (`order`, `item`, …; at `any-state` also those on the prefix of the reported dirty reach, when the verdict read it: no clean reach, inside the determinism contract), `run-fact-off-leaves` those of the run's marks that no leaf carries, `kill-without-evidence` both on the mutant; `halt-unsupported-hook` and `halt-unsupported-construct` the hook each leaf of that reason halted on, `unsupported-hook` the hooks the run left unevaluated; `end-not-comparable:*` and `query-not-confirmable:*` the hooks of their condition, read from the run that condition was judged on (`unsupported-hook` reads the load's records too for `end-not-comparable`, never for `query-not-confirmable`, whose condition reads the run's only). Each hook is read from k-rust's typed records (a mark's `hook` and `class`, an unsupported hook's `hook`), never from their text. The no-witness statement and the command's summary print them beside the count (`4 implementation-chosen-value (hook MAP.keys_list [order] named in 4 of them)`), and so do kink-flow's actions, which quote the statement. A rule or pattern witness's `comparable` judgement carries the same per condition as `comparable.hooks` (`unsupported-hook`, `unsupported-hook-unevaluated`, `implementation-chosen-value`, `run-fact-off-leaves`, and `halt` for a leaf that halted on an unsupported hook; absent when empty); `--replay` compares them exactly, an absent map being an empty one.
A case is counted once, under the first of its reasons in the order of `exec::UnjudgedReason`, which runs from facts of the run (an `Err`, a bound, a halt) through facts of a leaf (`not-ceil-free`, `undecided-state`, `implementation-chosen-value`, …) to facts of a judgement (`fired-off-trace`, `any-state-unattributed`, `natural-end-undecided`, `reached-undefined-step`, `reached-end-not-data`, `definition-not-confluent`, `mutant-end-not-data`, …).
A definition whose full critical-pair check reports findings has no data end at all (below), which is known before the first case: a campaign that reads data ends on it runs no case and ends `not-comparable` ([Not comparable at setup](#not-comparable-at-setup)). The reason `definition-not-confluent` keeps its place in the reason order, but no case of a campaign is counted under it any more.
A halt is read by the leaf's structured cause (`ExecutionLeaf::cause`), never its text: a `simplification-error` leaf is `halt-iteration-limit` (the simplification bound), `halt-smt` (a solver query without an answer: untranslatable, no solver, `unknown`, an unsatisfiable path condition (`inconsistent-ground-truth`: a state keeps a condition whose earlier checks were left undecided, so it shows the state empty, not k-rust wrong), or a script rejected for SMT text the definition or a user prelude supplied; also as an `indeterminate` leaf's cause), `halt-unsupported-construct` (equations that give conflicting results, an unsupported hook) or `stack-exhausted`, and a cause no correct k-rust gives is `internal-halt`, a crash ([Crash findings](#crash-findings)).
The no-witness statement, and the summary of a report with a witness, list the reasons, largest first, with the largest one's remedy (`UnjudgedReason::remedy`); a remedy only suggests actions that keep verdicts sound (a bound, a pattern, another program or hole range), never a change to the definition's claims, and names options by campaign key and command-line flag; a `not-ceil-free` case also adds a warning naming the partial function whose application a leaf holds.

### All paths on state sets

Under `paths = "all-paths"`, a rule target (every mode), a pattern target (`at: final` and `at: any-state`) and the program's run of every path that judges comparability run as k-rust state sets (`result_modality: state-set`; ARCHITECTURE 5.1, FZ-STATESET): each distinct configuration of a depth is explored once, and a path that reaches a configuration another path reached at the same depth is merged into it (its facts go to the result's lists, or onto every leaf under `max-work`; its trace is dropped). A path set has one leaf per path and grows with every interleaving, so on nondeterministic programs (IMP's `strict` operators, SIMPLE's threads) cases that were `work-bound` or `timeout` now get complete verdicts: IMP's `primes` with `m = 4` completes at work 467 where its path set was cut at 20000, and SIMPLE's two-thread rendezvous at 194 where its path set held 16799 leaves at 200000. One path, observers (whose state folds over a path), the solve proposer and the rule graph's entry stay path sets; the differential's sides were state sets already. An `at: any-state` case asks k-rust to match every state the run reaches inside the run (`matchStates`, FZ-STATESET-MATCH; [Pattern targets at any state](#pattern-targets-at-any-state)), so its own state-set run, which sets no terminal rule, is also the program's run of every path for its comparability. The report's `identity.execution-modality` records the modality of the case runs (`cases`), of the run of every path (`every-path`, rule and pattern targets) and of the any-state run (`any-state`, the case's own), each `path-set` or `state-set`.

What a state set keeps decides the verdicts:

- `fired` is a hit of a leaf from a retained leaf's trace or a terminal halt (its own path), and keeps its terminal rule. Otherwise it reads the run's committed transitions (`collectCommitted`, FZ-STATESET-MATCH: every rule whose successor some explored path took, merged paths included, and no candidate that was rolled back because its successor was undefined). A rule that is not committed was fired on no explored path, so `miss` and `stuck` stand. A committed rule is a hit of the whole run (no leaf named) when every leaf is clean (a clean natural end under `run-to-completion`, and data with `data-end`) and no fact lies off the leaves: every path ends at one of those leaves; outside the determinism contract it is demoted to `unsupported` or `timeout` as every hit is. Under `run-to-completion`, when the leaves' class is `stuck`, `undefined` or `reached-unfinished` and no path ends naturally (every leaf a decided abnormal stop or an undefined step resting on nothing open), a committed rule's case is `reached-unfinished`. Otherwise a case that would be `miss`, `stuck` or `reached-unfinished` is `unsupported` with `fired-off-trace`: each of those classes says, among other things, that no path that fired the rule reached a clean end of the kind the target asks for, and the rule may have fired on a path merged into another's configuration at its depth, whose continuation is that configuration's subtree and may end cleanly on a leaf that keeps the other path's trace. Such a case keeps the incidental `stuck` finding its leaves give ([Incidental findings](#incidental-findings)). `depth-bound`, `work-bound` and `timeout` already say the run is incomplete, and `undefined` names an undefined step a leaf really took, so those classes stand: a hit whose reaching path was merged may surface as one of them, or as `fired-off-trace`, where the path set gave a hit (V7).
- Which of two converging paths a state set keeps is decided by the depth-first exploration order. The order is deterministic, so every verdict reproduces, but some are order-dependent between a hit and `unsupported`. A `fired` case whose rule fired on one of the converging paths only, on a run whose leaves do not all qualify for a hit of the whole run, is a hit of its leaf when that path is met first and `fired-off-trace` otherwise, in every budget regime, since the kept leaf keeps its first arrival's trace. An `at: any-state` reach below a merged configuration keeps the prefix of the path met first, so it is a hit or `unsupported` by the same order (V8), never `miss`. In a campaign bounded by depth alone, a final-pattern case whose clean path converges with one that read a chosen value or contradicted a claim is a hit or `unsupported` by the same order (V1); with `max-work` every leaf carries every run fact, so that verdict does not depend on the order.
- `covered` and `condition-reached` read run coverage, the union over every explored path, merged ones included, and their hits need a complete run with every leaf clean, where both modalities give the same sets (V5).
- Without `max-work`, a merged leaf carries the facts of its first arrival only: a hit whose first-met path read a chosen value or contradicted a claim that a later clean path did not is `unsupported`, and with `fired`'s terminal rule every stuck or terminal leaf carries every run fact (V1). With `max-work` every leaf carries every run fact in both modalities, and nothing moves. Iteration exhaustion on the first-met path taints the merged leaf in both regimes (V2).
- A stuck leaf absorbs a later `depth-bound`, `indeterminate`, `simplification-error` or locally stopped leaf of its configuration, so `depth-bound` may become `miss` or `stuck` (V3).
- Condition records fill their caps with distinct entries and applied counts are per distinct state, so the climb's and the corpus's scores move (V6).
- A witness's `final-configurations` and `halts` list distinct ends, `totals.pattern-body-matches` counts distinct ends, and the witness's leaf, trace and steps are its first arrival's.

REPORT_VERSION 9 and ENGINE_VERSION 7 cover the change; `--replay` refuses a witness of an earlier version by its version and names the runs that moved to state sets (a differential witness's sides were state sets before too).

### Incidental findings

A rule missing from the semantics, or a partiality its author did not intend, is invisible to every target: no mutant of an absent rule exists, a baseline and its mutant get stuck alike, and coverage lists the rules that exist.
So the report keeps the first case of each of the classes `stuck` and `undefined` as information, `incidental.stuck` and `incidental.undefined` (`report::Incidentals`), whatever the target; the key, and each class's entry, is absent when no case had the class.
The classes are the classes of one run (above), under the normal end the report's `normal-end` names: `stuck` is a clean, decided `stuck` leaf that is not a natural end (under `every-k`, some `<k>` cell still holds a computation), `undefined` a clean undefined step (a rule applied whose result is undefined there; its leaf is the configuration before the step, and it is no end), each with no leaf of higher precedence.
The run is the semantics under test's: in a rule, pattern or observer campaign the case's own, so the finding's class is the case's class (or, for a case `fired-off-trace` made `unsupported`, the class its leaves gave: that reason says the target cannot be judged, while the leaves are the run's own); in a differential campaign the baseline's run of the case (all paths), classed alone, whatever the pair's class.
A stop or undefined step only the mutant has is never a finding: without `run-to-completion` it is a kill (an added or removed end, below); under `run-to-completion` an abnormal stop is no kill, and the pair's class (the mutant's) reports that the sides disagree.
A case that ends the campaign with a witness gives no finding; its witness shows its runs.
Each finding holds the case's number (counted from 0), its hole values, how many leaves the run has (`leaves`) and which one is the finding (`leaf`), its depth (`steps`; an undefined step is the step after it), the first item of each `<k>` cell that holds one, in order, as K text (`k-heads`: under `every-k` a stuck configuration is stuck in every thread, so each is where a thread stopped, a thread waiting for another included; for an undefined step, the items before the step), the leaf's configuration as KORE, the `krun` line that re-runs that run (on all paths for a differential baseline), and, for a differential baseline's run, `baseline-run: true`, which the summary line also states ("in the baseline's own run on all paths (not the pair's class)").
`krun` reports an undefined step only when every path of its run takes one; when another path of the finding's run does not, the krun line says so in its trailing comment (one comment, after the max-work note when there is one) with the finding's leaf and step, and the summary line says the finding is on one of several paths.
Only findings whose run is inside the determinism contract are kept, so a finding reproduces (in a differential case that run is the baseline's: a clock or stack fact of the mutant's run alone does not suppress it); keeping one changes no class, case or budget, and nothing is re-run or shrunk.
The summary prints one line per finding, worded as information: a K semantics often leaves a program stuck on purpose (an ill-typed program, a division by zero the language leaves without meaning).

### Crash findings

A panic of k-rust or of the engine during a case, or an error k-rust answers without a typed kind that is neither a stop nor a refused state (an internal error: a request the engine built that k-rust's own schema refuses, a result it cannot encode or decode), is a crash: a k-rust defect, which the definition may have triggered but k-rust should have rejected or reported (D30, D32).
The case keeps its class, `unsupported` (`baseline-incomplete` when a differential baseline crashed), with the reason `panic` or `internal-error`, and the campaign goes on; the report's `crashes` (`report::CrashFindings`, absent when empty) keeps the first case of each crash signature, at most 16, and `crashes-omitted` counts the crashed cases of further signatures.
A signature is the crash's `kind` (`panic`, `internal-error`, `internal-halt`), `side` (`baseline`, `mutant`, or `engine` for the code around the runs: assembly, a whole case's judgement, a confirmation's build), `stage` (`execute`, `judge`, `engine`) and `site`: a panic's location from its crate's `src` directory with the crate's version stripped (`site-kind: location`), or the message's first line before its first `:` with quoted spans and digits masked (`site-kind: message`), for an internal error, for a panic without a location (a panic hook an embedder installed after the campaign's replaced it) and for one located in toolchain or generated source.
Each finding holds its `signature`, the `phase` it first happened in (`case`, or a candidate's `confirmation`, a `shrink` candidate's screening, a witness's `comparability` run: a crash there leaves the candidate unconfirmed, drops the shrink candidate with the candidate's own values, or gives the witness `comparable: {holds: false, reasons: ["crash"]}`), the `message` (at most 1 KiB), the `case` number and `holes` (`{name, value}`), the `count` of cases with the signature, and `determinism`: never inside the contract, since after a panic or an error the run's solver `unknown`s and stack stops are lost, so `outside` when the clock stopped the run or a re-run did not repeat the crash, `unknown` otherwise (`outside` cases count in `totals.outside-determinism`).
A new signature's crash is re-run once on a fresh backend (`reproduced`, the comparability run's crash through that judgement on fresh cases; absent when no re-run was made: the clock stopped the crash, the fresh backend did not build, or the caller cancelled), and a reproduced crash of a case is shrunk under the same signature when the campaign shrinks (at most 32 candidates per signature and 64 per campaign, screened on the campaign's backends like a hit's), the shrunk values re-run once more (`shrunk-holes`, `shrunk-reproduced`); that work goes to `totals.crash-work`, charged to no budget, so a crash moves no case.
A finding also says whether the build has `debug-assertions` (whose panics a release build does not raise), the `program` and `config-vars` as instantiated, and, for a crash in `execute` on a route `krun` runs, a `krun-command` expected to reproduce it.
The summary prints one line per finding asking for the report's `crashes[i]`.
After a panic the campaign rebuilds its backends, sessions, solvers and assemblers (on the `from-definition` route from a copy of the internalized definition its session held) and asks them for what the run asked (condition entries, applied counts), so later cases run as they would have; a rebuild that fails ends the campaign `aborted` with kind `rebuild-failed`, keeping the crash that made it necessary (noted before the rebuild, at every phase); while a confirmed witness is shrunk it instead keeps the witness and makes no more runs, and the witness's `comparable`, which no run made, reads `{holds: false, reasons: ["crash"]}`. A finding first kept from another phase is taken over by the first case that crashes with its signature, which is then examined as a case's crash. A differential case that one side refuses stays `rejected`, but the other side's crash is kept.
A leaf whose halt's structured cause no correct k-rust gives is an internal halt (FZ-CRASH-CAUSE): a `builtin` failure or an `invalid-builtin-result-symbol` (terms are sort-checked, so a builtin hook meets arguments it does not take, or a result symbol it cannot build, only when a hook was declared at a signature its builtin does not fit and k-rust did not refuse it, or when k-rust built the application wrong: the finding names the definition's hook declaration or k-rust), a solver failure of k-rust's own making (a `malformed-script` blamed on k-rust's translation, `missing-model`, `missing-model-value`, `invalid-model-value`), a macro or alias at run time (`surviving-macro-or-alias`: compilation expands them and validation refuses one in the initial state), or a `simplification-error` leaf without a cause.
Such a leaf, on any path of either side, makes its case `unsupported` (`baseline-incomplete` on a differential baseline) with the reason `internal-halt`, whatever another leaf reaches, and is a crash of `kind` `internal-halt` at stage `execute`, whose `site` (`site-kind: cause`) is the cause's kind and the hook or symbol it names, never an input value (`builtin:wrong-arity:INT.add`, `invalid-builtin-result-symbol:IO.logString:dotk`, `smt:missing-model`, `surviving-macro-or-alias:<symbol>`); it is confirmed and shrunk as other crashes, but nothing is rebuilt, since the backend did not panic.
Environment refusals are no finding: `too-deep` names a configuration nested deeper than the backend's stack holds (a bound the build fixes, inside the determinism contract) and `stack-mapping-refused` a stack segment the host refused to map (outside it).
A panic in a client's `Observer` is the client's defect, not k-rust's: the observer is shared by every case and cannot be rebuilt, so the campaign ends `aborted` with kind `client-panic`, the `case`, its `holes` and the `panic` (`message`, `location`). An observer that panics while a crash is examined (its confirmation or its shrinking) or while a confirmed witness is shrunk aborts the same way, with the run's values; in the second case a warning keeps the confirmed witness's values, which the aborted outcome does not report as found.
A failed solver prelude still aborts (`solver-prelude-inconsistent`, `-malformed`, `-unknown`), and so does a solver that does not start for the definition (`solver-init`), which every case would repeat; a panic in a proposer or a generator, outside every case, still ends the process, and so do a stack overflow, an out-of-memory abort and a panic while unwinding, which no process can contain in itself.

## Hole declarations

A hole replaces a span of the unmodified program, addressed by `program`, an optional `line`, `find` (a text that occurs exactly once in the addressed line or program) and `literal` (the hole's literal, which occurs exactly once in `find`), or by `line`, `column` and `literal`.
Instead of a unique `find`, `line` and `column` may place the literal: `column` is the one-based column, counted in characters (a tab is one), of the literal's first character on that line, and `find` is then left out (or is the literal itself). This addresses a literal that also occurs nearby inside other text, such as the `3` of `(i32.const 3)`, whose `i32` holds a 3: give the line and the column of that `3`, with `literal = "3"`.
The text at the span is the hole's anchor value, the first value the explicit proposer tries.
A configuration variable (`$NAME`) can also be a hole, addressed by its name; so can a free variable of a KORE initial pattern, in the library API.
The declaration format of ARCHITECTURE 2.2, with the program `transfer.imp` unchanged:

```toml
[[hole]]
name = "AMOUNT"
sort = "Int"
program = "transfer.imp"
line = 4
find = "amount = 250;"
literal = "250"
range = { min = 0, max = 1000000 }
```

In the library, the same hole is a `HoleDecl` with a `HoleLocation::Span(SpanAddress { .. })` and its `Constraints`.
The flat form above is itself a library type, `holes::HoleFile`, which `HoleFile::into_decl` makes a `HoleDecl` with the refusals `krust fuzz` gives, each naming the hole; `krust fuzz` decodes its campaign file through it, so a front end that reads the same keys means the same hole.
`HoleFile` is a serde type and the library holds no TOML: a client deserializes it from whatever self-describing data it has, such as JSON (`serde_json::from_str::<HoleFile>`) or a `toml::Value` it decoded by hand (`value.try_into::<HoleFile>()`), and an unknown key is refused with serde's message.
A `choices` entry is a `holes::HoleChoice`, untagged: a 64-bit signed integer, a boolean, a string, or a table in the value form, each a value at the hole's sort (an integer is the unsigned value of an `MInt{N}` hole); a float, an array or a table that is no value is refused as it is decoded.

A span hole can take only the values whose printed text the grammar reads back, at the hole's position, as that value: every case is round-trip-checked, and a value that reads as something else is `rejected`.
For an `Int` hole the difference is the sign. Digits read back wherever the anchor's did, but whether `-` followed by digits reads back as a negative integer depends on the grammar there: a signed literal token (`INT-SYNTAX`) reads it as the value, while a grammar of unsigned literals (`UNSIGNED-INT-SYNTAX`, as in IMP and SIMPLE) reads a unary minus applied to the magnitude, or does not parse it.
So `Campaign::new` probes each `Int` span hole whose range admits a negative value (and whose anchor is not negative) with two admissible negative values of different digit strings, through the same round-trip check at the same position: the one nearest zero (`-1`, or the range's maximum) and the one of greatest magnitude with at most three digits (`-999`, or the range's minimum).
Only when every probe is refused do the hole's effective bounds start at 0.
The probes establish that those values cannot be written there, not that no negative value can: a grammar may spell one negative literal as a terminal of its own (a production `"-1"` beside signed literals) or read a sign before some digit strings only, and two probes of different lengths make such a collision unlikely to narrow a hole, but do not rule it out.
Narrowing is an economy of generation, not a judgement: generators, the dictionary, the climb, the corpus, the solve proposer and shrinking use the effective bounds, while the declared constraints and the round-trip check still judge each case, so an explicit negative value is still run and judged as before.
The report lists every narrowed hole in `identity.effective-constraints`: the declared and effective constraints, a reason code (`negative-not-read-back`), the side whose grammar refused, and each probe with its outcome (`reads-as`, with the term the position held instead as K text, or `does-not-parse`).
A warning says the same in words, with the parser's message for a probe that does not parse, and what to do.
A declared range that holds only negative values is refused at such a hole when every probe is refused, since no probed value of it can be written there.
Configuration-variable and KORE-template holes, holes with `choices`, and other sorts are not narrowed: a binding is parsed whole at its variable's sort, a template's values are never printed, and a choice set is the author's own list.
To give such a language a negative input, write the program with a unary minus before the literal (`- 5`) and keep the hole on the digits; to silence the warning, declare `range = { min = 0 }`.

A hole is data, and `Campaign::new` enforces it (ARCHITECTURE 2.4).
It refuses a hole whose sort is `K`, `KItem`, a cell sort, or a user sort in the closure of the program start sort's productions (a sort in which programs are written, such as `AExp` or `Stmt` in IMP).
It accepts builtin and hooked sorts that have a generator (`Int`, `Bool`, `String`, `Bytes`, `MInt`), collections with declared element sorts, and user sorts outside that closure, such as transactions, events or records declared in semantic modules.
The rule applies to every sort a value of the hole's sort may contain: collection element sorts and the argument sorts of its constructors, transitively, so `List<Stmt>`, `List<K>` and a record holding an `AExp` are refused, and `KResult` and other K-internal sorts count as computation.
When the start sort is `K` or `KItem`, the closure is every non-hooked sort of the syntax module.
User token sorts such as `Id` are refused, because an identifier names a declaration of the program.
`allow_refused_sort` (`allow-refused-sort = true` in a campaign file) overrides a refusal, and the report records the override; the refusal itself says why the sort is refused and, where an override applies, names it.
The values of an admitted token sort are tokens, written `{ token = { sort = "Id", text = "n" } }` in a campaign file (`{"token": {"sort": "Id", "text": "n"}}` in JSON), in `choices` too; a plain string there is refused with that form.

## Pattern targets at any state

A pattern target is matched at `final` (a clean end of the run, the default) or at `any-state` (the campaign file's `at = "any-state"`, `--at any-state`, `PatternTarget::at` in the library; ARCHITECTURE 4.1).
At `any-state` each case runs once, a state set under all paths, and k-rust matches the pattern against every state the run reaches, inside the run (`matchStates`, `docs/compatibility.md` "State matches"; FZ-STATESET-MATCH): the initial configuration (after its initializers are evaluated), every state the run steps or the depth bound stops. A state merged into an equal state of its depth has its verdict and is not matched again. Not matched: a state a bound, a timeout or a cancellation stopped before its normalization (its leaf takes its halt's class), a remainder (its parent's configuration under more constraints) and an undefined step's leaf (the configuration the step was taken from was matched when reached).
A configuration reaches the target when it has no constraint or variable, is shown to exist (k-rust's `ground_defined`) and matches with empty constraints (in both evaluation modes when the pattern evaluates a function or has a `requires`), as an end does at `final`.
A hit needs a reach whose path, up to the reaching configuration, carries none of the leaf facts of a clean leaf (an implementation-chosen value, a contradicted claim, iteration exhaustion, a failed condition simplification, undecided initial definedness), no unsupported hook in the run, no leaf halted on an internal cause (`internal-halt`), and a run inside the determinism contract (the matcher's solver `unknown`s and stack stops count as the run's). k-rust stops matching at the first clean reach whose configuration holds no term-level `\and`, which `query-confirmable` refuses, and keeps an earlier clean reach with one only while none without one is found. What follows the reach cannot unmake it, so a path that reaches the pattern and is then cut by `max-work` or `max-depth` is a hit. When the first path to a merged configuration read a chosen value and a later one did not, the later one is the clean reach. Below a merged configuration a reach keeps the prefix of the path the run expanded, so it can be a hit or `unsupported` by the deterministic depth-first order, never `miss` (V8).
Under `run-to-completion` the reaching configuration names no leaf, so a hit also needs every leaf of the run to be a clean natural end (and a data end with `data-end`) with no fact off the leaves. Otherwise a leaf the classification calls `unsupported` (a fact, an undecided natural end) keeps that class and reason; when no path ends naturally (every leaf a decided abnormal stop or an undefined step resting on nothing open) the case is `reached-unfinished`; and otherwise `unsupported` with `any-state-unattributed`.
A dirty reach or a configuration that cannot be decided (it matches but is not shown to exist, its match is undecided, or it holds a constraint) makes the case `unsupported` when no clean reach exists; otherwise it is classed by its leaves, none of which reaches (`miss` when every leaf is a clean natural end).
The witness's `reaching.configuration` is the reaching configuration and `reaching.step` its depth in rewrite steps from the initial configuration (0 for the initial configuration itself), the first clean reach in depth-first order (not necessarily the least depth); it names no `leaf` and no `steps`, and its `krun-command` is `krun --search-all --pattern` on the same input, with `--depth` when the campaign bounds the depth; without a depth bound the line says that the search may not terminate (it ends only when the reachable configurations are finitely many) and names the work bound the campaign used, which krun cannot take. The witness records no facts of the reaching prefix: a clean reach's prefix carries none of the facts a clean leaf may not carry, by its definition, and the diagnostics it may carry (an `undecided-condition`, say) bear on no verdict. `totals.pattern-body-matches` is counted at `final` only.
An any-state case costs one match per distinct reached state (two when the pattern evaluates something) inside the run, and holds no configuration beyond a few matched ones: TRIAL3's IMP `primes` case that held 7.4 GB through observed execution at max-work 1000 (and ran out of memory at 100 000) now takes 73 MB and completes at work 467, and `primes` with `m = 60` completes at work 36 366 in 0.9 s and 112 MB, about 5 % more time than the same case at `final`.

## Comparable ends and confirmable queries

Two options of a rule or pattern target ask for a witness that kink can use (P7-ADDENDUM section 4); both read facts k-rust already reports, and neither runs kink's own rules (its census exclusions and TV-01 reach a witness through kink itself).

- `comparable-end` (the campaign file's `comparable = true`, `--comparable`, `Target::comparable` in the library): a hit also needs the witness program's run of every path to be one kink can compare. It must be complete (every leaf a `stuck` end or an undefined step, no bound, timeout, stop or undecided halt; a run with no `work-bound` leaf is the unbudgeted run's result), every leaf decided (ground, no constraint, ceil-free), every end's and undefined step's term data (k-rust's `is_data`, as for `data-end`: ends are compared by their terms, which is sound only for terms that denote themselves, so an irreducible application such as `g(3)` refuses it, and so does every end of a definition whose full critical-pair check reports a finding), no diagnostic of any kind on any leaf (kink makes a diagnosed leaf incomplete, so an `undecided-condition` the clean-leaf rule ignores counts here), and no stop for lack of stack, chosen value, contradicted claim, allowance refusal or unsupported hook in the run or in the definition's load (load records, which taint no leaf of the fuzz's own verdicts, count here). `smtUnknowns` refuses it too, as the determinism contract does. That run is the hit case's own when the campaign runs all paths as a state set and the target sets no terminal rule (a `fired` rule target without `run-to-completion` stops at its rule); otherwise the hit case makes one more run of every path, a state set with the campaign's bounds (and the default work bound of 100 000 when the campaign bounds only the depth), which is part of the case: its work, its load records and its determinism count in the case. A hit that fails is `unsupported`, counted under `end-not-comparable:CONDITION` with the first condition that fails (`work-bound`, `undecided-condition`, `end-not-data`, `contradicted-claim`, ...), or `timeout` when a clock stopped that run. Without the option, every rule or pattern witness case carries the judgement as `comparable = {holds, reasons}`; when its case ran one path or stopped at the target's rule, the run of every path is made once per reported witness case, after the search and shrinking, outside every case: its work adds to `totals.work` alone, and it changes no case's class, determinism or coverage, so the campaign's cases are those it runs without the judgement. Such a judgement may name a fact that breaks determinism (`clock`, `smt-unknowns`, `stack-stops`, `allowance-refusal`), which it may not repeat. A witness found under the option names `comparable-end` among its `clean-leaf-facts`, which tells it from a witness whose judgement merely holds. On these conditions the fuzz may refuse more than kink (a vacuous leaf, `smtUnknowns`), never less, except on whether an end is a value, which kink judges by its own rule (TV-01, which refuses the overload data heads `is_data` admits); kink's own rules may still refuse a comparable witness.
- `query-confirmable` (`Target::query_confirmable` in the library only): a pattern hit, at `final` or `any-state`, also needs no diagnostic of any kind on any leaf of the run, no fact in the run's lists (a chosen value or contradicted claim on no leaf, an allowance refusal, an unsupported hook, a stop for lack of stack) and no stop for lack of stack in the definition's load (the load's other records do not refuse it), and no term-level `\and` in the matched state, which kink's query refuses even with equal sides. The run is read whole because kink's search absorbs the facts of converging paths into a matching state. This is necessary for kink's query to confirm the hit, not sufficient: kink's search stops at its first match, which may be another, undecided state. A hit that fails is `unsupported`, counted under `query-not-confirmable:CONDITION`, and a witness found under the option names `query-confirmable` among its `clean-leaf-facts`.

## Witness filters

A client that judges a witness by rules of its own (kink, whose end check gives a `String` domain value a value only when its bytes are ASCII) may refuse a candidate the campaign confirmed, for a reason that depends on the input. Refused after the campaign, such a candidate ends the search: the campaign stops at its first confirmed hit, and shrinking moves toward the values the client refuses (proptest shrinks a character drawn above U+00A1 no lower than `¡`). `Campaign::run_filtered(budget, cancel, &mut filter)` runs the campaign with a `filter::WitnessFilter`, which judges candidates inside the search (FZ-COMPARABLE-B; the rustdoc of `filter`):
- A hit's witness case is judged before its confirmation and the confirmed case after it. When the screen accepts and the confirmation's case is refused, the two cases differ in what the filter read (equal cases judged differently are a client defect, below): the hit is demoted, recorded as an engine defect, and not repaired, since a repair would start from neither case reliably. A refused hit costs no confirmation run; it is `unsupported` with the reason `client-refused`, counted per cause in `totals.filter.refused`, and the search goes on. The first refused hit of each cause (at most 16 causes) is kept in the report's `client-refusals`, with the client's detail and remedy; its `repaired` says whether that case is the one the witness was repaired from (`repaired-from`).
- Every shrink candidate that hits is judged the same way inside the shrink screen, so a shrunk witness is one the client accepts (`totals.filter.refused-shrink-candidates`).
- When the campaign shrinks, a refused hit is repaired from the filter's candidates (`WitnessFilter::repair`, at most 4, each a full assignment): each admissible candidate runs as a full case on the campaign's backend, charged as extra work like a shrink candidate (`totals.filter.repair-candidates`, `repair-work`, included in `totals.work`), and the first that hits with the same kind of kill, is accepted, is confirmed and is accepted again becomes the witness's `first`, shrunk under the filter; the witness's `repaired-from` names the refused case, its values and its cause. Once three refused hits of one cause have been repaired without success, no later hit of that cause is repaired (`repairs-skipped`): a refusal no input of the campaign avoids would cost its candidates on every hit. A repair counts (in `repairs` and toward those three) only when at least one candidate ran: a filter that proposes nothing, or only inadmissible candidates, costs no run, so a client should give a refusal it can repair its own cause.
- A campaign that ends without a witness after refusals says so in its statement and in a warning that starts `client-refused:`, so that it does not read as survival; the warning says that every candidate hit was refused only when no hit the filter accepted was lost to its confirmation (`totals.unconfirmed` is 0), and otherwise names those candidates as possible witnesses.

The filter only removes candidates: every witness of a filtered campaign is one the unfiltered judgement confirms too, and a filter that accepts every case gives the unfiltered report, byte for byte, apart from `identity.filter`. `judge` and `repair` must be pure functions of their arguments, and `id` must name every other input they read, since the report records it as `identity.filter` and is a function of it. When the two judgements of one hit disagree, the engine compares the two witness cases: equal cases judged differently abort the campaign (`client-defect`, as does a refusal whose cause is no token of `a-z`, `0-9`, `-` and `:` of at most 64 bytes); different cases are a difference the confirmation does not compare (it compares the reaching configuration, leaf and kind of kill), recorded as an engine defect, and the refusal wins. A panic of the filter aborts the campaign (`client-panic`); its identity is read first on every run, so a panic there aborts before any other outcome (an equivalent pair, a definition without data, backends that do not rebuild) could hide it. Replay runs no filter and ignores `identity.filter`: a confirmed witness hits without it, and the command notes a recorded one. Every witness side records its run's `work`, and the rule of each undefined step (`undefined-rules`, parallel to `halts`, absent when no leaf names one), which a client judges an undefined step by; replay compares both (an absent `undefined-rules` read as all `null`). These two fields are part of report version 9: the round-3 wave that introduced version 9 has not been handed over, so a version-9 reader is this wave's, and every witness, filtered or not, carries `work` (an earlier round-3 reader, which refuses unknown fields, refuses them; the case sequence of an unfiltered campaign is unchanged). The bindings expose no filter: neither runs client callbacks. A filter's own state is the client's memory: kink-flow's keeps one kink load per side for the whole campaign, about +90 MB of peak resident memory on SIMPLE.

## Differential target

A differential campaign (a mutant beside the definition) looks for an input on which the two definitions' sets of ends differ (ARCHITECTURE 4.3).
A side's ends on an input are its final configurations: each clean, decided `stuck` leaf, whether the program finished there (a natural end) or stopped mid-way (an abnormal stop); in both, no rule applies.
An undefined step (a `trivial` leaf) is no end: its configuration is reached but is not stuck, since a rule applies to it, and it has no successor, so the run's outcome there is undefinedness, which is no configuration (`krun` prints `\bottom`; `docs/compatibility.md`, "Undefined steps in proofs", "Trivial rule results"). A side whose every path takes one has no end at all.
A case kills the mutant by an *added end*, a mutant end that the baseline's complete set lacks, or a *removed end*, a baseline end that the mutant's complete set lacks: a baseline that stops where the mutant's step is undefined (a dropped guard on a division) is one.
Every compared end must be data, on both sides: built from constructors, injections, domain values, well-formed collections, and irreducible applications of data heads (`k_rust_backend::data_term`).
A data head is an `anywhere` production that is not a declared function and is declared total or `value-production` (which k-rust's compiler adds to a non-function production with `anywhere` rules), with no hook, lemma or ceil equation, rooting only executable equations, each overload one of the shape `g(p1, ..., pn) = inj(h(x1, ..., xn))` with each `pi` the variable `xi` or `inj(xi)` (SIMPLE's `_,_Exps` and `_,_Vals`, and its array lookup `_[_]`, whose two `anywhere` rules are plain); an application of it that no equation of its head matches (`_,_Exps(x = 1, inj{Bottoms,Exps}(.Bottoms))`, or a stored `a[4]`) is a normal form in every context, since an `anywhere` equation reads only the term it matches, and an element of its sort, distinct from every other one.
A definition has data only when its full critical-pair check (run once per definition at campaign setup, about 0.03 s on SIMPLE and 0.2 s on WASM) reports nothing: an identification anywhere reaches other terms through every equation that tells them apart, so a definition with an unjoined pair or an overload premise violation has no data at all, and the campaign is [not comparable at setup](#not-comparable-at-setup). WASM's `test.md` is such a definition today (four findings: two genuine pairs, the `getOrDefault` lookups of `list-int.k` and `list-ref.k`, which give a lookup at index -1 two results, and two undecided ones, of `sparse-bytes.k`'s `replaceAt` and `wasm-data.md`'s `unescape`), so its differential ends are not compared until those findings are named.
Each definition reads the ends with its own theory, so every compared end must be data in both definitions, each judged by its own (its own overload families, `anywhere` and function equations, and subsort order): a mutant that adds an overload member, an `anywhere` rule or a subsort below an argument sort of a data head's equation (`Id < Val` on SIMPLE) is never killed through an end the change makes reducible.
A side that carries an implementation-chosen value or a contradicted claim (`total` or `preserves-definedness`), on a leaf or on its result's lists, is no evidence: the baseline is then `baseline-incomplete`, and a would-be kill of the mutant `unsupported`.
Under `run-to-completion` only natural ends kill.
A case on which the work bound stops the mutant while the baseline reached all its ends is `work-bound`; the no-witness statement counts those cases apart, with the most work the baseline needed in one of them, and says that the mutant may not terminate on that program (a mutant that turns a loop's decrement into an increment), without advising a larger `max-work`, since whether a run terminates cannot be decided. A case on which the bound stops the baseline as well is `baseline-incomplete`, and its advice to raise `max-work` stands.

### Not comparable at setup

When the campaign's judgement reads data ends (a differential target, or a rule or pattern target with `run-to-completion` and `data-end`) and a definition's full check reports findings, no end of that definition is data, so no case could kill (or hit), whatever the budget, bounds or values. `Campaign::new` decides this before any case: every run reports the outcome `not-comparable` with the definitions without data (`sides`) and a statement, runs no case, and the report lists every finding in `definition-findings`, with one warning per such definition (`definition-not-confluent (baseline|mutant): ...`). A negated property, a target without `run-to-completion`, and `data-end = false` read no data end and are unaffected.

Each finding says whether it is **genuine** or **undecided**. A pair is genuine only when the check exhibits a ground input with two different results (the `instance`): an instance of the overlap built from normal forms (no map or set keyed twice by one normal form), at which both equations apply by the evaluator's own rule (each matches, its `requires` evaluates to true, and no equation of the same head with a higher `priority`, `owise` the lowest, applies there; one whose condition is undecided counts as applying), and whose two reducts evaluate to different normal forms (k-rust's internal normal form), or to a normal form and an undefined value. A normal form may hold an application of a declared total function that no equation rewrites; an undefined value holds, under constructors, injections and collection items only, an application of a declared partial function that no equation rewrites, which is `\bottom` in the normal-form reading although k-rust returns it as it stands; `instance.stuck` says which, per value (`null`, `total` or `partial`). Evaluation of that input is then not uniquely determined, so the definition read by its normal forms (`M_NF`, as `k_rust_backend::data_term` reads it) is not a model, and k-rust's result for the input depends on the order in which it tries the equations: a defect to fix in the definition. This is not a claim that no model satisfies the definition (KORE keeps, for instance, injections from different source sorts apart by no axiom). The instance is searched among small terms of each variable's sort (integers 0, 1, -1, the Booleans, short strings and byte strings, nullary constructors, empty and one-element collections, constructor applications over those, injections of a subsort's terms; at most 81 assignments per pair). Every other finding is undecided: *not shown to join*, which may be a limit of the check (a condition its solver-free reader does not decide, a collection its unifier gives up on) as well as a defect; do not rewrite a correct equation because of one. WASM gives 2 genuine pairs (`getOrDefault` at index `-1` in `list-int.k` and `list-ref.k`: on a one-element list the first equation gives the element, the second the default) and 46 undecided ones. Two different terms that would print alike (injections from different sorts) are written with each injection's source sort, `(t : Sort)`. Findings name each equation by its written position (`FILE:LINE:COLUMN`), and show the overlap, the two reducts, the conditions the check left open and the instance as K text. The summary groups findings by equation pair, genuine pairs first, and shows the first 5 pairs per definition; the report lists all of them.

A finding can be **assumed**, a premise the user states (for a pair, assumed joined): `--assume-joined NAME` (repeatable), the campaign file's `[options] assume-joined = [NAME, ...]`, `CaseOptions::assume_joined` in the library, with each `NAME` as the finding's `name` prints it (`FIRST,SECOND@POSITION`; a compiler-generated overload axiom, which has no written position, as `overload:GREATER:LESSER` with the K labels of its overloaded pair, each in `"` when it holds `,`, `:`, `@`, a quote, a backslash or whitespace (`overload:"_,__EXPS":"_,__IDS"`; the KORE names are accepted too); a rule part may also be any trailing part of the written path, the rule's unique id or its label, and a root pair may be named in either order). Every other finding that keeps a definition without data has a name too, so that each can be assumed: an equation at an evaluated hook that is not shown to agree with the hook (a hook pair, of which one name covers every equation of the hook's written meaning, or an equation at a hook with no written meaning) is `hook:EQUATION`, another equation the evaluator does not apply to every subject it describes `equation:EQUATION`, and a precondition row `precondition:EQUATION`, or `precondition:KIND:LABELS` when it names no equation (`precondition:no-least-common-overload:A:B`), each `EQUATION` a rule part as above. Such a finding is then read as resolved: the equation as agreeing with its hook or applied as written, an overload row (`OverloadShape`, `NoLeastCommonOverload`, `PinnedByInjectiveTotal`) as met. A precondition row stating that an equation is headed by a constructor or an injection, or indexed at a collection or a bare variable, is **decided** (its `verdict`), not a limit of the check: a constructor- or injection-headed equation rewrites terms the data judgement reads as free, and one indexed at a collection states such terms equal to its right-hand side (an axiom the evaluator never applies), so they are not distinct normal forms and no end of the definition is data, whatever is assumed; its name is refused, and the remedy is to change that equation. So is an equation whose right-hand side or `ensures` leaves a variable unbound by its left-hand side (only hand-written KORE gives one): read as written it equates its left-hand side with every value of that sort, and the evaluator never applies it, so there is no premise to assume. Every other finding can be assumed: a pair, an equation at an evaluated hook, an equation computed below its root (whose premise is that its unformed inner pairs join) and an overload row. The data judgement (a data end's, and `comparable`'s `end-not-data`) then reads both definitions as if those pairs joined: when no other finding is left, the definition has data again. Every verdict of the campaign then holds for the definition read that way, not for the definition as written; that no program reaches the pair (WASM's indices are unsigned, so `getOrDefault` at `-1` is unreachable from WASM programs) does not change this, since the judgement reads the definition by its normal forms, and a genuine pair leaves some input with two whatever the inputs that reach it. The assumed pairs are part of the campaign's identity (`identity.options.assume-joined`, sorted), the report keeps their findings marked `assumed` with their verdicts (the summary's counts include them, then say how many are assumed and how many of those are genuine), a warning states the premise, and one more names each assumed pair that is genuine. An unprefixed name applies on each definition where it matches and must match the same equations (by unique id) on both; `baseline:NAME` and `mutant:NAME` apply on one definition. A name that matches no finding, more than one finding of one definition, or different findings on the two definitions is refused, and so is any name on a campaign that reads no data end. The data heads still come from the definition's load verdict, which withholds the claims an assumed pair's taint reaches, so an assumption can only leave fewer terms data than a definition in which the pair joins. This reaches plain `anywhere` heads too: assuming joined two equations of one head with different results at an overlap (`g(X) => a` beside `g(c) => b`) leaves `g` withdrawn by the load, so none of its applications becomes data under the premise.

### How the sides run

The baseline runs on all paths and the mutant on the campaign's path mode, both as state sets (`result_modality: state-set`), which report the same final configurations as path sets without exploring the paths that converge on them (`docs/compatibility.md`, "Search results").
One mutant path cannot show what the mutant's other paths reach, so in the one-path mode a case whose one mutant path is complete, adds no end and misses some baseline end is decided by a second run of the mutant on all paths, whose work the case counts.
Each side of a witness lists every leaf's configuration with its halt (`final-configurations`, `halts`; every witness kind carries `halts`, and `--replay` compares them); the witness's `clean-leaf-facts` name the conditions its kind of kill rests on.
Re-entering a witness as a test takes the instantiated program and a `krun` line per side: every witness case with a program text carries `program` (the program with each span hole's K text in its span) and, when the program has configuration-variable bindings, `config-vars` (each binding as instantiated: span holes' K text in their spans, a configuration-variable hole's K text as the whole binding; added for kink-flow fuzz, report version 7 at integration), and a differential witness carries `krun-command` for the baseline (strategy `all`, its directory left as `<definition-dir>`) and `mutant-krun-command` for the mutant (`<mutant-dir>`; strategy `all` for a removed end or the all-paths mode, `any` for an added end in the one-path mode). The summary of a differential witness prints the kind of kill, the program, each side's ends as K text (krs-unparse's pretty form; `krust krun` itself prints KORE; the first four ends of each side and the killing end wherever it lies, marked, with the count of leaves at an undefined step, which are no ends, and whose recorded configuration is the state before the undefined step) and the two `krun` lines.
The all-paths mode can refuse a kill the one-path mode takes: when a chosen value or a contradicted claim lies on another path than the killing one (on a leaf, or on the result's lists after a state-set merge), the all-paths result carries it and the case is `unsupported`, while the one path never met it and its end kills. Both are sound: the one-path kill rests only on its own path, which carries no mark, and the all-paths refusal is conservative, since it judges the result as a whole and a mark anywhere on it could stand for a path that differs in another model; it can only miss a kill.

## Library usage

kink's client is `kink-flow fuzz` (`kink/crates/kink-flow/README.md`, "Killing a survivor with `fuzz`"): it builds both definitions from kink's own admitted baseline and claim-free mutant on the `from-definition` route, decodes its templates' holes with this crate's `holes::HoleFile`, runs a differential campaign with strict data judgement (a finding is assumed only when the flow's author names it), checks each witness side's `initial-configuration` against kink's own assembly of the instantiated program (`program` and `config-vars`), and prints the program for kink's `run` to prove.

The caller compiles the definition (`CompiledDefinition::from_artifacts` takes an in-process compilation, with the loaded definition's source table, and reduces it to what `krust kcompile` stores in a compiled directory, so that both give one definition), builds a `CampaignSpec` (the definitions, the program, the holes, the target, the case options, the proposers, the seed), and runs it:

```rust
use k_rust_fuzz::{Budget, Campaign, CampaignError, CampaignSpec, FuzzReport};

fn fuzz(spec: CampaignSpec) -> Result<FuzzReport, CampaignError> {
    let mut campaign = Campaign::new(spec)?;
    Ok(campaign.run(Budget::Cases(10_000), None))
}
```

`Campaign::new` validates the spec: a mutant is given exactly for a differential target, each definition's backend is built on its route, and the holes, their generators and the target are resolved.
It assembles and round-trip-checks the program with its anchor values, and returns a `CampaignError` for every refusal (a `find` or `literal` that does not occur exactly once, overlapping spans, an anchor that does not parse back, a refused hole sort, an unknown, ambiguous or refused target, and so on).

`Campaign::run` runs cases on the calling thread until the budget (`Budget::Cases` or `Budget::Work`) is spent, a witness is confirmed and shrunk, the rejection cap is reached, every assignment of the holes' finite domains has run, or the `CancellationToken` is cancelled.
When every hole takes finitely many values (its `choices`, a `Bool`, or a closed integer range of an `Int` or `MInt` hole, as generated, so a narrowed range counts from 0) and their product is at most 4096, the loop records which assignments have been tried, and no assignment is tried twice: a case's outcome is a function of its assignment, so a proposal that repeats one is not run and is replaced by the next untried assignment in a permutation of the domain drawn from the campaign seed, credited to the same proposer (which observes it as its own case; a climb or corpus proposer thus learns from the replacement, not from the repeat it proposed). Once each assignment has been tried, after exactly as many cases as the domain has assignments when every proposal lies in it, the campaign ends without a witness and its statement says `Domain exhausted` with the number of assignments. A value outside the domain (an explicit assignment outside the choices or the range) is run and not counted. A case outside the determinism contract (a timeout) counts as tried.
The explicit proposer tries the anchors first, then the author's assignments; the other proposers are mixed by a deterministic schedule seeded from the campaign seed.
This build provides blind generation (`ProposerKind::Blind`), the dictionary (`ProposerKind::Dictionary`), the climb (`ProposerKind::Climb`) and the corpus (`ProposerKind::Corpus`), below: guard harvesting, which draws each hole, with probability 1/2, from the literals of the guards and left-hand sides of the target and of the rules at most two rule-graph edges before it, of the equations their guards call, and of the higher-priority rules an `owise` rule competes with, plus or minus 1 to 3 and negated (ARCHITECTURE 8.3; the rustdoc of `proposers::dictionary`). `Campaign::new` refuses a proposer the build does not provide.
The default `ProposerConfig` weighs blind generation alone; a positive `dictionary` weight (in the library, the campaign file's `[proposers] weights` or the bindings' `proposers.weights`) adds the dictionary, and the report then records its parameters (`identity.dictionary`).
It also provides the climb (`ProposerKind::Climb`) for rule and observer targets: targeted hill climbing, which keeps the best-scored `miss` case and proposes typed moves of one or two of its holes (integers by `±2^e` with an exponent that grows after an improvement and shrinks after a rejection, Boolean negation, single edits of strings, byte strings and collections, constructor swaps), preferring the holes whose values the scored guard read, and spends at most half of the cases, and of the work up to its last case's work (ARCHITECTURE 6.4, 8.4; the rustdoc of `proposers::climb` and `score`).
A rule target's case is scored by its rule-graph distance to the target and the branch distance of the guard that stopped it, read from the condition records the backend reports (`collectConditions`), which only a campaign with the climb, the corpus or the solve proposer requests; an observer target's case by the greatest progress (`ObserverVerdict::Progress`) its observer reported.
A positive `climb` weight needs a positive `blind` or `dictionary` weight beside it, and the report then records the climb's parameters (`identity.climb`); pattern and differential targets are refused with the climb.
A campaign whose proposers score its cases (the climb or the solve proposer) reports `totals.best-score`: how many `miss` cases were scored and the best score among them, the earliest case on a tie, with its level (the rule-graph distance; absent when no rule-graph path reaches the target) and guard distance (an exact fraction `N/D`, 0 when the guard holds), which the summary prints, so that a reader sees how near the guided search came; it is `null` when no proposer scores. The best case may be one outside the determinism contract (a `miss` decided with a solver `unknown` on a clocked solver, counted in `totals.outside-determinism`), as the schedule observes those cases too.
It also provides the corpus (`ProposerKind::Corpus`) for every target kind: coverage-guided mutation, which keeps each `miss` case that reached a rule (in coverage `applied` or `matched`) no earlier `miss` case reached, or applied a rule a number of times in a bucket (each count below 16, then 16-31, 32-63, and so on) no earlier `miss` case applied it in (k-rust's applied counts, `collectCounts`, which a campaign asks for only when it weighs the corpus), or, beside the climb or the solve proposer (which score cases), that scored better than every earlier case, and proposes one or two typed mutations of a kept case (the newest three times in four): a collection hole replaces, inserts, deletes or appends one element, keeps a prefix, or crosses over with another kept case, and every new value or element is a harvested literal of its sort (the dictionary's harvest, which here also fills collection elements), a fresh draw, a nudge of the current value (for a record, one field, at any depth, so one field of one transaction in a list), or a splice from another kept case (ARCHITECTURE 8.5; the rustdoc of `proposers::corpus`).
It pays off on sequence-shaped holes, such as a `List` of transactions processed in a loop, whose progress lives in cells that neither the rule graph nor the climb's score sees; it spends at most half of the cases (and of the work, up to its last case's work), needs a positive `blind` or `dictionary` weight beside it, and the report then records its parameters (`identity.corpus`).
Where every step of a loop fires the same rule, the applied counts make a step more progress: a list of keys in a window, consumed by one rule, is followed one key at a time (the tally). The counts cannot tell progress from noise: where another rule's count follows the data too (work after the loop over the input left over, such as a map lookup per remaining item or a rule that drains the rest), a mutation that only lengthens that leftover also reaches a new bucket, is kept, and becomes the newest entry; on the tally with such a rule the corpus still reaches depths main never does, but at a fraction of the seeds (depth 16 at 1 to 4 of 10 held-out seeds instead of 9 or 10). Neither demoting count-only entries nor keeping only new maxima helped there (`research/stall-benchmark.md`, FZ-17 fix round). Where each step's values must also match the state (a balance, a nonce inside a record), one mutation rarely makes a whole valid step and the harvest holds none of the values; there the corpus gains little alone, and the run-time literals below supply the values (`research/stall-benchmark.md` in the fz26 notes, the bank).
The climb and the corpus also draw run-time literals (ARCHITECTURE 8.3; the rustdoc of `proposers::runtime`): for a rule target, their campaigns record the condition entries of the rules whose guards the dictionary's harvest reads (the target, the rules at most two rule-graph edges before it, and the higher-priority rules they compete with), and a case's pool is the comparisons in each such guard's last refuted entry that refuted it (below nodes that refuted it, so not under a disjunction that held or an undefined node), with the two values the run compared, such as a transaction's amount and the running balance in `A ==Int B`; a rule whose records the backend truncated gives none, and the target's comparisons come first (at most 64).
A proposal from a case whose pool is not empty is, with probability 1/4, a change from it instead of a move or a mutation: one occurrence of a compared value in the case's holes, at any depth (one field of one record in a list), takes the value nearest the other operand that passes the comparison (`B` for `==`, `<=` and `>=`, `B - 1` for `<`, `B + 1` for `>` and `=/=`; a `String` equality the other string); drawn by side of a comparison, then occurrence, and the climb proposes each change at most once from the same best case.
The climb changes its best case so; the corpus a kept case, and, with probability 1/2, its own last case when that was a `miss` with a pool, up to two such follow-ups after a mutation, so that a transaction appended with a wrong nonce is repaired though it reached nothing new.
The values belong to the state of the case that compared them, so the dictionary, which builds each case from nothing, does not draw them; a campaign without the climb or the corpus records no conditions and its cases do not change.
The report records the parameters (`identity.climb` and `identity.corpus`: `runtime-probability`, `follow-probability`, `follow-depth`, `max-comparisons`, `runtime-condition-rules`, and the climb's `runtime-guard-radius`).
With the `z3` feature (native builds; the `cli` feature implies it) it also provides the solve proposer (`ProposerKind::Solve`) for rule targets (ARCHITECTURE 8.6; the rustdoc of `proposers::solve`).
Every `miss` case that entered and refuted a guard on the target's keyed chain (the target, its predecessors whose right-hand side keys `<k>`, theirs, up to 8 edges; the cases of a solving campaign record those rules' condition entries) gives a query: the case's values with the `Int` and `Bool` holes whose values that guard read made symbolic (holes of a sort hooked to `Int` under another name stay concrete).
The proposer keeps the unsettled queries (at most 64, one per rule, symbolic holes and other holes' values), ranked by the guard's distance to the target along the chain, then its guard distance; when the score has not improved for 8 cases, it asks the best-ranked one.
It runs the configuration under strategy `all` on fresh backends of its own, on a thread of its own, within 4 times the case's work plus 64 states, and asks `Backend::get_model` for a model of the constraint of a leaf whose path applied the blocked rule (up to 4 leaves), with the holes' declared constraints conjoined.
A model is a candidate case like any other: admissible values, the round-trip check, and confirmation on a fresh backend.
Every query is asked once: whatever it answers (a candidate, no path, no model, an undecided model, a run stopped by a cancellation or the per-case safety limit, which is charged at least 1 work), it is settled and the next pending query is asked at the next draw while the stall lasts. A blocked rule with a given set of symbolic holes is given up for the campaign after 4 settled queries that gave no candidate.
The proposer's solver is clock-free (`BackendOptions::smt_resource_limit`): each decision of its run gets 250,000 Z3 resource units with 2 retries at doubled units, each model query 2,000,000 with 2 retries, and an undecided model query is a deterministic "no candidate", and an undecided decision of the run is handled as the backend handles any undecided answer (an indeterminate step, or both sides kept).
It spends at most a quarter of the cases and of the work; the work of its runs (states visited) and model queries (1 each) counts in its share and in `totals.work` before its candidate runs, so the share, and a work budget, may be exceeded by one run's bound plus one case's work.
A positive `solve` weight needs a positive `blind` or `dictionary` weight beside it; the report then records its parameters (`identity.solve`, with the unit budgets and the Z3 version that counts them) and its runs (`totals.solve`).
A build without the `z3` feature, and the WebAssembly package, refuse a positive `solve` weight.
The guided proposers (the climb, the corpus and the solve proposer) together also spend at most half of the cases and work, so blind sampling and the dictionary keep at least half whatever the weights (`engine::schedule`); the solve proposer's runs and model queries count in that work before its candidate runs.
A candidate hit becomes a witness only after a confirmation on a fresh backend agrees.
A confirmed witness is then shrunk (unless the options turn `shrink` off), within at most 256 candidate runs, each candidate confirmed as the witness was: every hole first tries its least value (the admissible integer nearest 0, or the shortest admissible prefix of a string, byte string or collection), a blindly drawn value then shrinks along its value tree, and passes of bisecting moves towards the least values repeat over every hole while one of them makes progress. So a hole the witness does not need ends at its least value, and a hole that could shrink only after another one did is moved again (TRIAL2's `M = 8, N = 8` ends at `M = 1, N = 0`).
Each move changes one hole: a witness that rests on a relation between holes (a kill that needs `X * 2 == Y + 1000` exactly) keeps it only through values where one hole alone can move, so its shrunk form may be larger than the smallest assignment that keeps the relation, and when no single-hole move keeps the hit the report has no shrunk witness (`X = Y = 1000` stays as it is, though `X = 500, Y = 0` also kills).
Each run starts from fresh proposer state, so a second run reports exactly what a fresh campaign with the same spec and budget reports.
The `FuzzReport` (`to_canonical_json` gives its canonical bytes) is a function of the definitions, program, holes, target, options, budget, seed, the k-rust revision, the k-rust-fuzz revision (`identity.fuzz-revision`, below), the parser's diagnostic work limit (`identity.parse-diagnostic-work`, read from `KRUST_PARSE_DIAGNOSTIC_WORK`: it changes the text of parse diagnostics a warning may quote) and `ENGINE_VERSION`, and for a solving campaign also of the Z3 version (`identity.solve.z3-version`), whose search counts the solver's resource units: the solver reads no clock, so its answers, `unknown` included, do not depend on the machine's speed or load.
Every source location a report names (`totals.coverage.names`, `identity.target-rule`, the positions of `definition-findings`) is the source's path relative to the directory of the main module's file (`imp.k`, `lib/expr.k`, `../lib/x.k`, a builtin by its `krust-builtin://` URI), as the identity's digests name sources, so the same definition compiled in two directories gives the same report, byte for byte.
The exceptions are counted or named, never hidden: cases outside the determinism contract (`totals.outside-determinism`; the cases run on the case options' clocked solver, as in every campaign), the solver's runs that a stack stop, a cancellation or the per-case safety limit ended (`totals.solve.outside-determinism`), and a witness's `comparable` judgement made outside its case (without `comparable-end`, for a witness whose case ran one path, stopped at the target rule or ran `at: any-state`), which names the clock, solver `unknown`, stack stop, allowance refusal or failed run that put its run outside the contract among its reasons; its work counts in `totals.work`, and replay does not compare such a judgement.
A case outside the determinism contract may end otherwise on another run (a timeout may be a hit there, which ends the campaign), and the schedule, the guided proposers and a work budget observe every case, so every later case depends on it: a report whose `outside-determinism` is above 0 reproduces exactly only up to its first such case (`totals.first-outside-determinism`, counted from 0), and may differ from that case on. A solve run outside the contract (`totals.solve.outside-determinism`) decides what the solve proposer proposes, so the first case proposed after it counts too, and so does a candidate whose confirmation ran outside the contract (a `timeout` case, no engine defect, since another run may confirm it). The no-witness statement says so, and so does the summary of a report with a witness.

### Report fields

Fields of the report that the sections above do not describe, as a client reads them (each type's rustdoc in `report.rs` is the full reference; the TypeScript declarations of the bindings mirror them):

- `identity.k-rust-revision` and `identity.fuzz-revision`: the k-rust build that ran the cases and the k-rust-fuzz build that classified, judged and reported them ([Command line](#command-line) says how each is derived).
- `identity.program-digest`: the SHA-256 of the program (its name as written, start sort and text, and the configuration-variable bindings, or the printed KORE template); `identity.overlay-digest`: of the hole declarations' canonical JSON; `identity.target-digest`: of the target's canonical JSON. `identity.definitions[]` holds each definition's digests ([Command line](#command-line)).
- `identity.caps`: the hard caps of this build's generators (`int-bits`, `length`, `depth`, `enumeration`, `value-size`), which bound every value whatever the bounds and constraints ask; `identity.bounds` the generation bounds used; `identity.rejection-cap` the rejected cases after which the campaign ends `rejected-out`, as a decimal string.
- `identity.dictionary`, `climb`, `corpus` and `solve`: each proposer's fixed parameters, present exactly when its weight is positive; they only choose cases, so replay does not compare them.
- `identity.parse-diagnostic-work`: `unlimited`, or the parser's diagnostic floor in chart steps, as a decimal string.
- `totals.rejection-rate-permille`: rejected cases per thousand cases, rounded down.
- `totals.target-blocked`: cases in which the rule target's guard was entered and refuted (the target blocked).
- `totals.unconfirmed`: candidates that reached the target but whose confirmation on a fresh backend failed, disagreed (an engine defect) or was cancelled; one of them may be a real witness.
- `totals.outside-determinism` and `totals.first-outside-determinism`: above.
- `totals.case-sequence-digest`: a SHA-256 chained over the proposed values of every case, in order, so that two runs that diverged are told apart even when every case had the same class; the golden test pins it per `ENGINE_VERSION`.
- `load-records`: the records each definition's load observed (`contradicted-claim`, `allowance-refusal`, `unsupported-hook`, `stack-stop`, with the backend's detail), once per campaign; they taint no leaf of the fuzz's own verdicts, and `comparable-end` reads them.
- `sort-overrides`: each refusal of a hole sort that `allow-refused-sort` admitted (the hole, the refused sort, the refusal).
- `warnings`: sentences for a reader (an `every-k` normal end, a narrowed hole, an assumed finding, a vacuous pattern, a statically unreachable target, and so on); they change no verdict.
- `engine-defects`: a defect of the engine met while judging a case (a case and its confirmation disagreeing, a halt the request never asks for, a rule applied outside the rule graph), with the case when there is one; never reported as a hit.

The Node-API (`k-rust-napi`) and WebAssembly (`k-rust-wasm`) packages run one campaign per call, `runFuzzCampaign`, from the specification's JSON form, and return this report; without a caller identity they record the same k-rust build identity as `krust-fuzz` (below).
Observer targets are library-only, and the WebAssembly package has neither the solve proposer nor a per-case safety limit ([k-rust-napi](../k-rust-napi/README.md#fuzzing-example), [k-rust-wasm](../k-rust-wasm/README.md#fuzzing-example)).

## Command line

The `krust-fuzz` executable runs the same campaign from a compiled directory, a program and a campaign file (ARCHITECTURE 9.4).
It needs k-rust's `cli` feature, which loads compiled directories (and implies Z3), so it is built with this crate's `cli` feature: `cargo build -p k-rust-fuzz --features cli,z3-gh-release`.
`z3-gh-release` links the Z3 release that k-rust's default features download, as `krust` does; with `cli` alone, a build of this package links the Z3 the build environment provides (README, "Install and build").
`krust fuzz ARGS` runs it, as `cargo` runs `cargo-NAME`.
krust looks for an executable `krust-fuzz` beside itself, then on `PATH`, skipping files that are not executable.
It passes the arguments after `fuzz` exactly as given (a leading `--` included) and its own k-rust build identity, and `krust-fuzz` refuses to run (exit status 2, "version skew") when it was built from other k-rust sources.
krust forwards before it reads its own environment, so an environment error (an unreadable `KRUST_PARSE_DIAGNOSTIC_WORK`) is `krust-fuzz`'s, with status 2.
When no `krust-fuzz` is found or it cannot be started, `krust fuzz` exits with status 2, never with `krust-fuzz`'s "no witness" status 1.
Each release ships `krust-fuzz` in its own archive (package `k-rust-fuzz`, built with `cli` and `z3-gh-release`) for every target `krust` ships for, with a shell installer that puts it in the directory where `krust`'s puts `krust`; the two packages share k-rust's version, so one release tag ships both (README, "Install and build").

```text
krust fuzz --definition imp-kompiled --program transfer.imp --campaign holes.toml \
  --reach-rule IMP.overflow --max-work 100000 --cases 5000 --seed 0x5eed --json
krust fuzz --campaign holes.toml --reach-rule imp.k:47
krust fuzz --replay witness.json
```

A rule target (`--reach-rule RULE`, the file's `rule`) names one rule of the definition's catalog, read by the shape of `RULE`:
`FILE:LINE`, where `LINE` is a decimal number, is a source position, any line from the rule's first to its last, as kink lists uncovered rules (`imp.k:47`). `FILE:FIRST-LAST`, the range the summary prints for a rule written on several lines (`calc.k:28-30`), names the rule that spans `FIRST`, as `FILE:FIRST` does, and is refused before any case unless that rule spans `LAST` too (a range past one rule may name another); the summary's `target rule:` line shows the rule chosen.
`FILE` must name exactly one file of the definition, whose files are named by their paths relative to the directory of the main module's file and are also known by the paths the compiled directory recorded (absolute for `krust kcompile`): a whole path, relative or recorded, names its file; otherwise the files whose relative or recorded path it is a suffix of after a `/` (`defs/sub/main.k`, written from the checkout's root); otherwise the longest relative path it ends with after a `/` (a path from another checkout); a leading `./` is dropped, and a `FILE` that names several files is refused, whatever the line, with the files listed.
Exactly 64 hexadecimal digits are a unique id, as the report names rules and the summary's `krun` line prints them; any other text is a label, `IMP.neg` or, when no label is that, `neg`.
Every rule has a source position and a unique id, so a label of either shape is still named by those, and unlabelled rules (most of SIMPLE's, IMP's expression rules) need no labelled copy of the definition.
A reference that names no rule is refused with what can be named instead: the nearest labels and the number of unlabelled rules, the rules written nearest the line, or the files that hold rules; one that names several rules lists them with their unique ids.
The report's `identity.target-rule` names the rule a rule target resolved to, and its `totals.coverage.names` gives every reached id its kind, label and source locations; each location's `source` is the file's path relative to the directory of the main module's file (`imp.k`, `lib/expr.k`), never the path the definition was compiled at, and its `reference` is the shortest suffix of that path that names its file alone, so `reference:line` (or `reference:first-last`) as printed is a valid `RULE`.
The summary names the target rule, then lists the rewrite rules the cases applied, and those whose condition was entered but which never applied, by source position, label and unique id.

A compiled directory is loaded as `krust krun --definition` loads it (`k_rust::native::load_runnable_artifact`, plus the directory's `syntaxDefinition.kore` and `macros.kore`, which printing and reading back data values need), and every backend is built on krun's route, with the compiler's rewrite order.
The program's path as written names it, as `krust krun` names a program: span holes address that name, and the program's locations carry it.
The start sort defaults to the sort of `$PGM`.

The campaign file holds the `[[hole]]` declarations of [Hole declarations](#hole-declarations) and, optionally, everything else; paths in the file are relative to its directory.
Every flag overrides the file: each switch has a negation (`--one-path`, `--no-run-to-completion`, `--no-negated-property`, `--data-end`, `--no-comparable`, `--shrink`), and a target named by flags replaces the file's target kind with its `mode` and `at`.
`--rule-mode` and `mode` are refused unless the target is a rule, `--at` and `at` unless it is a pattern, and `--mutant` selects the differential target only when no other target is named (a mutant with a rule or pattern target is refused).
A pattern the campaign refuses (it does not parse, or its `requires` reads a variable its configuration does not bind) is named by where it came from (`--pattern`, `--normal-end`, or the key and table of the campaign file), with positions as lines and columns of the pattern's own text; the library's `TargetProblem::Pattern` and `CampaignError::NormalEndPattern` give the same positions.

```toml
definition = "imp-kompiled"   # --definition; `mutant` (--mutant) names a mutant: the differential target
program = "transfer.imp"      # --program; `sort` (--sort) and `config-vars = ["N=1"]` (-c) as krun takes them
seed = "0x5eed"               # --seed; `cases` (--cases) or `work` (--work) is the budget, 1000 cases by default

[target]                      # exactly one of rule, pattern, differential (OD-2)
rule = "IMP.overflow"         # --reach-rule: FILE:LINE, a unique id or a label; `mode` (--rule-mode) is fired, covered or condition-reached
# pattern = '<k> .K </k> ...' # --pattern, in krun's --pattern syntax with `requires`; `at` (--at) is final or any-state
# run-to-completion = true    # --run-to-completion; negated-property (--negated-property)
# data-end = false            # --no-data-end: accept a run-to-completion hit whose end is not data
# comparable = true           # --comparable: a hit's program must have a run of every path kink can compare

[options]                     # paths = "all-paths" (--all-paths), max-depth, max-work, normal-end-pattern,
safety-limit-seconds = 60     # shrink, smt-timeout-ms, smt-retry-limit; no-safety-limit = true (--no-safety-limit)
# assume-joined = ["list-int.k:64:3,list-int.k:71:3@root"]   # --assume-joined NAME (repeatable, added to these)

[[hole]]
name = "AMOUNT"
sort = "Int"
line = 4                      # `program` defaults to the program's name; `$NAME` addresses a binding's text
find = "amount = 250;"        # defaults to `literal`; or `column = 10` places the literal on `line`
literal = "250"
range = { min = 0, max = 1000000 }   # also `length`, `elements = { element = "Int" }`, `choices = [1, 2]`

[[hole]]
name = "TX"
sort = "Tx"
config-var = "TX"             # a configuration variable's whole value
```

`[bounds]` (`int-bits`, `length`, `depth`) and `[proposers]` (`anchors-first`, `weights`, `explicit = [{ AMOUNT = 7 }]`) map onto `GenerationBounds` and `ProposerConfig`.
A value is written as a TOML integer (an `Int`, or the unsigned value of an `MInt{N}` hole), boolean or string, or as a table in the library's JSON form, such as `{ int = "123456789012345678901234567890" }` or `{ list = [{ int = "1" }] }`.
A `range` or `length` bound is a TOML integer, or a decimal string for a bound beyond 64 bits (`max = "115792089237316195423570985008687907853269984665640564039457584007913129639935"`); the table form is not accepted there.

Every case has a wall-clock safety limit of 60 seconds unless `--safety-limit SECONDS` or `--no-safety-limit` says otherwise (D24): `max-work` counts steps, and a step whose ground function evaluation does not terminate would otherwise never end.
The limit bounds each execution of a case, so a differential case (baseline, mutant, and in the one-path mode possibly the mutant's all-paths re-run) can take up to about three times it.
A limit of 0 seconds, which would stop every case, is refused, and so is a campaign file that sets both `safety-limit-seconds` and `no-safety-limit`.
A case the limit stops is `timeout` and outside the determinism contract; the report's options record the limit.
The library sets no limit by default.
The campaign runs on a thread with a 256 MiB stack, which the report records.
The report's k-rust revision is always k-rust's build identity (`k_rust::build_identity`), which `krust-fuzz --version` also prints; no flag or campaign-file key can name another.
The identity is the k-rust version followed by `+src.` and a digest of the sources k-rust is built from: k-rust's build script hashes the non-test Rust sources of `k-rust`, `k-rust-kore`, `k-rust-backend` and `k-rust-regex` and the files they embed (`crates/k-rust/build/source_digest.rs` gives the exact rule); crates.io dependency versions, features and the profile are not part of it.
Builds whose k-rust sources differ, committed or not, have different identities, and `krust` and `krust-fuzz` built from one tree have the same one.
Outside this workspace's layout the build script cannot read those sources, the identity is the version followed by `+unverified`, and the skew check and `--replay` say when they compare such identities.
The report also records `identity.fuzz-revision`, this crate's build (`k_rust_fuzz::build_identity`), derived by the same rule from the sources of this crate and of `krs-unparse`, which prints hole values as program text (this crate's `build.rs`; `tests/formats.rs` checks that every path dependency outside k-rust's digest is listed): the classification, the judgements, the statements and the report are this crate's code, so a fix of any of them changes the revision. `krust-fuzz --version` prints both revisions, and the library records the fuzz revision itself, for the bindings and kink-flow too. The identity also records `identity.debug-assertions`, the build profile's fact that decides which crashes occur (a debug assertion's panic is a crash a release build does not raise).
What lies outside the identity, so that a report is a function of its identity only for one lockfile and one build configuration: the versions of the crates.io dependencies (`Cargo.lock`: `serde_json`, `num-bigint`, `sha2`, the `stacker` texts the crash classification matches, and the others; the ones the case sequence rests on, `proptest`, `rand` and `rand_chacha`, are pinned exactly in this crate's manifest and guarded by the golden test with `ENGINE_VERSION`), the features and the profile beyond debug assertions (`opt-level`), the Z3 version of the cases' clocked solver (a solving campaign records the solve proposer's, `identity.solve.z3-version`), and a witness filter's own build (kink-flow's filter is named by its `FILTER_VERSION` and components, never its build). The lockfile is not folded into the fuzz revision: it is the whole workspace's, so every dependency change of an unrelated crate would refuse every recorded witness, and k-rust's revision leaves it out for the same reason.
Sources are named by the paths the compiled directory recorded, which `krust kcompile` takes as resolved: a required file that is a symbolic link is named by its target's path, relative to the main module's directory (`../../elsewhere/x.k` for a link into another tree), so such a name depends on where the target lies.

The summary goes to standard output, or the canonical report with `--json`; `--report FILE` writes the report, and `--witness FILE` writes the witness file when a witness is found or a case crashed and removes an existing FILE otherwise, so that the file never holds an older run's witness.
Both paths are checked before the campaign runs (and must name different files), and the result is printed before they are written, so a failed write loses no result.
The exit status is 0 when a witness was found and confirmed; 1 when not: no witness within the budget (or the domain exhausted), an `equivalent` pair, a `not-comparable` campaign, `rejected-out` or `aborted`; and 2 on an error: a usage error, a refused campaign (a hole, a rule reference, a pattern), an unreadable input or environment variable, or a failed write after the result was printed.
With `--replay` it is 0 when every recorded case and crash reproduced under the recorded identity, 1 when one did not, 2 when the replay is refused (another version, an identity mismatch without `--force`, inputs that do not load), and 3 when a replay forced past identity mismatches reproduced every case: the cases repeat, but on inputs other than the recorded ones, which confirms nothing the witness file claims.

A witness file (`schema: "krust-fuzz-witness"`, `version: 2`) holds the campaign as resolved (absolute paths, every option) and the report; `--replay` refuses a witness whose report is not a `krust-fuzz-report` of the `REPORT_VERSION` this build writes (10), by its schema and version, read before the rest of the file, so an older witness gets that refusal and not an error about the fields its version lacks.
`--replay FILE` loads the recorded definitions and program, rebuilds the specification and checks that its identity is the witness's.
It compares every field of the report's identity except ten, each listed with its reason in `replay.rs` (`IDENTITY_EXCLUSIONS`): the proposers and the budget, which the replay sets itself, `options.shrink` (a replay does not shrink), the dictionary's, the climb's, the corpus's and the solve proposer's parameters (`dictionary`, `climb`, `corpus`, `solve`), which cover only the code that chooses cases, `effective-constraints`, which only bounds generation, `parse-diagnostic-work`, which changes only the text of parse diagnostics no witness case holds, and `filter`, the client's witness filter, which only chose which cases became witnesses ([Witness filters](#witness-filters)). The comparison destructures the identity, so a field added to it must be put on one side or the other. A mismatch of `execution-modality` says what it means: the witness's runs reported their paths otherwise (one leaf per path, or one per distinct configuration), so the replayed case's leaves, steps and final configurations may differ; a mismatch of `program-digest` names the program each side ran, and one of `fuzz-revision` says that a change of any k-rust-fuzz or krs-unparse source, a comment included, gives another revision, so a witness kept across commits is replayed with `--force` (status 3 when every case reproduces) or found again.
That includes the k-rust and k-rust-fuzz revisions, the engine version, the debug assertions, each definition's modules, execution digest, route, rewrite order, frontend, execution-definition and syntax-and-macro digests and initial configuration, the program, overlay and target digests, the target rule (its id and its name, whose sources are relative to the main module's file), the options, the bounds, the caps, the rejection cap, the seed, the thread stack size and the solver.
The frontend and execution-definition digests are the SHA-256 of each definition's canonical provenance JSON with its source table, which holds every sentence, attribute, term and provenance record and reads back to an equal definition; the syntax-and-macro digest hashes the two KORE files with their layout normalized. In all three, each source is named by its path relative to the directory of the file holding the main module (that file by its own name, `./imp.k`, a file beside it `./expr.k`, one outside it `./../lib/x.k`, a builtin `krust-builtin://…`), not by the absolute path a compiled directory records: the same sources compiled in another directory or checkout give the same identity, and a witness replays there. The main file's own name is part of the identity, since the report's source locations and rule references name it: the same sources under another entry name (the bindings' default `definition.k` for an `imp.k`) give another identity. Each source's contents stay digested, so any change of a source's bytes refuses the replay, a comment-only edit included.
On a mismatch it lists every difference by its path in the report (for example `definitions[0].syntax-definition-digest`) and refuses (exit status 2) unless `--force` is given.
A forced replay prints each mismatch and a `forced: replayed despite N identity mismatches` line; its exit status is 3 when every case reproduced, and 1 when one did not.
It then runs the first and, when there is one, the shrunk witness case as the campaign's only explicit assignment, without shrinking, and a case reproduces when the replay confirms a hit whose witness equals the recorded one, compared whole: the label, the clean-leaf facts and, per case, the hole values, the instantiated `program` and `config-vars`, the class, each side's role, initial and final configurations, halts, undefined-step rules (an absent list read as all `null`) and work, the reaching side, leaf, step and configuration, the kind of kill, the step count, and the `comparable` judgement of a rule or pattern witness. A witness file is evidence, so a field edited by hand does not reproduce, and the comparison destructures the witness, its cases and their sides, so a field added to any of them must be decided there. Not compared, each for a reason: `shrunk` is the second recorded case, replayed on its own; `krun-command` and `mutant-krun-command` re-run the shrunk case when there is one, so they are compared in that case's replay; `repaired-from` records the refused hit a witness filter repaired `first` from, a fact of the campaign's search that a replay, which runs no filter, cannot repeat; and the `comparable` judgements are compared only when neither names a fact that breaks determinism (`clock`, `smt-unknowns`, `stack-stops`, `allowance-refusal`) or a failed run or crash (`run-failed`, `crash`), since only a judgement made inside the determinism contract repeats; the replay then says it did not compare them. Whether a case has a judgement follows from the target kind, so a judgement on one side only is a difference, and a recorded judgement that breaks its own invariant (it holds exactly when it names no condition, names its conditions in order and once, and names hooks only for its conditions) is refused when the file is read, as are a repaired witness without a filter, a crash that records a shrunk re-run without its shrunk values, and a campaign whose k-rust revision is not its report's.
It also runs each crash's first and shrunk values the same way, and a crash reproduces when the replay reports a crash of the same kind, side and stage, from a build with the same debug assertions, at the same site when both sites are locations or causes, and, on the replay of the first values, with the same hole values, instantiated `program` and `config-vars`, `krun-command` and, for a location or cause site, `message` (on the shrunk values' replay, the same shrunk hole values); a crash of a confirmation or a comparability run re-enters through its own path, and one of a shrink candidate as a case. A crash's `phase`, `case`, `count`, `reproduced`, `shrunk-reproduced`, `determinism` and `clock` record the campaign's search, and its `shrunk-holes` the campaign's shrinking, which a replay of the values does not repeat: they are not certified. A crash that does not repeat is reported without blame ("did not repeat here; its determinism is unknown").
The replay then compares the report's fields fixed before any case with its own: `definition-findings`, `sort-overrides`, `normal-end`, `load-records`, and the warnings the campaign starts with (narrowed holes, the rule graph's, the findings'), which must open the recorded warnings. It does not certify what depends on the whole campaign: the totals, the statement, the warnings the cases added, `incidental`, `client-refusals`, `engine-defects` and `crashes-omitted`; and of the identity, the excluded fields. Its last line says so. The exit status is 0 when every case, crash and fixed field reproduced and 1 otherwise.
`--definition`, `--mutant` and `--program` relocate the recorded inputs; the identity check still applies, and the replay's revision is always this build's.
