# In-process backend port

This document tracks the port of Runtime Verification's Haskell backend to idiomatic Rust. The
reference checkout is intentionally ignored and is used as a behavioral oracle rather than as a
build dependency.

## Reference

- Repository: `runtimeverification/haskell-backend`
- Commit: `ad54c7a55085b726c4d3c2728242a7e0695b0439`
- Described version: `release-0.1.155-1-gad54c7a55`
- Local checkout: `haskell-backend/`

The current reference is a two-engine system. Booster provides the fast execution path, while Kore
provides the complete fallback for cases Booster cannot decide. The Rust implementation must port
the semantics of that combined system; reproducing Booster's incomplete subset without its Kore
fallback is not completion.

## Crate boundaries

The intended workspace structure is:

- `k-rust-kore`: host-independent KORE syntax, parser, printer, serialization, pattern traversal,
  and encoding sniff shared across the frontend and backend, the measurement counters
  (`k_rust_kore::measure`) every crate
  increments, and the well-known KORE identities (`k_rust_kore::names`: the `inj`, `kseq`,
  `dotk`, `append`, `rawTerm` symbols and the builtin sorts both halves test for). A spelling
  that crosses the KORE boundary lives there once; the frontend and the backend compare
  through its predicates instead of repeating the string.
- `k-rust-backend`: definition verification and internalization, matching, substitution,
  simplification, SMT reasoning, and rewriting. It depends on `k-rust-kore`, not on the frontend.
- `k-rust`: the K frontend and the unified `krust` binary. It compiles K to KORE and invokes
  `k-rust-backend` directly in the same process. `k_rust::backend` is the orchestration layer
  called by the CLI, RPC server, NAPI binding, and WASM binding.

Keeping the backend independent from frontend ASTs preserves KORE as the semantic boundary while
avoiding a package dependency cycle when the CLI links both halves into one static binary.

The public `Backend::execute` result carries the ordered effects committed on each `ExecutionLeaf`, including when observation is disabled.
`ExecutionResult.effects` is a compatibility copy when execution retains exactly one leaf; it is empty for multiple leaves, whose effects remain on their respective leaves.
An observed transition's effects attribute committed branch effects to that activity.

## Compiled rule catalog

`Backend::rule_catalog(module_name)` returns the compiled axioms of the same module selection used by execution.
Passing `None` selects the backend's default module.
Each `CompiledRuleOutput` has an `id`, a backend-classified `kind` (`rewrite`, `function-equation`, `simplification`, or `definedness`), `executable`, `label`, `priority`, `origins`, and `sharedIdentity` in JSON.
The catalog includes non-executable axioms with `executable: false`.
Each origin contains the backend's `Source` and `Location` attribute strings when present, and `sentence`, the sentence's place in the KORE definition the backend was given: its declaring `module` and its zero-based `index` among all of that module's sentences, whatever their kind. The source and location say where the author wrote the sentence, when the sentence says so; they need not be unique, and an axiom written in KORE or generated by the compiler may carry neither. The sentence place is unique, so it tells apart entries that share their id and their position, such as two `UNKNOWN` axioms without `Source` or `Location`. It addresses the KORE definition, not the K input.
A written sentence's kind is found by matching its source and location against an entry's origins.
A position absent from the catalog compiled to no axiom in the selected execution definition.
Equivalent written axioms form one entry with all origins in declaration order.
If distinct entries share an id, both have `sharedIdentity: true`, and the observation filter refuses that id as ambiguous.
The Node-API and WebAssembly TypeScript facades expose the same catalog through `backend.ruleCatalog(moduleName?)`.

## Module map

Run `cargo run -p algo-graph -- render module-map` to write the generated backend module-map projection to `target/algo/module-map.md`; it groups source-card algorithm IDs by their declared `k-rust-backend` site module and derives each module's counters from the graph's `measured-by` edges.

Rewrite theory lookup first preserves the top-symbol `TermIndex` sequence, then filters it by the
head of the generated `<k>` cell. The rule-side `RuleIndex` treats variables, overload members,
associative and idempotent heads, and missing or uncertain cells as wildcards; the subject side
also treats function heads and configurations with multiple `<k>` cells as uncertain, which
disables filtering. This is an over-approximation of matching: every rejected
candidate has a rigid incompatible head, while every retained candidate stays in its prior
priority and declaration position. Function, simplification, and ceil theories continue to use
only `TermIndex`.

## Behavioral slices

The port proceeds in dependency order, with differential tests against the pinned Haskell source
or its checked-in fixtures at every boundary:

1. KORE definition sharing and backend internal terms, symbols, sorts, and attributes.
2. Capture-avoiding substitution, sort-aware matching, injections, and internal collections.
3. Definition verification and internalization into indexed rewrite and equation theories.
4. Builtin evaluation and equation simplification to a fixed point.
5. Priority-aware rewrite steps, side conditions, branching, and execution bounds.
6. Z3-backed satisfiability, implication, model queries, and symbolic path constraints.
7. User-facing execution in `krust`, with the in-process backend selected by default and LLVM
   retained only as an explicit alternative compilation target.

## Completion contract

The port is complete only when all of the following are demonstrated from the current tree:

- `krust` can compile and execute representative K definitions without launching or dynamically
  linking the Haskell backend.
- The native binary includes frontend Z3 inference and backend SMT reasoning in-process.
- Supported concrete and symbolic executions agree with the pinned backend on final patterns,
  substitutions, predicates, branching, halt reasons, and rule traces.
- Function and simplification equations, rewrite priorities, injections, builtin collections, and
  relevant K hooks are covered by differential tests.
- Unsupported behavior is not silently reported as stuck or successful.
  A hook without an evaluator or applicable equations halts with a typed unsupported-hook error when every argument is constructor-like; symbolic applications remain unevaluated.
  An application whose value the definition does not determine stays unevaluated with an `UnsupportedHookUnevaluated` warning instead; one whose result is above a size bound gets that warning in term simplification, and a step or search-pattern match that would decide a condition over it, or a step that would end the run stuck on it, is the unsupported-hook error; see "Backend scope" in `compatibility.md`.
- Release and CI checks prove that the default executable path has no runtime dependency on
  `kore-exec`, `kore-rpc`, or `kore-rpc-booster`.

Incremental checkpoints may implement narrower vertical slices, but they do not reduce this
completion contract.

## JSON depth policy

The standalone KORE JSON and KAST term JSON readers and writers impose no nesting-depth limit; memory is their only parser bound.
KORE patterns and sorts are parsed, printed, encoded, compared, cloned, formatted with `Debug`, and dropped with explicit work stacks, so a decoded KORE term of any depth can be held and released on any thread.
Host and RPC ingress never keeps a client's KORE as a `serde_json::Value`, whose construction, serialization, cloning, and destruction recurse once per level.
The facade's KORE request fields (`ExecuteRequest::state`, `SearchRequest::state`, `SearchPatternRequest::state` and `pattern`, `PatternRequest::state`, `ImplicationRequest::antecedent` and `consequent`) hold `kore::ast::Pattern`: each is captured on the wire as raw JSON text, which serde_json scans with an explicit stack, and decoded by the iterative KORE JSON codec during deserialization, so a malformed KORE field is an `invalid KORE JSON` deserialization error.
`backend::deserialize_request`, used by the Node-API and WebAssembly bindings, keeps serde's default recursion limit, so a deeply nested value in any other request field is an ordinary error.
The KORE RPC transport reads each frame as raw JSON text, takes the envelope members it needs (`jsonrpc`, `method`, `id`, `params`, and `haskell-logging`) from that text while skipping the others, decodes the method's typed parameters from the raw `params` text with the recursion limit on, and echoes a rejected request, `params` value, or cancelled `id` as compacted text.
A KORE request field of any depth therefore either reaches the backend as a decoded pattern or is an ordinary decoding error, on every host and RPC route.
A KORE term or RPC `params` object that repeats a member name is likewise an ordinary decoding error: RFC 8259 leaves the meaning of repeated names undefined, and readers disagree on which occurrence counts, so such a request has no single meaning to act on.
The WebAssembly `parseProgram`, `parseKast`, and `parseKore` results embed k-rust's own KAST and KORE JSON as text rather than rebuilding it as JSON values.
The CLI KORE readers use the same iterative codecs.
The KAST definition readers, of KAST JSON version 4 and of k-rust's own `KRUST-PROVENANCE` artifacts, keep serde's recursion limit on outside a sentence's terms: each term member is kept as raw JSON text and decoded, with the sorts and labels inside it, by the iterative KAST term codec.
A `KRUST-PROVENANCE` document (version 8) is linear in the definition it holds, whatever the depth or width of its terms: an origin receipt names its origin set by index into a table of normal-form nodes, each holding its own links and references to earlier entries, so a receipt that unites the sets of the node above it and of earlier passes costs a constant number of parts; it names its destination by index into a table of anchors, each a root (module, sentence, sentence index) or one child step below an earlier anchor; term metadata is addressed by field and preorder node index; and sources are named by their table index. Writing walks each distinct set and path allocation once and reading checks and builds each table entry once and walks each annotated field once in preorder, none of it recursively. A configuration initializer of 3,000 operands (`foo(0 + 1 + ...)`) writes a 4.0 MB `frontend.json` in 0.03 s where version 7 wrote 6.3 GB in 23 s (`draft/open-issues-2026-10/units/provenance-v8.md`, acceptance).
The rest of a definition is shallow in any definition k-rust accepts: its sort checks reject nested parametric sorts, so a declaration's sort nests at most two levels, and a declaration sort nested past about 55 levels, like any other member nested past the limit, is an ordinary error.
A KAST term or sort is dropped with an explicit work list, one node at a time, so a definition whose terms nest to any depth is read, refused, or dropped on any thread, by the reader on a refusal and by its owner otherwise; the other traits of the KAST terms it returns are under the KAST term bound below.
The backend's passes recurse once per level of the patterns and terms they read: standalone verification, alias expansion, and internalization of a decoded pattern, the execution, matching, simplification, and externalization of the internal terms built from it, the destruction of those terms, and the loading of a definition, including one extended by `add-module`.
Their stack therefore grows with the depth of the input, so the backend measures that depth before the work starts and provides the stack for it, rather than bounding the input by the stack of whichever thread calls it (`crates/k-rust-backend/src/nesting.rs`).
The depth is counted as the passes descend, by a recursion of at most 64 levels that hands deeper subpatterns to explicit work lists: a sort's levels below the node that carries it, an alias application at the height of its fully unfolded body above its arguments, an `\and` with `k` term arguments as the `k` levels of the chain of binary conjunctions it is internalized as, and an associative application as the chain it folds into (a collection's elements and units fold flat).
An operation's depth is the deepest of its request's patterns above the deepest pattern of its definition, since a rule places the request's terms below its own.
The stack it needs is that depth times a per-level bound (24 KiB in an unoptimized build, 6 KiB at opt-level 1 or with debug assertions, which covers the default `dev` profile, and 4 KiB in an optimized build without debug assertions; the deepest measured level took 19 KiB unoptimized, internalizing an `\and` level, and 4.0 KiB at opt-level 1 and 3.1 KiB in a release build, simplifying ground function chains), plus the simplifier's 128 KiB red zone.
Every facade operation over a request's patterns (`Backend::with_solver_over`, used by the Node-API, WebAssembly, and RPC routes) and every other facade operation (sized by its definition alone) run whole on that stack, and so does the loading of a definition, in three parts: its declarations on the stack of their depth, each axiom and claim on the stack of its own depth, measured just before it is verified, and the passes after verification on the stack of the deepest of them all.
Each runs on the current thread when its remaining stack covers the need, and otherwise on a stack segment of exactly that size, which is reserved address space whose pages are committed only as the work touches them.
The operation converts its results to their external form, KORE JSON text or values, and drops its internal terms before it returns, inside that stack; a loaded definition drops its internal rules on a segment sized for them as well, and alias expansion also provides the stack for each alias body where it enters it.
A segment is provided only where the thread's own stack is smaller, so the work always has at least the stack the calling thread would have given it.
An error outlives the stack of the work that found it, so a `DefinitionError` names its sorts and variables in their KORE form, which is cloned, compared, formatted, and dropped with explicit work stacks: an error from a failed operation or load is handled on any thread whatever the depth of the sort it names.
Only work that needs more than 4 GiB of stack (256 MiB in a 32-bit process), about a million levels in a release build, 700,000 in the `dev` profile, and 170,000 in an unoptimized build, is refused, before any pass over it runs, with the ordinary error `DefinitionError::InsufficientStack`; work whose segment is within that limit and which the system refuses to map is refused the same way with `DefinitionError::StackSegmentRefused`, which names the refused mapping instead of a depth limit the work did not reach.
Every site that runs work on a segment it sizes (this one, the simplifier's segments below, and the frontend's pre-sizing in `crates/k-rust/src/stack.rs`) maps it through one primitive, `nesting::map_segment`, which returns `SegmentRefused` when the system refuses the mapping; `stacker`, which maps it, reports the failed mapping as a panic, so the process's panic hook prints that panic's text before the refusal is reported.
A definition or module with a sentence that deep is refused with that error whatever else is wrong with it, although loading reads its declarations, and verifies the sentences before that one, before it measures that sentence.
Alias unfolding is bounded in size and time as well as in depth.
An alias body can apply further aliases and use a parameter several times, so a definition of a few kilobytes can imply an unfolding exponentially larger than itself.
Loading never unfolds an alias body: it measures once, as a function of the sizes of the alias's arguments, what unfolding an application of it builds (the unfolded body, and each alias application it enters on the way), in time linear in the definition, which also finds every alias cycle and malformed alias application, and every pattern is measured the same way before it is unfolded.
A binder renamed to avoid capture gets a longer name than it is written with, which the size spent counts at the longest index the operation can reach, so what is built never exceeds what is spent; otherwise unfolding builds exactly what is measured: an argument that an alias keeps no copy of, because the body ignores it or only uses it under a binder that shadows it, is never unfolded, and an argument it keeps is unfolded once and moved into its last copy; the free variables that capture-avoiding renaming needs are computed once per node, by merging the smaller set into the larger, and each binder of an alias body checks the parameters substituted under the body's binders with one lookup each, a check the measure counts with the applications the body enters.
A binder renamed to avoid capture resumes the search for a fresh name of its base where the last one stopped, so each candidate is tried at most once per pattern, and a rejected candidate is the name of a variable already built or of a variable of an alias body entered.
So unfolding takes time near-linear in what it builds and checks, plus the variables of the alias bodies it enters that are named like fresh names, however many free variables the arguments have: 18 to 150 ns per measured unit in a release build on the shapes measured, with the stack provided up front, and 0.55 s for an unfolding of 98% of 2^22 units.
Unfolding is charged to the operation that supplied the patterns unfolded: a request, a definition (the axioms of the modules it is given with, together), or one module added to it later (`BackendSession::add_module`, as an RPC `add-module` request does).
An operation whose unfolding would add more pattern and sort nodes, name bytes, and capture checks than the larger of 2^22 and 32 times the size of what it supplied (the request pattern; every axiom, claim, and alias body of its modules) is refused with the ordinary error `DefinitionError::AliasUnfoldingTooLarge` before any of it is built (`crates/k-rust-backend/src/alias.rs`, `UNFOLDING_LIMIT` and `UNFOLDING_FACTOR`); an alias itself is not refused for its size, which depends on what it is applied to.
The bound is relative because what an exponential unfolding exploits is the ratio of what is built to what was sent: a small module still gets only 2^22, while a definition whose unfolding is polynomial in its size, such as a closed alias that many axioms apply, loads at a cost within a constant factor of its own size; a module added to a large definition is held to its own size, not the definition's.
A unit of the measure costs from about 28 bytes of peak memory and 47 ns once internalized (closed bodies with long names) to about 235 bytes and 290 ns (one-byte variables), so 1 MB of KORE may make one operation build from about 0.4 to about 5 GB; the same shapes written out cost at least as much per unit.
The KORE RPC server writes each response, and drops it, with explicit work stacks, so a response carrying deep KORE as JSON values is written on any thread; `add-module` encodes the location of a module's error on a stack sized for the module.
The Node-API and WebAssembly `simplify`, `implies`, `getModel` and `prove` methods write their JSON text inside the operation (`Backend::simplify_json`, `implies_json`, `get_model_json`, `prove_json`), as the execution and search methods do, so the host thread holds only text; a proof leaf held as a `serde_json::Value` and serialized on the caller's thread overflowed a 256 KiB thread from about 800 levels.
On a native host, a request whose KORE is not a well-formed pattern of the definition, or a module that is not a well-formed extension of it, is therefore an ordinary error at any depth up to that limit, and a well-formed one is run.
On wasm32 the engine's call-stack limit is invisible to the module and its stack cannot be switched, so the passes run on the engine's stack there, unmeasured, as the simplifier's guard is, and a pattern too deep for it traps, which the JavaScript host reports; a native thread whose stack bounds cannot be read is likewise used as it is.
The WebAssembly module is linked with an 8 MiB stack, the size of a native main thread, where Rust's wasm32 default is 1 MiB (`crates/k-rust-wasm/build.rs`; the release module's `__stack_pointer` starts at 8,388,608).
The stack is the first 8 MiB of the module's linear memory, below its data and heap, so an instance starts with 7 MiB more linear memory (9.0 MiB in all, where it was 1.8 MiB); the pages are reserved at instantiation and become resident only as a recursion touches them (Node 24's resident memory after instantiation is the same for both sizes).
Under Node 24, through `node:wasi` and a release `wasm32-wasip1` build of the same portable code, a program nesting one level per statement traps when it is parsed from about 960 levels on the 1 MiB stack, and a nested function application traps when it is simplified from about 480.
With 8 MiB, the engine's own call stack (V8's default, about 1 MB) binds first: parsing traps from about 1,800 levels and simplification from about 930, with `RangeError: Maximum call stack size exceeded`.
A host whose engine stack is larger reaches what the 8 MiB hold, about 7,700 and 3,900 levels (Node with `--stack-size=7000`).
In a `dev` build (`wasm-pack build --dev`, what CI's package test runs) parsing traps from about 920 levels on 1 MiB and passes about 1,800 on 8 MiB, but the engine's call stack binds simplification at about 390 nested calls on either stack, so the package test checks the 8 MiB stack with a 1,400-statement parse only.
`krun` validates, internalizes and executes its initial configuration on the stack measured from it and its definition (`BackendDefinition::with_stack_for`), so a configuration as deep as macro expansion makes it runs or is refused with `InsufficientStack`; `kore-exec` and `kore-match-disjunction` do the same with the patterns they read from files (the initial and search patterns, the match pattern and the disjunction), including printing the result.
In the frontend, the recursions whose depth their callers do not measure check the remaining stack at every level and continue on a fresh 16 MiB segment when less than 256 KiB remains (`crates/k-rust/src/stack.rs`): copying and comparing a KAST term, sort injection and its sort inference, term-construction minimization, the ordering of cells in cell concretization, the conversion of KAST terms to KORE, the KAST text reader, which therefore reads terms and sorts of any depth on a native host, and every pass of the inner parser after recognition (the packed-forest and owned-tree disambiguation passes, portable and Z3 sort inference, list completion, lowering), whose packed forests and owned trees are dropped one node at a time.
The inner parser's recognition skips the Earley completions that no parse of the input can contain (`PredictionMode`): an item that cannot continue with the next token, and one whose node could reach the root only through callers that cannot hold it or cannot finish. A caller cannot hold the node when a relation forbids it there: the associativity relation on that side, or the priority, cast or scope restrictions, each of which drops the caller's node when it completes (a rewrite, sequence or `#let` below an operator denotes nothing and is a scope error like any other violation). A caller cannot finish when the first token its rest needs does not occur in the input after the node, in order along the chain of callers: in `rule foo(0 + 1 + ...) => .K`, a sum starting after the first operand could be the left operand of the rule's `=>`, but `foo(` would then need a `)` after that `=>`. A chain written directly as a side of a rewrite, with nothing to delimit it from the `=>` (`rule <k> 0 + 1 + ... => .K ... </k>` with `+` left-associative, or a right-associative chain on the right of the `=>`), has a reading for each operand, `0 + ... + (k + ... => .K)`, that puts the rewrite below `+`; every sum starting after the first operand lies only in such readings, which the scope restriction drops, so those sums are skipped. So a program or rule body that parses does so in chart work and memory linear in its length whether it is a nesting (also of a parametric production such as `syntax {S} S ::= wrap(S)`), a right-recursive list (`Stmt Stmts`, `List{Int, ","}`, `Stmt Stmt [right]`) or an associativity-disambiguated chain (`E "+" E [left]`), also where its sort has other operators that could take a partial chain as an operand: the K prelude's `#And`, `#Or` and `#Implies` at every sort, a lower-priority operator (`E "*" E [left] > E "+" E [left]`), and a rule body's rewrite and casts, also beside another token that can begin a rewrite, sequence or `#let` (`rule <k> 0 + 1 + ... => .K ~> foo(0) ... </k>`). A flat `~>` sequence written directly against the rewrite (`rule <k> foo(0) ~> foo(1) ~> ... => .K </k>`) is such a chain: its sequences starting after the first item would put the rewrite below `~>`. What a completion gives a caller depends only on the caller's production and dot, so it is decided once per group of callers that share them (and every caller of a refused group is skipped without reading its derivations). In a release build, a compile of a definition with one such rule (2.4 billion instructions with a one-item rule) retires 2.6 / 2.7 / 3.0 / 4.9 / 12.5 billion instructions with a `+` chain of 250 / 500 / 1,000 / 4,000 / 16,000 operands beside a sequence (`=> .K ~> foo(0)`), about the same as beside the rule's only `=>` (12.2 billion and 2.5 s at 16,000), and 2.8 / 3.1 / 3.8 / 8.0 / 25.3 billion (3.5 s CPU at 16,000) with a `~>` sequence of as many items against the rewrite; when the readings that put the rewrite below an operator were kept for the preference among an ambiguity's readings, both were cubic (66 and 185 billion instructions at 1,000). 100,000 nested levels or 100,000 statements run through `krun` in a few seconds and under 1 GB, and `kast` reads a 20,000-operand `+` chain under the prelude in 0.9 s, in a release build.
One shape of a rule body is not linear: a comma-separated list in the argument of a prefix symbol, `foo(0, 1, ...)` with `syntax Ints ::= List{Int, ","}`. The rule grammar also reads it as the generic application `#KApply` of `foo` to a `K "," K` list whose elements may themselves be sublists (each run of the numbers read as an `Ints` is a `K`), one reading per way of cutting the list, and every reading can be completed, so neither the relations nor the input remove any of them; only `foo`'s arity, applied after parsing, does. Their chart and packed forest grow faster than the square of the length (the Earley completion candidates about sixfold from 80 to 160 elements) and the passes over the forest at least as fast: in a release build 80 elements compile in 0.45 s, 160 in 2.4 s and 507 MB, and 320 in 29 s and 3.3 GB, about twelve times the time and six times the memory per doubling. (The readings are no longer also enumerated one argument vector at a time, nor the shared readings below each ambiguity compared anew for every ambiguity above, which made the cost exponential: 25 elements took 108 s and 4.1 GB.)
The diagnostic of a parse that fails is that of the context-free grammar, of which the priority and associativity relations only filter the parses: where the grammar's longest viable prefix of the input ends, or, when the grammar derives the input, a relation that a derivation of the input breaks, read from the forest of those derivations (a node that repeats itself over one span left out), never one met only on a node no derivation contains. The failed parse is therefore recognized again without the pruning the relations allow, and, when that recognition met a violation, once more with the relations ignored, deciding only which items exist (the parse forest is built only when the grammar derives the input, and only the passes over it that can report an error are run). For an associativity-disambiguated chain that is the Earley chart of an ambiguous grammar, cubic in its length (before the limit below, a chain of n operands of `E "+" E [left]` ending in a stray `+` was refused in 0.65 s at n = 200 and 6.7 s at n = 400 in a release build, and a `[non-assoc]` chain in 3 to 7 s at n = 50), and no reorganisation makes it linear: whether an ambiguous context-free grammar derives an input, and where its longest viable prefix ends, is general context-free recognition. So the work after the first attempt is limited (`DiagnosticWork`): the recognizer charges one step per item it takes from an agenda, per derivation the item reads and per caller a completion advances, and the passes over a relation-free forest as many steps again as the recognition that built it; the limit is the larger of a floor (2^20 steps by default; `KRUST_PARSE_DIAGNOSTIC_WORK` sets it, or `unlimited`, and `krust` refuses any other value) and 16 times the first attempt's steps. Past it the failure is reported by the first attempt's own `NoParse`, the first position past which no reading that respects the relations can be completed with the rest of the input, marked with the limit (`work_limit`) and saying that whether a reading that breaks a relation exists was not decided (an input that only breaks a relation is then reported at the operator the relation forbids, and an unclosed parenthesis at its first operand, since the recognition also skips readings whose tokens the rest of the input lacks); `ProgramParser::parse_configuration_k_value`, which tries the `K` entry only when the `KItem` entry has no reading, decides such an attempt again without the limit when the `K` entry accepts, so acceptance never depends on the limit. A failed parse therefore takes chart work linear in the work of its first attempt, plus the floor (`a_failed_chain_is_diagnosed_in_work_linear_in_its_length` in [parser.rs](../crates/k-rust/src/inner/parser.rs)). With the default floor, in a release build, the stray-`+` chain is explained up to about 100 operands (60 ms) and reported unexplained in about 0.1 s from 200 to 1,600 operands, then in time linear in its length (0.12 s at 3,200, 0.23 s at 6,400); a `[non-assoc]` chain, whose explanation builds and filters the relation-free forest, is explained up to about 40 operands (0.5 s) and reported unexplained in 0.1 to 0.7 s beyond; and `rule foo(0 + ... + B:Bool) => .K` is explained at 100 operands and reported unexplained from 250 to 2,000, the whole `kcompile` taking 0.25 to 0.33 s (0.16 s at 10 operands).
The exception is a forest that Z3 types (an ambiguous forest the portable decision does not settle, such as one with a parametric production the portable engine leaves to it): Z3 interns its constraint terms in time that grows faster than the forest, 7.5 s for 16,000 nested ambiguities in a release build.
What remains bounded by the calling thread's stack, and why each such recursion is accepted, is listed in [Stack bounds](#stack-bounds).
`kcompile` runs each compile stage, the structural checks before them, the emission of the compiled definition and the writing of its artifacts on a stack measured from the deepest term of the definitions the step reads, twice that depth for what a stage may build before it walks it (`DeepestTerm` in `crates/k-rust/src/kompile/pipeline.rs`). Loading runs configuration expansion, and the walks after it over the initializer rules expansion generates, the same way, on a stack measured from the deepest configuration term (rule bodies are still unparsed there): a configuration cell initialised with a long collection literal or a deep term loads as the same literal in a rule body does. A `~>` sequence counts as deep as its length, since the conversion to KORE nests its items into a `kseq` chain one level per item that emission walks; a rule whose right-hand side is a sequence of 128,000 items compiles on an 8 MiB main thread in 39 s and 5.5 GB in a release build, bounded by time and memory rather than by stack. The passes recurse once per level of a rule body and are given a per-level bound (2 KiB in an optimized build, 4 KiB at opt-level 1 or with debug assertions, 16 KiB unoptimized: twice the most measured on a segment of exactly that size), on the current thread when it has that much and on a segment of that size otherwise. A definition whose terms need more than 4 GiB of stack (about a million levels in a release build) is refused, before the stage runs, with a `TermTooDeep` error at the sentence that holds the deepest term. Compiling a deep rule body takes time and memory near-linear in its depth: `rule foo(0 + 1 + ...) => .K` compiles in 1.5 s and 0.20 GB at 8,000 operands and 1.7 s and 0.31 GB at 16,000, in a release build (user time and peak memory), where cell concretization and sort injection took 14 s and 7 s of 22 s at 16,000 before each receipted node's origin set named the sets it unites instead of copying their links (term-construction minimization, which once copied every left-hand subterm into its map, O(N × h), now numbers subterms, and a term a pass places unchanged under a node it builds is not receipted node by node).
No RPC or host surface applies a denial-of-service depth cap; process memory limits belong to the embedding application or process supervisor.

## Simplification iteration budgets

The backend limits simplification per fixed-point lineage rather than counting whole-pattern passes as Booster's `--equation-max-iterations` does.
The budget bounds the simplifier's own fixed point: rounds that apply simplification rules or builtins, and function equations over symbolic redexes or with residual definedness or `ensures` obligations, where a cut leaves a term equal to the input.
A function equation applied to a variable-free redex whose conditions are decided and whose result carries no constraint is a step of the definition's own computation with a determined value; it consumes no budget, because a cut there could only leave the application unevaluated and execution `Stuck` at a configuration the definition does not produce.
Determined ground function evaluation therefore runs to its value, bounded only by the caller's step deadline or cancellation and by the simplifier's stack (the typed `StackExhausted` error below); no default option bounds it, as no default option bounds the rewrite depth.
Execution, search, and proof configuration simplification follow Booster's exhaustion outcome: they retain the partial term or the original unsimplified constraints, record a `SimplificationBudgetExhausted` diagnostic, and continue.
Execution records every backend diagnostic on the `ExecutionLeaf` of the path whose work emitted it, or, for a state-set leaf, of a path merged into it (`ExecutionLeaf::diagnostics`), each distinct diagnostic once per path in first-occurrence order: a state's own constraint and term simplification belongs to its path; in the rewrite step, each unit of work belongs to the candidates derived from its result, in emission order: a right-hand-side alternative's construction to its candidate, one application group's matching, recovery and conditions (a match split yields one group per sub-case) to that group's candidates and to the remainder, whose constraint negates the group's applicability, and the remainder's simplification and the lower-priority work on it to the remainder and the candidates derived from it; a step that halts the state belongs to its leaf; the simplification of a leaf or candidate pattern to that leaf or candidate. A branch or cut-point leaf is the parent state: it carries the parent path's diagnostics, and each candidate it reports carries its own (`AppliedRule::diagnostics`, `RemainderBranch::diagnostics`). Work no reported successor is derived from (a rule attempt that does not apply, an alternative refuted to bottom, a group the sequential step does not follow) is on no leaf, although a surrounding collector sees it; a leaf cut off by a cancellation or timeout after the step carries the work of the step and of its candidates done before the interruption. A state-set leaf into which equal final leaves were merged keeps its own trace and branch, and its list is followed by the diagnostics of every merged leaf (see the result modalities below).
The public execution response serializes a nonempty leaf `diagnostics` list as typed `BackendDiagnosticOutput` entries. Predicates in those entries use the same KORE JSON encoding as other wire predicates. An absent list means that path, and for a state-set leaf every path merged into it, emitted no diagnostic.
For a `branch` or `cut-point` leaf, the response also serializes its reported successors as `candidates` with each candidate's constrained `state`, rule `uniqueId`, optional `label`, and own `diagnostics` list; a branch's remaining candidate is `remainder` with its constrained `state`, `ruleIds`, and diagnostics. The leaf's `diagnostics` remains the parent path's list.
Search attributes diagnostics by the same rule. Each state-set result (`SearchState::diagnostics`) and path witness (`PathWitness::diagnostics`) carries the list of the path its `trace` records: the simplification of each state on the path, the rewrite-step work each successor on the path was derived from, the externalisation of the reported copy (which the work state that continues the search does not inherit), and, for a state ending in a halting step (`Stuck`, an indeterminate or failed step, a cancellation after the step), that step's work. When state-set search deduplicates converging states, the kept state reports the recorded path's list, as it reports its trace; a dropped duplicate's own work is on no entry. The work of the rewrite step `state_may_expand` runs only to classify a result bound is on no entry. An `IncompleteSearch` entry carries the list of its state's path through that state. Matching a result against a pattern-search target is work on the match, not on the path: a `SearchMatch` or `PathSearchMatch` records it in its own `diagnostics`, apart from its state's or witness's list; an undecided match has no match entry, so its incomplete entry's state carries the path's list followed by the match's. Budget exhaustion is not an `IncompleteSearch` entry: it loses no successor. The public search responses serialize these lists as optional `diagnostics` on `SearchStateOutput`, `PathWitnessOutput`, `SearchMatchOutput`, and `PathSearchMatchOutput` with the same typed encoding as execution leaves. The KORE RPC responses are unchanged.
A caller collecting with `diagnostic::collect` around an execution or a search still receives every diagnostic in emission order: a nested collection forwards each emission to the enclosing collector as if it had been emitted there directly, also when the collected operation unwinds.
The standalone term simplifier retains typed `IterationLimit` errors.
An equation's side conditions (its `requires`, the definedness obligations of its bindings, and its `ensures`) are decided in their unsimplified form when simplifying them exhausts the budget, which may leave the equation unapplied; that exhaustion is recorded as a `SimplificationBudgetExhausted` diagnostic over `Predicates` followed by a `RuleConditionUnsimplified { rule_id, origin, limit }` diagnostic naming the rule, once per rule and limit in a collection, and once per rule and limit on an execution leaf's path, where a `RuleConditionUnsimplified` follows (not necessarily directly) the exhaustion over `Predicates` with the same limit that it qualifies.
A rule there is named by its id and its `origin`, the first written sentence of its axiom, as for `UndecidedCondition`: axioms that carry neither a label nor a `UNIQUE_ID` all have the id `UNKNOWN`, so the exhaustion of one such rule is recorded apart from another's.
When simplifying an equation's side conditions fails for another reason, they are likewise decided in their unsimplified form, and the cause is recorded: an unsupported hook on constructor-like arguments as an `UnsupportedHookUnevaluated` diagnostic naming the hook, any other failure (a solver query that cannot be posed, a builtin failure, an equation with several live right-hand-side alternatives or a misplaced `\top`, an invalid builtin result) as a `RuleConditionFailed { rule_id, origin, failure }` diagnostic naming the rule and carrying the failure, once per rule and failure in a collection; its wire form is `rule-condition-failed` with `ruleId`, an optional `origin` and the failure in the `SearchFailure` encoding.
The wire forms `rule-condition-unsimplified` and `rule-condition-failed` carry `origin` as `undecided-condition` does (that sentence, the first of the rule's catalog `origins`), omitted only when the backend has no sentence for the rule; the CLI warnings name the rule as every other warning does.
The backend does not yet implement Booster's separate equation-loop detector, so a non-terminating set of simplification rules, or a function unfolding over a symbolic argument, may produce a partial configuration with a diagnostic; a non-terminating ground function computation runs until the caller's step deadline or cancellation ends it, or ends with `StackExhausted`.

## Simplification stack depth

Simplification recursion depth is bounded by native stack, not by a depth count or the iteration budget, which restarts for every equation condition and does not count determined ground function steps.
The depth that evaluation reaches is not a property of the input: a recursive function over a list of n elements, or over a term that execution built step by step, descends n levels in the simplifier from an input a few levels deep.
So the simplifier reads the current stack's bounds at each entry of its recursion (each term and predicate it simplifies, `stop::with_stack_headroom`), and when less than a 128 KiB red zone remains it goes on on a new 16 MiB segment, as long as the segments its recursion holds on the thread stay within a budget, `nesting::SIMPLIFICATION_STACK_BUDGET`: 1 GiB on 64-bit targets and 256 MiB on narrower ones.
The facade sets the budget for each operation (`Backend::set_simplification_stack_budget`, the constant by default); a library caller of the backend can set it with `nesting::with_simplification_stack_budget`.
Past the budget, or when the system refuses to map a segment, the simplifier stops with the typed stop `StopCause::StackExhausted`, whose `StackLimit` says which of the three stopped it (the thread's budget, the process's budget below, or the system's refusal to map, which have different remedies: a recursion that went too deep, deep recursions on several threads at once or one thread whose budget an embedder set above the process's, or an address space or memory smaller than the budgets), returned on the outer layer of its layered result (`Stoppable<Result<_, SimplificationError>>`, apart from its failures), instead of overflowing the stack, which would abort the process.
A recursion that stays within its thread's stack maps nothing, so the budget costs nothing until a recursion uses it; a deeper one pays one mapping per segment, about 3,500 levels in a release build.
A segment is reserved address space whose pages are committed as the recursion touches them, so a runaway recursion commits up to the budget before it stops (1.4 GB peak resident memory for a release `krun` stopped this way).
The budget is per thread, and the segments of every thread of the process together are also bounded, by `nesting::SIMPLIFICATION_STACK_PROCESS_BUDGET` (4 GiB on 64-bit targets, the per-thread budget on narrower ones), counted in one atomic total when a segment is granted or released.
Without that bound a parallel embedder commits the budget once per thread: a divergent function that 16 workers reach would commit about 21 GB before any of them stopped, and the process could be killed for memory instead of returning `StackExhausted`.
Four threads at the full per-thread budget fit, so a thread stops below its own budget only when several threads recurse hundreds of thousands of levels at once.
A fresh segment per operation, which an earlier form of this provision mapped for every facade operation whatever its depth, added about 8 µs to each operation, a quarter to a third of a small `simplify` or `execute`; mapping only on demand adds nothing measurable.
The guard covers every native thread, whoever created it: CLI and RPC workers, Node-API calls on Node's JavaScript thread, and embedders' own threads.
On wasm32 the engine's call-stack limit is invisible to the module, so the guard is absent and exhaustion is a trap reported to the JavaScript host.
A ground recursive function (`size(c(T)) = 1 +Int size(T)` over a term `c^n(z)` that execution built) completes at 200,000 levels and stops at 250,000 in a release `krun`, whatever the thread, about 5 KiB per level; on an 8 MiB thread without the segments it stopped at about 1,700.
Its time grows linearly with the depth (30,000 levels take 0.5 s, 100,000 take 1.6 s and 200,000 take 2.8 s): each level combines its own step with what the level below passed up, whose applied rules, effects and conditions it shares rather than copies (`simplify::Log`).
Exhaustion is reported, never decided: an equation condition, definedness obligation, `ensures`, implication obligation, or claim remainder whose simplification is cancelled, interrupted by the step deadline, or runs out of stack propagates that stop instead of being decided unsimplified, and `KeepPartial` budgets do not absorb it.
Execution ends the state with `Stopped(StackExhausted)`, a proof records a `Stopped(StackExhausted)` leaf (outcome `stack-exhausted` in the host bindings' `prove` and in `krust kprove`'s listing, with the cause's text as its detail) and goes on with its other states, a search records a `Stopped` entry with that cause, KORE RPC `execute`, `simplify` and `implies` answer with a runtime error while the connection keeps serving, and the CLI prints `in-process backend halted at depth <n>: simplification exhausted its native stack: <limit>` (the cause's `Display` text) and exits nonzero, where `<limit>` is, for the thread's budget, `the thread's stack and its budget of 1 GiB more are used up: a recursion went too deep`, and for a refused mapping `the system refused to map another 16 MiB segment: the address space or memory the process may use ran out before the stack budget did`.
A stopped state can hold a term deeper than the stack it is dropped on; a backend term is freed one node at a time from a work list (`Drop for Term` in `crates/k-rust-backend/src/term.rs`), so dropping it takes the same stack whatever its depth.
A rewrite step that runs out of stack has no successor set, so its state is the stopped one, whichever candidate or remainder the step was working on.
The exception is the output normalisation of an execution or proof leaf whose outcome is already decided (`Stuck`, `DepthBound`, `BreadthBound`, `Indeterminate`): it only refines that outcome, so a stop there keeps the decided outcome with the unsimplified pattern.

## Cancellation

An in-process host cancels a request with a `CancellationToken` (re-exported as `k_rust::backend::CancellationToken`): it runs the request inside `token.scope(..)` on the thread that performs it and calls `cancel` from any thread.
Every facade operation that executes, searches, simplifies, decides an implication, generates a model or proves runs inside one operation boundary (`stop::operation`, through `Backend::with_solver`), in the portable and the Z3 build alike, so a request cancelled before its operation starts does not run and answers `Err(e)` with `e.stop_cause() == Some(&StopCause::Cancelled)`; constructing a `Backend` inside a cancelled scope fails the same way.
Errors found before the boundary (an unsupported schema version, an operation the build does not provide, an unknown or failing module, a state too deep for the backend) are reported instead; `add_module`, `rule_catalog`, `select_definition` and the internalizing constructors have no boundary and never answer `Cancelled`; those that load a definition (`select_definition`, the internalizing constructors) do not read the token, as the next paragraphs say.
A cancellation observed while `execute` or a search explores ends the whole run, which reports it in its result: `execute` returns the leaves completed before it and the stopped state as a `cancelled` leaf, without the states still pending, and a search returns a `cancelled` incomplete entry for the stopped state; such a result is incomplete and makes no coverage claim.
`simplify`, `implies` and `get_model` report a cancellation observed at any point as that `Err`; each polls once more after its work returns.
A proof that a cancellation ends has no leaf for the state it stopped, so `prove` answers the `Err` unless its verdict no longer depends on the work the cancellation prevented: it keeps `Ok` when the status is `disproved` (a certified refutation), when no state was left unexplored, or when the leaves that are not proven reached `max_counterexamples`; a failed solver prelude is always an `Err`.
A cancellation that lands after the boundary's entry poll and before the run's first poll still gives a depth-0 `cancelled` leaf or entry, so a host treats both shapes as a cancellation; which one it gets depends only on timing.
The step deadline (`step_timeout_ms`) is not a cancellation: a step that passes it ends its own state as a `timeout` leaf.
Loading a module's definition happens before the boundary and is not cancellable.
A load is detached from the request's token: neither the load-time critical-pair check nor the discharge of rewrite rules' definedness obligations reads it, so a definition loaded or cached inside a cancelled request (a module first used by a cancelled request, or one an internalizing constructor returns inside a cancelled scope) equals one loaded outside any token's scope ([`load_cancellation.rs`](../crates/k-rust/tests/load_cancellation.rs)); both are bounded by a budget of polls instead (the critical-pair check below).

## Stack bounds

A recursion is bounded by the stack of the thread that runs it, so k-rust provides the stack for the depth it can measure before the work starts, and accepts, case by case, the recursions whose depth it does not measure where no realistic input reaches the depth that would overflow.
These are the mechanisms:

- Frontend pre-sizing: `kcompile` runs configuration expansion, each compile stage, the structural checks before them, emission and artifact writing on a stack measured from the deepest term of the definition, a sequence counted as deep as its length (`DeepestTerm` in `crates/k-rust/src/kompile/pipeline.rs`, `stack::with_depth` in `crates/k-rust/src/stack.rs`), and refuses a definition that needs more than 4 GiB with a `TermTooDeep` error at the sentence ([JSON depth policy](#json-depth-policy)).
- Frontend guards: the frontend recursions whose depth their callers do not measure check the remaining stack at every level and continue on a fresh 16 MiB segment when less than 256 KiB remains (`stack::guarded`); the macro expander sizes its own stack.
- Backend pre-sizing: each facade operation (`Backend::with_solver_over`) and each definition load runs on a stack measured from the height of its KORE (`nesting::with_stack` in `crates/k-rust-backend/src/nesting.rs`), and work that needs more than 4 GiB is refused with `DefinitionError::InsufficientStack` ([JSON depth policy](#json-depth-policy)).
- The simplifier's segments: depth that execution creates is not a property of the input, so the simplifier checks the remaining stack at each level of its recursion, goes on on new segments up to a 1 GiB budget per thread and 4 GiB per process, and stops with `StopCause::StackExhausted` past it ([Simplification stack depth](#simplification-stack-depth)).
- Explicit work stacks: the KORE and KAST JSON readers and writers, copying, comparing and dropping a KORE or KAST term, and dropping a backend term, run each level with stack for one more or use explicit work stacks, and have no stack bound.

The backend's other walks over a term that execution made deeper than its input (matching, substitution, hooks, SMT translation, printing the result, and the derived `Clone`, `Hash` and `Eq` of predicates) run on the stack measured for the operation's input and are accepted, without a marker or a row, since no single site holds them: on the shapes measured, time and memory run out before their stack does. Measured with a release `krun` on an 8 MiB main thread: a state wrapped 1,000,000 times runs and prints, and growth without a depth bound runs until it is killed, without an abort; a term `c^n(z)` that a recursive function builds is printed, matched and compared with `==K` at n = 100,000 without an abort; at 400,000 the function stops with `StackExhausted`.
The recursions below are accepted: each is bounded by the stack of the thread that runs it, and an input deeper than that aborts the process with a stack overflow.
Each site carries a comment `// stack-accepted(<id>): <reason>. See docs/backend-port.md#stack-bounds.` (a `///` line for the facade methods), so `grep -rn 'stack-accepted(' crates/` lists them, and `crates/k-rust/tests/stack_bounds_list.rs` checks that the ids of those comments and of this table are the same set.
A case that is fixed loses its row and its markers; a newly accepted one gains both.

## Final search depth cuts

FINAL search treats `--depth N` as a cut of the execution graph.
A simplified configuration at depth `N` is a result without an additional rewrite attempt, including the initial configuration when `N` is zero.
A configuration below the bound is a result only when no rule applies.
Configurations whose constraints simplify to false and whole-state trivial or vacuous outcomes are not results.
The host backend retains `DepthBound` as an incompleteness signal for accepted frontier configurations; the CLI does not render that signal as an error.

Under strategy `all` without `stop_at_branch`, every path explored within `max_depth` and `max_breadth` ends in exactly one leaf before final merging.
A rule application whose result is empty on some instances ends those instances in a `trivial` leaf of their own, also when other applications of the same step continue: an undefined step.
The leaf's state is the configuration before the step, restricted to the instances the application's result is empty on and that no other applied candidate of its priority group takes to a defined successor.
That covers a refuted `ensures` or definedness obligation, a bottom right-hand side, and the part of a carried (partly holding, undecided) `ensures`, right-hand-side definedness obligation, or right-hand-side simplification constraint where it fails; the rule's fresh variables (`?X`) are existentially quantified in that condition.
The leaf is reported before the step's successors; its constraint is simplified and checked first, and a set shown empty is no leaf (an `ensures ?X >Int 0` always has a witness, so it leaves no instance undefined), while a set not shown empty, satisfiable or undecided, is kept. When observed, the application is also recorded in `discarded`, since its events are on no path.
A step with exactly one applied candidate and no remainder, whatever trivial entries it also has, goes on as a step with a single successor in both branch modes: it is no branch point, the cut-point and terminal rules apply to its candidate as to any single successor, and a candidate whose constraint turns out `\bottom` ends `vacuous` (or `trivial`) one step later, never as a `stuck` pre-step state.
Under strategy `all`, a run without depth, breadth, branch, cut-point, time, or cancellation stops and without diagnostics therefore covers its initial state: every ground instance satisfying the initial constraint on which the initial term is defined satisfies some leaf's constraint (the variables a path introduced taken existentially). An instance on which the initial term is undefined is no configuration and has no leaf; the run names the condition in an `UndefinedInitialInstances` diagnostic ([`docs/compatibility.md`](compatibility.md), "Undefined instances of the initial configuration").
The result has one of two readings, selected by `result_modality` and reported on the result as `modality`.
A `state-set` result (the default) is the disjunction of those leaves' configurations, merging structurally equal configurations, including depth- and breadth-bounded frontiers.
Merging loses no state: two leaves with one term, one constraint set, one effect journal, and one console state have the same future.
The first leaf in depth-first order retains its trace and halt reason, and its diagnostics are those of every leaf merged into it, its own first, so they may name work that is not on its own trace.
A merged diagnostic names variables as the path that met it named them, so a variable the request does not name may not occur in the leaf's state (names minted after a fork are distinct across paths, so it never names one of the leaf's own variables), and diagnostics equal up to such names are each listed.
Whole-state trivial and vacuous leaves carry no final configuration and are never merged.
A `path-set` result is those leaves unmerged: every explored path is exactly one leaf, each undefined step's `trivial` leaf included, and paths that converge on one configuration each keep their own trace, branch identity, observations, and halt reason.
The deduplicated configurations of a path-set result are the configurations of the state-set result, and exploration is identical under both.
Since a merged leaf keeps the diagnostics of every path merged into it, a state-set result is without diagnostics exactly when the path-set result of the same request is, so the coverage statement above holds under either reading.
An execution leaf's predicate implies the definedness of every partial term that a `requires`, `ensures`, right-hand side, or simplified state relied on along its path, with and without Z3, subject to the initial-state assumption below.
An instance excluded by a `requires` belongs to a remainder; an instance excluded by a carried right-hand-side definedness obligation or an `ensures` belongs to a `trivial` leaf.
With `assume_state_defined: true`, the initial state's definedness is assumed and need not be restated in the leaf predicate.
Builtin hooks are strict in every argument, including `andThenBool`, `orElseBool`, and `#if`, in concrete and symbolic evaluation; a value returned after a shortcut still carries the definedness of its arguments.
A rule or equation condition states the definedness of its Boolean terms when instantiated, before simplification or solver decisions can discharge the condition.
The contract interprets `total`, `functional`, and `preserves-definedness` attributes as part of the definition's meaning; a definition that declares a partial function total or falsely claims preservation is outside it.
Equations are read innermost: an equation's arguments are bound by membership in its argument patterns, so it applies to an application whose arguments are values, and priority is decided on those values. Under that reading the definition's normal forms are a model of it when evaluation terminates and the critical pairs of the executable equations join; the backend checks the second condition when it loads the definition (`k_rust_backend::confluence`) and makes value claims (instance normality, the normal-form certificate, the `value-production` discharge) only for the equation heads and collections that no non-joined pair withdraws, naming each such pair in a warning ([`docs/compatibility.md`](compatibility.md), "Anywhere rules"). Termination is assumed, as for every evaluation.
The check bounds each of its simplifications (the simplification of a condition of an overlap, the definedness of an instance's conditions, and the join's evaluation of a hooked application, which may apply the hooked symbol's equations) by a budget of polls for a stop (`stop::check`), not by a clock: the simplifier polls at every round of a term's simplification, ground function steps included, at every predicate simplification and in the loops of hooks, so the budget bounds the work a simplification may take, and where it stops is a function of the definition.
A simplification that met a stop decides nothing, even when a site dismissed the stop and the simplification returned a partial answer: its overlap is neither refuted nor joined through it, which can only withdraw claims.
The verdict, the value claims and the warnings are therefore a function of the definition, the same on every load, on every thread, under any load of the host, and on wasm32, which has no clock; the one exception is a simplification of the check that runs out of native stack, since the stack the simplifier may use depends on the loading thread's stack, on the segments other threads of the process hold, and on the build profile ([Simplification stack depth](#simplification-stack-depth)).
`ValueClaims::counts()` counts both kinds of stop, per condition answered (with the memo of condition simplifications or without it), per definedness computation and per hook evaluation: `condition_budget_stops`, which are part of the verdict, and `condition_stack_stops`; a host that compares the results of two backends (for example of a definition and a mutant of it) should treat a nonzero `condition_stack_stops` on either side as a result that another load may not reproduce.
The budget is 4,000,000 polls (`CONDITION_POLLS` in `confluence.rs`); any fixed number makes the verdict a function of the definition, and the number is a choice between the cost of a load and the conditions it decides.
Measured on 2026-10-15 in a release build, no condition of the 205 compiled definitions of the conformance corpus, of the definitions of the light reference gates (the compile corpus, the execution, RPC and proof cases, IMP and its verification module), or of the backend's own tests takes more than 29 polls.
A ground step of a recursive integer function takes 14 polls, and on that workload a release build makes about 2.0 million polls a second on a 32-CPU workstation at half load, so the budget is about two seconds of it; the time a poll stands for depends on the site (a traversal that polls at every term node reaches the budget sooner, a heavy hook that polls rarely later).
Each simplification that spends the budget costs that much of the load, the number of such simplifications in one definition is not bounded, and the load cannot be cancelled: the check is detached from the loading request.
After the check, the load discharges each rewrite rule's definedness where it can (a discharged rule needs no definedness obligation at run time), which may simplify the instance of a ceil equation's condition; that discharge is detached from the loading request in the same way and runs each rule under the same budget. A rule whose discharge met a stop stays undischarged, which only leaves its obligation to run time, and `BackendDefinition::discharge_counts()` counts the rules whose discharge spent the budget (`budget_stops`, a function of the definition) or ran out of stack (`stack_stops`); a host that compares backends treats a nonzero `stack_stops` as it treats a nonzero `condition_stack_stops`.
The WASM, MIR and KEVM definitions have not been measured, neither for the check's conditions nor for the discharge of their rewrite rules, whose simplifications are of another size (one walk over a whole rule, with every ceil equation's instance simplified).
The public-path [symbolic definedness tests](../crates/k-rust/tests/symbolic_definedness.rs) cover rule conditions in both solver profiles and the `assume_state_defined` modes; [rewrite tests](../crates/k-rust-backend/tests/backend/rewrite.rs) cover discarded hook operands and their leaf obligations.
`ExecutionResult.effects` holds the transcript only when exactly one leaf remains, which under `path-set` means one explored path.
The CLI and KORE RPC `execute` produce state-set results.
A `stuck`, `trivial`, `vacuous`, or `terminal` halt ends a path.
A `trivial` leaf is an undefined step: under its constraint some rule applies to every instance and, under strategy `all`, no instance has a defined successor; like `stuck`, it does not assert that an instance exists.
Strategy `any` offers the instances where a rule applies but its result is undefined to every later match of the rule (a later collection candidate or split case) and every later rule of the same priority, never to a lower priority, so a `trivial` leaf there also means that no rule of that priority gives an instance a defined successor.
An `ensures` of a `[simplification]` or function equation that the right-hand side's evaluation applied is trusted as the definition's axiom: the successor keeps it, and it never makes a step undefined.
 `branch`, `cut-point`, `depth-bound`, and `breadth-bound` mark a frontier; `indeterminate`, `unsupported-hook`, `simplification-error`, `timeout`, and `cancelled` mark a failure.
A `stuck` leaf with term `t` and constraint `phi` asserts that no instance `sigma(t)` has a rewrite successor under the definition when `sigma` assigns every free variable of `t` and `phi` a ground term of its declared sort and satisfies `phi` under the definition.
The assertion ranges over all such substitutions, not only the ground terms a client enumerates or the models a solver finds, and it does not assert that any satisfying instance exists.
It holds under both execution strategies and with or without an SMT solver; when rule applicability or a symbolic remainder cannot be decided, the leaf is `indeterminate` with a reason instead of `stuck`.
`--search-final` reports a state after a `Stuck` step under the same assertion; a search frontier or incomplete search result does not assert finality.
Proof certification uses the same assertion for a stuck leaf and handles non-emptiness separately.
A step keeps a remainder when the path's constraints and the remainder's condition are satisfiable; the definedness of the remainder's term is not conjoined to that query, so a remainder leaf may denote the empty set, as `<m> (1 |-> 2) M </m>` under `1 in_keys(M)` does (the concatenation is defined only where `1` is not a key of `M`).
Such a leaf adds nothing to the disjunction of leaves and claims no instance, so the result is the same set; deciding its term's definedness at each remainder would cost one simplification and one solver query per symbolic remainder, and a client that needs to know asks `implies` with the leaf as antecedent, which answers `valid` for a leaf whose emptiness the simplifier or the solver shows (`docs/compatibility.md`).
A proof's initial state is different: `prove_claim` conjoins the definedness of the claim's left-hand side to its constraints, so the loop head's constraint check sees such a contradiction there.
Strategy `any` gives each configuration the successors of the first rule, in priority then definition order, that gives it a defined result, among the rules of the highest priority that applies to it, through the first of that rule's matches that does, and makes no coverage claim; it keeps that rule's right-hand-side alternatives and passes a symbolic remainder to later rules, so it can produce several leaves; `result_modality` applies to whatever leaves it produces, and the two readings coincide whenever no two of those leaves share a configuration.
With `stop_at_branch`, execution stops at the first branch point and reports its successors inside the branch halt.
It still reports the `trivial` leaves of the steps it takes, before the leaf where it stops; KORE RPC `execute` answers with that last leaf, since its one-state response cannot express the undefined instances.
For the same request, `Backend::execute` and `Backend::execute_observed` return leaves in the same order, equal in every field except `branch` and `observations`.
Unobserved execution leaves `branch` empty.
Observed branch identities do not depend on the rule filter: `ObservedRequest.rules = Some(vec![])` yields every identity and no observation events.

Printed execution, search, and pattern-match disjunctions use the structural order of the externalized KORE pattern; the order of an `\or` is not part of the compatibility contract, and differential gates compare its disjuncts as a multiset.

The backend facade exposes each execution leaf's halt reason as `HaltReasonOutput`, serialized with the same kebab-case reason in JSON.
Consumers may match the Rust enum exhaustively.
`detail` is human-readable context and must not be parsed as a halt class.
An `indeterminate` execution leaf carries `cause`, the structured reason the step stopped, with the same encoding as `IncompleteSearchOutput::Indeterminate.reason`.
Other leaves omit `cause`; `detail` remains legacy human-readable context.
The reachable causes are `surviving-macro-or-alias` (preprocessing left an executable symbol), `match` (unsupported unification remainder), `instantiation` (unbound rule variable), `requires` (undecided rule condition with no solver), `smt` (an undecided rule query), and `remainder` (an undecided priority-group remainder).
An undecided query is one the solver answered `unknown` within its own timeout, resource limit and retries; a query that stopped (the request was cancelled, the step deadline passed, or the solver's prelude failed) has no answer, and the step publishes the stop instead of either cause.
`SearchFailureOutput::solver_unavailable()` is true for `requires`, and for `smt`, `smt-predicate`, or a `remainder` satisfiability error whose SMT failure is `unavailable`.
It says this step needed a solver absent from the build; it does not promise that a solver-enabled build decides the path, and a `match` cause may depend on an earlier equation left unevaluated without a solver.
When a `Trivial` halt names its responsible rule, `ExecutionLeaf.rule_id` and `rule_label` expose the same compiled id and optional label as the rule catalog (`ruleId` and `ruleLabel` in JSON).
Both fields are omitted when no rule is named and on other halt reasons; they do not imply that the undefined step committed a transition.
A `Trivial` or `Vacuous` leaf whose emptiness comes from an equation of a `total` (or `functional`) symbol that reduced an application of it to `\bottom` also carries `ExecutionLeaf.contradicted_total` (`contradictedTotal`: `symbol` (KORE name), optional `kLabel` (the K label it encodes), `ruleId`, optional `ruleLabel` and `origin`, `application`, `undefined`); it is a diagnostic about the definition and changes neither the reason nor the state (`docs/compatibility.md`, "A contradicted `total` attribute is named, not repaired").
`UndecidedCondition` and `UndecidedPredicate` diagnostics report a solver that was asked and could not answer, never the absence of a solver; an `UndecidedCondition` also reports an equation instance that is not used because the equation's result has variables its left-hand side does not bind (reason `unbound-result-variables`, `docs/compatibility.md`, "Unbound equation variables").
A diagnostic emitted during an equation attempt (an `UndecidedCondition`, or one raised while its conditions were simplified) is reported only with an outcome the simplification keeps: the equation applied, or the attempt was indeterminate and no other equation rewrote the subject, which was left unevaluated.
An attempt whose `requires` was refuted, one that another equation superseded, and one made while simplifying the condition of an enclosing attempt that was itself refuted or superseded report nothing.
A report of an attempt left indeterminate explains why its subject is unevaluated, so it is also dropped when a later part of the same simplification drops the subject: the simplifier entry that returns the result (a term with the conditions it carries, or predicates) keeps it only if that result still holds the subject.
A term dropped there did not matter to the result: an equation that drops an argument holds for every value of it, a condition decided without it holds whatever it is, and a definedness that is not provable stays in the result as `\ceil(t)`, where the term then still occurs.
The reports raised inside an attempt whose own subject is kept stand or fall with that subject.
A rewrite rule's attempt is one such scope around the simplifier entries it makes: a report raised while it was made is kept only if the attempt's outcome holds the subject, in a successor (its term or a constraint the rule adds to the path), in the remainder its applicability leaves to lower priorities, or in the sub-case or obligation of an application whose result is bottom.
So a rule condition decided without the term reports nothing, whether the simplifier or the solver decides it and whether it is the rule's `requires` or its `ensures`, as for an equation's `requires`; a refuted attempt reports nothing; an attempt left undecided, and one that failed or stopped, keep their reports.
A report that a rewrite step keeps stays with the path even if a later step drops the term: the state that held it is part of the path.
The predicates of an `UndecidedCondition` are one of two conditions of the equation instance: its instantiated `requires`, and then the equation is not used on that subject, or, once the `requires` held, the definedness of the terms its match bound, which the equation's result then carries as constraints; the reason `unbound-result-variables` comes with the `requires` only.
Its wire form names the equation by `ruleId` and by `origin`, the first sentence of its axiom, which is the first of the equation's rule catalog `origins`: equations whose axioms carry neither a label nor a `UNIQUE_ID` all have the id `UNKNOWN`, and the pair names the catalog entry, by the origin's `sentence` place when the sentences carry no `Source` or `Location`. It lists in `ruleVariables` each variable of that equation that they name free, by its printed `name` and its `definitionName`; the list comes from the attempt, so a variable of the subject is not listed even when it is another equation's variable, such as the requires-only variable of an enclosing equation whose `requires` was being simplified.

A rule whose left-hand side matches and whose `requires` holds has applied even when its result is
empty (an `ensures false` or bottom right-hand side). Lower priorities and `owise` do not see that
sub-case. [Trivial rule results](compatibility.md#trivial-rule-results) gives the reason and the RPC differential row that records the Booster divergence.
When every execution leaf is dropped as trivial or vacuous, the CLI reports each leaf's depth, applied rule when available, and refuted obligation on stderr while retaining the `\bottom` result and exit status.
