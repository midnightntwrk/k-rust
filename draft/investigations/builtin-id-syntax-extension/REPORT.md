# Builtin `Id` syntax-extension audit

## Conclusion

The right long-term surface is a grammar declaration separate from the term
literal:

```rust
#[k::token_extension(
    sort = k::builtin::Id,
    regex = r"\$[a-zA-Z0-9\_]+",
)]
const IMP_VERIFICATION_IDS: () = ();

// In a claim, rule, map key, or constructor argument:
let _: k::builtin::Id = k::id!("$n");
```

`#[k::token_extension]` says that bare text matching the regex is concrete
syntax for an already-existing sort. `k::id!("$n")` constructs one typed
domain token. Neither should pretend to do the other's job.

Use an attributed unit `const`, rather than a wrapper struct or an impl, for
the extension declaration. It is ordinary Rust, provides a stable declaration
name and source anchor, allows rustc to resolve the `sort` path generated by
the attribute macro, does not invent a second nominal sort, and does not run
into the orphan/inherent-impl restriction on the facade-owned `builtin::Id`.
The const value has no object-language meaning.

The minimal target-neutral protocol change is to widen the existing
`HostProductionOwner::TokenSort` / `DescriptorProductionOwner::TokenSort`
contract to admit `BuiltinSort::Id`, not to add an adapter-specific K-source
sentence or raw attribute. A nominal `#[k::token]` still registers both its
new sort and its token production; a token extension registers only the
grammar descriptor. The sort reference itself distinguishes the two cases.
Restrict the first extension surface to builtin `Id`; accepting `Int`, `Bool`,
`Map`, or `KSequence` would make considerably stronger domain and hook claims.

For the active claims lane, the bounded recommendation is different: finish
the typed `k::id!` transport and keep the current source fallback
`#token("$n","Id")`. It needs no concrete token production, avoids scanner and
import hazards, and becomes the same native `Term::Token` and KORE domain
value. Bare `$n` should be enabled only when the extension declaration and a
module-visibility/coverage check land together.

## Pinned source contract

The frozen IMP revision declares:

```k
module IMP-VERIFICATION-SYNTAX
  imports ID-SYNTAX
  syntax Id ::= r"\$[a-zA-Z0-9\_]+" [token]
endmodule
```

This is not part of K's generic `ID-SYNTAX`. In pinned K 7.1.337,
`ID-SYNTAX` declares `syntax Id [token]` but deliberately supplies no program
identifier regex. `ID-SYNTAX-PROGRAM-PARSING` is a different optional module
whose ordinary identifier regex begins with a letter or underscore. The IMP
verification module therefore extends the existing domain sort; it does not
declare a new sort or a subsort.

The Rust raw literal above has the desired descriptor value
`\$[a-zA-Z0-9\_]+`. K source quoting will escape it when rendered. Do not add
`^` or `$` anchors: K's scanner anchors matching at the current input position
and selects the longest lexeme. The `k::id!` validator, independently, should
check the complete Rust string and accept exactly `$` followed by one or more
ASCII letters, digits, or underscores. The in-progress syntax island's
`valid_extended_id` has this exact shape.

The pinned scanner's winner rules matter:

1. longest token wins;
2. on equal length, the larger `prec` wins;
3. omitted `prec` is zero;
4. terminals effectively have maximum precedence; and
5. registering the identical lexeme with different precedences is an error.

The recommended declaration omits `prec` to reproduce IMP. `$n` and `$s` are
disjoint from the ordinary identifier regexes. The broader IMP regex also
admits uppercase `$N`, which overlaps the rule/configuration token
`KConfigVar ::= r"\$[A-Z][A-Za-z0-9'_]*"` at the same default precedence.
The frozen claims use lowercase names and avoid the overlap; a general API
must nevertheless test and document it.

## What exists now

### Grammar and facade

`#[k::token(regex = ..., prec = ...)] struct Name(String);` is a nominal-token
declaration. The syntax parser requires exactly a one-field `String` tuple
newtype. Its macro expansion registers:

- a declared sort keyed by `TypeId::of::<Name>()`; and
- a grammar production owned by `TokenSort { sort: Name }`, containing one
  regex item and one token attribute.

This cannot be applied to `k::builtin::Id`: the builtin marker is declared in
the facade, cannot be redeclared as a local newtype, and wrapping it would
change the semantic sort identity. The existing `#[k::subsort] impl Super for
Sub {}` surface demonstrates that builtin endpoints can resolve through the
builtin registry, but a token extension is a production on the same sort, not
a subsort relation.

### Protocol and collector

The host and stable production representations are already target-neutral:
they carry a typed sort reference, a structured regex terminal, and classified
token/precedence metadata. The collector already resolves any
`HostSortReference` through the closed builtin registry, including
`builtin::Id -> BuiltinSort::Id`.

The actual blocker is protocol validation. `DescriptorProduction::validate`
currently groups token and bracket owners and rejects either unless the owner
is `DescriptorSortRef::Declared`. Its exact diagnostic is “token and bracket
owners must be authored sorts.” Expected provenance also assumes the
`token_declaration` role belongs to a nominal token newtype. This is a
deliberate contract boundary, not a collector limitation.

The fix should:

- allow `TokenSort { sort: Builtin(Id) }` while leaving builtin bracket owners
  and other builtin token sorts rejected;
- require token owner sort and production result sort to be identical (the
  current nominal expansion supplies this, but validation does not state it);
- add extension-specific declaration and target-sort provenance roles, while
  reusing the existing regex and lexical-precedence roles;
- keep exactly one unguarded regex item and exactly one token attribute; and
- bump the protocol version even if the serialized enum shape is reused,
  because an older consumer rejects the newly legal value. The current
  protocol version is 11.

A separate `TokenExtension` owner variant is unnecessary unless later phases
need different semantics. Whether the target is builtin versus declared is
already explicit, and whether a sort declaration exists is represented by a
separate descriptor.

### Semantic and Definition IR

After that validation gate, most of the vertical path already works:

- grammar reference validation accepts builtin sort references;
- generated token-production identity is derived from the grammar descriptor;
- Semantic production lowering preserves a builtin result sort, regex item,
  and optional lexical precedence;
- Definition validation accepts all closed builtin sort references and the
  one-regex/one-token production shape; and
- a typed token term already exists in Semantic and Definition IR.

The term front half is the missing piece. `DescriptorLiteral` currently
contains only inferred `Int` and `Bool` values. `k::id!` should lower through
an explicit typed token node, for example a host/stable term variant containing
`sort: Host/DescriptorSortReference` and `value`, rather than extending
`DescriptorLiteral`, coercing a host string, or manufacturing a constructor
application. The macro's Rust expansion must have type `k::builtin::Id`.

The collector resolves that explicit sort through the builtin registry;
semantic checking creates `SemanticTerm::token(..., Builtin(Id), "$n")`; the
existing Definition lowering then creates the corresponding
`DefinitionTerm::token`. This generic typed-token transport is preferable to
an Id-only wire node, even if `id!` is initially its only author surface.

### `.k` emission

Grammar emission already knows how to render a regex item and `[token,
prec(...)]`. Because builtin-import discovery visits production result sorts,
an `Id` extension causes the module to import `ID-SYNTAX`, matching IMP.

Two details require explicit decisions:

1. Every current Definition production owns a `SymbolIdentity`, and source
   emission always adds `symbol(...)`; the native adapter likewise supplies a
   label. Pinned IMP's token production is unlabeled. The pinned parser still
   produces an `Id` token when the token attribute is present, so the extra
   generated label is not needed for term construction. Suppressing emitted
   symbols/native labels for token productions is the closer K model, but it
   is an adjacent IR change and must be regression-tested against existing
   nominal tokens.
2. Current term emission intentionally renders builtin `Id` as
   `#token(value,"Id")`. It must not be changed to emit every `Id` value bare
   unconditionally.

The clean policy is adapter-side spelling selection: Semantic and Definition
IR retain only the typed token meaning. While emitting a particular module,
the source adapter indexes visible token productions. A `k::id!` value may be
rendered bare only when a visible `Id` production is known to cover the whole
value; otherwise it renders `#token`. For the first bounded implementation,
coverage can require the exact canonical IMP regex plus the already-fixed
ASCII validator. A future generic implementation needs a target-neutral
K-regex matcher, not Rust-regex guessing.

This visibility index must be module-aware. `render_term` currently has a
definition-wide context but not the emitting module's grammar closure, so the
module (or a precomputed per-module policy) needs to reach term rendering.
Do not encode “bare `$n`” as a native-specific string in Semantic IR.

### Native adapter

No new native term concept is needed. The adapter already maps:

```text
DefinitionTerm::Token { sort: Builtin(Id), value: "$n" }
  -> k_rust::kast::Term::Token { sort: Id, token: "$n" }
```

It also maps regex production items and token/`prec` attributes structurally,
and builtin import discovery adds `ID-SYNTAX` for any `Id` sort occurrence.
The pin-specific sort catalog maps `BuiltinSort::Id` to the literal native sort
name only at this boundary.

The pinned inner parser lowers a matched token production to exactly
`Term::Token`, regardless of a production label. Thus parsing bare `$n` and
adapting the typed Rust token converge before KORE. `#token("$n","Id")` also
constructs that same term without asking the concrete scanner to recognize
`$n`.

## Module, collision, and precedence risks

### Ownership and imports

Grammar descriptors are assigned to the generated module for their Cargo
package. A local builtin extension is legal because that module imports
`ID-SYNTAX` and adds a production to its `Id` sort.

A dependency package that contains only a builtin-Id extension is not
automatically imported by a downstream package merely because the downstream
uses `builtin::Id`: referenced-package discovery records declared item
references, while a builtin reference has no owning package. Therefore either:

- colocate the extension with the claims/rules that need bare spelling (the
  recommended first implementation); or
- add an explicit target-neutral module-import/reference surface before
  promising reusable syntax-extension crates.

Likewise, the source emitter cannot assume that an arbitrary external `.k`
module such as upstream `IMP-VERIFICATION-SYNTAX` is visible unless that import
is represented in the definition being emitted. The `#token` fallback is
independent of this uncertainty.

### Duplicate and overlapping productions

Reject exact duplicate local extensions by canonical key `(module, result
sort, regex, precede, follow, prec)`. Do not rely on frontend sentence
deduplication: KRS's generated symbol/label can make an otherwise identical
production structurally different from an imported unlabeled one.

Also test overlapping, nonidentical regexes. K does not calculate regex
inclusion for the author. Longest match and `prec` select a global scanner
winner, which can silently change the token's sort. In particular test:

- `$n`, `$s`, `$0`, and `$_` as `Id`;
- rejection of `$`, non-ASCII suffixes, whitespace, and partial matches;
- uppercase `$N` in rule and configuration positions against `KConfigVar`;
- a longer competing regex;
- equal-length competitors at lower/equal/higher precedence;
- identical regex at inconsistent precedence; and
- an empty-matching regex (the extension surface should reject it early).

Do not silently add `prec(1)` to “fix” the uppercase overlap: that changes the
pinned IMP production and can steal configuration variables. If the API later
offers `prec`, it must remain an explicit authored choice.

## Fallback comparison

| Property | Bare `$n` with token extension | `#token("$n","Id")` |
|---|---|---|
| Rust type | `k::builtin::Id` via `k::id!` | Same typed `k::id!` node; only source rendering differs |
| Parsed/native term | `KToken("$n", Id)` / native `Term::Token` | Identical |
| KORE domain value | Identical `Id` domain value | Identical |
| Concrete grammar required | Yes, visibly imported in the parsing module | No; only the `Id` sort must exist |
| Scanner precedence/collision exposure | Yes | None |
| Exact IMP human text | Yes | No |
| Accepts a value outside concrete Id syntax | No, when coverage is checked | Mechanically yes; retain the `id!` validator to prevent this |
| Duplicate/import sensitivity | Yes | Low |
| Current KRS source emitter | Not supported safely | Already selected for builtin `Id` |
| Current native adapter | Supported once typed term reaches Definition IR | Supported |

The fallback is not an untyped escape hatch when it originates from
`k::id!`: it still has builtin `Id` in every Rust/protocol/IR/native layer and
still uses the exact IMP lexeme validator. It only bypasses concrete lexing.

## Concrete implementation order

1. Complete the typed `k::id!` term node and prove that source `#token` and
   native adaptation converge to the same KAST/KORE value. This unblocks
   claims without grammar work.
2. Add and re-export `#[k::token_extension]` on the exact unit-const shape.
   Reuse the token regex/`prec` parser; add a rustc-resolved target-sort path.
3. Emit only a grammar host descriptor. Resolve owner and result from the same
   target key and assert their equality in host/stable validation.
4. Widen the stable `TokenSort` owner to builtin `Id`, add precise provenance,
   update exhaustive matches, and bump the protocol version.
5. Add module-local duplicate checks and explicit coverage/visibility
   analysis. Only then allow the `.k` emitter to choose bare `$n`.
6. Exercise both paths through the pinned source parser and direct native
   adapter, and compare normalized terms/KORE rather than only successful
   compilation.

No shared crate or active claim fixture was changed by this investigation.
