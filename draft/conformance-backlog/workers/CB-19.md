## Cause

### M1: K's `--io off` stdin tokenization is undefined on a delimiter run, and krust reports that the way Kore does

The stdin stream rules are K's own (`k/k-distribution/include/kframework/builtin/domains.md:2715-2790`, module `STDIN-STREAM`, instantiated by the frontend's `ResolveIOStreams` with the default delimiters `" \n\t\r"`, `k-frontend/src/main/java/org/kframework/compile/ResolveIOStreams.java:431-432`).
With `$IO = "off"` the whole standard input is one `#buffer(S)` and only three rules can fire on `ListItem(#parseInput("Int", D)) ListItem(#buffer(S))`:

- `stdinParseInt` (`domains.md:2746-2754`, "a hack: handle the case when we read integers without the help of the IO server"): `requires findChar(S, D, 0) =/=Int -1 andBool lengthString(S) >Int 1`; result `ListItem(String2Int(substrString(S, 0, findChar(S, D, 0))))`, buffer `substrString(S, findChar(S, D, 0) +Int 1, lengthString(S))`.
- `stdinTrim` (`:2757-2765`): `requires findChar(S, D, 0) =/=Int -1 andBool Sort =/=String "String" andBool lengthString(S) <=Int 1`; drops one character.
- `stdinGetc` (`:2725-2732`): only under `ListItem("on")`.

For `S = " 4 \t1\n…"` both conjuncts of `stdinParseInt` hold (`findChar = 0`, length 22), so it fires and its result is `String2Int(substrString(S, 0, 0))` = `String2Int("")`.
`stdinTrim`, which would skip the delimiter, is unreachable because the buffer is longer than one character; under `--io on` the buffer grows one character at a time through `#getc`, so it holds exactly one character when the delimiter is found and `stdinTrim` applies.
The tokenization therefore differs between the two IO modes exactly when a token boundary carries more than one delimiter, or the input starts with one.

`String2Int("")` is an undefined application of a partial hooked function (`function`, `hook(STRING.string2int)`, no `total`).
The pinned Kore engine returns `\bottom` for it (`haskell-backend/kore/src/Kore/Builtin/String.hs:358-366`, `_ -> return (Pattern.bottomOf resultSort)`), and `docs/compatibility.md:80-86` "Trivial rule results" says the rule has applied with an empty result.
krust does the same: `STRING.string2int` returns `BuiltinResult::Bottom` on an unparsable string (`crates/k-rust-backend/src/builtin/string.rs:174-184`, unit-tested at `:329-332`); `simplify_root` turns that into the constraint `Predicate::False` (`crates/k-rust-backend/src/simplify.rs:2354`); in `apply_rhs_alternative` the RHS is simplified because the rule carries a partial symbol (`crates/k-rust-backend/src/rewrite.rs:3135-3156`, `undefined_symbols` from `crates/k-rust-backend/src/rule.rs:1104-1121`), the `\ceil` obligation (`crates/k-rust-backend/src/definedness.rs:68-84`) is refuted (`simplify.rs:538-540`, `:696-697`), `rhs_obligation_verdict` maps that to `ObligationVerdict::Trivial` (`rewrite.rs:3064-3072`), the step becomes `RewriteResult::Trivial` (`:1751`) and the leaf halts with `HaltReason::Trivial` (`:590-592`).
`krun` drops `Trivial`/`Vacuous` leaves from `finals` (`crates/k-rust/src/main.rs:3097-3100`), prints `KorePattern::Bottom` for an empty set (`:3140-3141`), and exits 0 because the definition declares no `getExitCode` (`:3161-3163`).

Conclusions:

1. The checked-in `matrix.simple.out` is reachable only under `--io on`. Under the driver's `--io off` K's own semantics has no successful execution; the LLVM oracle aborts and Kore answers `\bottom`.
2. krust's `\bottom` is Kore-faithful; the LLVM abort is LLVM runtime behavior outside the Haskell-backend contract (`docs/compatibility.md:12-21` "Backend scope"), and a hook that has an evaluator but is undefined on its argument is not the unsupported-hook case of `:19-21`.
3. This is a divergence between IO modes of one definition, not between the untyped and typed-dynamic SIMPLE definitions: the typed-dynamic `matrix.simple.in` is the single line `2 4 1 5 7 8 27 1 2 3` and both `matrix.kool.in` files are single-space separated. A scan of all 26 `.in` files under `k-distribution/tests/regression-new` finds exactly one file with a delimiter run or leading delimiter: this one. Blast radius: one step of one case.
4. C9's register entry claims "the buffered stdin equals the piped .in bytes because each input has exactly one trailing newline" (`scripts/reference-normalisations.toml:256`) and `docs/compatibility.md:189` says "C9 applies only where krust's buffered stdin is the piped input". Byte equality holds; the missing premise is that the definition tokenizes the buffered input as it tokenizes the interactive stream. CB-09's note that an exhausted buffer "leaves the program stuck" (`workers/CB-09.md:114`) is also incomplete: a delimiter run collapses the run instead.

### M2: a mid-run collapse to `\bottom` is silent

The only bottom diagnostic in `krun` is gated on every initial input collapsing at depth 0 (`main.rs:3108-3111`, `rewrite.rs:295-303`, `:971-975`); the "halted at depth" error covers only `Cancelled | Indeterminate | Simplification` (`main.rs:3051-3070`); `HaltReason::Trivial` and `Vacuous` carry no rule or obligation (`rewrite.rs:251-255`); `BackendDiagnostic` (`crates/k-rust-backend/src/diagnostic.rs:12-29`) has no variant for an undefined partial application.
The RPC and wire surfaces do report the reason as `"vacuous"`/`"trivial"` (`crates/k-rust/src/rpc.rs:531`, `crates/k-rust/src/backend.rs:947-948`); only the CLI discards it.
`crates/k-rust/tests/cli.rs:1235-1277` (`krun_does_not_warn_when_the_first_semantic_rewrite_is_bottom`) pins only that the *initial-configuration* warning is not printed for a semantic collapse; it does not forbid a different diagnostic.
`docs/backend-port.md:62-63` ("Unsupported behavior is not silently reported as stuck or successful") and CB-13 (the previous silent ground `\bottom`, which cost an investigation to attribute) justify a diagnostic that names the depth, the rule, and the refuted obligation.

## Decision

Driver and observability fixes; no backend semantic change, no comparator normalisation, no floor change.

- Not a port fix of the value: making krust's `--io off` tokenize as `--io on` would mimic the K frontend's stream desugaring against the pinned Kore behavior; making `String2Int("")` anything but `\bottom` would leave Kore's hook contract (`docs/compatibility.md:88`).
- Not an `--io on` implementation here: real stdin through `#getc` is CB-15-3/4/5 (`workers/CB-15.md:69-113`), gated by D-01 and D-11, and CB-15 owns no pending verdict (D-11).
- The step is not translatable to C9: the recipe's oracle exists only under interactive stdin. That is the `undriven-recipe` doctrine (`docs/compatibility.md:153-156`, `scripts/conformance/expectations.toml:62-65`) at step granularity: "the skip is not evidence of a Rust pass and must be reconsidered when the driver learns to translate the feature", the feature being `--io on` stdin.
- The driver records the skip only when krust's own diagnostic (CB-19-A) attributes the collapse to a `STDIN-STREAM` rule and the `.in` bytes hold a delimiter run or leading delimiter under the definition's delimiters, so a different `\bottom` on an input program stays `krust-error`.
- No new `[[decision]]` row: every choice above is settled by the pinned semantics, the measured three-engine evidence, and D-01/D-11.

## Question disposition

1. Is the 3.2 s `\bottom` a wrong answer or a slow one? Neither: it is the correct Kore answer to a question the recipe does not ask. Under `--io off` K's own `stdinParseInt` applies `String2Int("")` to this input; Kore returns `\bottom`, the LLVM interpreter aborts, krust returns `\bottom`. The checked-in output exists only under `--io on`.
2. Does the untyped definition diverge from the typed-dynamic one on this program? No. The definitions share the builtin stream rules; the inputs differ (`2  4 \t1\n5 7 8 27\n\n1 2 3\n` against `2 4 1 5 7 8 27 1 2 3`). The bisection (depth 49 configuration, depth 50 `\bottom`) lands on the stream rule, not on a SIMPLE rule.
3. Backend fix, normalisation, or exclusion? Exclusion at step granularity through the existing `undriven-recipe` doctrine (CB-19-B), because the recipe supplies no oracle under the only mode krust can run; a normalisation would compare two different questions, and a backend change would mimic the frontend or leave Kore's hook contract. The DF-04 rule that a `\bottom` is never a completion-only match stays.
4. Should krust say why it returned `\bottom`? Yes (CB-19-A): the halt reason already exists on the RPC and wire surfaces and only the CLI drops it; the diagnostic is also what makes the driver's precondition exact instead of syntactic.
5. Does anything move to CB-12 or CB-15? Nothing new. The case's rank is CB-12's (thread throughput); CB-15-5 is the reconsideration trigger recorded above; CB-09's `workers/CB-09.md:114` sentence about an exhausted buffer is corrected by M1 but needs no work.
6. Host-UID dependency: the LLVM `--io off` abort and the Haskell fixture run were host-UID measurements; the implementer needs no reference run, because CB-19-B keys on krust's own diagnostic and the `.in` bytes, and the fixture's expected outputs are recorded here.
