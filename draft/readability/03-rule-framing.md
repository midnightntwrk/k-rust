# Proposal 03: Rule framing and the in-place rewrite

**Target: Cause 3 (rule scaffolding).** Configuration rules are where KRS is
furthest from K: `[done]` is one K line and twelve KRS lines. After proposal
01 removes the path noise, three structural costs remain, each addressed by a
sub-proposal below (03a–03c compose and keep the current pre/post function
shape; 03d is a bigger step that changes the shape).

The design direction for this already exists: the semantic-gap inventory's
"Local rewrite" row says the plan is to *"infer a whole-state pre/post
pattern from field updates"* (`draft/semantic-gaps.md`). These sub-proposals
are concrete spellings of that inference.

**Surface classification (see 08): all four sub-proposals are
authoring-layer constructs, not changes to the reference surface.** Each is
defined by its expansion: a rule written with implicit frames, inferred
binders, or in-place arrows expands to exactly today's fully explicit
form — named frames, declared binders, two-sided pre/post — and that form
remains the canonical spelling the collector's reference parsers accept and
`krs expand` displays. Implementation-wise this means new desugaring entry
points that *produce* explicit descriptors, never new permissiveness in the
reference grammar. Read the honesty arguments below with that correction:
where they argue for "removing" a frame or a binder declaration, the
two-surface strategy relocates it instead, which dissolves the tension with
the deviation ledger rather than winning the argument against it.

## 03a. Implicit configuration frame

`state @ ..` / `..state` appears in **every rule in imp.rs**, spelled
identically, binding a frame that is never inspected — pure rent. In K,
framing unmentioned cells is not an option the author chooses; it is what a
rule *is*. Proposal: unmentioned cells are framed automatically, and the
trailing `state @ ..` / `..state` pair becomes unnecessary. The named form
stays legal for the rare rule that genuinely moves the frame (none exist in
the current corpus).

Honesty check against the deviation ledger (design.md §"Explicit Rust
deviations"): the ledger requires that `cells!` visibly *frames rather than
updates*. That property lives in the `cells!` island itself (it is not a
struct literal and never was); it does not depend on a named binder being
threaded through. `krs expand` renders the explicit frame.

## 03b. Anonymous shared tail inside `KCell`

Same argument one level down: `tail @ ..` in the pattern and `..tail` in the
result, in every rule, always meaning "the rest of the computation is
untouched" — K's trailing `...`. Proposal: `..` with no binding, in both
positions, means the shared tail:

```rust
cells! { k: KCell(EmptyBlock(), ..) }   // pattern
cells! { k: KCell(..) }                 // result: tail flows through
```

A *named* tail stays required the moment the rule does anything nontrivial
with it (reorders, drops, or duplicates it) — so the compact form is
unambiguous: bare `..` on both sides always denotes the same frame variable,
generated by the expansion.

## 03c. Optional binder pre-declaration

Every rule variable is currently declared twice: as a leading typed `fn`
parameter and again in the pattern. The typed parameters are the only part
of a cells-rule that rustc genuinely checks (the expansion preserves them
verbatim — `crates/krs-macros/src/expand.rs:1921-1942`), which is a real but
modest benefit: it checks that `Term<dyn Stmt>` is a well-formed type, not
that the binder is used at that sort. The *actual* sort checking happens in
the semantic layer regardless (`VariableSortMismatch`,
`crates/krs-ir/src/semantic.rs:1791-1801`).

Proposal: make the leading parameters optional. A pattern binder without a
declaration gets its sort inferred exactly as K infers it (from the
constructor field sorts it appears under — information the semantic layer
already has). Authors keep writing the typed parameter when they want the
annotation as documentation or to force a narrower sort — the same contract
as Rust's own `let x` vs `let x: T`.

## 03a+b+c applied

```rust
/// `[step]`: expose the right-associated statement pair as K sequencing.
#[k::rule]
pub fn step(cells! { k: KCell(Sequence(first, second), ..) }: Machine) -> Machine {
    cells! { k: KCell(first, second, ..) }
}

/// `[var]`: replace an identifier at the head of `k` with its mapped value.
#[k::rule]
pub fn var(
    cells! {
        k: KCell(name, ..),
        env: Cell(map![name => value, ..]),
    }: Machine,
) -> Machine {
    cells! { k: KCell(value, ..) }
}

/// `[assign]`: consume a value assignment and update the environment map.
#[k::rule]
pub fn assign(
    cells! {
        k: KCell(Assign(name, value), ..),
        env: Cell(e),
    }: Machine,
) -> Machine {
    cells! {
        k: KCell(..),
        env: Cell(map![e [ name <- value ]]),
    }
}
```

`step` goes from 14 lines to 4; `assign` from 17 to 12. Reading effort drops
more than line count: everything that remains is information. Two subtleties
surface honestly: `var` must still mention `name: Term<Id>`-vs-inference
(here inferred from the `env` map's key sort), and a result that omits a
matched cell (`env` in `step`) means "framed", per 03a.

Note `var` quietly demonstrates a related cleanup: the value binding in the
map pattern (`value`) needs no pre-declaration, and the map-remainder rent
(`rest @ ..` → `..`) falls under 03b's rule too.

## 03d. The in-place rewrite: `=>` inside the island

03a–c keep r3's chosen shape — pattern in, term out — and its cost: the
unchanged context is still written twice (`k: KCell(...)` appears in both
halves of every rule). K's deepest readability device is that the rewrite
arrow sits *inside* the context, so context is written once:

```k
rule [assign]: <k> X = V:Value ; => .K ... </k>
               <env> E => E [ X <- V ] </env>
```

The equivalent step for KRS: allow `=>` at rewrite positions inside a single
`cells!` subject, with no separate result expression:

```rust
/// `[assign]`: consume a value assignment and update the environment map.
#[k::rule]
pub fn assign(
    cells! {
        k: KCell(Assign(name, value) => (), ..),
        env: Cell(e => map![e [ name <- value ]]),
    }: Machine,
) {}

/// `[while]`: unfold one loop test without making the constructor strict.
#[k::rule(label = "while")]
pub fn while_loop(
    cells! {
        k: KCell(
            While(condition, body)
                => IfThen(condition, Block(Sequence(body, While(condition, body)))),
            ..
        ),
    }: Machine,
) {}

/// `[done]`: remove an empty block from the computation cell.
#[k::rule(label = "done")]
pub fn done(cells! { k: KCell(EmptyBlock() => (), ..) }: Machine) {}
```

`done` is now structurally the K rule: one line, context written once,
rewrite visible as `EmptyBlock() => ()`. (Spelling of "rewrites to nothing"
is open: `()`, `.K`, or an empty right-hand side — `.K` matches the existing
`k!` grammar, `crates/krs-syntax/src/state_macro.rs:526`.)

### Why this is feasible

The island is *already* not Rust: `#[k::rule]` consumes the entire `cells!`
token tree before rustc sees it (`expand.rs:1803-2015`), and the `cells!`
grammar is hand-parsed (`crates/krs-syntax/src/state_macro.rs`). Adding `=>`
to that grammar changes no rustc-facing property. The IR is untouched: a
rule with embedded arrows lowers to exactly the same pre/post pair —
`krs expand` can display the two-sided reference form, satisfying the
ergonomic-macro contract's "deterministic reference-surface form" clause.

There is even a precedent for the item shape: `#[k::context_alias]` already
uses a fn returning `()` with an empty body and a single `cells!` subject
(`crates/krs-syntax/src/state_rule.rs:389-446`), so "declaration fn whose
whole content is its subject" is an existing KRS idiom, and the collector's
`syn::parse_file` re-parse accepts it (the body must exist — a semicolon
body would break the re-parse — hence `{}`).

### Costs, honestly

- **The function analogy weakens.** r3 chose pattern-in/term-out because
  pre/post extraction is trivially visible (`draft/investigations/
  r3-rule-surface.md:236-257`). With `=>` inside, a rule is no longer
  "a function from Machine to Machine" even visually; it is a marked
  declaration containing a K rewrite. The `-> Machine { ... }` tail
  disappears, which readers may miss (mitigation: `#[k::rule]` on a fn with
  a return type = two-sided form; without = in-place form; both remain
  legal, and mixing arrows with a result expression is an error).
- **rust-analyzer risk.** Today goto-def/hover work *inside* `cells!`
  payloads because rust-analyzer indexes attribute-macro input token trees,
  and the m1 LSP oracle hard-requires this (`tests/m1/tools/lsp_probe.py:
  242-337`). `=>` inside the tree is a token r-a tolerates (match arms), but
  whether its heuristic resolution still fires on identifiers around it must
  be gated on the existing LSP goldens before adoption. This is the main
  empirical unknown.
- **Two ways to write a rule.** Corpus guidance needed (suggested: in-place
  for single-focus rules, two-sided for rules that restructure several
  cells). This is the kind of choice design.md says to settle with corpus
  evidence, not in the abstract.
- Parser/collector/provenance work: extend the `cells!`/term grammars with
  rewrite nodes, add the collector re-parse arm, and add `ProvenanceRole`s
  for arrow positions — the standard new-surface cost.

## Recommendation

03a and 03b are near-pure wins: no information is lost, the deviation ledger
is untouched, and every rule in the corpus shrinks. Do them with proposal 01.
03c is low-risk and aligns binder ergonomics with K; adopt unless the
annotation-as-documentation argument wins on corpus review. 03d is the
highest-leverage single change in this folder *and* the one with a real
empirical gate (LSP goldens) and a real style cost (weakened function
analogy) — prototype it behind the ergonomics study and let the IMP + KWasm
corpus decide between "03a–c only" and "03a–d".
