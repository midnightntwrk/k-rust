# Language-scale state and builtins

{/* tour-concepts: extended-builtins tokens nested-cells nested-cell-field-metadata repeated-cells typed-hooks */}

IMP uses two leaf cells and a Map.
Larger definitions use the same declarations recursively: nominal cell groups organize state, fragments match part of a group, and builtin collections keep large terms symbolic.

## Nested and repeated state

KEVM's selected account state is a compact executable example:

```rust [semantics/kevm/src/lib.rs]
// [!include ~/snippets/kevm-accounts.rs]
```

`Account` is a nominal nested cell group.
The `nested` marker says that the field expands as that group rather than as one leaf cell.
`k::fragment!` can then describe the named portion of a nested configuration needed by a rule without reconstructing its unrelated fields.

The outer `account` field is repeated with `multiplicity = "*"` and represented by a `Map`-typed cell collection.
That exact shape has language-scale, end-to-end evidence.
The parser also accepts `Bag`, `List`, and `Set` as star-cell types, but those alternatives are only syntactically qualified today; optional cells and other multiplicities are not public KRS features.

Cell declarations are still symbolic schema.
Neither the Rust struct nor a fragment is a mutable host object, and a machine rule still performs one relational rewrite over the cells it names while framing the rest.

## Tokens and collection sorts

`#[k::token(regex = ..., prec = ...)]` introduces a lexical sort whose Rust tuple field records its host-facing shape.
The regular expression and optional lexical precedence determine parsing; they do not cause Rust's regex engine to run when a symbolic token is constructed.

The positive macro fixture declares an identifier token and then gives it ordinary sort memberships:

```rust [crates/krs-macros/tests/fixtures/positive/src/main.rs]
// [!include ~/snippets/token.rs]
```

Beyond IMP's `Int`, `Bool`, `Map`, and `Id`, the facade exports:

- `Bytes`, with length, indexed get/update, empty, right-pad, and substring operations;
- `List<T>`, with empty/item/concatenation, indexed access and update, size, repetition, ranges, and range updates; and
- `Set<T>`, with empty/item/concatenation and membership.

These are typed, zero-sized authoring markers for K builtins, not `Vec`, `HashMap`, byte buffers, or iterator APIs.
Calls such as `list::get(xs, index)` construct symbolic applications and may remain unevaluated when their semantic preconditions do not hold.

## Typed hooks

A function declaration may select one of KRS's typed hook operations, for example `krypto::keccak256_raw` for a Bytes-to-Bytes function.
Macro expansion rejects an unknown hook path.
After collection, KRS validates the declared operand and result sorts while constructing and checking Definition IR.
This is a bounded catalog: arbitrary hook strings and a general raw-K-attribute escape hatch are intentionally absent.

```rust [crates/krs-macros/tests/fixtures/positive/src/main.rs]
// [!include ~/snippets/typed-hook.rs]
```

Unknown hook names, wrong signatures, malformed nested fields, and unsupported cell metadata fail during Rust expansion or KRS checking.
A well-formed hook may still be rejected by a backend that does not implement the selected capability.

## What the large ports prove

KWasm, KMIR, and KEVM provide checked extracts for realistic syntax, state, functions, rules, claims, collections, and hooks.
They are incremental qualification ports, not complete language definitions.
The summaries below are generated from `semantics/coverage.toml` and include every recorded implemented entry, adapter boundary, and deferred area.
A tour example must never turn this evidence into a completeness claim.
