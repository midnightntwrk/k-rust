# Compose definitions

{/* tour-concepts: facets-composition facet-cfg-selection stable-identity backend-selection */}

A larger semantics can be split into ordinary Cargo packages and assembled explicitly at collection time.
Composition chooses definition facets; it does not merge source trees.
The definition it builds holds every selected facet, whether or not a source names one ([what the definition holds](#what-the-definition-holds)).

The root's facet declares the dependency facet it is composed with, so no command has to name it ([select the composition](#select-the-composition)).
A facet table needs no other key: every package emits a program-syntax module `<NS>-SYNTAX` and a semantics module `<NS>`, and each production chooses its module through its Rust visibility and `internal` flag.
When a dependency's rules need the root's configuration, the root also emits `<NS>-CONFIGURATION`, so the dependency can import the configuration without importing the root ([program syntax and the module pair](/reference/language#program-syntax-and-the-module-pair)).
The package-level `k-namespace` keeps emitted K names explicit.
The package-level `int-literals` key selects the module that supplies integer literals to the package's program syntax: `"signed"` (the default, `INT-SYNTAX`) or `"unsigned"` (`UNSIGNED-INT-SYNTAX`).
An unsigned package cannot compose a signed dependency whose program syntax uses integers, because K imports are unions and the signed literals would leak into programs.
The package-level `allow-raw-k` key (default `false`) admits the package's quoted hooks and `k::raw_k!` sentences, KRS's escapes from its no-strings rule, and the `profile` key, `"standard"` (the default) or `"strict"`, decides whether they warn or fail; `krs --profile strict` overrides every package, so CI can refuse raw K that a package allows ([raw K escapes](/reference/language#raw-k-escapes)).
Each package's keys govern only its own sentences.

Cargo package names, Rust crate names, and local dependency aliases are different identities here.
The root imports package `base-semantics` as `semantic-base`, which Rust exposes as `semantic_base` in paths:

```rust [tests/tour-composition/packages/root-semantics/src/lib.rs]
// [!include ~/snippets/composition-rule.rs]
```

That cross-package rule retains the base declaration's identity.
KRS does not resolve a constructor by comparing the text `Same`; ordinary Rust path resolution identifies it before collection.

Rust privacy is K privacy.
A production whose Rust item is not `pub`, including `pub(crate)` and `pub(in ..)`, is emitted with K's `private` attribute, so only its own package's rules can use it.
The exception is a production that an initializer calls in a definition whose configuration has a module of its own: `<NS>-CONFIGURATION` declares it and its package's module holds its equations, so it is emitted without `private`, and Rust visibility alone keeps other packages from naming it ([program syntax and the module pair](/reference/language#program-syntax-and-the-module-pair)).
A dependent that names it is rejected by rustc (E0603), and K's private syntax is invisible to every importing module, programs and proof modules included.
KRS keeps K imports public on purpose: a package's module imports the packages it references, and a claim may name a dependency's `pub` production.
A production that rules everywhere need but programs must not contain is `pub` and `internal`.

## Select the composition

A definition's composition is the dependency facets and the cfg values it is composed with.
It is part of what the definition is: its rules and its configuration differ by it.
The root facet therefore declares it, in the facet's table of the package's `Cargo.toml`:

```toml
[package.metadata.krs.definitions.main]
dependencies = ["base-semantics:base"]
cfg = ["tour_mode=extended"]
```

`dependencies` lists dependency facets, each written `PACKAGE:FACET`, and `cfg` lists KRS compiler inputs, each written `KEY` or `KEY=VALUE`; both keys are optional.
Every command that selects the definition reads them: `check`, `expand`, `emit-k`, `build`, `parse`, `run`, `search`, `prove`, `cases`, `compare` and `krs kink`, and the observer and patterns packages those commands compose with the definition.
The command shape is then:

```console
krs check \
  --manifest-path tests/tour-composition/Cargo.toml \
  --package root-semantics \
  --definition main
```

The teaching fixture declares its dependency facet and no cfg value.
A corpus whose flow names its definition needs no selection at all: `krs kink coverage --corpus DIR` takes the package and the facet from the flow and the composition from the facet's declaration.

The command line gives the same two kinds with the same spellings:

```console
krs check \
  --manifest-path tests/tour-composition/Cargo.toml \
  --package root-semantics \
  --definition main \
  --dependency base-semantics:base \
  --cfg tour_mode=extended
```

`--dependency PACKAGE:FACET` is repeatable and always names both halves.
`--cfg KEY` and `--cfg KEY=VALUE` are repeatable KRS compiler inputs; they are not Cargo features.
The command line replaces the declaration, one kind at a time: a command with any `--dependency` composes exactly the facets its flags name and none of the declared ones, and a command with any `--cfg` passes exactly the values its flags name.
A kind the command line does not give is read from the declaration, so `--cfg` beside a declared `dependencies` list keeps the list.
The command line cannot give an empty kind: a definition that some command composes with no cfg value, or with no dependency facet, declares none of that kind, and its other commands give theirs.
The selected root facet's declaration states the definition's composition whole: the keys of a dependency facet are not followed.
The facet of an observer or a patterns package declares what it adds to the definition it is composed with ([what an observer adds](#what-an-observer-adds)).
A composition given by declaration is the definition the same flags give: both emit the same K, with the same symbol and source maps.
The next steps `krs kink` prints repeat the flags the command line gave, so they name no selection that is declared.

In the teaching fixture, `tour_mode=extended` includes the `extended-root` constructor; the release gate emits the definition both with and without that value and checks that only the configured artifact contains the production.
An ambiguous root package name can be replaced by the exact `--package-id` selected from Cargo metadata.
Dependency selectors currently accept package names only, so an ambiguous dependency package cannot be disambiguated with `--package-id`.

A declaration is checked at planning, whatever the command line gives: a `dependencies` entry that names a package outside the graph, a facet its package does not declare, or a package outside the root package's resolved dependency closure is refused, and so is a key or an entry of another form.
The refusal names the manifest key (`package.metadata.krs.definitions.main.dependencies`), the manifest, and the facets the package declares.
A source that names an item of a package no selected facet is of is refused with `krs::collect::package-not-selected`, whose help names the `--dependency PACKAGE:FACET` that selects the package and the `dependencies` key that selects it for every command.

Missing packages, missing facets, and ambiguous package selections fail during planning before the collector is built.
A dependency facet must be in the root package's resolved dependency closure; the commands that evaluate views in an observer ([views and the observer](/reference/workflow#expectations)) give each composition, the definition and each observer, the facets its own closure holds, and each observer the facets it declares ([what an observer adds](#what-an-observer-adds)).
Selection order has no semantic meaning: the planner canonicalizes the same set to the same composition.

## What an observer adds

An observer and a patterns package are questions about a definition.
krs composes the package's facet with the definition a command selects and with that definition's composition ([views and the observer](/reference/workflow#expectations)).
Such a facet may need a facet the definition is not composed with: a package of functions its views apply, or of named constants its clauses name, which no semantics depends on.
That need is the observer's statement, so the observer's own facet declares it, with the key a root facet uses:

```toml
# my-views/Cargo.toml
[package.metadata.krs.definitions.views]
dependencies = ["view-helpers:main"]
```

The observer's composition is the definition, the dependency facets of the definition's composition, and the facets the observer declares.
Every command that prepares the observer reads the key: `run`, `search`, `cases`, `compare` and `krs kink`, for an observer a case, a stop condition, an observation or a view names, and `krs kink query` and `krs kink fuzz --pattern` for a patterns package.
No command names the facet with `--dependency`.

The declaration adds to the observer's composition and to nothing else.
The definition a command runs is planned from the definition's own declaration and the command line, which an observer's key does not enter.
Its emitted K, its Definition IR, its digests and its `kink.lock` are therefore the same with the observer and without it.
The observer's own digest and the record of its prepared definition are keyed by the observer's composition, which holds what it adds.

`--dependency` keeps its meaning.
It gives the definition's dependency facets and replaces the definition's declared ones.
A facet it names outside the definition's closure is composed by each observer whose closure holds it.
It does not replace an observer's declaration.

An observer's functions are evaluated at values the definition computed, so the observer's composition must hold the definition as it is.
Two kinds of entry would hold another definition instead.
Each is refused when the observer is prepared, and the refusal names the observer's key and the key of the definition's facet that states the entry instead:

- A facet of a package in the definition's own dependency closure that the definition is not composed with (`krs::plan::invalid-definition`).
  Whether such a facet is composed is part of what the definition is.
  Add it to the definition's `dependencies`, or remove it from the observer's.
- A cfg value the definition is not composed with (`krs::plan::invalid-cfg`).
  A cfg value applies to every package of a composition, the definition's packages too.
  Add it to the definition's `cfg`, or remove it from the observer's.

An entry the definition already has adds nothing, so an observer may list a facet or a cfg value of the definition it observes.
Which entries the definition has is decided by the command: a `--dependency` or `--cfg` that leaves one out has the observer's entry refused for that command.
A facet of a package outside the definition's closure is of a package that no source of the definition can name, as the observer's own package is.
It joins the composition beside the observer's facet, and every package of the definition is collected with the facets and the cfg values the definition has.
An entry is otherwise checked as a root facet's is: its package is in the observer package's resolved dependency closure and declares the facet.

A patterns package's declaration is read the same way, and what it adds reaches the package's clauses only as names.
A pattern is asked of the definition's runs in the definition's emitted K, which holds no facet the package adds.
A clause that names a constant of an added facet holds the constant's value and is asked like the clause that writes the value out.
A clause that applies a function of an added facet is emitted and is then `invalid-pattern`: the definition has no such function, and a function a pattern calls belongs to the specification ([chain patterns](/reference/language#chain-patterns)).

## What the definition holds

The definition's main module is the root package's module `<NS>`, and the definition holds every selected facet.
A package's module imports the packages its own sentences reference; the root's module also imports each selected package that those imports do not reach in the emitted K, so a facet is composed whether or not some source names it, and its `pub` productions join the root's program syntax through `<NS>-SYNTAX`, as a referenced dependency's do.
A dependency whose rules need the configuration imports the configured package's `-CONFIGURATION` module rather than the package's module, and that module holds none of the configured package's rules, so such an import does not count as reaching the configured package.
The root imports only what nothing else reaches, the topmost such packages, so a composition whose references already reach every facet emits the same K.
A dependency that imports the root package's module, which the root never references, is held the same way: the root imports it, and its import of the root becomes the `-CONFIGURATION` import above, so the main module stays the root's rather than the dependency's.

## Stable public symbols

Default declaration identities follow their Rust-resolved owning items and therefore change when public declarations move.
`#[k::symbol("public::Name")]`, immediately before the KRS declaration attribute, can pin a public symbol while preserving the new source provenance.
It delegates only to a sort or standalone constructor declaration, or, written among a family variant's helpers, to that variant, whose pinned identity then no longer depends on the enum's name; it is not a general renaming attribute.

The final path component becomes the readable emitted K name, while the complete `tour::…` path remains the stable logical identity.

Aliases, same-named crates, and renamed facade dependencies are supported because the collector uses exact package and Rust type identities rather than spelling heuristics.
Duplicate stable public identities are an authoring error.

## Choose a backend

`--backend llvm` is the default; `--backend haskell` selects the other native target dialect.
Only the Haskell target keeps claims; an LLVM build omits them because that backend executes but does not prove.
Backend choice is an explicit build input and may change capability diagnostics, but it must not change authored symbol identity.
`emit-k` and `build` require `--output`; backend failures are distinct from Rust expansion, KRS semantic analysis, and K frontend diagnostics.

Run `python3 tests/tour-composition/verify.py` from the repository root to check both packages, canonical formatting, deterministic expansion, dual cfg-value emission, the dependency import, stable emitted names, and the cross-package rule.
