# Measure the tests your AI writes

AI is getting better at formal verification, but KRS allows it to also hill-climb on test quality, all while maintaining readability.

## The problem

### Ever asked AI for tests that turned out to check nothing?

<VersionTest />

### Those tests add up

Meaningless tests slow down your development cycle and eat into your CI budget.

<TestSuiteCost />

### And even real tests miss cases

Tests can check real results and still miss the cases that would catch a bug.

<GreenButWrong />

### Why tests, now

Test quality matters for many AI workloads.

<WhyTests />

## A specification you can run

KRS lets you write a specification of your program in Rust, run it, and use it to grade and grow the test suite an AI writes for you.
k-rust, a Rust implementation of the K Framework, runs it.

### For example, let’s specify natural numbers and addition

Before any code, write down what `plus` means.

<WriteItDown />

### Your specification is Rust

The same specification in KRS.
KRS is real Rust, written in a particular style: the specification is a crate, Cargo builds it, and rustc checks it.

<SpecIsRust />

### The rewrite machine

KRS uses matching logic to describe values and states as patterns, with rules that say how they change.
To compute `plus`, a rule finds a subterm its pattern fits, binds the variables, and replaces the subterm using those bindings.

<RewriteMachine />

## Why matching logic?

Matching logic scales from our two rules for addition to specifications of real languages and virtual machines, including Rust’s MIR, WebAssembly, and the EVM.

<MatchingLogic />

### KRS generates Lean

KRS generates Lean code through `k2lean`.
You can start with a compact matching-logic specification, and use Lean to prove more complex properties around the generated model.

<LeanBridge />

### One specification, every tool

A small vocabulary of patterns and rules keeps the specification readable.
That shared structure also gives every tool the same rules to work with.
One definition becomes a parser, an interpreter, a search engine, a prover, a Lean library, and a fuzzer that crafts inputs to reach your target.

<EveryTool />

## Why a test corpus

KRS supports autoresearch and hill-climbing on your specification, using Lean proofs and bisimulation to check that changes preserve its intended properties and behavior.
It also gives AI a way to hill-climb on test corpus quality: measure which mistakes the tests catch, then add tests that close the gaps.

### A test corpus

A test is a program, and its expected result is whatever the specification computes for it.
Nobody guesses expected values, and nobody copies them from the implementation under test.

<Corpus />

### Coverage of the specification

Because the specification runs, you can see which of its rules each test makes fire.
That is coverage of the specification itself, not of one implementation's code.

<SpecCoverage />

### Past 100%

100% rule coverage does not mean no bugs.
Your tests can exercise every rule and still miss bugs in how they interact—for example, a READ that returns stale data only after a WRITE under specific conditions.

<PastFullCoverage />

## Mutation testing, done right

### Why people avoid mutation testing

<MutationReputation />

### Mutate the specification

Mutating the specification instead of the code changes the experience.
The specification is small, so there are few places to edit, and an AI proposes only edits that would be real misunderstandings of its meaning.
Each edit is checked against the corpus, and surviving edits become targets for new tests.

<MutateTheSpec />

### Cover patterns of interest

You can also extend the corpus to ensure it contains specific patterns of interest.
AI can propose interactions, check whether they appear in the corpus, and add tests for the ones that are missing.

<InteractionPatterns />

### Let KRS find the missing inputs

KRS fuzzing uses deterministic, specification-guided input search to find inputs that trigger specified behavior, so growing your corpus doesn’t rely solely on AI.
Choose targets yourself, with AI, or from your Lean proof obligations.

<TargetedFuzzing />

## Standing on K

Your KRS crate is a definition in the K Framework, so it builds on the same foundation as those language specifications.
Each KRS item becomes a K sentence you can read, and k-rust is a reimplementation of K in Rust.
