# Inspect what KRS builds

{/* tour-concepts: two-surfaces build-commands artifacts */}

KRS keeps authoring pleasant while making every compilation boundary inspectable.
The representations form a one-way pipeline:

```text
readable Rust → explicit Rust → descriptors → semantic IR → Definition IR → K → KORE
```

## Readable and explicit Rust

Readable layer 1 is the surface used throughout the IMP chapters: open-sort blocks, constructor families, declarative configurations, and rule tables.
`krs expand` produces deterministic explicit layer 2, where those conveniences become ordinary attributed Rust items.

Layer 2 is an audit and escape-hatch representation, not a second tutorial dialect.
The executable complete IMP fixture and its parity tests decide whether readable and explicit forms preserve the same theory.

The descriptor records the authored operator, `operator:add`, because `+` names no domain by itself; semantic analysis chooses it from the operands' sorts, here the `Int` that `where lhs: Int, rhs: Int` gives both binders, so the rule's result is the symbolic builtin application `int_add`.

## Semantic artifacts

`krs emit-k` writes an owned artifact directory containing:

- `definition.k`, emitted K source for the semantics;
- `spec.k`, the definition's claims, when it has any;
- `symbols.json`, stable-to-emitted identity mappings; and
- `sources.json`, generated ranges traced through authored macro and transformation frames.

With `--ir` it also writes the three levels above the K:

- `descriptor-bundle.json`, the collected host declarations;
- `semantic-ir.json`, the resolved symbolic theory; and
- `definition-ir.json`, the backend-neutral definition.

Each JSON artifact is compact JSON with one trailing newline and no whitespace outside strings.
KRS's serializer writes one encoding for each in-memory value, with object members in the order the value's type fixes; the encoding is not RFC 8785 canonical JSON, so another serializer may write the same value differently.
`jq .` indents an artifact for reading.

Every node of `sources.json` and of the three IRs carries its origin: the frames from its authored tokens through each transformation that produced it.
Most frames recur across nodes (an item's macro invocation, a transformation's role, a file's identity in every range), so each of these artifacts writes its provenance once, in a `provenance` object after its version and before its body:

- `packages`, each package a file or an item belongs to;
- `files`, each source-file revision, as its `package` index, `package_relative_path` and `content_sha256`;
- `items`, each Rust item a frame names, as its `package` index, `module_path`, `item_name`, `item_kind` and `disambiguator`;
- `labels`, each frame label; and
- `frames`, each distinct frame, as an array whose first element is its kind code:
  `[code, file, start, end, item, label]` for a ranged frame (0 authored, 1 macro invocation, 2 generated artifact, 3 frontend diagnostic),
  `[code, item, label]` for a transformation (4 generated descriptor, 5 Semantic IR, 6 Definition IR),
  and `[7, kind]` or `[7, kind, file, start, end]` for an inserted frame, without or with its anchor.
  `file`, `item` and `label` are indexes into their tables; `item` and `label` are `null` when the frame has none.

In the body, an origin is the array of its frames' indexes, its authored frame first.
Only the root object's `provenance` member holds the tables: in `descriptor-bundle.json` each descriptor also has a `provenance` member, holding its primary key and its nodes' origins, and those origins index the root's tables.
Each table lists its rows in the order the body first reaches them, so the tables are part of the one encoding of the value.
An artifact is read without any other file, and reading it restores every frame of every node.

Each `sources.json` entry records its node's depth in the rendered definition: a module is 0, its sentences 1, and each child one more than the node that holds it.
A configuration renders each cell's declaration and its initial value as one text, so a cell's declaration and its initializer cell, which span the same bytes, take two consecutive depths, the declaration first, and the cell's attributes, value and child cells come below both.
A configuration variable, rendered at its first use in the initializer, and a context alias's `HERE`, rendered at its hole, are one deeper than the deepest such use.
So a node whose range strictly holds another's is shallower than it, and nodes rendered at the same range have different depths.
An entry whose node KRS inserted, which no authored token denotes, carries an inserted frame (code 7) naming what was inserted:
`definedness_test` for the test of a partial construct a condition evaluates and the `andThenBool` that joins it,
`lookup_guard` for a looked-up instance's or computed key's fresh name and guard,
`generated_binder` for a name KRS made for no token and for an alias KRS adds under such a name (a `k::bits!` template's binder, the binder of a field a record update takes from its base),
`cell_frame` for a frame the language adds (a block-form rule's kept computation, a `have` read's remainder, the input stream's rest),
and `local_function` for the scaffolding of a lifted `let` block or `k::matches!`.
A definedness test's frame also carries the authored range of the construct it tests.
A node that renders authored syntax, once or many times, carries no such frame:
a `k::bits!` template's tests and field reads, an `else`'s negations, a constant at each use, and every frame the author wrote as `..`, whose authored range is that token.

Use an explicit output directory:

```sh
krs emit-k \
  --manifest-path tests/tour-imp/Cargo.toml \
  --package krs-tour-imp \
  --definition main \
  --ir \
  --output /tmp/krs-imp-emitted
```

K accepts claims only outside an executable definition, so `definition.k` holds no claims.
`spec.k` `requires "definition.k"` and holds the proof modules: each author spec module (`#[k::spec_module]`), then, when the definition states claims, a generated `<MAIN>-SPEC` module that imports the main module and wraps them.
Kompile `definition.k` once, then pass `spec.k` to `kprove` against that kompiled definition.

### Reading the emitted K

`definition.k` and `spec.k` name their Rust sources themselves, so a reader who never opens `sources.json` can find the K of a Rust item, and the Rust item of a sentence.
Each opens with a header that says it is generated, from which Cargo packages, and is not to be edited, and how its comments and default labels name the Rust sources; this is `definition.k`'s:

```k
// Generated by `krs emit-k` from krs, story-plus. Do not edit; edit the Rust sources and emit again.
// The `// KRS <package>/<file>: <item>` line above a sentence names the Rust item it comes from.
// A default label spells that item's path: `<namespace>--<module>--…--<item>`.
// Mutations of this K are patches in the package's kink/mutations/<topic>.toml, each edit anchored by `rule = <label>`;
// `krs kink check` resolves them and shows each edit's Rust line. Why K patches, not Rust edits: https://github.com/midnightntwrk/k-rust/blob/main/kink/decisions.md#m-mutation-input
```

`definition.k`'s header adds the last two lines, on mutations, since kink patches that file: a mutation is a K patch anchored by a rule's label, `krs kink check` resolves it, and the link gives the reasons; `spec.k`'s header has the first three lines only.
The packages are those of every module and sentence the file holds, so `definition.k` also names `krs`, whose sources declare the framework module.
Above each rule, equation, simplification, alias, desugar, context and claim, and above the configuration, a `// KRS` line names the Rust item the sentence comes from, by its package, its file relative to the package, and the item as the source spells it:

```k
  // KRS story-plus/src/lib.rs: plus_zero
  rule plus ( zero , N:Nat ) => N:Nat [label(nat--plus_zero)]
```

The item is the rule or equation fn, the row's label for a row of an [equation table](/reference/language#equation-tables), and the configuration struct for the configuration.
An equation a [branching body](/reference/language#branching-bodies) writes names its function and its branch, `InterruptVector, branch 3`, `SignedLess, branch 2.1` for the first branch inside the second, or the arm's label, `InterruptVector, branch vblank`; a function's one equation names the function alone.
An equation of a function KRS lifts out of a `let` block or a `k::matches!` names the item it was lifted out of and adds `, local function`.
An equation of a function that, within the definition, only claims apply ends with `(claim helper: only claims apply it)`: no initializer term, no production of the program syntax and no other sentence a run can fire applies the function, not even through the equations of the functions those apply.
The mark is about the definition alone: a run's [input](/reference/workflow#inputs-by-name) may apply any function through `{"$call": ..}`, a claim helper included.
A definition with a `raw_k!` sentence marks none, since its opaque text may apply any function.
A `raw_k!` sentence keeps its own `// raw_k! <package>/<file> (opaque to KRS)` comment instead, and the other sentences (sorts, productions, priorities, context aliases) have no line; a production's rustdoc is its own comment.

No comment holds a line, a column or a byte offset: the exact Rust line is the source map's, in `sources.json`.
An edit that only moves Rust lines, such as a blank line or a `//` comment above an item, therefore leaves both files byte-identical, so a committed `definition.k`, and every digest of it, changes only when an item is added, removed, renamed or moved, or when its K changes.
A rustdoc comment is different: a production's rustdoc is emitted above the production, so a new `///` line on one changes `definition.k`.
The comments are K comments outside the generated range of every sentence: they change no sentence and no range `sources.json` records for one, and only the source locations K's own front end reads from `definition.k` move with them.

`krs build` continues from Definition IR to selected LLVM or Haskell KORE artifacts.
The Haskell target carries the claims for proving; LLVM executes but does not prove, so its build omits the claims and reports how many.
It does not execute the object program: `krs run`, `krs search`, and `krs prove` do, with the k-rust backend that krs links ([run, search, and prove](/reference/workflow#run-search-and-prove)).

## Identity and diagnostics

Rust paths and generated declaration identities remain distinct from emitted K symbols.
A production's emitted symbol depends only on its own declaration (`Op::Add` is `opAdd`, a struct `Inc` is `inc`), so no other declaration can rename it.
`#[k::symbol]` can pin the public symbol of a sort, a standalone constructor, or a family variant where external compatibility requires it; inferred identities are preferred elsewhere.

Source maps preserve authored ranges through generated artifacts.
A failure should be reported at the stage that discovered it: Rust expansion, KRS analysis, the K frontend, or the native definition checks.
Not every stage currently has the same structured diagnostic fidelity, so the workflow and boundaries pages name the gaps.
