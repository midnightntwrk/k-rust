# Daily workflow

{/* tour-concepts: diagnostics-lsp formatter-comments */}

KRS has a short, staged command line.
Use the earliest command that can answer the question you have; later stages add generated artifacts and backend prerequisites.

## Edit and check

```console
krs fmt --check --manifest-path Cargo.toml
krs check --package my-semantics --definition main
```

`fmt` canonicalizes KRS DSL islands while leaving ordinary Rust to the Rust formatter.
It can format paths or stdin, and `--check` reports drift without rewriting files.
Without paths it selects what `cargo fmt --all` selects, restricted to workspace members:
each member target's root and the files of the modules it declares,
so fixtures beside a target are left alone unless named explicitly.
Inside DSL macro bodies, use line comments: non-doc `/* ... */` comments are rejected because procedural macros cannot recover them reliably.
The default aligned trailing-comment layout is provisional; `--trailing-comments gutter` selects the other implemented policy.

`fmt` lays `k::rules!`, `k::equations!`, and `k::claims!` bodies out within the Rust formatter's `max_width` (100 unless a `rustfmt.toml` sets it), indentation included.
The one-line rows of a block align their labels, `=>`, and `where` in columns.
A row too long for its line is laid out on its own and widens no column: its label on one line, then its pattern and `=> result` indented, and `where` on a line of its own.
A row that fits only without the alignment's padding stays on one line, unaligned.
Cell records put one cell per line.
Inside a term, a group too long for its line breaks from the outside in, as the Rust formatter breaks calls and struct literals: one argument, field, or element per line, indented, and an inner group breaks only when it still does not fit.
An or-pattern too long for its line puts one alternative per line with a leading `|` under the first; in parentheses, as in `op @ (A | B)`, it hugs them.
A condition breaks before `||`, else before `&&`, else before a comparison (`==`, `!=`, `<`, `<=`, `>`, `>=`), one level deeper.
An operator stays on the line that ends the operand before it when that line ends at or before the operator's indentation, as when a record or call before it breaks anyway (`} != rhs`) or the operand is short (`x != Record {`), and the operator and the first line of its operand fit there; a line comment beside the operator keeps it at the start of its line, and a `=> result` whose first operand must break stays on the pattern's line, as for that operand alone.
A call whose one argument is a delimited term (`f(..)`, `Record { .. }`, `m![..]`, or `[..]`) and which does not fit on its line hugs it, as the Rust formatter does: the call's delimiters stay on the argument's first and last lines, `list::item(Entry {` / fields / `}),`, and only the argument breaks; an argument with an alias, an operator, or a comment does not hug.
A `where` list too long for its line puts one binder per line under `where`.
A one-line attribute too long for its line breaks inside its arguments; one written over several lines keeps its layout.
`fmt` never reorders a token, and the only token it adds or removes is a list's trailing comma: as the Rust formatter does, a list broken over lines ends with a comma and a list on one line has none, whatever the source wrote.
A record's rest (`..`, `..base`) takes none, as in Rust, while a bracket's `..` or `rest @ ..` is an element and takes one; a `where` list takes none before its `;`, and `(a,)`, whose comma makes a 1-tuple, keeps it.
A line comment inside a delimited group keeps its place and breaks the group; any other comment of a clause moves to the lines before the clause, and so do all of the clause's comments when one of them would otherwise move before a comment kept in place.
Only a doc comment, a literal, or another token longer than the line leaves a line of a KRS body over the width.

`check` resolves Cargo metadata and selected facets, builds and runs the generated collector, validates descriptors, performs semantic analysis, and then judges the definition as every later command that needs no K toolchain would: it emits the K `emit-k` writes, with its symbol and source maps and their checks, and for each native route it consults the route's capability table and runs k-rust's preparation, definition checks, and compilation exactly as `build` does.
It does not render the JSON artifacts `emit-k` writes beside the K (the two maps, and with `--ir` the descriptor bundle and the Semantic and Definition IR), because rendering cannot refuse what emission accepts: the encoder fails only on a map key that is not a string or on a value whose serialization fails, and these types hold neither.
On the `native-rust` route, which `build --backend haskell`, `run`, `search`, and `prove` share, it also loads the compiled definition as the run commands do, including each spec module's proof definition.
It reports the same errors and warnings those commands report, but writes no artifacts.
A passing `check` therefore means that `emit-k`, `build` on either backend, and the run commands accept the definition; what remains are refusals of one invocation, such as a program that does not parse, `search` on a definition with `stream` cells, or `prove --spec-module` naming no spec module.
The exception is a feature one route's capability table lacks and another route builds, for example an existential rule result, which `native-llvm` refuses and `native-rust` runs: that is the documented limit of one route, not a fault of the definition, so `check` judges the routes that build it, passes, and warns with the refusal (`krs::capability::unavailable`), naming the commands of the route that refuses and of the routes that build it.
When every route refuses the definition, or a route's compile does, `check` fails with that refusal and a note naming the commands of that route.
`--backend llvm` or `--backend haskell` narrows the judgement to `emit-k` and that backend's route, so `check --backend haskell` passes for a definition only the symbolic route runs, and `check --backend llvm` for one only concrete execution runs.
The routes compile concurrently, so judging both costs about the time of the slower compile.
Rust errors from the collector build are reported at authored source spans when Cargo provides a mappable primary span.
They keep rustc's notes and help, and a suggested replacement in authored source is spelled out as the edit it makes (``remove `()` at src/lib.rs:48:28``); a note or help that points only into macro-generated code is left out, because it describes tokens the author did not write.
Under `deny(warnings)`, rustc also reports as unused an import that only a failed KRS item uses, because that item's expansion was withheld.
`check` leaves such an error out when the failed item, in the import's module, names the import, and reports every other unused import, one per name; a glob import is always reported, since its names are not known without resolving it.
`cargo check` and rust-analyzer still show it.
`check`, `expand`, `emit-k`, `build`, and the run commands render human-readable diagnostics on stderr by default, including their codes, notes, help, and authored source snippets when the source revision matches.
Pass `--message-format=json` when a tool consumes diagnostics.
Every command that lowers the definition (all but `fmt`) reports the definition's warnings, such as an uncovered total function or a `program` production programs cannot contain; `check` and `build` add those of the backend routes they judge, and `prove` those of the claims it trusts.
It reports them whether or not the command then succeeds: a failing command prints the warnings of the stages it completed before its error, so a `parse` that fails on a production placed outside program syntax shows the `krs::partition::not-program-syntax` warning that explains it.
`check`, `expand`, `emit-k`, `build`, and the run commands warn about each quoted hook and `k::raw_k!` sentence of a package that sets `allow-raw-k = true`; `--profile strict` overrides every package's `profile` and turns those warnings into errors, so CI can refuse the [raw K escapes](/reference/language#raw-k-escapes) a package allows.
In JSON mode, every diagnostic is one schema-2 JSON envelope line on stderr, with its stage, code, `kind`, severity, and message; collector failures have stage `analysis` and a `krs::collect::*` code.
`kind` says who can act on it: `author` for a mistake in the program, the manifest, or the command line, `internal` for a KRS bug (human output prints its message as "internal error (a KRS bug): ...", or "internal warning (a KRS bug): ..." for a warning), and `environment` for files, Cargo, the toolchain, or a stale build.
`authored_range` is the exact authored file revision and byte range, or `null` when no authored text is the diagnostic's subject; then `item`, when present, names the item it is about.
`labels` lists related authored locations, each a `range` with an optional `message`, such as the occurrence that contradicts a binder's declaration; human output underlines each in its source.
Only a failure without a code, such as a usage error or a collector that crashed, is a prose line, with the process status and stderr detail.
Run ordinary `cargo check` when you want Rust-only feedback on names, types, imports, and macro expansion while editing.

## Inspect the lowering

```console
krs expand --package my-semantics --definition main
krs emit-k --package my-semantics --definition main --output target/krs-k
```

`expand` prints the deterministic explicit Rust-facing reference surface.
It reads every module file of the package's library crate, from its root through each `mod name;`, and replaces each readable form by its long form in the file and module that hold it, so the printed package keeps the authored module structure, and every path the authored items write resolves as it did.
A long form also writes paths the readable form leaves implicit, such as a binder's sort: `expand` prints such a path only where the source shows it compiles there (an item of the package whose modules and own declaration are visible from the printing module, the path the clause writes, or a dependency's module that a `use` or a readable macro of the crate names), and otherwise refuses the package, naming the item.
Stdout does not say which file it holds: a consumer that overlays it on the crate root must check that the crate root is the one file that changed, or use `--output`.
When exactly one file changes, `expand` prints it on stdout (the crate root when none changes); when several do, it refuses and asks for `--output`:

```console
krs expand --package my-semantics --definition main --output target/krs-expanded
```

`--output` takes an absent or empty directory and writes only the files the expansion changes, each at its path relative to the package, such as `target/krs-expanded/src/rules.rs`, and stdout lists those paths, one per line.
The printed package is the authored one with exactly those files replaced: copy the package (a relative `path` dependency must still reach its package from the copy), copy the directory over it, and `krs check` and `krs emit-k` judge the printed source as they judge yours.
`emit-k` writes the generated K definition with the two maps that carry it back to your source: `symbols.json`, from stable identities to emitted K names, and `sources.json`, from generated ranges to authored ones.
Claims go to a separate `spec.k` beside `definition.k`, the layout `kompile` and `kprove` expect.
These outputs are audit artifacts, not a second source file to edit.

```console
krs emit-k --package my-semantics --definition main --ir --output target/krs-k
```

`--ir` also writes KRS's three internal levels, `descriptor-bundle.json`, `semantic-ir.json`, and `definition-ir.json`, for a tool that reads them, such as a harness that compiles `definition-ir.json` in process.
They are KRS's own representations, versioned together and read back only at the same schema version, so the default leaves them out.
An emission writes only its own selection: it removes from the output directory any `emit-k` artifact an earlier emission left there, such as the IRs of an earlier `--ir` run or a `spec.k` the definition no longer needs.

The lowering page names the descriptor, semantic, definition, K, symbol, source, and KORE boundaries in detail.
When a generated K range has an exact source-map entry, diagnostics should point back to the hash-checked authored bytes rather than expose a generated collector path.

## Build a backend target

```console
krs build \
  --package my-semantics \
  --definition main \
  --backend llvm \
  --output target/krs-native
```

`build` continues through K frontend and selected backend compilation.
The LLVM backend executes but does not prove, so an LLVM build omits the definition's claims and says how many it omitted.
Successful `check`, `emit-k`, and `build` commands reuse a previous result when the command options (for `emit-k`, `--ir` among them), collector executable, and files read by the collector are unchanged.
A reused command returns the same stdout and restores any missing or modified output files.
Each command keeps one previous result, so alternating `emit-k` with and without `--ir` replaces it each time, and neither is reused after the other has run.
Pass `--no-reuse`, or set `KRS_NO_REUSE=1`, to run the collector and later stages again.

The generated collector compiles KRS's own crates and the libraries they call at opt-level 3, and the definition's crates unoptimized and without debug information.
An override names a crate, so a dependency of the definition that shares one of those crates' names is optimized too.
Each collector has its own directory, with its own Cargo target, under the project's target directory, keyed by the generated package and the selection: the definition, the root and dependency packages with their versions and features, the cfg and registration settings, and KRS's own paths.
The first command with a new selection compiles KRS's crates once in a new collector directory, and the first after upgrading KRS compiles them again; after an edit, Cargo recompiles only the edited crates and the crates that depend on them.
An earlier collector directory stays until the target directory is cleaned.

The optimization repays its first compilation over the commands that follow it.
A one-shot run in a fresh target directory, such as a CI job, can compile those crates unoptimized instead, as KRS's own fixture tests do: krs builds each collector from its directory under the target directory, Cargo reads the configuration files of that directory and of every directory above it, and a configuration's profile takes precedence over the manifest's, so a `<target>/.cargo/config.toml` that sets `opt-level = 0` for each crate the generated `Cargo.toml` optimizes applies to every collector under that target.
The optimization level changes no output.

```toml
# <target>/.cargo/config.toml: one table for each [profile.dev.package.<name>] of
# <target>/krs/collectors/<digest>/Cargo.toml
[profile.dev.package.krs-collector]
opt-level = 0

[profile.dev.package.syn]
opt-level = 0
```

## Run, search, and prove

```console
krs run --package my-semantics --definition main prog.imp -c env='.Map'
krs search --package my-semantics --definition main prog.imp
krs prove --package my-semantics --definition main --claim branching
krs parse --package my-semantics --definition main --sort Stmt prog.imp
```

`run`, `search`, `prove`, and `parse` play the roles of K's `krun`, `krun --search`, `kprove`, and `kast` on the emitted definition.
They share the collection and lowering stages of `check`, then compile the Definition IR in-process with the k-rust backend over the symbolic KORE dialect, so they take no `--backend`.
Their results are never reused from an earlier invocation, but the compiled definition is: the first command compiles the Definition IR and keeps the compiled stage in a per-user cache, `${XDG_CACHE_HOME:-~/.cache}/krs/compiled-stages/v1` (or the directory `KRS_STAGE_CACHE_DIR` names), and a later command on the same Definition IR loads it instead of compiling again.
An entry is keyed by the digest of the Definition IR's canonical JSON and the `krs` executable, which links k-rust, so a changed definition or `krs` build (k-rust included) compiles again; an entry unused for 30 days is deleted.
`prove --spec-module NAME` also keeps the proof definition it compiles for that author spec module, under the same key plus NAME (the Definition IR digest covers the spec module's content), so a second proof of an unchanged spec module compiles neither.
`--no-reuse` or `KRS_NO_REUSE=1` compiles again and replaces the entry.
A cache directory inside the package's Cargo workspace is never used, so an entry is never committed with the package: each command then warns (`krs::exec::stage-cache`) and compiles the definition again, and setting `KRS_STAGE_CACHE_DIR` to a directory outside the workspace restores reuse.
FILE (or `-` for standard input) binds the main parameter of the `#[k::init]` (the one marked `#[k::config_var(.., main)]`, or the one the computation cell reads when none is marked), whatever its K name; a definition without a main parameter refuses FILE, naming every parameter to bind by name instead ([inputs by name](#inputs-by-name)).
Where the main parameter's type is exactly `Bytes`, FILE is its value: the file's bytes, unchanged, as `{"$file": ..}` gives them.
Otherwise FILE is text, parsed at the parameter's sort: as a program, at the start position of its sort, where that parameter is `$PGM`, and as `-c` text of that parameter otherwise; a file that is not UTF-8 text is refused, naming the parameter and its type.
`-c NAME=TEXT` binds a parameter by its Rust name (`env`) or its configuration variable's K name (`ENVIRONMENT` or `$ENVIRONMENT`); FILE together with a binding of the main parameter by name binds it twice and is refused.
`run` follows one path, choosing one successor per step as krun does, and `search` returns the set of reachable final states; `--mode` selects `all`, `one-step`, or `one-or-more-steps` instead.
`prove` proves every claim, or each `--claim` label given as the exact label or a unique suffix; `--spec-module NAME` proves the claims of an author spec module (`kprove --spec-module`) instead of the generated `<MAIN>-SPEC` ([spec modules](/verification/reachability-claims#spec-modules)).
`--depth N` bounds rewrite steps; evaluating functions, and applying `anywhere` rules, which are equations, is not a step.
`run --stop-before NAME` ends the run at a state whose one successor is a step by a rule NAME selects, and `--stop-after NAME` at that step's successor; a step by such a rule from a state with several successors stops nothing, and the run goes on past it.
Each flag is repeatable, and a run that ends so is `stopped`.
NAME is a KRS item or a K label.
An item is named by its Rust path as the root package's source names it, `crate::` and its path there (`crate::tick`, `crate::ppu::frame_end`) or a dependency's crate name and its path there (`lang::step`), and selects every rewrite rule the item lowers to (a context's heat and cool rules, a strict production's); a path with neither prefix is read both ways, and a path that names items of two packages is refused (`krs::exec::rule`).
A label is exact or a unique suffix.
`--stop-count N` ends the run at its Nth arrival at a stop instead of its first (it needs a stop to count): the run passes each earlier arrival by resuming from it, so nothing in the definition counts, and its steps and trace are those of the uncut run, as is its coverage but for an equation instance the uncut run serves from its memo, which a later piece evaluates again and counts once more.
The status line names the stop it ended at by a name the flags accept (``stopped after 11 steps, after `crate::boundary` (stop 3 of 3)``); a run that ends on its own before the Nth arrival reports that end, and the status line (`2 of 3 stops reached`) and `--output json` (`stops`) say how many arrivals it counted; `--depth` stays a bound, so a run that reaches it first is `depth-bound`, never `stopped`.
A proof ends a path `indeterminate` at the first state whose term matches the claim's right-hand side but whose condition is not decided there, and reports that state; it does not step past it, so a claim whose right-hand side is decided only where it recurs later in the run is not proven ([proof verdicts](/k-rust/compatibility#proof-verdicts)).
`--trace` prints each rewrite step with its rule label and authored source.
`run --coverage` lists the rules and equations the run used, each by its KRS item (or its K label where it has none) and authored source, with the k-rust predicates that hold of it, each under its own name: `matched` (the run began to decide its condition for an instance its left-hand side matched), `applied ×N` (N applications: a step by the rule built a successor, found the step undefined, or proposed the successor of a step a stop rule ended the run before; an instance of the equation gave a result), and `committed` (a path took the rule's step), printed beside `applied ×N`, whose N counts applications, not commits.
The sentences of K's builtin modules, and those a compiler pass generated from no authored source with neither a KRS item nor a label, are counted on a last line; `--output json` lists every sentence in `coverage.rules`, with its K label, `UNIQUE_ID` and each predicate, beside `coverage.offered`, which says whether rules only offered are listed.
`run`, `search`, and `prove` print configurations through the definition's grammar by default (`--output pretty`, as `krun --output pretty` prints them), and `--color auto|always|never` colours them from the productions' `color` and `colors` (`auto` colours only when standard output is a terminal and `NO_COLOR` is unset); `parse` prints KAST by default, and `--output program` prints the program back through the grammar, as `kast --output program` does.
`--output kast`, `json`, or `kore` selects the other formats (`none` prints no configuration from `run`).
A run that ends stuck, at the depth bound, or undefined exits 0; a proof exits 0 only when every selected claim is `proven` or `trusted` (a `trusted` claim is assumed, never proven, and the summary line counts it separately); an inconclusive result or an error exits 1, and a usage error exits 2.
When the definition declares an exit cell (`#[k::cell(exit)]`), a completed run instead exits with that cell's final value, as krun does (the OS keeps its low 8 bits), so a script that must tell it from an error reads `--output json`.
A definition with a `stream = "stdin"` cell reads standard input into it before the first step; `run` writes what its `stream = "stdout"` cell holds to standard output before the configuration, and `--output json` reports it as `stdout` instead ([console I/O](/reference/language#console-io-and-the-exit-cell)).
`run` and `search` write each line that `io::log` logs to standard error, one per line and before their own report, as `krun` and `krun --search` do on K's LLVM backend; `--output json` also reports them as `log`.

The current commands are `fmt`, `check`, `expand`, `emit-k`, `build`, `parse`, `run`, `search`, `prove`, and the [corpus loop](#the-corpus-loop)'s `kink`.

## Inputs by name

```console
krs run --package my-semantics --definition main --case cases/boot.toml
krs run --package my-semantics --definition main --input 'pc=256' --input 'rom={"$file": "boot.bin"}' -c 'memory=.Map'
```

A definition's inputs are the parameters of its `#[k::init]`, and `run` and `search` bind each one by its Rust name (`rom`) or its configuration variable's K name (`ROM` or `$ROM`), from whichever option gives it.
`--case FILE` binds the inputs a case document gives: a `.toml` file whose `[inputs]` table, or a `.json` file whose `inputs` object, holds one value per input by name; any other top-level key is refused.
`--input NAME=JSON` binds one input to a JSON document, and may be repeated.
A value of `--case` or `--input` is a document of the typed encoding below, read at the parameter's declared type, element types included, so no K text is needed; `{"$text": ..}` and `{"$text-file": ..}` give K text instead, parsed as `-c` text is.
A file that a document names is read relative to the document that names it: the case file's directory, the directory of the data file that includes it, or the working directory for an `--input` document.
FILE, `--case`, `--input`, and `-c` are bound in that order, and a parameter that any two of them bind is bound twice and refused; every parameter must be bound, the main parameter by FILE or by name.
A refusal names the input, its declared type, the position inside the document, and the reason.
A value that applies a function (`{"$call": ..}`) is the definition's computation: the configuration holds the application, which is evaluated when the first state is simplified, before the first step, so `--depth 0` shows its value; an application that has no value leaves no initial state, and the run ends `undefined` after 0 steps, naming the application.
A `Float` input runs under `run` and `search`, but the corpus tool kink refuses a test state that holds a `Float` value.

A case for a definition whose inputs are a `Map<Int, Int>` memory, a `Bytes` ROM, an `Int` program counter, and an `entry` of a declared sort:

```toml
[inputs]
memory = { "$data-file" = "data/memory.toml" }  # "0x0100" = 0, "0x0101" = 195, ...
rom = { "$file" = "data/boot.bin" }             # the file's bytes, unchanged
pc = 0x100
entry = { Load = { addr = 2, len = 3 } }        # the constructor Instr::Load of Op
# pc = { "$call" = { "Boot" = { n = 0 } } }     # Boot(0), evaluated before the first step
```

### The encoding

This section is the normative statement of the encoding.

A *document* is a value of the JSON data model: null, a boolean, a number, a string, an array,
or an object. A TOML document is first converted to it (`toml_document`): integers and
booleans, strings, arrays and tables as themselves, a finite float as a number, a NaN or an
infinity as `{"$float": "NaN"}`, `{"$float": "Infinity"}` or `{"$float": "-Infinity"}`, and a
datetime is refused, since it has no reading as a term. A JSON text is read with duplicate
object keys refused (`json_document`); a TOML parser refuses them itself.

A document is decoded at a *position*. A position is a declared type: a sort and, for a
collection, its element types (`Map<Int, Int>`, the type of the parameter or of an element
inside it). A position is *untyped* where the declared type says nothing: a `K` sort, the
elements of a collection whose element types are not declared (the field of a constructor
declared `List`, the elements of `$list`), and the field of a sort no KRS declaration names.

Every document has at most one reading at a position. Shorthands are read only where the
position's type decides them; elsewhere a *tagged form* states the reading. Where a shorthand
has two readings at a position, the document is refused and the message names the tagged
form of each reading. The decoder refuses rather than guesses.

#### Tagged forms

A tagged form is an object with exactly one key, which starts with `$`; no Rust identifier
does, so a tag never collides with a constructor or field name. An object with a `$` key and
other keys is refused. A tagged form means the same at every position, and one whose term is
of a sort that is not at most the position's sort is refused.

A map key is not a Rust identifier, and one that starts with `$` (a `String` or token key)
would make the object shorthand of a `Map` a tagged form: such a map is written in the pairs
form, `[["$x", 1]]`, and the refusal of the object says so.

| form | value | where |
|---|---|---|
| `{"$text": "K text"}` | the text, parsed at the parameter's sort as `-c` parses it | a whole input only |
| `{"$text-file": "path"}` | the file's UTF-8 text, as `$text`; parse locations carry the file's name | a whole input only |
| `{"$file": "path"}` | a `Bytes` of the file's bytes, unchanged | anywhere `Bytes` fits |
| `{"$hex": "00ff1a"}` | a `Bytes` of the bytes the hex digits spell (an even count, either case, no separators) | anywhere `Bytes` fits |
| `{"$data-file": "path"}` | the document the file holds (`.json` or `.toml`, by extension), decoded at this position | anywhere |
| `{"$string": "text"}` | a `String` | anywhere |
| `{"$int": "-0x1f"}`, `{"$int": 31}` | an `Int`: a string by the integer grammar of the `Int` row below, or an integer | anywhere |
| `{"$float": 1.5}`, `{"$float": "1.5f"}` | a `Float`: a number read as at `Float` (below), or the value a K `Float` literal names | anywhere |
| `{"$token": "text"}` | a token of the position's sort, which is a token sort | a token sort |
| `{"$token": {"sort": "Id", "text": "x"}}` | a token of the named token sort | anywhere |
| `{"$list": [..]}`, `{"$set": [..]}`, `{"$seq": [..]}` | a `List`, a `Set`, a K sequence, of untyped elements | anywhere |
| `{"$map": [[key, value], ..]}` | a `Map` of untyped keys and values | anywhere |
| `{"$call": {"path::f": fields}}` | the application of the function `f` to its arguments | anywhere |

A token's text, as `$token` or as a shorthand, is not checked against its sort's lexical
syntax: it denotes the domain value of that sort with that text, a term of the sort, even
where no K text of the definition spells it (`"top"` at a sort whose tokens match
`@[a-z]+`), while `$text` of the same text fails to parse.

A path in `$file`, `$text-file` or `$data-file` is relative to the document that holds it
(the case file, or the data file that includes it), and the decoder reads no file itself: the
caller's `InputFiles` resolves and reads it. A `$data-file` that includes itself, directly
or through others, is refused naming the cycle.

#### Constructors and functions

A constructor is written `{"Name": fields}`, with `fields` an object by field name or an array
in declaration order (a tuple variant's fields are named `0`, `1`, ..), and `[]` or `{}` for
none; at a position of a declared sort a bare string `"Name"` is a nullary constructor.
`Name` is the declaration's path or a `::`-aligned suffix of it (`Register::A`, `A`), resolved
among the constructors whose result sort is at most the position's sort (among all
constructors at an untyped position); a name that selects several is refused naming them.
Each field is decoded at its declared sort, with no element types: a field declared `List` has
untyped elements.

A function is applied with `$call`, its arguments written as a constructor's fields and
resolved among the function productions whose result sort is at most the position's sort. A
function written in the constructor form, and a constructor under `$call`, are refused: a
reader of a case sees which parts are data and which are computed. Any function may be applied,
partial and `internal` ones included, as the initializer's body may apply them; the
configuration holds the application, which the definition's equations evaluate when the first
state is simplified, before the first step.

#### Shorthands

| position | shorthands |
|---|---|
| `Int` | an integer; a string of an optional `-` and decimal digits, or of `0x`, `0o` or `0b` and digits of that base (for values beyond 64 bits, and for hex); a number with a fraction or an exponent is refused, since JSON delivers an integer beyond 64 bits as one and it would be rounded |
| `Bool` | `true`, `false` |
| `String` | a string |
| `Float` | a number, or a string that is a K `Float` literal; an integer is its binary64 value when binary64 holds it exactly and is refused otherwise; a number with a fraction or an exponent is its binary64 value, but one with an integral value of 2^64 or more, or of -2^63 or less, is refused, since a JSON reader delivers an integer it cannot hold as such a number, already rounded (write it as a K `Float` literal) |
| `Bytes` | an array of integers in `0..=255`; a bare string is refused, since its byte encoding is not determined |
| a token sort (`Id`, a `#[k::token]` sort) | a string, the token's text |
| `List<E>`, `Set<E>` | an array of documents at `E`; a `Set` with two elements that decode equal is refused |
| `Map<K, V>` | an object, each key read at `K` from its string (an `Int` by the integer grammar, a `String` verbatim, a `Bool` from `"true"` or `"false"`, a token's text, a nullary constructor's name) and each value at `V`; or an array of `[key, value]` pairs; two keys that decode equal are refused |
| a declared sort | a constructor form; a bare string: a nullary constructor, a token of a token sort at most it, or a `String` where `String` is at most it; a boolean where `Bool` is; a number where `Int` or `Float` is (below); an array or an object where a collection sort is, as at that sort with untyped elements |
| untyped | an integer (an `Int`), a boolean (a `Bool`), a number with a nonzero fraction (a `Float`), a constructor form, a tagged form; a bare string, an array, a number with an integral value written as a float, and any other object are refused as undetermined |

At a declared sort that is no builtin, the document's JSON type decides the builtin, as at an
untyped position: a string is never an `Int` or a `Float` there, so `"12"` at `Val`, with
`Int` and `String` subsorts of `Val`, is the `String` `"12"` (an `Int` beyond 64 bits is
written `{"$int": ..}`). A number is an `Int` where `Int` is at most the sort and a `Float`,
read as at `Float`, where `Float` is and `Int` is not. Where both are, an integer is an `Int`,
a number with a nonzero fraction a `Float`, and a number with an integral value written as a
float (`2.0`) is refused as undetermined, since JSON delivers an integer beyond 64 bits so:
the `Float` is written `{"$float": 2.0}`. A map key, which is always a string, is read at its
sort by every reading of the strings the `Map` row lists, so `"12"` as a key at `Val` reads
as an `Int` and as a `String` and is refused; such a map is written in the pairs form.

Two map keys or set elements that decode equal are refused because K's concatenation of two
maps that bind one key, or of two sets that share an element, has no value: keeping either
binding would accept a document that denotes no term, and would let `{"1": 2, "01": 3}` mean
a map that the text `1 |-> 2 1 |-> 3` does not.

A decoded value is still checked where a parsed one is: the configuration assembler requires
its sort to be at most the variable's declared sort, and every part of a collection to fit the
declared element types. The decoder's own checks make the refusal earlier and name the
position inside the document.

Not in the encoding: `$text` inside a value, sort-parametric productions (refused as
`ValueIndex::ctor` refuses them), and console input.

## The corpus loop

```console
krs kink results --package my-semantics --definition main
krs kink run --package my-semantics --definition main --full --output verdicts
krs kink emit --package my-semantics --definition main --check
```

`krs kink <verb>` runs the corpus loop of [kink](https://github.com/midnightntwrk/k-rust/blob/main/kink/README.md#using-kink-flow), k-rust's mutation tester, over the package's corpus, a directory `kink/` beside its `Cargo.toml` (`--corpus DIR` names another).
The verbs are kink-flow's, with kink-flow's options and its JSON documents: `check` admits the definition and every case, and resolves every mutation without running one; `results` reports each case's class and the rules its run matched and fired; `run` searches for a case that kills each mutation (`--full`: every case that does); `report` prints the last run's document again, as that run printed it, without building the package; `query` checks patterns of interest on each case; `fuzz` looks for the hole values of a case template that kill a mutation, match or fire a rule, or hit a pattern.
The corpus holds `FLOW.toml`, kink-flow's manifest, whose `[spec]` is `krs = { definition = "main" }`, the facet the corpus is for, which must be the one `--definition` selects; its cases, as program files or as case documents of the [typed encoding](#the-encoding) under `cases/`; mutations as K patches in `mutations/<topic>.toml` (else `MUTATIONS.toml`); `PATTERNS.toml` for `query` and `TEMPLATES.toml` for `fuzz`; and `definition.k`.
A K corpus (`[spec] entry = ..`) is refused, naming `kink-flow`, which runs it; a corpus of another facet is refused naming both facets.

Every verb but `emit` and `report` builds the package in process, as `emit-k` does, and kink judges `kink/definition.k`, which must hold exactly that emission: a command finds it `unchanged`, or writes it and says `written` in the document's `definition` object.
Writing it cannot change what a mutation means: a mutation is resolved against the current K on every command and refused when the text it replaces changed.
With `--locked` a command that builds the package refuses a stale `definition.k` instead (stage `definition`, reason `definition-stale`), and `krs kink emit --check` writes nothing and exits 1 when it is stale: the check a CI runs before trusting committed verdicts; `krs kink emit` writes it.
`report` builds nothing and judges no `definition.k`, so it takes no `--locked`.
Every rule a document names gains `krs = {item, package, file, line, column, kind, claim_helper}`: the Rust item the `// KRS` line above the sentence in `definition.k` names, and the position of the sentence's authored source, as `--trace` shows it; a rule KRS generated from no item has `null` there.
A specification diagnostic, a run's short-circuit reading and a query witness, which name compiled rules by label, gain `krs_rule` and `krs_observing_rule`, `krs` inside the reading's `rule`, and `krs_rules` where the label is one the emission wrote.
A claim helper (an equation of a function only claims apply) that no case matched has its own status in `results`, `claim-helper`, not `uncovered`: it serves the claims, which `krs prove` checks, and not the runs a case makes; a claim helper some case matched (a typed input can apply any function) is `covered`.
A function nothing applies is reached by no program text either, but no claim accounts for it, so it stays `uncovered`.
`results` lists a case in a rule's `matched_by` when kink's baseline run of the case, which follows every path, `matched` the rule, as `run --coverage` names the predicate, and in its `fired_by` when the run fired it: some path `committed` the rule's step, for a rewrite rule, or the run `applied` it, for an equation, whose application is no step; a case that is not `comparable` is listed under no rule.
`--output verdicts` (for `results`, `run` and `report`) prints kink-flow's deterministic rendering, which names each rule by its item and gives each case the rules that list it as `matched` and `fired`.
`fuzz --matched RULE` and `fuzz --fired RULE` take the rule's label or a suffix of whole components of it (`plus_zero` for `nat--plus_zero`), as a mutation's `rule` anchor does.
A case's typed inputs are read by the encoding `run --case` reads, except `$text` and `$text-file`, which are K text and are written under the case's `variables` instead.
A case's program file binds the main parameter as `run FILE` binds it, whatever the parameter's K name, so `[[program]] files = "roms/*.gb"` with the other parameters under `inputs` is one case per ROM; inline `text` under a `Bytes` main parameter is refused, since a `Bytes` value has no text reading (`$hex` under `inputs` gives bytes inline).
A case's digest holds the SHA-256 of its program's bytes, whichever way they bind.

The selection options are those of the other commands and may come before or after the verb; every other option is the kink-flow verb's own.
Every command that builds the package builds it in process, so `krs kink` takes no `--no-reuse`.
Exit status is kink-flow's: 0, 1 when anything is refused (the document says what and why), and 2 on a usage error.
A package `krs` refuses, from an unknown package or facet to a failed emission, prints krs's diagnostics on stderr and exits 1: a kink-flow verb prints its document with its `spec` refused at stage `krs-build`, reason `krs-refused`, and `krs kink emit` prints its own document (`krs-kink-emit`), whose `definition.status` is `null` and whose `refusal` says why.
`krs kink --help` lists the verbs, their options and the corpus layout.

## Read failures by stage

- Rust/rust-analyzer errors cover ordinary syntax, imports, types, macro expansion, and some precisely authored attribute spans.
  A proc macro can report an error only as a message without a code, so in raw `cargo` and rust-analyzer output a KRS macro error carries its code in front of the message, as `[krs::syntax::invalid-color] message`; `krs` commands print the same error as `error[krs::syntax::invalid-color]: message`.
- KRS analysis errors cover definition-wide identities, sort and grammar consistency, rule shapes, and overlap.
- K frontend errors are translated through emitted source maps when an exact authored interval exists.
- native definition-check errors come from `check` and `build` and point at the authored item whose sentence the checker rejected.

Macro islands are not ordinary Rust expressions, so editor behavior is bounded.
The repository's compatibility probes establish exact rustc and rust-analyzer selection for authored syntax tokens and exact K/source-sidecar translation for covered cases; they do not promise IDE understanding of every generated symbol or every DSL token.
