# Daily workflow

{/* tour-concepts: diagnostics-lsp formatter-comments */}

KRS has a short, staged command line.
Use the earliest command that can answer the question you have; later stages add generated artifacts and backend prerequisites.

## Edit and check

```console
krs fmt --check --manifest-path Cargo.toml
krs check --package my-semantics --definition main
```

`fmt` canonicalizes KRS DSL islands while leaving ordinary Rust to the Rust formatter.
It can format paths or stdin, and `--check` reports drift without rewriting files.
Without paths it selects what `cargo fmt --all` selects, restricted to workspace members:
each member target's root and the files of the modules it declares,
so fixtures beside a target are left alone unless named explicitly.
Inside DSL macro bodies, use line comments: non-doc `/* ... */` comments are rejected because procedural macros cannot recover them reliably.
The default aligned trailing-comment layout is provisional; `--trailing-comments gutter` selects the other implemented policy.

`fmt` lays `k::rules!`, `k::equations!`, and `k::claims!` bodies out within the Rust formatter's `max_width` (100 unless a `rustfmt.toml` sets it), indentation included.
The one-line rows of a block align their labels, `=>`, and `where` in columns.
A row too long for its line is laid out on its own and widens no column: its label on one line, then its pattern and `=> result` indented, and `where` on a line of its own.
A row that fits only without the alignment's padding stays on one line, unaligned.
Cell records put one cell per line.
Inside a term, a group too long for its line breaks from the outside in, as the Rust formatter breaks calls and struct literals: one argument, field, or element per line, indented, and an inner group breaks only when it still does not fit.
An or-pattern too long for its line puts one alternative per line with a leading `|` under the first; in parentheses, as in `op @ (A | B)`, it hugs them.
A condition breaks before `||`, else before `&&`, else before a comparison (`==`, `!=`, `<`, `<=`, `>`, `>=`), one level deeper.
An operator stays on the line that ends the operand before it when that line ends at or before the operator's indentation, as when a record or call before it breaks anyway (`} != rhs`) or the operand is short (`x != Record {`), and the operator and the first line of its operand fit there; a line comment beside the operator keeps it at the start of its line, and a `=> result` whose first operand must break stays on the pattern's line, as for that operand alone.
A call whose one argument is a delimited term (`f(..)`, `Record { .. }`, `m![..]`, or `[..]`) and which does not fit on its line hugs it, as the Rust formatter does: the call's delimiters stay on the argument's first and last lines, `list::item(Entry {` / fields / `}),`, and only the argument breaks; an argument with an alias, an operator, or a comment does not hug.
A `where` list too long for its line puts one binder per line under `where`.
A one-line attribute too long for its line breaks inside its arguments; one written over several lines keeps its layout.
`fmt` never reorders a token, and the only token it adds or removes is a list's trailing comma: as the Rust formatter does, a list broken over lines ends with a comma and a list on one line has none, whatever the source wrote.
A record's rest (`..`, `..base`) takes none, as in Rust, while a bracket's `..` or `rest @ ..` is an element and takes one; a `where` list takes none before its `;`, and `(a,)`, whose comma makes a 1-tuple, keeps it.
A line comment inside a delimited group keeps its place and breaks the group; any other comment of a clause moves to the lines before the clause, and so do all of the clause's comments when one of them would otherwise move before a comment kept in place.
Only a doc comment, a literal, or another token longer than the line leaves a line of a KRS body over the width.

`check` resolves Cargo metadata and selected facets, builds and runs the generated collector, validates descriptors, performs semantic analysis, and then judges the definition as every later command that needs no K toolchain would: it emits the K `emit-k` writes, with its symbol and source maps and their checks, and for each native route it consults the route's capability table and runs k-rust's preparation, definition checks, and compilation exactly as `build` does.
It does not render the JSON artifacts `emit-k` writes beside the K (the two maps, and with `--ir` the descriptor bundle and the Semantic and Definition IR), because rendering cannot refuse what emission accepts: the encoder fails only on a map key that is not a string or on a value whose serialization fails, and these types hold neither.
On the `native-rust` route, which `build --backend haskell`, `run`, `search`, and `prove` share, it also loads the compiled definition as the run commands do, including each spec module's proof definition.
It reports the same errors and warnings those commands report, but writes no artifacts.
A passing `check` therefore means that `emit-k`, `build` on either backend, and the run commands accept the definition; what remains are refusals of one invocation, such as a program that does not parse, `search` on a definition with `stream` cells, or `prove --spec-module` naming no spec module.
The exception is a feature one route's capability table lacks and another route builds, for example an existential rule result, which `native-llvm` refuses and `native-rust` runs: that is the documented limit of one route, not a fault of the definition, so `check` judges the routes that build it, passes, and warns with the refusal (`krs::capability::unavailable`), naming the commands of the route that refuses and of the routes that build it.
When every route refuses the definition, or a route's compile does, `check` fails with that refusal and a note naming the commands of that route.
`--backend llvm` or `--backend haskell` narrows the judgement to `emit-k` and that backend's route, so `check --backend haskell` passes for a definition only the symbolic route runs, and `check --backend llvm` for one only concrete execution runs.
The routes compile concurrently, so judging both costs about the time of the slower compile.
Rust errors from the collector build are reported at authored source spans when Cargo provides a mappable primary span.
They keep rustc's notes and help, and a suggested replacement in authored source is spelled out as the edit it makes (``remove `()` at src/lib.rs:48:28``); a note or help that points only into macro-generated code is left out, because it describes tokens the author did not write.
Under `deny(warnings)`, rustc also reports as unused an import that only a failed KRS item uses, because that item's expansion was withheld.
`check` leaves such an error out when the failed item, in the import's module, names the import, and reports every other unused import, one per name; a glob import is always reported, since its names are not known without resolving it.
`cargo check` and rust-analyzer still show it.
`check`, `expand`, `emit-k`, `build`, and the run commands render human-readable diagnostics on stderr by default, including their codes, notes, help, and authored source snippets when the source revision matches.
Pass `--message-format=json` when a tool consumes diagnostics.
Every command that lowers the definition (all but `fmt`) reports the definition's warnings, such as an uncovered total function or a `program` production programs cannot contain; `check` and `build` add those of the backend routes they judge, and `prove` those of the claims it trusts.
It reports them whether or not the command then succeeds: a failing command prints the warnings of the stages it completed before its error, so a `parse` that fails on a production placed outside program syntax shows the `krs::partition::not-program-syntax` warning that explains it.
`check`, `expand`, `emit-k`, `build`, and the run commands warn about each quoted hook and `k::raw_k!` sentence of a package that sets `allow-raw-k = true`; `--profile strict` overrides every package's `profile` and turns those warnings into errors, so CI can refuse the [raw K escapes](/reference/language#raw-k-escapes) a package allows.
In JSON mode, every diagnostic is one schema-2 JSON envelope line on stderr, with its stage, code, `kind`, severity, and message; collector failures have stage `analysis` and a `krs::collect::*` code.
`kind` says who can act on it: `author` for a mistake in the program, the manifest, or the command line, `internal` for a KRS bug (human output prints its message as "internal error (a KRS bug): ...", or "internal warning (a KRS bug): ..." for a warning), and `environment` for files, Cargo, the toolchain, or a stale build.
`authored_range` is the exact authored file revision and byte range, or `null` when no authored text is the diagnostic's subject; then `item`, when present, names the item it is about.
`labels` lists related authored locations, each a `range` with an optional `message`, such as the occurrence that contradicts a binder's declaration; human output underlines each in its source.
Only a failure without a code, such as a usage error or a collector that crashed, is a prose line, with the process status and stderr detail.
Run ordinary `cargo check` when you want Rust-only feedback on names, types, imports, and macro expansion while editing.

## Inspect the lowering

```console
krs expand --package my-semantics --definition main
krs emit-k --package my-semantics --definition main --output target/krs-k
```

`expand` prints the deterministic explicit Rust-facing reference surface.
It reads every module file of the package's library crate, from its root through each `mod name;`, and replaces each readable form by its long form in the file and module that hold it, so the printed package keeps the authored module structure, and every path the authored items write resolves as it did.
A long form also writes paths the readable form leaves implicit, such as a binder's sort: `expand` prints such a path only where the source shows it compiles there (an item of the package whose modules and own declaration are visible from the printing module, the path the clause writes, or a dependency's module that a `use` or a readable macro of the crate names), and otherwise refuses the package, naming the item.
Stdout does not say which file it holds: a consumer that overlays it on the crate root must check that the crate root is the one file that changed, or use `--output`.
When exactly one file changes, `expand` prints it on stdout (the crate root when none changes); when several do, it refuses and asks for `--output`:

```console
krs expand --package my-semantics --definition main --output target/krs-expanded
```

`--output` takes an absent or empty directory and writes only the files the expansion changes, each at its path relative to the package, such as `target/krs-expanded/src/rules.rs`, and stdout lists those paths, one per line.
The printed package is the authored one with exactly those files replaced: copy the package (a relative `path` dependency must still reach its package from the copy), copy the directory over it, and `krs check` and `krs emit-k` judge the printed source as they judge yours.
`emit-k` writes the generated K definition with the two maps that carry it back to your source: `symbols.json`, from stable identities to emitted K names, and `sources.json`, from generated ranges to authored ones.
Claims go to a separate `spec.k` beside `definition.k`, the layout `kompile` and `kprove` expect.
These outputs are audit artifacts, not a second source file to edit.

```console
krs emit-k --package my-semantics --definition main --ir --output target/krs-k
```

`--ir` also writes KRS's three internal levels, `descriptor-bundle.json`, `semantic-ir.json`, and `definition-ir.json`, for a tool that reads them, such as a harness that compiles `definition-ir.json` in process.
They are KRS's own representations, versioned together and read back only at the same schema version, so the default leaves them out.
An emission writes only its own selection: it removes from the output directory any `emit-k` artifact an earlier emission left there, such as the IRs of an earlier `--ir` run or a `spec.k` the definition no longer needs.

The lowering page names the descriptor, semantic, definition, K, symbol, source, and KORE boundaries in detail.
When a generated K range has an exact source-map entry, diagnostics should point back to the hash-checked authored bytes rather than expose a generated collector path.

## Build a backend target

```console
krs build \
  --package my-semantics \
  --definition main \
  --backend llvm \
  --output target/krs-native
```

`build` continues through K frontend and selected backend compilation.
The LLVM backend executes but does not prove, so an LLVM build omits the definition's claims and says how many it omitted.
Successful `check`, `emit-k`, and `build` commands reuse a previous result when the command options (for `emit-k`, `--ir` among them), collector executable, and files read by the collector are unchanged.
A reused command returns the same stdout and restores any missing or modified output files.
Each command keeps one previous result, so alternating `emit-k` with and without `--ir` replaces it each time, and neither is reused after the other has run.
Pass `--no-reuse`, or set `KRS_NO_REUSE=1`, to run the collector and later stages again.

The generated collector compiles KRS's own crates and the libraries they call at opt-level 3, and the definition's crates unoptimized and without debug information.
An override names a crate, so a dependency of the definition that shares one of those crates' names is optimized too.
Each collector has its own directory, with its own Cargo target, under the project's target directory, keyed by the generated package and the selection: the definition, the root and dependency packages with their versions and features, the cfg and registration settings, and KRS's own paths.
The first command with a new selection compiles KRS's crates once in a new collector directory, and the first after upgrading KRS compiles them again; after an edit, Cargo recompiles only the edited crates and the crates that depend on them.
An earlier collector directory stays until the target directory is cleaned.

The optimization repays its first compilation over the commands that follow it.
A one-shot run in a fresh target directory, such as a CI job, can compile those crates unoptimized instead, as KRS's own fixture tests do: krs builds each collector from its directory under the target directory, Cargo reads the configuration files of that directory and of every directory above it, and a configuration's profile takes precedence over the manifest's, so a `<target>/.cargo/config.toml` that sets `opt-level = 0` for each crate the generated `Cargo.toml` optimizes applies to every collector under that target.
The optimization level changes no output.

```toml
# <target>/.cargo/config.toml: one table for each [profile.dev.package.<name>] of
# <target>/krs/collectors/<digest>/Cargo.toml
[profile.dev.package.krs-collector]
opt-level = 0

[profile.dev.package.syn]
opt-level = 0
```

## Run, search, and prove

```console
krs run --package my-semantics --definition main prog.imp -c env='.Map'
krs search --package my-semantics --definition main prog.imp
krs prove --package my-semantics --definition main --claim branching
krs parse --package my-semantics --definition main --sort Stmt prog.imp
```

`run`, `search`, `prove`, and `parse` play the roles of K's `krun`, `krun --search`, `kprove`, and `kast` on the emitted definition.
They share the collection and lowering stages of `check`, then compile the Definition IR with the k-rust backend that krs links, over the symbolic KORE dialect, so they take no `--backend`.
`prove` does this in a worker process that runs the krs executable, so a crash of the worker while it proves a claim costs only that claim ([proving a batch of claims](/verification/reachability-claims#proving-a-batch-of-claims)).
Their results are never reused from an earlier invocation, but the compiled definition is: the first command compiles the Definition IR and keeps the compiled stage in a per-user cache, `${XDG_CACHE_HOME:-~/.cache}/krs/compiled-stages/v1` (or the directory `KRS_STAGE_CACHE_DIR` names), and a later command on the same Definition IR loads it instead of compiling again.
An entry is keyed by the digest of the Definition IR's canonical JSON and the `krs` executable, which links k-rust, so a changed definition or `krs` build (k-rust included) compiles again; an entry unused for 30 days is deleted.
`prove --spec-module NAME` also keeps the proof definition it compiles for that author spec module, under the same key plus NAME (the Definition IR digest covers the spec module's content), so a second proof of an unchanged spec module compiles neither.
`--no-reuse` or `KRS_NO_REUSE=1` compiles again and replaces the entry.
A cache directory inside the package's Cargo workspace is never used, so an entry is never committed with the package: each command then warns (`krs::exec::stage-cache`) and compiles the definition again, and setting `KRS_STAGE_CACHE_DIR` to a directory outside the workspace restores reuse.
FILE (or `-` for standard input) binds the main parameter of the `#[k::init]` (the one marked `#[k::config_var(.., main)]`, or the one the computation cell reads when none is marked), whatever its K name; a definition without a main parameter refuses FILE, naming every parameter to bind by name instead ([inputs by name](#inputs-by-name)).
Where the main parameter's type is exactly `Bytes`, FILE is its value: the file's bytes, unchanged, as `{"$file": ..}` gives them.
Otherwise FILE is text, parsed at the parameter's sort: as a program, at the start position of its sort, where that parameter is `$PGM`, and as `-c` text of that parameter otherwise; a file that is not UTF-8 text is refused, naming the parameter and its type.
`-c NAME=TEXT` binds a parameter by its Rust name (`env`) or its configuration variable's K name (`ENVIRONMENT` or `$ENVIRONMENT`); FILE together with a binding of the main parameter by name binds it twice and is refused.
`run` follows one path, taking at a state where several rules apply the first of them in item order ([intended nondeterminism](/reference/language#intended-nondeterminism)), and `search` returns the set of reachable final states; `--mode` selects `all`, `one-step`, or `one-or-more-steps` instead.
`prove` proves every claim, or each `--claim` label given as the exact label or a unique suffix; `--spec-module NAME` proves the claims of an author spec module (`kprove --spec-module`) instead of the generated `<MAIN>-SPEC` ([spec modules](/verification/reachability-claims#spec-modules)).
`--depth N` bounds rewrite steps; evaluating functions, and applying `anywhere` rules, which are equations, is not a step.
A step is a step of the compiled definition: the heating and cooling steps that strictness and contexts generate count, so the depth one KRS program reaches changes with how KRS compiles it, and a depth is a budget, not a point of the program's run; a run is observed at a point by a stop at a named rule and a stop count (below).
The arrivals at a rule the author wrote are that rule's steps, which the compilation does not change; the arrivals at a context or a strict production are the heating and cooling steps the compilation generates for it, which change with the compilation as the depth does.
`run --stop-before NAME` ends the run at a state whose one successor is a step by a rule NAME selects, and `--stop-after NAME` at that step's successor; a step by such a rule from a state with several successors stops nothing, and the run goes on past it.
The status line names each rule the run went on past so, with the steps to the first state it was passed at (``; went on past `crate::tick` after 0 steps``), and `--output json` lists them as `passed_stops` (`rule`, `depth`), as `krs cases` and `krs compare` do for a case's run, since the run's end is then not that of a system that stops at every step of the rule.
The successors are those the run reads: a rule whose condition reads an application with no value (a partial function defined by its equations alone, none of which applies there) does not apply, so it gives the state no successor beside the stop rule's step.
Each flag is repeatable, and a run that ends so is `stopped`.
NAME is a KRS item or a K label.
An item is named by `crate::` and its path in the root package (`crate::tick`, `crate::ppu::frame_end`), never by the root package's own crate name or `self::`, or by a dependency's crate name and its path there (`lang::step`), and selects every rewrite rule the item lowers to (a context's heat and cool rules, a strict production's); a path with neither prefix is read both ways, and a path that names items of two packages is refused (`krs::exec::rule`).
A dependency's crate name is the crate name of its library, by which Rust names the crate: its Cargo package name with `-` written `_`, or the name its `[lib]` section gives the library.
It is that name whatever a depending package's manifest renames the dependency to: with `isa = { package = "my-isa" }` the root's source calls the crate `isa`, but its item is `my_isa::step`, and `isa::step` is refused naming `my_isa::step`, unless the root package has an item at `isa::step`, which the path also reads as.
A name in a stop flag, a case document or an end document must denote one item to every reader of the definition and reach every item of it, which a rename, a property of one depending manifest, does not: another package may rename the dependency otherwise, and a package the root reaches only through another has no name in the root's source.
A package sets its library's name itself, so the name is the same to every reader: where package `my-isa` has `[lib] name = "isa_core"`, its item is `isa_core::step`, and `my_isa::step` is refused naming the library's crate name `isa_core`.
Two packages of a definition whose libraries have one crate name (`foo-bar` and `foo_bar`, or two libraries a `[lib]` section names alike) are refused when the definition is collected (`krs::collect::duplicate-crate-name`), since that name would name neither package's items alone.
A label is exact or a unique suffix.
`--stop-count N` ends the run at its Nth arrival at a stop instead of its first (it needs a stop to count): the backend counts the arrivals along the path and takes each earlier one as any other step, so nothing in the definition counts, the run is one request whatever N is, and its steps, trace and coverage are those of the uncut run up to where it ends ([stop count](/k-rust/compatibility#stop-count)).
The status line names the stop it ended at by a name the flags accept (``stopped after 11 steps, after `crate::boundary` (stop 3 of 3)``); a run that ends on its own before the Nth arrival reports that end, and the status line (`2 of 3 stops reached`) and `--output json` (`stops`) say how many arrivals it counted; `--depth` stays a bound, so a run that reaches it first is `depth-bound`, never `stopped`.

`--stop-when CELL,...=FUNCTION` makes a stop of only the arrivals at which a fact about the state holds: FUNCTION, a function of result sort `Bool` whose parameters are the CELLs in order, each a leaf cell by Rust field path, holds of the arrival's *stop state*, the state the run would end at there (the state before a `--stop-before` rule's step, the successor of a `--stop-after` rule's).
The run ends at its Nth such arrival (`--stop-count`, 1 by default) and takes every other arrival as any other step, so a condition that always holds changes nothing, and the run is still one request: the backend asks the condition at each arrival, and nowhere else ([stop condition](/k-rust/compatibility#stop-condition-in-process)).
Only an arrival is asked, since an arrival at a rule the author wrote is a fact of the definition, while the states between arrivals include the compiled definition's own steps (strictness, contexts); a step by a stop rule that has another successor beside it is no arrival and is not asked.
The condition is evaluated in one fixed definition, the observer `--observer PACKAGE:DEFINITION` names (a package that depends on the definition's and that no semantics imports, as a view's observer is), or else the run's own definition, loaded a second time beside the backend that runs the path, which never evaluates it, so the question asked of every state is the same whatever the definition being run; `--observer` naming the run's own facet is that default.
An observer needs no configuration of its own: krs composes it with the definition it depends on, so `krs check` of the observer's package alone, which judges it as a definition, refuses it (`krs::analysis::configuration-count`); it is checked by the run or the case that names it, which refuses it with its diagnostics.
A read cell must be observable and below no repeated or optional cell, and its value is carried to the observer by its constructors, as a view's is.
A condition with no value at a stop state (a partial function outside its domain, a cell holding an unevaluated application) refuses the run with exit 2 (`krs::exec::stop-condition`, as every refusal of a condition is), naming the rule, the steps and the reason; an evaluation that spends `--view-budget`'s polls, or that the solver leaves undecided, ends the run `stop-undecided`, which is inconclusive (exit 3).
The status line names the condition and every arrival the run passed (``stopped after 5 steps, before `crate::tick` (stop 1 of 1, where `Apart` holds; 6 arrivals)``, or ``stuck after 9 steps, 0 of 1 stops reached (no arrival where `Apart` holds; 6 arrivals)`` for a run that ended first), and `--output json` reports them as `stops` and `arrivals` (`krs-exec/6`), `stops` whenever the run has stop rules, 0 included.
A run that ends `stop-undecided` names the rule, the condition and why its evaluation has no answer (``before `crate::tick`, undecided whether `Climb` holds (0 of 1 stops reached; 1 arrival): its evaluation stopped before it ended (it spent its budget of 100 polls), so whether it has a value is not known``), and `--output json` reports them as `undecided` (`at`, `rule`, `reason`, `budget_spent`): a spent budget is decided by a larger `--view-budget`, an `Unknown` answer of the solver is not, which `budget_spent` and the status line say.
A case's run that ends so has no end, and `krs cases` and `krs compare` give the same rule, reason and remedy as the reason it is inconclusive.
Each Z3 query of `run`, `search` and `prove` is bounded by Z3's own resource units, 370,000 for the first attempt and twice the previous for each of 3 retries, and by no clock, so whether a condition is decided does not depend on the host's speed or load; `--smt-resource-limit UNITS` and `--smt-retries N` change the bound, and `--smt-clock-ms MS` bounds each attempt by the clock instead.
`prove --claim-timeout SECONDS` cancels a claim's proof still running after SECONDS of wall-clock time, with the verdict `timeout` ([proving a batch of claims](/verification/reachability-claims#proving-a-batch-of-claims)).
A proof ends a path `indeterminate` at the first state whose term matches the claim's right-hand side but whose condition is not decided there, and reports that state; it does not step past it, so a claim whose right-hand side is decided only where it recurs later in the run is not proven ([proof verdicts](/k-rust/compatibility#proof-verdicts)).
`--trace` prints each rewrite step with its rule label and authored source.
`run --coverage` lists the rules and equations the run used, each by its KRS item spelled as `--stop-before` reads it (`crate::plus_succ`, or `lang::step` for an item of the dependency crate `lang`), or by its K label where it has none, and its authored source, with the k-rust predicates that hold of it, each under its own name: `matched` (the run began to decide its condition for an instance its left-hand side matched), `applied ×N` (N applications: a step by the rule built a successor, found the step undefined, or proposed the successor of a step a stop rule ended the run before; an instance of the equation gave a result), and `committed` (a path took the rule's step), printed beside `applied ×N`, whose N counts applications, not commits.
The item's path is the one `krs expand` prints, so a function's equation is named by the item the expansion writes for it, after the function and its [branch](/reference/language#branching-bodies) (`crate::expected` for the one equation of `fn Expected`, `crate::clamp_2` for the second branch of `fn Clamp`), and a stop reads that name, not the function's.
The name is the item's, so every sentence one item lowers to (a context's heat and cool rules) has it; where it does not name the item alone (two packages of one crate name each have an item at its path, or the main package has an item at the whole of a dependency item's name), the sentence's K label follows it in brackets.
The sentences of K's builtin modules, and those a compiler pass generated from no authored source with neither a KRS item nor a label, are counted on a last line; `--output json` lists every sentence in `coverage.rules`, with its `item` spelled as a stop reads it, its K label (`label`, which the list prints in brackets beside a shared name), `UNIQUE_ID` and each predicate, beside `coverage.offered`, which says whether rules only offered are listed.
`run`, `search`, and `prove` print configurations through the definition's grammar by default (`--output pretty`, as `krun --output pretty` prints them), and `--color auto|always|never` colours them from the productions' `color` and `colors` (`auto` colours only when standard output is a terminal and `NO_COLOR` is unset); `parse` prints KAST by default, and `--output program` prints the program back through the grammar, as `kast --output program` does.
`--output kast`, `json`, or `kore` selects the other formats (`none` prints no configuration from `run`).
`run --output end` prints the run's end as an end document (`halt`, `rule`, `cells`, [as `krs compare` reads one](#compare-two-ends)), on one line and alone on standard output, so that the output is a side `krs compare` reads as it is.
It is always the full end, every cell the end states: a view belongs to a comparison, and a viewed value, at its view's result sort, is no end.
At `--depth 0` it is the configured state, each input applied with `$call` evaluated to its value.
An inconclusive halt has no end, so nothing is printed and the run exits 3.
An end with no end document is refused with exit 2 and the reason.
A cell holding a part the typed encoding has no document for (an unevaluated application) is refused at its position (``the end has no end document: `cells.status`: ...``).
A stopped end whose class names no stop rule is refused at `rule`: the run names the rule it stopped after only where its `--stop-after` names select one rule or it keeps its `--trace`, and the class names a rule only by a name that selects its item alone.
A state under a constraint is refused as such, since no position holds the constraint.
The exit status of `run`, `search` and `prove` says what the caller does next ([exit status](#exit-status)).
A definition with a `stream = "stdin"` cell reads standard input into it before the first step; `run` writes what its `stream = "stdout"` cell holds to standard output before the configuration, `--output json` reports it as `stdout` instead, and `--output end` writes it to standard error, before its own lines ([console I/O](/reference/language#console-io-and-the-exit-cell)).
Such a cell holds the stream's descriptor and buffer, which are no values of its `List` type, so `--output end` refuses the end of such a definition at that cell.
`run` and `search` write each line that `io::log` logs to standard error, one per line and before their own report, as `krun` and `krun --search` do on K's LLVM backend; `--output json` also reports them as `log`.

The current commands are `fmt`, `check`, `expand`, `emit-k`, `build`, `parse`, `run`, `search`, `prove`, [`cases`](#run-a-batch-of-cases), [`compare`](#compare-two-ends), and the [corpus loop](#the-corpus-loop)'s `kink`.

### Exit status

An exit status tells the caller which action to take next, and there are four actions, so `run`, `search`, `prove`, `cases` and `compare` exit with one of four statuses:

| status | answer | the caller's next action |
| --- | --- | --- |
| 0 | yes: the run completed, the expectation is met, the sides are equal, every claim is proven or trusted | rely on the answer |
| 1 | no: a finding; the expectation is unmet, the sides differ, a claim is disproved or failed | act on the finding |
| 2 | the question could not be asked: a usage error, a refusal, or any other error, a panic or an output that cannot be written included | fix the input or the command |
| 3 | no answer: an inconclusive halt, search or verdict, a run with no one path, or a claim `indeterminate`, `depth-bound`, `breadth-bound` or `timeout` | retry with more budget or another approach |

A refusal exits 2, not 1: an end document that leaves out a compared cell, an unknown case name, inputs or an expectation that are refused, a view with no value, or a definition that does not compile makes the question ill-posed, which is no answer about the definition.
A batch exits 2 when a member is refused or fails, since its answer is then incomplete; else 1 when a member is a finding; else 3 when a member has no answer; else 0.

- `run` exits 0 when the run ends stuck, at the depth bound, undefined or stopped, 3 when it ends at an inconclusive halt (`indeterminate`, `timeout`, `interrupted`, `unsupported-hook`, `simplification-error`) or reaches several states under conditions it cannot decide (it has no one path), and 2 on any failure.
  When the definition declares an exit cell (`#[k::cell(exit)]`), a completed run instead exits with that cell's final value, the program's own status (the OS keeps its low 8 bits), which shares the numbers above: a caller that must tell the program's status from krs's reads `--output json`.
  With an expectation (`--case`), the run exits by its verdict instead, 0 met, 1 unmet and 3 inconclusive, and a refused case or expectation exits 2.
  A run that reaches its depth bound or exhausts another budget under an expectation is inconclusive (3), since it is not known to have ended: it takes no step from the state at the bound, so the definition may go on from there and end otherwise, and a state at the bound that has no successor is inconclusive too.
  With `--output end`, an end with no end document exits 2 whatever the run's own status: the end it was asked for cannot be written.
- `search` exits 0 when its set of final states is complete or it stopped at `--max-solutions`, and 3 when some path was not decided; with an expectation, it exits by its verdict, as `run` does.
- `prove` is a batch of its claims: a claim `proven` or `trusted` counts 0 (a `trusted` claim is assumed, never proven, and the summary line counts it separately), `disproved` or `failed` 1, `indeterminate`, `depth-bound`, `breadth-bound` or `timeout` 3, and `crashed` 2, since the process proving it failed and gave no answer; a failure of the batch itself, such as a definition with no claims, a `--claim` that names none, or a crash after the last claim, which leaves the batch's own checks and output unfinished, exits 2.
- `cases` is a batch of its cases: `met` counts 0, `unmet` 1, `inconclusive` 3, `refused` 2, and `ran` 0, or 3 when the case's run has no end (it halted `indeterminate`, `timeout` or another inconclusive halt, or has no one path); its JSON summary's `status` is the exit status.
- `compare` exits 0 when the sides are equal (with `--expect`, when the expectation is met), 1 when they differ (unmet), 3 when the comparison is inconclusive, and 2 when a side or the comparison is refused.
  With `--pairs`, it is a batch of its pairs, each counting what it would exit alone, and a refused pair 2; its JSON summary's `status` is the exit status.

`krs kink` exits by the same four ([the corpus loop](#the-corpus-loop)).
Every other command exits 0 on success, 2 on a usage error and 1 otherwise.
A usage error prints its message, then the usage lines of the command it names (the list of commands when it names none or an unknown one) and the command that lists the options, not the whole help.
An option value refused for itself, such as a `--case` file that is neither `.toml` nor `.json`, prints its message alone.

## Inputs by name

```console
krs run --package my-semantics --definition main --case cases/boot.toml
krs run --package my-semantics --definition main --case cases/steps.toml --case-name ld-a
krs run --package my-semantics --definition main --input 'pc=256' --input 'rom={"$file": "boot.bin"}' -c 'memory=.Map'
```

A definition's inputs are the parameters of its `#[k::init]`, and `run` and `search` bind each one by its Rust name (`rom`) or its configuration variable's K name (`ROM` or `$ROM`), from whichever option gives it.
`--case FILE` binds the inputs a case document gives: a `.toml` or `.json` file of one case, whose `inputs` table holds one value per input by name, or of named cases, one of which `--case-name NAME` selects ("Case documents" below states the format).
`--case FILE#NAME` selects the same case by its id, the spelling `krs cases` prints and `krs compare` reads, so an id copied from a batch's output re-runs that case; the name follows the first `#` after the `.toml` or `.json` file, and a case named both ways is refused.
`--input NAME=JSON` binds one input to a JSON document, and may be repeated.
A value of `--case` or `--input` is a document of the typed encoding below, read at the parameter's declared type, element types included, so no K text is needed; `{"$text": ..}` and `{"$text-file": ..}` give K text instead, parsed as `-c` text is.
A file that a document names is read relative to the document that names it: the case file's directory, the directory of the data file that includes it, or the working directory for an `--input` document.
FILE, `--case`, `--input`, and `-c` are bound in that order, and a parameter that any two of them bind is bound twice and refused; every parameter must be bound, the main parameter by FILE or by name.
A refusal names the input, its declared type, the position inside the document, and the reason.
A value that applies a function (`{"$call": ..}`) is the definition's computation: the configuration holds the application, which is evaluated when the first state is simplified, before the first step, so `--depth 0` shows its value; an application that has no value leaves no initial state, and the run ends `undefined` after 0 steps, naming the application.
A `Float` input runs under `run` and `search`, but the corpus tool kink refuses a test state that holds a `Float` value.

A case for a definition whose inputs are a `Map<Int, Int>` memory, a `Bytes` ROM, an `Int` program counter, and an `entry` of a declared sort:

```toml
[inputs]
memory = { "$data-file" = "data/memory.toml" }  # "0x0100" = 0, "0x0101" = 195, ...
rom = { "$file" = "data/boot.bin" }             # the file's bytes, unchanged
pc = 0x100
entry = { Load = { addr = 2, len = 3 } }        # the constructor Instr::Load of Op
# pc = { "$call" = { "Boot" = { n = 0 } } }     # Boot(0), evaluated before the first step
```

A case may also state the instances its run starts with: its `instances` table names optional (`?`) and repeated (`*`) cells by Rust field path, as an end document's `cells` does, each stated as an end document states it, `[]` or `[content]` for an optional cell and the array of its instances for a repeated one.
The initializer states every fixed cell's start and one instance's template for each optional and repeated cell, so the case states how many instances there are and what each holds: a cell an instance states is read at its declared type (or as K text, `$text`, parsed at the cell's sort), and a cell it does not state starts as the template says, under the case's inputs.
A Map collection's instance states its key, and no two share one; a fixed cell starts as the initializer says, so a case that names one is refused (bind other inputs to start it otherwise).
`run`, `search`, `cases` and a case side of `compare` all start from the stated instances, and a case that states none starts from the initializer's own.

```toml
inputs.pgm = { "$text-file" = "boot.s" }  # every hart runs this program

[[instances.harts.hart]]                   # two harts, keyed by their first cell `id`
id = 0
pc = 0x1000

[[instances.harts.hart]]
id = 1
pc = 0x2000
```

A case may also say how it is run and what end it expects.
Its `run` table gives the depth bound, the stop rules, the stop count and the stop condition (`depth`, `stop_before`, `stop_after`, `stop_count`, `stop_when`), each rule named as `--stop-before` names one, by KRS item (`crate::machine::boundary`) or K label; `--depth` with a case's `run.depth` is refused, since only one may bound the run, and so is every stop flag (`--stop-count` and `--stop-when` included) with a case's stops, since only one may say where it ends and a flag may not change a case's question.
The count is the case's, beside its rules, since where a run is observed depends on the program it runs.
In a document of named cases, a case's own `run` table replaces the document's `run` whole, stop rules and `stop_when` included: a case that gives only `stop_count` names no stop rule, and is refused for it.
Its `expect` table states the end: the halt, the stop rule for `stopped`, named as `run` names it, and the cells by Rust field path, each value in the encoding below at the cell's declared type.
It must state every cell it is compared on: by default every cell that is not unobservable, which `compare` may narrow to the cells it names.
The halt is never `depth-bound`, which is refused: an expectation states what the definition computes, and the state after N steps is no fact about the definition, since the depth counts compiled steps; a case that expects the state at a point of its run stops the run at a rule the author wrote and counts its arrivals there, and expects that stop:

```toml
run = { stop_before = ["crate::machine::boundary"], stop_count = 3 }
expect = { halt = "stopped", rule = "crate::machine::boundary", compare = ["pc"], cells = { pc = 259 } }
```

`rule` names the one item the run stopped at, as the status line of `krs run --case` names it (``stopped after S steps, before `crate::machine::boundary` (stop 3 of 3)``), whichever of several stop items it is.
`depth` may stay in `run` beside the stop as a backstop: a run that never reaches the stop then ends `depth-bound`, and its expectation is inconclusive.
To find N, run the case without its `expect` table and with a count larger than the run reaches, beside a `run` table that holds only `depth` (`krs run --case FILE#NAME --stop-before ITEM --stop-count 1000000`); the status line says how many arrivals it reached (`depth-bound after S steps, A of 1000000 stops reached`).
Where the point of the run is a fact about the state rather than a count, `run.stop_when` states it, as `--stop-when` does, with the observer beside it: `{ function, cells, observer }`, `observer` optional.
A test ROM that signals its end by fetching a breakpoint instruction stops at the first boundary whose fetched byte is that instruction, read from the cells that hold the program counter and the cartridge:

```toml
[run]
stop_before = ["crate::interrupt::boundary_fetch"]
stop_when = { function = "MooneyeBreakpoint", cells = ["pc", "rom_end", "rom"], observer = "sm83-views:views" }
depth = 10000000            # a budget only: run out first, and the case is inconclusive

[[case]]
name = "ei_sequence"
[case.inputs]
cartridge = { "$file" = "ei_sequence.gb" }
[case.expect]
halt = "stopped"
rule = "crate::interrupt::boundary_fetch"
compare = ["regs"]
views = { regs = "MooneyeResult" }
observer = "sm83-views:views"
cells = { regs = { A = 0, B = 3, C = 5, D = 8, E = 13, H = 21, L = 34 } }
```

The function is written so that it has a value at every stop state: `if InRom(rom_end, pc) { bytes::get(rom, pc) == 0x40 } else { false }`, since `bytes::get` outside the ROM has none, which would refuse the run there.
The count, when the case gives one, counts the arrivals where the condition holds, and `--output json`'s `arrivals` says how many boundaries the run passed.

The expectation is met when every end of the definition from the case's inputs agrees with it.
A run that reaches its `run.depth` is inconclusive against the expectation, never met or unmet, whether or not the state at the bound has a successor: the run takes no step from that state, so it is not known to be an end.
`krs search --case` checks every final state; it applies no stop rule, so it refuses a case whose `run` names stops, which `krs run --case` and `krs cases` run.
`krs run` follows one path: an end of it that differs is unmet, and one that agrees is met only when no state of the path has several successors (the path is followed again, trying every rule at each step, to find out) and the run read no value the definition leaves open; otherwise the verdict is inconclusive, and names the state that has several successors and their rules, or the open values.
With an expectation, `krs run --case` prints its output as without one, then `krs run: expectation met`, or `unmet at` the first differing cell's path with the expected and the actual value as canonical documents (and the other compared cells that differ), or `inconclusive` with the reason: the run has no end to compare, or may have others; a run that cannot decide which of several states it reaches prints no state, only the verdict.
It exits by the verdict, in place of the exit cell's status ([exit status](#exit-status)).
An expectation that is no end of the definition, or that leaves out a cell it is compared on, is refused before the run (`krs::exec::case`); a `--case-name` the document does not hold is a usage error, as a missing or a superfluous one is.

`--output json` adds the verdict to the report as the member `expectation`, beside `run` or `search` (alone when the run reached no one state):

- `verdict`: `met`, `unmet` or `inconclusive`;
- `case`: the case's name, in a document of named cases only;
- `difference`: for `unmet` only, the first difference, a document that names its format (`format`, `krs-difference/3`), the expected end on its `left` side and the actual one on its `right`;
- `reason`: for `inconclusive` only, the reason as text;
- `views` and `observer`: the views the comparison applied and the observer it evaluated them in, when the expectation names them.

A difference names the first position where the ends differ by its `path`, which the human line prints too: the cell's Rust field path, an instance of a `List` collection by its index (`threads.thread[0].count`) and one of a `Map` collection by its key (`procs.process[1].ticks`, `harts.hart["boot"].pc`), followed by the segments inside the cell's value: a constructor's field with its constructor, as a position of the value's document spells it (`f.Flags.zf`, `bus[0].Idles.count`), a list's index in brackets (`bus[2]`), and a map's key in brackets as the canonical text of the key's own document at the key type (`regs["B"]`, `memory[5]`).
A key is so written whatever the map's document writes: a document writes a map as an object whose member names are strings (`"memory": {"5": 6}`), while its segment is the key's own value (`memory[5]`), so that a segment is read by the declared type of the position it descends into, and the key `5` of a `Map<Int, Int>` and the key `"5"` of a `Map<String, Int>` are told apart.
A `Map` collection is a map from key to instance, its key being the instance's first cell: two ends' instances with one key are the same instance, so a changed cell of one is one difference at its key, and a comparison that compares cells of the collection compares the whole of the key (one that leaves it out, or views it, is refused).
Version 3 of the format reads `path` differently from version 2 in these two places, so it takes the next version: version 2 named a constructor's field without its constructor (`f.zf`), and named an instance of a `Map` collection by its whole text, comparing the instances as a set's.

An expectation may compare a cell on what a view of it gives rather than on its whole value: `views` names, per compared cell, a function of one parameter, which the comparison applies to the expected and to the actual value alike, so the expected value is the cell's, not the view's.
The views are evaluated in the definition the case runs on, or in the definition `observer` names, `PACKAGE:DEFINITION` as `--dependency` names one: a package of the package graph Cargo resolves for `--manifest-path` (a workspace member or a dependency of one, so that the observer and the definition it compares come from one Cargo resolution, and a view is never built against another copy of the definition) that depends on the definition's package and that no semantics imports, so that editing a view changes neither the definition, nor its rules, nor anything keyed by it (the section [Expectations](#expectations) below states the rule).
krs composes the observer as it composes any definition, from its package's own dependency closure: the definition it depends on, held whether or not the observer's source names anything of it, and the facets `--dependency` names, so it may also compose a package no semantics depends on (one holding the functions the views apply); a `--dependency` facet outside the definition's own closure is composed by each observer whose closure holds it, and is refused when no prepared observer's closure holds it (a warning after `krs cases` has printed its verdicts).
An observer that cannot be compiled refuses the case with its diagnostics; a view, which no program writes, is marked `internal`, or it is program syntax and needs a `syntax`.
A view that does not apply to its cell is refused before the run, and one without a value at an end refuses the case.
A function evaluated in one instance of a Map collection ([a group held in a collection](/reference/language#a-group-held-in-an-optional-cell-or-a-collection)) is no view, whatever its parameters: it receives the instance's key, and a view is evaluated in no instance, so naming it is refused before the run with that reason.
Each evaluation of a view has a budget of `--view-budget POLLS` polls (30000000 by default): a count of the points at which the simplifier polls for a stop, which is the evaluation's own work, so whether the budget stops it does not depend on the host's speed or load.
An evaluation that spends the budget, or that another stop of the backend ends (the simplifier's stack, the solver's prelude), makes the verdict inconclusive, since the view may yet have a value; a value it reaches is the definition's value, whatever the budget.
So does an evaluation that ends short of a value after the solver answered a query `Unknown` (one of its bounds ran out, as under a small `--smt-resource-limit`, or the query is beyond what it decides): such a condition is undecided by that run of the solver, not by the definition.
A condition the definition decides false, or that stays undecided on decided answers alone, leaves the view no value, which refuses the case.
A view without a value at one value refuses the case even where its evaluation at another value stopped: the refusal holds whatever the budget, so a stop makes the verdict inconclusive only when no other viewed value refuses.
Whether a case is refused or inconclusive then depends on each value's own evaluation, not on which side, or which instance of a repeated cell, is evaluated first, which only chooses the value the refusal names; the exception is an evaluation that ends, within the budget or without an `Unknown` answer, only because it reuses an answer the observer's solver decided for a value evaluated before it.
To know that no value refuses, a verdict whose evaluations stop evaluates every distinct viewed value, so its time grows with their number, up to one budget for each; a value with a part that has no KRS description refuses before any evaluation.
The verdict's lines name the views it applied (``  views: `bus` = `WritesView`, in `sm83-views:main` ``).

[run]
stop_after = ["crate::machine::boundary"] # its KRS item; its K label also names it

[[case]]
name = "ld-a"
inputs = { pc = 256, regs = { A = 0 }, rom = { "$hex" = "3e01" } }
[case.expect]
halt = "stopped"

### The encoding

This section is the normative statement of the encoding.

A *document* is a value of the JSON data model: null, a boolean, a number, a string, an array,
or an object. A TOML document is first converted to it (`toml_document`): integers and
booleans, strings, arrays and tables as themselves, a finite float as a number, a NaN or an
infinity as `{"$float": "NaN"}`, `{"$float": "Infinity"}` or `{"$float": "-Infinity"}`, and a
datetime is refused, since it has no reading as a term. A JSON text is read with duplicate
object keys refused (`json_document`); a TOML parser refuses them itself.

A document is decoded at a *position*. A position is a declared type: a sort and, for a
collection, its element types (`Map<Int, Int>`, the type of the parameter or of an element
inside it). A parameter, a cell, a constructor's field and a function's argument or result
each have the type their declaration states, element types included (`regs: Map<Reg8, Int>`).
A position is *untyped* where the declared type says nothing: a `K` sort, the elements of a
collection whose element types are not declared (a field declared `List`, the elements of
`$list`), and the field of a sort no KRS declaration names.

Every document has at most one reading at a position. Shorthands are read only where the
position's type decides them; elsewhere a *tagged form* states the reading. Where a shorthand
has two readings at a position, the document is refused and the message names the tagged
form of each reading. The decoder refuses rather than guesses.

#### Tagged forms

A tagged form is an object with exactly one key, which starts with `$`; no Rust identifier
does, so a tag never collides with a constructor or field name. An object with a `$` key and
other keys is refused. A tagged form means the same at every position, and one whose term is
of a sort that is not at most the position's sort is refused.

A map key is not a Rust identifier, and one that starts with `$` (a `String` or token key)
would make the object shorthand of a `Map` a tagged form: such a map is written in the pairs
form, `[["$x", 1]]`, and the refusal of the object says so.

| form | value | where |
|---|---|---|
| `{"$text": "K text"}` | the text, parsed at the parameter's sort as `-c` parses it, or at a stated cell's sort | a whole input, and a whole cell a case's `instances` states |
| `{"$text-file": "path"}` | the file's UTF-8 text, as `$text`; parse locations carry the file's name | as `$text` |
| `{"$file": "path"}` | a `Bytes` of the file's bytes, unchanged | anywhere `Bytes` fits |
| `{"$hex": "00ff1a"}` | a `Bytes` of the bytes the hex digits spell (an even count, either case, no separators) | anywhere `Bytes` fits |
| `{"$data-file": "path"}` | the document the file holds (`.json` or `.toml`, by extension), decoded at this position | anywhere |
| `{"$string": "text"}` | a `String` | anywhere |
| `{"$int": "-0x1f"}`, `{"$int": 31}` | an `Int`: a string by the integer grammar of the `Int` row below, or an integer | anywhere |
| `{"$float": 1.5}`, `{"$float": "1.5f"}` | a `Float`: a number read as at `Float` (below), or the value a K `Float` literal names | anywhere |
| `{"$token": "text"}` | a token of the position's sort, which is a token sort | a token sort |
| `{"$token": {"sort": "Id", "text": "x"}}` | a token of the named token sort | anywhere |
| `{"$list": [..]}`, `{"$set": [..]}`, `{"$seq": [..]}` | a `List`, a `Set`, a K sequence, of untyped elements | anywhere |
| `{"$map": [[key, value], ..]}` | a `Map` of untyped keys and values | anywhere |
| `{"$ctor": {"path::C": fields}}` | the constructor `C` applied to its fields, as the constructor form `{"path::C": fields}` reads it | anywhere |
| `{"$call": {"path::f": fields}}` | the application of the function `f` to its arguments | anywhere |

A token's text, as `$token` or as a shorthand, is not checked against its sort's lexical
syntax: it denotes the domain value of that sort with that text, a term of the sort, even
where no K text of the definition spells it (`"top"` at a sort whose tokens match
`@[a-z]+`), while `$text` of the same text fails to parse.

A path in `$file`, `$text-file` or `$data-file` is relative to the document that holds it
(the case file, or the data file that includes it), and the decoder reads no file itself: the
caller's `InputFiles` resolves and reads it. A `$data-file` that includes itself, directly
or through others, is refused naming the cycle.

#### Constructors and functions

A constructor is written `{"Name": fields}`, with `fields` an object by field name or an array
in declaration order (a tuple variant's fields are named `0`, `1`, ..), and `[]` or `{}` for
none; at a position of a declared sort a bare string `"Name"` is a nullary constructor.
`Name` is the declaration's path, the crate name of its package's library and its path below
the crate root (`sm83::machine::Register::A`), or a `::`-aligned suffix of it (`Register::A`,
`A`), resolved
among the constructors whose result sort is at most the position's sort (among all
constructors at an untyped position); a name that selects several is refused naming them.
Each field is decoded at its declared type, element types included: a field declared
`Map<Reg8, Int>` reads `{"B": 1}`, and one declared `List` has untyped elements.

At a declared sort that `Map` is at most (`KItem`, a field declared `KItem`), an object is also
a map's object shorthand, so `{"Name": fields}` reads two ways there and is refused. The tagged
form `{"$ctor": {"Name": fields}}` states the constructor reading at every position, its name
resolved and its fields read as the constructor form's are; a function under `$ctor` is
refused, as one in the constructor form is.

A function is applied with `$call`, its arguments written as a constructor's fields and
resolved among the function productions whose result sort is at most the position's sort. A
function written in the constructor form, and a constructor under `$call`, are refused: a
reader of a case sees which parts are data and which are computed. Any function may be applied,
partial and `internal` ones included, as the initializer's body may apply them; the
configuration holds the application, which the definition's equations evaluate when the first
state is simplified, before the first step. A function evaluated in one instance of a Map
collection (its function context reads a cell group held there, or it applies such a
function) is refused: it receives the instance's key, and an input is evaluated in no
instance. It is not program syntax for the same reason, and text that applies it (`$text`,
`$text-file`), with its own arguments alone as its `syntax` declares them or with the keys its
emission adds after them, is refused with the same reason before the run.

#### Shorthands

| position | shorthands |
|---|---|
| `Int` | an integer; a string of an optional `-` and decimal digits, or of `0x`, `0o` or `0b` and digits of that base (for values beyond 64 bits, and for hex); a number with a fraction or an exponent is refused, since JSON delivers an integer beyond 64 bits as one and it would be rounded |
| `Bool` | `true`, `false` |
| `String` | a string |
| `Float` | a number, or a string that is a K `Float` literal; an integer is its binary64 value when binary64 holds it exactly and is refused otherwise; a number with a fraction or an exponent is its binary64 value, but one with an integral value of 2^64 or more, or of -2^63 or less, is refused, since a JSON reader delivers an integer it cannot hold as such a number, already rounded (write it as a K `Float` literal) |
| `Bytes` | an array of integers in `0..=255`; a bare string is refused, since its byte encoding is not determined |
| a token sort (`Id`, a `#[k::token]` sort) | a string, the token's text |
| `List<E>`, `Set<E>` | an array of documents at `E`; a `Set` with two elements that decode equal is refused |
| `Map<K, V>` | an object, each key read at `K` from its string (an `Int` by the integer grammar, a `String` verbatim, a `Bool` from `"true"` or `"false"`, a token's text, a nullary constructor's name) and each value at `V`; or an array of `[key, value]` pairs; two keys that decode equal are refused |
| a declared sort | a constructor form; a bare string: a nullary constructor, a token of a token sort at most it, or a `String` where `String` is at most it; a boolean where `Bool` is; a number where `Int` or `Float` is (below); an array or an object where a collection sort is, as at that sort with untyped elements |
| untyped | an integer (an `Int`), a boolean (a `Bool`), a number with a nonzero fraction (a `Float`), a constructor form, a tagged form; a bare string, an array, a number with an integral value written as a float, and any other object are refused as undetermined |

At a declared sort that is no builtin, the document's JSON type decides the builtin, as at an
untyped position: a string is never an `Int` or a `Float` there, so `"12"` at `Val`, with
`Int` and `String` subsorts of `Val`, is the `String` `"12"` (an `Int` beyond 64 bits is
written `{"$int": ..}`). A number is an `Int` where `Int` is at most the sort and a `Float`,
read as at `Float`, where `Float` is and `Int` is not. Where both are, an integer is an `Int`,
a number with a nonzero fraction a `Float`, and a number with an integral value written as a
float (`2.0`) is refused as undetermined, since JSON delivers an integer beyond 64 bits so:
the `Float` is written `{"$float": 2.0}`. A map key, which is always a string, is read at its
sort by every reading of the strings the `Map` row lists, so `"12"` as a key at `Val` reads
as an `Int` and as a `String` and is refused; such a map is written in the pairs form.

Two map keys or set elements that decode equal are refused because K's concatenation of two
maps that bind one key, or of two sets that share an element, has no value: keeping either
binding would accept a document that denotes no term, and would let `{"1": 2, "01": 3}` mean
a map that the text `1 |-> 2 1 |-> 3` does not.

A decoded value is still checked where a parsed one is: the configuration assembler requires
its sort to be at most the variable's declared sort, and every part of a collection to fit the
declared element types. The decoder's own checks make the refusal earlier and name the
position inside the document.

Not in the encoding: `$text` inside a value (below a whole input or a whole stated cell), sort-parametric productions (refused as
`ValueIndex::ctor` refuses them), and console input.

#### The canonical document of a value

Every value that has a document at a position has one *canonical document* there,
which `encode` writes and which decodes back to the value:
`decode(encode(v, t), t) = v`.
It is the spelling of a concrete value in every KRS-level report
(the two sides of a difference, the result of a view),
so that an expected value and an actual one read alike.
Each rule writes the form a reader of this encoding writes for the value:
a shorthand where the position's declared type decides it, a tagged form elsewhere.
A shorthand is written only where it has exactly one reading at the position,
by the decoder's own table:
where the definition gives it a second
(a constructor whose result sort is a token sort, named like a token's text,
which a definition KRS emits does not have),
the tagged form named below is written instead,
so no canonical document is one the decoder refuses.

- **Int**: at `Int`, an integer where it lies in `-2^63..2^63`
  (every JSON and TOML reader holds it), otherwise the string of its decimal digits;
  elsewhere an integer in that range, otherwise `{"$int": "<decimal>"}`.
- **Bool**: `true` or `false`.
- **String**: at `String`, the string;
  elsewhere `{"$string": ..}`,
  since a bare string at a declared sort may also read as a nullary constructor or a token.
- **Float**: at `Float`, a string:
  the K `Float` literal of the shortest decimal digits that read back to the value,
  a significand with a `.` and at least one fractional digit and an exponent `e<n>`,
  then `f` for binary32 and nothing for binary64
  (`1.5e0`, `1.0e300`, `5.0e-324`, `1.5e0f`);
  `NaN`, `Infinity`, `-Infinity` and `-0.0e0`, suffixed alike.
  A value of another format is written as its canonical literal (`1e0p11x5`).
  Elsewhere `{"$float": <that string>}`.
  Never a JSON number: a reader may round one, and none holds a NaN.
- **Bytes**: `{"$hex": "<lowercase digits>"}` at every position,
  `{"$hex": ""}` for the empty value.
  The array shorthand is read, never written, so a `Bytes` has one spelling.
- **A token**: at its own token sort, its text,
  or `{"$token": "<text>"}` where the bare text has another reading at that sort;
  elsewhere `{"$token": {"sort": S, "text": ..}}`,
  `S` the shortest `::`-aligned suffix of the sort's path that names it among the sorts.
  A domain value of a sort that is no token sort has no document.
- **List, Set**: at a position whose sort is the collection's,
  the array of the elements' documents at the element type (untyped where none is declared);
  elsewhere `{"$list": ..}` or `{"$set": ..}` with untyped elements.
  A set's elements are ordered by the bytes of their canonical text.
- **K sequence**: `{"$seq": [..]}`, its items untyped.
- **Map**: at a `Map` position whose key type is declared,
  where every key has a *key spelling* and none starts with `$`,
  the object of the key spellings to the values' documents at the value type;
  otherwise, at a `Map` position, the array of `[key, value]` pairs at the key and value types;
  elsewhere `{"$map": [[key, value], ..]}` with untyped keys and values.
  Pairs are ordered by the bytes of the key's canonical text.
  A key spelling is a string whose only reading at the key type is the key:
  an `Int` in decimal, a `Bool` as `true` or `false`, a `String` as itself,
  a token as its text, a nullary constructor as its name.
  `"12"` at `Val`, with `Int` and `String` subsorts of `Val`, reads two ways,
  so a map with `Val` keys that holds the `Int` 12 is written in pairs.
  An object key that starts with `$` would make the object a tagged form,
  so a map with such a key is written in pairs too.
- **A constructor**: `{"Name": fields}`,
  `fields` the array of its fields in declaration order for a tuple variant (fields `0`, `1`, ..),
  `[]` for none, and the object by field name otherwise,
  each field's document at its declared type, element types included.
  A nullary constructor is the bare string `"Name"` at a declared sort where that string
  has no other reading: one that neither `String` nor any token sort is at most.
  Where `{"Name": fields}` has another reading at the position
  (at a declared sort that `Map` is at most, where an object is a map too),
  `{"$ctor": {"Name": fields}}`, with the same name and fields.
  `Name` is the shortest `::`-aligned suffix of the declaration's path
  that selects exactly this declaration among the constructors the decoder resolves at the position
  (among all constructors at an untyped position).
- **A function application** (a value `ValueIndex::call` builds):
  `{"$call": {"Name": arguments}}`,
  named among the functions as a constructor is among the constructors.
- **No document**:
  an `Opaque` part (a variable, an unevaluated application,
  a freezer or another constructor without a KRS declaration, a matching-logic connective);
  the application of a parametric constructor, which no form of this encoding writes;
  and a value whose sort is not at most the position's.
  The refusal (`EncodeError`) names the part's position,
  in the notation of `InputError`'s positions
  (`.Run.log$list[2]`; an element of a set and a key of a map by its index in the value's order),
  what the part is, and the rule that refuses it.
  An `Opaque` part and a parametric application are parts a state may hold by its nature;
  a value with a part of another kind is refused naming that part, wherever they lie,
  so that the first two never hide a part that says the value is not what its position admits.
  A caller shows such a value as K text, marked as such,
  never as a document with K text inside it.

The *canonical text* of a document (`canonical_text`) is its compact JSON,
with the members of each object ordered by the bytes of their keys,
written by this crate rather than by a JSON library's map,
so that it is byte-identical across runs and hosts.

### Case documents

A *case document* is a TOML or a JSON document, by its file's extension,
that states one case or several named cases (`CaseDocument`).
A *case* is a table of four keys, each of which may be absent:

- `inputs`: a value for each input, by name
  (a parameter's Rust name, or its configuration variable's K name with or without `$`),
  each a document of the encoding, read at the parameter's declared type;
  a front end may bind the inputs a case does not name in its own ways.
- `run`: how the case is run:
  `depth`, at most this many rewrite steps;
  `stop_before` and `stop_after`, the rules at whose step the run ends,
  each an array of names of rules as `StopRules` takes them:
  a KRS item as a stop flag names it (`crate::machine::boundary`, or a dependency's crate name,
  the crate name of its library, and its path), or a K label, in full or by a
  unique suffix after a `.`;
  and `stop_count`, a positive integer, the arrival at a stop the run ends at
  (`StopCriterion::Rules`), the first by default,
  which needs a stop rule to count arrivals at;
  and `stop_when`, a stop condition (`StopWhen`),
  a table `{ function, cells, observer }`:
  `function` names a function of result sort `Bool` as a view names one,
  `cells` the leaf cells it reads by Rust field path, in the order of its parameters,
  and `observer`, optional, the definition it is evaluated in, `PACKAGE:DEFINITION`
  as an expectation names its observer, the run's own definition by default;
  an arrival is then a stop only where the condition holds of the state the run would end at,
  and `stop_count` counts those.
  The condition needs a stop rule, at whose arrivals it is asked.
  The count and the condition belong to the case, beside its rules,
  since where a run is observed depends on the program it runs.
- `instances`: the instances the run starts with, of the optional and repeated cells it names
  ("Instances", below).
- `expect`: the end the case expects of its run ("Expectations", below).

A document of one case holds these keys at its top, and no other.
A document of named cases holds `case`, the *list* of its cases,
and may hold `run`, the `run` of every case that has none of its own
(a case's own `run` replaces it whole);
it holds no other key, so a document is of one kind or the other.
A JSON document that is an array is a list, and a document of named cases.
A list is an array (TOML's `[[case]]` tables) of named cases, each a case with a `name`,
and of *includes*, `{"$data-file": "path"}`,
each naming a `.json` or `.toml` file whose document is a list
(an array, or a table whose one key is `case`, as TOML writes a list);
the file's cases stand at the include's place.
A path written in an included file, an include's or one in a case's values,
is relative to that file;
the caller's `InputFiles` resolves it, under its own rules, as it resolves every path,
and a file that includes itself, directly or through others, is refused naming the cycle.

A name is a non-empty string that no other case of the document has,
the cases of included files included,
so that the document and the name identify a case (`<document>#<name>`).
A front end selects a case of a document of named cases by its name;
the one case of a document has no name, and is selected by none.

#### Instances

The initializer states every fixed cell's start as a function of the inputs,
and one instance's template for each optional (`?`) and repeated (`*`) cell;
how many instances such a cell starts with is what it cannot state.
`instances` states exactly that: the starting instances of the cells it names.
A fixed cell starts as the initializer says, and a case that needs another start binds other inputs.

`instances` nests by group field as an end document's `cells` does
(`instances.harts.hart` is the cell `hart` of the group `harts`),
down to an optional or a repeated cell, which it states in the encoding an end document uses:
an optional cell as `[]` (absent) or `[content]` (present),
a repeated cell as the array of its instances, in order for a `List` collection.
An instance is the table of its cells by Rust field (a document for an optional leaf cell),
read as an instance a rule creates is:

- a stated leaf cell is read at its declared type, element types included,
  as an input's value is, and may be K text (`$text`, `$text-file`), parsed at the cell's sort;
- a stated group cell is the table of its cells, read the same way;
- a stated optional or repeated cell inside an instance states that cell's instances, as above;
- a cell the instance does not state takes the template's start, evaluated under the case's inputs,
  as the initializer's own instance takes it.
  The template is a function of the inputs, which the case binds, so every cell has one.

An instance of a `Map` collection states its whole key, its first cell,
as a value (no function application):
the key is the instance's identity,
and two instances with one key are refused, naming the key, since a map holds one instance per key.
Two instances of a `Set` collection stated alike are refused too: a set holds an instance once.
The stated instances of a cell replace the ones the initializer starts it with,
the instance `initial` starts included; a cell `instances` does not name starts as the initializer says.
A path that names a fixed cell is refused, listing the optional and repeated cells a case may state,
and a path the configuration does not declare is refused, listing the cells there, as an end document's is.
A function evaluated in one instance of a Map collection is refused in a stated cell's value or text,
as it is in an input's: it receives an instance's key, and the case's values are evaluated in no instance.

```toml
inputs.pgm = { "$text-file" = "boot.s" }

[[instances.harts.hart]]
id = 0
pc = 0x1000

[[instances.harts.hart]]
id = 1
pc = 0x2000
```

states two harts, keyed `0` and `1`, each with the program counter it gives
and every other cell as the template starts it (both run the program `pgm` binds).

#### Expectations

`expect` states the end the definition computes for the case,
as an end document (the section "End documents" of krs-exec's `ends` module)
with a narrowing:

- `halt` and, for `stopped` only, `rule`: how the run ends,
  the stop rule named as `run` and every end document name rules, by KRS item or K label,
  so that one spelling names a rule in all of them;
  the name selects the rules of one KRS item, which a stopped end's class names;
  `halt` is never `depth-bound`, which is refused:
  the depth counts the compiled definition's steps, heating and cooling included,
  so the state after N steps is no fact about the definition,
  and a run that reaches its bound is not known to have ended
  (`ends`, "Results");
  an expectation of the state at a point of a run stops the run at a named rule
  with a `stop_count` and expects `halt = "stopped"` with that `rule`;
- `cells`: the cells' values by Rust field path, nested by group field
  (`cpu.regs` is `cells.cpu.regs`),
  each read at the cell's declared type as an input's value is,
  its file paths relative to the document that holds the case;
- `compare`: the cells the end is compared on, by declared path,
  by default every leaf cell that is not unobservable;
- `views`: a table of a view by compared leaf cell (its declared path),
  each the name of a function of one parameter (`views`),
  which the comparison applies to the cell's value on both sides,
  so that the end is compared on what the case observes of the cell;
- `observer`: the definition the views are resolved and evaluated in,
  named as a front end names a definition (krs: `PACKAGE:DEFINITION`, as `--dependency` names one),
  by default the definition the case runs on;
  it is only given with `views`.

An expectation states every cell it is compared on:
it may omit an unobservable cell, which no use of the definition observes,
and a cell `compare` leaves out,
but a compared cell it omits is refused, naming the cell and its type, before the case runs,
since every value of that cell would meet it, which expects nothing of the cell.
A `compare` that names an unobservable cell is refused too: no observation of it exists to compare.
A cell the expectation states and does not compare is read, and never compared.
A viewed cell is stated as the cell's value, not as the view's:
the view is applied to the stated value as to the actual one,
so one expected end can be compared under several views.
A view that does not apply to its cell, or names no function of the observer, is refused before the case runs,
and one without a value at an end refuses the verdict, naming the view, the side and the cell,
since an observation that does not exist makes the ends neither agree nor differ.
A front end may bound each view's evaluation;
one that the bound or another stop of the evaluation ends before it reaches a value makes the verdict inconclusive, since it may yet have a value,
as does one that ends short of a value after the solver answered a query `Unknown`.

Against the ends of the case's run, the expectation is
*met* when every end agrees with it on the halt and on the compared cells;
*unmet* when an end does not, which is reported with the first difference
(`Difference`, `krs-difference/3`, which names the views it applied);
and *inconclusive* when no end can be compared,
or every known end agrees but not every end is known.
No end can be compared where
the run halted `indeterminate`, `timeout`, `interrupted`, `unsupported-hook` or `simplification-error`,
reached its depth bound (`depth-bound`: a budget ran out, and the definition may go on),
reached several states under conditions it cannot decide,
ended in a state that carries a constraint,
or stopped at a rule it does not name.
Not every end is known where a search was cut by its bounds,
where a run's path took one of several successors of a state,
and where the ends rest on a value the definition leaves open
(an implementation-chosen hook value), which another implementation of it may choose otherwise.
Inconclusive is never unmet: "no end to compare" and "ends differ" call for different actions.
"Every end" is the rule because one disagreeing end of a nondeterministic definition
is a result the definition can produce.

A run follows one path and has at most one end.
An end of it that disagrees is unmet, since the definition reaches it;
one that agrees meets the expectation only where it is the definition's only end:
no state of the path has several successors,
which the path, followed again trying every rule at each step, shows,
and the run read no value the definition leaves open.
A final-state search gives every end within its bounds.

## Run a batch of cases

```console
krs cases --package my-semantics --definition main cases/steps.toml cases/boot.toml
krs cases --package my-semantics --definition main cases/sst.toml --jobs 8 --output json
krs cases --package my-semantics --definition main cases/steps.toml --name 'ld-*'
```

`krs cases` runs every case of the case documents it is given, in the order given and the cases of an included file at its place, and checks each against its expectation as `krs run --case` does: the same inputs, `run` table, views and verdict.
`krs run --case` starts a process, reads the package, restores the compiled stage and loads the definition into the backend for each case; `krs cases` does that once, then loads the definition once per worker and runs every case it is given on it, so a case costs its own run and check.
`--jobs N` sets the workers (by default the available parallelism).
Each worker holds its own copy of the definition, and of each observer it uses, so the memory a batch takes grows with N; on a large definition, choose N by the memory free, not by the processors.
The output is the same for every N, since each case runs from its own configured state, whichever worker runs it, and a view's budget counts work, not time.
The exception is a verdict that a resource stop decides, which may depend on what runs beside the case or before it on its worker: the simplifier's stack budget, which the workers share; the solver's limits, under which a query a worker's solver decided before is answered from its record of decided answers, and one it did not may come back undecided; and a view's budget that only such reuse lets the evaluation meet.
A case binds only the inputs it states, and its `run` table alone bounds and stops its run, so `krs cases` takes no FILE, `--input`, `-c`, `--depth` or stop flag; it takes the solver options of `run` and `--view-budget`.
`--name PATTERN` runs only the named cases whose name PATTERN matches (`*` any text, `?` any one character), and a pattern that selects no case is a usage error.

A case's record is printed as soon as the cases before it are, so a slow case holds back the records after it, never their runs.
By default each record is the verdict's lines `krs run --case` prints, named by the case's id, the document as given and, for a named case, `#` and its name (`cases/steps.toml#ld-a: expectation met`), `ran, stuck after 3 steps` for a case that states no expectation, with the stop clause of `krs run`'s status line when its run has stop rules (``ran, stopped after 10 steps, before `crate::tick` (stop 1 of 1, where `AccOver` holds; 6 arrivals)``) (`ran:` and the reason when its run reaches several states under conditions it cannot decide, so has no end), or `refused:` and the reason for a case the definition cannot run: a document that cannot be read (one record, after which the next document runs), inputs or an expectation that are refused, an observer that cannot be prepared, or a view without a value at an end.
A case refused because its expectation is a `depth-bound` end gets a one-line record, and the reason and what to state instead are printed once, before the count, naming every case refused for it: the text is the same for each such case, and a corpus migrated from depth bounds has many.
A last line counts the verdicts.
`--output json` prints one document per line instead, each naming its format, `"schema": "krs-cases/4"`:

- a record per case: `case`, its id; `verdict`, `met`, `unmet`, `inconclusive`, `refused` or `ran`; `halt` and `steps`, when the case ran to a state; `difference`, for `unmet` (`krs-difference/3`); `reason`, for `inconclusive` and `refused`, and for `ran` with no end; `stop`, `stops`, `arrivals`, `undecided` and `passed_stops`, as `krs run --output json` reports them, when the case's run has stop rules; and `views` and `observer`, when the expectation names them, whatever the verdict;
- then the summary, `{"schema": "krs-cases/4", "summary": {"cases", "met", "unmet", "inconclusive", "refused", "ran"}, "status"}`, `status` being the exit status.

Version 2 of the format reads differently from version 1 in two places, so it takes the next version: a case that states no expectation and whose run has no one path is `ran`, with its `reason` and no `halt`, where version 1 recorded it `refused`; and the summary's `status` is the exit status of the four actions ([exit status](#exit-status)), under which a refused case gives 2, where version 1 gave 1.
Version 3 records a halt version 2 does not know, so it takes the next version: a case whose run's stop condition is left undecided at an arrival (`run.stop_when`) records the halt `stop-undecided`, and is `inconclusive`.
Version 4 records the stops of a run with stop rules, which a version 3 reader would read, from their absence, as a run that passed none.

`krs cases` exits as a batch of its cases ([exit status](#exit-status)).

## Compare two ends

```console
krs compare --package my-semantics --definition main ends/reference.json cases/steps.toml#ld-a
krs compare --package my-semantics --definition main left.json right.json --compare pc,regs,bus \
  --view bus=WritesView --observer my-semantics-views:main --output json
krs compare --package my-semantics --definition main --expect cases/steps.toml#ld-a ends/emulator.json
```

`krs compare` compares two ends of the definition, the left and the right side, on the halt and on every leaf cell that is not unobservable.
Each side is a `.toml` or `.json` file, read by its keys:
an end document (`halt`, `rule`, `cells`), written as [an expectation](#expectations) writes its end;
or a case document, whose case is run as `krs run --case` runs it (its inputs and its `run` table), and whose run's end is the side.
`FILE#NAME` names a case of a document of named cases, as the case's id in `krs cases` does.
The case of a case side is run, not checked: its own `expect` table is no part of the comparison.

An end document states the one end of whatever produced it: another implementation, a recorded run (`krs run --output end` prints one), an expected state written by hand.
A run's end is its case's only end exactly where the run chose nowhere: no state on its path had several successors, and it read no value the definition leaves open.
Where it chose, the definition may end otherwise from the same inputs, so its side is incomplete.
Two sides are *equal* when their ends are; they *differ* when one side has an end the other, complete, side does not; otherwise the comparison is *inconclusive*, as it is when a side has no end (its run halted `indeterminate`, `timeout` or another inconclusive halt).
An end document that leaves out a cell the comparison compares is refused, naming the cell and its type, before any case is run.

`--compare CELL,...` compares only the cells it names by declared path (a group names its leaves), and may be repeated; a cell it names may not be unobservable.
`--view CELL=FUNCTION` compares a cell on the value of a function of one parameter at the cell's value on each side, as an expectation's `views` does, and may be repeated, one view per cell; the views are evaluated in the definition compared, or in the definition `--observer PACKAGE:DEFINITION` names, composed with the `--dependency` facets its closure holds, within `--view-budget POLLS` polls each.

`--expect CASE` checks the one side given against the expectation of CASE (`FILE` or `FILE#NAME`) on the cells, views and observer it names, as `krs run --case` checks its run's end, so `--compare`, `--view` and `--observer` do not apply.
The side may be an end document: an end another implementation reached, checked against what the case expects.

`krs compare` prints `krs compare: equal`, or the first difference as `krs run --case` prints an unmet expectation's: where the sides differ, each side's value labelled `left` and `right`, the other compared cells that differ, and the views it applied; with `--expect`, the lines of `krs run --case`.
`--output json` prints one document instead, `{"schema": "krs-compare/1", "verdict", ...}`: `verdict` is `equal`, `differs` or `inconclusive` (`met`, `unmet` or `inconclusive` with `--expect`), with `difference` (`krs-difference/3`, the left side on its `left`) or `reason`, and `views` and `observer` when views were applied.
It exits by the verdict ([exit status](#exit-status)).

### Compare many pairs

```console
krs compare --package my-semantics --definition main --pairs pairs.toml --jobs 4 --output json
```

```toml
[[pair]]
left = "ends/emulator-ld-a.json"
right = "cases/steps.toml#ld-a"
compare = ["pc", "regs", "bus"]
views = { bus = "WritesView" }
observer = "my-semantics-views:main"

[[pair]]
expect = "cases/steps.toml#ld-b"
actual = "ends/emulator-ld-b.json"
```

`krs compare --pairs FILE` asks every question the document FILE lists, each one `krs compare` question:
`left` and `right`, with the `compare`, `views` and `observer` that `--compare`, `--view` and `--observer` would give it, or `expect` and `actual`, as `--expect CASE ACTUAL`.
A side is spelled as on the command line (`FILE` or `FILE#NAME`), relative to the directory of FILE, as every path a document names is relative to that document.
FILE lists its pairs under `pair` as a case document of named cases lists its cases under `case`, an array of tables in a `.toml` file or of objects in a `.json` file, read by its extension, and holds nothing else; a document that lists no pair is refused.
Since every pair states its own question, `--pairs` takes no sides, `--expect`, `--compare`, `--view` or `--observer`; `--view-budget` and the solver options apply to every pair.

A batch costs what `krs cases` costs: the package is read and the stage restored once, the definition is loaded once per worker (`--jobs N`, by default the available parallelism), each observer a pair names is prepared once and loaded once per worker that uses it, and memory grows with N in the same way.
A case side's end, and whether it is its case's only end, depend on the case and the definition alone, not on the comparison, its views or its observer, so each case the pairs name is run once for the whole batch and followed again at most once, whichever pairs and workers use it.
Each pair's verdict is then the one `krs compare` gives for that pair alone, with the exceptions `krs cases` states for a verdict a resource stop decides.

A pair's record is printed as soon as the pairs before it are.
By default it is the lines `krs compare` prints for the pair, headed by `pair N`, its sides as written and its `compare`, each view and its `observer` as `--compare`, `--view` and `--observer` give them, in place of `krs compare` (`pair 3 (ends/a.json, cases/steps.toml#ld-a): equal`, `pair 4 (ends/a.json, cases/steps.toml#ld-a, --view bus=WritesView): equal`), so that pairs over the same sides that ask different questions have different headers, or `refused:` and the reason for a pair that is no question (an unknown key, a missing side, a `compare` or `views` beside `expect`), whose side cannot be read or is refused, or whose observer cannot be prepared;
and `inconclusive:` and the reason where following a case side's run again reaches several states under conditions it cannot decide, where `krs compare` alone exits 3 with that reason.
A last line counts the verdicts.
`--output json` prints one `krs-compare/1` document per line instead:
each pair's is the document `krs compare` prints for it alone with one more member, `pair`, which holds its `number` (its place in FILE, counting from 1) and its sides as written (`left` and `right`, or `expect` and `actual`); a refused pair has `verdict` `refused` and its `reason`;
then the summary, `{"schema": "krs-compare/1", "summary": {"pairs", "equal", "differs", "met", "unmet", "inconclusive", "refused"}, "status"}`, `status` being the exit status.
A reader of a single comparison's document reads each pair's alike: `pair` is the only member added, and `refused` the only verdict a single comparison never prints, since it exits 2 with its diagnostic instead.

## The corpus loop

```console
krs kink results --package my-semantics --definition main
krs kink run --package my-semantics --definition main --full --output verdicts
krs kink emit --package my-semantics --definition main --check
```

`krs kink <verb>` runs the corpus loop of [kink](https://github.com/midnightntwrk/k-rust/blob/main/kink/README.md#using-kink-flow), k-rust's mutation tester, over the package's corpus, a directory `kink/` beside its `Cargo.toml` (`--corpus DIR` names another).
[Mutation testing a KRS specification](/verification/mutation-testing) walks through the loop and what to do with each status and refusal.
The verbs are kink-flow's, with kink-flow's options and its JSON documents: `check` admits the definition and every case, and resolves every mutation without running one; `results` reports each case's class and the rules its run matched and fired; `run` searches for a case that kills each mutation (`--full`: every case that does); `report` prints the last run's document again, as that run printed it, without building the package; `query` checks patterns of interest on each case; `fuzz` looks for the hole values of a case template that kill a mutation, match or fire a rule, or hit a pattern.
The corpus holds `FLOW.toml`, kink-flow's manifest, whose `[spec]` is `krs = { definition = "main" }`, the facet the corpus is for, which must be the one `--definition` selects; its cases, as program files or as case documents of the [typed encoding](#the-encoding) under `cases/`; mutations as K patches in `mutations/<topic>.toml` (else `MUTATIONS.toml`); `PATTERNS.toml` for `query` and `TEMPLATES.toml` for `fuzz`; `definition.k`; and `verdicts.lock`, the killer record.
kink-flow's caches are under `.kink-flow/` in the corpus, which is not committed (a `.gitignore` in the corpus holding `/.kink-flow/`).
krs keeps its own judgement of each mutation there too, in `.kink-flow/krs-judge/` (or under the directory `--cache` names), and `check --mutations`, `run` and a `fuzz` kill job read it back instead of judging the mutation again.
An entry is keyed by everything the judgement reads: the krs build, the emission (`definition.k` and its source map, which carries the digest of every authored file), and the mutation's edits as resolved with the mutant's text; so a rebuilt krs, an edited source or a respelled edit judges again, and an entry that does not decode is judged again and rewritten.
A case is a `[[program]]` entry of `FLOW.toml`: kink's documents list the cases under `programs` and name them by `id` (`killed_by`, `witnesses`, `matched_by`, `fired_by`), and the verdicts rendering writes each as a `[[case]]`.
A verb's list flag names another list than the layout's, a path relative to the working directory: `--mutations PATH` for `check`, `results` and `run`, `--patterns PATH` for `query` and `--templates PATH` for `fuzz`.
A K corpus (`[spec] entry = ..`) is refused, naming `kink-flow`, which runs it; a corpus of another facet is refused naming both facets.

Every verb but `emit` and `report` builds the package in process, as `emit-k` does, and kink judges `kink/definition.k`, which must hold exactly that emission: a command finds it `unchanged`, or writes it and says `written` in the document's `definition` object.
Writing it cannot change what a mutation means: a mutation is resolved against the current K on every command and refused when the text it replaces changed.
With `--locked` a command that builds the package refuses a stale `definition.k` instead (stage `definition`, reason `definition-stale`), and `krs kink emit --check` writes nothing and exits 2 when it is stale, as `--locked` refuses it, since the file is an input to regenerate: the check a CI runs before trusting committed verdicts; `krs kink emit` writes it.
`report` builds nothing and judges no `definition.k`, so it takes no `--locked`.
`run` of the corpus's own mutation list keeps `verdicts.lock` (kink-flow's `run --lock`; `--lock FILE` names another, and a run with `--mutations` uses none): each mutation's status and, for a killed one, its one recorded killer, which `run` tries first and keeps while it still kills, else the first killing case in the search's order replaces it; a run of the whole list rewrites the file.
The lock only orders the work and names the killer; every status comes from runs.
Under `--locked`, `run` leaves the lock unwritten (the cache is written as in any run) and compares the lock it would write with the file: a difference, an absent file included, is a finding (exit 1), and stderr names each change, each header value that differs, or, when neither a row's verdict nor a header value differs, the first line that does (rows in another order, a comment); so a CI runs `krs kink emit --check` and `krs kink run --locked`.
The lock's header names the solver profile and, under Z3, the Z3 build (`z3_version`, `z3_library_sha256`): whether a query is decided within its resource units depends on the machine code that counts them, so a lock recorded on another Z3 build is a finding under `--locked` even when every row agrees, since that run cannot confirm the committed lock on the instrument it names; a run without `--locked` rewrites the header, and the lock is recorded on the build the CI links.
Every rule a document names gains `krs = {item, source_item, package, file, line, column, kind, claim_helper}`: `item` names the KRS item that wrote the sentence as `run --coverage` and `--stop-before` name it (`crate::plus_zero`, `lang::step`), so a name copied from a document selects the same item as a stop, beside the sentence's own label; `source_item` is the item as the `// KRS` line above the sentence in `definition.k` names it (`Clamp, branch 3`); the rest is the position of the sentence's authored source, as `--trace` shows it; a rule KRS generated from no item has `null` there.
Every document the front end annotates carries `krs.version`, the version of how its `krs` objects read: 2 since `item` is spelled as a stop reads it, 3 since `stop.krs.when`, the stop condition as the corpus wrote it beside the `stop.when` it resolved, and 4 since a `results` document's guards are named by KRS construct (below); an annotated document with no `krs.version`, which an earlier krs wrote, names `item` as the `// KRS` line does.
The front end annotates every kink-flow document of a package it built and whose `definition.k` is fresh; a document refused before that (a package `krs` refuses, a stale `definition.k` under `--locked`) names no rule and has no `krs` member, and neither has `krs kink emit`'s document.
A specification diagnostic, a run's short-circuit reading and a query witness, which name compiled rules by label, gain `krs_rule` and `krs_observing_rule`, `krs` inside the reading's `rule`, and `krs_rules` where the label is one the emission wrote.
A rule's status in `results` is named for the predicate it tests: `fired` (some comparable case fired it), `matched` (some case matched it and none fired it: its right-hand side never ran), `unmatched` (no case matched it).
A claim helper (an equation of a function only claims apply) that no case matched has its own status, `claim-helper`, not `unmatched`: it serves the claims, which `krs prove` checks, and not the runs a case makes; a claim helper some case matched or fired (a typed input can apply any function) has that status.
A function nothing applies is reached by no program text either, but no claim accounts for it, so it stays `unmatched`.
A rule or equation with a condition has `guard`: the cases whose entries held, were refuted or stayed undecided, and each operand of the written condition with the cases for which it was `true` and `false` where it was reached (in a conjunction, where every operand before it is true); `never` lists what no case saw.
krs names every node of the condition by what produced it (`guard.operands[].krs`: `origin`, the item, and the Rust `text`, `file`, `line` and `column`) and groups the guard as you wrote it (`guard.krs`): `authored` lists your operands by their Rust text (`m[a] > 0`, `halted` in `!halted && irq`), each with its cases and `never`; `generated` lists apart the tests KRS inserted, each with the construct it serves (`anchor`): the definedness test of a division or a map read (a `false` there means the construct had no value, so the condition did not hold), and the guard of a looked-up key; and `templates` lists a `k::bits!` template's match test, which is pattern, not guard, with the cases whose templates matched (`matched_by`) and did not (`not_matched_by`).
Neither inserted tests nor templates count as gaps of your guard, and a condition the front end cannot name this way is listed under the document's `krs.unmatched_guards` with the reason.
`guard.krs.held_by`, `refuted_by` and `never` read your condition alone: `held_by` lists the cases for which your last conjunct was reached `true`, and `refuted_by` those for which one of your conjuncts was reached `false`; a template that did not match is a pattern miss, and an inserted test that was `false` leaves the conjunct it guards unreached, so neither refutes what you wrote.
A sentence whose condition has none of your conjuncts (only a template's match test or a looked-up key's guard) has `held_by` and `refuted_by` `null` and no guard gap: whether a case reaches it is its pattern's status.
Which conjuncts are yours is read from the definition, not from the cases, so a sentence no case reached is grouped too: with one of your conjuncts it has `held_by` and `refuted_by` empty and `never` lists both, and with none it has `null` and no guard gap.
A sentence with templates reads its match as its KRS pattern's: its K left-hand side is a bare variable, which every case that evaluates the function matches, so the row's `krs.matched_by` lists the cases whose templates matched and `krs.status` is `unmatched` where none did; the verdicts rendering reads both.
`results` lists a case in a rule's `matched_by` when kink's baseline run of the case, which follows every path, `matched` the rule, as `run --coverage` names the predicate, and in its `fired_by` when the run fired it: some path `committed` the rule's step, for a rewrite rule, or the run `applied` it, for an equation, whose application is no step; a case that is not `comparable` is listed under no rule.
`--output verdicts` (for `results`, `run` and `report`) prints kink-flow's deterministic rendering, which names each rule by its item and gives each case the rules that list it as `matched` and `fired`, and each killed mutation its `killer`; its header names the solver profile and, under Z3, the Z3 build, Z3's version string and the SHA-256 of the library its code comes from, on which the verdicts depend; a `results` rendering's header has `krs_annotation`, the document's `krs.version`, which the names' spelling follows.
`[result] cells` names the cells kink compares by Rust path, as `compare` in an [expectation](#expectations) and `krs compare --compare` do (`cells = ["regs", "ei_pending", "cpu.pc"]`), and `krs kink` gives kink-flow each cell's K name.
A K cell name (`eiPending` for `<eiPending>`) is read too, where no cell has that name as its Rust path: a path names one cell and is read first, so a corpus written by paths means what it says whatever the K names are, and a K name is read only where it competes with no path.
An entry that is neither is refused at stage `result` (`result-cell-unknown`), naming every cell by its path with its K cell, and two entries that name one cell, by its path and by its K name, are refused there too (`result-cell-repeated`).
Every document's `result`, which names the compared cells as kink-flow does, by K name, gains `krs`: `compared`, `not_compared` and `unobservable` by Rust path, and `cells`, each entry of `[result] cells` as written with the K cell it reads as.
`run --progress` prints a line on stderr as each phase krs runs first starts (the build and the emission, the binding of the corpus, the checks of the list), then the lines `kink-flow run --progress` prints: one before the baseline results, one as the specification's admission starts and one as the baseline runner's preparation starts, one as each case gets its baseline row, with its place, its id and its class, one before the list is resolved, and one as each mutation gets its row, with its place, its id and its status; a run prints them without the flag when stderr is a terminal; stdout is the document either way, and a cold `--full` run over many mutations can take minutes.
The rendering gives each case and each mutation its id, class or status, and the rules or killing cases; what to do next is in the JSON document: a rule's status (`rules[].status`: `fired`, `matched`, `unmatched`, `claim-helper`, `no-coverage-signal`, counted in `summary`; a guarded rule's `guard`, whose gaps the rendering lists as `[[guard]]`), a mutation's `witnesses`, `reason` and `action`, and each case's outcome on the mutant with its `cause` (`mutations[].executed[]`).
A rule in scope is one a run of concrete cases uses: a simplification (`krs.kind` `simplification`), a `symbolic` or a ceil equation can be `unmatched` and needs no case.
In a `check` document, each mutation that resolves gains `krs = {edits}`, and one whose source KRS's rule-level admission checks refuse (overlapping equations or rule heads, a nondet group, a priority after `owise`) also `siblings`.
`edits` holds one entry per edit, `{edit, label, item, judged, rust}`: the edit's index, its rule's label and KRS item, how krs judged it, and the Rust source it stands for, each `{file, line, column, end_line, end_column, text}` (with `end_line`, `end_column` and `text` null where only the item's position is known):

| `judged` | the edit | `rust` |
| --- | --- | --- |
| `authored` | changes syntax the author wrote, or a key cell KRS adds for the instance a rule is about, which is the key the authored pattern matches | the authored nodes it changes; for a key cell, the authored node that holds it |
| `inserted` | changes or cuts through a node KRS inserted on its own (a definedness test, a key guard, an implicit frame, a generated binder), so the row is refused as `generated-only` or `not-judged` | the authored node each inserted node comes from |
| `deleted` | removes its rule (`delete = true`) | the rule's item |
| `no-node` | changes no node of a rule's syntax: layout or comments only, a declaration, or tokens outside every rule sentence | the rule's item |
| `not-judged` | was not judged: an edit of the mutation edits another file than `definition.k`, the krs front end cannot read the emission, the edits do not apply to it, or the mutant kink-flow resolved differs from the emission with the same edits applied | the rule's item |

A mutation krs did not judge has a refusal of reason `not-judged`, whose `detail` says which cause it was, and each of its edits is `not-judged`, but a `delete = true` edit, which stays `deleted`; the refusal `not-judged` also follows an edit krs read but cannot yet tell a Rust source writes, whose `judged` is then `authored`, `inserted` or `no-node`, as the edit is.
`siblings` lists the renderings of each edited construct, `{label, item, rust, k, changed, named_by_krs}`, those of the sentences KRS's refusal names first; the refusal's `detail` lists the ones the mutation leaves unchanged, which an author's Rust edit of the construct would also change, and its `next` names them only when there are some.
A kill's `difference` in a `run` document is in the format of every KRS difference, `krs-difference/3`, as an unmet [expectation](#expectations)'s is: the first differing cell by Rust field path and each side's value as its canonical document, `left` the baseline's end and `right` the mutant's, compared on the cells kink compares (every cell but the unobservable ones, or those of `[result] cells`).
kink compares ends by their configuration alone, whichever way a path reached them, so a kill's difference compares no halt and its sides state no `class`; under `[stop]`, each of a program's `ends` says how the baseline's paths reached it (`halt`).
A [case document](#case-documents) of named cases gives one case per name, whose id is the document's path, `#` and the name (`cases/runs.toml#reset`); kink runs every case as the corpus says (`[stop]`, `stop_count`, `[budget]`), so a case's `run` is refused.
`[stop]` names its rules as `--stop-before` and `--stop-after` do, and its condition, `when = { function, cells, observer }`, as a case's `run.stop_when` does: `krs kink` resolves it as `krs run` does, in the observer package or else the definition itself, and refuses one `krs run` refuses at stage `stop`, reason `stop-condition-unresolved`; the condition is evaluated in that observer for the definition and every mutant, each evaluation with the default budget of `--view-budget`, so a case whose condition is undecided or has no value at an arrival is `unknown` (`stop-condition`), and every document's `stop` names the condition it resolved (`when`) and as the corpus wrote it (`krs.when`).
A case's `expect` is read as `krs run --case` reads it, a case whose expectation is no expectation of the definition is refused, and its row in `results`, `run` and `query` carries `expectation`: `met`, `unmet` with the first difference (`krs-difference/3`, `left` the expected end and `right` the baseline's), or `inconclusive` with why; `check` reads it from the case's stored result.
An expectation's [views](#expectations) are applied as `krs run --case` applies them, in the definition or in the observer the expectation names, which `krs kink` prepares and compiles once per command: a case whose observer cannot be prepared, whose view `krs run --case` refuses before the run, or whose view has no value at the expected end is refused (`expectation-value`), since each depends on the case alone; each evaluation has the default budget of `--view-budget`, and one that stops makes the expectation `inconclusive`; a view without a value at a baseline end, which refuses the case under `krs run --case`, makes it `inconclusive` with that refusal as its `detail`, since kink refuses no case after admission; and the `detail` of a verdict reached through the views names them.
A baseline that misses its own expectation is a finding about the definition against the reference the case was written from: it is reported, and the case is kept, since each of its kills is still a difference from the baseline, so no verdict or status depends on it; `results`, which asks whether each baseline meets its expectation, exits 1 for an unmet one and 3 for an inconclusive one.
Under `[stop]` an end kink keeps is stuck or stopped at a rule of the stop, and the ends do not say which, so the halt of an expectation of either is not observed: ends that differ from it on the compared cells make it unmet, and ends that agree on them inconclusive, since met is agreement on the halt as well (the expectation's `detail` says so); an expectation of another halt, which no end has, is unmet at the class; an expectation of an end stopped at a rule the corpus does not stop at is inconclusive, and one of a `depth-bound` end is refused, as everywhere.
Where that comparison shows no difference (it cannot read an end, for one), the evidence is kink-flow's own (`kink-k/1`: cells by K label, values as K text), with a `note` saying why.
`fuzz --matched RULE` and `fuzz --fired RULE` take the rule's label or a suffix of whole components of it (`plus_zero` for `nat--plus_zero`), as a mutation's `rule` anchor does.
A case's typed inputs are read by the encoding `run --case` reads, except `$text` and `$text-file`, which are K text and are written under the case's `variables` instead.
A case's program file binds the main parameter as `run FILE` binds it, whatever the parameter's K name, so `[[program]] files = "roms/*.gb"` with the other parameters under `inputs` is one case per ROM; inline `text` under a `Bytes` main parameter is refused, since a `Bytes` value has no text reading (`$hex` under `inputs` gives bytes inline).
A case's digest holds the SHA-256 of its program's bytes, whichever way they bind.

The selection options, those of the other commands and `--registration` (build tooling `krs --help` does not list), `--corpus` and `--locked` are krs's and may come before or after the verb, and so are the list flags that name a kink-flow operand (`run --mutations`, `query --patterns`, `fuzz --templates`); every other option is the kink-flow verb's own.
A usage error prints its message, the verb's usage line and the command that lists its options, not the whole help.
Every command that builds the package builds it in process, so `krs kink` takes no `--no-reuse`.
`krs kink` exits by the four actions of the other executing commands ([exit status](#exit-status)), as kink-flow does:
0 when the verb answered its question: every case is comparable and meets its expectation (`results`), every mutation has a verdict, killed, survived, equivalent or unkillable (`run`, and `report` as that run), every pattern has an answer (`query`), the fuzz found a witness or proved the mutant equivalent, every verdict is possible (`check`), `definition.k` is fresh (`emit`);
1 for a finding: a `--verify` mismatch, a `verdicts.lock` that `run --locked` would change, an unmet expectation (`results`), a refuted pattern claim (`query`), a case every baseline run of which kink excludes or a baseline without data (`check`);
2 when the question could not be asked: a usage error, a package `krs` refuses, a stale `definition.k` (`--locked`, `emit --check`), or a refused corpus, case, mutation list, lock, mutation, pattern or template, hole values the fuzz mostly rejected (`rejected-out`), a failed run or cache write, which the document names;
3 for no answer: a case or a mutation that timed out or is unknown, an inconclusive expectation, an `unknown` pattern answer, a fuzz that ended without a witness kink accepts.
A verb that answers for several cases or mutations exits as a batch does.
Under the Z3 solver profile, which `krs` builds kink with by default, `query` answers `no` only where the search received no undecided solver answer (a query Z3 did not decide within `smt_resource_limit` and its retries, or by its incompleteness), and the row's `cause` names that count, so the `no` rests on no answer the solver left undecided.
A pair whose search received an undecided answer is `unknown` (3), with the count in its `cause`, and a claim such a pair does not reach is `unconfirmed`, not refuted.
A package `krs` refuses, from an unknown package or facet to a failed emission, prints krs's diagnostics on stderr and exits 2: a kink-flow verb prints its document with its `spec` refused at stage `krs-build`, reason `krs-refused`, and `krs kink emit` prints its own document, whose `definition.status` is `null` and whose `refusal` says why.
`krs kink emit` prints `{schema, version, check, definition: {path, status}, refusal}`: `schema` `krs-kink-emit` and `version` 1, a bare schema name and an integer version as the kink-flow documents beside it have, unlike krs's own documents (`krs-compare/1`); `check` whether it was `--check`; `definition.path` the file as the package's directory shows it; and `definition.status`:
`unchanged` (the file is the emission; exit 0), `written` (it was not, and `emit` wrote it; exit 0), `stale` (it is not, and `--check` wrote nothing; exit 2, with `refusal` naming the command that writes it), or `null` (krs refused the package, or the file could not be read or written; exit 2, with `refusal` saying why).
`refusal` is non-null exactly when the command exits 2, so a caller tells a refused package from a stale file by `definition.status`.
`krs kink --help` lists the verbs, their usage lines, the corpus layout, the loop and the mutation format; `krs kink VERB --help` lists the verb's options, krs's and kink-flow's, each with what it does.

## Read failures by stage

- Rust/rust-analyzer errors cover ordinary syntax, imports, types, macro expansion, and some precisely authored attribute spans.
  A proc macro can report an error only as a message without a code, so in raw `cargo` and rust-analyzer output a KRS macro error carries its code in front of the message, as `[krs::syntax::invalid-color] message`; `krs` commands print the same error as `error[krs::syntax::invalid-color]: message`.
- KRS analysis errors cover definition-wide identities, sort and grammar consistency, rule shapes, and overlap.
- K frontend errors are translated through emitted source maps when an exact authored interval exists.
- native definition-check errors come from `check` and `build` and point at the authored item whose sentence the checker rejected.

Macro islands are not ordinary Rust expressions, so editor behavior is bounded.
The repository's compatibility probes establish exact rustc and rust-analyzer selection for authored syntax tokens and exact K/source-sidecar translation for covered cases; they do not promise IDE understanding of every generated symbol or every DSL token.
