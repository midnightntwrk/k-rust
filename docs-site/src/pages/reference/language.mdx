The `use` items at the top of a `k::rules!` or `k::claims!` block (`use Instruction::*;`, `use Value::{Integer, Undefined};`, as many as it needs) are Rust imports in the block's scope, and each import supplies the names it imports and nothing else.
Every path of a KRS term resolves as rustc resolves it at that place: through the block's `use` items, if any, and the enclosing module's, so a `use Instruction::*;` at the top of the module reaches every term position of every item in it, its tables, rule and equation fns, `cells!` rules, claims, and initializers alike.
A crate function, a constructor the module imports, or a builtin operation the module renames (`use k::builtin::map::update as set;`) is written bare, without `crate::`, and an imported variant wins over a crate item of the same name, as an inner glob import shadows an outer item in Rust.
The imports combine as Rust's do: an explicit `use Boxed::Load;` shadows the `Load` a glob brings in, and a name two globs both supply is ambiguous only where the block uses it, where rustc's error (`E0659`) names both imports.

Standalone constructors are structs annotated with `#[k::constructor(sort = ..., syntax = ...)]`.
Constructor families put `#[k::constructors(sort = ..., result = ...)]` (readable) or `#[k::constructors(sort = ..., reference)]` on an enum and attach syntax to its variants; every variant constructs `sort` itself, and the enum is not a sort.
A family whose productions need a sort of their own declares that sort in `k::sorts!`, for example `Freezer: KItem;` (every sort is a `KItem` anyway, [declared or not](#framework-and-builtin-sorts)), and names it with `sort = Freezer`.
The family form is preferred when a closed set of alternatives shares an open result sort; the standalone form remains useful for declarations owned independently.

## Helper attributes

`#[k::strict]` and `#[k::seqstrict]` add strict or left-to-right evaluation positions to constructor declarations.
Enum helper `#[k::precedence(...)]` names intra-family tiers, using explicit `left`, `right`, or `non_assoc` and leaving bare groups unconstrained.
A chain, when written, lists every variant exactly once (`krs::syntax::invalid-enum-precedence`).
It is required exactly when it could change a parse: when some variant's template begins or ends with a field whose sort admits the family's sort, that is, the sort itself, one of its supersorts in the whole definition, or `KItem` or `K`.
Such a field lets one of the family's productions sit directly at the edge of another, the only position its tiers constrain.
Without a chain the variants belong to no production group; a family that needs one and has none is `krs::analysis::missing-precedence-chain`, an error in every command that lowers the definition (`check`, `expand`, `emit-k`, `build`, and the run commands).
A variant's `group` comes from the chain, so it is rejected without one; a reference family names a `group` on every variant or on none.
Declaration order never supplies precedence.
Cross-family constraints are declarations: `k::precedence! { pair > atoms; }` and `k::associativity! { left: pair; non_associative: atoms; }`.
Enum helper `#[k::cons_list]`, written after `#[k::constructors(..)]`, declares the family's sort a [cons list](#list-notation), which bracket notation then builds.

Variant helpers include `#[k::syntax("...", group = "...", format = "...")]`, the equivalent separate `#[k::format("...")]`, and the `avoid` and `prefer` syntax flags.
`avoid` and `prefer` are one pair of parse-forest filters: where a program has several parses, K drops those whose top production is `avoid` or keeps those whose top production is `prefer`; an unambiguous program is unaffected, and they are not first-match ordering.
`#[k::syntax("if {condition} then {body}", prefer)]` resolves the dangling else so that `else` binds to the inner `if`; the reference layer and `#[k::constructor]` write `prefer = true`, and a production cannot take both flags.
`overload = Path` says that a production specialises another one with the same text: `#[k::syntax("{base}.{field}", overload = ExpSyntax::Dot)]` on `LValSyntax::Dot { base: LVal, field: Id }` makes `a.b` parse as the `LVal` access, the most specific production, instead of being ambiguous.
The key is written the same way in both layers and on `#[k::constructor]`; rustc resolves the path, and KRS checks that the target is a constructor production with the same arity whose result and argument sorts are each a supersort of the member's, at least one strictly.
Targets chain to one root, whose symbol is K's family key, and K's overload axioms make rewriting treat `expSyntaxDot(inj(L), F)` and `inj(lValSyntaxDot(L, F))` as equal, so `overload` is more than a parser hint; Rust itself has no overloading.
A production's K symbol depends only on its own declaration: a struct's is its name with a lowercase first letter (`Inc` is `inc`), and a variant's is its enum's name with a lowercase first letter followed by the variant name (`ExpSyntax::Dot` is `expSyntaxDot`, `Op::Add` is `opAdd`), whatever else the definition declares.
`#[k::symbol("path::Name")]` on a struct or a variant pins another one, the final path component with a lowercase first letter (`name`); a syntactic list's `Cons`/`Nil` symbols come from its enum and cannot be pinned.
Two productions that derive one symbol, such as `Op::Add` and a struct `OpAdd`, or a production whose symbol is one K generates itself, such as the sort predicate `isExp` or a cell's `initKCell`, are rejected with `krs::analysis::symbol-name-collision`; KRS never renames a symbol to make room for another.
A format is the syntax template plus K's layout codes `%n`, `%i`, and `%d`, the colour codes `%c` and `%r`, and `%%`; KRS emits each terminal by its position, so `while ({condition}) {body}` prints with `format(%1 %2%3%4 %5)`.
Colours belong to terminals: `color = "magenta"` paints every terminal, and `colors = ["blue", "blue"]` names one colour per printed terminal and one per `%c`, in printing order; `%r` resets.
`krun --color on` and `krs run --color always` print them; `kast --output program`, `kast --output pretty`, and `krun --output program` do not, and print an authored `%c` or `%r` as the letter `c` or `r`.
`#[k::function(total, memo, ...)]` gives a function K's `memo` hint, written as a bare flag after the totality in both layers: the Haskell backend may cache its results, while the LLVM backend and k-rust accept the hint and ignore it, so results never depend on it.
`#[k::function(total, fresh_generator, ...)]` makes a total function of one Int field K's `freshGenerator` of its result sort, the function a [fresh binder](#fresh-values) of that sort draws from.
`#[k::function(total, underspecified = "reason", ...)]` states that the function's equations leave some arguments without a value on purpose, which silences the [coverage lint](#coverage-of-total-functions); it is KRS-only, emits nothing to K, and is an error on a `partial` function (`krs::syntax::invalid-underspecified`).
Every configuration has exactly one `#[k::init]`, in an inherent `impl`: it is where the initial state is written, and no cell has a default value, since a cell's sort does not determine its initial content (a computation cell may start empty or with the program).
Without one, including when a `cfg` removes it, `krs check` reports `krs::expand::missing-initializer` at the struct.
The initializer's body is one `Self { .. }` struct literal that writes every cell, and a nested cell group's struct literal (inside `Some(..)` for an optional cell) writes every cell of the group; as in any Rust struct literal, the fields may be written in any order, and the configuration lists the cells in the order the structs declare them.
Initializer parameters may use `#[k::config_var(name = "PGM", main)]`.
A configuration variable is a value supplied at start, so the initializer may read it anywhere and more than once, as in `regs: k::map![Reg::A -> a, Reg::B -> b]`; each read is K's `$NAME:Sort`.
Its declared type is its parameter's type, element types included (`xs: List<Value>`, `sets: Map<Int, Set<Int>>`), and the initializer may place it anywhere that type fits ([typed collections](#typed-collections)).
An initializer's terms are KRS terms, written as in a rule result: constructors, positional (`Tag(v)`) or with every field named (`Tag { b: v }`), function calls, builtin operations, literals, and configuration variables, in a `k::k![..]` item, a `k::map![..]` key or value, or a call's argument, as in `k: k::k![pgm, StmtSyntax::Tag { b: bytes::empty() }, Init(n)]`; a function is evaluated when the configuration is built.
Since an initializer builds a term from its configuration variables and constants as a result builds one from a rule's binders, it holds what a result holds, each meaning there what it means in a result: a [`let` block](#local-bindings) (`{ let Pair(a, b) = p; Pair(b, a) }` emits `( #let pair ( A:Int , B:Int ) = $P:Exp #in pair ( B:Int , A:Int ) )`), a [`k::matches!` test](#shape-tests) (`( pair ( _ , _ ) :=K $P:Exp )`), `k::is!` and `k::project!` (`isInt($V:Val)`, `{$V:Val}:>Int`), and a turbofish on a [parametric constructor](#sort-parametric-productions) (`Wrap::<dyn ExpSort>(p)`); each is evaluated when the configuration is built, so `krs run -c 'P=pair(1, 2)'` starts from `pair(2, 1)` and `true` there.
A record update `Ctor { f: e, ..base }` is the record `base` with `f` replaced, where `base` is a configuration variable, a name a `let` binds, or a constant: no pattern matched it, so its other fields are read by the `let` that destructures it, `Pair { a: 5, ..p }` emitting `( #let pair ( _ , B:Int ) = $P:Exp #in pair ( 5 , B:Int ) )`, which is undefined where `p` is not a `Pair` record, as a refutable `let` is; a constant of another constructor is refused (`krs::analysis::invalid-record-update`).
An open record (`Ctor { f: e, .. }`) is not an initializer term (`krs::expand::initializer-record-update`): `..` leaves fields open, which only a pattern can, and an initializer builds every field. In a `k::matches!` pattern `name @ pattern` is refused, as in a result (K's right side holds no `#as`).
K reads each leaf cell's sort from its initial content, so a leaf cell's whole value is a term whose sort its head gives: a `let` block, `k::matches!` and `k::is!` are initializer terms below a cell's root, but not a leaf cell's whole value (`krs::syntax::unsupported-initializer-body`), since neither Java K's `kompile` (for `#let`) nor the native frontend (for `#let`, `:=K` and a generated sort predicate) reads a cell's sort from one; `k::project!` is the cast K reads one from, so `proj: k::project!(Int, v)` is a cell's whole value.
A cell's whole value written as a struct literal is a nested cell group's initializer, so a record constructor stands below a cell root, in a `k::k![..]` item, or in a `k::map![..]` entry.
rustc resolves every name in them; KRS checks the terms' sorts, a configuration variable's included, wherever it stands.
An initializer's `k::k![..]` lists its items and takes no remainder (`..pgm`, `krs::syntax::unsupported-initializer-body` at the remainder): a configuration variable of an item sort is written as an item, `k: k::k![Cmd::Go(), pgm]`.
A cell's whole `k::map![..]` has a [collection literal](#collection-literals)'s value, so of two keys that evaluate equal the later one wins (`map![a -> 1, b -> 2]` started with `$A` and `$B` equal is the map `a |-> 2`), and a rest is the map its entries are written over: `env: k::map![0 -> 1, ..env]` starts the cell from the configuration variable `env` with `0` mapped to `1`, `$ENV:Map [ 0 <- 1 ]`. How such a map is emitted is told [with the collection literals](#collection-literals).
Readable rule clauses can carry `#[k::rule(owise, label = "...")]` when they are an explicit fallback.

`#[k::requires]` guards rules, equations, and claims with a term of sort Bool, written as any term is: an operation or function application, a `k::matches!` test, a variable, or the literal `true`, the condition that always holds, or `false`, the one that never does; a term of another sort is a sort error at the term (`krs::analysis::invalid-term`), and the containing sentence decides whether a matching-logic predicate may stand there.

### Rule priority

K rules are unordered, and every rule has a priority, 50 by default; a rule is tried only after every rule with a lower number failed.
`#[k::rule(priority = N)]` sets a transition's priority and `#[k::equation(priority = N)]` an equation's, with `N` in `0..=254`, the range k-rust ranks.
`owise` is priority 200 on both (`#[k::rule(owise)]`, `#[k::equation(owise)]`), and the emitted `[priority(200)]` shows it; it is a lower band, not Rust's `_ =>` arm: several `owise` rules are unordered among themselves, and a guarded one can still fail.
A sentence takes `owise` or `priority = N`, not both.
`#[k::simplification(priority = N)]` is a hint to the simplifier and emits `simplification(N)`; `owise` has no meaning on a simplification, and an alias clause has no priority.
The standalone `#[k::priority(N)]` attribute is retired: KRS rejects it and names `#[k::equation(priority = N)]`.

### Intended nondeterminism

K does not forbid overlapping rules: when two rules can apply to one configuration, `krun` takes one and `krun --search` finds both.
KRS reports such a pair, because in Rust two arms matching one input are usually a mistake (`krs::analysis::overlapping-rule-heads`).
The check covers every transition: readable clauses, `#[k::rule]` functions (completed to the head of the computation cell), and `cells!` rules; equations are not checked.
Rules at different priorities never overlap, and two rules whose guards contain complementary conjuncts are separate: `g` and `bool::not(g)`, or an equality and its negation on the same operands (`int::eq` and `int::ne`, likewise for `bool`, `string`, `kequal` and `float`, and `bool::xor` against `bool::eq`), or an Int or String comparison and its converse-negation (`int::lt(a, b)` and `int::ge(a, b)`, `string::le(a, b)` and `string::gt(a, b)`).
So are two rules where unifying the patterns makes a guard false on literal operands: a rule on `0` and a rule on `x` with `int::ge(x, 10)` never apply to one configuration, because `0 >=Int 10` is false (K tutorial lesson 1.21); the same holds for a String comparison of two literals, a Bool guard the other rule binds to `false`, and `kequal::eq(v, Null())` when the other rule pins `v` to another constructor.
The Float orders are not complements, because a NaN operand makes both `a <Float b` and `a >=Float b` false.
Any other pair of guards is treated as possibly overlapping; KRS evaluates guards only on literals and constructor terms, and asks no solver.
Members of one `overload` family are one head, as K's overload axioms make them: a rule on `ExpSyntax::Dot` whose base is an `LVal` overlaps a rule on `LValSyntax::Dot`, while a rule on `ExpSyntax::Dot` whose base is an `Int` does not.
When the overlap is intended, put the rules in one group with `#[k::rule(nondet = toss)]`.
The key is check-only and emits nothing; a group needs at least two rules at one priority, and each of its rules must overlap another (`krs::analysis::nondet-group`).
Bare `#[k::strict]` is K's own evaluation-order nondeterminism and needs no key.

### Computation-cell patterns

A readable `for Machine` record matches the computation cell with a Rust slice pattern over K's sequence, read from its front, where the next step is.
`[p1, p2, ..]` matches a cell holding at least two items, the first matching `p1` and the second `p2`, and `..` keeps the rest; `[p1, p2]` matches a cell holding exactly those two items, and `[]` the empty computation `.K`.
`~>` is associative with unit `.K`, so a pattern that ends in `..` splits the sequence once, after its items: `store: { k: [v, Store { addr: a }, ..], acc: s } => { k: [..], acc: int::add(s, v) } where v: Int;` emits `<k> V:Int ~> store ( A:Int ) => .K ... </k>`, a finished value followed by the frame that consumes it, and `start: { k: [Run { n }] } => { k: [Boundary()] };` emits `<k> run ( N:Int ) => boundary </k>`, which applies only when nothing else is pending.
Each item is one `KItem`; a binder repeated across items is nonlinear matching, as inside one item.
An item may be [alternatives](#pattern-alternatives) without parentheses, `k: [Nop() | Halt(), ..]`, as in a Rust slice pattern.
The record is one configuration pattern, so a binder repeated across cells is nonlinear matching too: `load: { instrs: [Binary(ty, op), ..], valstack: [Integer(ty, r), Integer(ty, l), rest @ ..] } => ..` applies only where the instruction and both stacked values carry one type, and emits `Ty:IValType` at all three places.
The exception is the value binder of a [map entry](#rules-that-leave-the-computation-cell-out), which names what the entry maps to and must be a fresh name (`duplicate readable rule binding`); compare it with another term in `#[k::requires]` instead.
`where v: Int` is the sort test that makes `v` a finished value: without it `v` is any item, and the rule overlaps every rule on the item that would follow it.
The result has the pattern's shape: it ends in `..` exactly when the pattern does, since one `..` is the rest on both sides, so a pattern ending in `..` never drops the rest, and a whole-cell pattern has no rest to keep.
`..` may only end the pattern, because the cell is read from its front, and it is anonymous; `[..]` alone would match any computation and is rejected (leave `k` out to keep the cell unchanged).
Discarding the rest of the computation, or capturing it as a value, needs the `cells!` form.
There the remainder `tail @ ..` is a value of sort `K` the result may write, for instance in a `KSequence` field: `fn park(s: k::Term<List>, k::cells! { k: KCell(Park(), tail @ ..), stack: Cell(s), state @ .. }: Machine) -> Machine { k::cells! { k: KCell(Resume()), stack: Cell(list::concat(list::item(Saved { body: tail }), s)), ..state } }` emits `<k> park ~> Tail:K => resume </k>`.
A remainder the result does not put back with `..tail` has been moved, and the computation cell's new content is what the result lists; a bound remainder the rule neither puts back nor uses is an error.
A record whose result leaves `k` out only reads it, as for any [cell a rule only reads](#cells-a-rule-only-reads): `tick: { k: [Boundary(), ..], left: n } => { left: int::sub(n, 1) }` emits `<k> boundary ... </k>`, and so does a result that restates the matched items unchanged, `k: [Boundary(), ..]`.
`krs expand` writes the `cells!` entry `k: k::configuration::KCell(v, crate::Op::Store { addr: a }, tail @ ..)`, `KCell(crate::Op::Run { n })` for a whole cell, and `KCell(crate::Op::Boundary, ..)` for a read.

### List notation

Brackets build lists: K's builtin `List` and *cons lists*, object-language lists declared as a constructor pair.
An object-language stack or list is often a right-recursive constructor pair, an empty list and a cons whose second field is the list itself, and every access to it nests the cons: KEVM's word stack is `Stack::StackCons(a, Stack::StackCons(b, rest))`.
Such a sort is a cons list when it is declared one: every `#[k::syntax_list]` sort is, and so is the sort of a constructors enum marked `#[k::cons_list]`:

```rust
#[k::constructors(sort = WordStack, result = KResult)]
#[k::cons_list]
#[k::precedence((StackEmpty, StackCons))]
pub enum Stack {
    #[k::syntax(".WordStack")]
    StackEmpty(),
    #[k::syntax("{head} : {tail}")]
    StackCons { head: Int, tail: WordStack },
}
```

The enum has exactly one constructor with no field, the empty list, and one with two fields, the head and the tail, whose sort is the enum's own sort (`krs::syntax::invalid-cons-list` for the shape, `krs::analysis::invalid-cons-list` for the tail's sort); no other sort may be built by a second cons list.
The marker is opt-in, not inferred from the shape: a binary tree with a leaf, or a pair with a tail, has the same two constructors and should not read as a list.

Brackets read like Rust's slice pattern: the elements, and at most one rest `..`, anywhere; the elements before the rest are the list's front and those after it its back.
In a pattern the rest is `..` or `name @ ..`, and in a result `..term`, the list `term` spliced in:

| Position | Form | Cons list | Builtin `List` |
| --- | --- | --- | --- |
| both | `[]` | `Empty()` | `.List` |
| both | `[a, b]` | `Cons(a, Cons(b, Empty()))` | `ListItem(a) ListItem(b)` |
| pattern | `[a, b, rest @ ..]` | `Cons(a, Cons(b, rest))` | `ListItem(a) ListItem(b) rest` |
| pattern | `[a, ..]` | `Cons(a, _)` | `ListItem(a) _` |
| pattern | `[.., z]`, `[rest @ .., z]` | rejected | `_ ListItem(z)`, `rest ListItem(z)` |
| pattern | `[a, .., z]`, `[a, mid @ .., z]` | rejected | `ListItem(a) _ ListItem(z)`, `ListItem(a) mid ListItem(z)` |
| result | `[a, b, ..rest]` | `Cons(a, Cons(b, rest))` | `ListItem(a) ListItem(b) rest` |
| result | `[..rest, z]`, `[a, ..mid, z]` | rejected | `rest ListItem(z)`, `ListItem(a) mid ListItem(z)` |

The brackets are notation for those terms and nothing more: inference, the overlap and coverage checks, and the emitted K see the constructors, or `list::item(..)` and `list::concat(..)`, so for a cons list `[]` and `[_, ..]` cover the sort, a rule matching `[a, ..]` overlaps one matching `Stack::StackCons(a, _)`, and `[v, ..s]` at a `List` is `list::concat(list::item(v), s)`.
K's `List` concatenation is associative, with `.List` as its unit, so elements and one list term in a row have one meaning however they nest: a closed list is its items, `[a, b]` is `ListItem(a) ListItem(b)` with no trailing `.List`, and its elements are [typed](#typed-collections) by a `List<T>` cell they are written into.
The brackets do not name the list; the position's sort does, so they stand wherever a constructor field, a cell, a function parameter, or a result declares the builtin `List` or a cons-list sort: in a function body and its `match` (`[a, b, rest @ ..] => ..`), a `k::equations!` row, an equation result, a function argument, a `k::term!`, a `cells!` entry, a constructor field (`Store { at: [Deref(), ..] }`), and a claim.
A position whose sort is no list, or is not known, such as a `KItem` or an operator's operand, has nothing for them to denote (`krs::analysis::invalid-list-notation`).
Elements are ordinary terms: an element may be a [constant](#named-constants) (`[WORD, ..]`), use [operators](#operator-and-method-notation) (`[a + b, ..rest]`), or [update a matched record](#updating-a-matched-record) (`[Field { index: i + 1, ..f }, ..rest]`).
Rust has no spread in an array expression, so `[e1, ..rest]` in a result, where `..rest` would be a range, is KRS notation chosen for symmetry with the pattern; a range is no term anywhere else.

A bracket holds one rest, in patterns and results (`krs::syntax::invalid-list-notation` for a second): a pattern with fixed elements at both ends and one rest matches a list in at most one way, since the list's length fixes the rest's, but with two rests the elements between them could sit at several places, so the pattern would match some lists in several ways without saying which.
The same holds for an explicit pattern: `list::concat(left, list::concat(list::item(v), right))`, K's `Left ListItem(V) Right`, is rejected in a rule, equation, or simplification (`krs::analysis::ambiguous-list-pattern`).
Results keep the same rule for symmetry; join two lists with `list::concat(xs, ys)`, which says so.
`[..]`, which matches any list, is rejected (write `_`), and so are `[rest @ ..]` and `[..rest]`, which are `rest`.
A cons list is matched and built from its front, so its back is no constructor pattern: `[.., x]`, `[x, .., y]`, and a result `[..rest, x]` at a cons-list sort are `krs::analysis::invalid-list-notation`.
The builtin `List` has no such constructor, and its front and back are symmetric under concatenation, so a suffix is as primitive as a prefix.

In a readable `for Machine` record, a cell whose sort is a list reads a bracketed value as the computation cell does, so the common stack step names no rest:

```rust
add: { k: [Add(), ..], word_stack: [a, b, ..] } => { k: [..], word_stack: [Chop(a + b), ..] };
```

emits `<wordStack> A:Int : B:Int : Krs_RestWordStack:WordStack => chop ( A:Int +Int B:Int ) : Krs_RestWordStack:WordStack </wordStack>`.
`..` is one rest on both sides, as for `k`: the pattern holds `..` exactly when the result does, and the result's `..` keeps what the pattern's matched.
On a `List` cell it may stand anywhere on either side, so `queue: [a, ..] => queue: [.., a]` moves the front element to the back, and the computation cell keeps its front-only rule:

```rust
pop:  { k: [Pop(), ..], queue: [v, ..] }     => { k: [..], queue: [..], acc: v };
last: { k: [Last(), ..], queue: [.., v] }    => { k: [..], queue: [..], acc: v };
swap: { k: [Swap(), ..], queue: [a, .., z] } => { k: [..], queue: [z, .., a] };
log:  { k: [Log(e), ..], logs }              => { k: [..], logs: [..logs, e] };
```

`swap` emits `<queue> ListItem(A:Int) Krs_RestQueue:List ListItem(Z:Int) => ListItem(Z:Int) Krs_RestQueue:List ListItem(A:Int) </queue>`: these examples' `queue` is a `List<Int>`.
On a bare `List` an element is any `KItem`, as in K: `[_, ..] => [..]` drops the front element whatever it is, `[a, ..] => [.., a]` rotates whatever the list holds (`ListItem(A:KItem)`), and a binder that another occurrence sorts takes that sort (`[v, ..] => acc: v` with an `Int` cell `acc` emits `ListItem(V:Int)`).
A `KItem` chooses no operator, so `[a, .., z] => acc: a + z` on a bare `List` needs `where a: Int, z: Int` or a `List<Int>` cell (`krs::analysis::ambiguous-operator` names the binders and the narrowing).
The same holds for the keys and values of a bare `Map` and the elements of a bare `Set`, and a read such as `list::get(q, 0)` that no position sorts is a `KItem`.
A named rest, `[a, b, rest @ ..] => [b, a, ..rest]`, may be used elsewhere, and a result may also be one term, `[_, rest @ ..] => rest` or `s => [v, ..s]`.
A bracketed value reads by the cell's declared type: the computation cell reads items, a List collection instances, and a list cell elements.
The macro cannot see declared types, so it reads one bracketed value of a record as the computation cell's, a cell named `k` if there is one, and the collector moves that reading to the configuration's computation cell; a record may therefore name the stack first, `{ word_stack: [a, ..], k: [Pop(), ..] }`, and a configuration may call its computation cell anything.
`[]` alone on an ordinary leaf cell is that cell's empty list, a cons list's empty constructor or the builtin `List`'s `.List`, and on a List collection no instances.
A bracketed value on a cell that is none of the three is `krs::analysis::invalid-list-notation`, and a named rest or an element after the rest on the computation cell, whose rest is always anonymous and last, is rejected where the collector finds it.
`krs expand` writes a readable rule's lists as the terms they denote, `word_stack: k::configuration::Cell(crate::Stack::StackCons(a, crate::Stack::StackCons(b, rest)))` or `queue: k::configuration::Cell(k::builtin::list::concat(k::builtin::list::item(a), rest))`, with a parameter `rest` for an anonymous `..`, and a rule or equation subject's brackets the same way; the reference layer accepts the notation too, so a fn body keeps it as written.

### Cells a rule only reads

A readable `for Machine` record matches cells on the left and writes cells on the right; a cell the pattern matches and the result leaves out is only read, and keeps its content.
`store: { k: [Store(r), ..], z: v, regs: m } => { k: [..], regs: map::update(m, r, v) }` reads `z` to bind `v` and emits `<z> V:Int </z>` with no rewrite inside, the K reading of a cell the rule names without changing it.
`krs expand` writes it as a `cells!` subject entry with no result entry, `z: k::configuration::Cell(v)`; a pattern that constrains the content, such as `z: 0`, is read the same way, and the rule applies only where it matches.
Writing the cell back unchanged, `z: v` on both sides, denotes the same rule and emits the same read, so the result names only the cells the rule changes; a nested group entry (`frame: f`) and an ordinary leaf read alike.
`z: _` left out of the result constrains and binds nothing, so the rule would be the same without it; it is a syntax error that asks for the entry to be removed.

An entry that is only a cell name is Rust's field-init shorthand: `pc` means `pc: pc`, in the subject and in the result.
`jump: { k: [Jump(), ..], pc } => { k: [..], pc: int::add(pc, 10) }` binds the content of `pc` to the binder `pc`, and a result entry `gas` writes the binder `gas` into the cell `gas`, which the subject must bind, as any result term's binders; a raw identifier binds itself (`r#type` is `r#type: r#type`).
The shorthand is a spelling of the long entry and nothing more: a group cell's `frame` binds the whole nested cell, `{ gas } => { gas }` is a read, `k` alone is `k: k` (a binder over the whole computation cell, which a readable record rejects; match its items with `k: [..]`), and an optional or collection cell's result still restates its `Some`/`None` or instance list.
`krs expand` writes the long entries.

### Rules that leave the computation cell out

A K rule names only the cells it needs, and that includes `<k>`.
A readable `for Machine` record may leave the computation cell out: `burn: { fuel: f, acc: a } => { fuel: int::sub(f, 1), acc: int::add(a, f) }` under `#[k::requires(int::gt(f, 0))]` emits `rule [burn]: <fuel> F:Int => F:Int -Int 1 </fuel> <acc> A:Int => A:Int +Int F:Int </acc> requires F:Int >Int 0`, with no `<k>`.
The omitted computation cell is framed like every omitted cell, so the rule fires whenever its cells match, interleaved with the program; a Rust reader expects a struct pattern without `..` to be exhaustive, but here omission means untouched.
`krs expand` writes the reference `cells!` rule without a `KCell` entry or tail.
Such a rule is rejected when it changes no cell, for instance when it only reads (`krs::analysis::rule-changes-no-cell`), and when every cell pattern is a variable or `_` of the cell's sort and it has no guard, because it is then always enabled and execution never terminates (`krs::analysis::always-enabled-rule`).
The overlap check treats two rules that share no cell as independent, because they commute; rules that share cells are compared on those cells only.

A readable record reads entries of a Map cell with `env: { name -> value, .. }`: `value` binds what the entry maps to, and the cell is left unchanged, so the result record does not restate `env`.
The key is what the map is looked up by, and it reads by what stands at its root.
A key name the subject binds elsewhere looks its entry up, so the rule applies only where that key is present: `var: { k: [name, ..], env: { name -> value, .. } } => { k: [value, ..] }`.
A key name that nothing else in the subject binds matches the key of any entry and binds it, so the rule applies once per entry, a nondeterministic choice that `krs search` shows as one solution per entry: `pick: { k: [Pick(), ..], threads: { tid -> t, .. } } => ..` emits `<threads> Tid |-> T ... </threads>`, and a `Map<K, V>` cell gives `tid` the type `K`.
A key that applies a function, `env: { Size(n) -> v, .. }`, is evaluated and looked up, so a name below the application reads the value the rest of the subject gives it and binds nothing: with `n` bound nowhere else the rule reads a value nothing gave, and `n` is `krs::expand::unbound-name` at the name, in a `cells!` `map![..]` key alike.
Every construct that computes reads the same way, since the key is the value it computes: an operator or a method (`env: { n + 1 -> v, .. }`), a sort test, and a record update; the positions below it are built, so `_`, an alias, alternatives and an open record `Ctor { .. }` there are refused as in a result, and its names must be bound elsewhere in the subject.
The whole key is computed only when nothing in it outside those constructs selects an entry: a name the rest of the subject does not bind, `_`, an alias, alternatives or an open record makes the key a selection, matched against the map's evaluated keys, and a function application anywhere in such a key never matches, so `env: { Pair { a: Size(n), b: y } -> v, .. }` with `y` bound nowhere else is `krs::analysis::function-in-pattern`.
A computed key's names may be bound in any order a match can follow: outside the keys, by a key that selects, or by the value of an entry found before it, so `env: { x -> v, Size(v) -> w, .. }` selects an entry, then looks `size(v)` up, also across map cells and among a set's elements; keys that read each other's values, `{ Size(v) -> v, .. }` or `{ Size(y) -> x, Size(x) -> y, .. }`, follow no order of lookups, and are refused as a selection holding a function (`krs::analysis::function-in-pattern`).
A `cells!` `map![..]` key reads alike, operators included.
No key in a pattern, readable or `cells!`, holds a `let` block or `k::matches!` (`krs::expand::let-outside-term`, `krs::expand::matches-outside-condition`): the key would compute its value, but K's `#let` and `:=K` bind their patterns' names, and in a rule's left side those names would read as the rule's pattern variables.
`{ _ -> value, .. }` reads the value of any entry without naming its key.
It may read several, `regs: { a -> x, b -> y, .. }`, which is K's `<regs> A |-> X B |-> Y ... </regs>` and the `cells!` entry `regs: k::configuration::Cell(map![a -> x, b -> y, ..])`.
Each item is a different entry of the map, so the pattern matches only where the keys differ: with `a` and `b` bound to one key, the rule does not apply.
Two keys written as the same term could never differ, so `{ a -> x, a -> y, .. }` is a syntax error, and so is the pattern `map![a -> x, a -> y, ..]` in a `cells!` entry; read one entry and bind its value once instead.
Two `_` keys are two distinct entries: `{ _ -> x, _ -> y, .. }` matches a map with at least two.
Inside a `cells!` entry, `k::map![..]` is the same map as `map![..]`, as it is in an initializer.

A leaf cell of a builtin collection sort is emptied, or matched only when empty, with the term for the empty collection: `functions: map::empty()`, `seen: set::empty()`, and `stack: []` (or `list::empty()`) are K's `.Map`, `.Set`, and `.List`, on either side of a readable rule or claim and in every other term.
A claim that starts from empty maps therefore writes `functions: map::empty()` where the reference spelling writes `functions: k::configuration::Cell(map![.Map])`, and both emit `<functions> .Map </functions>`.
A `cells!` entry's and an initializer cell's whole `map![..]` is that cell's own map, where `map![]` and `map![.Map]` are the empty map. Where the map is matched, in a `cells!` subject and a claim's start state, its items are distinct entries of the map and `map![k -> v, ..]` leaves the rest unread; where it is built, in a `cells!` result, a claim's end state and an initializer, it has a [collection literal](#collection-literals)'s value, each entry written over the map before it (the empty map, the rest a framed subject leaves, or a map `..m` the subject binds whole), so the later of two equal keys wins, as in a readable result; a framed result writes only at keys its subject matched. Everywhere else, a readable record included, `map![..]` and `set![..]` are collection literals, the calls that build the collection, so `functions: map![]` is `map::empty()`.
Braces on a leaf cell are no empty map: `{ .. }` names a Set or Map collection's instances, and `cell: { k -> v, .. }` reads a Map's entries.

A leaf cell holds any term of its declared sort or of a subsort, on either side of a readable rule or claim and in a `cells!` rule, as an argument position does: with `Value: Stmt` and `impl Value for Int`, `acc: 2` fills a `Value` cell, `acc: vv` still matches one where a guard (`#[k::requires(vv == 1)]`) or an operator (`acc: vv + 10`) narrows `vv` to `Int`, `prog: Unit()` fills a `Stmt` cell with a `Value`, and a `KItem` cell holds a term of any sort.
A term of a sort that is not below the cell's is refused at the term.
An initializer leaf is the exception: the configuration gives a cell the sort of its initial content, so an initializer fills a leaf cell with a term of exactly its sort (a configuration variable of the cell's type, or a term of that sort), and `prog: ValueSyntax::Unit()` would declare a `Value` cell where the field says `Stmt`.

### Whole nested-cell variables

A nested cell is a value too: K gives `<frame>` the generated sort `FrameCell` (the cell name capitalised, hyphens removed, then `Cell`), so one variable captures the whole cell, as KEVM saves `<callState>` on its call stack.
In a readable record, `frame: f` binds the nested cell itself, not a Rust copy of its fields: `push: { k: [Push(), ..], stack: s, frame: f } => { k: [..], stack: [f, ..s] }` emits `<stack> S:List => ListItem(F:FrameCell) S:List </stack> F:FrameCell`, and `pop` restores a saved frame with `frame: _` in the pattern and `frame: f` in the result, emitted as `(_:FrameCell => F:FrameCell)`.
The group clause is written bare, never inside `<frame>...</frame>`, and a group the rule names covers every cell inside it.
As in K, every generated cell sort is a subsort of `KItem`, like [every sort but `K`](#framework-and-builtin-sorts), so the binder may also fill a `KItem` field of a user production: with `Held { saved: k::KItem }`, `stack: [Held { saved: f }, ..s]` emits `ListItem(held ( F:FrameCell ))`.
A nested entry is a group binder, `_` (patterns only), or a complete group term; in the reference spelling `krs expand` writes, it has no `Cell(..)` wrapper, because it mirrors the expanded struct, and the binder is typed by the nested `#[k::cell]` struct (`f: crate::Frame`).
Inside a group record, a group child may likewise be a binder or `_`: with `outer` holding the `frame` group, `outer: Outer { frame: fr, .. }` binds the `<frame>` cell as `Fr:FrameCell`, and a result `outer: Outer { frame: fr, flag: x }` writes it back; an alias over a group child, `frame: fr @ Frame { pc: p, .. }`, names the matched child, and a use of it is that child [rebuilt from its children](#pattern-aliases).
A readable record writes the group term as a record of the nested struct: `jump: { k: [Jump(), ..], frame: Frame { pc: p, gas: g } } => { k: [..], frame: Frame { pc: int::add(p, 10), gas: g } }` emits `(<frame> <pc> P:Int </pc> <gas> G:Int </gas> </frame> => <frame> <pc> P:Int +Int 10 </pc> <gas> G:Int </gas> </frame>)`, and `krs expand` writes the entry as `k::fragment![crate::Frame { pc: p, gas: g }]`, the spelling `cells!` entries and terms such as `list::item(..)` use.
rustc resolves the record's path with the block's `use Cmd::*` in scope, as it resolves every unqualified path in the block, and the record is the whole cell when the path names a `#[k::cell]` struct, so a `Cmd` variant of the same name wins, as in Rust, and `crate::Frame { .. }` names the struct; `Some(Mark { seen: s })` names an optional group the same way.
At a configuration cell's own position (the value of the entry that names the group, and each group child of a record there), the subject's record matches the running configuration's cell, so it leaves the children it does not name unconstrained, with or without `..`: `frame: Frame { pc: p }` and `frame: Frame { pc: p, .. }` both emit `<frame> <pc> P:Int </pc> <gas> _ </gas> </frame>`, and with `outer` holding the `frame` group, `outer: Outer { frame: Frame { pc: p }, flag: f }` leaves `<gas>` unconstrained the same way, since that record is the configuration's `<frame>` reached through `outer`.
Anywhere else, a group record is the group's cell term, a value of its cell sort like any constructor term: in a list element (`stack: [saved @ Frame { pc: p, .. }, rest @ ..]`), a constructor argument (`Held { saved: Frame { pc: p, gas: g } }`), the content of a leaf cell (`slot: Frame { pc: p, .. }` in a `KItem` cell), a group nested in such a value, an alias target, or a result.
It means exactly `k::fragment![Frame { .. }]` there, which may also be written in each of those places, and as a value it is complete: a pattern ends in `..` to leave the children it does not name unconstrained, and without `..` names every child (`krs::analysis::invalid-term` otherwise).
`k::fragment!` is exact at every position: it names every child or ends in `..`.
A record pattern may name no field at all, as in Rust: `Projection::DerefTruncate { .. }` or `frame: Frame { .. }` matches that constructor or group whatever its fields hold, and is the pattern that writes each field `_` (`krs expand` writes `DerefTruncate(_)`), in readable rules and claims, `k::equations!` rows, and the subjects of `#[k::rule]`, `#[k::equation]`, and `#[k::simplification]` fns, with or without `k::term![..]`; `Ctor()` and `Ctor {}` still name every field, so they are rejected for a constructor that has fields.
A result group record names every child, or [updates a matched group](#updating-a-matched-record).
Any other nested entry, such as `frame: 3`, is a syntax error, and a leaf entry still needs its `Cell(..)` or `KCell(..)` wrapper.
A rule that names a group and a cell inside it is rejected (`krs::analysis::group-and-descendant`), and so is a configuration in which one `#[k::cell]` struct is the content of two fields, because its K cell sort would name two cells (`krs::analysis::ambiguous-cell-sort`).
A repeated (`*`) cell is a collection, not one nested cell: its entry is an instance list, described in [optional cells and cell collections](#optional-cells-and-cell-collections).
The overlap check counts a group clause as sharing every cell inside the group.

### Optional cells and cell collections

K has two cell multiplicities besides "exactly once": `?`, a cell that may be absent, and `*`, a collection of cell instances.
KRS spells `?` as Rust's `Option`: `#[k::cell(multiplicity = "?")] pub counter: Option<Int>` is K's `<counter multiplicity="?">`, and `Option<Mark>` with `nested` is an optional group.
The initializer still writes a template, `counter: Some(0)`, because K needs one to know what a created cell looks like; the cell starts absent unless the field says `initial` (K's `initial=""`).
`None` in an initializer is a syntax error, and so are an `Option` field without `multiplicity = "?"` and a `?` field that is not an `Option`.
In a rule, `counter: None` matches or writes an absent cell and `counter: Some(p)` a present one, so `enable: { k: [Enable(), ..], counter: None } => { k: [..], counter: Some(0) }` creates the counter, emitted `(.Bag => <counter> 0 </counter>)`, `counter: Some(n) => counter: Some(int::add(n, 1))` updates it in place, and `Some(_)` to `None` deletes it, `(<counter> _ </counter> => .Bag)`.
A result that leaves the cell out leaves it as it was, as for every omitted cell; the reference spelling wraps the content, `counter: Some(k::configuration::Cell(n))`.

A collection is a `multiplicity = "*"` field of a `#[k::cell]` struct type with `nested` and a `cell_type`: `"Set"`, `"Map"` (keyed by the instance's first child), or `"List"`.
K requires the collection to be its parent's only child, so the field gets a parent struct of its own (`krs::analysis::collection-siblings`), and the initializer's value is the template of one instance; with `initial`, that instance exists at start, as K's first thread does in lesson 1.17-B.
Cell bags are refused, because K's LLVM and Haskell backends do not support them.
A rule names instances by record, in braces for a Set or Map and in brackets for a List, with `..` for the instances it does not name:

```rust
spawn: {
    thread: { me @ Thread { k: [Spawn(body), ..], .. }, .. },
    next_id: n,
} => {
    thread: { Thread { k: [n, ..], .. me }, Thread { id: n, k: [body], .. }, .. },
    next_id: int::add(n, 1),
};
```

A pattern record matches one instance (`..` inside it leaves its other children untouched), and `me @` labels it.
A Set collection is a set of its instances, so a pattern looks it up by an instance as it looks a set up by an element (`seen: set![n + 1]` emits `SetItem(N:Int +Int 1)`): an instance whose every cell is written, with no `..` in it, and which holds no name nothing else binds, `_`, alias, alternatives or open record, is computed from the names the rest of the subject binds, a function's application, an operator, a method or a sort test included, and the rule applies when the collection holds exactly that instance.
Its names may be bound by the subject outside the collection, by another instance that is matched, or by the value of an entry a key finds (in a `cells!` rule, since a readable map read's value binder stays fresh), in an order of lookups as for [map keys](#functions-in-patterns); a name bound nowhere is `krs::expand::unbound-name`, and names no order binds are a cycle (`krs::analysis::function-in-pattern`).
K writes an instance as the cells it holds, where neither K frontend reads a function, so KRS writes each construct a computed instance computes as a fresh variable and equates it with the value in the rule's condition, ahead of the author's `requires`; a set holds an instance once, so this is the lookup of one instance, the same rule:

```rust
probe: {
    k: [Probe(n), ..],
    obj: { Obj { oid: n + 1, hits: 0 }, .. },
} => { k: [..] };
```

emits `<obj> <oid> Krs_Instance0:Int </oid> <hits> 0 </hits> </obj>` with `requires Krs_Instance0:Int ==K (N:Int +Int 1)`: `probe 2` applies when an object `{ oid: 3, hits: 0 }` exists, and is stuck when none does or the object with id 3 has other hits.
A cell of a computed instance may hold an exact `map![..]` or `set![..]`, part of the value looked up; a map cell with `..` leaves entries open.
A label on a computed instance names it for the result as on any other, and a claim's state holds the instance as written, its applications standing for their values: a claim reads its instances' cells as any pattern, so it spells an operation there as its call, as elsewhere in its state.
An instance that leaves cells open or holds a name nothing else binds selects one by matching, and is matched as it stands, so a function there never matches (`krs::analysis::function-in-pattern`).
A Map collection's instances are written in the same braces, and only the cell's declared type tells the two apart, so a rule's braced instance's cells, a readable record's or a `cells!` instance record's (`k::fragment![..]` alike), are read as a key is (a pattern, or the term an expression denotes, `n + 1` the call `int::add(n, 1)`); in a Map collection's instance, which is matched, an operator is then refused as a function (`krs::analysis::function-in-pattern`), a sort test as `krs::analysis::invalid-sort-test`, and a record update as `krs::syntax::invalid-record-update`, or first, when its base is no alias of a matched record, as `krs::analysis::invalid-record-update`.
In the result, a record ending in `..me` updates the labelled instance in place, a record without a label's rest creates an instance (its `..` takes the template defaults, K's right-hand `...`), and a pattern instance the result does not mention is removed; `..ghost` naming no labelled instance is rejected (`krs::analysis::unknown-instance-label`).
A created Map instance states its key, the first child (`krs::analysis::map-collection-key`), and every child a created instance omits needs a template default.
An entry without `..`, such as `obj: { o @ Obj { oid: n, .. } }`, names every instance: it applies only when exactly one exists, and KRS writes it inside the parent cell.
A List is positional: `job: [Job { payload: p, .. }, ..]` matches the front instance, `[.., Job { payload: p, .. }]` the back one, and `[.., Job { payload: v, .. }]` in a result appends at the back, which KRS emits after a leading `_Instances1:Bag` because K closes a cell on the right.
A List rule changes either the front or the back, not both, and does not reorder matched instances (`krs::analysis::collection-entry`).
A bracketed value reads by the cell's declared type, so `[Job { payload: p }, ..]` is the front instance of the List collection `job` and `[Enqueue { value: v }, ..]` the head of the computation cell `k`: `retire: { job: [Job { payload: 0 }, ..] } => { job: [..] }` removes a front job whose payload is 0 and emits `(<job> <payload> 0 </payload> </job> => .Bag) ...` inside `<queue>`.
A bracketed value thus has up to four readings, the computation cell's head, a List collection's instances, a cons list's elements, and a builtin `List`'s elements, and the cell's declared type picks one: `[.., Job { payload: p }]` is the back instance of the collection `job` and, on a `List` cell, the list whose last element is the constructor `Job { payload: p }`.
A value that reads only one way is read that way: a record with a shorthand field, `[.., Job { payload, .. }]`, reads only as elements, and `[Push(), ..]` or `[x, ..]` reads as a head or as elements; a rule has one computation cell, so when one cell's value reads only as a head, every other bracketed value is a collection or a list.
The reference spelling `krs expand` prints writes the entry with the collection path, `Threads::thread: { me @ k::fragment![crate::Thread { .. }], instances0 @ .. }`, and the result `..instances0`.
A `?` or `*` cell whose template reads a configuration variable starts present, since the variable's input has to land in it, so the cell must say `initial`; without it the cell is rejected (`krs::analysis::collection-config-var-without-initial`), and every such cell is reported.
Optional and collection entries are not allowed in a context alias or an equation's function context, which read fixed cells only (`krs::expand::cell-collection-placement`).

### Typed binders

In a K pattern, `X:Int` is a runtime test: the rule matches only when the term bound to `X` has sort `Int`.
In KRS it is the binder's declared type: `where x: Int` after a readable clause, a typed parameter before the subject of a rule fn, or an entry of a `cells!` rule's binder list.
The three are one declaration: the binder has exactly that sort, and the emitted K is `X:Int`.
A rule fn's subject is a pattern, so it needs no wrapper: `fn unwrap(Wrap { value: v }: Term<Exp>)` is `fn unwrap(k::term![Wrap { value: v }]: Term<Exp>)`, compiler-owned islands below its root included; `krs expand` and this reference write the `k::term![..]` spelling.
The wrapper changes nothing at the root either: a subject's root is the constructor or function the sentence matches, so `_` and a compiler-owned island stand below it, with or without `k::term![..]`, in each alternative of a root `A | B` too (`krs::syntax::unsupported-rule-pattern`), as does an alias ([pattern aliases](#pattern-aliases)).
A rule for any term of a sort is a `for Sort` clause, whose root is either the constructor it matches or the whole subject: a bare name binds it, `_` is it unnamed, and an alias or an island stands there as below a constructor, so `for Stmt; skip: _ => Cmd::Done();` emits `<k> _:Stmt => done ... </k>` and `for Stmt; show: s => Cmd::Show { c: s };` emits `<k> S:Stmt => show ( S:Stmt ) ... </k>`.
The clause's optional `k::term![..]` reads its root the same way, and parentheses denote nothing: `k::term![s]`, `(_)` and `k::term![s @ Cmd::Red()]` are `s`, `_` and `s @ Cmd::Red()`.
A rule fn's whole subject is its parameter, which already names the subject, so a fn rule refuses `_`, an alias or an island there and its error shows the clause to write instead, with the fn's rule attribute, helpers and result (``= help: a rule for any term of a sort is a `for Sort` clause, ..: `k::rules! { for Stmt; #[k::rule(label = "warm", owise)] warm: _ => 1; }` ``), since an `owise` rule for any term that lost its `owise` would apply to every term first.
An `anywhere` rule rewrites the application its subject's root names wherever it occurs, so no form writes one for any term of a sort, and its refusal says so; an equation, a simplification, a context and a static clause get no help either, since their root is what they are written for: the function's application, the context's shape, the production they expand.
`fn unwrap(k::term![Wrap { value: v }]: Term<Exp>) -> Term<Exp> { v }` infers `v` at the sort of `Wrap`'s field, emits `rule wrap(V:Exp) => V:Exp`, and matches every expression; `fn unwrap(v: Term<Int>, k::term![Wrap { value: v }]: Term<Exp>) -> Term<Exp> { v }` emits `rule wrap(V:Int) => V:Int`, so `wrap(1 + 2)` no longer matches.
A declared sort may be narrower than inference would choose, never wider or unrelated: a binder declared `Bool` in an `Exp` position is rejected (`krs::analysis::incompatible-binder`, "binder `x` is declared `Bool`, but an occurrence needs `Exp`", with a label at the occurrence).
Every occurrence must admit the declared sort, in the pattern, the result, a condition, or a collection read alike; a `where` on a value read from a typed map names the value type or a sort below it.
A binder without a declaration is inferred as the most specific sort its occurrences share.
An unrelated declaration is rejected even when some terms have both sorts: with `Value: Stmt + Exp`, `where s: Stmt` on the binder of an `Exp` field names a sort the rule does not test, and the error's help names the declaration that does, `where s: Value`; a wider one, `where s: KItem` there, states more than the rule tests, and the help names `Exp`.
A `KItem` occurrence never narrows a binder, because every sort but `K` is a `KItem`: with `Hold { saved: k::KItem }`, `{ k: [Hold { saved: s }, ..] } => { k: [s, ..] } where s: Stmt` emits `hold ( S:Stmt ) => S:Stmt`, a binder that also occurs in a `Stmt` field is a `Stmt`, and one that occurs only at `KItem` positions is a `KItem`.
A `_`-prefixed single-use binder keeps its name, so `fn is_expression_exp(_e: Exp, k::term![IsExpression(_e)]: Term<Bool>) -> Term<Bool>` emits `rule isExpression(_E:Exp) => true`.

The binder list is all or nothing.
A rule fn whose subject is a term pattern either declares no binders, and every sort is inferred, or declares every subject binder exactly once, in the order the binders first occur in the subject; a `cells!` rule always declares all of them.
`_`, remainders such as `tail @ ..`, and the `here` binder of a context alias are not declared.
A remainder is still a binder of the rule: a result, `#[k::requires]`, and `#[k::ensures]` may name a computation remainder, a `K`, and a map remainder, a map of its cell's type (`#[k::requires(k::is!(KResult, tail))]` emits `requires isKResult(Tail:K)`).
A map remainder written as a value must still be put back with `..rest`: a rule cannot move one out of its cell yet.
The configuration remainder `state @ ..` and a collection's remaining instances stand for cells the rule leaves out and are not terms, so a condition that names one is an error (`krs::syntax::unsupported-rule-body`).
Narrowing one binder therefore means declaring all of them, each other one at its inferred sort; `krs expand` writes a readable rule's `where` the same way.
A partial or misordered list, a binder declared twice, and a declared binder the subject never binds are syntax errors.
KRS has no strict cast `::S` or `{T}<:S`: rule bodies are resolved Rust paths, never parsed by K, so there is nothing to disambiguate; `k::project!` is the cast a rule computes with.

### Typed collections

A cell declared `env: Map<Id, Value>` says what every reachable configuration holds there: each key of the map is an `Id` and each value a `Value`.
K's collections hold `KItem`s, so K neither states nor checks that; KRS checks it, and the element types are erased from the emitted K.
A collection type is `Map<K, V>`, `List<T>`, or `Set<T>`; each argument is a sort, `k::Term<S>` or `k::Term<dyn S>` (read as `S`), or a collection type itself, as in KEVM's `accessed_storage: Map<Int, Set<Int>>`.
A cell, a constructor field, and a function parameter or result take a collection type: `Body { blocks: List<BasicBlock> }`, `fn MarkAccountAccess(accessed: k::Term<Set<Int>>, account: k::Term<Int>) -> k::Term<Set<Int>>`, and in the long form `#[k::function(sort = Set<Int>, ..)]`.
A bare `Map`, `List`, or `Set` is untyped and accepts every write, and its keys, values, and elements are `KItem`s; `Map<Id>`, one argument where a map takes two, is an error, as is an element type that is neither a sort nor a collection type (`krs::syntax::invalid-collection-argument`).

The check is an induction over transitions: if the initializer fits the declared types and every rule writes only fitting terms, assuming every binder matched at a typed position has that position's type, then every reachable configuration fits.
So a pattern gives types and a written term is checked:

- A binder matched at a typed position takes its type: `env: e` gives `e` the type `Map<Id, Value>`, as do the rest of a typed `map![..]` pattern, a typed child of a group or collection instance, a typed field of a constructor pattern (`StackFrame { locals, .. }`), a typed parameter in an equation's subject, and a value read from a typed map (`nested: { name -> s, .. }` gives `s` the type `Set<Int>`).
  The binder's declared sort, `k::Term<Map>` in a `cells!` rule, names only the sort, which is why `krs expand`'s reference rules check exactly as the readable ones do.
- A key, value, or element written into a typed collection (the `k` and `v` of `map::update(m, k, v)`, the `x` of `list::item(x)` or `set::item(x)`, an element of [list brackets](#list-notation) `[x, ..rest]`, an entry of `map![..]` or `k::map![..]`) is inferred at the element sort, like any other occurrence: a binder used there and nowhere narrower gets that sort, and one whose other occurrences share no sort with it is an error.
- A collection written into a typed position must fit it. Collections are values, so every argument is covariant: a `Map<Id, Int>` fits `Map<Id, Value>` because `Int` is a `Value`, `.Map`, `.List`, and `.Set` fit every type, and a `Map<Id, Value>` does not fit `Map<Id, Int>`.
- A read has the element sort: `map::get(e, name)` is a `Value`, projected to the sort its position expects, or a `Value` where no position expects a sort, so `map::get(locals, name) + 1` over a `Map<Id, Int>` is `Int` addition. A read that asks for a sort the collection never holds is an error: `map::get(e, name)` where a `Stmt` is expected, `where v: Stmt` on a value read from `env`, or `map::in_keys(n, e)` with an `Int` key; a probe that is not a binder is checked at its final sort, so `set::contains(k::bytes!(b"a"), seen)` over a `Set<Id>` and `map::remove(e, 1 + 2)` are errors too.

Every term written at an element position is checked, whatever its kind: a constant such as `k::id!("$x")` or `k::bytes!(..)`, a `k::anonymous!` value, an operator expression (`1 == 2` is a `Bool`), a sort test, or a constructor, and the error names the term, its sort, and the position (`krs::analysis::collection-element-sort`).
Every write path is checked: readable rule and claim results, claim left-hand sides, `cells!` rules, single-body rewrites, group and collection-instance records, `k::fragment!` terms, initializer values, the arguments of typed constructor fields and function parameters, and a typed function's equation results.
The operations type as their K meaning says:

| Operation | Operands | Result |
| --- | --- | --- |
| `map::empty()`, `list::empty()`, `set::empty()` | | fits every type |
| `map::update(m, k, v)`, `map::update_all(m, n)` | the maps at the position's type, `k` at `K`, `v` at `V` | the position's type |
| `map::remove(m, k)`, `map::remove_all(m, s)` | `m` at the position's type, `k` read at `K` | the position's type |
| `map::get(m, k)`, `map::get_or_default(m, k, d)` | `k` read at `K`, `d` at `V` | `V` |
| `map::in_keys(k, m)` | `k` read at `K` | `Bool` |
| `map::keys`, `keys_list`, `values` | | `Set<K>`, `List<K>`, `List<V>` |
| `list::item(x)`, `list::make(n, x)`, `list::update(l, i, x)`, brackets `[x, ..l]` | `x` at `T`, `l` at the position's type | the position's type |
| `list::concat`, `list::range`, `list::update_all` | the lists at the position's type | the position's type |
| `list::get(l, i)`, `list::contains(x, l)` | `x` read at `T` | `T`, `Bool` |
| `set::item(x)`, `set::concat`, `set::union` | `x` at `T`, the sets at the position's type | the position's type |
| `set::difference(a, b)`, `set::intersect(a, b)` | `a` at the position's type, `b` any set | the position's type |
| `set::contains(x, s)` | `x` read at `T` | `Bool` |
| `set::to_list(s)`, `set::from_list(l)` | | `List<T>`, `Set<T>` |
| `kequal::ite(c, t, e)` | both branches at the position's type | the position's type |

"At" a sort means inferred and checked there; "read at" means the operand must share a sort with the element sort, since a probe for an element of another sort is merely never found.
A reading operation (`map::keys`, `keys_list`, `values`, `get`, `get_or_default`, `list::get`, `set::to_list`, `set::from_list`) whose operand the sentence builds itself, so that no declaration types it, is checked through: at `Set<K>`, `map::keys(m)` checks `m` at `Map<K, KItem>`, `map::values(m)` at `List<V>` checks it at `Map<KItem, V>`, `set::from_list(l)` at `Set<T>` checks `l` at `List<T>`, and a `get` at a collection type `T` checks its map or list at values or elements of `T`; the parts the operation discards are `KItem`s, unconstrained.
So `set::from_list([a, b, c])` is how to write a set of elements at a typed position, `seen: map::keys(map::update(map::empty(), name, s))` checks `name` as an element of `seen` whatever `s` is, and a wrong key is reported where it is written, as "stored as a key of the map whose keys `map::keys(..)` writes to the cell `seen`".
An operand that comes from outside the sentence keeps its own type: a typed binder's result type is computed and checked, and an untyped one is still an error.
A rule fn's binder declaration, an equation fn's subject and result sort, and a `where` narrowing still name only the sort (`where log: List` rather than `List<BusCycle>`, `krs::syntax::parametric-collection-sort`): a narrowing is a runtime sort test, and K cannot test the elements of a collection, while a binder takes its type from the position that matches it and an equation from its function's signature.

The rule this check exists for stores a statement in a `Map<Id, Value>` store through a nested update:

```rust
store: {
    k: [Assign(name, _), s, ..],
    env: e,
} => {
    k: [..],
    env: map::update(map::update(e, name, 0), name, s),
}
where s: Stmt;
```

```text
error[krs::analysis::collection-element-sort]: `s` of sort Stmt is stored as a value of the cell `env`, declared `Map<Id, Value>`, and Stmt is not a Value
```

K would accept the rule; the `Stmt` it stores makes a later read `Name |-> V:Value` of `env` fail to match, so the program gets stuck far from the cause.

A typed signature is an interface the check reads instead of the function's body: an argument is checked at its parameter's type, an application has the declared result type, and each of the function's equations is checked against that result type, with the binders of its subject at the parameters' types.
KEVM's storage-access marker is typed this way, and its body checks against the signature: `map::get(accessed, account)` reads a `Set<Int>`, and `set::item(index)` stores an `Int` in it.

```rust
#[k::function(total, syntax = "#kevmMarkStorageAccess({accessed}, {account}, {index})")]
pub fn MarkStorageAccess(
    accessed: k::Term<Map<Int, Set<Int>>>,
    account: k::Term<Int>,
    index: k::Term<Int>,
) -> k::Term<Map<Int, Set<Int>>> {
    if map::in_keys(account, accessed) {
        map::update(accessed, account, set::union(map::get(accessed, account), set::item(index)))
    } else {
        map::update(accessed, account, set::item(index))
    }
}
```

A rule then writes `accessed_storage: MarkStorageAccess { accessed, account, index }` into a `Map<Int, Set<Int>>` cell with nothing left unchecked, and an equation that stored a `Stmt` there would be rejected at the stored term.
`krs expand` writes the types into the long form, `#[k::function(sort = Map<Int, Set<Int>>, ..)]`, and its equations as `k::Term<Map>`.

A collection whose elements nothing declares is untyped: a binder matched in a bare `Map` cell, field, or parameter, a function's untyped result (`-> k::Term<Map>`), or a projection `k::project!(Map, t)`.
A collection the sentence builds, such as `map::update(map::empty(), 1, s)`, is not untyped: it has no type of its own and is checked where it is written.
Writing one into a typed position is an error, since nothing would check its elements:

```text
error[krs::analysis::untyped-collection]: `Put3(..)` returns an untyped `Map`, so nothing checks the elements it writes to the cell `env`, declared `Map<Id, Value>`
```

The fix is to declare the element types where the collection comes from: the cell, the constructor field, or the function's signature.
A rule's `#[k::exists(m: Map)]` is an untyped source too: the step may put any map there, so writing `m` into a typed position is `untyped-collection` in every rule form; a claim's existential is not, since it stands for what the target state holds.
A user function is a term like any other: `env: Put(e, name, s)` is the function's result written into `env`, never read as a map update.
A configuration variable of `#[k::init]` is a binder of its parameter's type, as a typed function's parameter is, and KRS checks the flow wherever it is placed: as a cell's whole content its sort must be below the cell's, and `xs: List<Stmt>` in `stack: list::concat(xs, list::item(1))` is `collection-element-sort` and a bare `xs: List` there is `untyped-collection`.
A variable of any other sort is checked by sort inference, as any occurrence is.
Reading an element out of a bare-collection variable is not a write of the collection: `list::item(list::get(xs, 0))` in a `List<Value>` cell reads a `KItem` and emits the projection `{$XS:List [ 0 ]}:>Value`.

```text
error[krs::analysis::collection-element-sort]: `xs`, the configuration variable `$XS`, has type `List<Stmt>`, which does not fit the cell `stack`, declared `List<Value>`: Stmt is not a Value
```

The value a configuration variable is given at run time is the induction's other base case, and only execution sees it.
`krs-exec` checks it when it assembles the initial configuration, for `krs run -c NAME=TEXT`, `krs search`, and a value given to `Semantics::configure` alike: a variable declared with a typed collection type must hold a value of that type, wherever the initializer places it, key by key, value by value, and element by element, nested collections against their own element types, each element's sort at most the declared one in the definition's sort lattice (an `Int` or a `Ptr` declared `Ptr: Value` fits `Value`).

```text
$ krs run -c 'ENV=x |-> skip' ..
error[krs::exec::collection-element-sort]: configuration variable `$ENV`, declared `Map<Id, Value>`: the value at key `x` is `skip` of sort Stmt, which is not a subsort of Value
```

A part the configuration leaves unevaluated is checked at the sort its symbol declares, which bounds every value it can take: `x |-> noop(1)` is rejected when `noop` returns a `Stmt`, but the elements of a set that `evens(1)` would compute are not seen.
Three inputs stay unchecked: those computed elements, configuration values Java K's `krun` reads, and `k::raw_k!` sentences, which the compiler does not check, so a raw rule can break the invariant after the first step.

### Functions in patterns

A pattern matches terms as they are, and a function application denotes the value evaluation produces, not a term of its own.
Every term a rule or an equation is applied to has its functions evaluated, so a function application at a matched position of a rule's or an equation's pattern describes a term that never occurs, and the sentence would never apply.
A matched position is the root of every slot the sentence matches as well as any position below it: a `#[k::rule]` fn's subject (a term rule's, a single-body rule's, an `anywhere` rule's), a `for Sort` clause's subject, a computation item (`k: [Size(x), ..]`, `KCell(Size(x), ..)`), and a cell's content (`acc: Size(x)`, `Cell(Size(x))`), an equation's function-context cells included.
A context matches the computation the configuration holds as a rule does, so its subject and a context alias's are matched positions too.
So is a collection's value or element in a pattern, which is compared with the values the collection holds: a `cells!` `map![..]` value (`map![k -> Size(x), ..]`), an element of a List cell or of a cons list (`stack: [Size(x), ..]`), and a child of a cell collection's instance: a List collection's instance is its element, and a Map collection pairs an instance's key cell with the whole instance, key cell included, as the value it maps to, so a function in the key cell never matches either.
A Set collection is a set of its instances, which a pattern looks up by an instance as a set by an element: an instance whose every cell is written and whose names the subject binds elsewhere is computed, and the rule applies when the collection holds the instance it computes ([cell collections](#optional-cells-and-cell-collections)); an instance that selects one by matching (`..` in it, or a name nothing else binds) is matched cells, where a function is refused as in a Map collection's.
A `let` pattern and a `k::matches!` pattern match the value their term computed, whose functions are evaluated as well, wherever they stand: `let Size(y) = e;` and `k::matches!(e, Size(_))` never match.
KRS refuses it at the application (`krs::analysis::function-in-pattern`): a user function, a builtin operation such as `int::add(a, 1)`, and a collection's lookups and sizes alike, written as calls or as an [index or a collection method](#index-reads-and-collection-methods) (`m[k]`, `m.len()`).
That a head is a function is a fact of what it resolves to, so the refusal is told after the term's names and sorts: where a binder declared `KItem` is the operand, `int::add(x, 1)` in a pattern is first `krs::analysis::incompatible-binder`, since the term does not resolve until its operand has a sort the operation takes; a construct refused by its spelling and position alone, `_` in a result or `x + 1` in a pattern, is told before both.
Match a variable there and relate it to the application in a `#[k::requires]` guard, or state a fact about the unevaluated application as a `#[k::simplification]`.
A rule whose whole subject applies a function, `fn twist(k::term![Size(x)]: Term<Int>) -> Term<Int>`, would otherwise read as a definition of that function, not a step of the computation; to define the function, write the sentence as an equation, a `#[k::equation]` fn or a `k::equations!` row.
The application is the meaning, and is accepted, at the root of an equation's subject (the function the equation defines), anywhere in a simplification's subject, which rewrites symbolic terms whose applications stand unevaluated, anywhere in a claim's subject, a symbolic state, and in a map's key, a set's element or a Set collection's instance that the subject computes, `env: { Size(x) -> v, .. }`, where a lookup evaluates the key.
Conversely, an equation defines one function, so its subject's root is that function's application: a constructor there, `#[k::equation] fn f(Cmd::Red(): Term<Stmt>)`, is a value, which evaluation leaves as written, and defines no function, and neither does a literal or a builtin operation such as `int::add(x, 1)`, which its builtin domain defines (`krs::analysis::subject-root-not-function`, at the root's head, also when root alternatives apply one constructor, and at the first alternative that applies no function, `Cmd::Red() | Cmd::Blue()` at `Red`, since each alternative is a whole subject), and neither does a collection's element or list notation, `set::item(x)` or `[x, ..rest]`, which build a value; write the function's application there, a `#[k::rule]` for a step from that term, or a `#[k::simplification]` for a fact about a builtin operation.
A simplification rewrites a function's unevaluated application, a declared or a builtin one, so a constructor, a collection's unit, element or concatenation (`set::item(x)` is the singleton set) or a literal at its root, which is a value, is refused the same way.
Because the key is evaluated, its names below the application must be bound elsewhere in the subject (here `x`); one bound nowhere else is `krs::expand::unbound-name` ([map reads](#rules-that-leave-the-computation-cell-out)).
A set is looked up by its elements as a map by its keys, so the same holds for a set element: in `set::concat(set::item(Size(n)), rest)`, `n` must be bound elsewhere in the subject.

### Pattern aliases

`p @ Pair(a, b)` in a left-hand side is the Rust pattern you know: it matches what `Pair(a, b)` matches and also binds `p` to the whole matched term.
K writes the name last, `( pair ( A:Exp , B:Exp ) #as P:Exp )`, and KRS emits exactly that, always parenthesised.
Like `tail @ ..`, `name @ pattern` binds what its pattern matched; unlike Rust's `@`, which copies or moves a value, K's alias is the matched term itself (a conjunction of patterns), so a result can reuse it without rebuilding it.
`dup_pair: Dup(p @ Pair(a, b)) => Pair(p, Pair(b, a));` turns `dup(pair(1, 2))` into `pair(pair(1, 2), pair(2, 1))`.
A group record is the exception: a use of `saved @ Frame { .. }` is the update `Frame { ..saved }` (see [updating a matched record](#updating-a-matched-record)), the matched cell rebuilt from its children, which the alias's pattern binds.
A cell's children are placed by their labels, not matched as terms, so KRS names each child instead of writing `#as` among them; the rule means the same, in rules and claims alike.
`push: { k: [Push(), ..], stack: s, frame: saved @ Frame { pc: 0, .. } } => { k: [..], stack: [saved, ..s] }` emits `<frame> <pc> ( 0 #as Krs_UpdateSavedPc:Int ) </pc> <gas> Krs_UpdateSavedGas:Int </gas> </frame>` and pushes `ListItem(<frame> <pc> Krs_UpdateSavedPc:Int </pc> <gas> Krs_UpdateSavedGas:Int </gas> </frame>)`.
An alias over a group record bound inside `|` or more than once matches no one record, so it keeps `#as`.
An alias may name any subterm of a rule subject, a `cells!` cell value, a `k!` item, a `map!` key or value, or a readable clause pattern, a group's cell term included (`saved @ CallState { .. }` or `saved @ k::fragment![CallState { .. }]` in a list element), but not a whole rule subject, with or without `k::term![..]`, whose root is the matched constructor or function.
A readable `for Machine` record's computation items and cell values are not rule subjects, so an alias may name a whole one: `charge: { k: [op @ (Push() | Pop()), ..], gas: g } => { k: [Charged(op), ..], gas: int::sub(g, 3) }` emits `<k> ( ( push #Or pop ) #as Op:Op ) => charged ( Op:Op ) ... </k>`.
An alias may also stand inside each alternative, `stack: [(saved @ Frame { pc: 0, .. } | saved @ Frame { pc: 1, .. }), rest @ ..]`, which is `saved @ (Frame { pc: 0, .. } | Frame { pc: 1, .. })`.
It counts as a binder before the binders inside its pattern, so `fn wrap_pair(p: Exp, a: Exp, k::cells! { k: KCell(Wrap(p @ Pair(a, _)), tail @ ..), state @ .. }: Machine)` declares `p` first.
`@` in a result, a requires or ensures condition, or an initializer is a syntax error (K's `#as` is left-hand-side only), as are `ref` or `mut` on the alias, an alias inside its own pattern (rustc's E0416), and `name @ ..` outside a sequence, collection, or `cells!` pattern.

### Updating a matched record

A rule that rewrites a term into the same constructor with a few fields changed writes Rust's struct update: `t @ Ctor { f: p, .. }` in the left-hand side, then `Ctor { f: e, ..t }` in the result, which is the record `t` matched with the listed fields replaced.
KMIR's projection traversal drops one projection and keeps the other five fields:

```rust
deref_truncate: {
    k: [t @ Execution::TraverseProjection {
        projections: Projections::ProjectionsCons { head: Projection::DerefTruncate { .. }, tail },
        ..
    }, ..],
} => {
    k: [Execution::TraverseProjection { projections: tail, ..t }, ..],
};
```

K has no field projection on a term, so `..t` is defined by expansion: every field an update of `t` leaves out is bound in `t`'s pattern, to the binder the pattern gives it (`tail` above) or to a hidden binder, and the update writes that binder back.
A field the pattern leaves out or writes `_` is matched by the hidden binder instead of a wildcard, and one it matches with another pattern `p` by `( p #as Hidden )`.
Nothing new reaches K: the rule is the one written with every field named, and an alias over a group record, and any alias used only as a base, is matched without `#as`; `krs expand` writes that long form, naming each hidden binder after its alias and the path of fields below it (`t_target`, `o_frame_pc`), with a number added when two paths would read the same.
The base is a matched record, not a field projection, so it must be an alias `t @ Ctor { .. }` or `t @ Ctor(..)` of one record of the update's constructor, bound once and outside `|`: a binder of the whole term (`t` matched as `t`), an alias of another constructor, and a name bound by `let` or `k::matches!` are rejected (`krs::analysis::invalid-record-update`), and so are a base that is not one binder and a field listed twice (`krs::syntax::invalid-record-update`).
An update builds a record, so it stands only where a sentence builds a term: in a pattern, which denotes no record by `..base` and leaves out the fields it does not constrain with `..`, it is rejected at the base (`krs::syntax::invalid-record-update`).
An update may nest, `Outer { inner: Inner { x: 1, ..i }, ..o }`, also for groups: `outer: o @ Outer { frame: fr @ Frame { pc: p, .. }, .. }` and the result `outer: Outer { frame: Frame { pc: int::add(p, 1), ..fr }, ..o }` change `<pc>` and keep `<gas>` and `<flag>`; an update stands in readable rules and claims, `k::equations!` rows (whose records may end in `..` like a readable rule's), and `#[k::rule]` and `#[k::equation]` fns; a reference `cells!` term names every field (`krs::expand::invalid-record-update`).

A nested `#[k::cell]` group is a record too.
In a readable record, `frame: saved @ Frame { pc: p, .. }` matches the group and leaves its other children unconstrained, and `frame: Frame { pc: int::add(p, 1), ..saved }` writes it back with `pc` changed; a group saved as a value updates the same way, so KEVM's return from a call restores the caller's frame from the call stack with three cells changed:

```rust
return_from_call: {
    k: [Return { gas_left }, ..],
    call_stack: [saved @ CallState { word_stack: s, gas: g, .. }, ..],
    call_state: _,
} => {
    k: [..],
    call_stack: [..],
    call_state: CallState { word_stack: [1, ..s], gas: int::add(g, gas_left), local_mem: bytes::empty(), ..saved },
};
```

In the list element, `CallState { .. }` is the group's cell term, as `k::fragment![CallState { .. }]` is, and it ends in `..` because a cell term outside the group's own cell position is complete; `krs expand` writes it as the fragment.
`Frame { ..saved }` with no listed field is the matched frame unchanged, which is what a use of `saved` means.
A group child that the base's pattern matches with a group record is rebuilt from that record's children in turn: with `outer: o @ Outer { frame: Frame { pc: 0, .. }, .. }`, the result `outer: Outer { flag: 7, ..o }` writes back the matched `<frame>` (its `<pc>` and `<gas>` through hidden binders) and sets `<flag>`.

### Pattern alternatives

`Red() | Green() | Blue()` in a left-hand side is the Rust or-pattern you know: it matches what any of its alternatives matches.
K spells it `( red ( ) #Or green ( ) #Or blue ( ) )`, and KRS emits exactly that, always parenthesised and in source order.
`rgb: Color(Red() | Green() | Blue()) => 1;` turns `color(green())` into `1` and leaves `color(3)` stuck, and the equation `fn code_rgb(k::term![ColorCode(Red() | Green() | Blue())]: Term<Int>) -> Term<Int> { 1 }` emits `rule code ( ( red ( ) #Or green ( ) #Or blue ( ) ) ) => 1`.
In a readable clause the whole subject may be an or-pattern, `primary: Red() | Green() | Blue() => 1;`, which matches at the head of the computation cell, and so may a fn's subject, with or without `k::term![..]`: `fn warm(k::term![Red() | Green()]: Term<Stmt>) -> Term<Stmt> { 1 }` emits `rule ( red ( ) #Or green ( ) ) => 1`; alternatives may also appear in any subterm of a subject, a `cells!` cell value, a `k!` item, or a `map!` key or value.
A readable record's values are not rule subjects, so `|` and parentheses there read as below a constructor: `pc: (p)` binds `p` as `pc: p` does, a bare name inside `|` is a binder (`k: [(Nop | Halt), ..]` is ``variable `Nop` is not bound in all alternatives``), and a unit constructor is written `Name()` (`k: [Nop() | Halt(), ..]`).
A record entry that names a group cell, an optional group's `Some(..)`, and a group child of a cell term are not terms but cells, which K places by their labels, so `|` cannot join alternatives there, also below an alias (`krs::analysis::invalid-pattern-or`).
Write the alternatives at the child they test, `outer: Outer { flag: 0 | 1, .. }`, which a cell term distributes over as a constructor does, or write one rule per alternative, in a `nondet` group when both can match one configuration.
In Rust, `|` tries its alternatives left to right; in K, `#Or` means "any of these", and when two alternatives match one term with different bindings the backends disagree: on `pick(pair(1, 2))`, `pick(Pair(x, y) | Pair(y, x)) => x` gives `1` on the LLVM backend and `1 #Or 2` on the Haskell backend.
KRS lets you write `|` only where the readings agree.
Every alternative binds the same names (``variable `x` is not bound in all alternatives``, rustc's E0408), each at one sort, and two alternatives that bind names must not match one term with different bindings (`krs::analysis::ambiguous-or-pattern`): `Pick(Pair(x, Red()) | Pair(x, Green()))` is accepted, `Pick(Pair(x, y) | Pair(y, x))` is not, and alternatives that bind no names may overlap freely.
The rule-overlap check treats an or-pattern as each of its alternatives.
An equation with alternatives is one equation per alternative: `Code(Red() | Green())` is the two equations `code(red())` and `code(green())`.
A constructor, a function application and an alias distribute over `|`, so alternatives below any of them mean the same as alternatives at its root: `Code(Pair(x, Red() | Green()))` is `Code(Pair(x, Red()) | Pair(x, Green()))`, `Code(op @ (Red() | Green()))` is `Code((op @ Red()) | (op @ Green()))`, and an equation's whole subject `Code(Red()) | Code(Green())` is `Code(Red() | Green())`, which KRS emits.
Every alternative of an equation's whole subject applies the one function the equation defines (`Code(Red()) | Size(Green())` is `krs::analysis::invalid-pattern-or` at `Size`), and they differ in one argument at most: an equation matches each argument on its own, so `Mix(Red(), 1) | Mix(Green(), 2)` is not `Mix(Red() | Green(), 1 | 2)`, which also matches `Mix(Red(), 2)`, and is refused (`krs::analysis::invalid-pattern-or`); write one equation per alternative.
An or-pattern in each of two arguments is one equation per pair of alternatives. Alternatives in a function context cell, which is one more argument of the function, and in a `k::matches!` pattern, which K tests with a generated equation, are read the same way.
A simplification rewrites one term, so its left-hand side takes no `|` at all (`krs::analysis::invalid-pattern-or`).
In a result, a requires or ensures condition, or an initializer, `|` is the [bitwise-or operator](#operator-and-method-notation) on `Int`, never an alternative: `Red() | Green()` there is an error (`krs::analysis::ambiguous-operator`) that says `|` joins alternatives only on a left-hand side, and `|` on `Bool` points to `||`.
`|` next to a `..` remainder and `|` between whole machine records are syntax errors.

### Shape tests

`k::matches!(t, Pattern)` is std's `matches!` with K's meaning: an object-language Bool that is true when the term `t` matches the Rust pattern `Pattern`.
K spells it `Pattern :=K T`, pattern first, and KRS emits exactly that, always parenthesised: `#[k::requires(k::matches!(e, Pair(_, _)))]` on `is_pair: IsPair { e } => true;` emits `requires ( pair ( _ , _ ) :=K E:Exp )`, and `bool::not(k::matches!(e, Pair(_, _)))` emits `notBool ( pair ( _ , _ ) :=K E:Exp )`, which is K's `:/=K`.
It is valid in a rule's or equation's `#[k::requires]` and `#[k::ensures]` conditions and as a Bool-sorted result, such as the equation `fn twin(k::term![Twin(e)]: Term<Bool>) -> Term<Bool> { k::matches!(e, ExpSyntax::Pair(x, x)) }`, which emits `rule twin ( E:Exp ) => ( pair ( X:Exp , X:Exp ) :=K E:Exp )`.
The subject is a term; the pattern is a left-hand-side pattern with `_`, `name @ pattern`, and `A | B`, but no `if` guard (conjoin a separate condition with `bool::and`).
K compiles `P :=K T` into a fresh function with two equations, one returning `true` for the pattern and an `owise` one returning `false`, so the test works on symbolic terms too, and the names in the pattern stay inside it: they are local binders, emitted under names of their own.
A name that occurs twice tests equality, as `Pair(x, x)` does; a name read once is rejected (``write `_` ``).
The trap is a pattern name that is also a rule binder: in K, `pair(X, _) :=K E` binds a new `X` and ignores the rule's `X`, so KRS rejects it (`krs::analysis::invalid-matches`) and points to `int::eq` or `bool::eq` for a comparison.
A pattern whose sort cannot meet the subject's, which would always be false, is rejected as well.
K rejects `#as` in a rule's right-hand side, so `name @ pattern` inside `k::matches!` is accepted only in conditions, as in `k::matches!(e, Pair(p @ Pair(_, _), p))`.
It is also an [initializer term](#declarations-and-sentence-forms), evaluated when the configuration is built.
`k::matches!` in a left-hand side or inside a pattern, a map's key included, std's bare `matches!` (which tests a host value; ``did you mean `k::matches!`?``), and an `if` guard are syntax errors, as is `k::matches!` in a `cells!` cell value.
A claim's states are terms over its variables and its conditions Bools, so `k::matches!` would mean there what it means in a rule, but no prover takes it: the native prover and Java K's `kprove` lower `:=K` to its generated function only in a definition's sentences, never in a claim, so a claim refuses it (`krs::expand::matches-outside-condition`, with that reason); define a function whose equations match the pattern and apply it.

### Local bindings

A Rust block in a term position is K's `#let`: zero or more `let pattern = term;` statements and one result term.
`swap: Swap { e } => { let Pair(x, y) = e; Pair(y, x) };` emits `<k> swap ( E:Exp ) => ( #let pair ( X:Exp , Y:Exp ) = E:Exp #in pair ( Y:Exp , X:Exp ) ) ... </k>`, and a rule or equation body may itself be such a block: `fn swap_pair(k::term![SwapPair(p)]: Term<Exp>) -> Term<Exp> { let ExpSyntax::Pair(x, y) = p; ExpSyntax::Pair(y, x) }` emits `rule swapPair ( P:Exp ) => ( #let pair ( X:Exp , Y:Exp ) = P:Exp #in pair ( Y:Exp , X:Exp ) )`.
A block nests anywhere a term does, `int::mul({ let n: Int = int::div(bytes::length(data), 160); int::mul(n, g1_mul(n)) }, 2)`, and is valid in results and in `#[k::requires]` and `#[k::ensures]` conditions; each `#let` is parenthesised, and several statements nest to the right.
K defines `#let P = A #in B` as `#fun(P => B)(A)`: a generated function with the one equation `P => B`, applied to `A`.
Two things differ from Rust.
First, the pattern may be refutable, and a failed pattern makes the term **undefined**, where rustc would have rejected the program: `swap(3)` aborts on Java K's LLVM backend and ends as undefined on k-rust (the [boundaries](/reference/boundaries) record how Java K's Haskell backend differs).
`let x: Sort = term;` is a runtime sort test of the same kind, not rustc's static check: `let m: Int = e;` emits `#let M:Int = E:Exp`, which is undefined when `E` is not an `Int`.
Second, the `let` is a function call, not a statement sequence: `A` is evaluated outside the pattern's scope, and each statement's names are local binders, visible in its pattern and the rest of the block only and emitted under names of their own, so a `let` that shadows a rule binder, `{ let e = Pair(e, e); e }`, leaves the outer `e` as it was.
A block holds only `let` statements and one result without a semicolon (``a term block is `let pattern = term;`* followed by one result term (K's #let)``): `let .. else`, `mut` and `ref` bindings, expression statements, and items are rejected.
A `let` pattern reads its value by one shape, whose names the rest of the block uses, so it takes neither `|` nor `name @ pattern` (`krs::syntax::invalid-let`, at the `|` or the alias): test which shape a value has with `k::matches!`, or match each shape in a sentence of its own, and write `let p = e; let P = p;` for `let p @ P = e;`, since a bare name already names the whole value. An ascription names one binder.
A block is also an [initializer term](#declarations-and-sentence-forms), evaluated when the configuration is built.
A block in a pattern, a map's key included ([map reads](#rules-that-leave-the-computation-cell-out)), a let-bound name used outside its block, and a pattern whose sort cannot meet its value's (`krs::analysis::invalid-let`) are rejected, as is a block in a `cells!` cell value.
A claim's states and conditions would hold a block as a rule's do, but no prover takes one: the native prover and Java K's `kprove` lower `#let` to its generated function only in a definition's sentences, never in a claim, so a claim refuses it (`krs::expand::let-outside-term`, with that reason); write the term it computes, or define a function and apply it.

### Function contexts

A K function can read the configuration it is evaluated in.
An `#[k::equation]` may end with a second parameter, its **function context**: a `k::cells!` pattern over the configuration struct, framed by an anonymous `..`.

```rust
#[k::requires(int::le(0, b))]
#[k::equation]
fn bar_plus(
    n: Term<Int>,
    b: Term<Int>,
    k::term![BarPlus(n)]: Term<Int>,
    k::cells! { bar: k::configuration::Cell(b), baz: k::configuration::Cell(0), .. }: Machine,
) -> Term<Int> {
    int::add(b, n)
}
```

It emits K's function-context rule, the rewrite in `[[ .. ]]` and the cells it reads on the following lines: `rule [[ barPlus ( N:Int ) => B:Int +Int N:Int ]]`, then `<bar> B:Int </bar>` and `<baz> 0 </baz>`, then `requires 0 <=Int B:Int`.
The caller never passes the configuration: `read: ReadBar() => BarPlus(1);` stays `barPlus ( 1 )`, and K adds a hidden configuration argument to `barPlus` and threads it through every function that needs it, including a function such as `barTwice`, whose own equation has no context but calls `barPlus`.
K's warning for a total function whose context may not match shows that argument: `Non exhaustive match detected: barPlus(_,<generatedTop>(_,<bar>(_),<baz>(#token("1","Int")),_))`; KRS's [coverage lint](#coverage-of-total-functions) does not count an equation with a context, so it reports `barPlus` as having no equation at all.
The context is read-only: an equation returns a term, never the configuration, so this is not a multi-cell rule, which is a transition.
Because a rule that calls such a function reads those cells, the overlap check counts them in the rule's footprint (as unconstrained cells): a rule that writes `<bar>` and a rule on `<k>` that calls `barPlus` are reported as overlapping.

The context names leaf cells with the usual `Cell(..)`/`KCell(..)` wrappers and frames, and its binders are the equation's: the binder list becomes mandatory and declares the subject's binders, then the context's, each in first-occurrence order.
A context on a `#[k::rule]`, `#[k::simplification]`, or `#[k::alias]` is rejected (``a configuration context belongs only on #[k::equation] (K's [[ ]] function context)``), as are a final parameter that is not `k::cells!` typed by the configuration struct, a context without its anonymous `..` or with a bound `state @ ..` (a function context frames the rest of the configuration with an anonymous `..`), a whole nested cell, and a binder declared at a sort its cell does not have (`krs::analysis::invalid-function-context`).

### Coverage of total functions

`total` claims that a function has a value on every argument, and KRS trusts the claim: where no equation applies, the function still has a value, but the definition does not say which.
Every command that lowers the definition reports such arguments as `warning[krs::analysis::uncovered-total-function]` at the function, with a witness: ``total function `R8` has no equation for `R8(8)` ``, or, when the equations are guarded, ``has no equation for `DecodeCb(opcode)` when `FieldX(opcode)` is 4``.
A condition is a refutation: every argument that satisfies it is uncovered, and an argument it does not constrain may be anything, shown as `0` for an Int, so ``has no equation for `SignedLess(0, right)` when `Sign(right)` is 0`` holds for every `left`.
It is a warning, not an error, because the definition means something: an unconstrained value, not a contradiction.

The check runs on the assembled definition, because a package that depends on another may add constructors, subsorts, or a parametric constructor to its sorts; a function covered in one definition can be uncovered in a larger one, and the witness names the constructor that uncovers it.
A sort's values are its constructors' terms, its subsorts' values, and builtin domain values: `true` and `false` exhaust Bool, while Int, String, Bytes, Map, List, Set, token sorts and `KItem` need a binder.
A binder covers the values of its own sort only, so `x: Int` in an `Exp` argument covers the Ints and not `Plus(..)`.
Priorities and `owise` decide which equation applies, never whether one does, so an `owise` equation is an equation like any other; `concrete` and `symbolic` restrict how a backend applies an equation, not what it states, and play no part either.
An or-pattern covers each alternative; a Map, List, Set or K-sequence pattern, a function application in a pattern, and a binder that occurs twice cover nothing the check can see.

A guarded equation covers its pattern where its `requires` holds.
When every equation of the function bounds each `Int` argument its `requires` reads to finitely many values, by a literal pattern, an or-pattern of literals, or top-level comparisons with constants (`0 <= x && x < 256`, which every [bit template](#bit-templates) has), and those values, with one more outside them per argument, are at most 2^16 argument vectors, the check evaluates every `requires` on each of them.
That decides coverage exactly: outside the bounded values a bounded equation does not apply and the others do not read the argument, so one value there stands for all of them.
The four templates `k::bits!("00 yyy zzz")` to `k::bits!("11 bbb zzz")` of `DecodeCb` cover `0..=255` and no more, so the witness is `DecodeCb(256)`.
The evaluation is the builtins' definition on literals, with constructor terms as values, `k::matches!` of a value as matching, and an application of a total function by the function's own equations (as the [overlap check](#overlapping-equations) evaluates it); a `requires` that calls a function the evaluation cannot evaluate, or is undefined somewhere (`12 / x` at `0`) unless a false top-level conjunct already rules that argument out, ends it, and the check falls back to the abstraction below.

Otherwise the check decides a set of guards as Boolean combinations of comparisons with integer constants (`x < 0`, `x == 3`, `0 < x`, folded through `+`, `-`, `*` and the like), of the order of two integer terms (`a < b`, `a == b`, `b < a`, exactly one of which holds), and of opaque Bool atoms, which two equations share when they test the same term; literal patterns count, so `sgn(-1)`, `sgn(x)` when `x < -1`, when `x == 0` and when `x > 0` cover Int.

An application of a `total` function in a guard, such as `Sign(left)` in `Sign(left) == 1`, is one unknown value of its result sort.
Two applications are the same unknown when they apply the same function to the same arguments, binders compared by the argument they bind, so every equation that tests `Sign(left)` tests one value; the unknown is unrelated to every other term, its own arguments included.
When the check finds the function's own equations cover every argument, the unknown is also one of their results, its range: each result that is a literal or a constant, a constructor application (its variant), an application of a function with a range, `x.bit_range::<Int>(o, l)` (`0` to `2^l - 1`), `x & m` (`0` to `m`), `x % c` with Euclidean `modInt` (`0` to `|c| - 1`), or a length or size (not negative), for constant `o`, `l`, `m >= 0`, `c != 0`; any other result, or an `underspecified`, hooked, or sort-parametric function, gives no range.
So a `TwoSign` whose equations return `1` and `-1` makes `match (TwoSign(left), TwoSign(right))` over those four pairs cover every argument, while KEVM's `Sign`, which is also `0` outside `0..2^256`, leaves ``SignedLess(0, right)` when `Sign(right)` is 0``.
A function is checked once, before the functions whose guards apply it; one still being checked when a guard asks for its range, in a cycle of functions whose guards apply each other, has none.

A `k::matches!(t, Pattern)` test, which a [branching body](#branching-bodies) writes for a term scrutinee and for a nested catch-all, is read as pattern matching when `Pattern` binds each name once and the check decomposes it: the equation becomes one case where each test holds, its pattern for `t` narrowed by `Pattern`, and one where it fails, narrowed to the other values of `t`'s sort, the test replaced by `true` or `false` in the rest of the guard.
For `t` a parameter, that refines the parameter's pattern, so a nested catch-all `_` guarded by `k::matches!(shape, Shapes::Circle { .. }).not::<Bool>()` covers `Shapes::Pair(..)` and the other values of `Shape`, injected Ints and `KItem`s included.
For another term of a declared sort, such as `Classify(value)`, it is one more column of values of `t`, one unknown shared by every equation that tests `t`, and a witness names its value: `match Classify(value)` with arms for `Kinds::A()` and `Kinds::B()` only has no equation for ``PartialScore(value)` when `Classify(value)` is `Kinds::C` ``.
A test whose pattern repeats a name or is not decomposed, or whose term is an Int, Bool, or other builtin, is an opaque Bool atom.
A comparison `x.bit_range::<Int>(o, l) == v` or `(x & m) == v` with constant `o`, `l` and `m` also fixes bits of `x`, and the check skips valuations no integer `x` has, so a bit template's equation covers the values it matches.
A guard holds only where it is defined, and the check reads a partial Int operation together with its domain: a division or remainder holds only where its divisor is not zero, a shift or exponent where its amount is not negative, and `bitRangeInt(x, o, l)`, which is `(x >>Int o) modInt (1 <<Int l)`, where `o` and `l` are not negative.
So `w > 0 && x < 1 << (w - 1)` counts, because the shift is defined wherever `w > 0` holds, while `x / d >= 0` and `x / d < 0` leave `d == 0` uncovered.
Comparisons are read through constant summands, so `w - 1 >= 0` is `w >= 1`, and the orders and bounds of a valuation are read together, so `a == b`, `b == c` and `a < c` do not all hold.
A lookup is read the same way: `map::get(m, k)` is defined where `map::in_keys(k, m)`, and `list::get(l, i)` where `-list::size(l) <= i < list::size(l)` (a negative index counts from the end); a length or size is never negative.
A guard with any other operation that may be undefined, such as a call of a partial function, counts for nothing.
A guard also counts for nothing when a partial operation is in the right operand of a negated `&&` or of a `||`, where a backend that evaluates them lazily and the strict reading of matching logic disagree on whether the guard holds.
The abstraction never calls an uncovered argument covered, but it can miss a fact, such as the range of a result it does not bound (`1 + StackSize(tail)`), a correlation between a call and its arguments (`Sign(x) == 1` only where `x >= 0`), or a partial function's value, and then report a gap that does not exist.
A matching-logic `requires` and an equation with a [function context](#function-contexts) are not counted.

Partial functions are not checked, since a missing case is what `partial` means, nor are hooked and `smt_hook` functions, which the backend or the SMT translation define, nor total functions, or instances of a sort-parametric one, with no equation at all, which are declared rather than defined.
Simplifications are lemmas, not definitions, and do not count; neither do `raw_k!` sentences, which the check does not read, and since one could be an equation that gives a function another value, a definition with a `raw_k!` sentence has no ranges and evaluates no function by its equations.
A warned function takes more equations, an `#[k::equation(owise)]` equation, `partial`, or `underspecified = "reason"`, which states the gap on purpose; `underspecified` on a function whose equations cover every argument is itself a warning (`krs::analysis::stale-underspecified`).

### Functions declared by a fn

`#[k::function(..)]` on a `fn` declares the function symbol from its signature, and a body declares its equation:

```rust
/// The low 8 bits of an integer.
#[k::function(total, internal)]
pub fn Byte(value: k::Term<Int>) -> k::Term<Int> {
    int::rem_euclid(value, 256)
}
```

It is the struct `pub struct Byte { pub value: k::Term<Int> }` with `#[k::function(total, internal, sort = Int, syntax = "byte({value})")]`, plus the equation `#[k::equation] fn byte(k::term![Byte(value)]: k::Term<Int>) -> k::Term<Int> { int::rem_euclid(value, 256) }`, and `krs expand` prints exactly that pair.
Its fields, like those of a `#[k::constructor]` struct, an enum variant, a syntactic list's cons variant, or a token's representation, may carry doc comments, which document the Rust item and have no K meaning; any other field attribute is an error.
The fn is named as its applications are written, `Byte(x)`, in UpperCamelCase, so the name a rule uses is the name the declaration spells; the equation takes the snake-case name, `byte` (`FieldX` gives `field_x`, `R8` gives `r8`).
The return type is the sort, so a `sort` key is rejected; every parameter is a plain name typed `k::Term<S>`, because Rust parameters are irrefutable: cases are written as [branches](#branching-bodies) of the body, rows of a table, or `#[k::equation]` fns.
`#[k::requires(..)]` on the fn guards the equation, `total` and `partial` mean what they mean on the struct, and a generic fn, a pattern parameter, `#[k::equation(..)]`, and `hook` with a body are rejected (`krs::syntax::invalid-function-shorthand`).

#### Branching bodies

A body that is an `if` chain or a `match` defines one equation per branch:

```rust
#[k::function(total, internal)]
pub fn StorageValue(storage: k::Term<Map>, index: k::Term<Int>) -> k::Term<Int> {
    if map::in_keys(index, storage) { map::get(storage, index) } else { 0 }
}

#[k::function(total, internal)]
pub fn SignedLess(left: k::Term<Int>, right: k::Term<Int>) -> k::Term<Int> {
    match (Sign(left), Sign(right)) {
        (1, 1) => BoolToWord(int::lt(left, right)),
        (1, -1) => BoolToWord(false),
        (-1, 1) => BoolToWord(true),
        (-1, -1) => BoolToWord(int::lt(Magnitude(right), Magnitude(left))),
    }
}

#[k::function(total, internal)]
pub fn Describe(value: k::Term<Val>) -> k::Term<Int> {
    match value {
        Value::Integer { ty: 32, value } if int::lt(value, 0) => 0,
        Value::Integer { value, .. } if int::ge(value, 0) => value,
        _ => -1,
    }
}
```

`Sign` is a helper whose equations return `1` or `-1`, which makes `SignedLess` covered (see [the coverage check](#coverage-of-total-functions)); KEVM's `Sign` is also `0` outside `0..2^256`, so there `SignedLess` states that gap with `underspecified`.

A branch is a case of the function's definition, and K states cases as equations, so each branch is an equation whose `requires` is the condition under which Rust reaches the branch.
`StorageValue` is `storage_value_1`, under `map::in_keys(index, storage)`, and `storage_value_2`, under `map::in_keys(index, storage).not::<Bool>()`.

- Branch `i` of `if c1 { .. } else if c2 { .. } else { .. }` is guarded by the negation of each earlier condition, then its own, conjoined with `&&` in source order: the third branch above is guarded by `c1.not::<Bool>() && c2.not::<Bool>()`. Each condition is evaluated only where the earlier ones are false, as in Rust, and the branches are disjoint by construction. An `if` without `else` is an error: it has no value in Rust, and a function that leaves the other arguments without a value is `partial`, guarded by `#[k::requires(..)]`. `if let` is an error too; match on the value instead.
- The scrutinee of a `match` is a parameter, a tuple of parameters and other terms, or another term, such as `Sign(left)`. An arm's pattern for a parameter becomes that argument's pattern in the equation's head, with the whole pattern grammar of an equation (constructors, literals, `_`, `|`, `@`, record rest `..`), and its names are bound in the guard and the result. An arm's pattern for any other term is tested in the guard: a literal as an equality (`Sign(left).eq::<Int>(1)`; `true` is the term itself and `false` its negation), alternatives of literals as a disjunction of equalities, and any other pattern as `k::matches!(term, pattern)`, K's `:=K`. Such a pattern binds no names, because the binders of `:=K` are local to the test. A tuple arm lists one pattern per component, and `..` stands for the components it leaves out.
- `pattern if guard => ..` adds the guard after the pattern's tests, and the fn's `#[k::requires(..)]` comes before every branch's guard.
- A branch whose result is itself an `if` or a `match` branches further, and the conditions conjoin. An `if` or `match` anywhere else, as an argument of a call or after a `let`, is an error that suggests a helper function, because an equation can only branch at its root.
- A parameter that a branch's guard or result still reads after an arm refined it is kept with `@`, as `width @ 0`; a parameter a branch never reads is `_` in its head.

Rust tries a `match`'s arms in order, and K's equations are unordered.
The two readings agree when no two arms apply to one argument, because then every argument reaches the same arm under both, so the arms of a branching body must not overlap; one priority per arm would instead make reordering arms change the definition, and would make each equation carry the negation of every earlier arm.
The one exception is a last arm that matches everything, one without a guard whose every pattern is `_` or, for a parameter, a plain name: in the body's own `match` it is the `owise` equation, since "no other equation applies" is "every earlier arm failed" there.
A catch-all arm that is not last is an error, since the arms after it could never apply.
In a `match` nested in a branch, a catch-all arm cannot be `owise`, which is one priority for the whole function: there it is guarded by the negation of each earlier arm's test, `k::matches!(op, Op::Add(_, _)).not::<Bool>() && ..`, which needs each earlier arm's guard to read no name its pattern binds; when one does, move the nested `match` into a helper function, where its catch-all is `owise`.
The coverage check reads those tests as pattern matching, so a nested catch-all covers exactly the values the earlier arms leave, whether its scrutinee is a parameter or another term.

The [overlap check of equations](#overlapping-equations) checks the arms.
Two arms it proves to apply to one argument with different results are `krs::analysis::overlapping-match-arms`, at the later arm, which Rust would not reach for that argument:

```text
error[krs::analysis::overlapping-match-arms]: branches `small_1` and `small_2` of `Small` both apply to `Small(0)` and give it different results, `1` and `2`; Rust would take the earlier arm, but each branch is an equation and equations are unordered, so the arms of a branching body must not overlap. ..
```

The check reports an overlap only when it can exhibit an argument, so arms whose patterns or guards it cannot decide pass unchecked; the common shapes, distinct constructors, distinct literals, and Int comparisons on one binder, are decided, and so is a guard that calls a total function like `Sign` wherever the function's own equations evaluate it on the argument, as for `(1, v) if v < 10` and `(_, v) if v >= 5` on `(TwoSign(value), value)`, which both apply to `5`.
An arm that overlaps an earlier one with the same result is not reported, since both readings then give the argument one value.

Each equation is named after the function and its branch's position, from 1, and a branch inside a branch appends its own: `signed_less_2` for the second arm, `nested_2_1` for the first branch of the second arm's `match`.
Adding a branch at the end keeps every other name.
`#[k::label(name)]` on an arm, which Rust allows on a match arm, names its equation instead, and the branches inside it take `name_1`, `name_2`; give an arm a label wherever its identity matters, such as a proof hint, because reordering arms renumbers the others.
`krs expand` prints each branch as its `#[k::equation]` fn.

A branching body is not K's `#if c #then a #else b #fi`: that is one function application, undefined wherever either branch is, so `#if map::in_keys(i, s) #then map::get(s, i) #else 0 #fi` would be undefined where the key is absent.
Separate equations keep each branch's definedness to itself.

A fn that ends with `;` declares the symbol only, for a [table](#equation-tables) or `#[k::equation]` fns to define: `#[k::function(total, internal)] pub fn R8(index: k::Term<Int>) -> k::Term<Operand>;`.

`syntax` is optional on every function, struct or fn, that is not program syntax: one marked `internal`, or not `pub` (see [Program syntax and the module pair](#program-syntax-and-the-module-pair)).
The default is the K symbol applied to the fields, `byte({value})` or `fieldX({opcode})`.
A program-syntax function needs an explicit `syntax` (`krs::syntax::missing-function-syntax`): in a program, a terminal outranks the object language's tokens, so a default `byte` would turn a program variable named `byte` into a keyword.
A function with a `Map`, `List`, or `Set` field already sits outside `<NS>-SYNTAX`, but that placement follows from K's module layout, so a default still asks for `internal`.
The template is used even when no program spells the function: `krs run` prints applications through it, emitted `.k` writes every rule that mentions the function with it, and `raw_k!` names the function by it.

### Equation tables

`k::equations!` writes the equations of one function as a table, one equation per row:

```rust
k::equations! {
    for R8;
    use Operand::*;
    use Register::*;
    r8_b          : 0  => Reg(B);
    r8_hl_indirect: 6  => HlIndirect;
    r8_a          : 7  => Reg(A);
    #[k::equation(owise)]
    r8_other      : _  => Immediate;
}
```

`for R8;` names a non-parametric `#[k::function]`, and each row `label: args => result;` is the equation `#[k::equation] fn label(k::term![R8(args)]: ..) -> .. { result }`, named by its label, with `R8`'s result sort.
The arguments are one pattern, or a parenthesized list for several (`both: (true, v) => v;`, `none: () => 0;`), with every pattern an equation accepts; a row may carry `#[k::equation(..)]` keys, `#[k::requires(..)]`, and documentation, and takes no `where` narrowing.
The table's `use` items are in scope for its rows only, and rustc resolves every unqualified name in a row through them and the module, so two of them that export one name are rustc's ambiguity error at the name.
That includes the first segment of a qualified path: under `use Register as Reg;`, a row may write `swap_a: Reg::A => Reg::B;`, and `krs expand` prints `crate::Register::A`.
`krs expand` prints each row as its `#[k::equation]` fn with qualified paths, and `krs fmt` lays a table out as it lays out `k::rules!`.

Rows are unordered, like every set of equations: a row never wins by its position, and the label, not the position, is the equation's identity, so reordering rows changes nothing.
A function whose cases read better as Rust, with guards, or tests of computed terms such as `Sign(left)`, can be written as a [branching body](#branching-bodies) instead.
Two consequences are checked at once.
Two rows without `requires` at one priority whose arguments are the same literals, or literals and [bit templates](#bit-templates) that share a value, would state that one application equals two results, or repeat one equation (`krs::syntax::duplicate-equation-row`).
A row whose arguments are all `_` matches every application, so beside other rows at its priority it needs `#[k::equation(owise)]` (`krs::syntax::catch-all-equation-row`).
These checks see one table's patterns only; the [overlap check of equations](#overlapping-equations) also reads guards and `#[k::equation]` fns.
A bare name in a row's pattern is a binder, as in every KRS pattern, so a unit variant is written `A()` or `Register::A`; where the table's `use` items or the module make a bare name a unit variant, which Rust would read as that variant, rustc rejects the row (``E0308 mismatched types`` at the name) instead of letting it bind everything.
A bare name spelled as a Rust constant, with an uppercase letter and no lowercase one (`IF`, `WORD_SIZE`, `P2`), is the exception in every pattern: it names a [named constant](#named-constants) and binds nothing.
The header must name a function (rustc's ``E0277 `Seven` is not a non-parametric `#[k::function]` ``), and a row's argument count must be the function's (rustc's ``E0308 expected a tuple with 2 elements``).
A table's index is always written, never taken from the order of an enum's variants: variant order is presentation, and reordering source must not change a definition.

### Bit templates

`k::bits!("00 yyy 100")` is a pattern of sort `Int` written as its bits, for decoding instruction words and other bit fields:

```rust
k::equations! {
    for Decode;
    use Instruction::*;
    decode_nop   : 0                           => Nop;
    decode_jr_cc : k::bits!("00 1cc 000")      => Jr(c);
    decode_inc_r : k::bits!("00 yyy 100")      => Inc(R8(y));
    decode_halt  : k::bits!("01 110 110")      => Halt;
    #[k::requires(op.ne::<Int>(118))]
    decode_ld_r_r: op @ k::bits!("01 yyy zzz") => Ld(R8(y), R8(z));
    #[k::equation(owise)]
    decode_other : opcode                      => Unknown(opcode);
}
```

The template is a string because Rust's lexer rejects `0b00yyy100`.
Its characters are read most significant bit first: `0` and `1` are fixed bits, `_` is a bit that may be either, a lowercase letter is a bit of the field it names, and spaces separate groups and are not bits.
The width is the number of bits, here 8, and a template matches exactly the integers `n` with `0 <= n < 2^width` whose fixed bits are as written, so `decodeOf(4)` is `inc rb` while `decodeOf(260)`, whose low 8 bits are those of `4`, and `decodeOf(-252)` fall to the `owise` row.
A field names that part of the matched value, `bitRangeInt(n, offset, length)`, in the sentence's `requires` and result: `y` above is bits 5 to 3.
A field is unsigned and its bits are adjacent unless a modifier says otherwise (below).
`op @ k::bits!(..)` also binds the whole value; otherwise the value has no name an author can write.

A template is sugar, and `krs expand` prints its long form.
`decode_inc_r` above is the equation

```rust
#[k::requires(
    bits.ge::<Int>(0) && bits.lt::<Int>(256)
        && bits.bit_range::<Int>(6, 2).eq::<Int>(0)
        && bits.bit_range::<Int>(0, 3).eq::<Int>(4)
)]
#[k::equation]
fn decode_inc_r(k::term![Decode(bits)]: Term<Instr>) -> Term<Instr> {
    Instruction::Inc(crate::R8(bits.bit_range::<Int>(3, 3)))
}
```

that is: the template becomes a variable, the `requires` gains the range and one `bitRangeInt` equality per run of fixed bits within a group, before any condition the row already has, and each field becomes its bit range.
The template's guard comes first because the template is part of the pattern: `&&` evaluates left to right, so a condition of yours is evaluated only on values the template matches, and a function it calls that is defined only there is never applied outside them.
K emits `rule decode ( Krs_Bits0:Int ) => inc r8 ( bitRangeInt(Krs_Bits0:Int, 3, 3) ) requires .. andThenBool ((bitRangeInt(Krs_Bits0:Int, 0, 3)) ==Int 4)`: the value's variable is a generated one, which no binder of yours can collide with or shadow, and `krs expand` names it `bits` (or a fresh variant).
A template without `_` or fields is its decimal literal, `decode_halt` above is the row `118 => Halt`, so it is matched as a literal, without a guard.
Splitting runs at spaces keeps the guards of templates written on one grid (`xx yyy zzz`) on the same terms, so templates that differ in a fixed bit compare equal terms with different values: the rule-overlap check, which reads such guards as facts about the bits of a term, keeps `kindOf(k::bits!("0___ ____"))` and `kindOf(k::bits!("1___ ____"))` apart, and reads the same guards written by hand alike.

**Signed, shifted, and scattered fields.**
After the template, a modifier per field says how its value is read, the way an ISA manual draws the encoding:

```rust
k::equations! {
    for Decode;
    use Instruction::*;
    addi: k::bits!("iiiiiiiiiiii sssss 000 ddddd 0010011", i: signed)                        => Addi(d, s, i);
    sw  : k::bits!("iiiiiii ttttt sssss 010 iiiii 0100011", i: signed[11:5 | 4:0])           => Sw(t, s, i);
    beq : k::bits!("bbbbbbb ttttt sssss 000 bbbbb 1100011", b: signed[12 | 10:5 | 4:1 | 11]) => Beq(s, t, b);
    lui : k::bits!("uuuuuuuuuuuuuuuuuuuu ddddd 0110111", u: signed[31:12])                   => Lui(d, u);
}
```

- The brackets list the value bits that the field's template bits carry, most significant template bit first, in the manuals' notation: `hi:lo` is a run of bits from `hi` down to `lo`, and `n` is one bit. RISC-V's B-type immediate is `imm[12|10:5]` in bits 31 to 25 and `imm[4:1|11]` in bits 11 to 7, so `b`'s twelve template bits carry `[12 | 10:5 | 4:1 | 11]`.
- Value bits that no template bit carries are zero: B-type's bit 0, and bits 11 to 0 of LUI's `u`, which is the immediate already shifted into place.
- `signed` reads the value as two's complement of its width, one more than its highest value bit: ADDI's `i` is in -2048..2047, and BEQ's `b` is an even offset in -4096..4094.
- A letter whose bits are not adjacent needs the brackets (``field `b` is split`` otherwise): joining its parts in template order would be a guess, and a wrong one for B-type.

The long form stays arithmetic over bit ranges: each piece is its `bit_range`, times the power of two of its lowest value bit, and the pieces are summed; a signed field then subtracts its sign bit times `2^width`.
`addi`'s `i` is `bits.bit_range::<Int>(20, 12).sub::<Int>(bits.bit_range::<Int>(31, 1).mul::<Int>(4096))`.
The prover reads a bit range by constant amounts as division and remainder and the rest as linear arithmetic, so it decides claims about such fields exactly: under `k::bits!(i, "1___ 0011")`, the signed field of `k::bits!("iiii 0011", i: signed)` is proven to be `(i - 259) / 16`.

A template stands in an `Int` argument of a rule's, an equation's, or a table row's left-hand side, or in an argument of a sort above `Int`; at a position of another sort, such as `Bool`, it is `krs::analysis::bit-template-sort`, reported at the template.
In a readable configuration rule it may also be the computation cell's first item, `{ k: [k::bits!("0000 01xx"), ..], acc } => { k: [x, ..], acc: int::add(acc, x) }`, whose fields every result term reads; a field in the result of an optional or collection cell, which is state syntax rather than a term, is `krs::syntax::bit-template-position`.
As a pattern, a template is rejected in a result, a guard, a `cells!` cell pattern, a context, or an alternative of `|` (`krs::syntax::bit-template-position`), as is an unnamed template in a sentence that lists its binders, whose value must be named to be listed.
A character that is no bit, an empty template, more than 128 bits, a split field without its value bits, and a malformed modifier (one that names no field, a second one for a field, value bits written upward or twice, a count of value bits other than the field's template bits, or a value bit of 128 or more) are `krs::syntax::invalid-bit-template`; a field letter that is also a binder of the sentence, a field of another template, or a name a `let` or `k::matches!` binds again is `krs::syntax::bit-field-collision`.
In a table, two rows that match one argument with templates of different widths are `krs::syntax::bit-template-width-mismatch`, a missing or extra bit being the likely cause, and two rows without an authored `requires` whose templates and literals share a value are `krs::syntax::duplicate-equation-row`, naming the arguments both apply to.

**Testing a value.**
`k::bits!(op, "01 yyy zzz")`, with the value first, is the template as a test: a `Bool` term, for a `requires`, a claim, or any other place a `Bool` term may stand.
It is `op >= 0 && op < 2^width` followed by one `bitRangeInt` equality per run of fixed bits: the terms of the pattern `k::bits!("01 yyy zzz")`'s guard, in the same order, so a claim can state exactly what a row tests.
A claim need not restate the guard, though: the prover reads a `bitRangeInt`, a shift or a low-bit mask by constant amounts as division and remainder by a power of two, so `0 <= op < 8` is enough to reach a row whose template is `"0aaa"`, and an argument outside every template's range reaches the `owise` row even past a literal row.
A template without free bits tests the same terms; only the pattern turns it into a literal.
Field letters and `_` constrain nothing in a test, and a test binds nothing: its letters are accepted so that a row's template can be copied as it is, and outside the test a letter is only what the sentence's own binders make it, usually unbound.
The value is a variable, a field of the sentence's own template, or a bit range of a variable (`x.bit_range::<Int>(0, 8)`).
The long form reads it once per term, so a larger term, which would be repeated as many times, is bound to a name first: `op @` in the pattern, or a `let` (`krs::syntax::invalid-bit-template` otherwise).
`k::bits!("..")` alone in a condition or a result is `krs::syntax::bit-template-position`; a test takes no field modifiers, since it binds no field, and a pattern takes its template first (`krs::syntax::invalid-bit-template` otherwise).

**Migrating from field functions.**
A decoder written with field functions, such as `FieldX(op) = op >> 6` and `FieldY(op) = (op >> 3) & 7` in guards like `FieldX(op) == 0 && FieldZ(op) == 4`, becomes one template per row:

- the fixed fields become fixed bits, and each field the row reads becomes a letter that the result uses directly: `FieldY(op)` becomes `y`;
- a row that also needs the whole value keeps it with `op @ k::bits!(..)`, as `decode_ld_r_r` above does for `op.ne::<Int>(118)`;
- a field computed from another (`FieldY(op) - 4` for the two low bits of `y`) becomes its own letters, `"00 1cc 000"`;
- the template also requires `0 <= op < 2^width`: a guard that reads its top field without a mask (`op >> 6`) already did, but one that masks it (`(op >> 6) & 3`) also matched values such as `260`, which a template leaves to the `owise` row;
- the field functions, which the templates no longer call, can go, and a claim that restated a guard writes `k::bits!(op, "00 yyy 100")`.

#### Overlapping equations

Equations are unordered, so two equations of one function at one priority that apply to one argument state that their results are equal there.
KRS checks this on the assembled definition, for table rows and `#[k::equation]` fns alike, guarded or not.
When the equations bound their `Int` arguments to at most 2^16 argument vectors, as for the [coverage check](#coverage-of-total-functions), it evaluates every `requires` on each of them.
Otherwise it compares them pair by pair: it unifies the two equations' patterns over the definition's sorts (a binder `ty: Term<Ty>` does not match `TyUnknown()` of the supersort `MaybeTy`, but a binder of the field's sort `MaybeTy` does), and where they unify it decides the two `requires` together with the coverage check's reading of guards, which proves most pairs disjoint (`d == 0` and `d != 0`; `x == y`, `y == z` and `x != z`; `pc < 0` and `pc >= bytes::length(code)`).
A pair it cannot prove disjoint is reported only when it can exhibit an argument: integer values at which both `requires` evaluate to `true` and the results differ.
Two equations that both apply to one argument, with results that differ once the argument is substituted and builtins on literals are evaluated, are `krs::analysis::overlapping-equations`.
`decode_ld_r_r` above with a typo in its guard, `op.ne::<Int>(117)`, is (without any `requires`, the table check above reports the two rows first)

```text
error[krs::analysis::overlapping-equations]: equations `decode_halt` and `decode_ld_r_r` of `Decode` both apply to `Decode(118)` at the same priority and give it different results, `Instruction::Halt` and `Instruction::Ld(R8(6), R8(6))`; ..
```

The pair check finds the overlap of a binder at a field's wider sort, as in this lookup, where `lookup_known` binds `ty` at `MaybeTy`:

```text
error[krs::analysis::overlapping-equations]: equations `lookup_known` and `lookup_unknown` of `Lookup` both apply to `Lookup(_, Maybe::TyUnknown)` at the same priority and give it different results, `map::get(_, Maybe::TyUnknown)` and `TypeInfo::Void`; ..
```

Two arms of one [branching body](#branching-bodies) that overlap are `krs::analysis::overlapping-match-arms` instead, at the later arm.
Identical results agree, so equations that overlap with them are no error.
A `k::matches!` test is read as the coverage check reads it, which proves disjoint the equations a test and its negation separate, and evaluated on the concrete argument as matching.
An application of a `total` function that neither the backend nor the SMT solver defines, and none of whose equations reads the configuration, is evaluated by the function's own equations (unless the definition has a `raw_k!` sentence): in the lowest priority (`owise` is 200) at which an equation's patterns match and its `requires` evaluates to `true`, every such equation must give the same value, which is the application's value.
The evaluation gives up, and the pair is not reported, when no equation applies, two applying equations give different values, a pattern or `requires` is one it cannot evaluate, a `requires` is undefined there (where a lazy and a strict reading disagree), or the calls nest deeper than 64 or exceed 4096; so it states only values the definition states.
The same evaluation decides the bounded case above, so `Field(op) == 1` on `0 <= op < 8` is evaluated on each of the eight values.
A pair is not reported when a pattern is one the check does not decompose (a collection pattern), when a `requires` calls a function the evaluation cannot evaluate or a partial operation the guard reading does not read, or when none of the integer values it tries, up to 64 arguments per pair, makes both `requires` evaluate to `true`; templates over more than 16 bits are compared pair by pair, and the table check above still compares unguarded rows' templates of any width.

### Sort-parametric productions

A K sort parameter is a Rust type parameter of a production struct with exactly the bound `?Sized` (sort markers such as `dyn ExpSort` are unsized); `sort = S` and `k::Term<S>` fields name it.
Read `<S: ?Sized>` as K's `{S}` and `k::Term<S>` as a term of sort S.

```rust
#[k::function(total, sort = S, syntax = "choose({cond}, {then_branch}, {else_branch})")]
pub struct Choose<S: ?Sized> {
    pub cond: Term<Bool>,
    pub then_branch: Term<S>,
    pub else_branch: Term<S>,
}

#[k::equation]
fn choose_true_int(
    k::term![Choose::<Int> { cond: true, then_branch: a, else_branch: _ }]: Term<Int>,
) -> Term<Int> {
    a
}
```

It emits `syntax {S} S ::= "choose" "(" Bool "," S "," S ")" [symbol(choose), function, total]`, and the equation `rule choose ( true , A::Int , _::Int ) => A:Int`.
Rust generics are monomorphised, so one generic fn body would serve every instance; a K rule never quantifies over sorts, so each equation or rule head names its instance with a turbofish, and each layer has one spelling for its argument.
Reference code writes the sort marker that goes inside `k::Term<..>` (`Choose::<Int>`, `Choose::<dyn ExpSort>`); the alias `Choose::<Exp>` there would mean `k::Term<k::Term<..>>` fields to rustc, so it is a compile error that names the marker.
A readable `k::rules!` clause writes the sort (`Choose::<Exp>`), a marker there is rejected with the sort's name, and `krs expand` renders the marker, `Choose::<dyn crate::ExpSort>`.
The emitted head writes each variable at a parameter position as K's strict cast to its own sort, `A::Int`, and a wildcard as `_::Int`: a semantic cast `A:Int` there would let K instantiate the parameter at `K`, and the equation would never apply.
Natively, labels never carry sort parameters; those variables are sorted at the same sorts and k-rust solves the instance from them, bounded by the rewrite's sort, exactly as K's text solver does.
A head whose binders all sit below its turbofish (`Choose::<dyn ExpSort>` over two `Term<Int>` binders) would be solved at `Int` instead, so it is rejected (`krs::analysis::native-instance`).
Terms elsewhere need no turbofish: K solves the instance from the arguments, bounded by the position when the result is the parameter, and KRS mirrors that solver; a term whose instance has no unique least solution is rejected, and a turbofish there must name the instance K solves.

A parametric constructor is a value-building schema: `#[k::constructor(sort = S, syntax = "wrap({inner})")] pub struct Wrap<S: ?Sized>` emits `syntax {S} S ::= "wrap" "(" S ")"`, so `wrap(v(7))` is a `Val`; it cannot be instantiated at a sort whose values its domain or hook fixes (Int, Bool, String, a token sort).
The backends differ: equations of parametric functions run on the k-rust and Java Haskell routes and the LLVM routes refuse them (K's llvm-kompile crashes on them, whether Java K or k-rust wrote the KORE), while parametric constructors run on the k-rust and Java LLVM routes and Java K's Haskell backend rejects them (`krs::capability::unavailable` on the route that lacks the feature).
K's own `#if` (`kequal::ite`) is a hooked parametric function.

A lifetime, const, defaulted, otherwise bounded, or unused parameter, a where clause, generics on an enum family (a parameter belongs to one production), on a sort trait (K and k-rust have no user parametric sorts), or on a rule fn (``K rules never quantify over sorts``), and a turbofish with a lifetime, a const, or the wrong arity are rejected; so are a parameter named like a sort, strictness, an alias or desugar marker, a hook, a token, or a bracket on a parametric production (`krs::analysis::invalid-parametric-production`), and an equation or rule head without a turbofish, with one that disagrees with its declared sort, or with a non-variable argument below the instance (`krs::analysis::parametric-instance`).

### Local rewrites

K writes a rule as one pattern with `=>` inside it, around exactly what changes; the rest of the pattern is the frame.
A `#[k::rule]` fn that returns `()` is such a single-body rule: its `k::cells!` or term subject (with or without `k::term![..]`) is the whole rule, and `k::rewrite!(from => to)` marks each change.
One whose subject marks no change changes nothing, a mistake of the whole rule told at its name (`krs::syntax::invalid-local-rewrite`); a construct its subject or its conditions may not hold where they stand is told first, at the construct, since it must go whatever the rule changes, and a names mistake after it: a name the subject reads but nothing binds, or a binder list that declares a name the subject does not bind.

```rust
#[k::rule(label = "assign")]
pub fn assign(
    name: Term<Id>,
    value: Value,
    k::cells! {
        k: k::configuration::KCell(k::rewrite!(StmtSyntax::Assign(name, value) => ()), ..),
        env: k::configuration::Cell(map![name -> k::rewrite!(_ => value), ..]),
        state @ ..
    }: Machine,
) {}
```

emits `rule [assign]: <k> (Name:Id = Value:Value ; => .K) ... </k> <env> Name:Id |-> (_ => Value:Value) ... </env>`, and the term-shaped `fn unmark_left(k::term![ExpSyntax::Pair(k::rewrite!(ExpSyntax::Marked(value) => value), _)]: Term<Exp>) {}` emits `rule pair ( (marked ( Value:Exp ) => Value:Exp) , _ )`, completed at the head of the computation cell like any term rule.
A readable rule, or a reference rule with a result, states the before and after of each cell it changes, which is the same rule; the single-body form is reference-only.
The left side of a rewrite is a pattern and binds like the rest of the subject; the right side is a term built over those bindings, in which a `let` binds its names in the rest of its block and a `k::matches!` pattern its own, as in a result: `k::rewrite!(p => { let Pair(x, y) = p; Pair(y, x) })` emits `(P:KItem => ( #let pair ( X:Exp , Y:Exp ) = P:KItem #in pair ( Y:Exp , X:Exp ) ))`. `()` on the right is `.K`, which removes a whole K-sequence item.
The binder list of a `cells!` rule declares the left image's binders (the subject with each rewrite replaced by its left side), in first-occurrence order.
In a map a rewrite changes a value: `name -> k::rewrite!(_ => value)` requires the key to exist, while `map::update` in a result would add it, so assigning an undeclared variable is stuck in the local form and proceeds in the restating one.
A key is what the map is looked up by, so a rewrite never stands in one: moving an entry to another key is a removal and an insertion, which may meet a key the map already holds; a rule with a result writes it with `map::remove` and `map::update`.
A frame variable written once is a variable K sees once; write `_` for it.
The syntax rejects `k::rewrite!` outside the subject of a single-body rule (in ordinary code it is a compile error), in a rule with a result, in a readable clause, inside another rewrite, in a map key, with a right-side name the left image does not bind, and a single-body rule without a rewrite, with statements in its body, or with `#[k::exists]`, `#[k::ensures]`, or `#[k::fresh]` (`krs::syntax::invalid-local-rewrite`).
A single-body rule is a transition; the overlap check and inference read each rewrite through its left and right images.

### Heating and cooling

`#[k::strict]` and `#[k::seqstrict]` ask K to generate the rules that evaluate a production's arguments; `#[k::rule(heat, hole = h)]` and `#[k::rule(cool, hole = h)]` write those rules by hand, K's `[heat]` and `[cool]`.
A heat rule moves the subterm its `hole` names to the front of the computation and leaves a freezer behind; a cool rule plugs a finished value back into the freezer's place.
Freezers are ordinary `KItem` constructors, written as a reference family, `#[k::constructors(sort = k::KItem, reference)]`, like the frames of a CEK machine's continuation stack.

```rust
k::rules! {
    for Machine;
    use Op::*;

    #[k::rule(heat, hole = h)]
    #[k::requires(k::is!(KResult, e))]
    heat_add_rhs: { k: [Add(e, h), ..] } => { k: [h, Freezer::AddRhs(e), ..] };
}

#[k::rule(cool, hole = h, label = "cool-add-rhs")]
pub fn cool_add_rhs(
    h: Exp,
    e: Exp,
    k::cells! { k: k::configuration::KCell(h, Freezer::AddRhs(e), tail @ ..), state @ .. }: Machine,
) -> Machine {
    k::cells! { k: k::configuration::KCell(Op::Add(e, h), ..tail), ..state }
}
```

emits `rule [heat-add-rhs]: <k> E:Exp + HOLE:Exp => HOLE:Exp ~> freezer1 ( E:Exp ) ... </k> requires isKResult(E:Exp) [heat]` and `rule [cool-add-rhs]: <k> HOLE:Exp ~> freezer1 ( E:Exp ) ~> Tail:K => E:Exp + HOLE:Exp ~> Tail:K </k> [cool]`.
The hole binder is always spelled `HOLE` in the emitted K, and no other binder takes that name; it is listed in a binder list like any other binder.
K adds `requires notBool isKResult(HOLE)` to every heat rule and `requires isKResult(HOLE)` to every cool rule, so the rules carry no such guard; `result = Value` (K's `result(Value)`) uses `isValue` instead.
Replacing hand-written rules for `+` and `&&` by `#[k::seqstrict]` gives the same steps: both run lesson 14 of the K tutorial alike natively and on Java LLVM, heat, compute, cool.
The keys are written the same way on a readable `for Machine` clause and a `cells!` rule, so the cool rule above is also `cool_add_rhs: { k: [h, Freezer::AddRhs(e), ..] } => { k: [Add(e, h), ..] };` under `#[k::rule(cool, hole = h)]`, which emits `...` where the `cells!` rule names its tail.
A heat or cool rule holds whatever follows it, so `krs check` rejects one whose computation-cell pattern is a whole cell (`krs::analysis::invalid-heat-cool`).
The syntax rejects `heat` with `cool`, either without `hole = x`, `hole` or `result` without either, and either with `owise`, `priority`, `nondet`, or `anywhere`, and `#[k::fresh]` on a heat or cool rule, when the macros expand; and `krs check` rejects a hole that the left side does not bind, or binds twice (`krs::analysis::invalid-heat-cool`).
Heat and cool rules are outside the overlap check, since K orders them by the condition it adds.

### Contexts

A context says where evaluation may happen, and K turns it into a heat rule and a cool rule, as in [Heating and cooling](#heating-and-cooling), with a generated freezer.
`#[k::context(hole = h)]` on a fn that returns `()` is K's `context`: its subject is the whole context, and `hole = h` names the binder K calls `HOLE`, as `here = site` names the binder a context alias calls `HERE`.
A `k::term!` subject is completed to the computation cell by K; a `k::cells!` subject may also constrain other cells, and then lists its binders, the hole included.

```rust
#[k::context(hole = h)]
#[k::requires(k::is!(KResult, e))]
fn add_rhs(k::term![Op::Add(e, h)]: Term<Exp>) {}

#[k::context(hole = h)]
fn increment_target(k::term![Op::Inc(k::rewrite!(h => Op::LValue(h)))]: Term<Exp>) {}

#[k::context(hole = h, result = ExecResult)]
fn assign_target(
    h: Exp,
    k::cells! {
        k: k::configuration::KCell(Op::Assign(h, _), ..),
        evaluate: k::configuration::Cell(true),
        state @ ..
    }: Machine,
) {}
```

emits

```text
context [add-rhs]: E:Exp + HOLE:Exp
    requires isKResult(E:Exp)
context [increment-target]: ++ (HOLE:Exp => lvalue ( HOLE:Exp ))
context [assign-target]:
    <k> HOLE:Exp = _ ... </k>
    <evaluate> true </evaluate>
    [result(ExecResult)]
```

The label defaults to the fn name with `_` written `-`, and K labels the rules it generates `add-rhs-heat` and `add-rhs-cool`; `label = ".."` names it explicitly, and `result = S` is K's `result(S)`, as on a heat or cool rule.
One `k::rewrite!` of the hole, `HOLE => term-containing-HOLE`, evaluates a different term in its place: here the operand of `++` is evaluated by the rules for `lvalue(..)`, and cooling plugs that term's evaluated operand back.
The hole lies in the computation cell, because heating moves it to the front of `k`; the other cells may only constrain when the context applies, as the `evaluate` cell does here.
A context alias takes `result = S` too, `#[k::context_alias(name = translate, here = site, result = ExecResult)]`, and context aliases may share a name: K instantiates each of them for every production strict through that name.
Lesson 14 of the K tutorial with contexts for `+` and `&&` runs like `#[k::seqstrict]` natively and on Java LLVM, through the generated rules.
The syntax rejects a context without `hole = x`, with a result, a body, or more than one `k::rewrite!`, with an incomplete or misordered binder list, and with `#[k::exists]`, `#[k::ensures]`, or `#[k::fresh]`; `krs check` rejects a hole the pattern does not bind or binds twice, a rewrite of anything but the hole or to a term without it, and a hole, or a context alias's `HERE`, outside the computation cell (`krs::analysis::invalid-context`).
A context's subject, and a context alias's, match the computation's evaluated terms as a rule's does, so a function applied there never matches and is refused ([functions in patterns](#functions-in-patterns)).
Contexts are outside the overlap check.

### Anywhere rules

Most rules act at the head of the computation cell, and equations act wherever their function appears.
`#[k::rule(anywhere)]` gives a constructor that behaviour while it stays a constructor: the rule applies to every subterm its left-hand side matches, and emits `[anywhere]`.
It is written as a term-shaped `#[k::rule]` function, never as a readable clause or a `cells!` rule, takes no `owise`, `priority`, or `nondet`, and is outside the overlap check.
The k-rust route and Java K's LLVM backend run anywhere rules; K's Haskell backend does not, so a Java Haskell reference step refuses such a definition with `krs::capability::unavailable` before anything is kompiled, and `--allow-anywhere-haskell`, which would drop the rules, is never used.
`krs emit-k` still writes the rule, marks it with a `// krs-capability: AnywhereRule <label>` comment, and lists the requirement in `symbols.json`.

### Existential results and ensures

A rule normally computes its result from what it matched.
`#[k::exists(x: Int)]` after `#[k::rule(..)]` says the result contains an unknown integer: the step introduces a symbolic value, which K writes `?X:Int`, and `#[k::ensures(int::ne(x, 0))]` records a condition on it that holds on every later path.
The same helpers work on a term rule, a `cells!` rule, and a readable clause, where `krs expand` keeps them verbatim before the clause's `#[k::rule(label = ..)]`; on a claim they keep their meaning there, a value the prover must exhibit.
An existential occurs only in the result and the ensures condition: one in the subject or in `requires`, one the result never mentions, and one that reuses a subject binding's name are syntax errors, and the helpers on an equation, simplification, or alias are rejected.
An existential, like a fresh value, has exactly its declared sort: one written where that sort does not fit, `#[k::exists(v: Stmt)]` in an `Int` field, is `krs::analysis::incompatible-binder`, and `krs::analysis::collection-element-sort` at a typed element position.
Ensures conditions are object-language Bool terms.
This is symbolic execution, unlike Rust's `rand()`, which produces a concrete value: the Haskell backend and k-rust run such rules, and `krs search` reports one final state per path with its constraints.
Concrete (LLVM) execution cannot, so `krs build --backend llvm` refuses a definition with an existential rule (`krs::capability::unavailable`), `krs emit-k` marks the rule with a `// krs-capability: RuleExistential <label>` comment, and an LLVM build of a rule with `ensures` alone warns that the condition is ignored (`krs::capability::ignored-ensures`).
An existential of a collection sort ranges over every collection of that sort, whatever a typed cell declares, so a rule may not write one into a typed position (`krs::analysis::untyped-collection`); introduce the elements instead, as in `env: map::update(e, name, v)` with `#[k::exists(v: Value)]`, or declare the cell without element types.
`#[k::exists(...)]` and `#[k::ensures]` bind and constrain claim results in the same way, and a claim's `requires` and `ensures` may also be [matching-logic predicates](/verification/reachability-claims#matching-logic-predicates).
Cell-field helpers carry names, colors, nesting, multiplicity (`?` or `*`), `initial`, and cell collection type (`Set`, `Map`, or `List`) only in the shapes described in [optional cells and cell collections](#optional-cells-and-cell-collections) and [current boundaries](/reference/boundaries).

### Fresh values

`#[k::fresh(l: Loc)]` on a rule declares a value the step creates, as an allocator returns a new address: K writes it `!L:Loc` and fills it from the `<generatedCounter>` cell, which every fresh value of every sort advances.
The value does not exist until the step happens, so it cannot be matched: a fresh name occurs only in the result and the ensures condition, and one that is also a pattern binding, one in `requires`, and one the result never mentions are rejected (`krs::analysis::fresh-binder-position`).
K calls the sort's generator on the counter value: Int and Id have K's own (`freshInt`, `freshId`), and any other sort needs exactly one `#[k::function(total, fresh_generator, sort = Loc, syntax = "freshLoc({seed})")]` of one Int field, with equations such as `freshLoc(seed) => loc(seed)` (`krs::analysis::no-fresh-generator`, `krs::analysis::duplicate-fresh-generator`, `krs::analysis::invalid-fresh-generator`).
So `alloc a; tx; alloc b; tx;` with a fresh `Loc` in `alloc` and a fresh `Int` in `tx` allocates `loc(0)` and `loc(2)` and records transactions `1` and `3`.
The helper is written the same way on a term rule, a `cells!` rule, and a readable clause, where `krs expand` keeps it verbatim before `#[k::rule(label = ..)]`, and `#[k::fresh]` before `#[k::rule]` is handed to the rule; fresh names are not binder parameters.
Only a transition step reads the counter, so `#[k::fresh]` on an equation, simplification, alias, claim, context, context alias, anywhere rule, or heat or cool rule is rejected (`krs::expand::fresh-placement`).
Unlike `?X` from `#[k::exists]`, a fresh value is concrete, so every backend runs such rules; K assigns the counter offsets of several fresh binders of one rule in an unspecified order (k-rust: by name), so results that depend on that order differ between backends.

### Trusted claims

`#[k::claim(all_paths, label = "helper-axiom", trusted)]` states an axiom: the prover assumes the claim without proving it and may apply it while proving other claims, which K writes `[trusted]`.
`krs prove` reports it `trusted`, never `proven`, and every prove run and Haskell build warns once per trusted claim (`krs::emit::trusted-claim`).
`trusted` is a bare flag after the label: a repeated `trusted`, `trusted = true`, and `trusted` with `circularity` are syntax errors (see [trusted claims](/verification/reachability-claims#trusted-claims)).

### SMT translations of functions

Z3 knows Int arithmetic but not your functions: during symbolic execution and proofs an application such as `myAbs(I)` is an unknown value to it.
Two keys of `#[k::function]` change that, and both are trusted, because nothing checks them against the function's equations.
`smtlib = "probeH"` gives the function a name in Z3, the uninterpreted SMT-LIB symbol `probeH`: Z3 then knows only that equal arguments give equal results (K's `smtlib(probeH)`).
`smt_hook = "(ite (< {value} 0) (- 0 {value}) {value})"` gives it a meaning in Z3's language, an SMT-LIB term over the arguments, so a claim such as `go(I) => true` after the rule `go(I) => myAbs(I) >=Int 0` is proved even though `myAbs` has no equation.
The template is checked like a `#[k::syntax]` template: each `{field}` names a field of the function (a field may occur any number of times, and `{{`/`}}` spell braces), the text is one balanced S-expression, and K's positional `#1` and a `"` are rejected; KRS emits K's `smt-hook(..)` with each placeholder renumbered to its field's position, so `clampSub({low}, {value})` with `(- {value} {low})` emits `(- #2 #1)`.
The two keys are mutually exclusive, and `smtlib` may be combined with a typed `hook`, so the hook computes concrete values while Z3 sees a symbol (`krs::syntax::invalid-smt-metadata`); two functions with one `smtlib` symbol are rejected, because Z3 would treat them as one function (`krs::analysis::duplicate-smtlib`).
A function with an `smt_hook` and no equation means something only to Z3: concrete execution leaves its applications unevaluated, and `krs build --backend llvm` warns (`krs::emit::smt-only-function`); `krs prove` and Haskell builds, which hand it to Z3, do not.

### Concrete, symbolic, and SMT lemmas

A simplification fires on any term its left side matches, whether the matched values are ground or contain variables.
Three keys of `#[k::simplification]` and `#[k::equation]` change that; they name left-hand binders by their Rust names and are written after the priority:

```rust
#[k::simplification(concrete(x), smt_lemma)]
fn h_concrete(k::term![H(x)]: Term<Int>) -> Term<Int> { int::add(x, 1) }
#[k::simplification(priority = 40, concrete(c), symbolic(s))]
fn fold_constant(k::term![int::add(int::add(s, c), d)]: Term<Int>) -> Term<Int> { int::add(s, int::add(c, d)) }
#[k::equation(concrete, smt_lemma)]
fn chop(k::term![Chop(i)]: Term<Int>) -> Term<Int> { int::rem_euclid(i, 256) }
```

`concrete(x)` applies the sentence only when `x` is ground, the usual guard on constant folding that would loop on symbols; bare `concrete` restricts every left-hand binder.
`symbolic(x)` applies it only when `x` contains a variable.
`smt_lemma` hands the equation to Z3 as an axiom, so the solver can use it on terms the prover never rewrites; like an SMT translation it is trusted, not checked.
KRS emits K's attributes with the sentence's variable names, before the label: `[simplification, concrete(X), smt-lemma, label(..)]`, `[simplification(40), concrete(C), symbolic(S), label(..)]`, and `[concrete, smt-lemma, label(..)]`.
Syntax errors (`krs::syntax::invalid-match-restriction`): a repeated key, `concrete` both bare and with a list, an empty list, a value on a key, and any of the keys on `#[k::rule]`, since restrictions apply to equations and simplifications.
Analysis errors (`krs::analysis::invalid-match-restriction`): a listed name that is not a left-hand binder, a binder restricted both ways (bare `concrete` with any `symbolic` restricts every binder twice), and an equation whose function's other equations are not bare `concrete` (or `symbolic`) too, which K rejects ("Found concrete attribute without simplification attribute on function with one or more non-concrete rules"); write the restricted case as a simplification instead.
An `smt_lemma` may mention only functions Z3 can see, so a user function needs `smtlib` or `smt_hook` and a builtin needs an SMT translation in the K prelude (`krs::analysis::smt-lemma-untranslatable`).

### Desugar and recursive aliases

A K macro rewrites the definition's rules and the input program once, before anything runs; it is not a runtime step, and it is not a Rust macro (there are no tokens and no hygiene).
KRS calls it `desugar`: `#[k::desugar]` on a production emits K's `[macro]`, and each `#[k::desugar] fn` is one clause, `pattern => replacement`, emitted as a plain `rule`.
`unless ({c}) {s}` with the clause `Unless(c, s) => IfThenElse(c, EmptyBlock(), s)` emits `rule unless ( C:Expr ) S:Stmt => if ( C:Expr ) { } else S:Stmt`, so `unless (false) x = 1;` runs as the if/else form.
An alias (`#[k::alias]`) expands the same way and also runs backwards when K prints a result; a desugar never does.
By default an expansion does not apply again to its own output; `recursive` on the production allows it: `#[k::desugar(recursive)]` emits `macro-rec` and `#[k::alias(recursive)]` emits `alias-rec`.
`int x, y, z;` with `DeclareMany(Ids::Cons(x, Ids::Cons(y, rest))) => Sequence(Decl(x), DeclareMany(Ids::Cons(y, rest)))` expands fully only when the production is `recursive`; with a plain `#[k::desugar]` it expands one step and leaves `int y, z;`, which Java K's LLVM backend leaves stuck and k-rust refuses to execute, because the macro symbol, which has no value of its own, is still in the program.
K does not check that a recursive expansion terminates; k-rust reports a non-terminating one when the definition is built.

`recursive` is a property of the production: a clause takes the plain marker or `unbound_variables` (below), and has no priority or `owise`.
A clause applies unconditionally, so `#[k::requires]` on a desugar or an alias clause is refused at the attribute (`krs::syntax::invalid-rule-key`): there is nothing to test a condition against before anything runs.
A clause takes its production's mode: a `#[k::desugar]` clause must expand a production marked `#[k::desugar]`, an `#[k::alias]` clause one marked `#[k::alias]`, and an alias or desugar production without a clause is rejected because nothing expands it (`krs::analysis::invalid-static-clause`); a clause's root is the production it expands, so a root that is none (a constructor of an unmarked production, a function, a literal) is refused at the root.

A clause's subject is matched by static expansion against terms as they are written, before anything evaluates: a program's terms, and the terms KRS writes in a definition's rules, equations and initializers, which kompile expands the same way. Two spellings of one value meet only if they are the same text, so KRS emits the subject as that match reads it, in the spelling KRS writes everywhere:
- below its root it holds what is written as one term, constructors, literals, tokens and names, and none of what computes: a function's application, a collection literal that builds (`map![k -> v]`, even with one entry, the update it denotes; `set![a, b]`), an index or a method there would stand for its spelling rather than its value (`f(x + 1)` would expand the program `f(y + 1)` but not `f(1 + y)`, where everywhere else the two are one value), so each is refused at the application (`krs::analysis::function-in-pattern`), and a sort test `k::is!`/`k::project!` at the construct (`krs::analysis::invalid-sort-test`; restrict a binder with a typed parameter, `fn f(x: Int, k::term![..])`), naming what to write instead: a rule or the function's equation to rewrite a computation, constructors to expand a term a program writes;
- a collection of two or more parts is refused (`krs::analysis::collection-in-static-subject`): static expansion neither reorders a set's elements or a map's entries nor regroups a list's parts, so `lw([1, 2, 3])` meets a rule's `Lw([1, 2, 3])` and `Lw(list::concat([1], [2, 3]))` but not `Lw(list::concat([1, 2], [3]))`; a list with a rest, named or not, is such a collection too. The empty collection, a set's singleton `set::item(x)` and a list's `[x]` have one spelling, and stay;
- an alias's or a desugar's application below its root is written expanded, since a program's is expanded before the clause is tried and the clause matches the expansion: with `zero() => red`, `dn(x, zero()) => b(x)` emits `rule dn ( X , red ) => b ( X )`, and `dn(1, zero())` expands to `b(1)`. KRS writes the expansion only where it needs no value: the application's arguments are ground, and the one clause whose subject matches them (constructors, names and tokens compared as written) expands it, through a `recursive` production's clauses too; or the production is not recursive and has one clause, whose parameters are plain names of the production's argument sorts, and the arguments take their places (`twice(a) => pair(a, a)` writes `twice(box(y))` as `pair(box(y), box(y))`, and `twice(n @ box(y))` as two copies of the alias, which one value matches; a clause that drops an argument drops it, `first(x, box(y))` being `one(x)`, where the clause names `y` nowhere else). A clause of a production that is not `recursive` applies once on a path, as the expansion that runs does: `pp(x) => wrap(qq(x))` with `qq(aa) => pp(bb)` leaves `pp(bb)` inside `pp(aa)`'s expansion unexpanded. Alternatives in a desugar's application's arguments are distributed first, `digit(0 | 1)` being `red | box(1)`. Otherwise which term the application stands for depends on what a program gives it, or there is none, and it is refused at the application (`krs::analysis::invalid-static-clause`), saying why: the arguments are not ground and the production is recursive, has several clauses or a clause whose parameters are patterns (write one clause for each of its clauses instead); the clause drops an argument binding a name the clause uses elsewhere, or copies one holding `_` or `|`; its result computes; no clause, or more than one, matches ground arguments; a clause that is not recursive would apply twice on one path; or the expansion repeats an application on its path, grows past 256 nested rewrites, or takes 10,000;
- a desugar's alternatives `A | B` are emitted as one clause per alternative, distributed over every constructor, alias and collection above them (`alt(z @ (box(x) | tag(x)), red)` is two rules, `alt((box(X) #as Z), red)` and `alt((tag(X) #as Z), red)`): static expansion does not match an or-pattern, and a desugar runs only forward, so `A | B` means either, which one clause each states. An alias's subject holds no `|` (below);
- a `k::bytes!` token has one spelling wherever KRS writes it, in a subject, a rule's result, an equation, an initializer or a claim: the one `krs run` prints but for `"` (`b"ab"`, `b"a\x22\n"`): each printable ASCII character as itself but `"` and `\`, a backslash, a newline, a tab, a carriage return and a form feed escaped (`\\`, `\n`, `\t`, `\r`, `\f`), and every other byte as `\xHH`, `"` included, since emitted K's `#token(..)` cannot carry `\"`; so a term KRS writes meets a subject KRS writes, and a program writing that spelling does too. A program writing the same bytes with other escapes (`b"\x61\x62"`) is not expanded, since static expansion compares token text; so with other tokens' spellings (`+1` and `1`).

An alias clause runs two ways, so it is judged both ways.
Forward, its subject is matched against the terms a program or a rule writes and its result is built; backward, when a result is [printed](#printing-through-the-grammar), each term its result matches, literals included, prints as its subject, built from what that match bound, wherever that subject expands back to the term; a clause whose subject holds its whole result (`twin(x, hold(x)) => hold(x)`) does not print backwards.
So the subject holds only what can be built from the result's bindings, and each of these is refused there at the construct (`krs::expand::irreversible-alias`), since the alias would print as a term that does not denote the printed value:
- `_`, which names no term the match gives a value: `wild(x, _) => b(x)` prints `b(1)` as `wild(1, _Krs_Wildcard0:Int)`;
- `name @ pattern`, a test of the term's shape that building cannot make: `named(y @ red) => one(y)` prints `one(green)` as `named(green #And red)`, no term, and one that does not expand back to `one(green)`;
- `A | B`, which denotes no one term: `either(box(x) | tag(x)) => pair(x, x)` prints `pair(1, 1)` as `either(box(1) #Or tag(1))`; write one clause per alternative instead;
- an open record `Ctor { f: x, .. }` and a list's anonymous rest (`[x, ..]`, `[.., z]`, `[a, .., z]`), whose fields or elements left out have no value from the match: `rec(Pair { a: x, .. }) => b(x)` prints `b(1)` as `rec(pair(1, _Krs_Wildcard0:Int))`.

A set's concatenation `set::concat(a, b)` in an alias's subject is refused as in a desugar's (a collection of two or more parts, above); printed backwards it would moreover write the parts the result's match bound, which may overlap: `elems(set::concat(set::item(x), rest)) => bs(x, rest)` would print `bs(1, set::item(1))` as `elems(SetItem ( 1 ) SetItem ( 1 ))`, which denotes no set.
An alias's or a desugar's application in an alias's subject is written expanded, as in a desugar's (above), and the alias prints back the term its expansion is: with `zero() => tag(9)`, `whole(zero()) => tag(0)` prints `tag(0)` as `whole(zero())`.

Every name the subject binds must be one the result uses, or it has no value when printing: `free(x, y) => b(x)` prints `b(1)` as `free(1, Y:Int)`, and is refused at `y`.
A name the result binds itself, in a `let` or a `k::matches!` pattern, is the result's own, so `free(x, y) => b({ let y = x; y })` is refused at `y` too.
A list of one element is one term the match binds, so `items([x]) => two(x, [])` prints `two(1, [])` as `items(ListItem ( 1 ))`; a list with a named rest is refused as any list of two or more parts is (above).
The result may compute (an application, an operator, a method, a sort test, `let`, `k::matches!`, a record update): the alias applies backwards only where a printed term holds the very application the clause's result writes, unevaluated (a symbolic value, or a function no rule evaluates, such as one only an `smt_hook` gives a meaning), and there the printed alias expands to exactly that term, so it denotes the printed value (`plus(a) => l(a + 1)` prints the stuck `l(N +Int 1)` as `plus(N:Int)`); a value whose applications are evaluated prints expanded. One exception is pending (finding NT-23-1): an application on ground arguments (`three() => 1 + 2`) is folded before the printer reads the clause, so the value `3` prints as `three`, which denotes it, though its expansion writes `1 + 2`.
For an expansion that runs only forward, write `#[k::desugar]`: its subject may hold every pattern construct below its root (`_` and `name @ pattern` stand below a subject's root in a desugar clause too, D3), and a name its result does not use.
A context alias (`#[k::context_alias]`) names a context, not a production, and is never printed backwards.
A production is an alias or a desugar, not both.

A desugar written in other rules' patterns may name variables that only the rule using it binds.
`#[k::desugar(unbound_variables = [n, _])]` on a clause lists them and emits K's `unboundVariables(N, _)` with the sentence's variable names; `_` admits wildcards in the result.
With `Twin() => Pair(n, Pair(n, rest))` under `unbound_variables = [n, rest]`, the rule `TestTwin(name, Shape::Twin()) => Assign(name, 1)` expands to a pattern that matches `pair(3, pair(3, 7))` and not `pair(3, pair(4, 7))`, and `AnyPair() => Pair(_, _)` under `unbound_variables = [_]` matches any pair; each use of the desugar gets fresh variables on both routes.
A listed name must occur in the result and must not be bound by the clause's pattern, `_` needs a `_` in the result, and the key applies only to desugar clauses: an ordinary rule's unbound right-side name is an error (`krs::expand::unbound-name` for a snake-case name; a `PascalCase` name is a constructor reference, which rustc resolves), and `unbound_variables` on a rule, equation, simplification, claim, context, context alias, alias clause, or production marker is rejected (`krs::syntax::invalid-unbound-variables`).

### Console I/O and the exit cell

`#[k::cell(stream = "stdin")]` and `#[k::cell(stream = "stdout")]` connect a `List` cell to standard input or output, and the bare flag `#[k::cell(exit)]` makes an `Int` cell's final value the process exit status, like `std::process::exit`.
I/O in K is configuration state: a rule reads by consuming the front of the input cell, `input: [x, ..] => input: [..]` (or `input: [x, rest @ ..] => input: rest`) with `where x: Int`, and prints by appending to the output cell, `output: out => output: [..out, x]`; K adds the rules that connect the cells to the process.
K feeds input only to that read, so KRS emits it as K's `<input> ListItem(X:Int) => .List ... </input>` and rejects any other rule over a stdin cell.
A stream cell starts as `list::empty()`, because K replaces its content with the stream; at most one cell connects to each stream and it is outside every repeated cell, at most one cell is the exit cell and it is outside every repeated cell, and the computation cell is neither (`krs::analysis::console-cell`).
Configuration initializers accept such ground terms directly: `input: list::empty()`, `status: 1`.
`krs run` reads standard input to end of file before the first step, as `krun --io off` does, prints what the output cell holds when the run ends, and exits with the exit cell's value; give the program as a file, because FILE `-` and the stdin cell would both read standard input.
Because I/O is state, search and rollback stay sound, but K's search has no console I/O, so `krs search` refuses a definition with stream cells; `krs prove` treats them as ordinary List cells.

## Program syntax and the module pair

K decides what a program may contain with the main syntax module and what rules may use with the main module.
KRS therefore emits two modules for each package: `<NS>-SYNTAX` holds the grammar programs may use, and `<NS>` imports it and adds everything only rules may use, the configuration, and the rules.
Each production chooses its module; the Rust module that declares it plays no part.

| Production | Module | In programs |
| --- | --- | --- |
| `pub` | `<NS>-SYNTAX` | yes |
| `pub` and `internal` | `<NS>` | no; rules, including a dependent package's, may use it |
| not `pub` (also `pub(crate)` and `pub(in ..)`) | `<NS>` | no |
| `pub` with a `Map`, `List`, or `Set` result or field | `<NS>`, placed automatically because K has no MAP-SYNTAX, LIST-SYNTAX, or SET-SYNTAX module | no |

A production that is not `pub` is also emitted with K's `private` attribute: K hides it from every importing module, so a dependent's rules, programs, and claims cannot name it, and `krs check` rejects a claim or a spec-module simplification lemma that does with `krs::analysis::private-production-in-spec` (see [Spec modules](/verification/reachability-claims#spec-modules)).
Token productions follow the visibility of their `#[k::token]` carrier: the tokens of a struct or type alias that is not `pub` are `private` too, so only the package's own rules lex them, a spec module does not, and `krs check` rejects a program production whose field sort has only private tokens (`krs::analysis::invalid-token-sort`), because no program could spell that field.
Only K rules construct the variants of a `#[k::constructors]` family that is not `pub`, so the macro allows rustc's `dead_code` lint on it.
`internal` is the bare flag `#[k::syntax("...", internal)]` on a variant, `internal = true` in the reference layer and on `#[k::constructor]`, a bare flag on `#[k::function]`, or the family flag `#[k::constructors(sort = ..., result = ..., internal)]`, which marks every variant.
A function that is not program syntax may omit `syntax` and gets the default `symbol({field}, ..)`; see [Functions declared by a fn](#functions-declared-by-a-fn).
`program` is spelled the same way and asserts that a production is program syntax; when KRS must place it in `<NS>` anyway, it reports the warning `krs::partition::not-program-syntax`.
`krs check --partition` prints each package's partition: the contents of `<NS>-SYNTAX`, then the `pub` productions placed in `<NS>` with the reason.

Builtin operations such as `+Int` and `andBool` are never program syntax, because `<NS>-SYNTAX` imports builtin sorts only through `INT-SYNTAX`, `BOOL-SYNTAX`, `ID-SYNTAX`, `STRING-SYNTAX`, and `BYTES-SYNTAX`.
`int-literals = "unsigned"` in `[package.metadata.krs]` selects `UNSIGNED-INT-SYNTAX` instead, so a program's `-1` is a unary minus applied to `1`; rules keep signed literals because `<NS>` imports K's integer module.

A dependency package may hold rules but no configuration: a `for Exp` rule rewrites the computation cell of whichever package declares the configuration.
Its module must import that configuration, while the configured package's `<NS>` imports the dependency, and K rejects the cycle.
KRS then emits the configuration in a third module, `<NS>-CONFIGURATION`, which imports `<NS>-SYNTAX` and every import of `<NS>` that does not import `<NS>` back; the dependency's module imports `<NS>-CONFIGURATION` instead of `<NS>`, and `<NS>` imports it too.
A definition without such a dependency keeps the configuration in `<NS>`.
The configuration may then name only what `<NS>-CONFIGURATION` imports: an initializer that names a production of `<NS>` that is not program syntax is rejected with `krs::partition::configuration-visibility`.

## Checked islands

| Island | Result |
| --- | --- |
| `k::term![...]` | checked symbolic term/pattern application; a pattern reads every island below without it, so around a pattern it changes nothing, and `krs expand` keeps it around fn subjects as the reference spelling. A term in ordinary Rust code, outside any KRS sentence, still needs it |
| `k::id![...]` | builtin `Id` literal, one constant of `Id`: a rule, an equation, or a claim matches or builds it like any constant, and an initializer holds it |
| `k::bytes![...]` | builtin `Bytes` literal, one constant of `Bytes`: `IsElf(k::bytes!(b"\x7fELF"))` in an equation's subject matches exactly those bytes, `k::bytes!(b"")` in a result is the empty `Bytes`, and `mem: k::bytes!(b"\x7fELF")` in an initializer starts the cell at those bytes |
| `k::anonymous!(Sort, "_Name")` | typed anonymous value allowed only in a claim subject, never its result or an initializer |
| `k::lexeme!(Sort, "text")` | one token of a `#[k::token]` sort, K's `#token("text","Sort")`, in rules, claims, and initializers |
| `k::is!(Sort, t)` | K's generated sort predicate `isSort(T)`: a total Bool in results, guards, claims, and initializers (below a cell's root), and in the subjects that hold applications (a claim's, a simplification's, a static clause's) and a map's key; never in a pattern over evaluated terms |
| `k::project!(Sort, t)` | K's generated projection `{T}:>Sort` (`project:Sort`): a partial function with no value when `t` is not a `Sort`, where `k::is!` stands |
| `k::or_bool!(lhs, rhs, ...)` | claim-only Boolean disjunction of at least two symbolic operands, never in an initializer |
| `k::fragment![...]` | nominal nested-cell term, anywhere a pattern or a term stands, in every rule, equation, and claim form; a record of the `#[k::cell]` struct means the same ([whole nested-cell variables](#whole-nested-cell-variables)); an initializer writes the record (`krs::expand::initializer-fragment`), and a constant's value holds no cell term |
| `k::k![...]` | K sequence, including tails/splice/erase notation |
| `k::map![...]` | a `cells!` entry's or an initializer cell's builtin Map: `map![]` or `map![.Map]` is the empty map; in a pattern its items are distinct entries and `map![k -> v, ..]` leaves the rest unread; built (a result, a claim's end state, an initializer) it has a [collection literal](#collection-literals)'s value, each entry written over the map before it (the empty map, the rest a framed subject leaves, or `..m`, a map the subject binds whole), emitted as K's join where its keys are provably distinct and as the calls otherwise; below a cell, and in every other term, a collection literal, as `set![..]` is |
| `k::cells![...]` | explicit multi-cell rule body |
| `k::rewrite!(from => to)` | K's local `( FROM => TO )` inside the subject of a single-body `#[k::rule]` fn; `()` on the right is `.K` ([Local rewrites](#local-rewrites)) |

K generates `isS` and `project:S` for every sort `S`.
`where v: Value` and a typed binder restrict what a rule matches; `k::is!(Value, v)` is a Bool the rule computes with.
They agree on concrete terms and differ in proofs, where a sort test is a condition rather than a matching constraint.
A projection that does not apply is undefined: Java K's LLVM backend aborts the run, and the symbolic backends yield `#Bottom`.
Rust's `Any::is` and downcasts are the analogues, except that a downcast returns `None` where K's projection has no value at all.
`krs check` rejects either macro in a left-hand side or pattern and a projection into `K` (`krs::analysis::invalid-sort-test`), and warns on a projection to a supersort of its operand's sort and on `k::is!(K, ..)` (`krs::analysis::trivial-sort-test`).
A projected collection lookup such as `k::project!(TypedLocal, list::get(locals, i))` keeps its `KItem` result, so the emitted term has exactly one cast.

These are restricted object-language grammars embedded in Rust tokens.
They do not evaluate arbitrary Rust expressions, methods, closures, or control flow; `&&`, `||`, the operators, and a method call with a domain turbofish are [notation for builtin calls](#operator-and-method-notation), and an island hands rustc the call each one denotes, an operator as a call of its facade marker (`k::builtin::__operator::add(a, b)`), which takes operands of any type.
The claim-only boundary is enforced during macro expansion rather than being a style convention.

Every list and every macro or attribute argument list accepts one trailing comma, as in Rust, including a single argument: `k::bytes!(b"..",)`, `k::k![a, b,]`, `KCell(x, tail @ ..,)`, `#[k::requires(c,)]`, `where a: Int, b: Int,;`.
A comma adds no element, so the term, the IR, and the emitted K are those of the list without it.
A record's `..` or `..base` takes none, as in Rust's struct patterns and updates (`Ctor { a, .. }`); in brackets, `..` and `rest @ ..` are elements and take one like any other.

## Literals

| Rust literal | K token |
| --- | --- |
| unsuffixed integer `N` in decimal, `0x` hex, `0o` octal, or `0b` binary (with `_` separators) | `Int` |
| `-N` on an unsuffixed integer | signed `Int` |
| `true`, `false` | `Bool` |
| `"..."` and raw `r"..."` | `String` |
| float literal, optionally suffixed `f32`, `f64`, or K's `pNxM`; `-` on it | `Float` |
| `f32::`/`f64::` `NAN`, `INFINITY`, `NEG_INFINITY` | `Float` |

An integer literal denotes one integer whatever its radix, so the radix is spelling: `0xFF0F`, `0o177417`, `0b1111_1111_0000_1111`, and `65295` are the same `Int`, K receives it in decimal, and a table keyed by `0xFF0F` matches `65295`.
K's integers are unbounded, so a literal wider than any Rust integer type, such as `0x1_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000_0000` (2^256), is still one literal.
A suffix names a Rust width, which K's `Int` does not have, so `0xFFu8` is rejected as `255u8` is.
`k::bits!("..")` is not a radix: a [bit template](#bit-templates) has fields and wildcards, while `0b0100_1000` is one value.

The sign belongs to the literal: `-1` is one K `Int` token wherever a term may appear, in patterns as well as results, so `Sgn(-1)` and `Div { lhs, rhs: -1 }` match it; `-0x10` is `-16`.
A literal is a value; `int::sub(0, 3)` is a call and cannot be matched as `-3`.
A minus on anything but a literal (`-x`, `-(1)`, `--1`) is the [negation operator](#operator-and-method-notation): K has no unary minus on `Int`, so on an `Int` it is `int::sub(0, x)`, and on a `Float` it is `float::neg(x)`; `-0` (or `-0x0`) is rejected in favour of `0`.
Rules lex `-1` with K's signed `INT-SYNTAX` even in a package with `int-literals = "unsigned"`, where a program's `-1` is instead a unary minus applied to `1`.

A string literal is a K `String` token, in patterns as well as results, so `Greet("world")` matches it.
K 7.1.337 strings hold code points U+0000 to U+00FF (Latin-1) only, so a code point above U+00FF is rejected; use `Bytes` for other data.
KRS spells each value one way in the emitted K: `"\u{c1}"` in Rust is `"\xc1"` in K.
A `char` literal is rejected (K has no `Char` sort; write `"a"`), and so is a byte string (write `k::bytes!(b"..")`).
Code points from U+0080 to U+00FF evaluate alike on every backend, with one exception: Java K's LLVM backend does not match a rule's `"\xc1"` against a program's, which k-rust does.

`k::bytes!(b"..")` is one K `Bytes` token and `k::id!("$name")` one K `Id` token, in rules, equations, claims, and initializers, in patterns as well as results, as a string literal is: `fn is_elf(IsElf(k::bytes!(b"\x7fELF")): k::Term<Int>) -> k::Term<Int> { 1 }` emits `rule isElf ( b"\x7f\x45\x4c\x46" ) => 1`, which matches exactly those four bytes, and `k::id!("$main")` emits `#token("$main","Id")`.
A call such as `bytes::empty()` computes a value and cannot be matched; the literal can.
An initializer holds a literal wherever it holds a term, since a constant has the same value there as in a rule: `mem: k::bytes!(b"\x7fELF")`, `who: k::id!("$main")`, `label: k::lexeme!(Label, "entry")`, `env: k::map![k::id!("$x") -> 1]`, and `list::item(k::bytes!(b"ab"))` start the configuration at those values, and a rule's literal pattern matches them.
`k::anonymous!` and `k::or_bool!` are not initializer terms (`krs::expand::claim-subject-only-term` and `krs::expand::claim-only-term`): an unknown value makes the initial configuration symbolic, so no run could start from it, and an initializer holds no condition.

K has one `Float` sort, and every value carries its precision and exponent range in its token.
Rust's `f32` and `f64` are K's binary32 and binary64: `0.1f32` is the K token `0.1f`, `1.5f64` is `1.5d`, and an unsuffixed `1.5` is K's default, binary64.
`1f32` is a Float, while an unsuffixed `1` stays an `Int`.
K's own suffix `pNxM` (N bits of precision, M exponent bits) is kept as written, as in `1.0p113x15`; any other suffix is rejected.
As for integers, the sign belongs to the literal, so `-0.0` is one token and keeps its sign.
`f64::NAN`, `f64::INFINITY`, and `f64::NEG_INFINITY` are `NaN`, `Infinity`, and `-Infinity`, and their `f32` forms are `NaNf`, `Infinityf`, and `-Infinityf`.
NaN has no sign in K's token syntax, so `-f64::NAN` is rejected, and `-f64::INFINITY` is rejected in favour of `f64::NEG_INFINITY`.
The operations follow IEEE 754 in their operands' format: `float::eq(NaN, NaN)` is false and `float::eq(0.0, -0.0)` is true, while `kequal::eq` compares the terms, so it holds for two NaN tokens and fails for `0.0` and `-0.0`.
`float::to_int` rounds ties to even, so `2.5` gives `2` and `3.5` gives `4`.
A Float result prints as `krun` prints it with the LLVM backend: MPFR's correctly rounded significand digits after `0.`, the decimal exponent, and the format suffix, so `krs run` shows `-1.5` as `-0.15000000000000000e1` and `0.1f` as `0.100000001e0f`. Every output format of `krs run` and `krs search` carries that text, as krun's do: `--output kast` prints `#token("-0.15000000000000000e1","Float")`, and `--output kore` and `json` hold the same token, never k-rust's internal `-1.5000000000000000e+00p53x11` or a program literal's own spelling. `krs parse` keeps the literal's text, as `kast` does, and `krs prove`, whose reference is `kprove` on the Haskell backend rather than the LLVM runtime, rewrites a leaf's Floats only in `--output pretty`.

Not every Float runs on every route.
The k-rust frontend folds an application of a `FLOAT` operation whose arguments are all tokens, such as `float::add(0.1, 0.2)`, while compiling, in every build, through k-rust's backend, which no native run of KRS has been checked against yet; k-rust also evaluates only binary32 and binary64.
KRS records both as capability requirements (`GroundFloatFolding`, `FloatPrecisionBeyondBinary64`), and the native and browser routes refuse such a definition before compiling it, while Java K's LLVM backend runs it.
Bind a variable or write the folded literal instead of applying an operation to tokens.
Java K's Haskell backend has no Float evaluator, so Float definitions are compared with Java K on the LLVM route.

## Named constants

`#[k::constant]` on a Rust `const` item names a value:

```rust
/// Interrupt flag register.
#[k::constant]
pub const IF: Int = 0xFF0F;

#[k::constant]
pub const START: Instr = Instruction::Jump(IF);
```

The type is a KRS sort, such as `Int`, `Bool`, or a sort alias, and the value is a ground constructor term: a [literal](#literals) or a `k::id!`, `k::bytes!` or `k::lexeme!` token, each one constant of its sort, a constructor application whose arguments are ground terms, or another constant.
A constant is a name for that term, so every use stands for it: `int::add(g, IF)`, a table row `port_if: IF => 1;`, a readable record `{ pc: PC_START }`, an initializer, a claim, and a `requires` all mean what they would with `65295` written there.
KRS substitutes the value at every use before it analyses anything, so sort inference, the overlap and coverage checks, and the emitted K see the value and never a symbol for the constant: two rows of one table keyed `IF` and `65295` overlap, and `krs check` says so.

A constant is a Rust item, and its name follows Rust's rules: it is declared, imported (`use io::LCDC;`), re-exported, and made `pub` like any item, and a path such as `crate::io::LCDC` names it from anywhere.
In a pattern, a bare name spelled as Rust spells a constant, with an uppercase letter and no lowercase one (`IF`, `WORD_SIZE`, `P2`), refers to a constant and is compared, as a Rust `const` in a pattern is; every other bare name is a binder.
KRS binders are snake case, so the two never meet, and a bare uppercase name that names no constant is rustc's unresolved-name error at the name, never a binder.
Rust shares one hazard: a misspelled lowercase name in a pattern is a binder, which matches everything.

The value is restricted to ground constructor terms so that every use is a value a pattern can match and nothing about it depends on evaluation: an application of a function or a builtin operation (`int::add(1, 2)`, `1.add::<Int>(2)`) is rejected (`krs::syntax::invalid-constant` for operator and turbofish method notation and the other term macros, `krs::analysis::invalid-constant` for a function or a builtin operation's call, and for an index or a collection method, which a constant reads as the call it denotes), as are a `static`, generics, and a type that is not a sort (`krs::syntax::invalid-constant`).
The value's sort must be the declared sort or one below it, which `krs check` reports as an ordinary sort error at the value, so a use is well sorted wherever the declared sort is; a use is then checked at the value's own sort, as if the value were written there.
Constants that refer to each other in a cycle, and a use that passes a constant arguments (`IF(1)`), are rejected (`krs::analysis::invalid-constant`).
The Rust item a constant expands to is a unit struct of the same name, which gives the name its place in Rust's scopes; Rust code does not use it as a value.
`krs expand` prints a use as the constant's path, such as `crate::IF`.

## Framework and builtin sorts

`KItem` is the framework sort of computation items, and every sort except `K` is a `KItem`, declared or not: each declared sort, each builtin sort, and each generated cell sort.
A `KItem` field, parameter, or result admits a term of any sort but `K` (`Hold { saved: Seq { .. } }`, `Hold { saved: true }`), and `X: KItem` in `k::sorts!` is allowed and states nothing KRS does not already know; it still emits `syntax KItem ::= X`.
`KResult` marks terms that count as evaluated results for strictness.
`KItem` and `KResult` are part of every definition, so `k::KItem` and `k::KResult` may be written wherever a sort may (a field, a binder, `k::is!`, a strictness `result`) with no sort declared below them; the emitted K contains their `KRS-FRAMEWORK` module only when the definition uses one of them, and a module imports it when one of its declarations names one.
`KSequence` is the symbolic computation sequence sort.
A constructor field, function parameter, or function result of type `KSequence` holds a computation sequence, K's `K`, and its module imports K's `SORT-K`, which declares that sort and nothing else; a rule matches such a value with a binder bound at a `K` position and splices it into the computation with `k: [b, ..]`, and a `cells!` rule fills one with its computation remainder `tail @ ..`. Programs cannot write one.
The facade also exposes `Id`, `Int`, `Bool`, `Bytes`, `Endianness`, `Signedness`, `Float` (also `float::Float`), `Map<K, V>`, `List<T>`, and `Set<T>`, plus `Cell<T>`, `KCell<T>`, and `CellFragment<Parent>` authoring wrappers.
The arguments of a collection type on a cell, a constructor field, or a function signature are its element types, which every term written there is checked against ([Typed collections](#typed-collections)); K's collection sorts themselves are not parametric.
K's `String` sort is `string::String`: write `use k::builtin::string;` and `string::String`, so Rust's own `String` stays in scope (`k::builtin::String` remains as a root spelling).

## Builtin operation catalog

Operation paths below are tuple-struct constructor aliases.
Calling them constructs a typed symbolic application; it does not run a Rust implementation.
An operation of `int`, `bool`, `string`, `float`, `bytes`, or `kequal` may also be written as a method of its first operand, `bool::and_then` and `bool::or_else` as `&&` and `||`, and the arithmetic, bitwise, and comparison operations of `Int`, `Bool`, `String`, and `Float` as Rust's operators ([Operator and method notation](#operator-and-method-notation)).
A lookup of a `Map` or a `List` may be written as an index, `m[k]`, and most `Map`, `List`, and `Set` operations as a method of their collection, `m.contains_key(k)` ([Index reads and collection methods](#index-reads-and-collection-methods)).
A `Map` or a `Set` may be built with a literal, `map![k -> v]` or `set![x, y]` ([Collection literals](#collection-literals)).

| `builtin::bool` | `not`, `eq`, `ne`, `or`, `and`, `xor`, `implies`, `and_then`, `or_else` |

Every name follows one rule, so you can find an operation from K's documentation (`domains.md`) without a table.
Find the K production; its module is the production's hook namespace in lowercase (`INT.tdiv` is in `int`, `SET.set2list` in `set`).
Its name is the operator's word for an `Int`, `Float`, or `Bool` operator (`+Int` is `add`, `%Int` is `rem`, `--Float` is `neg`, `==Bool` is `eq`); the hook's word, in snake case, for a symbolic `String`, `Bytes`, `Map`, `List`, or `Set` operator (`-Set` is `difference`, `M [ K ]` is `get`, `.Bytes` is `empty`); otherwise K's own name without its sort word, in snake case with `NaN` as one word (`minInt` is `min`, `andThenBool` is `and_then`, `isNaN` is `is_nan`); and `A2B` conversions are `from_a` or `to_b` in the module that owns them (`Int2Bytes` is `bytes::from_int`, `Set2List` is `set::to_list`, `Int2Float` is `float::from_int`).
When that name is a Rust keyword or is already taken in the module, KRS uses the Rust standard method with the same meaning: `modInt` is `rem_euclid`, `divInt` is `div_euclid`, and K's `in` is `contains`.
The four integer divisions therefore read exactly like Rust's: `int::div` and `int::rem` truncate like `/` and `%`, and `int::div_euclid` and `int::rem_euclid` are `i64::div_euclid` and `i64::rem_euclid`.
`int::rem_euclid` was called `int::modulo` before this rule.
`bool::and_then` is K's `andThenBool`, not `Option::and_then`, and `map::get` and `map::get_or_default` are K's partial and total lookups, not `HashMap::get` returning an `Option`; a lookup's result is projected to the sort its position expects.
`bytes::from_int`, `from_int_no_len`, and `to_int` take a byte order (`bytes::little_endian()` or `bytes::big_endian()`) and, where K does, a signedness (`bytes::signed()` or `bytes::unsigned()`), of the builtin sorts `Endianness` and `Signedness`.
`set::to_list` and `set::from_list` come from K's `COLLECTIONS` module, which KRS imports when a rule uses them.
`string::length` counts code points, `string::concat` (`+String`) takes time linear in its operands, and `string::to_int` is partial: it is undefined on text that is not a decimal integer, the analogue of `str::parse` returning `Err`.
An operation enters the catalog only after one ground application evaluates both natively and on Java K's LLVM backend.
The `K-IO` hooks `io::write(fd, s)` and `io::putc(fd, b)` are the exception: they are impure, and k-rust performs them only in committed execution with console state, which KRS's in-process backend does not supply.
Their sort is `K` and they evaluate to the empty computation `.K` after writing; like any `K` item, a hook splices into a result sequence as K's `~>` does, so one rule can write and continue (`k: [io::write(1, "hi\n"), Next(), ..]` is K's `#write(1, "hi\n") ~> next ~> ...`).
A `K` item beside `KItem`s is accepted only in a rule result; in a pattern or a configuration initializer the items keep one most-specific common sort.
They run on Java K and through `krs build --backend llvm`, and the in-process commands (`krs parse`, `run`, `search`, and `prove`) and the browser route refuse a definition that uses them (`krs::capability::unavailable`, the `ConsoleWriteHook` requirement) instead of stopping on an unsupported hook.
`io::log(s)` needs no console state, so it evaluates on the native routes; `krs run` and `krs search` write its line to standard error, as Java K's LLVM backend does (its Haskell backend only records the line in its own log), and the browser route, which has no console, refuses it with the `ConsoleIO` requirement.
Stream cells cover console I/O, so these direct hooks are rarely needed.

`kequal::eq` and `kequal::ne` are K's `==K` and `=/=K`: syntactic equality of two terms of any sort, like a derived `PartialEq` on a closed enum of terms.
They differ from `int::eq` only on symbolic terms.
`kequal::ite(c, t, e)` is K's `#if c #then t #else e #fi`, a sort-parametric function rather than control flow.
Its sort is the least sort of its two branches that fits where it occurs, the rule k-rust uses, so `ite(b, 1, 2)` in an `Exp` position has sort `Int`; branches with no unique such sort are an error that asks you to narrow one with a typed binder or `where`.
k-rust keeps the definedness condition of the untaken branch, while Java K's LLVM and Haskell backends answer with the taken branch alone, so keep both branches defined and every backend agrees.
There is deliberately no Rust `if` sugar for it, because a Rust `if` evaluates one branch.

### Operator and method notation

Three forms of a term expression are notation for a builtin call and have no meaning of their own.
`a && b` is `bool::and_then(a, b)`, K's `andThenBool`, and `a || b` is `bool::or_else(a, b)`, K's `orElseBool`.
These are the short-circuit connectives: k-rust evaluates the left operand first and the right one only when the left does not decide the result, so a guard such as `d != 0 && n / d > 1` evaluates in the order it reads, while the value keeps the definedness of an operand it does not evaluate, as for `kequal::ite` above.
They group and associate as in Rust: `a || b && c` is `a || (b && c)`, both connectives associate to the left, and parentheses group subexpressions.
The strict `bool::and` and `bool::or` remain available as calls.

Rust's binary operators `+ - * / % << >> & | ^ == != < <= > >=` and the unary `!` and `-` denote an operation of one builtin domain:

| Operator | `Int` | `Bool` | `String` | `Float` |
| --- | --- | --- | --- | --- |
| `a + b`, `a - b`, `a * b` | `int::add`, `sub`, `mul` (`+Int` ...) | | `+` only: `string::concat` (`+String`) | `float::add`, `sub`, `mul` |
| `a / b`, `a % b` | `int::div`, `int::rem` (`/Int`, `%Int`, truncating) | | | `/` only: `float::div` |
| `a << b`, `a >> b` | `int::shift_left`, `int::shift_right` (arithmetic) | | | |
| `a & b`, `a \| b`, `a ^ b` | `int::bit_and`, `bit_or`, `bit_xor` | | | |
| `!a` | `int::bit_not` (`~Int`) | `bool::not` (`notBool`) | | |
| `-a` on anything but a literal | `int::sub(0, a)` | | | `float::neg` (`--Float`) |
| `a == b`, `a != b` | `int::eq`, `int::ne` | `bool::eq`, `bool::ne` | `string::eq`, `string::ne` | `float::eq`, `float::ne` (IEEE) |
| `a < b`, `a <= b`, `a > b`, `a >= b` | `int::lt`, `le`, `gt`, `ge` | | `string::lt` ... | `float::lt` ... |

An operator does not name its domain: KRS chooses it after sort inference, from the operands.
An operand pins a domain when its sort is that domain or a subsort of it: an Int literal, a binder inferred or declared `Int`, or a function returning `Int` pins `Int`, and a comparison is a `Bool` in every domain.
The operator denotes the operation of the one domain its operands pin, and from then on sort inference, arity, SMT restrictions, the coverage lint, the overlap check, and the emitted K are those of the call: `a + 1` with `a` a binder of sort `Value`, a supersort of `Int`, narrows `a` to `Int` exactly as `int::add(a, 1)` does, and a binder declared `Value` is rejected as it is for the call.
Each builtin domain defines its operations on that domain only, so operands that pin a domain leave one well-sorted reading, and KRS never guesses one: operands that pin no domain, such as two binders of a user sort, or two domains, such as an `Int` and a `Float`, are an error (`krs::analysis::ambiguous-operator`) that lists the explicit forms, `a.eq::<Int>(b)` through `a.eq::<K>(b)`.
A binder that no occurrence sorts more precisely than `KItem`, such as an element of a bare `List`, is named in the error with the narrowing that picks a domain, `where a: Int, z: Int` in a readable rule; the operator never takes its domain from the position it is written at.
An operand whose sort is only fixed later in the sentence, as when `a * b` precedes the cells that bind `a` and `b`, is read once inference has seen the whole sentence.
An operand a `let` binds has its value's sort: `{ let b = a; b + b }` reads in `a`'s domain.
`Bytes` and the collections have no operators, and `==` compares values of a builtin domain, not terms: `==` on a user sort, `Bytes`, a collection, or `K` points to `a.eq::<K>(b)` (`==K`), which compares terms and means something different to the solver.
An operator the chosen domain does not define is an error (`krs::syntax::invalid-expression-notation`) naming what to write instead; `Float` has no remainder in the catalog, and `<<` and `>>` are `Int` only.

`&` and `|` are not `Bool` connectives: Rust's precedence makes `a == b & c == d` a parse error, so they would need parentheses everywhere, and `&&` and `||` already cover `Bool`; on `Bool` they point to `&&` and `||`, or to `bool::and` and `bool::or` to evaluate both operands, and `^` on `Bool` points to `bool::xor` or `!=`.
On `Int`, `&`, `|`, `^`, and `!` are bitwise, as Rust's are on integers, so the SM83 half-carry flag reads `(a & 15) + (b & 15) > 15`.
Rust's reading agrees with K's on every operation the table admits: `/` and `%` truncate toward zero, `>>` is arithmetic, `!a` is `-a - 1`, and `==` on floats is IEEE equality, so `0.0 == -0.0` holds and `NaN == NaN` does not.
The one difference is width: K's `Int` is unbounded, so `1 << 64` and `a + b` never wrap; a specification that needs wrapping writes it explicitly, as a `Byte` or `Word` sort or a chop function.
Precedence and associativity are Rust's: `a & 15 == 0` is `(a & 15) == 0`, `-x * y` is `(-x) * y`, and a chained comparison such as `a < b < c` is a Rust parse error.
Compound assignment (`a += b`), `as`, and ranges outside a pattern are errors (`krs::syntax::invalid-expression-notation`): a term has nothing to assign to, and no builtin operation stands behind a cast.

`recv.op::<D>(args..)` is `d::op(recv, args..)`, where `d` is the builtin module of the domain `D`:

| `D` | Module | Example |
| --- | --- | --- |
| `Int` | `int` | `a.lt::<Int>(b)` is `int::lt(a, b)` |
| `Bool` | `bool` | `a.not::<Bool>()` is `bool::not(a)` |
| `String` | `string` | `s.concat::<String>(t)` is `string::concat(s, t)` |
| `Float` | `float` | `x.sqrt::<Float>()` is `float::sqrt(x)` |
| `Bytes` | `bytes` | `b.length::<Bytes>()` is `bytes::length(b)` |
| `K` | `kequal` | `a.eq::<K>(b)` is `kequal::eq(a, b)`, K's `==K` |

`op` is the name of any operation of that module in the catalog above, and the receiver is its first operand, so every operation that takes an operand has a method form, and every operator its explicit form.
Method calls chain: `b.bit_and::<Int>(m).ne::<Int>(b)` is `int::ne(int::bit_and(b, m), b)`, which `b & m != b` also denotes.
The domain is a bare name from the table, not a Rust type path, and rustc never resolves it; it selects the module and is not an instance of the operation.
No form needs an import: the call each denotes names the facade's `builtin` module itself, so it resolves under a renamed facade and in a module that does not import `bool` or `int`.

All three forms are valid exactly where the call they denote is, and nowhere else: in results, `#[k::requires]` and `#[k::ensures]` conditions, initializers, claims, and the checked islands, which hand rustc the call.
The reference projection of a rule prints the call, as in `k::builtin::bool::and_then(..)` or `k::builtin::int::sub(0, x)` for `-x`.
No form is a Rust pattern, so a pattern rejects each, naming the form and the calls it denotes (`` `&&` is not a pattern: a pattern writes `bool::and_then` as the call `bool::and_then(..)` ``, `` `+` is not a pattern: a pattern writes a builtin operation as its call, `int::add(..)`, `string::concat(..)`, or `float::add(..)` ``).
The call itself stands in a pattern only where an application may: in a simplification's or a claim's subject, and in a collection's key, value, or element; at any other position a rule's or an equation's pattern matches, its root included, it is evaluated in every term the sentence is applied to, so it is refused there ([functions in patterns](#functions-in-patterns)).
An operand of a compiler-owned macro such as `k::or_bool!` is a term even on a left-hand side, and takes the forms exactly as it takes the call.
A method call without a domain turbofish (``write `lt::<Int>`, `lt::<String>`, or `lt::<Float>` ``), with a turbofish that holds anything but one domain name, with a domain outside the table, with an operation its module does not define, or with an operation that takes no operand (``write the call `bytes::empty()` ``) is an error (`krs::syntax::invalid-expression-notation`).

### Index reads and collection methods

Two more forms are notation for a collection operation.
`m[k]` is `map::get(m, k)` on a `Map` and `l[i]` is `list::get(l, i)` on a `List`.
An index is exactly the call: it is partial wherever the call is, so a key the map lacks or an index outside the list leaves the term undefined, as K's `M [ K ]` and `L [ I ]` do, and a guard that must hold first writes it first, `m.contains_key(k) && m[k] > 0`, since `&&` short-circuits.
A negative index counts from the end, as K's does: `l[-1]` is the last element, where Rust would refuse the index.
Its result is the element, projected to the sort its position expects, as the call's is.

A method without a domain turbofish is a collection method when its name is in this table, and denotes the call in the right column:

| Collection | Method | Denotes |
| --- | --- | --- |
| `Map` | `m[k]` | `map::get(m, k)` |
| `Map` | `m.get_or(k, d)` | `map::get_or_default(m, k, d)` |
| `Map` | `m.contains_key(k)` | `map::in_keys(k, m)` |
| `Map` | `m.update(k, v)` | `map::update(m, k, v)` |
| `Map` | `m.without(k)`, `m.without_all(s)` | `map::remove(m, k)`, `map::remove_all(m, s)` |
| `Map` | `m.extend(n)` | `map::update_all(m, n)` |
| `Map` | `m.keys()`, `m.keys_list()`, `m.values()` | `map::keys(m)`, `map::keys_list(m)`, `map::values(m)` |
| `Map` | `m.len()` | `map::size(m)` |
| `List` | `l[i]` | `list::get(l, i)` |
| `List` | `l.update(i, x)` | `list::update(l, i, x)` |
| `List` | `l.contains(x)` | `list::contains(x, l)` |
| `List` | `l.len()` | `list::size(l)` |
| `Set` | `s.contains(x)` | `set::contains(x, s)` |
| `Set` | `s.union(t)`, `s.difference(t)`, `s.intersection(t)` | `set::union(s, t)`, `set::difference(s, t)`, `set::intersect(s, t)` |
| `Set` | `s.is_subset(t)` | `set::is_subset(s, t)` |
| `Set` | `s.len()`, `s.to_list()` | `set::size(s)`, `set::to_list(s)` |

The receiver fills the argument its row names, which is the first but in `contains_key` and `contains`: K writes key and element membership `K in_keys(M)` and `K in S`, so `s.contains(x)` is `set::contains(x, s)`.
Every method builds a new collection or reads one, as a persistent collection's does; none changes its receiver, and `without` and `extend` say so where Rust's `remove` and `insert` would suggest mutation.
There is no `get` that returns an `Option`, since K's lookup is partial and has no option sort: `m[k]` is the partial lookup and `m.get_or(k, d)` the total one.
A constructor has no receiver, so `empty`, `item`, `list::make`, and `set::from_list` have no method form, and neither do `list::concat`, `set::concat` (defined only on disjoint operands), `list::range(l, i, j)` (which trims `i` elements from the front and `j` from the back, unlike the slice `i..j`), and `list::update_all`: each keeps its call as its only form.
The table is the builtin catalog's own (`CollectionMethod`), which the parser, sort inference, and the facade all read.

An index or a method does not name its collection either: KRS chooses the row after sort inference, from the receiver's sort, `Map`, `List`, or `Set`, typed or not, as an operator's operands choose its domain.
From then on it is the call: sort inference, typed collections, arity, the coverage lint, the overlap check, and the emitted K are the call's, and `krs expand` prints a rule's, an equation's, or a claim's sentence with the call and the collection inference chose (`k::builtin::map::in_keys(k, m)`); a `#[k::function]` body and an initializer it prints as written (`Cell::new(map::empty().update(1, 2))`).
A receiver bound by a `let` has its value's sort, as an operator's operand does (`{ let n = m; n.len() }`).
A receiver that no occurrence sorts more precisely than `KItem`, or `K`, is an error (`krs::analysis::ambiguous-operator`) that names the receiver, the narrowing (`where m: Map` in a readable rule, `m: Term<Map>` elsewhere), and the calls.
A receiver of a sort that is no collection is no ambiguity but a form that does not apply (`krs::syntax::invalid-expression-notation`), and the error names the operation of the same name in the receiver's scalar domain, if it has one (`update::<Bytes>` for a `Bytes`).
A method its receiver's collection lacks, such as `m.union(n)` on a `Map`, is the same error, naming the collections that have it and the receiver's own methods; so is a method with the wrong number of arguments (`` `.len()` takes no argument besides its receiver ``).
A name in no table keeps the error of a method without a turbofish, which lists the scalar `::<D>` forms (``write `lt::<Int>` ``), and a collection method with a turbofish, `m.len::<Int>()`, names a scalar domain's operation as any turbofish does, with the help that a collection method takes no turbofish: its receiver's sort chooses the collection.

An index or a method stands wherever its call does: in a result, a condition, an initializer, a claim, a fn body, the checked islands, and a computed map key or set element, which is looked up (`{ st.len() -> v, .. }` reads the entry whose key is the stack's length).
Rust parses `m[k]` and `m.f(k)` as expressions, so they hold at the positions rustc parses too, a rule fn's or an equation's result and a `#[k::function]` body included.
Where a pattern matches a term it applies a function, which never matches, so it is a [function in a pattern](#functions-in-patterns) (`krs::analysis::function-in-pattern`), with its own advice: an index points to `{ k -> v, .. }` to read an entry, and a method to reading the value into a name and comparing it in a guard.
In a map's key it reads exactly as `map::get(m, k)` does: a key it computes is looked up once the names it reads are bound, by the subject or by other keys in any order (`{ x -> v, st[v] -> w, .. }`), and only keys that read each other's values in a cycle are refused; in a key that selects an entry by matching, it is a function in a pattern.
Writing a map's entry has no index form: `m[k] = v` and `+=` assign, and a term has nothing to assign to; `m.update(k, v)` is the value with the entry written.

### Collection literals

`map![k1 -> v1, .., kn -> vn]` builds a map wherever a term is built: a result, a rewrite's right side, a fn body, a guard, an initializer's term below a cell, and a computed map key or set element.
It is notation for the calls that build the map, each entry written over the map before it, `map::update(..map::update(map::empty(), k1, v1).., kn, vn)`, and has no meaning of its own: its sort, its K, and every check are the calls'.
A built map is therefore total, as a Rust map literal is: two keys that evaluate equal are one entry, whose value is the later one's, so `map![a -> 1, b -> 2]` with `a` and `b` bound to one key is the map `a |-> 2` (K's `.Map [ A <- 1 ] [ B <- 2 ]`), never an undefined join.
Two keys written as the same term are one key whose earlier value could never be read, so `map![a -> 1, a -> 2]` is an error at the second (`krs::syntax::invalid-expression-notation`), as the pattern `{ a -> x, a -> y, .. }` is.

`set![x1, .., xn]` is `set::union(..set::union(set::item(x1), set::item(x2)).., set::item(xn))`, so elements that evaluate equal are one element; `set::concat`, which is defined only on disjoint sets, would leave the set undefined.
An element written twice is one element, so `set![a, a]` is the set `set![a]`: the union loses nothing, and it is no error.
`map![]` and `set![]` are `map::empty()` and `set::empty()`, and `set![x]` is the singleton `set::item(x)`.

A literal may end in a rest, the collection its entries are written over: `map![k -> v, ..m]` is `map::update(m, k, v)`, the map `m` with the entry written, as `Ctor { f: e, ..t }` is the record `t` with the field written, and `set![x, ..s]` is `set::union(s, set![x])`.
The rest comes last, since the entries are applied over it, and it names a collection: an anonymous `..` names none, so `map![k -> v, ..]` is an error wherever it stands, a pattern included, where `{ k -> v, .. }` reads a map's entries; so are `map![..m, k -> v]` and `map![..m]`, which is `m` itself.
A malformed entry is the same error at its token: an entry without `->` (a key's own comma, as in a turbofish `Wrap::<A, B>(x)`, is the key's), `=>` in an entry, and K's `.Map` or `.Set` where `map![]` or `set![]` is meant.

The macro's last path segment names it, so `k::map![..]` and `k::set![..]` are the same literals and neither needs an import; `krs expand` prints a sentence's literal as its calls (`k::builtin::map::update(k::builtin::map::empty(), a, 1)`), and a `#[k::function]` body as written.
A literal stands where its calls stand.
Where a pattern matches a term, a map with an entry and a union of sets apply functions, which never match, so `env: map![n -> v]` in a subject is a [function in a pattern](#functions-in-patterns) (`krs::analysis::function-in-pattern`), whose advice names the forms that read entries; `map![]`, `set![]`, and `set![x]` are values, so `seen: set![n]` matches the set whose one element is `n`.
A constant's value holds no builtin operation's application, the empty collection's included, so no literal is a constant's value (`krs::analysis::invalid-constant`, as for `map::empty()` and `map::update(..)`).
A `cells!` entry's and an initializer cell's whole `map![..]` is that surface's spelling of the cell's map, and where it is built, in an initializer, a `cells!` result and a claim's end state, it has the literal's value: of two keys that evaluate equal the later one wins.
It is emitted as K's join of its entries wherever the join provably is that value, and as the calls otherwise: one entry is `K |-> V`, which is `.Map [ K <- V ]` whatever `K` is; entries whose keys are pairwise provably distinct are the join, which is defined there and is the same map, the keys being ground tokens with different values (`map![1 -> x, 0x2 -> y]` is `1 |-> X 2 |-> Y`; `1` and `0x1` are one key) or keys the subject matched as distinct entries of the map, in a claim the start state's in the same cell; any other entries are the calls, so `regs: map![a -> x, b -> y]` as an initializer cell's value or over `regs: Cell(r)` in a `cells!` result is `.Map [ A <- X ] [ B <- Y ]`, `b`'s entry written over `a`'s where the two are equal.
Two entries whose keys are provably one key, as `a` and `(a)`, are one entry with the later value; a key written twice in one spelling is an error, as in a literal (`krs::syntax::invalid-expression-notation`).
An initializer's `map![0 -> 1, ..env]` is `$ENV:Map [ 0 <- 1 ]`, and a `cells!` result's `map![k -> w, ..m]` over a map the subject binds whole, `env: Cell(m)`, is `M [ K <- W ]`, the entries written over `m`.
A claim's end state describes the states whose map is that value; where it is the join, the join describes exactly those states, and where it is the calls, the claim also covers keys that evaluate equal.
A framed result is written over the map the subject leaves: with the subject `env: Cell(map![k -> v, rest @ ..])` the result `Cell(map![k -> w, ..rest])` is `rest` with `k`'s entry written, and with the subject `Cell(map![k -> v, ..])` the result `Cell(map![k -> w])` is the unread rest with it written.
K keeps that rest by joining it with the result's entries (`<env> K |-> V Rest => K |-> W Rest </env>`), which is the same map at a key the subject matched, since the subject's entries are distinct and the rest is what they leave; a key the subject does not match may already be in the rest, where the join has no value, and writing it there needs the rest bound on the left alone, which KRS cannot emit yet, so it is an error at the key (`krs::analysis::invalid-term`): bind the whole map instead, `env: Cell(m)`, and write `map![k -> w, ..m]`.
Where a `cells!` subject or a claim's start state matches the map, its items are distinct entries, K's join `A |-> X B |-> Y`, so `map![a -> x, b -> y]` there matches only a map in which `a` and `b` differ.
A literal below the cell, `Cell(Wrap(map![a -> x]))`, is a term, and so is a cell's whole `set![..]`, which those surfaces read no other way.

Function hooks bind a production to backend code, and are a separate typed catalog selected in `#[k::function(total, ..., hook = krypto::sha256_raw)]`: a checked Rust path whose signature KRS checks against the hook.

### Raw K escapes

Two escapes keep K that the surface cannot express yet, and both are deliberate exceptions to the rule that KRS embeds no strings.
A quoted hook, `hook = "KRYPTO.keccak256"`, is K's exact hook name: KRS checks only that the pinned K and k-rust know the name, that the typed catalog does not cover it (`"KRYPTO.keccak256raw"` is an error that names `hook = krypto::keccak256_raw`), and, for a crypto hook, its argument count; the production's sorts are not checked.
Java K evaluates a hook outside its default namespaces only when `kompile` is given the namespace, for example `--hook-namespaces KRYPTO` on the Haskell backend.
`k::raw_k!(r#"rule <k> double(I:Int) => I +Int I ... </k> [label(raw-double)]"#)` is one K `rule`, `claim`, or `context`, with no `module`, `endmodule`, or `imports`; KRS prints it verbatim in the package's semantics module after a `// raw_k! src/lib.rs:L:C (opaque to KRS)` comment, and K parses it with that module's grammar, so a K parse error fails the build on every route.
Treat a `raw_k!` as a TODO marker: KRS does not check it, its names are the emitted K names, it takes part in no overlap check, and it is the full module of every builtin sort the package uses that its text can see.
A package admits either escape only with `allow-raw-k = true` in `[package.metadata.krs]`; without it each one is an error (`krs::policy::raw-k-not-allowed`).
With it, every build warns once per use (`krs::expand::raw-hook`, naming the hook's native capability, per backend for a plugin hook such as `KRYPTO.*`, which `--backend llvm` does not admit, and `krs::semantic::raw-k`), and `profile = "strict"` or `krs --profile strict` turns the warnings into errors.

## Running a definition

Each command compiles the selected definition in-process and corresponds to a K tool on the emitted `definition.k` and `spec.k`; the [workflow reference](/reference/workflow#run-search-and-prove) lists their options.

| KRS | Java K | Result |
| --- | --- | --- |
| `krs parse --sort Stmt prog.imp` | `kast --sort Stmt prog.imp` | the program as KAST |
| `krs parse --output program prog.imp` | `kast --module MAIN --output program prog.imp` | the program printed back through its grammar |
| `krs run prog.imp -c env='.Map'` | `krun prog.imp -cENV='.Map'` | the final configuration of one path |
| `krs search prog.imp` | `krun --search prog.imp` | the set of reachable final states |
| `krs prove --claim branching` | `kprove spec.k --claims MAIN-SPEC.branching` | a verdict for each claim |
| `krs prove --spec-module IMP-SUM-SPEC` | `kprove spec.k --spec-module IMP-SUM-SPEC` | a verdict for each claim of an author spec module |

A run ends `stuck` when no rule applies; K has no separate finished state, so a program is finished when `<k>` holds only `.K`.
Proof verdicts are k-rust's `proven`, `disproved`, `failed`, `indeterminate`, `depth-bound`, and `breadth-bound`, and `trusted` for a [trusted claim](/verification/reachability-claims#trusted-claims), which is assumed without proof.
`--output json` prints a `krs-exec/1` report whose configurations are KAST JSON, as `krun --output json` prints them.

### Printing through the grammar

The grammar is also the printer: there is no `Display` impl to write.
`krs run`, `krs search`, and `krs prove` print each configuration through the compiled definition's grammar, in the layout `krun --output pretty` uses (formats, brackets, sorted collections), and reverse aliases only where the printed term is the value: so a print may differ from K's where K's would not denote the state (below).
Each production prints through its `format` (the syntax template, terminals spaced by default), so `while ({condition}) {body}` prints `while (x > 0) x = x - 1;`.
Parentheses come back only where `#[k::precedence]`, associativity, or sorts require them: `(1 + 2) * 3` keeps them and `1 + 2 * 3` gets none.
A non-empty `<k>` cell prints its items joined by `~>` and ending in `.K`, and a finished program's `<k>` holds only `.K`.
Maps and sets print one entry per line, sorted by their printed text with numbers compared by value (`x2` before `x10`), not in a `HashMap`'s order.
Every alias prints in reverse, so with `rule zeroAlias => 0` every `0`, even a value inside `<env>`, prints as `zeroAlias`; a K `macro` (`#[k::desugar]`) is one-way and prints expanded.
The printed alias is its clause's subject built from what the result matched, which is why an alias clause's subject holds no `_`, `@`, `|`, open record, anonymous rest or set concatenation, and binds only names its result uses ([desugar and recursive aliases](#desugar-and-recursive-aliases)).
A clause prints backwards only a term its result matches with every literal it writes, and only where the printed alias expands back to the printed value: with `whole(box(1)) => tag(1)` and `whole(box(2)) => tag(2)`, `tag(1)` prints as `whole(box(1))`, `tag(2)` as `whole(box(2))`, and `tag(3)`, which neither clause's result matches, as `tag(3)`.
Nothing prints a reversal that does not expand back: a name the subject binds only through a subterm it shares with its result takes that subterm's value (`pick(x, h(x)) => k(h(x))` prints `k(h(5))` as `pick(5, h(5))`); a clause whose subject holds its whole result (`twin(x, hold(x)) => hold(x)`) never prints backwards, since every term would print inside a larger one holding it again; a term the subject writes is printed backwards again only by other clauses, so `fc(kk(1), x) => kk(x)` prints `kk(5)` as `fc(kk(1), 5)` and stops; and a name binds only a term of its declared sort.
An `alias-rec` reverses repeatedly: with `nest(.Ints) => nil` and `nest(I, Is) => pair(I, nest(Is))`, the value `pair(1, pair(2, nil))` prints as `nest(1 , 2 , .Ints)`.
`krs parse --output program` prints a parsed program the same way, with its macros as written, as `kast --module MAIN --output program` does: KRS reverses the main module's aliases, while a bare `kast --output program` uses only the program-syntax module, which has no alias rules.
A production without a printable format prints its term as KAST, with a `warning:` line naming it.

### Values from Rust

A Rust program that runs a definition through the `krs-exec` crate can give configuration variables as values and read results by KRS names, without writing K text or reading KORE.
`Semantics::values()` returns the definition's `ValueIndex`, which names constructors and sorts by the Rust path of their declaration, in full or by any `::`-aligned suffix that is unique: `Register::A` or `sm83::machine::Register::A`, never the emitted symbol (`registerC`).

```rust
let index = semantics.values().clone();
let a = index.ctor("Register::A", [])?;
let read = index.ctor("Cycle::Read", [("addr", 1.into()), ("value", 2.into())])?;
let state = semantics.configure(&ConfigInputs {
    variables: vec![
        ("REGS".into(), Value::map([(a.clone(), 7.into())]).into()),
        ("BUS".into(), Value::list([read]).into()),
        ("PC".into(), "256".into()), // text, parsed at the declared sort
    ],
    ..ConfigInputs::default()
})?;
let report = semantics.run(&state, RunOptions::default())?;
let View::State(view) = semantics.view(&report.state)? else { panic!("the state is #Bottom") };
let regs = view.value("cpu.regs")?;          // the cell `regs` of the group cell `cpu`
assert_eq!(regs.as_map().unwrap()[&a], 7.into());
```

- A `Value` is a constructor application (`Ctor`: its declaration, the sort arguments of a parametric production, and its fields by name), an `Int` (a `BigInt`), a `Bool`, a `String`, `Bytes`, a `Float` (its canonical literal), a `Token` of a sort without a builtin hook, a K sequence (`Seq`, the content of a `k` cell), a `List`, a `Set`, a `Map`, or `Opaque`: the KORE pattern of anything else, such as a variable, an unevaluated function application, or a collection with a symbolic part.
- Values carry no injections: `Register::A` is the same value as a map key, a field, or a cell content. Two ground values are equal exactly when they are the same term.
- A configuration value is typed as its text would be, and must have at most the variable's declared sort. A value names its constructor, so it is never ambiguous: as text, a `Map` key is parsed at `KItem`, where a terminal two sorts share (`c`) has two readings.
- A cell path is the chain of Rust field names below the configuration, joined by `.`, so a cell renamed with `#[k::cell(name = "eiPending")]` is still `ei_pending`. `StateView::value` reads a leaf cell, `at` a group cell as a sub-view, `present` whether an optional cell exists, and `instances` the instances of a repeated cell.
- `Semantics::views` gives one view per disjunct of a search or proof state (`View::Bottom` for `#Bottom`), each with the predicates conjoined with its configuration as `constraints()`.
- A configuration value is checked against K's signature and against the element types of the typed cell its variable fills: a `Map<Reg, Int>` value with a `Bool` among its values is rejected (`ExecError::CollectionElementSort`, [Typed collections](#typed-collections)), as the same text given to `krs run -c` is.

For accepted-but-unqualified, open, and absent shapes, continue to [current boundaries and open questions](/reference/boundaries).
