# Current boundaries and open questions

{/* tour-concepts: simplification-priority one-path-claims incremental-semantics open-cell-questions open-grammar-style open-initialization open-formatter-style deferred-term-format-sugar open-rule-doc-style unsupported-logic unsupported-grammar unsupported-cells restricted-rust */}

KRS deliberately exposes less than arbitrary Rust and less than the full K language.
The status words below are part of the tour contract:

- **current** has an implemented public surface and production or canonical positive evidence;
- **qualified** is supported only for the stated bounded shape;
- **unqualified** is accepted below some layer but lacks a positive end-to-end specimen;
- **open** is a recorded design question; and
- **unsupported** is not current public syntax.

## Restricted Rust is intentional

Term islands, readable rule bodies, and configuration initializers accept a checked symbolic subset.
Constructor applications, literals, binders, collection notation, and the documented builtin calls are available where their grammar permits them.
Arbitrary operators, method calls, closures, host `if`/loops, mutation, and generic constructor shapes are not silently interpreted as semantics.

This boundary keeps object-language meaning deterministic and collectable.
If an expression is ordinary Rust, rustc executes or type-checks it as host code; if it is inside a KRS island, the island parser must recognize it as symbolic syntax.

## Qualified or unqualified today

| Surface | Status | Exact boundary |
| --- | --- | --- |
| repeated cells | qualified | `multiplicity = "*"` parses with Bag/List/Map/Set; only Map has language-scale end-to-end evidence |
| program syntax | qualified | each package emits `<NS>-SYNTAX` and `<NS>`; a production over `Map`, `List`, or `Set` is never program syntax, because K has no `-SYNTAX` module for them |
| token sorts | qualified | `#[k::token]` adds regex or terminal token productions to a closed struct sort, another token sort, or builtin `Id`, and `k::lexeme!` writes a token in rules and claims, not in initializers; KRS does not check a lexeme's text against the regex, and does not detect a token regex that shadows K's own rule-level tokens |
| syntactic lists | qualified | `#[k::syntax_list]` declares `List{}` and `NeList{}` of one element sort, with a closed sort and symbols derived from the enum name; there is no slice-pattern sugar, and a list sort has no other constructors |
| layout and lexicals | qualified | `k::layout!` replaces K's default layout and also applies when K parses the emitted rules, which KRS does not check; a layout regex that swallows a terminal breaks Java K's rule parsing but not the native route |
| typed hooks | qualified | the typed catalog exported by KRS is checked; a quoted hook (`hook = "KRYPTO.keccak256"`) must name a hook of the pinned K and k-rust, its signature is unchecked, and the package must set `allow-raw-k = true`; no raw-attribute escape hatch |
| raw K sentences | qualified | `k::raw_k!` keeps one K rule, claim, or context verbatim in the package's semantics module, with `allow-raw-k = true`; K parses it with the package's grammar, a parse error fails the build, and every build warns (the strict profile refuses it) |
| existential rule results | qualified | `#[k::exists]` and `#[k::ensures]` on transitions run symbolically on the k-rust and Java Haskell routes (K tutorial lesson 1.21 agrees on both); the LLVM routes refuse them (`krs::capability::unavailable`); ensures conditions are object Bool, not matching logic |
| fresh values | qualified | `#[k::fresh]` binders on transitions draw from K's shared generated counter through the sort's `fresh_generator` (Int and Id use K's own) on every route; one fresh binder per rule agrees across backends, while K assigns the offsets of several binders of one rule in an unspecified order (k-rust: by name) |
| trusted claims | qualified | `#[k::claim(.., trusted)]` emits `[trusted]`; `krs prove` and Java `kprove` both apply it as an assumed lemma, `krs prove` reports it `trusted` rather than `proven`, and every prove run and Haskell build warns; Java prints `#Top` even for a spec of only trusted claims, so the trusted status comes from `krs prove` |
| SMT translations | qualified | `#[k::function(.., smtlib = "sym")]` emits `smtlib(sym)` and `smt_hook = "tmpl"` emits `smt-hook(..)` with `{field}` placeholders renumbered to `#N`; k-rust (Z3) and Java `kprove` both use them, both are trusted rather than checked against equations, and a function with an `smt_hook` but no equation is evaluated only by Z3 on symbolic paths |
| Concrete, symbolic, and SMT lemmas | qualified | `#[k::simplification(..)]` and `#[k::equation(..)]` take `concrete`, `concrete(x, ..)`, `symbolic`, `symbolic(x, ..)`, and `smt_lemma`, emitted as K's `concrete(X)`, `symbolic(X)`, and `smt-lemma` with the sentence's variable names; k-rust and Java `kprove` agree on a `concrete(x)` simplification that leaves a symbolic claim unproved and on an `smt_lemma` that proves it |
| desugar and recursive aliases | qualified | `#[k::desugar]` emits `macro` and `recursive` on the production emits `macro-rec` or `alias-rec`; programs and rules expand alike on k-rust and Java K, and both printers reverse `alias-rec` clauses; a plain desugar that leaves its own symbol in a program after one step leaves Java K's LLVM run stuck there, while k-rust refuses to execute the program |
| desugar unbound variables | qualified | `#[k::desugar(unbound_variables = [x, _])]` on a desugar clause emits `unboundVariables(X, _)`; k-rust and Java K both expand such a desugar into the rules that use it as a pattern, with fresh variables per use; the key is rejected on every other sentence and on production markers |
| anywhere rules | qualified | `#[k::rule(anywhere)]` on term-shaped rules runs on the k-rust and Java LLVM routes; the Java Haskell route refuses it (`krs::capability::unavailable`), and k-rust leaves a left-hand side that nests the rule's own head unreduced |
| floats | qualified | binary32 (`f32`) and binary64 (`f64`) Floats run on every route; a `FLOAT` operation applied to tokens only and formats other than `f32` and `f64` (`pNxM`) run only on Java K's LLVM backend, and the native and browser routes refuse them (`krs::capability::unavailable`); Java K's Haskell backend has no Float evaluator |
| typed binders | qualified | a rule fn declares no binders or every subject binder, in first-occurrence order, each at its inferred sort or a narrower one; a declared sort an occurrence cannot accept is rejected |
| sort tests and projections | qualified | `k::is!(S, t)` and `k::project!(S, t)` are K's `isS(T)` and `{T}:>S` in results, guards, and claims, never in patterns; a projection that does not apply aborts Java K's LLVM run, while k-rust splits on whether it is defined and ends in a stuck leaf and a `#Bottom` leaf |
| console I/O | qualified | `stream` cells and the `exit` cell run with `krs run`, which reads standard input before the first step and prints the output cell when the run ends, and with Java K's `krun`; `krs search` and the browser route refuse them; the direct `io::write` and `io::putc` hooks run only on Java K |
| KWasm, KMIR, KEVM | qualified | incremental extracts tracked in `semantics/coverage.toml`, not complete ports |
| one-path claims | unqualified | grammar acceptance exists, but no positive end-to-end authored fixture currently qualifies the backend route |
| simplification priority | unqualified | parsing and lowering accept `simplification(priority = N)`; no positive authored macro specimen was found |

Traps need no special KRS construct.
A language defines an ordinary object-language trap state and transitions to it; backend hook/capability failure is a different outcome.

## Open design questions

The following questions remain recorded rather than answered by this tour:

- whether `{ .. }` in a cell position means only a tail map pattern or an all-framed cell record;
- the style rule for naming cross-family precedence groups;
- whether a future const-style configuration initializer should complement `#[k::init]`;
- aligned-column versus fixed-gutter trailing comments (aligned is only the provisional default); and
- the documentation style for individual readable rule clauses.

An implementation or example that depends on one of these must surface the decision; source order and formatter output must not decide it accidentally.

## Unsupported surface

Optional cells and multiplicities other than the qualified star shape are unsupported.
General matching logic, strict casts (`::S` and `{T}<:S`), and arbitrary raw grammar are not current public features; a typed binder or `where x: S` narrows what a rule matches, `k::project!` is K's projection cast, and fresh values are [`#[k::fresh]`](/reference/language#fresh-values).

Method-call term sugar is deferred, and there is no `% ` format escape: a plain space in a format prints as written.
Non-doc block comments inside DSL macro bodies are rejected.
Source order is never a rule tie-breaker: rules are ordered only by `priority = N` or `owise` (see [rule priority](/reference/language#rule-priority)).
`krs run`, `krs search`, and `krs prove` always use the in-process k-rust backend; their results print through the grammar as `krun --output pretty` prints them, and the printer adds parentheses by K's simple algorithm, which is not guaranteed to reparse (as in K).
There is no stepping debugger: `krs run --trace` lists the rewrite steps of a finished run.

When an example needs an unsupported feature, state the semantic gap and use a checked adapter only if its limitation is recorded.
Do not present parser acceptance, a historical draft, or a generated reference spelling as a supported idiom.
