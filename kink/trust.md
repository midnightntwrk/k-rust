# kink's trust document

This file states the premises every verdict of kink rests on: what a kill, a cached outcome and a stored verdict trust, and why each premise holds or how it is checked.
It is normative and kept beside the code.
The user guide is [`README.md`](README.md) ("Using kink-flow", and its summary of this file, "What a kill means"); for a KRS specification it is the docs-site page "Mutation testing a KRS specification" (`docs-site/src/pages/verification/mutation-testing.mdx`).
A change to a premise is judged against kink's decision register, [`decisions.md`](decisions.md).

The k-rust passages and sources cited below with line numbers are cited at k-rust `0068938b1`; kink's drift pins (light-tier tests) pin the ones kink rests on, so a k-rust change that moves one fails a kink test in k-rust's own test run, to be judged then.
The k-rust revision kink keys on and its corpus and campaign documents report (`kink_native::K_RUST_REVISION`, the `k_rust_revision` and `k_rust.revision` fields of those documents, and the semantics identity's `kink.k_rust_revision`) is the version of the in-repo k-rust package; kink-flow's documents and `kink-flow --version` report k-rust's build identity instead (`k_rust::build_identity`, the version and a digest of its sources; KINK-R4); every store honoured without re-deriving its verdicts also keys on the build itself (`kink_build`, below).
kink writes `collect_offered: false` in its execution requests. It reads every run-level field of an execution result, fail-closed: the lists of open values read, contradicted claims, allowance refusals and unsupported hooks each exclude a run (below, "What a kill trusts"), and the count of undecided solver answers is reported only.

## The cache premise

Only a proved difference kills: kink-campaign's runner compares the exit stop and the whole final configuration of the baseline and the mutant on each program.
With identical inputs, a cached proved difference stands without being re-run: this rests on k-rust's compile and execution determinism,
on the cache key naming every input of the outcome (kink's build, the k-rust revision, the specification, the mutation, the program, its baseline result and the budget),
and on the integrity of the cache directory, which is trusted like the build.
`kink-flow run --verify` re-proves every cached outcome and reports any disagreement as an error.
A recorded killer (the lock, `run --lock`) never decides a status: it only orders the work, and a run checks that it still kills; a hand-edited or stale lock can change the cost and the reported killer, never a status.
When a mutation runs live, the baseline result of each program it runs is compared with that program's cached result, which detects a corpus that changed under the cache.
A killed mutation decided by a cached outcome, or a survivor whose every outcome is cached, runs nothing and gets no such check: there the programs' cached results are trusted with the rest of the cache directory.

## What a kill trusts

What a kill trusts, besides the cache premise above:
- k-rust executes the definition correctly: its rewriting, its simplifier and every hook it evaluates, the STRING and INT hooks k-rust 501f18b9 newly evaluates included (re-pin decision 3).
  This includes its state-set merge (re-pin lane 1, L1-1): a test without a pattern oracle runs as one unobserved state-set run on each side, in which k-rust merges equal final configurations and expands each distinct state of a depth once, and a complete state set has exactly the distinct final configurations of the path set of the same request, diagnostics included. Every result run is the state set k-rust answers, whatever its leaves (fz26 KINK-PATHSET-FALLBACK). An undefined step's `Trivial` leaf is never merged and names the rule of the undefined step from its own configuration, so a state set holds one such leaf per distinct pre-step configuration and depth. Every contradicted claim k-rust records for a run, on a leaf, on a sibling candidate or on an arrival the merge absorbed, is on its `contradictedClaims` list, which excludes the run. On a symbolic input k-rust can record none for a `preserves-definedness` claim that is false only at an instance a later step narrows to, and no leaf names that rule either, so such a run is not excluded, in either modality (KINK-PD-SYMBOLIC-INSTANCE, a known gap pinned by kink-native `tests/exclusion.rs`). (The one leaf whose rule is not its own step's is a remainder its own normalization refutes, which names the rule that produced its parent; when that parent is the merged state, a state set names the witness path's producer only, so the `preserves-definedness` leaf rule below can read a contradiction on the path set that the state set does not. That reading never shows the named rule's claim false: the remainder's leaf is `Trivial` only through its own `\ceil` or `Defined` constraints, which come from its parent or its negated condition, and a `preserves-definedness` step adds no definedness obligation, its `requires` and `ensures` being outside its claim. kink-native `tests/exclusion.rs` pins both modalities.) A test with a pattern oracle runs as a stepped path set on both sides.
  kink compares sets of projections of the final configurations, so most comparisons are the path set's. Three routes give a kill where the path set of the same request gives none; each is a real difference between the two sides' sets of final configurations and rests on this premise alone (re-pin decision 3; the orchestrator's judgement in the decisions log, 2026-10-17, which Sebastien can override; kink-campaign `tests/state_set_routes.rs` pins each):
  1. The single-crash rule reads multiplicity: a side is a crash side only when it has exactly one terminal leaf. Two paths to one crash configuration are one leaf in a state set (a crash side) and two in a path set (`unknown`).
  2. An undefined step on a merged state: two paths to one undefined step are one `Trivial` leaf in a state set and two in a path set, which with route 1's single-crash rule distinguishes a crash side from a side whose every path takes an undefined step where both sides as path sets refuse the baseline (since kink27 R1-UNDEF the single-crash rule counts ends only, so the number of undefined-step leaves no longer matters). (Before KINK-PATHSET-FALLBACK this route was mixed modality: a side with an undefined step was replaced by its path set.)
  3. An absorbed bound: an earlier stuck leaf stands for a later depth-bound or indeterminate leaf of the same configuration (k-rust `docs/backend-port.md`, "Final search depth cuts"), which then leaves no leaf, so kink reads the state set as complete where the path set of the same bounds is not. Since k-rust 58720d2e5 this is a k-rust contract (KINK-22, `docs/compatibility.md` "Search results", lines 2129-2134 at 0068938b1, pinned by kink-native `tests/run_facts.rs`): a `state-set` result in which every bound or undecided leaf was merged into an earlier stuck leaf of its configuration reports the final configurations of the same request without those bounds on those paths. kink reads that as the merge's meaning (the configuration is decided stuck by the earlier leaf), not through k-rust's coverage statement, which requires a run without depth stops.
  Also, a state set can finish within the time bound where the path set did not (IMP: `and-false-returns-rhs` is killed by `primes`, `collatz` became comparable; L1-1, confirmed by its review with a single concrete path, `crates/kink-flow/tests/imp_primes_kill.rs`).
  kink-flow `tests/modality.rs` is the safeguard: on the flow corpus, its mutants and the converging fixtures of `testdata/k/l1` (and, on demand, `examples/imp` and its mutants) it runs every program as a path set and as a state set (except on the flows `fuzz/imp`, whose path sets take minutes, and `diamonds`, whose 2^14-path programs exist to show a path set cut by a work or clock bound where the state set finishes; both are listed there without a minimum) and fails on any difference but an absorbed bound: deduplicated final configurations with their terminal classes, undefined steps, incomplete leaves, diagnostics, stack stops, the bridged state-slot inputs and coverage, and, on the flow corpus, the campaign runner's verdict for every mutant under both modalities.
  Every run carries no trace, collects k-rust's run coverage (scheduling and reports only) and answers a cancellation with an error: a timed-out run publishes no leaf.
  Coverage (kink-native `coverage`, `kink/coverage/v4` since a rewrite rule edit is witnessed by `applied` only when it is confined to its result; v3 since re-pin L2-1-tail, v2 since L2-1) is every rule and equation a baseline run matched (k-rust `matched`) and applied (`applied`), and the sentences it fired (a rewrite rule's step some path took, k-rust `committed`, or an equation that gave a result), each predicate named as in every kink-flow document (kink-flow README, "Coverage predicates"). It only orders: a mutant's tests (kink-campaign `selection`) and kink-flow's programs run first where the baseline's coverage witnesses the edit, and the rest after them. Both read the edit from the compiled sides once the mutant compiles (kink-campaign `CompiledEdit::between`, on the claim-free mutant every test runs on; kink-flow, whose programs are ground, reads the mutant as written instead when kink withdrew only definedness claims from it, `total`, `functional` and `preserves-definedness`, since such a withdrawal changes no sentence a run uses, and a ground program whose coverage reaches no edited sentence can reach one on the claim-free mutant only through an operand a short-circuit operator skipped in its baseline run, which its coverage does not record, so the withdrawal adds no witness through coverage: `CompiledEdit::for_ground_tests`): an edit confined to a rule's or an equation's right-hand side or `ensures` is witnessed by `applied`, since the rule is tried, matched and decided as before and only a run that built a candidate of it sees what it builds; every other rewrite rule edit (its `requires`, left-hand side or attributes, a deleted rule) by `matched`, since it changes whether the rule takes a step from a state its left-hand side matches: after an edit of the `requires` or the left-hand side, a run that matched the rule and refuted its old guard can take the edited rule's step, and an attribute edit or a deletion shows, at a state the rule matched, only where a run applied the rule or left its guard undecided (where its guard is refuted, a rule takes no step and blocks no lower priority group wherever it is placed), which `matched` holds without telling an undecided guard from a refuted one; an attribute edit that raises the rule in its site's trial order (a higher priority, a removed `owise`) can also show at a state where the old rule was not tried, and a deletion or an edit that lowers the rule at one where its match was left undecided, which blocks the lower priority groups: only k-rust's `offered` records those states, kink does not collect it, and such a run is no witness and runs after the witnesses; an equation edit by `matched` when it changes the `requires` (alone or with the right-hand side or `ensures`); every other edit, such as an equation's left-hand side or attribute, an `owise` or `smt-lemma` equation, the `requires` of a `concrete` or `symbolic` equation or a deleted equation, is witnessed by every test, so it keeps manifest order (in kink-flow, its cost or corpus order). An alias of a left-hand side (`P #as V`, which k-rust's compiler also writes for a subterm of the left-hand side that the right-hand side builds again) is read as the pattern it names, with `P` for `V` in the rest of the axiom, since the axiom then has the same instances (kink-campaign `selection`). kink-campaign reads its tests' coverage by compiled id; kink-flow's result records keep coverage by baseline sentence, so it reads each removed id through the compiled baseline's rule authors (`CompiledEdit::witness`; kink-flow README, `run` step 3), and the two orders can differ there: kink-flow witnesses a removed id with no baseline sentence (an axiom a compiler pass generated) by no program, where kink-campaign witnesses it by compiled id, and a sentence behind several compiled ids by a program that matched or applied any of them, where kink-campaign counts only the removed id. No test or program is ever left out. In the no-Z3 profile (kink's default build), while no wall-clock bound fires (kink-flow's `budget.time_ms`, kink-campaign's `ExecutionBudget::time`), no status therefore depends on coverage or on any other order: under first-kill a kill ranks above every other outcome and every test before the first kill runs, which needs each test's outcome not to depend on the tests run before it, as k-rust's Execute promise gives. That promise excludes a request the clock bounds or cancels, so a run near its time bound can time out in one order, while caches are cold, and finish in another: the order can then move a status between `timeout` and the status the run gives when it finishes (a `timeout` is host- and timing-dependent anyway; review L2-1-tail-1 D2). Under Z3 the promise covers the resource-bounded queries kink's backends ask (kink-native `BACKEND_OPTIONS`, kink-flow's `[budget] smt_resource_limit`): whether such a query is decided is a function of the query, the units and the Z3 build, whatever a reused backend asked before (k-rust `docs/compatibility.md`, Execute), so the same holds in the Z3 profile. Under a solver bounded by the clock the premise would fail: an SMT query could time out, and a mutant's backend and the baseline's are reused for every test in schedule order and keep a cache of satisfiability answers across requests, so the order could move a status between `killed`, `unknown` and `survived`: a solver timeout makes a test `unknown`, and a cache an earlier test warmed can answer the same query, turning that test into a kill or an agreement, so with no kill the fold gives `survived` in one order and `unknown` in the other (review L2-1-tail-1 D1). It never gives a false kill, since a kill is still a proved difference (re-pin L2-1-tail, review L2-1-1 D4). kink-flow turns its outcome cache off for such a solver for the same reason.
  A mutant's state-set run may carry a work budget calibrated from the baseline's run of the same test (kink-flow `[budget] work_factor`; kink-campaign `WorkBudget`): a run it does not stop is the unbounded run, and a run it stops ends in a `work-bound` leaf, which never completes the run, so the program is `unknown` for that mutant unless the one-sided rule below kills it. Baseline runs and stepped runs are never work-bounded.
- A work-bound mutant run can kill one-sidedly (re-pin L1-2, decision 6, finding A-15; kink-campaign `OneSided`, which kink-flow turns on). k-rust checks the work budget before it expands a state, so every leaf before the `work-bound` one is a state whose own expansion finished; since k-rust 58720d2e5 this is a k-rust contract (KINK-22, `docs/compatibility.md` "Work budget", lines 2346-2349 at 0068938b1, pinned by kink-native `tests/run_facts.rs`): every leaf finished before the `work-bound` leaf is a leaf of every run of the same request with a larger budget or none, at the same position. In a build with Z3 k-rust gives this only when neither run reports `smtUnknowns` (line 2349), a count kink carries and never reads (decision D-7 (a1), below). The rule does not rest on the contract there, and needs no such condition: it reads only a leaf that is a fact of its own path. k-rust reads an undecided answer as an over-approximation (`docs/compatibility.md` line 2516): it refutes a branch or discharges a condition only on a decided answer (for example k-rust-backend `rewrite/step.rs` `may_have_instance`, where only `unsat` refutes), so a path an undecided answer kept still carries the condition it left open in its state, or a diagnostic saying a condition was left undecided. The rule refuses both (no path predicate on the leaf, no diagnostic on any leaf of the run; kink-native `work_bound_stuck_terminals`), and the leaf's reachability and finality below follow from its own path, not from the order of exploration (the contract's further fact, that the leaf keeps its position, is one the rule does not use). When such a leaf is stuck, clean (no diagnostic, no contradicted claim) and a ground value (one term, no path predicate, no free variable, definition-independent on the mutant's own definition), its configuration is reached from the test's initial state and final in every model, so it is a final configuration of every completion of the mutant's run. If the slot's projection of it is not in the baseline's projected set, the mutant's projected set differs from the baseline's whatever the unexplored part holds: the slot distinguishes, and the mutant's side stays `unknown`. The rule needs all of: a baseline side that is a value (a complete run free of every exclusion), a ground test, a mutant run judged into sides (not an error, not timed out, no exclusion) whose only incompleteness is its last, `work-bound` leaf (no stack stop, no diagnostic on any leaf, every other leaf stuck, an undefined step or vacuous, every other path complete, no crash), a slot projecting the whole term, the configuration without its unobservable cells or the exit stop without an exit-code cell (projections defined on every configuration, below), and a classifier that never answers crash (the caller states it: kink-flow's and kink-corpus's `all_normal`; the slot does not compare a set mixing a crash with a normal terminal, and the rule cannot see the unexplored part). Never from a cancelled or timed-out run (decision 6), never on a pattern slot (stepped runs carry no work budget). Contradicted claims are read per path (Sebastien, 2026-10-17, "Land per-path, on"). A kill must be a fact about the definition the author meant. Suppose a claim the claim-free mutant kept is false (a kept claim's support is untouched by the edit, so it is a false baseline claim, against the trusted premise above), and correct it to "true except where it fails": the definition then has models, the baseline's complete set is unchanged, and so is the killing leaf's path, unless that path itself used the claim at an input where it fails, which is the same undetected risk every two-sided kill carries (a false claim used in a condition shows in no leaf, decision 2 below). The unexplored part of the mutant's run can only add or remove other final configurations, never take the killing leaf away. So a contradiction elsewhere in the mutant's run, explored on another path or unexplored, does not void the leaf; one on the leaf's own path does, and the rule refuses it: the leaf is stuck (not an undefined step), carries no contradicted claim and is a decided value (a stuck term that is not a value, such as `f(-1)` left unevaluated under a false `total`, is no leaf). The rule also reads the explored part as decision 2's per-test rule does (an explored contradicted leaf makes the run no evidence), which is stricter than the principle needs and harmless. The rule adds no execution premise; for claims it applies the per-path principle, of which the two-sided per-test rule (decision 2 below) is a conservative over-approximation, so a work budget can kill where the unbounded run is `unknown`: the L1-2 review's probes `testdata/k/l1/l12ct.k` (k-rust names the contradicted `total` on the late branch) and `l12cs.k` (the late branch ends in a term that is not a value) are `unknown` unbounded and killed one-sidedly under budgets 14, 7 and 3 (kink-campaign `tests/one_sided.rs`, which also checks that the killing leaf is a clean leaf of the unbounded run apart from the offending one). Making the two-sided rule per path too would relax a refusal; it waits for a separate decision. A one-sided kill is deterministic under a given budget (k-rust's work count is a function of the request), so kink-flow's tier 1 records it, keyed with the budget. The rule's version (kink-campaign `ONE_SIDED_VERSION`, v3 since the cell projection joined the total projections, v4 since a run with a stop gives one-sided evidence across its stages, v5 since the cell projection reaches cells inside `?` and `*` cells) is a component of kink's semantics identity (below, re-pin L1-2-land), so a store or cache made without the rule or under another version of it misses or is refused, naming `one_sided`. kink-campaign `tests/one_sided.rs` pins the rule and checks, on a fixture, every budget below the mutant's work against the unbounded verdict, and on the probes, whose unbounded run does not compare, that every one-sided kill is explained: the unbounded run is `unknown` only because of a contradicted claim or a non-value terminal on a leaf other than the killing one (`testdata/k/one_sided_support.rs`); kink-flow `tests/one_sided.rs` (on demand) does the same over the flow corpus and over IMP.
  The rule needs the slot's projection π to be total, defined on every configuration a completion of the mutant's run can end in.
  For a total π, every completion's projected set holds π(ℓ) of the killing leaf ℓ, so π(ℓ) outside the baseline's complete projected set makes every completion's set differ from the baseline's, whatever the unexplored part holds.
  A projection that fails on some configuration would make the two-sided comparison of such a completion `error`, not a set difference, so the argument does not reach it: a term-path slot, whose path an unexplored end need not have, is excluded, and so is the exit stop with an exit-code cell, which fails on an end without exactly one `Int` code.
  The whole term and the exit stop without a code cell are defined on every configuration.
  So is the cell projection (kink-campaign `StateProjection::Cells`, next bullet): it walks each uncompared position's argument path from `<generatedTop>`, through each instance of a collection on the way, checking the symbol of each cell on the path and that the subterm at the position has the position's sort, replaces that subterm by `\top` of the sort, sorts the components of each Map or Set collection it passed through, and leaves an end without the position as it is, so it never fails; the argument applies to it unchanged, and nothing else in the rule reads the projection.
  Under a stop (kink-flow `[stop]`, the bullet after next) the rule reads a clean ground stop leaf of the run, a `cut-point` or `terminal` leaf at its path's `N`th stop event, as it reads a stuck one (v4).
  Such a leaf is final in the truncated system by a fact of its own path: its last step is its `N`th stop event, or its one successor is a step of a rule the run stops before, decided without a diagnostic (an undecided guard keeps a branch, a predicate or a diagnostic, each of which the rule refuses); the path's earlier stop events are steps of it like any other.
  Under a stop condition (`[stop] when`, v6) its last stop event is an arrival at which the condition was decided to hold of the stop state, and every earlier arrival of its path was decided to fail or was an earlier event; each decision is a fact of the observer and that state, not of a budget, since an equation applies only where its condition is decided true, so the leaf is final by a fact of its own path as before.
  A run with a path that ended at an arrival the condition left undecided gives no one-sided evidence: it is no evidence at all (`stop-condition`, below).
  So every completion of the run has it among its ends, as it has a clean ground stuck leaf.
- Unobservable cells.
  A cell declared `unobservable` (k-rust `docs/compatibility.md`, "Unobservable cells") holds state no use of the definition may observe, and the attribute changes nothing the definition computes: it is not emitted to KORE.
  A cell slot (kink-campaign `StateProjection::Cells`; `CellLayout::unobservable_projection` builds the one that leaves out every unobservable cell from the compiled baseline's configuration, and a narrowed one takes its positions from `CellLayout::position`) compares each end with its counter content erased, as a whole-term slot does, and with the subterm at each uncompared cell's position replaced by `\top` of the position's sort; a crash side of the slot is projected the same way.
  A position is the cell's argument path from `<generatedTop>`: a cell application's arguments are its production's non-terminals, in order, so through cells of multiplicity `1` that path is the same in every end.
  Inside a `?` or `*` cell a position is fixed relative to the instance that holds it, so the walk reaches it in each instance.
  A `?` cell's position holds its instance, the cell's own application, and the path goes on through it; an absent cell has no position below it, and presence is compared.
  A `*` cell's position holds a collection: its elements and the rest folded by the collection's concatenation (the symbols its sort declares with the hooks `MAP.element`, `MAP.concat`, `MAP.unit`, or `SET.` or `LIST.`).
  The walk goes on through the instance in each element, then sorts the components of a Map or a Set, so that the projection of the collection is a function of the multiset of its projected components, whatever order the end wrote them in; a List keeps its order, its instances' identity.
  A Set is never re-read as a set, which would merge instances the projection made equal: two jobs that differ only in an unobservable cell stay two.
  A Map holds each instance by its key, the instance's key cell, which the element also holds beside the instance, so a Map's projected collection is the map from each key to its projected instance; the key itself is never left out (`map-key-left-out`), since the walk goes on through the instance alone and the element's key argument would still carry the content left out: drop `unobservable` from the key, or mark the `*` cell unobservable so that the whole collection is left out.
  The walk checks the symbol of each cell on the path, and at the position that the subterm there has the position's sort under the baseline's declarations: an application of a symbol the baseline declares with that result sort, an injection into the sort, or a variable of the sort.
  So the placeholder stands where a pattern of its sort stood, and the projection is well-sorted wherever the end is.
  Two ends then have equal projections exactly when they are equal outside the counter's content and outside the uncompared positions, each Map or Set collection on a position's path read as the multiset of its components: where both ends have a position, the placeholders agree and the rest is compared; where neither has it, nothing is replaced; where one has it and the other does not, they differ at or above it (an instance's presence, key or list position included), and one projection holds the placeholder where the other holds a subterm that is not it.
  So a kill under a cell slot is a difference some compared cell shows in some end, never a difference only in an unobservable cell.
  A survivor of a cell slot is a survivor relative to the cells it compares, and says nothing about the content of the cells it leaves out; a cell wrongly declared unobservable can hide kills, never make one.
  Only positions are left out, never other applications of a cell's symbol, so a cell term held as data elsewhere (inside `<k>`, say) is compared.
  A `?` or `*` cell can itself be unobservable: its own position is left out, the whole optional cell or collection.
  A `cell` production written outside any configuration has no position in any end, so declaring it unobservable is refused (`unobservable-cell-outside-configuration`): declare the cell in the configuration, or drop the attribute.
  The data judgement still reads whole ends ("Every compared end is data under both definitions", below): an unobservable cell that holds a non-value makes the slot `unknown`, which is stricter than the projection needs and never wrong.
  The projection is the baseline's and applies to both sides: a mutant that only adds or removes the attribute compiles to the baseline's KORE and is `equivalent`, and where a mutant's end has another shape than the baseline's on a position's path or at the position, the walk replaces nothing there, which can only add differences that are real: the ends differ there in a cell the slot compares.
  kink-flow's second slot is this projection whenever some cell is left out (kink-flow README, "Which cells are compared"): without `[result] cells` it is `CellLayout::unobservable_projection`, so a mutant that changes only an unobservable cell is not killed there, and admission refuses the projections above at stage `result`.
- A run with a stop is a run of the truncated system, and a kill is relative to the stop (kink-flow `[stop]`, README "Where a run ends"; kink-campaign `Stop`, `STOP_VERSION`).
  A stop σ is rule sets `B` (stop before) and `A` (stop after), each named on the definition run, and a count `N`.
  A stop event is a step by a rule of `B` or `A` that is its state's only successor.
  The truncated system T'σ has the states `(s, k)`, `k` the stop events passed: after a rule of `A`, the event leads to `(s', k + 1)`, final when `k + 1 = N`; a state `(s, N - 1)` whose one successor is by a rule of `B` is final; a state with no successor is final, the run's own end.
  An end is a final configuration of T'σ reachable from the test's initial state, without `k`; with no stop T'σ is the definition's system, and every verdict is what it was.
  A kill is a difference between the projected end sets of the baseline under σ and the mutant under σ: a fact of the observation σ states, not of what either side does after it.
  - k-rust stops a path only where the selected rule's step is the state's one successor, and lists each selected rule it went on past where the step had another (`passedStops`, k-rust `docs/compatibility.md` "Passed stops").
    A run with such an entry is excluded on either side (`passed-stop`, `unknown`), so every verdict is a fact of the system in which every step of a named rule is a stop event, which on a deterministic baseline is the system the author meant.
  - k-rust merges two states only where their subtrees in T'σ are equal: a state only with one whose path passed as many stop events, a cut point by configuration (that a rule of `B` is the one successor is a fact of the configuration) and a terminal leaf by arrival, only with leaves that are final there.
    A stuck and a stop leaf of one configuration can merge, keeping either halt, so the halt is never compared: both are ends of T'σ, compared alike, and kink-flow reports the halt as evidence only (`halt`).
  - The count is k-rust's (`stopCount`, k-rust `docs/compatibility.md` "Stop count"): a run to the `N`th stop event is one request from the program's initial configuration, whose paths count their stop events, take each one before the `N`th as any other step (committed, so a cut point's rule has fired) and end at the `N`th.
    Its stop leaves and its own ends (stuck, undefined step) are the ends of T'σ from that configuration, and a bound, a diagnosed leaf or an exclusion keeps the run incomplete, as in a run without a stop.
    `max_depth` bounds each path from the initial configuration, the work budget and the time budget the whole run, as without a stop; a leaf whose count of stop events its request cannot yield (a stop leaf short of `N`) refuses the run.
  - Each side resolves the names on its own definition, by the exact label of a rewrite rule: a `UNIQUE_ID` names one rule's text, which any edit of the rule changes, and an equation takes no step.
    A baseline on which a name selects nothing is refused (stage `stop`), and such a mutant is `not-admitted` (`stop-unresolved`), never run without its stop, which would compare ends of two different observations.
  - Under a stop before a rule with `N = 1` the rule's step is never taken, so an edit of only its right-hand side or `ensures` changes no end and survives; with `N > 1` the run takes its first `N - 1` steps, and an edit of its left-hand side, `requires` or attributes moves the stops. kink-flow warns of such an edit (`stop-hides-edit`), and of a deletion of a rule the stop names, whose mutant is `not-admitted` (`stop-rule-deleted`).
    A mutant that never reaches its `N`th stop meets a bound and is `unknown` (a one-sided kill still possible); one that ends first, on its own or at another stop, has another end, a kill where the projection differs.
  - Under `[stop] when`, a stop event is an arrival whose stop state (the state before a stop-before rule's step, the successor of a stop-after rule's) satisfies the condition (kink-campaign `Stop::with_when`, `STOP_VERSION` v3).
    The condition is a function of named cells of that state, evaluated in one fixed observer definition, the named observer package or else the baseline, for the baseline and every mutant alike.
    A mutation therefore changes the states the condition is asked at, never the condition, and a kill is relative to (definition, stop rules, count, condition): with the condition P, T'σ counts only the arrivals where P holds, takes every other arrival as any other step, and a condition that holds everywhere is the stop without one.
    An arrival where the condition has no value or is undecided makes the run `unknown` (`stop-condition`) on either side: continuing would run past a possible stop and stopping would claim an event that was not shown, so neither ends the path in T'σ; on the baseline the program is not judged, named in the results.
    Such a result is never cached, since an undecided answer can be its evaluation's budget.
    The front end reads every side's cells with the baseline's declarations of their values, and refuses a term with a part the baseline does not declare (that arrival has no answer, and the run is `unknown`), so a reading can be wrong only through a part both definitions declare, declared otherwise.
    A mutant that declares a sort or symbol the read cells reach otherwise than the baseline (another signature, a function where the baseline has a constructor), or a subsort of a reached sort between two sorts the baseline declares that the baseline does not have, is therefore not admitted (`stop-condition-incompatible`), never run under another reading of its states; a constructor it adds under a new name, or one it lacks, is admitted.
    The condition is not asked at a passed stop, which stays an exclusion.
    Under a condition a stop rule's step is taken at every arrival where the condition fails, so a count of 1 does not hide the rule's right-hand side by itself; it is hidden exactly where no judged program took the step (every arrival of every path was an event, ending it), which `check` reads from the comparable programs' coverage, and warns of then (`stop-hides-edit`).

- The same holds for short-circuiting (re-pin decision 1, `short-circuit-reading`).
  `domains.md` lets a concrete backend skip an operand of `andBool`, `orBool` (and `impliesBool`) and `#if`, and calls `andThenBool` and `orElseBool` short-circuiting; k-rust evaluates the definedness of every operand, so a step through one whose skipped operand is undefined (`false andBool 10 /Int 0 >Int 0`) is an undefined step in k-rust and a value elsewhere.
  For K that KRS emits, the strict reading is the meaning: KRS documents `a && b` as exactly `bool::and_then(a, b)` and `a || b` as `bool::or_else(a, b)`, each keeping the definedness of the operand it does not evaluate, with Rust's laziness had only by branching into separate equations (`docs-site/src/pages/reference/language.mdx`, sections "Operator and method notation", "Partial constructs in a condition" and "Branching bodies"; k-rust's own statement is `crates/k-rust-backend/src/deferred.rs`).
  The exclusion exists because K's text admits both readings, and because claim removal may withdraw a mutant's `total` claims (below), so an operand the baseline declares defined may be undefined in a mutant.
  The analysis below flags a rewrite rule whose right-hand side applies one of these over an operand that may be undefined (a partial function, directly or through a function's equation), a rule whose condition depends on it, and one whose right-hand side applies a function whose equation's condition does; no leaf need show where the readings part: an undefined candidate beside a defined same-priority sibling leaves no leaf (k-rust drops it and keeps the sibling's successor), and an undefined condition just leaves the rule unapplied.
  The analysis is k-rust's `k_rust_backend::short_circuit`, which `krs check` reads too: on a KRS definition it warns at every operator a KRS sentence's reading depends on where a dependence originates (`krs::analysis::skipped-operand`), each at the place the author wrote it, a `let` block's included, and at each of the sentence's applications of a prelude function whose equation holds one, unless the author's `skipped_operand` key silences it or `krs::analysis::dead-guard` already reports the operand's construct.
  Since CF-03 such a definition is not excluded as a whole: each run is judged by what it read.
  The operand a skipping reading may skip is the one after the deciding left operand: the branch a decided `#if` does not select, and the right operand of `andThenBool`, of `andBool` after `false`, of `orElseBool`, of `orBool` after `true` and of `impliesBool` after `false`.
  A skipping reading evaluates the deciding operand, and a `[simplification]` such as `_ andBool false => false` binds an element variable, which matches only a defined value, so it licenses no skip of an undefined left operand.
  k-rust lists, per run, every place its work used the strict definedness of such an operand and did not find it defined (`shortCircuitReadings`, k-rust `docs/compatibility.md`, "Short-circuit readings"), with the rewrite rule whose work used it.
  A memo's reuse is attributed to the work it serves, and the load's undefined entries are on every run's list.
  A completed run whose list is empty is the same run under a skipping reading: an operator application differs between the readings only where a skipped operand is undefined in the strict reading, so every term the run evaluated has the same value in both, and so does every match, condition, equation choice (an `owise` guard included), dropped candidate and successor, by induction on the run's steps.
  The premises are kink's own: the claims each side keeps are true (the trusted-baseline premise; a mutant's unbacked claims are removed, below), and evaluation terminates (A1; k-rust evaluates an operand a skipping reading skips, so a diverging one is a timeout, which kink never judges).
  So on a definition the analysis flags, a run is excluded (`short-circuit-reading`) exactly when its list holds an entry that counts: one its definition's load observed, one of no rule's work (the initial state's normalization, a step's remainder, a leaf's constraints), one of a flagged rule's work, and, on a run that does not start from a ground state or on a definition whose rules introduce variables, every entry (a term a flagged rule built can then be evaluated later under another rule).
  An entry of an unflagged rule's work on a ground run does not count: the analysis shows that rule's applicability and successor equal in both readings.
  A backend that lists no readings leaves every run of a flagged definition excluded.
  A non-empty list does not show that the readings differ, so the rule fails closed.
  On a definition the analysis clears, no list is read for the rules (its over-reports, such as a positive conjunct of a condition, are what the clearance ignores).
  The analysis of rules does not cover what a test's initial state applies, so a run whose initial state applies a reading-dependent function or operator is judged by its list on every definition, by the same counting rule: the state's normalization is work of no rule inside the run, so with no entry that counts the run starts from the same state in both readings and is the same run.
  On a cleared definition an entry of no rule there can be an over-report of a step's remainder, which the list does not tell from the state's normalization; for such a state it counts anyway, which only fails closed.
  The rule does not depend on what else the analysis flags, so a flag on an unrelated rule changes no such run's class.
  kink-flow names each counting entry (rule, operator, outcome, operand) in the program's result row and in a mutant's executed entry, and `check` names the flagged rules (`spec.short_circuit`) without failing on them; `check` reports a program excluded at stage `initial-state` when its depth-0 run, the normalization every run of it starts with, already lists an entry that counts against its initial state.
  A route that judges without a run's list reads the analysis instead.
  kink-flow's fuzz witness filter refuses a case whose initial state applies such a function or operator, or whose leaf is an undefined step of a flagged rule: it can refuse a case kink would judge, and it can keep one kink's confirmation then refuses, since it never sees the run's list (a flagged rule whose condition reads an undefined skipped operand does not apply, so the run ends in no `trivial` leaf of that rule); the confirmation's judgement is the verdict.
  A pattern query's `no` needs the search's own list to hold no entry that counts, as a run's.
  "May be undefined" is read on the definition each side runs: a mutant's after the claims its edit leaves unbacked are removed (below), so a function whose `total` was removed counts as partial there; the analysis trusts the `total` declarations and the ceil equations a definition keeps.
  Cost: none on testdata, flow or examples (kink-native `sweep::heavy::every_testdata_definition_passes_every_definition_check`).
  Since CF-01 a condition is read leaf by leaf.
  A K condition compiles to a matching-logic predicate built with the connectives `\and`, `\or`, `\not`, `\implies`, `\iff`, `\exists` and `\forall`.
  Its leaves are of two kinds.
  One is the Bool reading `\equals(C, true)` of a Bool term `C`, which the argument below reads.
  The other is every other part of the side that holds the condition: an `\equals(t, u)` of two terms (a K `#Equals`), a `\ceil`, an `\in` (an argument constraint, or a match part of an `owise` guard) and a rewrite rule's configuration; each is read whole, as a term, by the operand-definedness analysis below.
  An `owise` equation's guard is `\not(\or(\exists.(\equals(C_i, true) /\ match_i), ..., \bottom))` over its competitors' conditions `C_i` and their match parts `match_i`.
  Where `C` is a tree of `andThenBool` and `andBool` over atoms that do not depend on the reading, both readings make `C` true exactly where every atom is true, and differ only as `false` (a skipped conjunct) versus `\bottom` (k-rust's strict value); `\equals(false, true)` and `\equals(\bottom, true)` are both `\bottom`, so the leaf, and every connective over such leaves, has the same truth value in both readings.
  The argument covers no other Bool leaf: where `C` has a skippable operand under `orElseBool`, `notBool`, `impliesBool` or `#if`, the readings can differ as `true` versus `\bottom` (`true orElseBool u`), and the leaf keeps the operand-definedness analysis below.
  So an `owise` equation over an `andThenBool` condition with a partial operand (SM83's `decode`) does not depend on the reading, and neither does the prelude's `replace`, whose `owise` equation negates `Count >Int 0 andBool findString(..) >=Int 0`.
  A skippable operand counts only where one of its applications of a partial or reading-dependent function is evaluated by no operand that runs whenever it is skipped (KINK-SC-DEFINED, the must/may rule of kink-native `exclusion.rs`): where every one is, both readings are undefined together, so `#if pd(A) >Int 0 #then pd(A) #else 0 #fi` is not flagged and `#if A >=Int 0 #then A #else pd(A) #fi` is, whatever its guard says; no guard's truth is read.
  An application of a partial function counts only where the definition's ceil theory does not discharge it beyond its arguments (CF-01, k-rust-backend `application_owes_nothing`): `bitRangeInt(X, 4, 4)` and `X /Int 16` owe nothing (the ceil equations of `INT-SYMBOLIC-KORE` and its amendments in `domains.md`), `X /Int Y` owes `Y =/=Int 0`, so `notBool (X >=Int 0 andThenBool bitRangeInt(X, 4, 4) ==Int 0)` is not flagged and `notBool (X >=Int 0 andThenBool X /Int Y ==Int 0)` is.
  A recursive function's own calls are read as independent while its equations are checked, which rests on premise A1 (evaluation terminates).
  This clears the prelude's `findChar`, and so the `stdin` stream rules whose conditions apply it.
  A definition with `stdin`/`stdout` stream cells is therefore excluded neither by this rule nor by the census: the I/O hooks of kompile's copied stream rules are run-list hooks, judged per run through `unsupportedHooks` (above).
- A mutant drops the claims its edit leaves unbacked (re-pin R0c-fix-2, Sebastien 2026-10-17). A claim is the specification author's assertion about the definition they wrote: k-rust trusts it instead of checking it (kink-patch `TRUSTED_CLAIMS`, each with its k-rust citation: `total`, `functional`, `injective`, `smt-hook` and `smtlib` on a production; `preserves-definedness` and `smt-lemma` on a rule; the `simplification` lemmas; an equation's non-trivial `ensures`; a `concrete` or `symbolic` equation; a hooked symbol's equations). When a mutation edits part of the definition, every claim whose truth depends on the edited part is backed by nobody, and a mutant carrying a false one is an inconsistent theory on which any verdict follows. So kink builds every mutant without them (kink-patch `ClaimSupport::withdraw`, the one function the campaign runner, kink-corpus and kink-flow build mutants through): the edited symbols E are the heads of the edited equations (a rule written with configuration context, `rule [[ F ]] C`, is an equation of `F`'s head, as k-rust reads it; re-pin R0c-fix-4), a symbol reaches E when one of its equations (left side, right side, `requires` or `ensures`) applies a symbol of E or one that reaches E (the equations kompile generates count too: each member of an `overload(key)` family reaches every other through the overload axiom `g(inj(x)) = inj(l(x))`, and a production with `unit(u)` reaches `u`; re-pin R0c-fix-3), and kink removes the claims of every symbol in E or reaching E, every lemma that mentions one (deleted: a lemma is a claim as a whole), and the `preserves-definedness` and `smt-lemma` of every rule that is edited or applies one. An edit of a rewrite rule only removes that rule's own claims (the lambdas kompile generates for a `#let` or `#fun` in it carry no written claim: a lambda is declared `total` only by k-rust's judgement of its body on the claim-free mutant). Baseline claims are a trusted premise; mutant claims the edit can affect are removed, so k-rust executes the mutant without trusting them, and every test, ground or symbolic, runs on it. Removing claims makes the mutant's claims backed; it does not make it a consistent theory by itself (next item). Equivalence is decided on the mutant as written, with the baseline's claims, so removing claims never makes a mutant `equivalent`. A claim no removal takes away without changing the definition (one the patch writes, a lemma it edits or inserts, an equation's `ensures`, `concrete` or `symbolic` restriction or hook agreement whose support the edit touches) refuses the mutant (`unsupported-claims`), and so does a claim-free mutant k-rust does not compile (`stripped-claim-compile-failure`); both are `unknown`, never killed. The removed claims are recorded per mutant (the campaign report's `claims`, kink-flow's `removed_claims` and its outcome files), and kink-flow's tier-1 context names the removal algorithm's version. On testdata and examples, catalogue-v1 mutants with removed claims and refusals are counted in the R0c-fix-2 handoff; IMP declares no function, so nothing is removed there.
- A mutant must be a theory with models (re-pin R0c-fix-3; decisions log 2026-10-17, "inconsistent mutants"). `function` is part of a symbol and a function has at most one value per input, so an edit that makes two equations of one function apply to the same input with different values (a guard literal, a dropped `owise` or `priority`) leaves a mutant with no model, and k-rust's verdict on it is the order in which it lists the equations (the R0c-fix-2 review's `fpos` 0 -> -5 was killed and its mirror `fneg` 0 -> 5 survived). After claim removal, kink checks every pair of equations of every symbol the edit can change with k-rust's own load-time critical-pair check (kink-native `consistency`, `BackendDefinition::value_claims_in_scope(CheckScope::All)` on the claim-free mutant): root pairs of one priority group (an `owise` group is its own), self pairs of a map or set pattern, inner pairs, k-rust's reports of an equation it never applies as written, and the precondition rows that put an equation outside the check (a constructor-headed or injection-headed row refuses only when its equation is itself checked: k-rust classifies no overlap of such an equation, so one with a checked equation below the root of a checked left-hand side would be neither classified nor refused; no K source is known to give one, re-pin R0-tail). A pair the check does not show to join (the reducts differ, a condition is neither refuted nor decided, the join is refused or runs out of budget, ...) refuses the mutant as `inconsistent-mutant`, naming the pair (the campaign report's and kink-flow's `inconsistent_pairs`): it is `not-admitted`, like a mutant that does not compile, outside the score, never killed or survived. So is a check that cannot run: kink reads the claim-free mutant's full check (`CheckScope::All`, which has no early return for a definition that declares no equation head; before fz26 KINK-BASELINE-FINDINGS kink checked a copy with an added equation head instead), computed once on the backend the mutant runs on (`Backend::from_definition`, kink-native `data::DataFacts`), and refuses the mutant when the check did not read every executable equation, skipped a candidate pair, classified fewer pairs than the definition's root pairs, or met a stop for lack of stack (`condition_stack_stops`). k-rust reports these counts for the whole definition only, so the guard shows that the check ran on the whole definition, not that each group's root, self and inner pairs were classified. Which symbols the edit can change is read from the compiled definitions, which k-rust executes (re-pin R0c-fix-4, kink-native `consistency::admit_mutant`): every index of the claim-free mutant's function theory whose equations differ from the baseline's (compared without their unique ids, origins and the claims removal handles; an index on one side only counts; the simplification and ceil lemmas are compared alike, and a changed predicate lemma checks every head), and every index whose equations reach one over either compiled theory (an equation reaches the symbols it applies; an overload family is linked both ways), together with kink-patch's source reading (`ClaimSupport::affected`); a changed or reached index that is not a symbol checks every head. So the equations kompile generates (the `#lambda` of a `#let` or `#fun`, in a rewrite rule or a function equation) and equations whose source form kink-patch would misread are checked. An edit that changes no compiled equation still has the symbols of kink-patch's source reading checked (an equation edit that compiles equal except in what the diff ignores is checked on its head), and an unknown source reading checks every head; only an edit that changes no compiled equation and whose source reading names no symbol checks nothing (re-pin R0-tail). The source reading is a fail-closed cross-check: every compiled equation that a sentence the patch touches or inserts gives, on either side, must be headed by a symbol kink-patch reads as redefined or by a generated lambda, and no other generated `total` symbol may have changed equations; otherwise the claims the edit leaves unbacked are not known and the mutant is refused as `unsupported-claims` (key `unread-equation`). The check reads the mutant's heads only: a pair of symbols the edit cannot reach is the baseline's, normalized with the baseline's equations; kink checks that every such finding of the mutant is the baseline's, by name and by the unique ids of its equations, and refuses a difference as `mutant-findings` (`unknown`), and the baseline's own pairs are the next item's. The witness equations the full check adopts (k-rust FZ-EMPTYJOIN-WITNESS: each interprets a stuck partial application at an element of a sort with no normal form, and a pair may join only through one) are part of the edit's effect (fz26 KINK-WITNESS): they are read from the same full checks the gate reads (`DataFacts::witnesses`), a head whose witnesses differ from the baseline's counts as changed and a witness reaches the symbols it applies as an equation of its head does, and a flip of the pass the check adopts between baseline and mutant checks every head, so a mutant whose check then keeps a pair unjoined is refused as `inconsistent-mutant` before the `mutant-findings` comparison. Premise: k-rust's critical-pair checker decides joinability in `M+` correctly, and A1+ holds (the equations "have `M+` as a model when the executable equations and the witness equations the check adopts terminate innermost over the signature with the added constants (A1+), and their critical pairs join, which the backend checks", k-rust `docs/compatibility.md`, where `M+` adds a fresh constant to each sort that does not have an element in every model and agrees with `M_NF` on every term free of them; A1+ is a premise k-rust states and does not check; the passages and the checker's source are pinned by digest in kink-native's `consistency` test). The check proves nothing beyond k-rust's simplifier without a solver. Since k-rust 58720d2e5 (KINK-20/3) that simplifier also refutes the integer bounds that one-term comparisons with literals state, so two disjoint single-variable guards (`I >=Int 5` beside `I <Int 0`, `r0c/cfgf.k`'s `fpos` 0 -> 5) are refuted and the mutant is admitted (decisions log 2026-10-20, "admit mutants whose guards k-rust's KINK-20/3 refutes as disjoint"); guards that do not overlap but that k-rust neither refutes nor decides (a partial key whose definedness is a sibling conjunct, a guard beyond one term and a literal) still refuse a consistent mutant. The cost on testdata and the flow lists is in the R0c-fix-3 and R0c-fix-4 handoffs. The versions of claim removal, the consistency check, the compiled reading and the definition exclusions are components of kink's semantics identity (below), so a report or store an older build wrote at the same k-rust pin is refused by replay, by kink-corpus resume and by its summary, and missed by kink-flow's caches.
- A mutant that only weakens the specification is `unkillable` and runs nothing (kink27 R5-WEAKENING; kink-patch `ClaimSupport::weakening`; a kink-flow status, while kink-corpus and the campaign runner keep their statuses for it (kink's harness: [its tally](crates/kink-corpus/README.md#the-summarys-tally))). Its rewrite rules are the baseline's, and each edit deletes an equation of a `function` head or a `simplification` lemma, or replaces one by an instance of itself. An instance is the sentence under a substitution σ, found by matching the original against the replacement with the replacement's variables held fixed. The replacement's body and `ensures` are the original's under σ, its attributes are the original's, and every conjunct of the original's `requires` under σ is a conjunct of the replacement's (`andBool` or `andThenBool`, either side; a rule without `requires` is `requires true` and narrows to any; a label counts as a conjunction only when it denotes conjunction in every model: each of its productions is a `function` hooked `BOOL.and` or `BOOL.andThen` with no macro-like attribute, and no rule outside the builtin catalog is headed by it, since a macro rule or an equation can make a label so hooked mean anything, `rule A &&& _ => notBool A` making `c &&& true` mean `notBool c`). A variable's sort is the one the loaded sentence gives it, which is the sort compilation quantifies its axiom over: the sort written for it (`X:S`) or the one sort inference gave it, every occurrence carrying that sort; the test reads no position and no span, so two mutations that load to one sentence get one verdict. σ maps each variable to itself, or a variable of sort S to a term of sort S or a subsort of it built from tokens, variables and labels whose one production has no `function`, macro-like, `hook`, `binder` or cast attribute and no sort parameter, and which head no `anywhere` rule. Such a term denotes one element of its sort under every valuation, so the instance holds in every model of the original. Where σ moves a variable, neither sentence applies a macro-like label, a cast, `#withConfig`, `#let`, `#fun`, a binder or a label without a production, nor carries `concrete` or `symbolic`: compilation expands or resolves those by the shape of the terms below them, so the instance of the text need not be the instance of its axiom. No remaining equation of an edited head ranks after an edited one (`priority`, `owise`): deleting or narrowing an equation widens every equation of its head ranked after it. Then each axiom and claim of the mutant is one of the baseline's or entailed by one, so every model of the baseline is a model of the mutant, and a kill, which must hold whatever value the definition leaves open, would have to tell a model from itself. In the operational reading, each equational step of the mutant is a step of the baseline, so a function application only reduces less, and an application no equation reduces is an open value, never an end compared as data. A rewrite rule is left to execution even when it is only narrowed: a configuration no rule rewrites is an end, so a rule that applies to fewer configurations changes the ends of a run in every model, and that difference is a kill. `anywhere` and macro-like rules and `overload` families are left to execution: deleting the last `anywhere` rule of a symbol makes it a constructor, whose no-confusion the baseline need not satisfy. The test is syntactic and misses a guard rewritten into a narrower one (`W -Int 1` to `W -Int 2`), a wildcard met by anything but an equal term (a wildcard binds nothing, so `_:KItem` narrowed to `_:Nat` is not read as an instance), and a binding of a variable whose occurrences carry no sort or two sorts; such a mutant runs as any other and ends `unknown` or `survived`, never `killed`. A weakening also has models (the baseline's), so the consistency check's `inconsistent-mutant` refusal of one is no evidence that it has none; its action says so. The argument reads the baseline's normal forms as one of its models, which a baseline finding `[spec] assume_joined` leaves unnamed puts in doubt, so kink-flow decides `baseline-findings` first: on such a baseline a weakening with a program to run is `unknown` with that reason, as every mutation is. A replacement that keeps the original's body, `ensures` and attributes and adds to its `requires` only conjuncts that hold under every valuation of their variables is the original axiom itself, kind `valid-condition`: the only such conjunct the test reads is the sort predicate `isS` of a variable whose sort is S, the sort the loaded sentence gives it, written or inferred, which is the membership test of S applied to a variable that ranges over S, so the conjunction is the original's wherever the axiom is read; a production of the definition that declares the label fails closed, as does any other conjunct. A mutation every edit of which is of that kind has exactly the baseline's models, and kink-flow reports it `equivalent` with reason `valid-condition`, never `unkillable`: there is no input the edited equation stopped covering, so no replacement is to be written for it.
- The baseline must be shown confluent, or its findings named as premises (fz26 KINK-BASELINE-FINDINGS, finding KINK-BASELINE-TRUST). A kill compares ends as values of the definition, and k-rust's full check reads the definition by the model `M+` (its normal forms with a fresh constant in each sort that does not have an element in every model, agreeing with the normal-form model `M_NF` on every end kink compares), a model only when the critical pairs of the executable and witness equations join, under the premise A1+ (k-rust-backend `data_term`). The baseline's pairs were a trusted premise "which the backend checks", but nothing checked them, and a pair that does not join can make the compared ends equal in every model: with `q(_) => a` beside `q(_) => bb`, a mutant writing `bb` where the baseline writes `a` is equal to it, and kink-flow killed it (and six more DATAEND-review repros, `testdata/flow/findings`). An identification reaches other terms through congruence, so no reading of the compared terms rules it out. kink therefore computes each definition's full critical-pair check once per load, on the backend it runs (kink-native `data::DataFacts`, k-rust's `data_heads`), and counts a kill only when both sides' compared ends are data, each under its own side's definition (`data::data_ends`, the one function that says so: while a finding is left no end is data). A baseline with a finding the author has not named makes every mutation `unknown` with reason `baseline-findings`, before any mutant compiles and whatever a cache holds; `kink-flow check` fails, naming each finding with what to do about it; `results` lists the findings (`data`) and marks every comparable program `unable_to_kill`, and a query `no` is `unknown` (a hit stands: k-rust reached that configuration). The author may name a finding as a premise in kink-flow's `[spec] assume_joined`, by the name `results` prints, which is k-rust-fuzz's name byte for byte (k-rust-backend `data_term::names`, the one renderer); a decided finding cannot be named, and a name must name exactly one finding. Every verdict is then relative to that premise, which every document prints; a genuine finding named is a premise known to be false of the definition as written. The version of these facts is a component of kink's semantics identity (`data_facts`), so no store made before kink read them is honoured. On WASM (4 findings since k-rust FZ-EMPTYJOIN-WITNESS joined the `#t2aStmt` pair over the empty `EmptyStmt`, 2 of them genuine) and KEVM (15 before the checker work of P7-KEVM-S2A/B/C, 5 after it at fz26 int9, 4 of them genuine) every mutation is `unknown` until the findings are fixed upstream or named.
- Every compared end is data under both definitions (fz26 KINK-OVERLOAD-VALUE; P7-SIMPLE-KINK design, (c)). A compared end must be a value no model of the definition identifies with another: built from free constructors, normal-form injections, identity-safe domain values and trusted natural collections (TV-01), and, since this ticket, instance-normal applications of a data head (an irreducible `_,_Exps` or `_,_Vals` list, which every SIMPLE end holding an argument list or a declaration with an initializer has; since fz26 KRUST-ANYWHERE-HEAD also an `anywhere` head with plain `anywhere` equations declared total or `value-production`, such as SIMPLE's `_[_]`), admitted where k-rust's data judgement holds under the definition's own facts (k-rust-backend `BackendDefinition::is_data` with the definition's `data_heads`, called once at each outermost such application: the evaluator's own matcher, subsort order and overload axioms decide irreducibility, so kink has no second matcher, and the fuzz uses the same judgement). Each definition reads the ends with its own theory, and a mutant can change a symbol's role: an `anywhere` attribute on the baseline rule `c(1) => d` makes the baseline's end `c(1)` and the mutant's `d` one value of the mutant, and an added overload member lowers a baseline normal form (k-rust-backend `data_term`, "Two definitions"). So each side's terminals are judged under its own definition when its run is judged, and every compared end of a pair (state-slot terminals, reused baseline runs included, one-sided terminals and pattern bindings) under the other side's definition before the pair's slots are compared (kink-campaign `runner::judge_across`); an end that is not data there makes that side's slot `unknown` for that pair (a one-sided terminal is dropped), so r2-anyw written as that attribute edit is `unknown` where it was killed. kink-native `data::data_ends` is the one function that says which ends are data; the mutant's definition is the claim-free mutant, the one it runs. Two different compared ends then differ in each definition's initial model, under premises A1+ (evaluation by the executable and witness equations terminates over the signature with `M+`'s constants, which implies A1, the termination every evaluation assumes) and A2 (`simplification` lemmas and `[symbolic]` equations are theorems of the executable equations; the baseline's claims are trusted, and a mutant's that its edit unbacks are removed). `data_term`'s module documentation, its head selection and its walk are pinned by digest (kink-native `tests/data.rs`). Since KRUST-ANYWHERE-HEAD (`TERMINAL_VALUE_VERSION` v2), `a[i]` in SIMPLE leaves an application of `_[_]` that no `anywhere` rule of `_[_]` matches (its receiver is an `Id`, not a `Val`): an `anywhere` equation reads only the term it matches, so the application is a normal form in every context, and `value-production` makes it a value of its sort, so the array programs are comparable where k-rust's data judgement holds. The version of this walk is a component of kink's semantics identity (`terminal_value`).
- A `Bytes` domain value in an end is compared (kink27 R5-BYTES-ENDS). A value of a sort hooked `BYTES.Bytes` is a byte sequence. Its literal `b"…"` writes each byte as a printable ASCII character, an escape `\t \n \f \r \" \\`, or `\xhh` (`domains.md`, `BYTES-SYNTAX`), so `b"A"` and `b"\x41"` are one value, and two values are equal exactly when their sequences are. k-rust stores each value in one payload on every route (`docs/compatibility.md`, "Strings and their literals": one byte per code point at `SortBytes`, the UTF-8 of one code point per byte at a renamed sort). So equal payloads are one value and distinct payloads distinct ones, and TV-01 trusts this codec wherever the value occurs: in a cell, a Map key or value, a List or Set element (pinned by kink-native `the_passages_the_bytes_end_codec_rests_on_are_pinned`). A payload outside its sort's form, which no k-rust route stores, has no value. The same codec admits Bytes in step-event patterns, configuration existence and shared feasibility. Which sequence a hook computes is the hook's value: `String2Bytes`/`Bytes2String`, whose sequence k-rust's AM-1 states since GAP A1, stay on the census by kink's own choice until GK-1/GK-2, and a run with an allowance refusal stays excluded.
- An undefined step is no end (kink27 R1-UNDEF; finding KINK-UNDEFINED-END). k-rust's semantics states the reading (`docs/compatibility.md`, "Undefined steps in proofs"): the configuration on which a step is undefined exists and is reached, and the path to it is real; the step's outcome is undefinedness, which is no configuration, so that configuration is no end.
  kink takes no verdict from undefinedness itself: a kill comes only from ends and from reached configurations, never from the presence or absence of an undefined outcome. That is sound whether undefinedness is read as an outcome or as vacuity, since two complete sets of ends that differ are a difference of outcomes under the first reading and of behaviours under the second.
  So every state slot (`exit-stop`, `whole-term`, a term-path or a cell projection) projects the run's ends only. A side whose every path takes an undefined step has the empty set, which is a value: such a run's exploration is complete and has terminals, while a run with no terminal or an exploration that is not complete is never a value. A baseline end the mutant lacks distinguishes (a removed end), as in `krust fuzz`'s differential (`crates/k-rust-fuzz/README.md`, "Differential target"); an undefined path beside the same ends distinguishes nothing, whichever side has it; two sides that end undefined at different configurations agree. The single-crash rule and the free-variable rule read the ends only too.
  The pre-step configuration is not one of the ends judged as data under the other definition (kink-campaign `judge_across`, the witness filter's cross judgement), and a result record's final configurations do not list it (since result schema `kink-flow/result/v7`).
  A pattern oracle, a `query` hit and coverage observe the path to an undefined step, the configuration the step is taken from included, since those configurations are reached; they read no outcome of the step. A diagnostic (a refused baseline's leaves, a cause) may still show the pre-step configuration.
  kink-native's bridge completes such a leaf when its pre-step configuration is shown to exist (feasible, or ground without a path condition and a terminal value or k-rust's `ground_defined` on its own definition, behind kink's read-back guards; never for a term with a collection symbol where an axiom rooted at a collection role symbol makes kink distrust collections, finding C-10), not when its term is a terminal value: no comparison reads that term, but its path must be real (kink27 R3-UNDEF-BRIDGE).
  Two exclusions of a run with an undefined step are no verdict from undefinedness and stay: a step of a `preserves-definedness` rule falsifies a trusted claim, so the definition is inconsistent (below), and a step undefined only where a short-circuit operator would skip the undefined operand may have a defined successor under another reading (above). Both fail closed.
- A rule or equation condition that equates two terms (K `{ A #Equals B }`) is a gap of k-rust's own answers when the terms may be undefined: its SMT translation has no model where both sides are undefined, so answers over the definition may wrongly be empty, `valid` or `proven` (k-rust `docs/compatibility.md`, "Two gaps remain"). A definition (baseline or mutant) with such a condition is never compared (`equals-condition`, kink-native `exclusion`). Conditions are every antecedent of an axiom, whatever its left-hand side (an application, `#Ceil` or another predicate), a rewrite rule's `requires`, and every `ensures` (re-pin R0c-fix-4), a rewrite rule's under the `\exists` kompile wraps around a right-hand side with an existential variable `?Y` included (re-pin R0-tail: every `\equals` of a rewrite rule's right-hand side is read); no testdata or example definition has one.
- A kill on an inconsistent definition says nothing (re-pin decision 2). A mutant no longer carries a claim its edit can falsify (above), so the remaining claims are the baseline's, a trusted premise, and those of a mutant's unedited part. A run whose undefined step falsifies one (k-rust names a contradicted `total`, or the step's rule carries `preserves-definedness`) is no evidence (`contradicted-claim`) for its own test. Since re-pin adoption A-1 so is a run on whose `contradictedClaims` list k-rust holds any record, ground or not, observed by the run or by the load of its definition (`docs/compatibility.md` 1653-1661 at 0068938b1): the list holds what no leaf carries, a candidate a defined sibling covered, a state-set arrival a merge absorbed and a condition decided through the contradiction, and a comparison of complete sets needs every path of each side to be a path in every model of a consistent repair of the definition. A load record (`observedIn: load`) is on every run's list, so it takes every test of its definition out of the score (decision D-6). The records are reported as specification diagnostics (kink-flow: `specification_diagnostics` in a program's row and in a mutant's executed entry), so the author learns which claim is false where. The rule is per test (Sebastien, 2026-10-17): a kill counts when the killing test's baseline and mutant runs are both complete and free of every exclusion, a contradiction included, whatever another test shows. When a claim is false only at inputs the killing test never touches, weakening the claim there gives a definition that has models, and the killing test behaves the same in all of them. A test compares its slots only when both runs gave sides, and an excluded, timed-out, stack-stopped or unbridged run gives none, so a contradicted leaf in the killing test's own runs never yields a kill. On the baseline a run whose own leaf contradicts a claim makes only its test unknown for every mutant (the campaign is not refused; in kink-flow the program is not comparable); a baseline run excluded only by a record on the list is refused, as any other excluded baseline is, because before A-1 such a run was either compared or, when its leaf carried the record, unknown and refused, and keeping it per test would relax that refusal without a decision. `FirstKill` and `Full` agree. The finding A-13 residual (a false baseline claim used in a condition, or beside a defined same-priority sibling, shows in no leaf) is closed for ground tests by reading the list. A symbolic run's empty list says nothing (k-rust trusts the claims on a symbolic state, compatibility.md 1669), so kink-campaign's symbolic tests still rest on the premise that the baseline's claims are true.
- A run whose result can depend on the host is no evidence: one that counted a stop for lack of native stack (`stack-stop`), one on a definition whose load counted one (`load-stack-stop`), one with a Bytes hook refused for the process's memory allowance (`allowance-refusal`), on a leaf or, since re-pin adoption A-1, on k-rust's `allowanceRefusals` list of the run or its load, which also holds a refusal inside an undone attempt or a passed-over equation that steered the result and left no diagnostic (`docs/compatibility.md` 92). A result whose list is empty is the result under every allowance of at least as many bytes (compatibility.md 859), so the outcome records carry no allowance key.
- A run on whose `unsupportedHooks` list k-rust holds an application left unevaluated as an unsupported hook, in the run or its load, whatever became of the work that met it, is no evidence (`unsupported-hook`, re-pin adoption A-1): such an application can steer a passed-over equation without a leaf showing it.
- A program `kink-flow fuzz` found adds nothing to trust (fz26 P7-KINKFLOW): it decides no status, and `run` proves its kill like any other program's. The fuzz is a search for such a program under stricter rules than `run`'s, so that its candidates are ones `run` can confirm: its data judgement is strict (a finding no name assumes makes the campaign `not-comparable`, and an assumed finding is only ever the author's named premise, printed beside the fragment), and it refuses a job on which `run` would compare another input than the one the campaign judged.
- A mutant is held to compilation, not to K's rule parser (decisions log 2026-10-18, STRUCT-SORT parked). kink-flow takes only text edits: k-rust's K parser parses each edited rule text before the mutant is built (`kink-flow` `mutation`), so every mutant kink-flow scores is one some K text yields. A structural edit, an edit of kink's term tree rather than of text, is held only to compilation: kink-patch's operators (`OperatorSpec` with `Action::ReplaceHead` or `Action::Wrap`, and the other operators of `catalogue_v1`), the kink-corpus manifest's `operators` form and catalogue sweeps that apply them, and any `Patch` a library caller builds from terms. k-rust's compile checks the mutant's sorts and declarations, not that some K text parses to the edited rule, so a structural edit can build a mutant no K text yields. At main such an edit fails closed when it is ill-sorted (a compile refusal, or an infrastructure `error`), and none has been found `Killed`; the decisions log reopens the question if one is, or if structural edits become an input of the flow. A catalogue proposal for the flow is rendered as K text and parsed like any other edit.

## Stack dependence

Stack dependence (k-rust KINK-06/4 and KINK-06/5): k-rust can dismiss a stop for lack of stack silently, in the load's discharge of rewrite-rule definedness and its critical-pair check and in a run's refinement of a result, so a result could depend on the stack of the thread that loads the definition or runs the program, and on other threads.
For every comparison through k-rust's `execute`, the re-pin closes this: a run that reports a nonzero `stackStops`, or whose definition's load reports a nonzero `discharge_counts().stack_stops` or `value_claims().counts().condition_stack_stops` (read through `select_definition` on the backend that runs), is no evidence, on the baseline and on the mutant, live, on a reused baseline run and before any outcome is cached. A reused baseline run is judged under the load facts of the call that produced it together with the current call's (each call loads the definition again), and a run whose own load was excluded is never kept for reuse, only its exclusion.
What remains: under the Z3 profile a solver query can be left undecided within its resource units, never by the clock; k-rust counts the undecided answers of a run (`smtUnknowns`, KINK-19/1) and kink those of its own queries about the run (leaf feasibility, the observation decider: `decider_smt_unknowns`), which kink carries and reports (kink-flow's program rows and executed entries) but never reads as an exclusion (decision D-7 (a1): kink re-decides every leaf's feasibility itself, so an undecided answer can make a comparison unknown, never a kill); the outcome cache (tier 1) is on in a Z3 build, since such an answer is a function of the query, the units and the Z3 build, which its key names; and kink's verdict path also calls k-rust outside `execute` (`definition_facts`, the unification of `BackendRelations`, the bridge's internalization of leaf states), whose determinism no k-rust promise states (re-pin finding B-13(a)). For kink-flow's ground programs these decide nothing a kill depends on.

A pattern query's `no` reads the undecided answers of its own search (KINK-query-no-z3; the k-rust sites below are cited at `b7b2fe528`).
The search is one facade operation, and the facade gives every operation's work its solver through a counter of undecided answers (`crates/k-rust/src/backend/mod.rs:3415`, `run_with_solver`; module docs 106-111).
The counter forwards `is_sat`, `check_predicates` and `get_model`, the three queries of k-rust's solver interface (`crates/k-rust-backend/src/smt.rs:3701`, `3862`), and counts an `Unknown` answer of each once, where it reaches the work that asked, after the solver's retries, in the innermost operation record open on the thread (`smt.rs:3803`, `3825`; `stop.rs:981`); kink-flow opens one around the search (`stop::with_operation_record`, `stop.rs:1006`, its `unknown_answers`), on the thread the search runs on (a deeper stack is a segment of the same thread).
Every way a query goes undecided reaches the consumer as such an answer: Z3's `unknown`, its resource units spent or its incompleteness met, is retried and then returned as `Unknown` (`smt/z3.rs:827-858`).
The solver's caches hold decided answers only (`smt/z3.rs:516-517`, and the typed cache's invariant, `smt/z3.rs:8`), so a cached answer is never undecided.
k-rust's memos of equation-condition verdicts and of evaluations live only while their outermost scope is open and are cleared when it closes (`simplify.rs:2712-2720`, `10313-10322`); every such scope opens inside the search's operation, so a verdict served that rested on an undecided answer was counted when the same search first decided it.
What is not counted is no undecided answer: a decided answer (`Sat`, `Unsat`, a validity verdict, a model) and a failure (a query that does not translate, a script Z3 rejects, an internal error of Z3, `smt/z3.rs:257`, `756`) are functions of the query and the Z3 build (each query runs on a context of its own, `smt/z3.rs:336`); a model `Unknown` that reports an approximate translation is a fact about the query (`smt.rs:3780`); a stop (a cancellation, a failed prelude) ends the search, which kink reads as the clock or an `error`, or ends one state as an incomplete entry, so no completed exploration has met one.
Every query kind of a search goes through that solver: a rule's condition and remainder, an equation's side condition, a definedness obligation, a state's feasibility and the match of the pattern against each state (`crates/k-rust-backend/src/search.rs:2810`, `2861`); the backend builds no Z3 solver of its own outside its tests, and the load's checks, which run before the search and detached from it (`stop.rs:740`), simplify with no solver (`confluence.rs:1915`, `definedness.rs:1107`).
Work isolated from a run, whose answers no record counts (`coverage.rs:463`, `472`; `stop.rs:920`), is a condition record or `execute`'s state matcher, neither of which a search request asks for.
So a completed search whose count is zero took every decision from decided answers and from failures.
A decided answer is true of the definition's translation, whose `smt-hook` and `smt-lemma` claims are trusted as every claim of the baseline is (above); an `Unsat` means no K valuation on every definition kink answers a query on, since a condition equating two terms makes every answer unknown (above).
A failure carries no information about the query's answer, and the `no` needs every consumer to read it so: a failure must never refute a condition, a match or a state, which only a decided `Unsat` or refutation may do.
The failures differ by profile: without Z3 every query that needs a solver fails with `Unavailable` (`smt.rs:3722`, `3761`, `3773`), while under Z3 a query can also fail with `Translation`, `SolverFault` or `MalformedScript` (`smt.rs:3626-3649`), which no portable run exercises.
Every consumer of a solver answer in a search reads each failure as no refutation (k-rust-backend at `b7b2fe528`): a rule's condition refutes only on `Refuted`, and every failure leaves the attempt indeterminate (`rewrite/apply.rs:1715`, `1760-1767`); a rule's match remainder and its narrowed constraints refute only on `Refuted` or `Unsat` (`rewrite/apply.rs:1123-1126`, `1287-1297`, `1544-1558`); a right-hand side's definedness obligation is carried and its `ensures` indeterminate on a failure (`rewrite/apply.rs:2120-2129`, `2139-2158`); a state is pruned or found undefined only on `Unsat` (`rewrite/mod.rs:456-461`, `1274-1291`); the match against the pattern fails only on `Unsat` or a refutation, and a failure leaves it undecided (`search.rs:3408-3414`, `3504-3511`); an equation's side condition is refuted only on `Refuted` (`simplify.rs:3441`, `3339`), while `Unavailable` and `Translation` leave it indeterminate and every other failure is returned as a simplification failure, never as a refutation (`simplify.rs:3452-3458`, `3370-3375`, `1009-1015`), which in an equation's condition leaves the condition unsimplified with a diagnostic (`simplify.rs:2152-2156`).
With failures so read, the portable `no` rests on k-rust's search being sound for "no reachable configuration matches" when no solver query refutes anything; the Z3 `no` with the count zero rests on the same, together with Z3's decided answers.
A k-rust change that read some failure as a refutation would break this `no` and not the portable one, so the sites above are part of what this argument reads.
A search that counted an undecided answer gives `unknown` with its count: its `no` would also rest on every consumer of an undecided answer reading it as no information about what is reachable, which no portable run exercises, since that profile's solver never answers `Unknown`.
The count is the search's own and not the baseline run's: the baseline is a separate operation whose answers decide nothing in the search.
`tests/query.rs` (`a_no_needs_a_search_without_undecided_solver_answers`) pins both sides under Z3: a definition whose equation conditions only the solver decides answers `no` with the count zero, and the same search with one resource unit for each query's first attempt completes with undecided answers and stays `unknown`.

## Threads

Threads (re-pin L1-3, L1-3-fix-1): only relinking and compiling run on several threads. kink-flow (`run --compile-workers N`, 4 by default) and kink-campaign (`CampaignOptions::compile_workers`: kink-corpus passes 1, and kink-flow passes 1 to each of its one-mutant calls because it compiles across mutations itself) compile a chunk of mutants ahead (kink-native `NativeValidator::compile_ahead`: each patch is applied on the calling thread, in order, and a worker thread only relinks and compiles the applied mutant), join every worker, then run the chunk one mutant at a time in list (candidate) order on the calling thread, exactly as with one worker. Relinking and compiling are the only steps k-rust documents as independent of the thread: they read only their arguments and no process-wide input, several threads may run them at once on one shared loaded definition with each call returning what it returns alone, and every compile stage runs on a stack sized from the definition (k-rust `docs/compatibility.md`, "Concurrency"; `crates/k-rust/tests/compile_concurrency.rs`). Applying a patch is not among them: it types each edited rule with k-rust's `SentenceTyper::typing_in`, whose recursion has no stack guard, so on a worker's default stack a rule about 1,500 terms deep aborted the process where the calling thread's 256 MiB stack succeeds (review L1-3-1 D1; kink-native `a_deep_edited_rule_compiles_ahead_as_on_the_calling_thread`); since re-pin L1-3-fix-2 that typing runs on a stack sized from the rule's depth, but apply stays on the calling thread, in order. A compile refusal can depend on the calling thread's stack, so only a successful compile is taken from a worker and every refusal comes from the calling thread. Everything after compile that runs the simplifier stays sequential, outside every compile, and outside the watchdog where it is a load: the consistency check, every backend build (its load's critical-pair check and definedness discharge) and every execution, whose stack stops depend on the running thread's stack and on what other threads hold of the simplifier's process-wide stack budget ("Execute"; a stop refuses a mutant or excludes a run, so it would make a status or the score depend on the schedule). The worker count changes no status, row, report, record or lock (kink-campaign `tests/compile_workers.rs`, kink-flow `tests/compile_workers.rs`), only wall time and memory: on `examples/imp`, cold, mutant compiles are 28 % of the run, and 4 workers took 2.5 s off a 16 s run on average (8 paired runs on a shared host) while peak memory rose from 126 MiB to about 305 MiB; a warm run compiles nothing. The workers are capped at the host's parallelism and at half the process's memory allowance, which counts what a worker's share of a chunk holds at once: one compile in flight (an estimated 64 MiB plus 32 bytes per byte of the baseline's `definition.kore`) and the at most 8 mutants compiled ahead that it keeps (8 MiB plus 8 bytes per byte each, two to three times the 4.4-5.7 MiB measured on the small fixtures); `compile_ahead` keeps no more than 8 per worker, so the bound holds whatever a caller asks (`NativeValidator::compile_workers`, `KEPT_PER_WORKER`). The estimates are calibrated on small definitions and on k-rust's KEVM compile figure; no large definition was measured.

## Deep terms

Deep terms (re-pin L1-3-fix-1, L1-3-fix-2, L1-3-tail): K bounds no term's depth, and a recursion that descends one level per term level overflows the thread it runs on, which aborts the process and loses every row of the run. k-rust guards or sizes its own recursions (loading, compiling, executing). kink's own are k-rust's typing of a rule (of an edited rule in `apply`, of every baseline rule when kink-patch resolves a universe or a sort-selected discovery), which has no guard, and serde_json's parse and serialization of kink's JSON, which nests two levels per term level; kink-patch measures each input's depth without recursion and runs that work on a stack sized from it (kink-patch `stack`; on the calling thread when enough of it remains), so the outcome is a function of the input and not of the thread (kink-patch `a_deep_rule_is_typed_alike_on_a_thread_too_small_for_its_typing`, `a_deep_patch_encodes_and_decodes_alike_on_a_thread_too_small_for_it`, kink-flow `deep_rules_are_judged_alike_on_a_thread_too_small_for_them`). Every reader of kink's JSON goes through kink-patch `parse_json`, and no JSON document kink reads or writes may nest deeper than `MAX_JSON_DEPTH`: 600,000 levels in a release build and 128,000 in the unoptimized test build, set so that dropping a document at the limit, the one recursion serde_json runs on the caller's stack, takes under half of the 256 MiB that kink's commands run on (`DEFINITION_STACK_BYTES`; a library caller handling documents that deep needs such a stack too). Past the limit a reader refuses the document with an error that names the limit, and each writer refuses to write it (kink-patch codec `CodecError::TooDeep`, which kink-flow reports as `edited-rule-too-deep`; kink-campaign's report; kink-corpus `Store::write_json`; a KORE test input as `inputs`/`too-deep`), so every reader accepts what its writer writes. The stack each step takes is sized from its own input's depth (a patch's from its document's exact depth, `Patch::document_depth`), so a shallow input never needs a large segment; when the host refuses a segment (an address-space limit such as `ulimit -v`), the refusal names the host and never the input: kink-flow reports the mutation as `error`/`host-stack-refused`, kink-corpus a KORE test input as `inputs`/`host-stack-refused`, and a rule's typing becomes a `not typed` diagnostic. The typing bound per level (kink-patch `TYPING_STACK_PER_LEVEL`) is set with a stated margin over the costliest of the term shapes measured, parametric productions included.

A leaf is as deep as the run that made it: a list a step appends to comes back from k-rust one level deeper per step, as a right-nested chain of concatenations.
kink holds a leaf as the `kore::Pattern` k-rust's facade hands it in (`Backend::execute_kore`), whose clone, comparison, printing and drop keep their work on the heap, so the leaf's encoding bounds no depth.
kink-native's walks of a leaf keep their work on the heap too (the terminal value and the reason a term has none, `ObservationDecider::terminal_value` and `first_non_value`, definition independence, and the adapter's constructor-term check; kink-native `deep_walks_keep_their_work_off_the_stack`, chains 200,000 levels deep on an 8 MiB thread),
and every admission of a leaf, or of a subterm of it, to k-rust runs, with everything it does over the internal terms it builds, on the stack k-rust sizes for an operation over that term with its builtin collections associated (`BackendDefinition::with_stack_for_associated`), and reads that associated form: the adapter's leaf feasibility and the step-tracked bridge's, `configuration_exists`, a pattern slot's relation and feasibility decisions over event payloads, bound values and the path predicate (`BackendRelations`), and, with `judging_data`, k-rust's data judgement of an overload application.
Association writes each spine of a builtin collection's concatenation as the associative application KORE defines as that spine, so it denotes the same term, and k-rust internalizes both forms to the same internal term; a collection's length then adds no level to the admission.
kink-native `tests/deep_leaf.rs` judges a leaf with a million-entry list on the definition thread's stack (in a release build, one entry more than its largest stack holds levels): as k-rust hands it the leaf is deeper than the largest stack k-rust provides, which the test asserts, and admitted it is as deep as with a three-entry list.
A term whose associated form is deeper than the largest stack k-rust provides (about a million levels in a release build, 700,000 in the test build) is refused there before any of that work, and the judgement is its one-sided answer, a function of the term: `unknown` feasibility, not shown to exist, not data.
Such a term is deep by its structure, not by a collection's length: a K sequence or another constructor chain as long as the run, or collections nested in each other one level per step.
When the host refuses to map the stack (an address-space limit such as `ulimit -v`), the refusal names the host and never the term: the adapter fails the run with a `Backend` failure, as when k-rust refuses the run's own stack, and the decider records it (`ObservationDecider::host_refusal_during`, which covers its `BackendRelations` too), which the step-tracked bridge reports as `BridgeFailure::HostStackRefused`.
The campaign runner fails the run as infrastructure wherever such a refusal happens: in judging the run into sides, in judging its pattern slots, and in judging a pair's ends and bindings under the other side's definition, where it fails the pair's mutant run; kink-flow's outcome cache stores no failed run.
kink-flow's diagnostics read a refusal the same way: the hint of a refused baseline names the host, and the fuzz filter accepts the candidate, as it does when it cannot reach a side.
A leaf written into kink's JSON is bounded by memory only: a run's sides, in a campaign report and in kink-flow's baseline row and result record, hold each pattern (an end of a whole-term value, a term at a path, a pattern binding, a semantic crash's pattern) as its compact KORE text, one JSON string (kink-campaign `CampaignReport::baseline_row`, report version 6), which k-rust's printer writes and its KORE parser reads back to the same pattern, both with their work on the heap.
A side's JSON depth is fixed by the report's shape whatever its terms hold, so neither the `MAX_JSON_DEPTH` refusal nor serde_json's drop of a document, one stack frame per level, is reached by a long collection or any other deep end (kink-campaign `a_deep_end_is_written_as_kore_text_and_read_back`, kink-flow `a_record_for_a_deep_leaf_is_written_and_read_back`: a list of `MAX_JSON_DEPTH` entries, whose KORE JSON would nest twice that).
kink-flow's result record holds each end once, in its baseline row (an unknown record's diagnostic leaves in `final_configuration`), and is written member by member, never built as one JSON value (`results::write_record`).
What kink's JSON still nests with its terms is what holds them as KORE or KAST JSON, two levels per application: kink-corpus's KORE test inputs and the campaign manifest's initial states and observation patterns (an input past the limit is refused as `inputs`/`too-deep`), the KAST JSON of an edited rule's term or sentence in a patch and in a report's `diff` and origins, as deep as the rule, and kink-native's step-3 report (`report::step3_report`, read only by kink-native's own tests), which writes a leaf's state, path predicates and bindings as KORE JSON.
In the campaign report and kink-flow's documents and records, the bound that remains on a run's ends is k-rust's admission, above: an end whose associated form is deeper than the largest stack k-rust provides is deep by its structure (a long K sequence or another constructor chain as long as the run) and is judged by its one-sided answer, `unknown`; writing it is bounded by memory only.

## What a stored verdict is bound to

What a stored verdict is bound to (packets CACHE-ID and CACHE-ID-fix-1; kink-campaign `identity`): a stored verdict is honoured without re-deriving it only if the code that derived it is the code now running, and two identities say so.
kink's build identity, `kink_build`, is the SHA-256 of the running executable (decision D14-1 (a), first used by kink-flow's tier 1).
It guards all of kink's verdict code, including the code that has no version constant at all (the comparison and its Distinguish, the status fold, pattern-oracle matching, leaf adaptation, step events, feasibility, the census), and the linked k-rust; nothing has to be bumped for it to change.
kink's semantics identity, `kink`, is one object, `{k_rust_revision, fingerprint, canonical_patch, compiled_kore, patch_admission, claim_removal, mutant_consistency, mutant_effect, weakening, data_facts, terminal_value, definition_exclusion, execution_request, result_schema, coverage, one_sided, stop}`: it names the k-rust revision and kink's versioned algorithms (how a patch is addressed and admitted, no typing error refusing one since L2-2-fix-1; which claims a mutant loses; the consistency check; the compiled reading of an edit; whether an edit only weakens the specification, kink27 R5-WEAKENING; what kink refuses on each definition's full critical-pair check, kink-native `DATA_FACTS_VERSION`; which ends a slot compares, kink-native `TERMINAL_VALUE_VERSION`; the definition exclusions; the execution request, with state sets whatever their leaves (KINK-PATHSET-FALLBACK, v2), no trace, run coverage, a cancellation as an error and the mutants' work budget, L1-1; what counts as a comparable flow result; how coverage is read; when a work-bound mutant run kills one-sidedly, L1-2 and L1-2-fix-1, over the cell projection too since v3, at a stopped run's stop leaves since v4, and over cells inside `?` and `*` cells since v5, kink-campaign `ONE_SIDED_VERSION`; how a run with a stop is made of requests, one to k-rust's count since v2, and how each side resolves the stop's rules, kink-campaign `STOP_VERSION`).
It is the human-readable part: a refusal names the first component that differs, and campaign manifests carry it, so campaign reports stay independent of the build.
Every store honoured without re-deriving its verdicts carries both and is refused or missed when either differs: each kink-corpus index entry and admission record names its writer's `kink_build` (outside the campaign report's bytes) and each campaign manifest names `kink`, so resume and summary refuse an entry of another build or identity, naming the build and the component, and summary reads an admission record of another build as missing; kink-flow's result key and tier-1 context hold both, so their records miss and are recomputed; kink-flow's warm-path memos (re-pin L1-4: a mutation's resolution facts and the specification's declaration census) key every record on both and on every input of the memoised value, so a record of another build, identity, specification or mutation text misses, and `run --verify` re-derives and compares every one; and `kink-flow report` refuses a run document of another build or identity.
Replay re-derives instead (it regenerates the manifest, re-runs the campaign and reproduces only byte-identical reports), so it needs no build binding; it still refuses another semantics identity in its environment check (`kink.<key>`) before regenerating anything.
kink-flow's killer record (`verdicts.lock`) carries neither: a recorded killer decides no status, and a run re-checks it by a run or a record that carries both.
An unreadable executable gives no build identity, and every honouring store then recomputes or refuses.
The rule for adding to the semantics identity: a constant whose change can change a verdict is a component (bump it whenever its algorithm changes what it decides); every other versioned constant (a `const` or `static` whose name ends in `_VERSION` or `_DOMAIN`, whose string value ends in `/v<N>`, `/v<N>.<M>` or `-v<N>`, or that names such a constant) is listed outside it with the path that checks it.
kink-campaign `tests/identity.rs` parses every kink member's sources and fails on a versioned constant in neither list.
A forgotten bump, or verdict code with no version, no longer lets a store be reused: the build identity changes with any edit that changes the executable.

## kink's harness: corpus resume and replay-check

kink's corpus harness (kink-corpus's binary; [`crates/kink-corpus/README.md`](crates/kink-corpus/README.md), "Not a user tool") keeps a store of campaign reports, which users' corpora do not have; what it trusts is this:
Corpus resume: `kink-corpus run` resumes a definition whose completed campaign report is already in the store only when the index entry was written by this build (`kink_build`) with kink-corpus's run options (`run_options`, packet CACHE-ID-fix-1; every option is recorded, the one-sided rule's `one_sided` included, kink-campaign `RunOptions::value`, re-pin L1-2-land), and the report is checked against the manifest digest, the profile, the report and artifact digests, the report version and kink's semantics identity.
The store's bytes stay a function of its inputs except the writer's `kink_build` in each index entry and admission record, so the binary's and the library's stores differ only there (kink-corpus `tests/runner.rs`).
Any rebuild of kink therefore refuses every store an earlier build wrote: delete the store to rerun it with the new build.
`kink-corpus replay-check` re-derives a stored report instead, so it can check a store from another build.
