# k2lean: design

k2lean turns a K definition, as krust compiles it to KORE, into a Lean 4 library that models the definition and proves facts about the model.
This note says what the generator writes, why the encoding is sound, how the generated proofs are checked, and where the limits are.
How to state and prove invariants of a generated semantics is in [`invariants.md`](invariants.md).

## 1. Input and output

The input is krust's compiled definition: `definition.kore` and `runtime.json` from `krust kcompile` (the KORE theory of the definition, and its configuration variables).
The output of `k2lean gen --kore definition.kore --runtime runtime.json --out DIR --name NS` is a Lake project in `DIR` that requires the prelude `KPrelude` (`lean/prelude`) by relative path (`--prelude`, relative to `DIR`):

| module | content |
|---|---|
| `NS/Terms.lean` | one Lean type per sort (with `--arity-terms`, one family indexed by the sorts, §2.1), constructors, injections and projections, decidable equality and an order on terms |
| `NS/Functions.lean` | each function defined by KORE equations, as a Lean definition; hooked functions are the prelude's, and the library's parameters (§2) are the fields of `class Hooks` |
| `NS/Equations.lean` | each K equation and simplification rule as a theorem about the generated definitions, or, when its generated proof fails, a named open obligation (`def Eqn.….statement : Prop`) |
| `NS/Rules.lean` | `App c` (some rule applies at `c`), `Step c c'` (one constructor per rewrite rule) and the executable `step` |
| `NS/Adequacy.lean` | `step` against `Step` and `App`: sound by construction, complete rule by rule |
| `NS/Determinism.lean` | `Step` is deterministic, by cases on pairs of rules, or along the rule index modulo the definition's overlapping pairs (`--det2`, §3.1); for a definition whose rules match a map at several keys, why it is not claimed, and the check `uniqueAt c` instead |
| `NS/Init.lean` | `init`, the initial configuration of the configuration declaration, with one parameter per configuration variable |
| `NS/Preserves.lean` | `Step.Case.r P` per rule and `Step.preserves_of`, the per-rule preservation principle |
| `NS/InvariantDefs.lean`, `NS/Invariants.lean` | with `--invariant NAME[@CELL]` or `--sidecar FILE`: the invariant and its `Preserved` theorem (`invariants.md`, §3) |
| `NSTest/Axioms.lean` | the axiom guard: `#k2l_assert_axioms` over every proved theorem |
| `NSTest/Main.lean`, `NSBench/Main.lean` | the test and benchmark drivers (`lake test`; `goldens`, `cases` and `configs` fill their data) |

Every generated file starts with "Generated by k2lean … do not edit".
A library is regenerated from the KORE whenever the definition changes; what a person writes lives elsewhere: the open lists (`open-obligations.txt`, `open-invariant-cases.txt`) and the hand module `NS/InvariantsHand.lean`, which `gen` writes once and never overwrites, and kind 2 projects of their own.

## 2. The encoding

The generated Lean is a model of the KORE theory: every symbol gets an interpretation, and the generated theorems show that the interpretation satisfies the theory's axioms that the generator states.

- **Sorts.** Each sort is a carrier, and its constructors are free: KORE's `constructor` symbols carry the no-confusion axioms, and each sort's "no junk" axiom lists exactly its constructors and the injections of its subsorts.
- **Injections.** Injections compose (`inj{B,C}(inj{A,B}(x)) = inj{A,C}(x)`), so a value of sort `S` is determined by its leaf, the most specific sort that built it.
  A sort with several leaves is a sum over them (`S.inj_L`), so every K value has exactly one Lean representation; `proj_S_L` is the partial inverse of an injection, defined exactly on the injected values.
- **Builtin sorts and hooks.** `Int`, `Bool`, `String`, `Map`, `Set`, `List` and the IO sorts are the prelude's types, and a hooked function is the prelude definition chosen by its `hook{}` attribute only, never by the symbol's K name (`crates/k2lean/src/hooks.rs`).
  Each hook has the meaning `domains.md` gives it; where `domains.md` leaves a value unspecified (`/Int` at divisor 0, `substrString` out of range), the model makes a documented choice or leaves the result undefined.
- **Parameters.** A hooked function the hook library does not implement (`KRYPTO.keccak256`, `BYTES.bytes2hex`), and a function symbol with neither equations nor a hook, is unconstrained by the definition: it is a field of the generated `class Hooks` (`Functions.lean`), `Option`-valued, and every later module has `variable [Hooks]`.
  Every theorem then holds for every implementation of the hooks, with no axiom; a test driver needs an instance.
- **Partiality.** A partial function is `Option`-valued, `⊥` is `none`, and matching logic's `\equals` holds between two `⊥`s, so an equation over partial terms is an equation of `Option`s.
- **Functions.** A function's equations are tried in priority order, `owise` last; the first equation whose argument patterns match and whose `requires` is `true` gives the value, even when that value is `⊥`.
  An `owise` equation's guard is the negation of its competitors' applicability, which the cascade position realizes.
  Where no equation applies the result is `none`: the least-defined model, since KORE leaves the value unconstrained there.
- **Free-key map patterns in function equations.** An equation `f(K |-> V REST) => e requires c` whose key `K` is bound nowhere else in its left-hand side is, as a KORE axiom, `∀ K V REST. M = (K |-> V) REST ∧ c → f(M) = e`: one instance per binding of `M` at which the rest of the left-hand side matches and `c` holds (a *matching binding*).
  - When every matching binding gives the same value (`⊥` included), that value is the K function's meaning at `M`.
  - When two matching bindings give different values, the axioms equate `f(M)` with both; a function denotes one value (or `⊥`), so no model of the definition contains `M` with that equation, and the K definition determines no value at `M` (the definition is not confluent there; krust's `UnjoinedCriticalPair` warning flags equations where this can happen).
  - The generated definition takes the first matching binding in the map's canonical order (ascending keys): `MapHook.chooseFirst`, which tries each binding and passes to the next exactly when the rest of the left-hand side or the requires fails there, and otherwise gives that binding's value, even `⊥`.
    So it is the K function's meaning wherever the definition determines one (`MapHook.chooseFirst_eq_of_agree`: if some binding gives `b` and every value at any binding is `b`, the result is `b`), and a choice among the instances where it does not; `chooseFirst_eq_some` and `chooseFirst_eq_none` characterize it.
  - The equation applies at `M` exactly when some binding matches; an `owise` equation or one of a lower priority is tried only when none does, as the KORE guard of the cascade says.
  - Several free keys in one left-hand side choose lexicographically; a function that recurses on the rest or on the value of the binding terminates by `MapSizeOf` (the value and the rest are smaller than the map, from the certificate the continuation receives).
  - Such an equation is not stated in `Equations.lean`, as no equation with a map pattern in its arguments is (their arguments are partial patterns, not terms); its K statement, the agreement of all matching bindings, holds exactly where the definition is confluent.
  Well-founded recursive functions are Lean definitions by well-founded recursion, and their equations get a proof by the recursion's own unfolding (`k2l_eqn_r`).
  The measure is the length of a list the function destructures, an integer distance bounded by a requires, or one the generator synthesizes from the equations (`termination.rs`: integer distances from the requires, from failed earlier guards and from defined partial hooks, constructor ranks for fallback chains, combined lexicographically); the proof is Lean's (`k2l_decreasing`), so a wrong choice is a build error, never an unsound definition.
  `gen --termination FILE` (TOML, keyed by K label) supplies a measure and its proof where no generic rule does, or makes a function whose rewriting diverges on some arguments the least fixed point of its equations (`partial_fixpoint`): `none` exactly where the rewriting diverges, the equations' value everywhere else.
- **Rules.** `Step` has one constructor per rewrite axiom of the compiled definition, heating and cooling included, at the top configuration.
  A rule whose left-hand side matches and whose `requires` is `true` but whose right-hand side is `⊥` applies (`App`) and has no `Step`: matching logic gives that configuration no successor.
  With priorities, `Step` is stratified: a rule of a lower rank steps only where no rule of a higher rank applies (`¬ App j lhs`).
  A map pattern whose key is bound nowhere else (`K |-> V REST`, the cell maps of SIMPLE's threads) matches once per binding, so `step` returns the first match whose result is defined and `successors` all of them.
- **Overloads.** A left-hand side that mentions an overloaded symbol matches its variants modulo the `symbol-overload` axioms (`crates/k2lean/src/overload.rs`).

### 2.1 The arity-indexed universe (`--arity-terms`)

The default universe is one Lean type per sort, all in one `mutual` block, a sort with subsorts having one constructor per leaf injection.
Two limits of Lean make it unusable at KEVM's size (measured 2026-10-23, Lean v4.24.0 and v4.30.0, shared 32-CPU host):

- the auxiliary constructions of a mutual block (recursors, `below`, `brecOn`, `sizeOf`) grow with types × (types + constructors): SIMPLE's block (86 types, 362 constructors) took 284 s, and KEVM's (392 types, 1,160 constructors) had not finished after 90 minutes at 17.9 GB;
- Lean's runtime cannot compile a constructor with fields at index 244 or above, and KEVM's `KItem` has 277 injections (KMIR's 309).

A single indexed family with one constructor per K constructor elaborates, but every `match` at a fixed sort then refutes every other constructor of the family (2.4 s per two-arm match on KEVM's 1,160) and it is not executable either.

`gen --arity-terms` (`crates/k2lean/src/terms_arity.rs`) writes one family `Term : Tag → Type` indexed by the sorts, with one constructor per arity of the sorts' own constructors (`c2 (c : C2 s) (a0 : Term (A2_0 s c)) (a1 : Term (A2_1 s c))`, `Ck s` enumerating sort `s`'s constructors of arity k), one per builtin carrier, one per collection sort (a nested list), and the leaf injection `inj (hs : hasLeaves s = true) (l) (h : leafOK s l = true) (a : Term l)`.
Each K constructor keeps its name as a reducible `@[match_pattern]` definition, so the rest of the library is generated as before.
It is the same model: a value of a sort is one of its constructors applied to values of its argument sorts, or one leaf injection with a proof field, so canonical forms, and Lean's `=` as K's equality, are unchanged; kimp and SIMPLE give the default encoding's goldens, traces and case results exactly (the gate's `arity` tier).
The family has about twenty constructors whatever the definition, its enumerations are scalars, and a match at a fixed sort splits the family's constructors (all but one refuted by their index) and then that sort's own enumeration.
It needs Lean ≥ v4.30.0, whose match compiler accepts nested patterns whose enumeration type depends on the family's index (v4.24.0 rejects them).

Measured on 2026-10-24 (Lean v4.30.0, 1-minute load 25 to 53): `Terms.lean` of kimp builds in 5.5 s (per-sort 46 s), SIMPLE's in 17 s (per-sort 302 s), KEVM's in 396 s / 814 CPU-s / 5.7 GB peak, and KMIR's (338 types, 1,145 constructors) in 78 s / 3.0 GB (2026-10-23).
The gate's arity tier (kimp and SIMPLE, built and tested) took 225 s wall and 623 s of CPU from an empty work tree, 4.5 GB peak, under a load of 7 to 9; in the heavy tier, SIMPLE alone took 396 s and 622 s of CPU in the per-sort encoding.
Whether the arity universe becomes the default is open (§9).

Two choices in the family follow from its match compilation (measured 2026-10-23 on KEVM, load 2 to 10):

- `hasLeaves s` comes before the leaf tag in `inj`: a match at a sort without leaves refutes `inj` on that field, instead of splitting the leaf tag over every sort; on `evm.md:751:5` the match compiler's subgoals drop from 2,512 to 130 and the matcher's elaboration from 1.78 s to 0.44 s.
- Every `match` on a non-variable pattern gets a fallback arm, an irrefutable one too (`--no-fallback-arms` turns it off), so the other constructors of the family go to `_` instead of being refuted one by one: KEVM's 626 matchers take 252 s / 443 CPU-s without the arms and 121 s / 211 CPU-s with them, and `Adequacy` 740 against 803 CPU-s (loads 15 and 34), so the arms cost the proofs little.
  In the per-sort encoding a match on a single-constructor sort is exhaustive and Lean rejects the arm as redundant, so the default encoding has none; it does not have the refutation cost either.

## 3. What is proved, and how it is checked

- `Adequacy`: the executable `step` (and `successors`, for rules with several matches) agrees with `Step` and `App`: sound by construction, since every matcher returns a proof of its match, and complete rule by rule.
  That a rule is in the index bucket of its own left-hand side (`Rules.r.mem`, `memS`) is the path the generator took through the index tree, one `apply` per node, so no tactic reduces the rest of the index (KEVM: 10 lemmas in 1.5 CPU-s, against 25.9 by reducing the index); the per-rule `complete`/`applies` proof evaluates the matcher test by test, identifying each split's bound value with the relation's (`k2l_fundep1`) so that the next `match` reduces instead of being split.
- `Equations`: each K equation is a theorem, proved by generic tactics (`k2l_eqn_a`, `k2l_eqn_b`, `k2l_eqn_r`, `k2l_fold_eqn`); it shows that the theory restricted to the generated symbols is consistent with this model.
  An equation the tactics do not prove is listed in `open-obligations.txt` and emitted as a statement: it is never assumed, never proved with `sorry`, and never under the axiom guard.
  `k2lean open-from-log Equations.lean BUILD.log open-obligations.txt` adds the theorems whose proofs failed in a Lake build log.
- The axiom guard (`#k2l_assert_axioms`, `KPrelude.Tactic`) fails the build when a guarded theorem depends on `sorryAx` or on any axiom other than `propext`, `Classical.choice` and `Quot.sound`; the prelude declares no axiom.
- Test data from krust runs compares the model with krust's executions: `k2lean goldens` (initial configurations by `krust krun --depth 0`, expected finals recorded from kimp, and step traces against krust and K's LLVM backend), `k2lean cases` (SIMPLE's tests, krust's final configurations, with search) and `k2lean configs` (benchmark programs).
- `k2lean claims` states K reachability claims (`claim` sentences of a `--for-proving` definition) as Lean propositions over `Step` (`KClaims`, `lean/claims`), proves those its tactic can, and lists the others for hand proofs; `k2lean claims replay` turns a proof that `krust kore-rpc` explores into a Lean script of named steps.
- `k2lean relate` pairs the rules and symbols of two definitions of one language and generates the translation and, when every rule pairs, a bisimulation proof (`demos/ImpRel`).

### 3.1 Determinism along the rule index (`--det2`)

The default proof of determinism is one `cases h₁ <;> cases h₂`: every pair of rules, quadratic in their number (KEVM's 597 rules of one rank: 356,409 inversions).
`gen --det2` (`crates/k2lean/src/det2.rs`, implied by `--arity-terms`) goes along the structure the index already has:

- the first item of the `<k>` cell, as an enumeration `Det.Key`, splits each rank's relation (`Det.split{i}`, one linear `cases`), and each rule's lemma `Rules.r.det` inverts only its key's relation and that of the rules without a key (KEVM: 137 keys, the largest group 108 rules, 9 rules without a key, 36,512 inversions);
- a pair classifier (`crates/k2lean/src/pairs.rs`: the KORE left-hand sides unified with sorts, the requires under the unifier by the definition's equations, the builtin hooks, complementary atoms, `z3` and finite case splits) chooses one certificate per goal that survives the inversion (`k2l_case`, with the closers of `KPrelude.Determinism`); it is untrusted, a failed certificate is reported and its goal goes to the default closers, and the kernel checks every proof;
- the pairs it cannot separate are the definition's own overlaps: `overlaps` lists them, `noOverlap c` decides that no listed pair applies with both rules, and the theorems are `Step.deterministic_of (h : noOverlap c = true)`, `step_complete_of` and `step_iff_of_noOverlap` (with no overlap, `Step.deterministic`, `step_complete` and `step_iff`).

kimp has no overlap; its `Determinism.lean` builds in 9.8 s on the default encoding, against 107 s by cases on pairs, and in 14 s on the arity universe, where cases on pairs did not finish in ten minutes (2026-10-24, load 25 to 53; 2026-10-23).
KEVM has 79 overlapping pairs: 78 in `driver.md` and `state-utils.md`, and `evm.md`'s stack underflow and overflow rules, which both apply to `DUP(N)` with `N ≥ 1025` and a stack of 1,024 to `N − 1` items.
The gate's light tier builds kimp with `--det2` and one exclusive pair listed as overlapping (`kimp-d2`), so the conditional statements are built too.

The gate (`tests/gate.sh`, `docs/testing.md` of the repository) regenerates every library and demonstration and fails when an open set grows, a guard loses a theorem, a `k2l_preserve` call closes fewer rules, a recorded output changes, a generated file changes without an accepted baseline, or any Lean source contains `sorry`, `admit` or an `axiom`.
The inputs a person writes (the open lists and the kind 1 hand modules) are not generated files: the gate does not hash them, and the builds that use them check them.

### 3.2 Claims that K's prover cannot state

`k2lean claims` (`crates/k2lean/src/claims.rs`, `lean/claims`) has three statements beyond the translation of K claims; their proofs are generic and checked by the kernel, like the claims'.

**Transfer along a bisimulation** (`KClaims/Bisim.lean`).
A strong bisimulation `R` between `S₁` and `S₂` relates states whose successors correspond in both directions, and the claim modalities look only at successors and at the target, so `AF.of_bisim : Bisimulation S₁ S₂ R → (∀ a b, R a b → P a → Q b) → R c d → AF S₁ P c → AF S₂ Q d`, its converse, and `AF_bisim_iff` when `P a ↔ Q b` on related states; `EF` and `Reach` likewise.
The all-path transfer needs both directions of the bisimulation (`fwd` gives the related state a successor, `bwd` sends each of its successors back), the one-path and reachability transfers only `fwd`.
`demos/ImpRelClaims` carries kimp's `sum-N` (proved by the generated claims, with `sum-loop` as a lemma) to the KRS IMP port through `relate`'s `ImpRel.bisim`, with the port's program written in the port's own constructors and no step of the port explored.
The continuation is a translated kimp continuation: `bisim` relates only translations, and the port has constructs kimp lacks.

**Claims under a preserved invariant** (`--assume-invariant NAME`).
A claim generated with it is `∀ vars, hyps → NAME lhs → AF Step Q lhs`: it says nothing of a left-hand side outside `NAME`, so it is weaker than the K claim, and holds for every configuration reachable from one that satisfies `NAME`.
`NAME` is a predicate on the top cell with a theorem `NAME.preserved : Preserved Step NAME` (`--invariant-preserved`), declared in `--invariant-module` (default: the kind 1 invariant of `gen --invariant`, `Invariant` in `NS.Invariants`).
The proof is `AF.circularity_inst_inv` with the target strengthened to `NAME d ∧ Q d`, so that the state a circularity or a proved claim leads to satisfies `NAME` too; `kc_auto … inv [NAME.preserved]` steps by `AFn.of_rule_inv`, which puts `NAME` of the successor in context (`hinv`), carries it through Boolean splits and claim applications, and, where no rule applies, opens a copy of it (the `kc_inv` simp set: the unfolding set of the kind 1 invariant, read from `--invariant-unfold`, and the collections' `toList`; then `kc_inv_fns`, the functions it calls) and splits on a projection it constrains (`proj_KItem_Value x`: the case `none` contradicts the invariant, in the case `some y` the variable `x` becomes the injection of `y`).
Sound because `Preserved` is a theorem: every state on a path from a state satisfying `NAME` satisfies it, which is all `AF.circularity_inv` assumes.

**Termination of a sublanguage** (`--induction FILE`).
FILE names a syntax sort, classes of the sublanguage with the sort of their values, and typings of constructors (`demos/claims/kimp-expr-eval.toml`: kimp's arithmetic and Boolean expressions without variables or division).
The generated module states the sublanguage as an inductive predicate `Sub cl e`, one obligation per typing ("if the arguments are in their classes and each, in any continuation, reaches a value of its class, the constructor's term does"), and `holds : Sub cl e → ∀ K cells, Reach Step (Target cl K cells) (cfg e K cells)` by induction on `Sub`, with the obligations of the open list as hypotheses.
`Reach` is a finite path to the target: total correctness, not the partial correctness of `AF`; with a deterministic `Step` it says that the run terminates in a value.
The induction hypotheses are claims over strict subterms, so the tactic may apply them anywhere, not only after a step as a circularity.
An obligation is closed by `kc_auto using [ih…] split`: where no rule applies it splits a variable of a type with at most 8 constructors, none of which has a field of the type itself (an argument expression into value and compound), refutes the cases whose `Sub` hypothesis no constructor of `Sub` can prove (inversion), and drops the Boolean cases whose arithmetic hypotheses contradict each other.
The `split` behaviour is off for the translated K claims, so their proofs and statistics are as before.

Measured on 2026-10-24 (Lean v4.30.0, shared 32-CPU host, load 15 to 35, each module built on its own after its dependencies):

| statement | result | module build |
|---|---|---|
| `sum-N` transferred to KRS IMP (`demos/ImpRelClaims`) | proved by a 3-line proof (`AF.of_bisim`) | 0.8 s |
| `copy`, `copy-loop` under kimpinv's `envOk` (`generated/kimpinv-claims`) | both proved generically (10 and 47 configurations); both false over kimp (`krust kprove` fails them, `Hand.copy_false`, `Hand.copy_loop_false`) | 4.7 s, after the rest of kimpinv's library (138 s wall, 125 s CPU, 3.8 GB) |
| kimp's expressions without variables or division (`ExprEval`) | 15 of 15 obligations closed, `holds` unconditional | 2.5 to 3.9 s |
| with `_/_` (`ExprDiv`) | its obligation does not close (4 goals left at `i / j`), and is false (`Hand.expr_div_false` at `1 / 0`) | under 1 s |

kimpinv's invariant now also conjoins `storeNoIds` (no store value is an `Id`), so the two claims assume both parts, though their truth needs only `envOk`.
On Lean v4.34.0, with that invariant, the heavy gate of 2026-10-24 proved both generically in the same 10 and 47 configurations.

## 4. Commands

| command | does |
|---|---|
| `gen` | the library (§1) |
| `open-from-log EQUATIONS.lean BUILD.log OPEN.txt` | adds the failed theorems of a build log to an open list (equations, or the cases of a kind 1 invariant) |
| `goldens`, `cases`, `configs` | test and benchmark data from krust runs |
| `survey` | which constructs of a definition the generator supports, without writing a library |
| `relate` | the correspondence of two definitions, and its Lean translation |
| `claims`, `claims replay` | K claims as Lean statements and proofs; with `--assume-invariant`, under a preserved invariant; with `--induction`, the termination of a sublanguage (§3.2) |
| `new-invariant` | the skeleton of a kind 2 invariant project (`invariants.md`, §4) |
| `diff OLD NEW [--hand PATH]…` | the rules whose `Step.Case` changed between two generations, the generated functions whose definitions changed with the rules that call them, and the hand-written references to both (`invariants.md`, §7) |

The flags of each command are in its module under `crates/k2lean/src/` and in the calls of `tests/libs.sh`.

## 5. Rule names

A rule's name, which names its `Step` constructor and every case derived from it, is its K label when it has one, else the focus of its left-hand side in K syntax (`«X + Y»`), with variable sorts and then a digest of the rule only when names collide; the source position is a doc comment.
So inserting lines or unrelated rules renames nothing, and a hand proof refers to a rule by a name that changes only when the rule does (`invariants.md`, §7.1).

## 6. The KRS sidecar

KRS declares the element sorts of collection cells (`env: Map<Id, Value>`), which KORE does not carry: the compiled `Map` maps `KItem` to `KItem`.
`k2lean gen --sidecar FILE` reads them from a JSON file keyed by KORE names and makes each declared cell a part of the invariant, so the declared type becomes a theorem (`Preserved Step Invariant`) rather than a check.

Format `k2lean-krs-sidecar`, version 1, a JSON object:

| key | value |
|---|---|
| `format` | `"k2lean-krs-sidecar"` (required) |
| `version` | `1` (required) |
| `producer`, `definition` | free text, for people (optional) |
| `cells` | an array of declared cells |

Each declared cell:

| key | value |
|---|---|
| `cell` | the cell's KORE symbol, as in `definition.kore` (`Lbl'-LT-'env'-GT-'`) |
| `krs` | the KRS declaration, copied into the generated documentation (optional) |
| `collection` | `"Map"`, `"List"` or `"Set"`: the builtin collection sort of the cell's content |
| `key`, `value` | for a `Map`: the declared KORE sorts of keys and values (`SortId`, `SortValue`) |
| `element` | for a `List` or a `Set`: the declared KORE sort of elements |

For a declared cell the generated part says that every binding (element) has the declared sorts, where "a `KItem` `t` has sort `S`" is `∃ y, proj_KItem_S t = some y`: the projection is defined exactly on the injections of values of `S` and of its subsorts.
The generator refuses a cell that is not in the definition, whose content is not the named collection, whose sorts are unknown or not subsorts of the collection's element sort, or that lies inside a cell collection; nested arguments (`Map<Int, Set<Int>>`) have no field in version 1.
`krs build` writes it as `k2lean-sidecar.json` beside `definition.kore` (`krs/crates/krs-cli/src/command.rs`, from the configuration cells of the Definition IR, `declared_cell_types`): one entry per leaf cell whose content is a `Map`, `List` or `Set` with declared element sorts that are not collections with arguments of their own, outside every repeated (`*`) or optional (`?`) cell, keyed by the KORE names k-rust's compilation gives the cell's label (`Lbl'-LT-'env'-GT-'`) and the element sorts (`SortId`); `producer` is `krs build`.
The recorded `demos/k/krs-imp/k2lean-sidecar.json` is its output for KRS IMP (`krs/tests/imp/rust-definition`); the library generated from it equals, file for file, the one generated from the hand-written file it replaces.

## 7. Lean version

Every generated project, the prelude and KClaims pin Lean v4.34.0 (`LEAN_TOOLCHAIN` in `crates/k2lean/src/main.rs`, and each `lean-toolchain`); the generated tactics and the prelude's proofs are checked on that version only.
The arity-indexed universe needs v4.30.0 or later (§2.1).
The repository's own Lean proofs (`lean/`) are a separate project with a toolchain of their own.

## 8. Limits

- Not every KORE construct is supported: `k2lean survey` lists what a definition uses that the generator does not; an unsupported construct is an error, not an approximation.
- Function equations with map patterns in their arguments (bound or free keys) are not stated as theorems in `Equations.lean`; a free-key set pattern `SetItem(X) REST` in a recursive function has no termination facts (`MapSizeOf` covers map carriers only), so its termination is Lean's own search or a `--termination` entry.
- Determinism is not generated for definitions with several-match rules; `uniqueAt c` checks it at one configuration.
- Recursive functions on lists close only in the fold shape `k2l_fold_eqn` recognizes; other equations the tactics cannot prove stay open obligations (`generated/*/open-obligations.txt` lists them per library).
- The limits of the invariant tooling are in `invariants.md`, §9.

## 9. Large definitions: cost and what is open

KEVM through `pipelines/kevm.sh` (krust's compilation of `driver.md`, `gen --arity-terms --termination kevm-termination.toml`, the matchers split into four modules, `lean -j 8`), measured on 2026-10-24 on a shared 32-CPU host:

| module | wall | CPU | peak | load |
|---|---|---|---|---|
| krust `kcompile`, `k2lean gen` | 12 s, 3 s | | 0.4 GB | 32 |
| `Terms` | 396 s | 814 s | 5.7 GB | 32 → 31 |
| `Functions` (21 recursive groups, no `sorry`) | 92 to 209 s | 136 to 200 s | 2.7 GB | 31 to 52 |
| `RulesRel` (`App`, `Step0`, `Step`) | 164 to 345 s | 165 to 266 s | 9.2 GB | 28 to 52 |
| the 626 matchers, four modules | 530 s | 582 s | 3.2 GB | 52 to 66 |
| `Rules` (index, `step`, `run`) | 47 s | 50 s | 2.3 GB | 66 → 43 |
| `Adequacy` (2,504 per-rule lemmas and the global theorems) | 256 s | 602 s | 9.6 GB | 43 → 26 |

Every module builds without an error, a `sorry` or an axiom beyond Lean's three; KEVM's 13 `KRYPTO` hooks are the parameters of `class Hooks`, and `senderTxData`, whose rewriting diverges at chain id −4, is a least fixed point (`pipelines/kevm-sender-diverges.lean` proves it has no value there).
KMIR's term universe builds (78 s, 3.0 GB, 2026-10-23); `gen` stops at its one `ensures` rule.

Open, in the order they block a KEVM library with kimp's guarantees:

- **KEVM `Equations`** (1,111 statements) does not build as one module: it exceeds 20 GB. In chunks of 139 theorems (2026-10-24), at least 273 of the 694 that finished fail: 171 are the equations of the two schedule functions, which are recursive and need to be unfolded once (`eq_def`) before the generic proof; the 83 equations of `#dasmOpCode`, a 150-rule cascade, exceed 20 GB together and need the cascade evaluated at the equation's own left-hand side; and the module needs splitting. The equations of a least fixed point (`senderTxData`) have no generic proof yet.
- **KEVM determinism** (`--det2`, 79 overlapping pairs) was built against the statements of `Adequacy` with their proofs omitted (2026-10-24): 543 of the 626 per-rule lemmas proved, 74 CPU-minutes in 16 files at `lean -j 4` (one file exceeds 20 GB), with 75 goals open in 62 lemmas (102 with the first closers): 32 that `z3` separated with bytes, string and set facts that `omega` lacks, 26 that need evaluating a variable's membership in a set of literals, 7 complementary atoms equal only after evaluating a call, 10 clashes inside map and list patterns; and 21 lemmas out of heartbeats, three of them rules whose first `<k>` item is a variable of sort `Gas`, which invert all 597 rules of their rank and cost a third of the module. Not rebuilt against the real `Adequacy`.
- **Termination**: all 21 recursive groups of KEVM that Lean's own search does not prove are proved, 15 by the generator's measures and 5 by `kevm-termination.toml`; a mutual group gets no synthesized measure, and the termination file's lemmas name generated definitions and the arity universe's constructors, so a change to either breaks them at build time.
- **A KEVM run**: the test drivers need an instance of `Hooks` (real hashes, outside the semantics) and krust-produced initial configurations; none is generated yet.
- **KMIR**: `ensures` rules, and per-program instances of its three equation-less `lookup*Kore` functions, now parameters.
- **The arity universe as the default**: kimp's and SIMPLE's results are equal on both encodings and the arity universe builds them several times faster (§2.1); not checked on it are the invariant tooling (kinds 1 and 2), `relate`, the claims, and the typed collections of the KRS sidecar. A delaborator from `Term.cK` back to the K constructors' names would make its goals readable.
- **`--det2` as the default** for the per-sort encoding: kimp's `Determinism.lean` takes 9.8 s with it and 107 s without (§3.1).
- **`Terms` cost**: about 280 of KEVM's 665 CPU-s are the decoder's round trip by `simp` and 128 leaf-inclusion lemmas by `decide` (estimate from a profile, 2026-10-23).
- **Lean's realization of match equations and equation lemmas for imported constants** runs under the default 200,000 heartbeats whatever the importing file sets with `set_option` (Lean v4.30.0 and v4.34.0): the adequacy proofs avoid splitting large matches of another module and each equation proof unfolds only its own definitions, but another proof that does either can reach that limit.
  A probe of 2026-10-24 measured it on both versions: the 101 equation lemmas of a three-argument match over 100 constructors, defined in one module, stop at 200,000 heartbeats when another module realizes them under `set_option maxHeartbeats 0`, and are realized in 23 to 27 s when that module is elaborated with `-D maxHeartbeats=0` on Lean's command line, which does raise the limit.
