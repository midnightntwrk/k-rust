# k2lean: design

k2lean turns a K definition, as krust compiles it to KORE, into a Lean 4 library that models the definition and proves facts about the model.
This note says what the generator writes, why the encoding is sound, how the generated proofs are checked, and where the limits are.
How to state and prove invariants of a generated semantics is in [`invariants.md`](invariants.md).

## 1. Input and output

The input is krust's compiled definition: `definition.kore` and `runtime.json` from `krust kcompile` (the KORE theory of the definition, and its configuration variables).
The output of `k2lean gen --kore definition.kore --runtime runtime.json --out DIR --name NS` is a Lake project in `DIR` that requires the prelude `KPrelude` (`lean/prelude`) by relative path (`--prelude`, relative to `DIR`):

| module | content |
|---|---|
| `NS/Terms.lean` | one family indexed by the sorts (with `--per-sort-terms`, one Lean type per sort, §2.1), constructors, injections and projections, decidable equality and an order on terms |
| `NS/Functions.lean` | each function defined by KORE equations, as a Lean definition; hooked functions are the prelude's, and the library's parameters (§2) are the fields of `class Hooks` |
| `NS/Equations.lean` | each K equation and simplification rule as a theorem about the generated definitions, or, when its generated proof fails, a named open obligation (`def Eqn.….statement : Prop`); each proof has its own heartbeat budget (`gen --equations-heartbeats`, default 100,000, and per theorem `--equations-heartbeats-file`); when the statements weigh more than `gen --equations-part-weight` (default 2000; the weight of a statement is 1 plus the definitions its proof may unfold), they are in `NS/Equations/Part1.lean` … `PartN.lean`, which `NS/Equations.lean` imports (§9) |
| `NS/Rules.lean` | `App c` (some rule applies at `c`), `Step c c'` (one constructor per rewrite rule) and the executable `step` |
| `NS/Adequacy.lean` | `step` against `Step` and `App`: sound by construction, complete rule by rule |
| `NS/Determinism.lean` | `Step` is deterministic, along the rule index modulo the definition's overlapping pairs, each witnessed (§3.1), or by cases on pairs of rules (`--det-pairs`); for a definition whose rules match a map at several keys, why it is not claimed, and the check `uniqueAt c` instead |
| `NS/Init.lean` | `init`, the initial configuration of the configuration declaration, with one parameter per configuration variable |
| `NS/Preserves.lean` | `Step.Case.r P` per rule and `Step.preserves_of`, the per-rule preservation principle; `Step.Rel.r Q` and `Step.rel_of`, the same for a relation `Q c c'` between a step's source and target, which the scaffolds (§3.5 to §3.7) state their obligations with |
| `NS/InvariantDefs.lean`, `NS/Invariants.lean` | with `--invariant NAME[@CELL]` or `--sidecar FILE`: the invariant and its `Preserved` theorem (`invariants.md`, §3) |
| `NSTest/Axioms.lean` | the axiom guard: `#k2l_assert_axioms` over every proved theorem |
| `NSTest/DetAxioms.lean` | the axiom guard of `NS.Determinism` alone, which `NSTest.Axioms` imports: it builds without `NS.Equations` (§3.1) |
| `NSTest/Main.lean`, `NSBench/Main.lean` | the test and benchmark drivers (`lake test`; `goldens`, `cases` and `configs` fill their data) |

Every generated file starts with "Generated by k2lean … do not edit".
A library is regenerated from the KORE whenever the definition changes; what a person writes lives elsewhere: the open lists (`open-obligations.txt`, `open-invariant-cases.txt`) and the hand module `NS/InvariantsHand.lean`, which `gen` writes once and never overwrites, and kind 2 projects of their own.

## 2. The encoding

The generated Lean is a model of the KORE theory: every symbol gets an interpretation, and the generated theorems show that the interpretation satisfies the theory's axioms that the generator states.

- **Sorts.** Each sort is a carrier, and its constructors are free: KORE's `constructor` symbols carry the no-confusion axioms, and each sort's "no junk" axiom lists exactly its constructors and the injections of its subsorts.
- **Injections.** Injections compose (`inj{B,C}(inj{A,B}(x)) = inj{A,C}(x)`), so a value of sort `S` is determined by its leaf, the most specific sort that built it.
  A sort with several leaves is a sum over them (`S.inj_L`), so every K value has exactly one Lean representation; `proj_S_L` is the partial inverse of an injection, defined exactly on the injected values.
- **Builtin sorts and hooks.** `Int`, `Bool`, `String`, `Map`, `Set`, `List` and the IO sorts are the prelude's types, and a hooked function is the prelude definition chosen by its `hook{}` attribute only, never by the symbol's K name (`crates/k2lean/src/hooks.rs`).
  Each hook has the meaning `domains.md` gives it; where `domains.md` leaves a value unspecified (`/Int` at divisor 0, `substrString` out of range), the model makes a documented choice or leaves the result undefined.
  A choice never contradicts an equation `domains.md` gives the hooked function, since the model must satisfy every equation of the definition: `replaceFirst(S, "", R)` is `R +String S`, the value of its equation at an empty `ToReplace`.
- **Parameters.** A hooked function the hook library does not implement (`KRYPTO.keccak256`, `BYTES.bytes2hex`), and a function symbol with neither equations nor a hook, is unconstrained by the definition: it is a field of the generated `class Hooks` (`Functions.lean`), `Option`-valued, and every later module has `variable [Hooks]`.
  Every theorem then holds for every implementation of the hooks, with no axiom; a test driver needs an instance.
- **Partiality.** A partial function is `Option`-valued, `⊥` is `none`, and matching logic's `\equals` holds between two `⊥`s, so an equation over partial terms is an equation of `Option`s.
- **Functions.** A function's equations are tried in priority order, `owise` last; the first equation whose argument patterns match and whose `requires` is `true` gives the value, even when that value is `⊥`.
  An `owise` equation's guard is the negation of its competitors' applicability, which the cascade position realizes.
  Where no equation applies the result is `none`: the least-defined model, since KORE leaves the value unconstrained there.
- **Free-key map patterns in function equations.** An equation `f(K |-> V REST) => e requires c` whose key `K` is bound nowhere else in its left-hand side is, as a KORE axiom, `∀ K V REST. M = (K |-> V) REST ∧ c → f(M) = e`: one instance per binding of `M` at which the rest of the left-hand side matches and `c` holds (a *matching binding*).
  - When every matching binding gives the same value (`⊥` included), that value is the K function's meaning at `M`.
  - When two matching bindings give different values, the axioms equate `f(M)` with both; a function denotes one value (or `⊥`), so no model of the definition contains `M` with that equation, and the K definition determines no value at `M` (the definition is not confluent there).
  - The generated definition takes the first matching binding in the map's canonical order (ascending keys): `MapHook.chooseFirst`, which tries each binding and passes to the next exactly when the rest of the left-hand side or the requires fails there, and otherwise gives that binding's value, even `⊥`.
    So it is the K function's meaning wherever the definition determines one (`MapHook.chooseFirst_eq_of_agree`: if some binding gives `b` and every value at any binding is `b`, the result is `b`), and a choice among the instances where it does not; `chooseFirst_eq_some` and `chooseFirst_eq_none` characterize it.
  - The equation applies at `M` exactly when some binding matches; an `owise` equation or one of a lower priority is tried only when none does, as the KORE guard of the cascade says.
  - Several free keys in one left-hand side choose lexicographically; a function that recurses on the rest or on the value of the binding terminates by `MapSizeOf` (the value and the rest are smaller than the map, from the certificate the continuation receives).
  - Such an equation is not stated in `Equations.lean`, as no equation with a map pattern in its arguments is (their arguments are partial patterns, not terms); its K statement, the agreement of all matching bindings, holds exactly where the definition is confluent. An `owise` equation after it is stated, with the pattern's no-match premise (§3, the owise equations' proof).
  - So that a theorem need not depend on the choice, each function `F` with such an equation gets, after every function is defined (`crates/k2lean/src/agree.rs`; the `freekey` fixture builds all of them):
    - `F.instN x : List _`, the *instances* of equation `N` at the arguments `x`: one per match of its left-hand side and requires, each the value of its right-hand side there (`none` for `⊥` when `F` is partial), in the map's order (`MapHook.chooseAll`, which enumerates every binding).
      A binding at which the rest of the left-hand side or the requires fails is no instance; a requires is part of the match, as in the KORE axiom, whose antecedent it is.
      With several free keys in one left-hand side an instance is a tuple of bindings, enumerated lexicographically (each binding of the first map pattern, then each of the next one in the rest), since the axiom quantifies over all of their variables at once.
      An equation without a free key has at most one instance.
    - `F.instances x`, the instances of the first priority group of `F`'s equations that has one at `x` (`KPrelude.firstNonempty`), followed by the cascade's value where no equation applies when that is not `none` (an `anywhere` symbol's constructor, or the value of a total function's last equation).
      These are the instances that K's axioms equate with `F x`: an equation of a lower priority is guarded by the negation of the higher ones, so it constrains `F x` only where none of them applies, and the equations of one priority are all axioms there, so two of them that overlap at `x` constrain `F x` together, the same way as two bindings of one equation.
    - `F.Agrees x : Prop`, every two instances are equal (`KPrelude.Agree (F.instances x)`).
      It holds exactly where K's axioms are consistent at `x`; when `F.instances x` is not empty, it holds exactly where they determine `F x`, and an empty list (no equation applies, `F x = none`) is the least-defined model's documented choice (above).
      It is one predicate per function, not per equation, because which equation's instances count at `x` depends on the equations of higher priority; a per-equation statement would need their inapplicability as a hypothesis, which `F.instances` already encodes.
    - `F.Agrees` is an `abbrev` and `Agree` has a `Decidable` instance whenever the value type has decidable equality, so `decide` evaluates `F.Agrees` at a concrete map wherever `F`'s definition reduces in the kernel (a non-recursive function: on `freekey`, `hasNeg` and `twoPos` agree at a two-binding map and `anyPos` does not, 2026-10-25); a function defined by well-founded recursion does not reduce there (`allNat`), and its agreement at a concrete map is a proof by its equations.
    - The theorems: `F.instN_head`, the first instance of equation `N` is the value of its matcher in `F`'s cascade (`F.ruleN`, or `F.eqnN`, the same text as the matcher a recursive definition inlines), by `k2l_inst_head` (`KPrelude/Ext.lean`), which splits the instance list's matches and reduces or refutes the matcher's with the hypotheses (a fallback arm's case by the split's no-match hypothesis instantiated by reflexivity, `k2l_no_arm`: `simp_all` does not instantiate it when the pattern binds many cells, as SIMPLE's five-cell `<thread>`), and `MapHook.head?_chooseAll` under the binder; `F.eq_instances`, the generated value is the first instance (`F x = (F.instances x).head?.join` for a partial `F`, `(F.instances x).head? = some (F x)` for a total one), by case analysis of each equation's instances in the cascade's order; and `F.eq_of_agrees`, under `F.Agrees x` the generated value is every instance's value (`KPrelude.Agree.head?_eq`).
      So "the generated function equals K's meaning wherever K's axioms determine one" is a theorem per function, and a theorem that must not depend on the choice assumes `F.Agrees` and rewrites with `F.eq_of_agrees`.
      These theorems are under the library's axiom guard.
    - `gen` prints a note per such function, saying whether its instances are shown to agree at every argument: they are when the right-hand side (with the partial calls it evaluates) reads no variable that the choice of a binding binds, directly or through a later match on one, since then every match evaluates one expression over variables every match binds alike (`agree::reads_no_choice`; a sufficient condition, so the note says only "not shown" otherwise).
      krust's load-time critical-pair check has the same condition for an equation whose left-hand side matches one subject in several ways (a self pair, `SeveralMatches` in `confluence.rs` of `k-rust-backend`), reported as `UnjoinedCriticalPair`; but the load classifies pairs only where one can change a value claim of krust's (an equation head, that is an `anywhere` production, or an overloaded symbol that is not a free constructor: the load's shortcut in that file), so on `freekey` `kcompile` and `krun` print no such warning, and `gen`'s note is the only report.
  Well-founded recursive functions are Lean definitions by well-founded recursion, and their equations get a proof by the recursion's own unfolding (`k2l_eqn_r`).
  The generator chooses each recursive group's measure and Lean proves that it decreases (§2.2), so a wrong choice is a build error, never an unsound definition.
  `gen --termination FILE` (TOML, keyed by K label) makes a function whose rewriting diverges on some arguments the least fixed point of its equations (`partial_fixpoint`): `none` exactly where the rewriting diverges, the equations' value everywhere else; it can also supply a measure and its proof.
  Lean proves a `partial_fixpoint` body monotone only when the recursive calls sit under `Option`'s bind, and never in a test that decides which branch is taken; so an equation whose left-hand side is guards only is a branch `if guards then do … else`, and one that matches patterns is two expressions over the same match: `aK : Bool`, whether it applies (its match and its requires), and, where it does, its right-hand side with the partial calls chained by `>>=`; the body is the `if` chain over the `aK` in cascade order, so the equation that applies first gives the value, as in the cascade.
  A left-hand side that calls a function of its own group is refused (whether the equation applies would depend on the function being defined, which is not monotone), and so is a free-key map pattern; in a mutual group every member is a least fixed point, since Lean defines the group by one fixed point.
  Each entry needs a checked witness of the divergence that justifies it (`f.fixpoint_induct` with a motive at the cyclic arguments: `pipelines/kevm-sender-diverges.lean` and the gate's `demos/k/term/term-diverges.lean`), so that `none` is shown to be what the equations determine there and not a lost value.
- **Rules.** `Step` has one constructor per rewrite axiom of the compiled definition, heating and cooling included, at the top configuration.
  A rule whose left-hand side matches and whose `requires` is `true` but whose right-hand side is `⊥` applies (`App`) and has no `Step`: matching logic gives that configuration no successor.
  With priorities, `Step` is stratified: a rule of a lower rank steps only where no rule of a higher rank applies (`¬ App j lhs`).
- **`ensures`.** A rule `l => r requires c ensures e` is the KORE axiom `\rewrites(l ∧ ⌈c = true⌉, r ∧ ⌈e = true⌉)`: from a configuration that matches `l` under a valuation σ at which `c σ` is `true`, the rule leads to the configurations of the pattern `r σ ∧ ⌈e σ = true⌉`.
  - The ensures is a conjunct of the right-hand side, so it takes no part in whether the rule applies: `App` is the match of `l` and the requires, as without it.
  - Where `e σ` is `true`, the pattern is `r σ`, and the rule steps as it would without the ensures.
  - Where `e σ` is `false`, or `⊥` (a partial function in `e` is undefined at σ, and `⊥` equals no value, so `⌈⊥ = true⌉` is `⊥`), the pattern denotes no configuration: the rule applies and has no successor, as a rule whose right-hand side is `⊥`.
  - So the rule's `Step` constructor has the ensures' tests among its hypotheses, after the requires', and its `App` constructor has none of them; the executable `step` returns `.undefined` (a rule applies, no successor) where they fail, the outcome of a `⊥` right-hand side, and `step_undefined` (`App c ∧ ∀ c', ¬ Step c c'`) states exactly that, so no theorem's statement changes.
  - Priorities restrict a lower rank to the configurations where no rule of a higher rank applies, and applicability does not read the ensures: where a rule of a higher rank applies with a false ensures, an `owise` rule does not step, and the configuration has no successor.
  - Determinism is a statement about `Step`, which an ensures only shrinks, so its statement is unchanged; two rules are apart where their requires and ensures cannot all hold at once, and the pair classifier reads both (`Rule.kore`'s conditions), so a witness of an overlap satisfies both rules' ensures, as its facts are steps of `Step`.
  - An ensures may mention only variables that the left-hand side binds: one over a variable bound nowhere constrains an existential of the right-hand side, which the generator refuses, as it refuses such a right-hand side.
  - The gate's library `ens` (`demos/k/ensures.k`) has a rule of each kind: an ensures that is a variable of the left-hand side (KMIR's `#assume`), one by a partial function (undefined at a divisor 0), one over a rule with an `owise` competitor, a pair apart by their ensures only, and a pair that overlaps exactly where both ensures hold (witnessed).
  - A function equation `f(ps) = r requires c ensures e` is, in KORE, `c → f(ps) = r ∧ ⌈e = true⌉`, so the function's value is `r` where `e` holds and `⊥` where it does not; no function equation of KMIR has one, and the generator refuses one (`survey` counts it), since its value and its statement would both need the ensures.
  - A simplification rule with an ensures states `c → L = (r ∧ ⌈e = true⌉)`, in the model `L = if e = some true then r else none`; the 17 of `domains.md` (`(K |-> V M)[K] => V ensures notBool (K in_keys(M))` and the like) are in its `MAP-KORE-SYMBOLIC` and `SET-KORE-SYMBOLIC` modules, which neither KMIR nor a definition of the gate imports, so none is in their KORE; `gen` does not state one yet (its right-hand side is not lowered, and `gen` notes it).
  A map pattern whose key is bound nowhere else (`K |-> V REST`, the cell maps of SIMPLE's threads) matches once per binding, so `step` returns the first match whose result is defined and `successors` all of them.
- **Overloads.** A left-hand side that mentions an overloaded symbol matches its variants modulo the `symbol-overload` axioms (`crates/k2lean/src/overload.rs`).

### 2.1 The arity-indexed universe (the default; `--per-sort-terms`)

The per-sort universe (`gen --per-sort-terms`; the default until 2026-10-25) is one Lean type per sort, all in one `mutual` block, a sort with subsorts having one constructor per leaf injection.
Two limits of Lean make it unusable at KEVM's size (measured 2026-10-23, Lean v4.24.0 and v4.30.0, shared 32-CPU host):

- the auxiliary constructions of a mutual block (recursors, `below`, `brecOn`, `sizeOf`) grow with types × (types + constructors): SIMPLE's block (86 types, 362 constructors) took 284 s, and KEVM's (392 types, 1,160 constructors) had not finished after 90 minutes at 17.9 GB;
- Lean's runtime cannot compile a constructor with fields at index 244 or above, and KEVM's `KItem` has 277 injections (KMIR's 309).

A single indexed family with one constructor per K constructor elaborates, but every `match` at a fixed sort then refutes every other constructor of the family (2.4 s per two-arm match on KEVM's 1,160) and it is not executable either.

`gen` (`crates/k2lean/src/terms_arity.rs`) writes one family `Term : Tag → Type` indexed by the sorts, with one constructor per arity of the sorts' own constructors (`c2 (c : C2 s) (a0 : Term (A2_0 s c)) (a1 : Term (A2_1 s c))`, `Ck s` enumerating sort `s`'s constructors of arity k), one per builtin carrier, one per collection sort (a nested list), and the leaf injection `inj (hs : hasLeaves s = true) (l) (h : leafOK s l = true) (a : Term l)`.
Each K constructor keeps its name as a reducible `@[match_pattern]` definition, so the rest of the library is generated as before.
It is the same model: a value of a sort is one of its constructors applied to values of its argument sorts, or one leaf injection with a proof field, so canonical forms, and Lean's `=` as K's equality, are unchanged; kimp and SIMPLE give the per-sort encoding's goldens, traces and case results exactly (the gate's kimp-ps and simple-ps, whose recorded outputs must equal kimp's and SIMPLE's: `same_as` in `tests/areas/core.py`).
The family has about twenty constructors whatever the definition, its enumerations are scalars, and a match at a fixed sort splits the family's constructors (all but one refuted by their index) and then that sort's own enumeration.
It needs Lean ≥ v4.30.0, whose match compiler accepts nested patterns whose enumeration type depends on the family's index (v4.24.0 rejects them).
Equality on the family is `Term.beq`, by structural recursion on both terms (`termination_by structural`; without it Lean falls back to well-founded recursion, which the kernel does not unfold), with builtin leaves compared by `KPrelude.LeafEq` (a `Bytes` value as its byte list, a `String` as its UTF-8 bytes), and `DecidableEq (Term s)` is derived from `Term.eq_of_beq` and `Term.beq_self`: the kernel decides `a = b` on closed terms without decoding a serialization, so a witness's comparison of a 49,153-byte value is linear (§3.1).
Measured on 2026-10-25 (Lean v4.34.0, cold module, prelude built, 8 GB cap, load 18 to 24; against the same file with the former comparison of `ser` values), `Terms` of kimp builds in 4.5 to 6.0 s and 7.3 to 10.0 CPU-s (before: 3.8 to 4.1 s, 6.6 to 7.0 CPU-s), SIMPLE's in 15.0 to 17.5 s and 31.1 to 37.0 CPU-s (before: 14.2 to 15.6 s, 31.6 to 34.9 CPU-s), at the same peak (0.84 and 1.3 GB), and KEVM's in 274.7 s and 554.8 CPU-s (before: 241.8 s, 510.7 CPU-s; both built at once, load 12 to 19).
Goals print as K terms: `KPrelude.Delab` prints `Term.ck c a0 …`, `Term.inj hs l h a` and `Term t` by the names of the K constructor, the leaf injection and the sort's abbreviation that they unfold from, and every arity `Terms.lean` ends with `#k2l_check_delab NS`, which fails the build unless every constructor and leaf injection of the library, unfolded and applied to variables, prints as its definition applied to them (kimp 86, SIMPLE 354, KEVM's driver 1,148).
On KEVM the check costs 1.4 s and 50 MiB over importing `Terms` (2.7 s and 1,707 MiB against 1.4 s and 1,657 MiB, each file elaborated alone; 2026-10-25, Lean v4.34.0, load 70).

Measured on 2026-10-24 (Lean v4.30.0, 1-minute load 25 to 53): `Terms.lean` of kimp builds in 5.5 s (per-sort 46 s), SIMPLE's in 17 s (per-sort 302 s), KEVM's in 396 s / 814 CPU-s / 5.7 GB peak, and KMIR's (338 types, 1,145 constructors) in 78 s / 3.0 GB (2026-10-23).
The gate's former arity tier (kimp and SIMPLE, built and tested) took 225 s wall and 623 s of CPU from an empty work tree, 4.5 GB peak, under a load of 7 to 9; in the heavy tier, SIMPLE alone took 396 s and 622 s of CPU in the per-sort encoding.

The arity universe is the default of `gen` and `relate` since 2026-10-25 (K6): `gen --per-sort-terms` and `relate --per-sort-terms true` select the per-sort universe, and `gen --arity-terms`, the former opt-in, is accepted and changes nothing.
Every generated theorem states the same thing on both universes, so no statement changed with the default.
A library or demo whose arity form would lose a count stays per-sort, with `encoding = "per-sort"` in its gate registry entry (`tests/areas/AREA.py`; `gate.sh list` prints it); these are, with the reason of each:

- six snapshot tests of the generator (params, measure, peano, counter, freekey, counter_det2), which keep the per-sort output under test (`--per-sort-terms` in `tests/snapshots.rs`).

Since 2026-10-26 the claims are no longer a holdout: kimp's claims and kimpinv's run on the arity universe, `kimp-claims` on `kimp` and `kimpinv-claims` on `kimpinv`, with every `kc_auto` line equal to the per-sort run's. Their 20 GB on the arity universe had two causes in the claim tactic, both fixed. First, the variable and cell splits accepted only types without indices, and every sort is an indexed family there, so a symbolic expression was never split into its value forms and no rule applied: on the family the splits take `familyCases`' cases under the same conditions. Second, a `match` on the family, such as a collection's `toList`, is not reduced while its scrutinee contains a metavariable, so the map equations of a claim instance were never solved and a loop's circularity never applied: the tactic unrolled the loop until its fuel was spent. The structural unifier now reduces with the metavariables read as free variables, `whnfDOpen`, which every instantiation of them preserves.

Two choices in the family follow from its match compilation (measured 2026-10-23 on KEVM, load 2 to 10):

- `hasLeaves s` comes before the leaf tag in `inj`: a match at a sort without leaves refutes `inj` on that field, instead of splitting the leaf tag over every sort; on `evm.md:751:5` the match compiler's subgoals drop from 2,512 to 130 and the matcher's elaboration from 1.78 s to 0.44 s.
- Every `match` on a non-variable pattern gets a fallback arm, an irrefutable one too (`--no-fallback-arms` turns it off), so the other constructors of the family go to `_` instead of being refuted one by one: KEVM's 626 matchers take 252 s / 443 CPU-s without the arms and 121 s / 211 CPU-s with them, and `Adequacy` 740 against 803 CPU-s (loads 15 and 34), so the arms cost the proofs little.
  In the per-sort encoding a match on a single-constructor sort is exhaustive and Lean rejects the arm as redundant, so that encoding has none; it does not have the refutation cost either.

Tactics split a variable of the family with `familyCases` (`KPrelude.FamilyCases`), which leaves the cases of the sort's values only. It refutes a constructor `ck` by `cases` on its enumeration field when `Ck t` has no constructor, or by a contradiction among the hypotheses that needs no search (two constructors equated, `p` and `¬p`); not by `contradiction`, whose search for a hypothesis of an empty type runs `cases` on every hypothesis of the context, so a case only that search refutes stays, for the caller to close. A leaf is split further (to its builtin carrier's value, `b_SortInt v`) only when the family has a `b_` constructor at its tag.
Measured on 2026-10-28 in heartbeats, each module elaborated alone on one thread (`lean -j1 -DElab.async=false`; heartbeats count allocations, so they do not depend on the load, which was at 100% of the CPUs), before and after these two changes: `PickRel.Bisim` 1,099M to 249M (61 to 12 CPU-s), `KImpClaims.ExprVars` 1,355M to 705M (per-sort 345M), `ExprEval` 794M to 347M (per-sort 163M), ImpTypes' `Soundness` 1,204M to 646M, ExprTypes' 573M to 331M, ImpWrites' `Cases` 966M to 777M. `familyCases` is then 2 to 8% of each; the rest of the gap to the per-sort encoding is in the tactics that use it (the claims' interpreted tactic code, 31 against 15 s; `simp` in `k2l_preserve`'s closers over functions matching on a tag and a term).

### 2.2 Termination measures

A recursive group (one function, or several that call each other) is one well-founded definition, so each function needs a measure that decreases at every recursive call; `termination.rs` chooses it and Lean proves the decrease (`decreasing_by`).
In order:

- the earlier rules, unchanged: the length of a builtin `List` the function destructures (when every recursive call is on the rest of the list), an integer distance bounded by a requires, or one integer measure or constructor rank chosen from the facts at the calls;
- structural recursion on the pieces of a parameter (constructors over variables of its patterns) is left to Lean's own search (`sizeOf`);
- otherwise each function gets a tuple of components, of one length across the group, compared lexicographically, chosen as Lean's `GuessLex` chooses: a component that no remaining call increases and some call decreases, then the next one for the calls that leave it equal.

The components:

- an integer distance `(e).toNat` over the function's integer parameters and terms over them (`lengthBytes(B) -Int I`): from the facts at its recursive calls (the requires, the failure of earlier guard-only equations, the ranges of defined partial hooks, facts about callees), carried from a callee to its caller through the call's arguments and back; it may read an integer field of a parameter that the equations match with a constructor, and the measure is then a definition by cases on that parameter (`f.k2l_measure`);
- the shape of a parameter, in the arity-indexed universe (`KPrelude.Shape`, `Term.shape`): the number of its constructors and builtin values, every builtin value counting one whatever its magnitude, every collection element one more than its own shape; it decreases where a function replaces a list item by smaller pieces even when the list grows (KEVM's `#bloomFilterAux`), and through functions that return a sublist (`qsortJSONs`'s filters), where `sizeOf`, which grows with an integer's magnitude, does not;
- a rank of the function within its group, along the calls that leave the earlier components equal; when the calls between functions form a cycle under the earlier components, the rank is guarded by the facts that hold at every call into the function from the group, and is above every other rank where the guard fails;
- a counter's distance to a bound, before a component that decreases only beyond that bound (KEVM's `#fakeExponential`: the counter `I` increases towards `|NUMER| + 1`, and beyond it the accumulator `ACCUM *Int NUMER /Int (DENOM *Int I)` is smaller than `ACCUM`, `KPrelude.IntHook.tdiv_mul_facts`).

The choice is checked symbolically before it is emitted: facts are linear integer forms, and a decrease is a consequence of the facts at the call, decided by Fourier–Motzkin elimination over the rationals with each fact's constant rounded down (sound for integers, incomplete); `omega` decides at least as much.
A case the facts exclude (the branch of a guarded rank where its guard fails, at a call where the guard holds) constrains nothing, whatever the components' values there.
The facts include the prelude's about the hooks the calls go through: a right shift (`IntHook.shr_facts`; `popcount` of the gate's `demos/k/term`), a defined `findString` is `-1` or an index at which the needle fits (`StringHook.find_facts`), the length of a `substrString` is at most the string's and at most what follows its start when the start is in range (`StringHook.substr_facts`), a string literal's length (by `rfl`); the lengths of a function's `String` and `Bytes` parameters are terms an invariant may bound, so KMIR's `#splitSemicolon` group (a string split at each separator, the inner function called only with an index `findString` returned) gets the measure `length S + 1`, then a rank guarded by `-1 ≤ I ≤ length S - 1`.
That case is not in the gate's `demos/k/term`: a library with the sorts `String` and `Int` states the hook library's `countAllOccurrences` equations, and the second one is open (it is open in SIMPLE's libraries on `main`), so the fixture would gain an open entry that is not its test's; it returns to the fixture when that equation is proved, a change to the five SIMPLE libraries of the core and invariants areas.

Facts about a callee that the measure needs are lemmas derived from the callee's equations and proved before the group, registered with `@[k2l_fact]` so that `k2l_facts` adds them to a goal:

- what a non-recursive function returns (`f.k2l_out`: facts of its arguments when it is defined, and of an integer result; `f.k2l_out_i`: facts of the integer fields of a constructor result, per pattern), as the strongest sums of one to three integer atoms that hold on every way the function returns (total callees inlined), then pruned to the facts the measure needs;
- the range of a total integer function (`f.k2l_range`, KEVM's `#widthOpCode ≥ 1`);
- a bound on a result's shape (`f.k2l_shape`: `shape r ≤ shape x_j`), by induction on the callee's own measure when it is recursive.

Each lemma is proved by unfolding the function in its hypothesis and splitting its cascade (`k2l_fn_facts`); none changes a definition, and a lemma that does not hold is a build error.

## 3. What is proved, and how it is checked

- `Adequacy`: the executable `step` (and `successors`, for rules with several matches) agrees with `Step` and `App`: sound by construction, since every matcher returns a proof of its match, and complete rule by rule.
  That a rule is in the index bucket of its own left-hand side (`Rules.r.mem`, `memS`) is the path the generator took through the index tree, one `apply` per node, so no tactic reduces the rest of the index (KEVM: 10 lemmas in 1.5 CPU-s, against 25.9 by reducing the index); the per-rule `complete`/`applies` proof evaluates the matcher test by test, identifying each split's bound value with the relation's (`k2l_fundep1`) so that the next `match` reduces instead of being split.
- `Equations`: each K equation is a theorem, proved by generic tactics (`k2l_eqn_a`, `k2l_eqn_b`, `k2l_eqn_r`, `k2l_fold_eqn`); it shows that the theory restricted to the generated symbols is consistent with this model.
  An equation of `domains.md` about a hooked function that needs more than unfolding (`bitRangeInt`, `_&Int_`, `replaceFirst`, `rfindChar`, `_|Set_`, …) is a theorem of `KPrelude.HookLaws`, stated in the shape the generator writes it; `k2l_hook_law` closes the generated statement with it, matching at reducible transparency.
  **Well-formedness premises.** An equation of a hooked function assumes that each of its variables of a `Set` or `Map` sort is well formed: `(hwf0 : KPrelude.SetHook.WF S1)`, `KPrelude.MapHook.WF M` (`eqns.rs`, `wf_premises`).
  This is the meaning K gives the equation: a K variable of sort `Set` ranges over sets and one of sort `Map` over finite maps, while the Lean carrier is a representation (a list of entries, §2) that also holds lists that are not sorted or repeat a key, which represent no K value.
  `MapHook.WF` (keys strictly sorted, with its executable check `MapHook.wfb`) is the representation invariant every hook preserves and every K value satisfies; `SetHook.WF` is the same predicate on a set's map to `Unit`, not a second notion.
  A hook model implements K's meaning on the sets and maps only, so where it is applied to a list that is no set its value is an artifact of the representation, and an equation between two hook expressions can fail there although it holds at every K value: `S1 |Set S2 = S1 (S2 -Set S1)` fails exactly at the carrier values that are not sets (`SetHook.union_eqn_not_wf`), and holds at all of them that are (`SetHook.union_eqn`).
  The premise is on hooked functions' equations only.
  A generated function is defined by its equations (§2, "Functions"), so each of them holds at every carrier value, well formed or not, and a premise would only weaken a theorem that is true without it (and add a side condition to every rewrite with it, such as the invariant tactic's unfolding).
  A `List` carrier is isomorphic to `List E` (`ListIso`): every value is a K list, so a list variable gets no premise.
  Simplification rules (`Simp.*`) get none either, although the same reasoning applies to those about hooks: none of the gate's libraries states one over a set or map variable, and of KEVM's 22 such rules 3 are proved without it, so the premise is added where a rule is shown to need it, not by default.
  A cascade that matches an injected variable (`inj_Val_Exp K0` against a pattern of another subsort) reduces after a case split on the variable (`k2l_case_inj`).
  A right-hand side's partial calls (hooks and K functions, whose results are `Option`s) are bound by the definition's cascade with a `match` on each call's value and by the statement with `Option.bind`, so both sides are functions of those values: the last generic attempt (`k2l_eqn_c`), and the case loop of `k2l_eqn_r`, case on each such call that a `match` inspects (`k2l_case_call`), generalized in the goal and the hypotheses, after which both sides reduce.
  A recursive call whose argument is an earlier call's value (`popcount(N >>Int 1)` in `demos/k/term`) is cased on once the case on that call has made it closed; two partial calls in one right-hand side (`popcounts(M, N) => popcount(M) +Int popcount(N)`, `topBoth` of `demos/k/kimp-inv/imp-both.k`) are cased on in turn.
  A list pattern of the left-hand side (`ListItem(I) L`, `L ListItem(X)`, `ListItem(X) L ListItem(Y)`, `ListItem(X)`, `.List`) is a term built from `ListHook.concat`, `element` and `unit`, while the definition takes its argument apart with `ListHook.uncons` and `unsnoc` and tests it against `.List`; none of these is a constructor, so the cascade does not reduce by unfolding.
  Their values on such a term follow from the list model (`KPrelude.Ext`: `uncons_concat`, `unsnoc_concat`, `uncons_element`, `concat_eq_unit_iff`, …), and the first step of `k2l_eqn_r`'s case loop, `k2l_case_list`, uses them: it splits each `match` on `uncons` or `unsnoc` of such a term and decides each case by that value (the pattern's variables get the statement's, the other case is refuted), and decides each test against `.List`.
  Without it, `k2l_case_call` took such a `match` for one on a partial call and cased on its value as an unknown, after which the pattern's variables were unrelated to the statement's and no case closed (`listIn` of `demos/k/simple-inv/simple-envs.k`; `allPos`, `ends`, `total` and `twice` of `demos/k/term`).
  The equation of an `owise` rule (and of a rule tried after others) has a variable where the others have patterns, and one premise per rule tried before it, `∀ xs, x = p → c = true → False`: that rule's pattern does not match, or its `requires` is false.
  Its last proof attempt, `k2l_eqn_o`, unfolds the function and reduces the cascade as `k2l_eqn_r` does; a list variable that the cascade takes apart is split into `.List` or a list with a first (last) element (`ListHook.cases_front`, `cases_back`), substituted for the variable (`k2l_case_lvar`), after which `k2l_case_list` decides the cascade's matches.
  A case where another rule's arm applies is refuted by that rule's premise (`k2l_owise_arm`): the arm has built the argument as the pattern describes it, so the premise's equations hold by reflexivity once both sides' concatenations are normalized (`concat_assoc` and the unit laws; `ListItem(X) ListItem(Y) L` is written left-nested, and the arm builds it right-nested), and its `requires` holds by the case's own hypothesis (`k2l_no_arm`).
  The other cases reduce to the `owise` value.
  In `demos/k/term`: `sumPairs`, `lastSum`, `edgeSum` (front, back, both ends) and `headOr` (not recursive, a second argument in its pattern); `width`'s `owise`, after a rule with a `requires` only, closes the same way.
  An alias in the other rule's pattern (`I:Int` at a `KItem` argument is `\and(inj(I), X)`) is its term, as in the equation's own arguments (`strip_as`): `x = inj I` (`demos/k/term`'s `itemOr`).
  A pattern with partial calls in the other rule (a free-key map pattern `(K |-> V) R`, whose `_Map_` is undefined on overlapping keys) matches `x` when it is defined and is `x`: the premise is `∀ K V R, (K |-> V) R = some x → c = true → False`, and for two free keys in one pattern, `((K₁ |-> V₁) (K₂ |-> V₂)).bind (· R) = some x` (the pattern is left-nested).
  The definition's matcher of such a rule is `MapHook.chooseFirst`; where it finds a binding, `k2l_case_choose` takes it (`chooseFirst_eq_some`) with its decomposition `(k |-> v) (remove m k) = some m`, which instantiates the premise; a second free key's decomposition is of the first one's rest, and the two give the left-nested pattern by associativity of `_Map_` where defined (`MapHook.concat_bind_of_concat`, from `SAL.concat_assoc_left`), which `k2l_no_arm` applies when no hypothesis is the premise itself.
  The equation of the free-key rule itself is not stated (below); the `owise` one is, since its argument is a variable (`freekey`'s `hasNeg`, `twoPos`).
  An equation the tactics do not prove is listed in `open-obligations.txt` and emitted as a statement: it is never assumed, never proved with `sorry`, and never under the axiom guard.
  `k2lean open-from-log Equations.lean BUILD.log open-obligations.txt` adds the theorems whose proofs failed in a Lake build log; for an `Equations.lean` written in parts it reads the errors of every part the file imports, and an error Lean reports at the first line of a declaration (its doc comment: a proof out of heartbeats) counts for the theorem that line opens.
  The generated lakefile passes Lean `-DmaxErrors=0` (`weakLeanArgs`: it changes what is reported, not what is built), so a build log names every failed proof of a module, not only its first 100, and one round finds them all (a module with 161 failed proofs: 161 listed, against 101 with Lean's default limit of 100).
- The axiom guard (`#k2l_assert_axioms`, `KPrelude.Tactic`) fails the build when a guarded theorem depends on `sorryAx` or on any axiom other than `propext`, `Classical.choice` and `Quot.sound`; the prelude declares no axiom.
- Test data from krust runs compares the model with krust's executions: `k2lean goldens` (initial configurations by `krust krun --depth 0`, expected finals recorded from kimp, and step traces against krust and K's LLVM backend), `k2lean cases` (SIMPLE's tests, krust's final configurations, with search) and `k2lean configs` (benchmark programs).
- `k2lean claims` states K reachability claims (`claim` sentences of a `--for-proving` definition) as Lean propositions over `Step` (`KClaims`, `lean/claims`), proves those its tactic can, and lists the others for hand proofs; `k2lean claims replay` turns a proof that `krust kore-rpc` explores into a Lean script of named steps.
- `k2lean relate` pairs the rules and symbols of two definitions of one language and generates the translation and, when every rule pairs, a bisimulation proof (`demos/ImpRel`).
- `k2lean soundness` generates the type soundness of a semantics for a type checker written in K, but for the store typing and the rules that read or write the store (§3.3, `demos/ImpTypes`).

### 3.1 Determinism along the rule index

One `cases h₁ <;> cases h₂` proves determinism over every pair of rules, quadratic in their number (KEVM's 597 rules of one rank: 356,409 inversions); `gen --det-pairs` keeps that proof for the per-sort encoding.
By default (`crates/k2lean/src/det2.rs`; `--det2` is still accepted and changes nothing, and the arity universe ignores `--det-pairs`) the proof goes along the structure the index already has:

- the first item of the `<k>` cell, as an enumeration `Det.Key`, splits each rank's relation (`Det.split{i}`, one linear `cases`), and each rule's lemma `Rules.r.det` inverts only its key's relation and that of the rules without a key (KEVM: 137 keys, the largest group 108 rules, 9 rules without a key, 36,512 inversions);
- a pair classifier (`crates/k2lean/src/pairs.rs`: the KORE left-hand sides unified with sorts, the requires under the unifier by the definition's equations, the builtin hooks, complementary atoms, `z3` and finite case splits) chooses one certificate per goal that survives the inversion (`k2l_case`, with the closers of `KPrelude.Determinism`, which read a decided hook `decide p = true` as `p` whatever `Decidable` instance the term carries: a `simp` that rewrites the hook's arguments rewrites them in `p` but not in the instance, and on Lean v4.34.0 `decide_eq_true_eq` applies only when the term's instance is reducibly the one it synthesizes); it is untrusted, a failed certificate is reported and its goal goes to the default closers, and the kernel checks every proof;
- the pairs it cannot separate are the definition's own overlaps: `overlaps` lists them, `noOverlap c` decides that no listed pair applies with both rules, and the theorems are `Step.deterministic_of (h : noOverlap c = true)`, `step_complete_of` and `step_iff_of_noOverlap` (with no overlap, `Step.deterministic`, `step_complete` and `step_iff`);
- each listed pair is witnessed: `overlap_witness_k : Overlap.Witnessed Step ⟨r, p⟩` gives a configuration, built by the classifier from its unifier and a `z3` model, at which both rules step, to different configurations, and both steps are steps of `Step` (no rule of a higher rank applies); a pair whose results coincide there is joinable and not listed; with every pair witnessed, `overlaps_witnessed : ∀ o ∈ overlaps, o.Witnessed Step` says that the list is exactly the definition's nondeterminism, and the axiom guard checks it (otherwise it checks each `overlap_witness_k`);
- a witness's map cells are chosen by the search: a lookup `M[K] orDefault D` stuck on an unknown map (a variable, or bindings with a variable rest) gives `K` either one of the keys bound so far or a new binding `K |-> V`, with the variables of `K` given small values different from the other keys (`ty(0)`, `ty(1)`) and `V` a variable of the sort of `D`, which the search then refines like any other variable (the cases of its constructors, a `z3` model), and the rest becomes the empty map; so a configuration whose rules read a table (KMIR's `<types>`) gets the entries its two rules need, and nothing else is assumed of the table (the gate's `ovl`: `look(A, B)` overlaps where the table binds `A` and `B` to `wrap(A)`, witnessed by `ty(0) |-> wrap(ty(0))`);
- each fact of a witness (`Det.wk_a`, `Det.wk_b`, `Det.wk_ne`, `Det.wk_sj` for the higher ranks) is its own theorem (in a module whose heartbeat bound is five times the lemma modules': KEVM's fact that no higher-priority rule applies at its witness 0 takes 496,000), proved by `k2l_decide`: the kernel's evaluation of its `Decidable` instance, and, where that is stuck at a definition by well-founded recursion (the kernel reduces it only through the accessibility proof of its measure), an evaluation in the elaborator (`DetEval`) that unfolds such a call by its unfolding equation, or evaluates it in the kernel as the iteration `fuel N` of its functional (`fuel n := Nat.rec f (fun _ g => F g) n`, equal to `f` by induction), hands to the kernel every argument that reaches no such definition, rewrites the evaluated subterms by `Eq.rec`, and compares the two values field by field; the proofs use Lean's three axioms only;
- a `Bytes` value of a witness is written as the list of its bytes (`List.replicate` for runs), not through a `String` literal: the kernel decodes a literal's UTF-8 bytes in time quadratic in its length (100 characters in 0.84 s, 400 in 9.9 s), and a list in linear time (the length of 49,153 bytes in 5.7 s); a witness holding a `String` or token literal longer than 256 characters (`--det2-long-literal N`) is reported and not checked, a bound on the cost of the check, not a failed proof;
- a `Bytes` value has its own bound, 131,072 bytes (`--det2-long-bytes N`): with the structural equality of terms (§2.1) the kernel compares two byte lists in time and memory linear in their length, but the memory grows by 18 to 26 KiB per byte (`==` at 2^16 bytes: 4.6 s and 1.7 GB; at 2^18: 21 s and 5.3 GB on equal lists, 26 s and 7.4 GB on lists that differ at the end; 2026-10-25, Lean v4.34.0, load 13 to 15), so the bound keeps one comparison near 15 s and 4 GB (interpolated) and the facts of one witness to tens of seconds, and a larger value is reported rather than exhausting the build's memory; a `String` literal keeps the lower bound because the kernel still encodes it in time quadratic in its length, and a string hook may decode it by well-founded recursion;
- an unwitnessed pair stays in `overlaps`: `Step.deterministic_of` assumes it apart, as it does every listed pair, so the statement stays sound, and only the claim that the list is exact (`overlaps_witnessed`) is not stated; the axiom guard then checks each `overlap_witness_k` that is stated;
- the determinism theorems have their own axiom guard, `NSTest/DetAxioms.lean`, which imports `NS.Determinism` and what that imports, not `NS.Equations` or `NS.Preserves`; the library's guard `NSTest.Axioms` imports it, and KEVM's determinism is checked with it without building KEVM's `Equations`, which builds only in parts and with open obligations (§9; `pipelines/kevm.sh det` builds the guard last).

### 3.2 Relating two definitions (`relate`)

`k2lean relate` reads the compiled KORE of two definitions `A` and `B` of one language, each generated into its own library, and pairs them:

- a constructor of `A` with the constructor of `B` of the same KORE symbol, else of the same result and argument sorts and the same concrete syntax (the `format` attribute of `syntaxDefinition.kore`), a strictness freezer with the freezer of its symbol's counterpart; this gives the translation `tr : A → B` on every sort of `A`'s term universe;
- a rule of `A` with the rule of `B` whose KORE axiom is the same after renaming symbols and variables, or of which `B`'s is an instance at a subsort of some variables (a refinement); a KORE axiom is one rule per overload variant, in the same order on both sides, and the variants correspond one to one.

When every rule of `A` pairs, it states and proves `bisim : Bisimulation A.Step B.Step R` with `R c d := Inv c ∧ d = tr c`, and `app_iff` (a rule applies in one exactly when its counterpart applies in the other), `stepsN_iff`, `terminal_iff` and `run_agree`; each simulation is one case per rule, by generic tactics.

- **Priorities.** A step of rank `i` holds only where no rule of a higher rank applies (`hpri : ∀ j < i, ¬ App j c`, §2).
  A pair of rules must be of the same rank (otherwise the bisimulation is not stated); then `hpri` of one side follows from the other's through `app_bwd` and `app_fwd`, rank by rank, so the statement respects priorities exactly.
- **The order of map keys.** A map value is canonical: its bindings sorted by its library's order on keys, which compares serializations whose tags are constructor positions, and positions come from symbol names.
  A pointwise translation of a sorted map is sorted again exactly when it preserves the order of the keys involved, so this is what decides how maps are related.
  - *Every position kept* (the two libraries order each sort's constructors alike, as for two versions of a definition whose renamed symbols keep their place): `ser (tr a) = ser a` for every term (`ser_tr_*`, by structural induction), so `tr` preserves the order of every key (`SAL.Pres`) and commutes with every collection operation without a hypothesis (`MapHook.concat_pointwise` and the rest, `KPrelude.Relate`); `Inv` is `True`.
    Map patterns with a free key (a rule matching any binding: the thread cell map of SIMPLE) are inverted through the translated map's bindings (`concat_element_pointwise_inv_free`), and typed cell maps are collection sorts like any other.
  - *A constructor moves* (the KRS IMP port numbers constructors its own way): `Inv` restricts the keys of the configuration's map cells, at depth one, to injections of builtin and token sorts, on which the translation preserves the order; free-key map patterns, priority ranks, typed cell maps and keys of other sorts are refused in this case, since a key invariant would have to hold of every map anywhere in the configuration (inside computations and stacks too), which is not generated.
- **Functions.** Each function the rules call commutes with `tr` (`comm_fn_*`, in the `k2l_rel` simp set): a non-recursive one by unfolding both definitions; a recursive one by the same well-founded recursion as its definition: the lemma unfolds both definitions once, splits the two cascades in step (its parameters generalized first, so that each split leaves the equation `x = pattern` its termination proof reads), and rewrites `B`'s recursive calls by itself, with `A`'s termination measure or Lean's search (with `A`'s termination tactics); a mutual group together.
  A call on the result of another call (SIMPLE's `V[N1][N2, Vs]`) is a translation only once the inner call's value is identified, so the rewriting goes in rounds; a case where one cascade falls through a pattern that the other's translated scrutinee matches is refuted (`solve_by_elim` instantiates the negated pattern with the translation).
  A function with a free-key equation (`MapHook.chooseFirst`, §2) commutes with a translation that keeps every constructor's position, and needs no agreement of its instances: `chooseFirst` finds the first binding in the map's order, and the translation of a canonical map keeps its bindings in that order (`MapHook.chooseFirst_pointwise`), so the lemma rewrites the two free-key equations at once (`MapHook.dite_chooseFirst_pointwise`, by `k2l_choose`, the maps related by `tr`'s commutation with `remove`) and compares the two continuations binding by binding (a nested free-key equation by the same step).
  A recursive function with a free-key equation, one whose result is not builtin, or any under a translation that moves a constructor, gets no lemma, and `relate` refuses the bisimulation; for a translation that moves a constructor, the first binding would have to be the same in both maps' orders, which is where the instances' agreement (`F.Agrees`, §2) would come in.

The light gate builds three self-relations of the generator's fixtures under two namespaces: `demos/PeanoRel` (an `owise` priority, recursive and mutual functions) and `demos/CellMapRel` (a free-key rule over a typed cell map), 5 s each once their libraries' `Rules` are built (2026-10-24, Lean v4.30.0), and `demos/PickRel` (three functions with free-key equations, one with two free keys, one partial, and a free-key rule), 46 s wall for its module in the arity universe (the default), against 3.5 s wall and 5 s of CPU in the per-sort one (2026-10-25, Lean v4.34.0, load 13 to 23; where the arity proofs spend it is not measured).
SIMPLE against a variant of it (`tests/simple-variant.py`: three constructors under other symbols, the rules in another order; `demos/SimpleRel`, `pipelines/simple-rel.sh`) is generated, 226 symbols and 169 rule pairs in 0.2 s, and builds with `--split true` (one module per simulation, the backward cases as one lemma per rule) outside the gate tiers; §9 has the measurements.

In the arity universe (the default: both libraries generated by `gen` without `--per-sort-terms`, §2.1) the translation is one function `tr : {s : A.Tag} → A.Term s → TrTy s`, by structural recursion on `A`'s family, where the motive `TrTy s` is `B.Term s` on the tags it translates (the covered sorts and the builtin carriers) and `Unit` elsewhere; each family constructor is rebuilt by a builder per arity (`mkK`, a match on the sort and its enumeration) and a leaf injection by `mkInj` (the same leaf of `B`'s sort), and the per-sort names `tr_S` are `tr` at sort `S`, with their equations `k2l_tr`, so the statements above read as on the per-sort encoding and none of them changes.
On the family, `ser` writes a constructor's position in its enumeration, a leaf injection's leaf tag by its position in `Tag` and a collection by its position among the collection sorts; `ser (tr a) = ser a` is one theorem by structural recursion on `A`'s family, with the per-sort statements as its instances.
Case splits on a family variable use `k2l_cases` (`KPrelude.FamilyCases`), which refutes the family's constructors that no value of the sort has.
`relate --per-sort-terms true` relates two libraries generated with `gen --per-sort-terms` (the holdouts of §2.1); `--arity-terms true`, the former opt-in, changes nothing.

### 3.3 Type soundness (`soundness`)

`k2lean soundness` generates the part of a type-soundness proof that follows from two K definitions: a semantics `A`, and a type checker `B` written as a second K definition over `A`'s syntax (`demos/k/imp-typing.k`), each generated into its own library, with the translation of programs `tr : A → B` that `relate --roots` writes.
The checker's typing functions (`--typing typeOf,wt`) each take a term of a syntax sort and a typing environment `G`; those that return a type return one of an enumeration sort, and exactly one returns a `Bool` and accepts programs.
The cells whose typing is specific to the language (`--store-cell env`) are typed by hand, by a predicate on their content (`--store-typing envTy`).
The theorem, for kimp (`demos/ImpTypes`):

```lean
theorem soundness {G : TEnv} {P : KImp.SortStmt} {E : KImp.SortMap} {g : KImp.SortGeneratedCounterCell}
    (hP : KImpTypes.K.«wt(_,_)_IMP-TYPING_Bool_Stmt_Map» (tr_SortStmt P) G = some true) (hE : envTy G E)
    {n : Nat} {c : KImp.SortGeneratedTopCell} (h : StepsN KImp.Step n (init P E g) c) :
    Final c ∨ KImp.App c
```

`App c` says that some rule applies at `c` with a true side condition: a step, or a step whose result is undefined (`x / 0`); so the theorem excludes stuck configurations, not undefined results.
`Final c` says that `<k>` is empty, and `init P E g` is the configuration whose `<k>` holds `P`, whose store cell holds `E` and whose other cells are parameters.

The generator writes two modules around one hand-written module:

- `Typing.lean`, before the hand module:
  - the typing functions at `A`'s terms, `typeOf G e := B.typeOf (tr e) G`;
  - one inversion lemma per equation of a typing function whose first argument is a constructor applied to variables (or an injected variable) and whose environment is a variable, such as `typeOf G (e₁ + e₂) = match typeOf G e₁, typeOf G e₂ with | some r, some r_1 => if r = int ∧ r_1 = int then some int else none | _, _ => none`.
    The right-hand side is the equation read in the model: a call in the `requires` clause that is undefined makes the equation inapplicable, so the function takes its `owise` value, or is undefined when it has none; a call in the right-hand side that is undefined makes the result undefined; `==K` of two values of one sort is their equality (`KEqHook.eq` is `decide (a = b)`).
    Each lemma is proved by unfolding the generated definition once and casing on the calls' values, so a lemma that does not hold fails the build.
    An equation that another non-`owise` equation could also match, or whose environment is a pattern (`typeOf(X, X |-> T _)`), gets no lemma, and the function stays opaque at that constructor (the store typing speaks of it);
  - `plug f e`, from each cooling rule `HOLE ~> f(args) => item` (a rule whose `<k>` is the hole followed by the freezer on the left and an item on the right, every other cell unchanged): the item with `e` for the hole and the freezer's arguments projected to their sorts;
  - the stack typing: `item0 G it` is what an item leaves for the next one (the type of a term, or nothing for an accepted statement), `item G (some t) (inj_KItem f)` types the freezer `f` as the item that cooling makes of it and a value of type `t` (`dflt t`, built from the checker's equation at a value sort, `typeOf(_:Int, _) => int`), and `kty` threads these along `<k>`, with nothing left at the end.
    It is a definition, so it cannot be unsound; that it is the right typing is what preservation checks rule by rule: heating and cooling keep it by computation, because the checker's equations look only at the types of subterms, so a value and the placeholder of its type are typed alike;
  - `WTc St G c`: `kty G none (kOf c) = true`, and `St G` of the content of each store cell, where the store typing `St` is a parameter (the hand cases are stated against `WTc`, so it cannot name a definition of the hand module);
  - `Progress.Case.r St`, for each rule `r` that reads a store cell (a pattern on it, or a side condition on its content): every well-typed configuration with `r`'s head of `<k>` has a rule that applies;
  - every lemma that computes the typing is `@[k2l_pres]`, the unfolding set of `k2l_preserve`.
- The hand module (`--hand-module`, default `NS.Store`): the store typings, the preservation case `hand.r : A.Step.Case.r (WTc envTy G)` of each rule that reads or writes a store cell, and the progress case `hand.progress.r : Progress.Case.r envTy` of each rule that reads one.
- `Soundness.lean`, after the hand module: `preserved` by `k2l_preserve split [typeOf, wt] hand NS.hand`, which takes each rule's case from the hand module when it has one; `progress` by cases on the head of `<k>`, read off the term universe (a value, a leaf of `KResult`, followed by a freezer; a typed term, with its operands cased on whether they are values; the head of a store-reading rule, by its hand case), each leaf closed by `k2l_ctor_search` among the constructors of `App`; and `soundness` from `progress`, `preservation` and the typing of `init`.

On kimp and `imp-typing.k` (measured 2026-10-25 on the shared 32-CPU host): generation takes 0.1 s; `Typing.lean` is 293 lines (23 inversion lemmas, 26 cases of `plug`) and builds in 4.8 s at a load of about 40; `Soundness.lean` is 108 lines and builds in 151 s wall and 2.5 GB at a load of about 80 (93 s at about 35); the hand module `Store.lean` is 100 lines, 64 of them Lean code (the hand-written proof it replaces was 674 lines in five modules).
On the arity universe, the default of `soundness` since 2026-10-27 (`--per-sort-terms true` writes the per-sort proofs), the theorems are the same and the proofs split the family. `k2l_cases` and the splits of `KPrelude.Soundness` take `familyCases`' cases, with a variable's sort index computed first. The lemmas of `kty`, which is well-founded on the family, are proved by `simp only [kty]`, and `item` and `item0` are computed by one `rfl` lemma per leaf.
Measured on 2026-10-28 (Lean v4.34.0, each file elaborated alone, twice in turn, load 13 to 54), ImpTypes' `Soundness.lean` takes 40 s wall, 40 to 41 CPU-s and 3.7 GB peak; ExprTypes' takes 17 to 18 s and 2.6 GB.
The splits run `familyCases` in the goal's whole context; its refutations need no search over the context (§2.1). Until 2026-10-28 they reverted every hypothesis the variable's type does not depend on first (`familyCasesAlone`), which saved `contradiction`'s search over that context while `familyCases` used it; measured back to back on the two files above, it no longer saves time, and it is gone.
The typing of an ill-typed shape computes to `false = true`, which `ty_simp` rewrites to `False` (`Bool.false_eq_true`), closing the goal `typing → App c` (`false_implies`); so each shape is normalized once, and a well-typed shape keeps that normal form for the case analysis after it.
Until 2026-10-25 `ty_simp` lacked those two lemmas, and every shape fell back to a full `simp` of the typing (measured: 204 fallback calls, 9.8 s of `simp` alone, most of them failing on well-typed shapes).
Progress alone, run three times in turn on one tree (2026-10-25, Lean v4.34.0, load 11 to 18): 22 to 27 s wall and 50 to 64 s of CPU, against 34 to 40 s and 90 to 105 s before the change, and 43 to 47 s and 43 to 48 s for the hand-written progress the generated one replaced (single-threaded); the remaining CPU over the hand-written one comes from computing the typing of values through the inversion lemmas and splitting on `Option Bool` where the hand-written proof used `Bool`.
Compared with that proof, `soundness` has the same statement; `WTc G` became `WTc envTy G` (the store typing is a parameter), and the hand-written `tyOf`, `wtS : … → Bool` became `typeOf`, `wt : … → Option Bool`, so `preservation` is stated over `WTc envTy G`.
The case splits are prelude tactics (`KPrelude.Soundness`: `k2l_cases_apps`, `k2l_cases_args`, `k2l_cases_bools`, `k2l_cases_frz`, `k2l_cases_typing`) whose arguments are the library's constants; `Soundness.lean` instantiates them in a few macros.
It is a command of its own rather than an option of `relate`: it reads the checker's equations and the semantics' rules and writes two modules around a hand module, while `relate --roots` stays the translation.

**Programs that end with a value** (`demos/ExprTypes`: kimp's expression language `expr.k`, whose configuration is `<k> $PGM:Expr </k>`, against the checker `k/expr-typing.k`).
With no Bool-valued typing function (`--typing typeOf`), the one type-returning function accepts programs, and the theorem assumes `typeOf (tr P) G = some t`.
A program then ends with its value on `<k>`, so `kty` accepts what the last item leaves (`kty G i .dotk = true`: the type of the program, of a subterm being evaluated, or of a value), and `Final c` holds when `<k>` is empty or is one value (a leaf of `KResult`) followed by nothing; `progress` proves that case `Final` and every other case `App` (`progress_app`).
With no `--store-cell`, `WTc G c` is the typing of `<k>` alone and the hand module is empty.
With a Bool-valued function, all of it is as above (ImpTypes generates as before).
On EXPR (2026-10-25, Lean v4.34.0): 16 inversion lemmas, 24 cases of `plug`, `k2l_preserve` 66 of 66 rules, and `Soundness.lean` builds in about 20 s; nothing is written by hand.
Not supported (the command stops with a message): rules of several priorities; a top cell whose children are not leaf cells; holes of several sorts; types that are not an enumeration; typing functions that are not `Option`-valued or take other than a term and an environment; a store-reading rule whose head of `<k>` is not a `KItem` injection of variables, or two such rules with one head.

**Shapes beyond the supported ones**, in the order a typed SIMPLE would meet them (SND-3; none built).
Each says what the statement would become and what obligation it adds.

1. *A checker written as rewrite rules.* SIMPLE's type system (`pl-tutorial/2_languages/1_simple/2_typed/1_static/simple-typed-static.md`) computes types on `<k>`, with typing tasks in a `<tasks>` cell (each function body typed in a task of its own) and types as `KResult`s; `soundness` reads typing functions.
   The direct route is a checker written as functions (`typeOf(Exp, Map)`, and `wt(Stmt, Map, Type)` with the enclosing function's return type, item 4), which also makes the checker's results equations of `gen` rather than outcomes of a run.
   Relating the two runs (the static semantics' run accepts, so the dynamic one does not get stuck) would be a different theorem: a simulation between two semantics, of `refine`'s kind (§3.5).
2. *A top cell whose children are not leaf cells, and a thread cell map* (every SIMPLE configuration: `<T>`, `<threads>`, `<thread>*`, `<env>` per thread, a shared `<store>`).
   `WTc` quantifies over threads: each thread's `<k>` typed by `kty` under its environment's typing, and the store typed once; `Final c` holds when every thread's `<k>` is empty or one value.
   A thread whose head is a synchronization (`acquire`, `join`, `rendezvous`) can have no rule, legitimately, so the statement becomes `Final c ∨ App c ∨ Blocked c`, with `Blocked c` stating that every thread not final is at a synchronization whose condition is false.
   The obligations added: for each synchronization rule, a hand progress case (its head with the condition true has the rule apply, as store-reading rules have); and preservation of a per-thread typing over the thread cell map, whose cases have the element-wise shape of INV-2's walks (`invariants.md`, §3).
3. *Types that are not an enumeration* (`Types -> Type`, `Type[]`).
   `Ty` becomes the checker's sort of types, as terms with a decidable equality (generated), and `kty` stays computable.
   `dflt t`, the placeholder value of type `t`, does not exist for every type: a function type has lambdas, but an array type's values are locations, typed only through the store typing.
   So the freezer typing quantifies over the values of the hole's type instead (`item G (some t) f` holds when `item0 G (plug f v)` does for every `v` of type `t`), `kty` becomes a proposition, and preservation needs, per freezer, a lemma that the plugged item's typing depends only on the value's type: what is now computed ("a value and the placeholder of its type are typed alike") is then stated and proved.
4. *Typing functions with other arguments than a term and an environment* (SIMPLE's statements need the return type), or that are total.
   The environment generalizes to a structure of the extra arguments, as long as no rule changes them; a total typing function is the `Option`-valued one composed with `some`.
5. *Holes of several sorts* (SIMPLE's calls and `print` evaluate `Exps`, lists of expressions).
   The pending typing becomes `Option (HoleSort × Ty)` (a list of values is typed by `Types`), with one `plug` per hole sort, and the obligation of item 3 per hole sort.
6. *A store-reading rule whose head is not a `KItem` injection of variables, or two such rules with one head* (SIMPLE reads a variable through `<env>` and then `<store>`, and `++X` and `X = V` read its location through `lvalue`).
   The hand progress case is keyed by the rule rather than by the head: the head is cased like the other leaves, and the hand case receives the case's shape.
7. *Rules of several priorities* (none in SIMPLE).
   A lower-priority rule's `Step` constructor carries the premise that no rule of a higher priority applies.
   The statements stay as they are: `App c` is "some rule applies", and one generic lemma turns an applicable rule into a step by the highest-priority applicable one; preservation ignores the extra premise.

### 3.5 Refinement: a stuttering bisimulation (`refine`)

Two definitions of one language can take steps of different granularity: a rule split in two, a loop that unrolls in one step less.
`R` is a stuttering simulation of `A` by `B` with measure `μ` (`StutterSim`) when a step `c → c'` of `A` from a state related to `d` is matched by one or more steps of `B` to a state related to `c'`, or by none, with `c'` still related to `d` and `μ c' < μ c`; a stuttering bisimulation (`StutterBisim`) is one in each direction, with measures `μ` and `ν`.
It transfers terminating runs (`StutterBisim.terminal_run`): a run of `A` to a terminal state is matched by a run of `B` from a related state to a terminal state related to it, because at a state related to a terminal state of `A`, `B` can only stutter, and `ν` bounds that.

`k2lean refine` takes the correspondence of `relate --per-rule true`: the translation `tr`, and for each pair of rules with the same KORE axiom up to renaming, the lemmas `fwd.r` (a step of `A` by `r` translates to a step of `B` by its counterpart) and `bwd.r` (a step of `B` from a translation is the translation of a step of `A`), proved as the arms of `relate`'s simulations are (§3.2; an order-preserving translation, no priority ranks).
The relation is `Stutter.Rel tr X c d := d = tr c ∨ X c d`: the translation where the steps correspond, and the non-local part `X` that the hand module defines where they do not.
Each rule's case in each direction is split in two parts (`Stutter.fwdQ_of`, `bwdQ_of`):

- at a translation (`fwd_tr r`, `bwd_tr r`): one step of the other side and the translation again, from `fwd.r` or `bwd.r`, when `r` has a counterpart;
- at a state `X` relates (`fwd_x r`, `bwd_x r`): refuted by `cases` on `X`, which closes when the rule's left-hand side and `X`'s indices clash on a constructor.
  So `X` is an inductive predicate whose `B` side is a pattern of `B`'s constructors over variables, each equated to the translation of `A`'s: `cases` then never has to invert a translation.

The parts the generator cannot write are listed in an open list (`--open`, `KIND RULE` per line) and taken from the hand module (`hand.fwd_tr.r : A.Step.Rel.r (Stutter.FwdTr …)` and so on); a generic part that does not close is a build error, so the list is exactly the hand cases.
The output module proves `bisim : StutterBisim A.Step B.Step (Stutter.Rel tr X) μ ν`, `run_fwd` and `run_bwd`.

`demos/ImpUnroll` relates kimp to a variant whose `while` rewrites straight to the two-armed `if (C) {…} else {}` (`tests/kimp-unroll.py`), so kimp takes two steps (`while`, `if-else`) where the variant takes one.
78 of 79 rules pair, and all 316 case parts are generated, with no hand module (`--hand-module none`, 2026-10-28; before, a hand module supplied `X`, the measures and 6 parts).
`refine` finds the step of `B` that `A` takes in two (`find_splits`): an unpaired rule `b` of `B` and an unpaired rule `a1` of `A` with the same left-hand side up to renaming, and a rule `a2` of `A` whose left-hand side matches `a1`'s right-hand side, with `a2`'s right-hand side then `b`'s (kimp's `while` and `if-else` against the variant's `while`; the rules of a split have no side conditions).
From it, it generates `X` (one constructor: `A` after `a1`, `B` after `b`, over `A`'s variables and their translations), `X_inv`, `μ` (1 after `a1`, where `A` stutters), `ν = 0`, and the parts that need `X`'s constructor: `fwd_tr a1` (`b`, into `X`), `fwd_x a2` (`A` catches up, `μ` decreases), `bwd_tr b` (`a1` then `a2`), and `bwd_x r` for each paired step of `B` at an `X` state (`A` takes `a2`, then `r`'s counterpart; on ImpUnroll the variant's `if-true`, `if-false` and condition heating).
The mirror, `B` taking in two a step of `A`, and splits into more than two steps or with side conditions, are still hand-written.
`Run.lean` derives that two runs to terminal states end in translations of each other, since `X` never relates a terminal state of kimp.

**Priorities and moved constructors (design, not implemented; REL-5).**
`refine` takes today only an order-preserving translation without priority ranks; both restrictions can be lifted without changing `Stutter.Rel`'s shape, at the cost of the obligations below.

- *A constructor moves.* `relate`'s relation is then `Inv c ∧ d = tr c`, with `inv_step` (generated, by `k2l_preserve`) and simulation arms that take `hi : Inv c`.
  Refinement would use `Stutter.Rel tr X c d := (Inv c ∧ d = tr c) ∨ X c d`: the parts at a translation (`fwd_tr`, `bwd_tr`) take `Inv c` from the left disjunct, pass it to `relate`'s per-rule lemmas, and re-establish it at the target by `inv_step`.
  One obligation is added: a part that leaves `X` at a translation owes `Inv` there; requiring `X.inv : X c d → Inv c` of the hand module (an `X` state's `A` side satisfies the key invariant) lets the generated parts derive it by `inv_step`, so only that lemma is new.
  The restrictions of `relate`'s key-invariant regime (no free-key patterns, ranks or typed cell maps) carry over unchanged.
- *Priority ranks.* A step of rank `i` carries `hpri : ∀ j < i, ¬ App j c`.
  In `fwd_tr`, `B`'s step at `tr c` needs `∀ j < i, ¬ B.App j (tr c)`, that is `B.App j (tr c) → A.App j c`; `relate` proves it as `app_bwd` only when every rule pairs.
  With unpaired rules (why `refine` exists), it holds rank by rank for the ranks whose `B` rules all pair, and for a rank `j` with an unpaired `B` rule `r` it needs `app_bwd.r : B.App_r (tr c) → A.App j c` (by hand, or generated when `r`'s left-hand side clashes with every translation); `bwd_tr` needs `app_fwd.r` for the unpaired `A` rules symmetrically.
  Steps of the other side at `X` states are the hand parts, which carry their own `hpri`; a stutter takes no step and needs none.
  So the obligations added are one `app_bwd.r` per unpaired `B` rule and one `app_fwd.r` per unpaired `A` rule whose rank has priority over that of some paired rule (`hpri` of a step of rank `i` quantifies over the ranks `j < i`); none when the unpaired rules are all of the last rank.
- *Generating `X`.* Done for `A` taking one of `B`'s steps in two, the rules without side conditions (`--hand-module none`, above): `X` has one constructor, its `B` side a pattern of `B`'s constructors over translated variables, `μ` is 1 at an `X` state's `A` side, `ν = 0`, and the parts are generic.
  The mirror (`B` split in two) swaps the roles and is not generated yet, nor are side conditions on the split's rules (their hypotheses would be fields of `X`'s constructor) or several splits (one constructor each, and `X_inv` a disjunction).
  Other shapes (a step that skips several states, an unrolling by a varying number of steps) stay hand-written.

### 3.6 Confluence modulo scheduling (`confluence`)

The statement, for a program hypothesis `H` (a predicate with `H.preserved : Preserved Step H`, from the hand module) and an observation `obs` (the cells `--obs` names): two runs from a configuration satisfying `H` that end in terminal configurations end in the same one (`terminal_unique`), so they observe the same `obs` (`obs_confluent`).
Equality is the instance `E = Eq` of the prelude's theorems, which hold modulo any equivalence `E` that is a strong bisimulation of `Step` with itself (`StepEquiv`), for definitions whose finals differ in unobserved cells.
It follows from the diamond property modulo `E` (`DiamondMod`: two steps from one state join in at most one step each; `terminal_unique_of_diamond`, by the strip lemma, with no termination hypothesis) or, with `--join local`, from local confluence (`JoinMod`) and a measure every step from `H` decreases (Newman's lemma, `terminal_unique_of_local`; the hand module supplies `μ` and `μ_dec`).
The joins are one obligation per ordered pair of rules, `pair.r₁.r₂ : Step.Rel.r₁ (fun c c₁ => Step.Rel.r₂ (fun c' c₂ => c' = c → H c → DiamondMod Step Eq c₁ c₂))`, attempted in order by:

- refutation: the two left-hand sides do not unify (`cases` on `c' = c`);
- one instance: the same rule at the same match gives the same successor;
- two bindings of a cell map matched at a free key (threads, workers): two updates of different bindings commute (`MapHook.concat_element_comm`), and an update and the insertion of a fresh binding commute (`concat_element_comm_insert`); the same binding is one instance;
- each rule applied after the other with its own hypotheses (rules on disjoint cells);
- the joined states closed by `k2l_join_eq`: equal, or equal up to the commutativity and associativity of integer addition (two updates of a shared counter).

The map lemmas rest on the extensionality of canonical maps (`SAL.ext`: two sorted association lists with the same lookups are equal).
The pairs listed in `--open` (`RULE | RULE`) are the hand module's (`hand.pair.r₁.r₂`, of the same type).

The report (`--report`) classifies the unordered pairs without Lean.
At one binding (two free-key matches taken as the same, `pairs.rs`'s classifier with `same_binding`): `clash`, `exclusive`, `priority` (pairs of different ranks, which the stratified `Step` separates), and `overlap`, split by footprint into `overlap-independent` (neither rule writes a cell the other reads or writes) and `overlap-conflict`.
At two bindings of one cell map: `independent` (both update their binding and their footprints on the other cells are disjoint, so the map lemma commutes them), `conflict` (they race on a shared cell, named in `[races]`), and `map-structure` (a rule changes the map's bindings otherwise: a removal, a two-map concatenation).
The critical pairs are the `overlap-conflict`, `conflict` and `map-structure` ones; the footprints are untrusted, the Lean build is the check.

`demos/RaceConf` is the fixture `race` (`tests/fixtures/race`: workers in a cell map each add their count to a shared accumulator, one unit at a time; `spawn` inserts a worker with a fresh id): all 9 ordered pairs are generated and proved, `H = True` (a fresh id is not a key, which the insertion's own definedness says), and every schedule ends in one configuration.
SIMPLE's 169 rules would make 28,561 pair theorems, beyond a gate tier's budget (estimate, from the fixture's cost per pair; not measured); `--threads CELL` proves what is generic about them instead, once per rule rather than per pair (`demos/SimpleConf`, heavy tier, built against the library `simple`: 53 s on one module, 2026-10-28, load about 10; 57 s and 5.9 GB against the per-sort `simple-ps` before).
Each rule gets a view, read off its match: a `thread` rule updates one binding of the map in `CELL` (`TStep k t t' ch`: the binding `k` goes from `t` to `t'`, the other top cells change by `ch : Change`, per cell none or the value it has and the one it gets, `KPrelude.Ch`); a `shared` rule leaves the map as it is (`SStep ch`); the others are `global` (they insert or remove bindings or match two: on SIMPLE `spawn`, a thread's end, `rendezvous` and `read()`).
`view_of` proves every step is a step of some rule in its view, with the rule's rank and the priority side condition (`ViewOf`), from one frame lemma per rule; `Local` says the view's step is a step of `Step` wherever no rule of a rank before applies, so a view can be replayed after another step.
Two views commute when their changes are compatible (`Ch.Compat`: no cell written by one and read or written by the other, `apply_comm`): two updates of different bindings (`tstep_comm`), an update and a shared step (`tstep_sstep_comm`), two shared steps (`sstep_comm`).
Replaying needs the priorities to stay off: a rule of a rank `j` below the other's that applies after a step applied before it (`app_back`), which holds when the step changes no cell the rules of rank `j` read (`appSafe`, a table per class of change, `Cls`; a rule of rank `j` that reads the thread map is never safe).
`staticOK r₁ r₂` decides, from the rules' ranks, kinds, classes and these tables, the pairs that join this way (`join_static`), except two steps of one thread; those with keys that may be equal (`KeyPat`: the first item of the thread's `<k>`, its injection and its constructor when the rule's pattern fixes them; `KeyPat.disj_sound`) are the hypothesis `SameThreadJoins` (the determinism of one thread), and the pairs `staticOK` rejects are the hypothesis `OpenJoins`.
`terminal_unique_of (O : OpenJoins) (S : SameThreadJoins)` is the statement above with `H = True`; nothing in the generated module is quadratic in the rules.
On SIMPLE (`[threads]` in `simple-confluence.toml`): 158 thread rules, 7 shared, 4 global, 12 classes of changes; of the 28,561 ordered pairs, 1,699 are left in `OpenJoins` (1,304 with a global rule, 75 on cells one writes and the other uses, 320 where a step may enable a rule of a rank before), and 12,936 same-thread pairs in `SameThreadJoins`, many because a cooling rule's first item is a variable (the key could also read the item after it).
Of its 14,365 unordered pairs, 13,702 are separated at one binding (10,332 clashes, 2,705 exclusive, 665 of different ranks) and 12,545 commute at two threads; 678 are critical: 20 at one binding of a thread (17 pairs of heating rules of one strict operator: the order of evaluation of its arguments, which joins only after several steps, so SIMPLE needs `--join local` and a measure; the two `acquire` rules, the two `setEnv` rules, and a thread's end against `rendezvous`, which matches two threads), 16 at two threads racing on `store`, `busy`, `nextLoc`, `input`, `output`, `genv`, `terminated` or the fresh counter, and 642 with a rule that changes the thread map's bindings (`spawn`, a thread's end, `rendezvous`).
At one binding the classifier unifies the two bindings' keys whatever their shape when each side has one binding left (`element(k₁, v₁) = element(k₂, v₂)` forces `k₁ = k₂`), so a thread's end, matched at `<id> T </id>`, clashes with every rule whose thread's `<k>` is not empty (158 pairs; the `threadend` fixture of `tests/cli.rs`).
A data-race freedom hypothesis `H` would discharge the 16 races; the 20 and 642 need joins of several steps.

What would close the rest, class by class (a note; none of it is built):

- Strictness. SIMPLE's arithmetic, comparison, call and array operators are `[strict]`: their arguments are evaluated in either order, and an argument may have effects (`read()`, assignment, `++`, a call), so `print(read() - read());` prints different values for the two orders of the same input. SIMPLE is not confluent on all programs, and no measure or local-confluence argument changes that; the statement needs a program hypothesis `H` (no two arguments of one strict operator with conflicting effects, an effect analysis of the program preserved by `Step`, a kind 2 invariant built with the invariants area's tools), or a weaker statement for programs without it. Under such an `H` the 17 heating pairs of one binding join after both arguments are evaluated, several steps: `--join local` with a measure (the size of the thread's `<k>` with heated terms counted, decreasing on every step but `spawn` and the function calls, which a measure of the remaining program must cover).
- `SameThreadJoins`. Most of the 12,936 pairs never apply together: two keys with different constructors under one injection already refute them, and a cooling rule's key is a variable only because the value comes first (`V ~> freezer`); reading the item after it (the freezer) makes the cooling rules' keys disjoint from each other and from the heating rules. The rest are the pairs `pairs.rs` classifies at one binding: refuted in Lean by `cases` on the two matches (the classifier is untrusted), apart from its 20 overlaps: the heating pairs above, the two `acquire` rules and the two `setEnv` rules (one instance each when their side conditions exclude each other), and a thread's end against `rendezvous`.
- `OpenJoins`, global rules (1,304 pairs). `spawn` inserts a binding with a fresh id: an insertion view, commuting with an update of an existing binding by `concat_element_comm_insert` as in RaceConf, and with the fresh counter as a shared write. A thread's end removes a binding: a removal view, commuting with an update of another binding. `read() #aef085` (the input empty, the request to the stream) reads its thread's `<k>` and writes only `input`: a shared step guarded by one thread, commuting with the updates of other threads. `rendezvous` matches two threads: a view of two bindings, commuting with updates of the others. Each is a new kind with its commutation lemmas, linear in the rules.
- `OpenJoins`, cells (75) and priorities (320). The cells are the races of two threads on `store`, `busy`, `nextLoc`, `input`, `output`, `genv`, `terminated` or the fresh counter: a data-race freedom `H` (no two threads use one location of `store` where one writes; `nextLoc` and the fresh counter commute up to a renaming of locations and ids, an `E` coarser than `Eq` under `StepEquiv`). The priorities are the output stream's rules (`STDOUT-STREAM`, ranks 0 and 1, before the threads' rank 2): a thread step that writes `output` may enable a flush, so the two steps join only after it; local confluence with the length of the output buffer as the measure.

### 3.7 Noninterference (`noninterference`)

The statement (termination-insensitive): for a program `secure` at a labelling and two stores related by `lowEq`, two runs from `init P E₁` and `init P E₂` that both end in final configurations (`<k>` empty, `Final`) end in stores related by `lowEq`.
`secure` and `lowEq` are the hand module's; in `demos/ImpNI` they are the acceptance of the program's translation by a two-level security checker written in K (`demos/k/imp-sec.k`: `lev` the level of an expression, `sec` at a low program counter, `conf` for the confined branches of a high condition; library `impsec`, translation by `relate --roots`), and the agreement of two stores on the identifiers labelled `lo`, both stores holding values.
The reduction is `ProductInv.final`: a relation `Rel` on pairs of states from which, unless both are final, one side that is not final, or both, can be advanced by any of their steps without leaving `Rel` relates the final states of any two runs from related states.
`ProductInv.of_modes` builds it from three modes of `Rel`: `Sync` (both runs step), `Left` and `Right` (one run steps while the other waits, where a secret branch desynchronizes them), and `cover` (which mode a pair is in).
The generated module states `Obligations Rel Sync Left Right`, a structure of `init`, `final`, `cover` and one field per rule and mode (`sync:r`, `left:r`, `right:r`, stated with `Step.Rel`), and proves `noninterference` for every relation that satisfies it, `Final`, and that a final configuration has no step.

On kimp the structure has 240 fields (3 per rule for 79 rules, and 3).
Given the checker (`--checker-kore`, `--lev`, `--sec`, `--conf`: the level of an expression, the acceptance of a statement at a low program counter, its confinement under a high one), `noninterference` also generates the relation and discharges every field (`demos/ImpNI`: `obligations` and `kimp_noninterference`, the statement for kimp, on Lean's axioms only), in three modules around two hand modules:

- `Levels.lean`: `lev`, `sec`, `conf` at the semantics' terms (the checker's functions at the translation, `relate --roots`), and one inversion lemma per constructor, proved by one tactic: the checker's equations at that constructor in order, then its `owise` value, with the calls of the guards matched once (`soundness`'s emitter of §3.3, which also renders calls of the checker's other functions, `orBool` and `==K`); an equation whose labelling is a pattern (`lev(X:Id, X |-> L _)`) gets none, and the hand module states it (`lev_id`);
- `Stack.lean`: two stack typings of `<k>` in the style of §3.3's runtime typing, read off the checker and the cooling rules (`plug`, as §3.3 generates it): the low typing `lk` (every item is a low expression or a statement `sec` accepts, and a freezer is typed by plugging a low value into it) and the confined typing `CK G K` (the items above a continuation `K` assign only high identifiers, `conf`, with any expression); and three properties of a step, `CQ` (a step inside a confined stack stays confined and changes the store only at high identifiers), `SQ` (a step from a low stack leads to a confined stack over a low stack) and `SameQ` (from the same low stack and low-equal stores, the other run steps by the same rule, by `Step.deterministic`, to the same stack and low-equal stores);
- (hand, `Hand.lean` before `NI.lean`) `secure`, `lowEq`, the stores (`Good`) and `HiOnly` (a store that changes only at high identifiers);
- (hand, `Store.lean`) `hiOnly_refl`, `lowEq_symm`, `lowEq_hiOnly`, the store lemmas, and the per-rule cases listed in `--open` (`KIND RULE`, `KIND` one of `cq`, `sq`, `same`);
- `Proof.lean`: each property for every rule, by one tactic per property (compute both typings with the inversion lemmas, case on the values of `lev`, `sec`, `conf` where the computation stops, compute again) or the hand case, assembled by `Step.rel_of` (`cq_step`, `sq_step`, `same_step`); `Rel`, `Left`, `Right`; and every field: the 237 per-rule fields by one generic term each (`rel.r` from the property of every step), `init`, `final` and `cover` by fixed proofs.

`Rel` relates two configurations whose `<k>` cells are confined stacks over a common low stack `K`, with low-equal stores; `Left` is the left run inside its confined part, `Right` the right one once the left has reached `K`, `Sync` both at `K` (the same `<k>`).
A run leaves `Sync` only by a step into a high assignment or a branch on a high condition, which becomes the start of its confined part.
On kimp, 30 inversion lemmas are generated; of the 237 per-rule cases, 232 are generic, and the 5 hand cases are the rules that read or write the store (`CALC.var` in all three properties, `CALC.assign` in `CQ` and `SameQ`), as in §3.3 (the report `noninterference.toml` counts them).
The relation was first written by hand and then generated from what was uniform in it; the hand version's 12 s, 38 s and 2.0 GB compare with the generated modules, the hand modules and the examples: 15 s wall, 59 s of CPU, 2.4 GB peak (2026-10-25, Lean v4.34.0, shared 32-CPU host, load 12, on built libraries).

On the arity universe (the default; `--per-sort-terms true` writes the one type per sort modules, unchanged) five things differ, each because a family term is not an inductive type of its own: the inversion lemmas unfold the translation by its `k2l_tr` equations (as §3.3's); the case splits are `k2l_cases`, the value forms of a sort, in the typings' lemmas, the store's split (`KPrelude.Soundness.casesVar`, on a variable whose type computes to the store cell's sort) and the split on a level; `lk` and `CK` are defined by well-founded recursion on `SortK`, so their equations are proved by unfolding, not `rfl`, and the closer of `CQ` tries `HiOnly`'s reflexivity reducibly, since unifying it with an unfolding of `CK` does not end in Lean's default budget; and `Stack.lean` realizes `plug`'s equation lemmas itself: realized in `Proof.lean`, under Lean's default heartbeats whatever the file sets (§9), the fallback equation's side conditions, a family constructor against each cooling rule's, exceed it.
The hand module `Store.lean` uses `k2l_cases` where it cased on a value, and `lev_id` unfolds the translation by `k2l_tr`.
On the arity universe the same modules take 46 s wall, 494 s of CPU and 3.9 GB peak, `Proof.lean` 26 s of it (2026-10-28, Lean v4.34.0, cold modules on built libraries, load 22 to 32): the counts are the per-sort ones.

The statement is not vacuous (`ImpNI/Examples.lean`, `nonvacuous`): at a labelling with one high and one low identifier, the checker accepts a program whose branch on the high identifier writes only it, rejects an explicit flow (`l = h;`) and implicit flows through `if` and `while`, and the empty stores are low-equal; the checker's verdicts are computed through its inversion lemmas, since its functions are defined by well-founded recursion, which the kernel does not reduce.

`lowEq` includes that both stores are canonical maps whose identifiers hold values (`Good`), and so does the conclusion; without it a store could hold a statement, which a lookup would put on `<k>`.
The generation covers checkers of `imp-sec.k`'s shape: two levels (two constants, the low one read off an equation `lev(_:S, _) => lo` at a builtin sort, which also gives the low value `dflt`), a level function on the sort of the holes and two acceptance functions on one statement sort; any other shape is refused.

### 3.8 Claims that K's prover cannot state

`k2lean claims` (`crates/k2lean/src/claims.rs`, `lean/claims`) has three statements beyond the translation of K claims; their proofs are generic and checked by the kernel, like the claims'.

**Transfer along a bisimulation** (`KClaims/Bisim.lean`).
A strong bisimulation `R` between `S₁` and `S₂` relates states whose successors correspond in both directions, and the claim modalities look only at successors and at the target, so `AF.of_bisim : Bisimulation S₁ S₂ R → (∀ a b, R a b → P a → Q b) → R c d → AF S₁ P c → AF S₂ Q d`, its converse, and `AF_bisim_iff` when `P a ↔ Q b` on related states; `EF` and `Reach` likewise.
The all-path transfer needs both directions of the bisimulation (`fwd` gives the related state a successor, `bwd` sends each of its successors back), the one-path and reachability transfers only `fwd`.
`demos/ImpRelClaims` carries kimp's `sum-N` (proved by the generated claims, with `sum-loop` as a lemma) to the KRS IMP port through `relate`'s `ImpRel.bisim`, with the port's program written in the port's own constructors and no step of the port explored.
The continuation is a translated kimp continuation: `bisim` relates only translations, and the port has constructs kimp lacks.
`claims --transfer REL --transfer-target B --transfer-out FILE` carries every claim it proves the same way, one theorem per claim (`demos/ImpRelClaims/ImpRelClaims/Transfers.lean`: 18 of kimp's claims to the port): `∀ vars, hyps → REL.Inv lhs → AF B.Step (fun d => ∃ a, REL.R a d ∧ Q a) (REL.tr lhs)`, by `AF.image_of_bisim` (`EF.image_of_bisim` for a one-path claim) and the claim's own proof, where `REL.R a b` is `relate`'s relation `REL.Inv a ∧ b = REL.tr a`.
The target is the image of the claim's target, so no translation of the target predicate is needed; a statement in the port's own terms, as `sumN_holds`, is then a step of the same shape with the target's correspondence proved by hand.
The invariant at the left-hand side is a hypothesis: whether it holds depends on the left-hand side's store (an empty one satisfies it, `inv_unit`).
Along `refine`'s stuttering bisimulations (§3.5), one-path claims carry the same way (`KClaims/Stutter.lean`: `Reach.of_stutter` by induction on the path, `EF.of_stutter` by coinduction with the measure bounding the stuttering, both from the simulation alone, to the image target), but all-path claims do not in general: one step of the refined side may stand for several of the other, whose target may hold only at an intermediate state that nothing relates (the module's comment has a four-state counterexample); an all-path transfer needs a target that stays reached once reached.
It also holds when the refined side is deterministic. Each configuration then has at most one successor, so "some successor is in the set" and "a successor exists and every successor is in the set" are the same condition, and the two greatest fixpoints coincide (`AF_iff_EF_of_det`).
`claims --transfer REL --transfer-kind stutter` generates the one-path transfers (`EF.image_of_stutter`, an all-path claim through `AF.toEF`).
With `--transfer-det MODULE`, the module of the target's `B.Step.deterministic`, an all-path claim carries back to an all-path one. `gen` states that theorem only for a definition with no overlapping rules (§3.1), and the generator never checks it: a target without it fails to build.
`demos/ImpUnrollClaims` carries kimp's 18 proved claims to its unrolling variant `KUnroll` this way; the report's `[[transfer]]` entry counts the carried claims and the all-path ones (`carried`, `all_path`).

**Claims under a preserved invariant** (`--assume-invariant NAME`).
A claim generated with it is `∀ vars, hyps → NAME lhs → AF Step Q lhs`: it says nothing of a left-hand side outside `NAME`, so it is weaker than the K claim, and holds for every configuration reachable from one that satisfies `NAME`.
`NAME` is a predicate on the top cell with a theorem `NAME.preserved : Preserved Step NAME` (`--invariant-preserved`), declared in `--invariant-module` (default: the kind 1 invariant of `gen --invariant`, `Invariant` in `NS.Invariants`).
The proof is `AF.circularity_inst_inv` with the target strengthened to `NAME d ∧ Q d`, so that the state a circularity or a proved claim leads to satisfies `NAME` too; `kc_auto … inv [NAME.preserved]` steps by `AFn.of_rule_inv`, which puts `NAME` of the successor in context (`hinv`), carries it through Boolean splits and claim applications, and, where no rule applies, opens a copy of it (the `kc_inv` simp set: the unfolding set of the kind 1 invariant, read from `--invariant-unfold`, by default the `invariant-unfold.txt` that `gen --invariant` writes beside the library, and the collections' `toList`; then `kc_inv_fns`, the functions it calls) and splits on a projection it constrains (`proj_KItem_Value x`: the case `none` contradicts the invariant, in the case `some y` the variable `x` becomes the injection of `y`).
Sound because `Preserved` is a theorem: every state on a path from a state satisfying `NAME` satisfies it, which is all `AF.circularity_inv` assumes.

**Termination of a sublanguage** (`--induction FILE`).
FILE names a syntax sort, classes of the sublanguage with the sort of their values, and typings of constructors (`demos/claims/kimp-expr-eval.toml`: kimp's arithmetic and Boolean expressions without variables or division).
The generated module states the sublanguage as an inductive predicate `Sub cl e`, one obligation per typing ("if the arguments are in their classes and each, in any continuation, reaches a value of its class, the constructor's term does"), and `holds : Sub cl e → ∀ K cells, Reach Step (Target cl K cells) (cfg e K cells)` by induction on `Sub`, with the obligations of the open list as hypotheses.
`Reach` is a finite path to the target: total correctness, not the partial correctness of `AF`; with a deterministic `Step` it says that the run terminates in a value.
The induction hypotheses are claims over strict subterms, so the tactic may apply them anywhere, not only after a step as a circularity.
An obligation is closed by `kc_auto using [ih…] split`: where no rule applies it splits a variable of a type with at most 8 constructors, none of which has a field of the type itself (an argument expression into value and compound), refutes the cases whose `Sub` hypothesis no constructor of `Sub` can prove (inversion), and drops the Boolean cases whose arithmetic hypotheses contradict each other.
The `split` behaviour is off for the translated K claims, so their proofs and statistics are as before.

**Leaves read from a cell** (`[[leaf]]` in FILE; `demos/claims/kimp-expr-vars.toml`: kimp's expressions with variables).
A leaf `{ class = "AExp", sort = "SortId", cell = "env" }` types the values of a subsort of the syntax sort (kimp's identifiers) by a child cell of the top cell whose content is a map.
`Sub x cl e` then takes that cell `x` as a parameter, and the leaf is a constructor `AExp.env`: `Sub x .AExp (inj i)` when `x = <env> m`, `m` is well formed and binds `i` to a value of the class's value sort (`lookup m (inj i) = some (inj v)`).
`cfg` and `Target` are as before, with the cell among the other cells; `Inst` and `holds` fix it to the parameter: `holds : Sub x cl e → ∀ K cells, Reach Step (Target cl K x cells) (cfg e K x cells)`.
The leaf is one more obligation, closed by one step and the target: the step is the constructor of `Step` that unifies with the configuration (kimp's `var`), whose map pattern holds since a well-formed map that binds `i` is `i |-> v` concatenated with its `remove` (`MapHook.concat_element_remove`).
`kc_auto` does not find that step, because it evaluates each rule's matcher, which tests `wfb m` and `lookup m (inj i)` and does not reduce on the map variable `m`; a definition whose lookup rule has another premise has the leaf obligation fail, to be listed as open.
The compound obligations close as before: an argument that is an identifier is a case of the split, and its induction hypothesis applies where it is evaluated.
No separate check that an expression's rules leave the cell alone is needed, because `Target` states it: an obligation whose rules write the cell does not close, and is open.
No invariant is assumed either: the leaf's premise is what types the value that `var` reads, so the theorem applies to any configuration whose cell gives the variables of `e` their classes (an invariant such as kimpinv's `envOk` is one way to establish that, outside the statement).
Statements are the next sublanguage, not built: they write `<env>`, so their `Target` has the cell's new content existentially, with a typing of it for the statements after (a typing environment in `Sub`, as soundness's `kty` has).

Measured on 2026-10-24 (Lean v4.30.0, shared 32-CPU host, load 15 to 35, each module built on its own after its dependencies):

| statement | result | module build |
|---|---|---|
| `sum-N` transferred to KRS IMP (`demos/ImpRelClaims`) | proved by a 3-line proof (`AF.of_bisim`) | 0.8 s |
| `copy`, `copy-loop` under kimpinv's `envOk` (`generated/kimpinv-claims`) | both proved generically (10 and 47 configurations); both false over kimp (`krust kprove` fails them, `Hand.copy_false`, `Hand.copy_loop_false`) | 4.7 s, after the rest of kimpinv's library (138 s wall, 125 s CPU, 3.8 GB) |
| kimp's expressions without variables or division (`ExprEval`) | 15 of 15 obligations closed, `holds` unconditional | 2.5 to 3.9 s |
| with `_/_` (`ExprDiv`) | its obligation does not close (4 goals left at `i / j`), and is false (`Hand.expr_div_false` at `1 / 0`) | under 1 s |
| with variables, read from `<env>` (`ExprVars`; 2026-10-25, Lean v4.34.0, load 19) | 17 of 17 obligations closed (the two leaves by one `var` step each), `holds` unconditional | 4.1 to 4.7 s |

kimpinv's invariant now also conjoins `storeNoIds` (no store value is an `Id`), so the two claims assume both parts, though their truth needs only `envOk`.

## 5. Rule names

A rule's name, which names its `Step` constructor and every case derived from it, is its K label when it has one, else the focus of its left-hand side in K syntax (`«X + Y»`), with variable sorts and then a digest of the rule only when names collide; the source position is a doc comment.
So inserting lines or unrelated rules renames nothing, and a hand proof refers to a rule by a name that changes only when the rule does (`invariants.md`, §7.1).

## 6. The KRS sidecar

KRS declares the element sorts of collection cells (`env: Map<Id, Value>`), which KORE does not carry: the compiled `Map` maps `KItem` to `KItem`.
`k2lean gen --sidecar FILE` reads them from a JSON file keyed by KORE names and makes each declared cell a part of the invariant, so the declared type becomes a theorem (`Preserved Step Invariant`) rather than a check.

Format `k2lean-krs-sidecar`, version 1, a JSON object:

| key | value |
|---|---|
| `format` | `"k2lean-krs-sidecar"` (required) |
| `version` | `1` (required) |
| `producer`, `definition` | free text, for people (optional) |
| `cells` | an array of declared cells |

Each declared cell:

| key | value |
|---|---|
| `cell` | the cell's KORE symbol, as in `definition.kore` (`Lbl'-LT-'env'-GT-'`) |
| `krs` | the KRS declaration, copied into the generated documentation (optional) |
| `collection` | `"Map"`, `"List"` or `"Set"`: the builtin collection sort of the cell's content |
| `key`, `value` | for a `Map`: the declared KORE sorts of keys and values (`SortId`, `SortValue`) |
| `element` | for a `List` or a `Set`: the declared KORE sort of elements |

For a declared cell the generated part says that every binding (element) has the declared sorts, where "a `KItem` `t` has sort `S`" is `∃ y, proj_KItem_S t = some y`: the projection is defined exactly on the injections of values of `S` and of its subsorts.
The generator refuses a cell that is not in the definition, whose content is not the named collection, whose sorts are unknown or not subsorts of the collection's element sort, or that lies inside a cell collection; nested arguments (`Map<Int, Set<Int>>`) have no field in version 1.
`krs build` writes it as `k2lean-sidecar.json` beside `definition.kore` (`krs/crates/krs-cli/src/command.rs`, from the configuration cells of the Definition IR, `declared_cell_types`): one entry per leaf cell whose content is a `Map`, `List` or `Set` with declared element sorts that are not collections with arguments of their own, outside every repeated (`*`) or optional (`?`) cell, keyed by the KORE names k-rust's compilation gives the cell's label (`Lbl'-LT-'env'-GT-'`) and the element sorts (`SortId`); `producer` is `krs build`.
The recorded `demos/k/krs-imp/k2lean-sidecar.json` is its output for KRS IMP (`krs/tests/imp/rust-definition`); the library generated from it equals, file for file, the one generated from the hand-written file it replaces.

## 8. Limits

- Not every KORE construct is supported: `k2lean survey` lists what a definition uses that the generator does not; an unsupported construct is an error, not an approximation.
- Function equations with map patterns in their arguments (bound or free keys) are not stated as theorems in `Equations.lean`; a free-key set pattern `SetItem(X) REST` in a recursive function has no termination facts (`MapSizeOf` covers map carriers only), so its termination is Lean's own search or a `--termination` entry.
- Determinism is not generated for definitions with several-match rules; `uniqueAt c` checks it at one configuration.
- Recursive functions on lists close only in the fold shape `k2l_fold_eqn` recognizes; other equations the tactics cannot prove stay open obligations (`generated/*/open-obligations.txt` lists them per library).
- Equations of hooked functions are stated for well-formed set and map values only (§3, "Well-formedness premises"): `S1 |Set S2 => S1 (S2 -Set S1)` is false at a carrier value that is not a set (an unsorted list, or one with a repeated element), where `_Set_` is undefined and `|Set` is not (`SetHook.union_eqn_not_wf`), and is proved under the premise.
  The carriers keep their values that are not K values; making them subtypes, so that well-formedness holds by construction and the premise disappears, is an open design question.
  Equations of generated functions and simplification rules are stated without the premise.
- One equation of `domains.md` is false in this model, so it stays open in every library that has it; `KPrelude.HookLaws` proves the counterexample.
  `countAllOccurrences` equation 2 fails at an empty `ToCount`: its condition holds there (`findString(S, "", 0)` is `0`) and it reads `countAllOccurrences(S, "") = 1 +Int countAllOccurrences(S, "")`, which no total function satisfies (`domains.md` declares `countAllOccurrences` `total`).
- The limits of the invariant tooling are in `invariants.md`, §9.
